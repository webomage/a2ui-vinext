# w0m Ecosystem — Full-Spectrum Audit

**Date:** 2026-06-13
**Scope:** Full ecosystem (excl. vendored `wom7mlx`): `wom7web`, `wom7api`, `wom7cfworkers`, `wom7ext`, `wom7sec`, `wom7swarm`, `wom7skills`
**Method:** Applied the w0m skill arsenal — `security-guardrails` (Trail-of-Bits secure defaults), `torvalds` (pragmatic architecture review), `w0m-review` (readability/maintainability), `observability-instrumentation`, and `doubt-driven-development` (adversarial verification of every P0/P1 below).

> Each subproject is its own git repo on branch `beta`. Findings cite `path:line`.

---

## Executive summary

The ecosystem is functionally rich but has **critical security exposure that requires same-day action**. The single most urgent item is a set of **production secrets committed to git**. Two independent authentication-bypass classes exist on Supabase Edge Functions, and several data tables are effectively world-readable/writable.

Code quality is mixed: a correct, well-designed auth/CORS foundation exists in `_shared/`, but several functions bypass it with hand-rolled, insecure variants. Test coverage and CI are near-absent for the size of the codebase.

| Severity | Count | Theme |
|---|---|---|
| **P0 Critical** | 4 | Committed secrets · JWT signature bypass · public RLS on PII · service key shipped in extension |
| **P1 High** | 3 | Unauthenticated AI endpoints · open swarm API · extension content-script XSS |
| **P2 Medium** | 5 | Wildcard CORS · god-components & duplication · `any` sprawl · no CI · thin tests |
| Good | — | `_shared/cors.ts`, `requireAuth.ts`, `checkBearer`, gitignored `dev_secrets.json` |

## P0 — Critical (act today)

### P0-1 · Production secrets committed to git (`.env.bak` ×3)
**Where:** `wom7web/apps/cp/.env.bak`, `wom7web/apps/join/.env.bak`, `wom7web/apps/web/.env.bak`
`.gitignore` excludes `.env` but **not** `.env.bak`, so these backups are tracked (present in history; 2+ commits).

`apps/join/.env.bak` (83 lines) leaks, among others:
- `AWS_ACCESS_KEY` (`AKIA…`) + `AWS_ACCESS_SECRET`
- `SUPABASE_SERVICE_ROLE_KEY` (full DB, RLS-exempt master key)
- `DATABASE_URL` (direct Postgres connection string)
- `GITHUB_APP_PRIVATE_KEY`, `GITHUB_APP_CLIENT_SECRET`, `GITHUB_APP_WEBHOOK_SECRET`, `GITHUB_TOKEN`
- `GEMINI_API_KEY`, `COHERE_API_KEY`, `CF_RUNTIME_API_TOKEN`, `HUME_API_KEY`/`HUME_SECRET_KEY`
- `CRYPTO_KEY`, `CRON_SECRET`, `DEBUG_BYPASS_KEY`, `HCAPTCHA_SECRET`, `WORKERS_WEBHOOK_SECRET`
- `ADMIN_PASSWORD`, `MEMBER_PASSWORD` (**plaintext**)

**Impact:** Total compromise. The service-role key + `DATABASE_URL` alone grant unrestricted DB read/write, making every RLS control below moot. AWS keys and the GitHub App private key extend blast radius beyond this project.

**Remediation (in order):**
1. **Rotate every credential** in all three files — assume all are burned. (AWS, Supabase service-role, DB password, GitHub App key + secrets, all third-party API keys, admin/member passwords.)
2. Remove the files from the working tree and add `*.env.bak` (and `*.env*` except `*.example`) to each `.gitignore`.
3. **Purge from history** (`git filter-repo` / BFG) and force-push — deletion in a new commit is not enough; they remain in history.
4. Adopt the existing pattern: secrets via env/Infisical only (this repo already uses `dev_secrets.json`, correctly gitignored — follow that everywhere).

### P0-2 · JWT signature never verified → admin auth bypass (CWE-347)
**Where:** `wom7api/supabase/functions/admin-todos-api/index.ts:40-71`, `wom7api/supabase/functions/admin-invite-candidate/index.ts:73-103`
Both run with `verify_jwt = false` (`wom7api/supabase/config.toml`) — the gateway does **not** validate the token. Inside, each splits the JWT and `JSON.parse(atob(parts[1]))` to read claims **without verifying the signature**:
- `admin-invite-candidate` then trusts `claims.app_metadata?.role === "admin"` / `claims.role === "service_role"` and proceeds using the **service-role** Supabase client.
- `admin-todos-api` passes the forged `claims` into `withRls()` → `_shared/database/db.ts:31` runs `set_config('request.jwt.claims', <attacker JSON>)`, then executes CRUD.

**Impact:** Any unauthenticated caller forges a payload (`{"app_metadata":{"role":"admin"}}`) with a garbage signature and gets admin-level behavior: read/write `admin_todos`, invite candidates / create users, and drive RLS context from attacker-controlled claims.

**Remediation:** Delete the hand-rolled decode. A correct helper already exists — `_shared/requireAuth.ts` `requireAdminAuth()` calls `supabase.auth.getUser()` (verifies signature) and checks the `user_roles` table. Use it. Keep `verify_jwt = true` unless a function has a deliberate, documented reason and its own verified check.

### P0-3 · Public read/write RLS on PII tables
**Where:** `wom7ext/supabase/migrations/20251210170000_init_wom7ext.sql:19-20`, `wom7ext/supabase/migrations/20251219030000_add_missing_tables.sql:26-28`
```sql
-- Policies (for local dev, allow all - specifically for anon key)
create policy "Allow all access" on freelancers   for all using (true) with check (true);
create policy "Allow all access" on agencies        for all using (true) with check (true);
create policy "Allow all access" on jobs            for all using (true) with check (true);
create policy "Allow all access" on proposals       for all using (true) with check (true);
create policy "Allow all access" on linkedin_profiles for all using (true) with check (true);
```
Tables store scraped profile data (`data jsonb` — PII). `for all using(true)` with no `to` clause applies to the `public`/`anon` role. The Supabase **anon key is public by design** (and is hardcoded in `wom7web/apps/{web,cp}/src/components/ChatApp.svelte:11`).

**Impact:** Anyone with the anon key (i.e., anyone) can read and overwrite all freelancer/agency/job/proposal/LinkedIn-profile rows. The migration comment says "for local dev," but migrations apply in production.

**Remediation:** Replace with least-privilege policies scoped by `auth.uid()` / role; gate writes to service-role or authenticated owners. If these tables are only ever written server-side (service role), remove anon policies entirely. (`wom7web/db/technologies_schema.sql:79-92` has the milder version — any *authenticated* user can write the global tech catalog; tighten too.)

### P0-4 · Supabase **secret** key shipped in the browser extension
**Where:** `wom7ext/extension/src/services/supabaseService.ts:19`
In production mode (`EXT_MODE !== "local"`) the extension's Supabase client is created with a **secret** key:
```js
SUPABASE_ANON_KEY = "sb_secret_<REDACTED 2026-09-02 — real service key, removed before this file entered version control>";  // line 19 — NOT an anon key
```
`sb_secret_*` is Supabase's service/secret key format — it bypasses RLS entirely. It is bundled into the distributed extension and committed to git. Anyone who unpacks the extension (trivial) gets full, RLS-exempt database access. (Line 13 uses the correct `sb_publishable_*` key, but only in `local` mode.)
**Impact:** Full DB compromise via any installed extension. This is also *why* the P0-3 `using(true)` policies "worked" — the client was handed a master key, so RLS was never the gate.
**Remediation:** Use the `sb_publishable_*` key in all modes; rely on RLS + Supabase auth for access. Move privileged writes (scraper caches) to a service-role **edge function** rather than letting the client hold a secret key. **Rotate the leaked `sb_secret_` key immediately.** Needs an architecture decision (see Remediation status).

## P1 — High

### P1-1 · Unauthenticated AI edge functions (cost abuse / prompt injection)
**Where:** `wom7api/supabase/functions/agent-architect/index.ts`, `…/news-post-generator/index.ts` (both `verify_jwt = false`, no internal auth — only a `playwright-test` mock bypass that, notably, keys off the now-leaked `E2E_ACCESS_SECRET`).
**Impact:** Anyone can POST and trigger LLM generation on your account — quota/cost exhaustion, arbitrary content generation, prompt-injection surface. **Contrast:** `chat-internal` *is* protected (`x-internal-key`), and `agent-consultant` has guards — so the fix pattern already exists in-repo.
**Remediation:** Require auth (`requireAuth`) or an internal-key/quota gate before `routeChat`.

### P1-2 · Open agent-swarm API
**Where:** `wom7swarm/main.py` — FastAPI `POST /architect` (and helpers) have **no authentication**; the endpoint spins up an autonomous multi-agent run (`enable_subagents=True`).
**Impact:** If deployed publicly (`deploy.py`), unauthenticated callers trigger expensive recursive agent runs.
**Remediation:** Add an API-key dependency / network restriction before exposing.

### P1-3 · DOM-XSS sink in extension content script
**Where:** `wom7ext/extension/src/content/specEngine.ts:142`
```js
overlay.innerHTML = `… <p><strong>Action:</strong> ${payload.actionId}</p>
  <textarea …>${payload.result}</textarea> …`;
document.body.appendChild(overlay);
```
`payload.result`/`payload.actionId` are interpolated unescaped into `innerHTML` and injected into the host page from a content script. A `</textarea><img src=x onerror=…>` payload breaks out and executes in page context.
**Impact:** DOM XSS in a privileged content-script context on LinkedIn/Upwork pages.
**Remediation:** Build the overlay with `createElement` + `textContent`, or escape before interpolation. Same class (lower severity, admin-only): `wom7web/apps/cp/src/components/admin/BlueprintEditor.svelte:156` injects `blueprint.diagram_mmd` into `innerHTML` before `mermaid.run`.

## P2 — Medium

- **P2-1 · Wildcard CORS on edge functions.** `linkedin-oauth`, `linkedin-share`, `github-repos`, `gamification-ingest`, `upwork-poller` inline `"Access-Control-Allow-Origin": "*"` instead of the well-documented `_shared/cors.ts` `makeCorsHeaders()`. Lower severity (no `Allow-Credentials`, so browsers won't attach cookies), but inconsistent with the project's own stated rule. Route all non-public functions through `makeCorsHeaders()`.
- **P2-2 · Hardcoded Supabase anon key** in `ChatApp.svelte:11` (both apps). Public-by-design, but inline-hardcoding blocks rotation and duplicates across apps — move to `PUBLIC_SUPABASE_ANON_KEY` env.
- **P2-3 · God-components & cross-app duplication** (`torvalds`/`w0m-review`). `TeamManager.svelte` (1,723 lines), `ResourceLibrary.svelte` (1,323), `PageManager.svelte` (1,250), `ProjectManager.svelte` (1,030). `TemplateManager.svelte` and `ChatApp.svelte` are duplicated near-identically across `apps/web` and `apps/cp` — extract to a shared package.
- **P2-4 · Type-safety erosion.** ~1,373 `any`/`as any`/`<any>` and 25 `@ts-ignore`/`@ts-nocheck` in app source. Each `any` is a data-structure the compiler can no longer protect (`torvalds`: "worry about data structures").
- **P2-5 · Tests & CI near-absent.** ~15 test/spec files for ~1,200 source files; **no GitHub Actions workflows in any repo** (`.github/workflows` absent everywhere). With the security issues above, nothing gates regressions. Add at minimum: secret-scanning (gitleaks) + typecheck + the existing vitest/Gauge suites on push.

## Fact-check & deeper pass (2026-06-15)

### Facts verified (against source via the Read tool — Bash/grep was mangling identifiers)
- **P0-2 fix is safe.** `user_roles` SELECT policy (`20260112200000_rbac_setup.sql`) has a bootstrap `OR user_id = auth.uid()` clause, so `requireAdminAuth` can read the caller's own role — admins keep access, non-admins are denied. No lockout, no recursion.
- **Corrected an earlier wrong claim:** the `/n` endpoint was a grep-display artifact. ChatApp actually calls **`agent-consultant`** (chat) and **`agent-architect`** (helper) — `agent-architect` *is* the public path, so rate-limiting (not hard auth) was the right call. `news-post-generator` is the cron/admin tool, not the public chat.
- **Rate-limit infra is real:** `ai_usage` table + `get_user_daily_tokens(...)` `SECURITY DEFINER` RPC exist (`20260110220000_ai_infra_upgrade.sql`). `agent-consultant` already throttles via `chat-core` under `web:<ip>`.
- **`verify_jwt=true` is not authorization** — the public anon key is a valid JWT, so it only blocks no-key requests; real authz must live inside each function.

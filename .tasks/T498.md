# T498 — Resume Studio writes real resumes: curated highlights with role and tech tags

## Summary

Owner report (2026-09-29): Resume Studio generates versions in different styles, but each one only lists work-history
titles. The intent was well-written resumes where each version accents different positions.

**Measured cause.** Studio builds every version from `profile_experience`: 95 rows, all Upwork contract titles, 0 with a
description, 0 with skills. The ranking (`synthesizeResume`) scores keywords in title, description and skills, so it can only
reorder titles. The 21 stored documents carry `parsed_data = {type, title}` only. The curated content already exists in
`project/data/cv/resume.json` (29 employers and engagements, Webomage alone has 27 highlights) and Studio never reads it.

Split from [[T484]] (which fixed promotion and seeded the document library, and never touched what the generator writes from).

## Owner decisions (2026-09-29, "Go")

1. Curated highlights live in a new per-profile table `public.profile_cv_facts`, one row per employer, loaded from `resume.json` by
   an owner-run script. Not into `profile_experience.description` (a different grain: 95 contracts against 29 employers).
2. Tags are PROPOSED by a script and APPROVED by the owner in a diff (`project/data/cv/highlight-tags.json`).
3. Phase 1 (this ticket): load the facts and rank highlights by tag so the same content is accented differently per role and tech.
   Phase 2 (a follow-up ticket): role-specific summary text and skill groups, plus a "why this version" panel.

## Definition of Done

- Generating the DevOps version and the AI-infrastructure version for the owner's profile produces DIFFERENT top bullets for the same employer, and every bullet is a verbatim line from `resume.json`.
- Nothing from `x_private` or `x_engagements` (phone, earnings, client feedback) exists in `profile_cv_facts` after a live load: a query for those keys returns 0 rows.
- The masked version of a resume contains no company name from the facts table, in headings or in bullet text.
- A different signed-in member reads 0 rows from the owner's facts.
- The owner has opened `/me/profile/resume` and seen employers with written bullets instead of contract titles.

## Status notes (build, 2026-09-29)

- Built test-first: `packages/lib/src/resume` (`curated-highlights.spec.ts`, `highlight-tags.spec.ts`: 41 tests), Studio component tests (4 new, mock made table-aware), loader tests (17, `just cv-facts-load-test`). `just typecheck` 0 errors; mypy clean.
- Findings the tests caught: (1) masking only the registered company name missed the short form in prose ("VXG Inc" vs "VXG's"), so the legal suffix is now stripped as a second form; (2) a `\p{L}` inside a template literal silently lost its backslash and the whole-word guard never applied; then semgrep refused any dynamic `RegExp` (ReDoS), so masking is a plain scanner that fails closed if case folding changes the length; (3) semgrep refused SHA-1 for the highlight id: both sides use SHA-256 now, with one pinned vector asserted in TypeScript and Python.
- Data facts: `resume.json` has 29 employers and 206 highlights; the proposer tags 120, and excludes 7 written in Cyrillic (status `excluded`, reversible). About 6 more look Spanish and are NOT auto-excluded: the owner decides while approving. Dry run of the loader on the real file: 29 employers, 199 highlights, 0 approved tags.
- Known limits: masking covers company names known to the facts table only (a client named only in a bullet, or an Upwork client, is not masked); the keyword proposer is crude (`webrtc` lands on storage and video bullets), which is why approval is a human step; Studio still prints contract titles for a member with no curated facts, with a notice.
- Migration proven on a scratch Postgres with stubbed `profiles` and `current_profile_id()`: owner reads own row only, another member and "no profile" read 0, authenticated insert/update/delete and anon are denied, the constraints (array, date order, unique key) fire, service-role upsert works.

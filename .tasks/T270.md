# T270 — one small skill, and the question of what "default" means here

## Summary

Owner direction 2026-08-23: *"I added eli5 community skill from claude community but let's include
it also in common standard default skills set for projects after deeper review for security and
upstream"*.

**Measured the same day, read-only:**

| | |
|---|---|
| installed as | a **plugin**, at `~/.claude/plugins/marketplaces/claude-community/eli5` |
| marketplace | `anthropics/claude-plugins-community` (GitHub) |
| contents | **three files** — `README.md`, `.claude-plugin/plugin.json`, `skills/eli5/SKILL.md` |
| `SKILL.md` | **321 bytes** |
| licence · author | **MIT** · Thariq Shihipar |
| scripts, network, exec | 🟢 **none** — no `curl`/`wget`, no URL, no `bash`/`exec`/`eval`, no `npm`/`pip`, no token or key reference |
| what it does | emits an HTML explainer artifact; `description` triggers on `/eli5 <topic>` |

⇒ **The security half of the ask is close to answered and the answer is "clean".** 321 bytes of
prose with no executable surface is about as small a review as this estate will ever do. AC1 still
records it properly rather than letting this summary stand as the review.

🔑 **The governance half is the real ticket, and it is bigger than the skill.**

## Three things the ask runs into

**1. A plugin is not a governed skill.** [[T127]] governs skills through `.w0m/skills.json` +
`.w0m/skills.lock.json`, with **fully-qualified** provenance (`owner/repo@skill` — a bare name is
rejected) and a content hash. `eli5` arrived through the **marketplace/plugin** channel, which sits
entirely outside that. Today the estate reads **87 installed / 77 managed / 0 unmanaged**; a plugin
skill is a fourth thing, governed by neither `skills.json` nor `exclude`.
⚠️ Its `plugin.json` carries `name`, `version` and `author` but **no repository field** — so the
fully-qualified provenance T127 demands has to come from the marketplace record, not the artefact.

**2. There may be no "default set" to add it to.** The nearest existing concept is
`project/skills-policy.json → recommended`, and that is **tech-triggered**: a skill is recommended
because `stacks-policy.json` detected `dep:<name>`. `eli5` is triggered by nothing technical — it is
useful on any project regardless of stack. ⇒ Adding it needs either **a new "unconditional default"
concept** or a decision that the recommendation model does not cover skills like this. **Do not
invent the concept quietly by wedging eli5 into `recommended` with a fake detector** — that is the
shape [[T135]] keeps catching.

**3. It renders HTML, and this estate has a design system.** The skill's output is an HTML artifact
with *"big visuals and few words"*. The canonical DS is `wom7web/design-system` and the runtime one
is `packages/ui`, and [[T183]] is currently establishing whether a project even declares a DS. An
explainer that emits styled HTML outside that is a small, real inconsistency — worth **naming and
accepting** rather than discovering later. It is not a reason to decline the skill.

## 🔴 A SECOND `eli5` — and it is not a version of the first

Owner ask 2026-08-23, added after filing: *"let's also add into that ticket about eli5 research of
this repo — https://github.com/DreambigOu/ELI5"*.

Fetched the same day:

| | installed (marketplace plugin) | **DreambigOu/ELI5** |
|---|---|---|
| what it does | *"a dead-simple HTML picture explainer with big visuals and few words"* | *"explains anything to anyone — kids, managers, engineers, parents. Adapts tone, vocabulary, analogies, and framing to match the audience"* |
| size | **321 bytes**, one `SKILL.md` | `skills/eli5/` **plus** `eli5-workspace/` — an evaluation framework with test cases |
| stack | prose only | prose + a **Python** evaluation system |
| author | Thariq Shihipar | DreambigOu (andrewou.pages.dev) |
| distribution | `anthropics/claude-plugins-community` marketplace | a **standalone GitHub repo** — no marketplace |
| traction | — | **258 stars · 9 forks · 10 commits**, no open issues or PRs |
| licence | MIT | MIT |
| self-reported eval | — | **83.3% pass with the skill vs 41.6% baseline** |

🔑 **These are two different skills wearing one name.** The first renders a picture explainer; the
second calibrates an explanation to a named audience. Neither is a fork or a version of the other.
⇒ **This is [[T135]]'s recorded trap arriving in the open**: *a shared skill name may mean two
DIFFERENT skills — resolve by content diff, never by name.* That rule was written after a
name-match reported *"22 of 22 are upstream, done"* while a blob-SHA comparison said **18 of 23
differed**. Here the collision is not subtle and there is no excuse for merging them by name.

⚠️ **The audience-adaptive design is the better fit for the stated purpose**, on the face of it —
*"a common standard default skills set for projects"* implies explaining w0m's own systems to
different readers, which is the second skill's whole subject and not the first's. That is a
reason to compare them properly, not a reason to swap.

🔬 **It ships its own eval harness, and that cuts both ways.** A skill carrying test cases and a
measured pass rate is unusual and genuinely valuable — this estate keeps finding gates that were
never observed failing. **But 83.3% vs 41.6% is the author's own number, self-reported, with the
author's own rubric.** The estate's standing rule applies without softening: a recorded measurement
is a claim with a method. **Re-run it or discount it; do not repeat it.**

⚠️ **A repo is a wider surface than a manifest.** The first skill's review was three files and 321
bytes. This one carries Python that runs — `eli5-workspace/` is an evaluation framework, and
evaluation frameworks execute things. **AC1's "zero executable surface" finding does NOT transfer**,
and AC8 exists to stop it being assumed.

## Acceptance criteria

- [ ] AC1 — **The security review is recorded, not assumed.** Re-read all three files and record:
      no executable surface, no network egress, no filesystem writes outside an artifact, no
      credential access. 🔑 **Review the pinned CONTENT, and hash it** — [[T135]]'s standing rule is
      *resolve by content diff, never by name*, and a marketplace entry can change under a stable
      name. The hash is what makes the review mean something later.
- [ ] AC2 — **Upstream is identified to T127's standard.** Fully-qualified provenance
      (`owner/repo@skill`), the marketplace commit or version pinned, the licence recorded, and a
      statement of who can change it and how a change would reach us. ⚠️ `plugin.json` has no
      repository field; the marketplace record is `anthropics/claude-plugins-community`, and the
      **author is an individual contributor** — Anthropic hosting the marketplace is not the same as
      Anthropic authoring the skill, and the review must not blur the two.
      🟢 **MEASURED 2026-08-23 (owner asked: "do we have sources of community version of eli5?").
      Yes — but it is VENDORED, not linked.** The marketplace entry reads `"source": "./eli5"`, a
      relative path *inside* the marketplace repo, so there is **no independent upstream** to track:
      | fully-qualified | `anthropics/claude-plugins-community@eli5` |
      | pinnable commit | **`f4c9452f5ca091f1be7064d9faab1b001ea21645`** (2026-08-21) — also marketplace HEAD |
      | local | `~/.claude/plugins/marketplaces/claude-community/eli5` (a real git checkout) + a copy under `plugins/cache/` |
      ⇒ The only pinnable reference is a **marketplace** commit, which moves whenever *any* plugin in
      that repo changes — pinning `f4c9452` pins the whole catalogue, not this skill. 🔑 **That is a
      real difference from `DreambigOu/ELI5`**, which is its own repo and can be pinned on its own,
      and it belongs in AC9's comparison rather than being discovered during adoption.
- [ ] AC3 — 🔴 **Decide what "default skill set for projects" IS, before adding anything to it.**
      Either extend `skills-policy.json` with an unconditional-default tier, or record that
      stack-triggered recommendation is the only model and eli5 is adopted a different way. **A
      fabricated `detect:` rule to make an untriggered skill look triggered is not acceptable** —
      it makes the registry lie about why the skill is there.
- [ ] AC4 — **The plugin↔governed-skill relationship is stated.** Is a marketplace plugin brought
      under `.w0m/skills.json`, mirrored into `.agents/skills`, or declared in `exclude` with a
      reason the way the 10 openspec skills are? **All three are defensible; none may be implicit.**
      Whatever is chosen must survive `just skill check`.
- [ ] AC5 — **Adoption is proven by the gate, not by the file.** After adoption
      `just skill check` passes and the installed/managed/unmanaged counts are re-measured and
      recorded. An adopted skill that leaves an `unmanaged` count behind has not been adopted.
- [ ] AC6 — **The DS inconsistency is recorded**, in one line, linked to [[T183]]: eli5 emits HTML
      that does not come from `packages/ui`. Accept it or scope it — do not leave it unremarked.
- [ ] AC7 — **It propagates to projects the declared way, or not at all.** If eli5 becomes a default,
      say how an existing project gets it — `just skills-sync`, the client import path ([[T182]]),
      or nothing — and confirm against a real project. 🔴 [[T177]] is the standing case of a fix that
      *"stops at the estate boundary"*: a default that only exists in w0m is not a default.
- [ ] AC8 — 🔴 **Review `DreambigOu/ELI5` as its own artefact, at a repo's standard, not a
      manifest's.** It contains a **Python evaluation framework**, so the *"no executable surface"*
      finding from the marketplace skill **does not carry over** and must not be reused. Pin the
      commit, read what `eli5-workspace/` actually runs and what it touches, and record the licence
      (MIT) and the author. ⚠️ 10 commits, no issues, no PRs, one author: a small, young repo with
      258 stars is a popularity signal, not a maintenance signal — state the bus factor rather than
      the star count.
- [ ] AC9 — **Choose ONE, on stated axes, and record why the other lost.** Candidates: the
      marketplace picture-explainer, `DreambigOu/ELI5`'s audience-adaptive skill, both under
      distinct names, or neither. 🔴 **They may not both be installed as `eli5`** — two skills
      resolving under one name is the [[T135]] failure and, at runtime, whichever resolves first
      wins silently (exactly the `.agent/skills` shape [[T182]] AC4 hit).
      🔑 Weigh against the ask: *"a common standard default skills set for projects"* points at
      explaining our own systems to different readers, which is the second skill's subject and not
      the first's.
- [ ] AC10 — **The self-reported eval is re-run or discounted, and never repeated.** *83.3% vs
      41.6%* is the author's number, from the author's rubric. Either run `eli5-workspace/` against
      our own cases and record what WE measured, or state plainly that the figure is unverified.
      ⚠️ Quoting it as a reason to adopt would be the estate's most-repeated mistake — accepting a
      recorded measurement as a fact instead of a claim with a method.

## Definition of Done


Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
the security review is RECORDED rather than assumed, upstream is identified to [[T127]]'s fully-qualified standard, and adoption is proven **by the gate, not by the file's presence**. 🔴 AC3 must be answered first and is the real subject: *what "the default skill set for projects" IS* — adding a skill to an undefined set is how an unmanaged corpus grows. ⚠️ Two honesty clauses: choose ONE candidate on stated axes and record why the other lost; and the upstream's self-reported *83%* eval is re-run or discounted, **never repeated** — a vendor's own number quoted onward becomes our claim.

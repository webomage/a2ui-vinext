## 2026-08-17 — AC1's first attempt FAILED on a toolchain gap; fixed, and the failure was correct

The owner ran `just db-backup` and it aborted:

```
pg_dump: error: server version: 17.6; pg_dump version: 14.14 (Homebrew)
pg_dump: error: aborting because of server version mismatch
```

🔑 **The refusal was RIGHT and is worth preserving.** An older dumper cannot serialise a newer
server's catalog, so pg_dump aborting protected the backup rather than obstructing it. What was
wrong is that the recipe called **bare `pg_dump`** and had no opinion about which one it got — on
this host `postgresql@14` wins the Homebrew PATH.

**Nothing needed installing.** `postgresql@17` was *already* present; measured:

| | version |
|---|---|
| server | **17** |
| `pg_dump` on PATH (`postgresql@14`) | **14** ← the failure |
| `/opt/homebrew/opt/postgresql@17/bin/pg_dump` | **17.9** ✅ |
| `/opt/homebrew/opt/libpq/bin/pg_dump` | 16.4 |

→ **`wom7api/scripts/db_backup.py`**, and the recipe now calls it. It asks the SERVER its version
(`SHOW server_version`) rather than assuming, picks the newest pg_dump that meets it, and **refuses
with exit 2** naming every candidate it found if none does.

🔴 **It refuses rather than reassures, which is the whole point of this ticket:**
- pg_dump fails → the **partial file is DELETED**. A failed dump that leaves a file behind is the
  dangerous case: the directory looks populated and the next person reads that as *"we have backups"*.
- dump under 50 KB, or missing the `PostgreSQL database dump complete` trailer → **exit 1**, file
  kept but explicitly named as not-a-backup.
- ⚠️ It prints, every time, that a dump is **not a proven restore**. AC1 asks for a restore into a
  scratch database and this cannot stand in for it — *a dump that has never been restored is a
  belief, not a backup.*

Verified without dumping (the recipe is agent-denied, confirmed in `permissions-deny.json`): the
resolver picks `postgresql@17/bin/pg_dump` (17) against server 17, where bare `pg_dump` returns 14.
`just py-typecheck-api` green, 36/36 files — the new script is inside the mypy gate's scope, not
beside it.

🚧 **Still the owner's to run.** `just db-backup` now has a working dumper; AC1 stays open until a
dump exists AND has been restored.

## 2026-08-18 — AC1 PROVEN: the dump restores, verified against live

**The claim this AC exists to refuse is *"we have a dump"*.** A dump that has never been restored is
an untested assumption. It has now been restored and diffed against the live database.

### What was done

`supabase/backups/backup_20260817_195143.sql` (27 MB, owner-run 2026-08-17 19:51:43Z) restored into
a scratch PostgreSQL **17.9** instance. ⚠️ The estate had **three** Homebrew Postgres versions
installed and none running; the owner removed 14 and 15, leaving only 17. It is **keg-only**, so
nothing is on `PATH` — the restore needs `/opt/homebrew/opt/postgresql@17/bin` prepended.

### Two prerequisites the dump does NOT carry — both were discovered by failing

| Missing | Errors it caused | Fix |
|---|---|---|
| a `postgres` **role** | **414** | Homebrew names the superuser after the OS user; `CREATE ROLE postgres SUPERUSER LOGIN` |
| **pgvector** | **342** (`extensions.vector` / `halfvec` / `sparsevec`) | `brew install pgvector` |

Errors fell **965 → 555 → 59**. 🔴 **The 342 pgvector errors are the finding worth keeping**: without
that extension the vector-bearing tables do not restore at all, and nothing in the dump, the backup
script or this ticket said so. A recovery attempted in an emergency, on a fresh host, would have hit
it cold. The remaining **59** are `pg_net` (`net`), `pg_cron` (`cron`) and `supabase_vault` — Supabase
platform extensions, unavailable off-platform, holding **no user data**.

### The verification — measured, not asserted

| Check | Result |
|---|---|
| Schemas & table counts | **7/7 schemas, exact match** — public 99 · auth 23 · gamification 15 · storage 8 · realtime 7 · drizzle 1 · supabase_migrations 1 |
| Tables in `public`+`gamification` | **114 / 114**, no table missing, none extra |
| Total rows | restored **23,341** vs live **23,444** (−103) |
| Row-count mismatches | **3**, all append-only logs — `admin_activity_logs` −70, `schema_change_log` −27, `analytics_events` −6 |
| Content, byte-for-byte | **technologies, capabilities, blueprints, proposals — IDENTICAL** |
| RLS | **99/99 public tables** have RLS on, matching live |

✅ **Every difference is accounted for as post-dump change, not loss.** Live
`count(*) where created_at <= '2026-08-17T19:51:43Z'` on `admin_activity_logs` returns **2749** —
*exactly* the restored count. `contracts` differs on **95 of 96** rows, and live reports
`count(*) where updated_at > <dump time>` = **95**. The 27 `schema_change_log` rows are this
session's own migrations. Policies restored **257** vs live **240**: the same 27 post-dump DDL
events dropped 17 policies. **No table lost a row, and nothing restored that live does not have.**

### ⚠️ Two measurement mistakes, both mine, both worth recording

The first content comparison used `row::text` and reported **3 of 3 tables DIFFER**. Both causes
were in the comparison, not the data:

1. **Timezone.** The local session was `America/Cancun`; Supabase renders UTC. The same instant
   printed `…41.472479-05` and `…41.472479+00`.
2. **Locale quoting of multi-byte characters.** After pinning UTC, `technologies` still differed —
   on **two rows**, and the entire difference was `🧠` versus `"🧠"`. `row::text` quotes
   emoji differently under a different `lc_ctype`.

⇒ **`row::text` is NOT a valid cross-instance comparator.** `to_jsonb(t)::text` is — sorted keys,
JSON string escaping, no locale-dependent quoting. Under it, 4 of 5 tables were immediately
identical. 📌 **Twice in one verification, the tool said "the data is corrupt" and the tool was
wrong.** A restore check that had stopped at the first red would have condemned a good backup.

## 2026-08-18 — the restore is now a RECIPE, not a one-off

The previous entry proved the dump restores **by hand**, which left the finding true and
unrepeatable: the next person would re-derive the `postgres` role and the pgvector requirement from
756 errors, exactly as that run did. `just db-restore-verify` now does the whole thing.

**`scripts/db_restore_verify.py`** — restores the newest dump into a scratch database, diffs it
against live, and drops the scratch db afterwards (`--keep` to inspect). It is the sibling
`db_backup.py` names in its own docstring: *"a real restore needs a scratch database."*

### What it refuses, and why each refusal exists

| Refusal | Why |
|---|---|
| dump missing, or under the size floor | the thing being verified must be real |
| a restore error **outside** the benign allowlist | an unrecognised error is a finding, not noise |
| a table present live, absent restored | the data loss the check exists to catch |
| **more** rows restored than live | the dump is not of this database |
| a shortfall **not** explained by a post-dump timestamp | otherwise loss reads as drift |
| **zero** tables, or zero content hashes, compared | 🔴 a verifier green over nothing would certify an unrestored dump |

Prerequisites are checked **up front** and name their own fix, so they are never re-derived from
wreckage. Benign errors are an **allowlist with a reason each**, never a suppression.

### Proven RED by mutation, on the real 28 MB dump

| Mutation | Result |
|---|---|
| **A** — `DROP TABLE public.technologies` appended | ❌ *"1 table present live and ABSENT from the restore"*, 114 → 113 |
| **B** — `DELETE FROM public.proposals` appended | ❌ *"3 row shortfall(s) NOT explained by post-dump growth"*, −644 rows |
| **C** — an extra table the live db lacks | ⚠️ warns and continues, as intended |

⚠️ **Honest note on C:** the run still exited 1, because my fixture filename carried a fake dump
date (`backup_20260103`) and the shortfall check reads the dump time from the filename. The
extra-table branch did warn correctly; the failure came from my fixture, not from that branch.

🔬 **Mutation A also surfaced something good.** The first attempt failed with
`Direct schema change refused: DROP on public.technologies` — **`wom_ddl_guard` restored with the
dump and was protecting the scratch database.** The guard survives a restore and works off-platform;
the mutation needed the guard's own `SET w0m.migration = 'on'` to land.

### Two bugs of mine, found by running it for real

1. **`-tA` spliced at index 3** landed between `-v` and `ON_ERROR_STOP=0`, so psql read the latter
   as a **username** — `role "ON_ERROR_STOP=0" does not exist`. Never splice argv by index.
2. **The timestamp-column list was incomplete.** The first real run **failed closed** on
   `schema_change_log`, which carries `occurred_at` — none of `created_at`/`inserted_at`/
   `updated_at`. ✅ **The gate refusing was correct; the list was wrong.** Candidates are now ordered
   by how well each answers *"when did this row arrive"*, with `updated_at` **last on purpose**: it
   moves when a row is edited, so it under-counts rows that existed at dump time and have been
   touched since — which would read as loss on a table that lost nothing.

### Current state

`just db-restore-verify` → **green**: 59 benign errors, 0 unexpected, 114/114 tables, 23,341 rows,
all 3 shortfalls explained against dump time, **6/6 content tables byte-identical**.
`just db-restore-verify-test` → **21 checks**, offline, exercising every refusal above.


## 2026-08-18 — AC4: Storage is backed up, and the copy is proven intact

`pg_dump` captures Postgres and **no files**. Measured independently two ways — a `storage.objects`
query and the Storage API — the estate holds **555 objects / 53,930,649 B across 13 buckets**, and
both counts agree exactly. `documents`, `blueprints`, `profile_snapshots` and the served CV PDFs all
reference storage paths, so a database restore alone brings back rows pointing at nothing: **a
half-restore that looks like a whole one.**

**`just storage-backup`** (`scripts/storage_backup.py`) walks every bucket, downloads every object,
and writes a `manifest.json` carrying a **sha256 per object**. `--verify-only <dir>` re-checks the
bytes on disk against that manifest rather than trusting it.

### First real run

```
buckets 13 · upwork 327 · news 187 · snapshots 20 · domains 8 · blueprints 7 · cv 3 …
objects 555 downloaded · 53,930,649 B          ← exactly the storage.objects total
verified 555/555 object(s) intact on disk, every sha256 matches
```

### What it refuses

| Refusal | Why |
|---|---|
| **zero buckets**, or **zero objects** | 🔴 the empty-corpus trap — a downloader that finds nothing and exits 0 would certify 555 files as safe having copied none |
| any object that fails to download | partial coverage reported as coverage is how a backup becomes fiction |
| a downloaded size ≠ the size the API reported | **a 200 is not evidence of content** |
| missing credentials | a backup that silently skipped is worse than one that failed |

⚠️ **Recursion is load-bearing.** The list endpoint returns one directory level, so a flat walk would
back up only bucket roots and report success. A probe asserts the nested object is captured.

### Handling

Registered in **`confirm-policy.json` alongside `db-backup`**, for the same reason: the output is
**secret material**. Private buckets hold applications, blueprints, domain scans and the Upwork
corpus. Confirmed `supabase/backups/` is gitignored (`.gitignore:117`) and `git status` sees nothing
of the 53 MB written.

### ⚠️ What this deliberately does NOT claim

**It does not prove a restore.** Uploading 555 objects back into live storage is destructive and has
**no scratch equivalent** — there is no throwaway bucket the way `db-restore-verify` has a throwaway
database. So this proves the copy is **complete and intact** (count, per-object size against the
API, sha256 manifest), not a round trip. The script says so in its own output, so a green run cannot
be read as more than it is.

`just storage-backup-test` — **18 offline checks** against a localhost stub, including a tampered
file, a deleted file, a truncated download, and both empty-corpus shapes.


## 2026-08-18 — AC2: a missed run is visible, and it is measured from the DISK

AC2 asks for two things and names its own constraint:

> ⚠️ the scheduler surface is split, and desktop-app routines are invisible to the CLI scheduler,
> so *"it is scheduled"* must be verified by its **output**, not by its existence.

🔴 **That constraint decides the design.** A routine can exist and never fire, or fire and never be
listed — so asking a scheduler proves nothing. **`just backup-freshness` asks the filesystem
instead**: what artefacts exist, and how old are they. That answer is **scheduler-agnostic** —
whatever ends up running the backup, cron, a desktop routine or a human, this notices when it stops.

```
✅ postgres  backup_20260817_195143.sql     0.8d old (limit 7d)  · 28,364,067 B
✅ storage   storage_20260818_141108        0.0d old (limit 30d) · 54,052,290 B
```

Limits are declared in **`.w0m/sdlc.json → backups.max_age_days`** (postgres 7, storage 30) — in
config because the cadence changes more often than the checker, and a cadence written into a script
is one nobody edits. A missing or unparseable config falls back to the same conservative numbers
rather than **skipping the check**.

### What it refuses

| Refusal | Why |
|---|---|
| 🔴 the directory missing, or holding **no** dumps | **zero backups is the loudest state this check has, never "nothing to check ✓"** — that tick would be the exact failure this ticket documents |
| older than its declared limit | the job stopped, or never ran |
| present but under the size floor, **even when fresh** | a truncated file is not a backup |
| a filename whose timestamp cannot be read | an undatable file is a hole in the answer, not a pass |

Each surface is checked **separately, on its own limit** — a fresh dump must not mask storage that
has not been copied in three months.

### Where it shows up

Wired into the standing audit (`▶ BACKUPS`), so a missed run appears without anyone remembering the
recipe. ⚠️ **Deliberately OUTSIDE `--quick`**, i.e. not on every push, and the tier-coverage block
names the omission so `--quick` cannot silently claim it. The reasoning is the one `check_knowledge`
already carries: **once a backup ages past its limit it stays past it**, so a pre-push placement
would warn on every push for days and train people to scroll past it — which is how the warning that
matters gets missed. Reported as **WARN**, since the blocking judgement on cadence belongs to this
ticket's own gate, not to a status sweep.

`just backup-freshness-test` — **16 offline checks**: a missing directory, an empty one, a stale

### ⚠️ What is NOT claimed

**This does not schedule anything.** Registering the job belongs to whichever surface the owner
actually uses, and given the split scheduler that is a decision rather than a command — which is
precisely why AC2 was written as *"make a missed run visible"*. The visibility half is now real and
independent of that choice. **And freshness is not integrity**: `just db-restore-verify` and
`just storage-backup --verify-only <dir>` are what prove content.

### ⚠️ A regression I introduced and had to back out: `.w0m/sdlc.json` is NOT JSONC

The limits were first added as `//` comments, matching this estate's stated **JSONC-for-config**
preference. **That broke the file.** `version-check` died with a `JSONDecodeError` pointing at
line 430 — the first comment line — and measurement showed why: **all 8 `//` lines in the file were
mine**, the file has always been strict JSON carrying `"_comment"` STRING keys, and **33 scripts
parse it**, most with a plain `json.load`.

📌 **My own validation missed it, and the way it missed is the lesson.** I checked with
`re.sub(r'^\s*//.*$', '', raw, flags=re.M)` — which strips comments, so of course it parsed. **I
verified the file against a tolerant reader while every real consumer uses a strict one.** A
green check proves what the checker looked at, not what the consumers will do.

⇒ Converted to the file's own `"_comment"` convention. `backup_freshness.py` keeps a tolerant strip
as defence, with a comment saying never to rely on it. **A general preference does not override a
specific file's contract**, and the contract is discoverable by looking at what is already in it.

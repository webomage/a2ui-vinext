## Summary

The CV corpus has **no canonical source**. Seven markdown CVs exist across three locations, they
disagree on job title, dates and content, and every correction has to be applied by hand to each
one. Owner ask 2026-08-05: *"find out if there are open standards and opensource libs to handle cv
info like crm style and with any import/export options."* Survey delivered:
[`docs/backend/branding/CV-DATA-STANDARDS-2026-08-05.md`](../../docs/backend/branding/CV-DATA-STANDARDS-2026-08-05.md).

**The drift is measured, not theoretical.** Correcting one fact — VXG Inc. is `Nov 2025 – Feb 2026`,
not current — required edits in **six files** on 2026-08-05:

```
applications/agilityfeat_senior_devops_webrtc_livekit.md   (3 places)
skills-matrix.md
Aleksei_CV_2026.md                                          (public variant)
apps/{web,cp}/public/cv/aleksei-tcelishchev-cv-full.md      (×2)
apps/{web,cp}/public/cv/aleksei-tcelishchev-cv-upwork.md    (×2)
```

⚠️ **And the first sweep missed two of them.** The downstream list named `AT resume.md`, which
predates VXG and never mentioned it; the real carriers were `cv-full`/`cv-upwork`, found only by
grepping for the *claim* instead of the *filename*. A canonical source removes the class of error,
not just this instance. The same session also found `Aleksei_CV_2026.md` asserting **10,500+ hours**
in its summary and **4,000+ hours** in Certifications — one document, 2.6× apart.

**Chosen standard: JSON Resume** (MIT). Decisive property, verified against the raw `schema.json`:
**`additionalProperties: true` at the root and inside `work`/`education`**, plus a formal `meta`
object. No CV standard models what this corpus carries — per-engagement **hours**, **weighted client
feedback**, client contact, `not rated`/`ongoing` states — and JSON Resume is the one that will hold
them without failing validation.

**Rejected, with reasons** (detail in the survey): **HR Open Standards** — enterprise
system-to-system HR exchange, wrong altitude for one person's CV. **OpenCATS / Odoo Recruitment /
EspoCRM / Twenty** — ATS and CRM shapes model *many candidates seen by one recruiter*; this needs
*one person's history across many audiences*. **Europass/ELM** — unverified (URL 301'd, target
404'd), and credential-exchange oriented regardless.

### 🏗️ How to build the full version — the design the rediscovery implies

The blocker was never rendering; `bake-variants` already turns markdown into PDF. What is missing is
the step that produces the markdown **from canonical**. Concretely:

1. **Selection must be DECLARED, not inferred.** A variant manifest (which roles, which projects,
   what depth) per audience. Without it "full" vs "standard" is arbitrary — and the measured proof
   is that today they carry **16 / 12 / 7 / 5 / 3 of 28 roles** with no recorded reason for any of
   those numbers.
2. **Join projects to roles through `company-aliases.json`, never by name.** `projects[].entity` →
   `entities` → the work entry. A joined project renders **nested under its role**; an unmapped one
   renders in a standalone section. This is what stops `Kayse` and `kayse.ai` appearing as two
   engagements.
3. **Generate markdown → then `bake-variants`.** Two steps, the second already built and proven.
4. **Gate it with what already exists** — `cv-validate` (AC3's drift check), `cv-leak-check`
   (fail-closed, already proves PDFs), `cv-claims` (evidence per claim).

11 projects are populated and 6 carry explicit associations.

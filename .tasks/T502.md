# T502 — the legacy resume parse writes without review, twice

## Summary

Split from [[T501]] AC5 (owner rule: close leftovers into a dependent ticket). T501 moved Resume Studio to the reviewed `w0m-personnel` parse. The older path is still live and has three defects, measured 2026-09-30 by reading the code:

1. `supabase/functions/parse-resume` writes `profile_experience` rows (source `resume`, AI-authored descriptions) and inserts a `profile_resumes` row with `is_primary: true` for EVERY parse, with no review step.
2. `packages/ui/.../ResumeParser.svelte` (used by `apps/join` dashboard and `apps/cp` `/me/profile`) then inserts the same experience rows and another primary `profile_resumes` row from the browser. The two writers do not share a key, so one upload can create two of each.
3. It sends the resume text to Google (`gemma-4-31b-it` via `routeChat`) unless T501 AC5 has moved it.

## Acceptance criteria

- [ ] AC1 — One writer. `parse-resume` returns what it found and writes nothing to `profile_experience`; the client shows it and the member approves (as Studio does for highlights).
- [ ] AC2 — A parsed upload is never made `is_primary` unless the member has no primary resume, or the member chooses it.
- [ ] AC3 — The model behind it is the Cloudflare alias (no resume text to Google); the model choice comes from the T501 evaluation.
- [ ] AC4 — Both callers (join dashboard, CP profile) are updated in the same change; a test proves one upload creates at most one `profile_resumes` row and no `profile_experience` row before approval.

## Definition of Done

- Uploading a resume in onboarding shows what was found and writes nothing until the member accepts.
- After accepting, exactly one row per employer exists.
- No resume text leaves Cloudflare and Supabase.

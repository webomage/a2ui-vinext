# T585 — First-Party Webomage (`w0m` / `eg-w0m`) Project Vault, Cloudflare R2 Sync & Knowledge Hub Integration

## Context & Problem Statement

In `T580`, per-engagement Cloudflare R2 Obsidian vaults (`r2://wom-engagement-vaults/engagements/...`) and the `/api/vault/r2/[engagement]` WebDAV/REST gateway were provisioned for the 4 managed client engagements (`1945` / `eg-1945`, `artemio` / `eg-artemio-quiero-comer`, `servicios777` / `eg-servicios777`, `personaje0` / `eg-personaje0`).

However, the first-party **Webomage (`w0m` / `eg-w0m` / `webomage`) project vault** (`id: "w0m"` in `project/policies/clients-policy.json`) was not yet wired into:
1. `project/policies/clients-policy.json` (`knowledge_hub` declaration for `id: "w0m"` with `vault_slug: "w0m"`, `engagement_public_id: "eg-w0m"`, `org_slug: "webomage"`, `project_slug: "w0m"`, `r2_bucket: "wom-engagement-vaults"`, `r2_prefix: "engagements/eg-w0m"`, `corpus_root: "w0m-web/projects/w0m/vault"`).
2. `w0m-web/projects/w0m/vault/` Karpathy LLM Wiki corpus (`index.md`, `mocs/architecture.md`, `mocs/requirements.md`, `mocs/deliverables.md`, `notes/mobile-sync-user-guide.md`, `claims/`, `sources/`, `.obsidian/`).
3. `/api/vault/r2/eg-w0m` (and aliases `w0m` / `webomage`) in `vault-r2-gateway.ts` — authorizing platform admins and active holders of an org hat on `webomage` while strictly denying (`403 Forbidden`) pure client users (`artemio`, `1945`, `maksim`).
4. `/admin/vaults` (`vaults.astro` + `VaultSyncPanel.svelte`) and `/o/webomage/projects/vault` (`pages/o/[org]/projects/vault.astro`) — exposing the Webomage (`w0m`) `<KnowledgeHub>` (with multi-engagement vault switcher across `eg-w0m` + client engagement vaults and the "Connect Mobile App (CF R2)" panel) alongside `<VaultSearch>`.
5. Live Cloudflare R2 (`r2://wom-engagement-vaults/engagements/eg-w0m/`) and `public.project_vaults` / `public.vault_notes` migration (`20261029183000_t585_w0m_project_vault.sql`).

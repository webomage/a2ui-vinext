# T235 — the Rust *toolchain* is ungoverned (the stack is not)

## Summary

**Owner, 2026-08-19:** *"we will have more and more — I'm looking to build a solid foundation, and
Rust here is first citizen for speed etc in our tools, same way as zeroclaw."*

🔬 **CORRECTED 2026-08-19, before any code was written.** This ticket was filed with two false
measurements. Both were found by reading the registry instead of its key list, and both *shrink*
the work:

| filed claim | measured reality |
|---|---|
| 🔴 "Rust is **not** declared in `stacks-policy.json`" | ❌ **WRONG** — the **`mlx` stack IS the Rust stack**: `runtime: "rust"`, and the full `build`/`test`/`lint`/`fmt`/`fmt-check` contract. I read the stack *names* (cf, edge, ext, mlx, …) and never opened one. A `rust` stack was drafted, rejected by the schema, and on reading `mlx` **reverted** — it would have been a second declaration of one language. |
| 🔴 "clippy **MISSING**" | ❌ **WRONG** — `cargo-clippy 0.1.97` is installed and `cargo clippy` runs. I probed the bare name `clippy`; the binary is `cargo-clippy`. |

⇒ Same error in both: **probing a name instead of the thing.** That is the [[measurement-traps-w0m]]
rule — *never match on a name the inspected thing supplies* — applied to my own filing.

✅ **What survives, and it is real.** Rust is load-bearing here:

| | |
|---|---|
| Rust crate w0m **owns** | **1** — `wom7-mlx-rs` (+ vendored `candle`, `mlx-rs` it does not) |
| Rust **daemon already running** | `com.zeroclaw.daemon`, a launchd user service |
| Rust binaries **declared** in `tools-policy.json` | `zeroclaw` — the *runtime* |
| 🔴 **the compiler under all of it** | **cargo · rustc · rustfmt · clippy · rustup — 0 of 5 declared** |

⇒ 25 tools carry a `min` floor. The toolchain that **builds** the one thing this ticket wants to add
carries none. That is the exact shape of the omlx / tart / zeroclaw gap: *load-bearing, and invisible
to `tools-check`.* A machine with no Rust — or a 2023 rustc — reports a clean toolchain today.

📌 **This still dissolves the ai-memory objection.** [[AgDR-0009]] left one concern — *"a daemon on
`:49374`"*. The estate already runs a Rust daemon under launchd. A second is a known shape.

## Evidence — 2026-08-19

**AC1** — 5 entries added; `just tools-check` → **30 tools**, all five resolve:
`cargo ✓1.97.1 · cargo-clippy ✓0.1.97 · rustc ✓1.97.1 · rustfmt ✓1.9.0 · rustup ✓1.29.0`.
🔑 Declared as **`cargo-clippy`**, its real binary name — `tools_check.installed_version()` does
`shutil.which(<key>)`, so a `clippy` key would have re-committed the ticket's own filing error.

**AC2 — red-proven, both modes:**

| mutation | result |
|---|---|
| `cargo.min → 99.0.0` (optional) | `✗ 1.97.1 < min 99.0.0`, 1 warn, **exit 0** |
| + `required: true` | **1 required-problem**, still exit 0 |
| + `--strict` | **exit 1** ✅ |
| restored, `--strict` | **exit 0** ✅ |

⚠️ **Stated, not assumed:** a below-floor Rust toolchain **warns and does not block** by default.
That is deliberate — `tools-policy.json:2` says per-machine versions are *ADVISORY*, and `--strict`
is the gating form. I briefly flagged the exit-0 as a vacuous gate; **it is documented design.**
🔴 But `--strict` is invoked by **no hook and no CI** in the estate — so the floor is a signal, not
a guard. Correct while nothing in the push path compiles Rust; revisit when AC6 lands.

**AC3** — `just discovery` now prints the runtime split:
`deno (1): edge · node (5): cf, ext, skills, web, worker · python (3): sec, tooling, tooling-api · rust (1): mlx`
Red-proven: `runtime: "zig"` → schema rejects (`not one of ['node','deno','python','rust']`);
`runtime: "python"` → the `rust` group **disappears**, proving the line is derived, not printed.

**AC4 — verified, not re-litigated.** `just lint` in `wom7mlx/wom7mlx` still exits **101** with
**29 errors, all inside the vendored `mlx-rs` clone** (`mlx_gather_qmm` arity, generated
`bindings.rs`) — matching the `mlx` stack's recorded note exactly. `build`/`test` stay `phase:
manual`. A `rust` stack was drafted here and **reverted**: `mlx` already is it.

**AC5** — zeroclaw needed no new entry; it is declared (`min 0.8.3`, `auto: none`, with the
crates.io name-collision warning). The gap was the **compiler beneath it**, closed by AC1.

**🔎 Found while evaluating the fork (new, not in the original ACs):**
- 🔴 **`deny.toml` is inert.** ai-memory ships a `cargo-deny` supply-chain policy (advisories,
  licenses, registry allow-list) and **`cargo-deny` is not installed** — a policy file with no
  enforcing tool, the exact vacuous shape [[measurement-traps-w0m]] warns about.
- ⚠️ **`rust-toolchain.toml` pins `channel = "1.95"`**, so building ai-memory makes rustup fetch a
  *second* toolchain regardless of the 1.97.1 default. The AC1 floor (1.85.0, from wom7mlx's
  `edition 2024`) is **below ai-memory's declared `rust-version = "1.95"`** — 🔑 **if AC6 adopts it,
  the estate floor must rise to 1.95.**

**AC6 — built and running.** `cargo build --release` in `_ext/ai-memory` (owner cloned it
2026-08-19): **exit 0, 3m28s, 286 crates**, → `ai-memory 1.28.1`, a 23.8 MB binary. No prebuilt
release artefact was downloaded.

🔬 **Two supply-chain observations from the build, one of which corrects my own alarm:**
- ⚠️ **rustup silently installed a SECOND toolchain.** `rust-toolchain.toml` pins `channel = "1.95"`,
  so `cargo build` fetched `1.95-aarch64-apple-darwin` alongside the 1.97.1 default — an implicit
  toolchain acquisition triggered by cloning a repo. `~/.rustup` is now 1.9 GB.
- ✅ **The `tailwindcss` binary in `target/release` is NOT an unmanaged prebuilt.** I flagged it as
  one on sight (45.8 MB, Mach-O, never compiled). It is fetched by `crates/ai-memory-web/build.rs`
  from the official `tailwindlabs` release, at a **pinned version**, and verified against a
  **hardcoded per-platform SHA-256** that `panic!`s and deletes the file on mismatch — with a
  `panic!` for unknown platforms rather than a silent skip. That is *better* hygiene than most, and
  it counts **for** ai-memory, not against. 🔬 Same lesson as the head of this ticket: I judged an
  artefact by its appearance before reading the code that produced it.

**AC9 — guard built, red-proven, and wired.** `project/scripts/stage_guard.py` + `just stage-guard`
(pre-commit) + `just stage-guard-test`. Two checks of deliberately different kinds:

| check | catches | blind to |
|---|---|---|
| `project/co-tenancy.json` registry | declared co-tenant paths, durably | a path nobody has declared yet |
| live open-write-handle probe (`lsof`) | **undeclared** paths, in flight now | a process that closed the handle |

Neither suffices alone and the script's docstring says so. Overriding needs `W0M_STAGE_GUARD_OK=1`,
which **prints what it let through** — an override that leaves no trace is a bypass.
🔴 **Red-proven against the real incident, not a synthetic one:** the probe stages the actual
`upwork_mcp_sync.py` → **exit 1**; unstaged → **exit 0**; staging set restored. When that file is
absent the probe **exits 2 and says SKIP≠PASS** rather than reporting green ([[T96]] AC3).
📌 It was not hypothetical: at commit time the Antigravity agent's `upwork_mcp_sync.py` **and** a
relocated `project/data/upwork/` were sitting untracked in the tree. `git add -A --dry-run` confirmed
both would have been swept.

**AC7 — honored as a constraint, and the distinction is real.** ai-memory was **built and run**;
it was **not adopted**. No daemon installed, no memory migrated, nothing deprecated, `~/.claude`
auto-memory untouched. [[T234]] still owns the adoption decision, and its AC4 kill criterion and
AC8 *"one surface goes or the tool does"* are unchanged by anything here.

**Registry hygiene — caught by the estate, not by me.** `just suites-drift` failed on
`stage-guard-test` being undeclared; registered in `project/test-suites.json` (100 suites, 0
undeclared). 📌 Second time this session that [[T130]]-family strictness caught my own omission —
the first being the schema rejection that surfaced the duplicate-stack error at the top of this file.

## Floor raised — 2026-08-19 (owner: *"rize rust version"*)

Floors moved to the **highest requirement declared by Rust code present in the estate**:

| tool | was | now | why this number |
|---|---|---|---|
| `cargo` · `rustc` | 1.85.0 | **1.95.0** | `_ext/ai-memory` declares `rust-version = "1.95"` and pins `channel = "1.95"`; wom7mlx needs ≥1.85 (`edition 2024`). max = 1.95 |
| `cargo-clippy` | 0.1.85 | **0.1.95** | measured: `rustup run 1.95 cargo-clippy --version` → `clippy 0.1.95` |
| `rustfmt` | 1.8.0 | **1.9.0** | 🔬 measured, and it mattered — rustfmt does **not** track the rustc number: the 1.95 profile ships **rustfmt 1.9.0-stable**, the *same* rustfmt as 1.97.1. Inferring "1.95 → rustfmt ~1.5" would have set a floor that never matches reality. |

✅ **The raise has teeth, proven against the gap** — not just re-confirmed on the installed version
(which passes either way and would prove nothing):

| version | old min 1.85.0 | new min 1.95.0 |
|---|---|---|
| 1.85.0 · 1.90.0 · 1.94.9 | pass | **FAIL** ← the raise bites |
| 1.95.0 · 1.97.1 | pass | pass |

`just tools-check` → **30 tools, 0 required-problem(s), 0 warn**; installed 1.97.1 clears it with
room, and `rustup check` confirms **1.97.1 IS current stable** (so this was a floor change, not a
toolchain upgrade — there is nothing newer to move to).

⚠️ **Recorded so it can be undone honestly:** ai-memory is **evaluated, not adopted** (AC7 / [[T234]]).
The floor tracks code *present and buildable* in the estate. **If ai-memory leaves `_ext/`, 1.95 is
no longer justified and should drop back to 1.85.0** — a floor that outlives its reason is the
[[t67-supabase-pat-dead]] trap: a recorded constraint nobody re-tests.

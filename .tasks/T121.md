# T121 — Chat lead-capture is 401ing on a hardcoded, dead anon key

## Summary

Four source files carry a hardcoded Supabase **anon** key. In the two test files it is a
*fallback* (`process.env.… || "eyJ…"`); in the two `ChatApp.svelte` files it is the **only** value —
a compile-time constant with no env read at all, which is what makes this a live defect rather than
a latent one.

| File | Line |
|---|---|
| `tests/bot_security_steps.ts` | 15 |
| `tests/bot_chaos_steps.ts` | 15 |
| `apps/web/src/components/ChatApp.svelte` | 19 |
| `apps/cp/src/components/ChatApp.svelte` | 13 |

## 🔴 ESCALATED to P1 — it is a LIVE DEFECT, not just hygiene

Filed as P2 hygiene. Probing the endpoints changed that:

| Key used | `POST /functions/v1/client-register` |
|---|---|
| Live vault `PUBLIC_SUPABASE_ANON_KEY` | **400** — auth OK, body rejected (expected for `{}`) |
| **The hardcoded key, as shipped** | **401 — auth rejected** |

Same request, same body; only the key differs. And the hardcoded key **is in the deployed
bundle** — confirmed by fetching `https://webomage.com/_astro/ChatApp.B7tIWnmy.js` and finding it.

In `ChatApp.svelte` the key is **not a fallback** — it is the only value, a compile-time constant.
So **lead capture from the chat widget is failing in production with 401**. The two AI endpoints
(`agent-consultant`, `agent-architect`) return 400 with the same key, i.e. they accept it — they are
deployed `--no-verify-jwt`, which is why the chat itself appears to work and this stayed invisible.

**That asymmetry is the whole trap:** the visible feature (chat) works, the revenue path
(lead → client registration) does not, and nothing distinguishes them from the outside.

This also means the 2026-07-15 verification of the register flow (recorded in T41) passed against a
key that has since stopped being accepted — worth confirming when the JWT secret was rotated.

## Verified 2026-07-22 — this is NOT a credential leak

Two checks that change the severity, both worth not re-deriving:

1. **The hardcoded value is STALE.** It does not match `PUBLIC_SUPABASE_ANON_KEY` in Infisical
   (different SHA).
2. **It is DEAD.** `GET /rest/v1/` with that key returns **HTTP 401**. It authenticates nothing.

Combined with the fact that a Supabase **anon** key is public by design — it ships to every browser
in the client bundle — there is **no exposure here to remediate**. It is not a security incident.
It is a P1 because the key is *dead*, not because it is *published*.

## Why it still needs fixing

- **A fallback that cannot work is worse than none.** If `PUBLIC_SUPABASE_ANON_KEY` is ever unset,
  the code silently substitutes a dead key and the failure surfaces as a mysterious `401` from
  Supabase — far from the actual cause. Failing loudly at startup ("PUBLIC_SUPABASE_ANON_KEY is
  required") turns a debugging session into a one-line error.
- **It blocks commits.** `gitleaks` flags the literal as a JWT, so any change touching those lines
  fails pre-commit. It already blocked the T119 lint pass on 2026-07-22, which is how it was found.
  That cost is recurring and lands on whoever next edits those files.
- **It is a stale copy of a rotated credential.** Even dead, it invites someone to "fix" the wrong
  thing by refreshing the literal rather than removing it.

### Regression found and fixed on the way: `just build` was broken

Removing `.env` in T119 AC2b broke the build, and it went unnoticed because my verification then
ran *while `.env` still existed*. Cause: **turbo sanitises the environment** for cache correctness,
so variables injected by `infisical run` never reached the app build subprocesses. `turbo.json` now
declares `globalPassThroughEnv` with prefix wildcards (`PUBLIC_*`, `SUPABASE_*`, …) rather than a
90-line list that would drift.

**Third confounded verification this session.** The pattern each time: the new mechanism appeared to
work while the old one was still present. The control arm — remove the old source, re-test — is
what exposed it every time.

### One annotation, not a rewrite

`historyContainer` in the cp component is flagged `no-unassigned-vars`, but it **is** assigned — by
Svelte's `bind:this`, which the linter cannot see. Annotated as a false positive rather than
restructuring working code to satisfy a tool.

## ✅ 2026-07-22 — deployed and verified live

Both apps serve `f68343a0`. The deployed bundle (`ChatApp.C5oa7gCG.js`) ships the live key with

### The key is not a JWT any more

Worth recording, because it invalidates the obvious way to check this: the live
`PUBLIC_SUPABASE_ANON_KEY` is **46 characters, `sb_publishable_…`** — Supabase's newer publishable
format, not a JWT. The dead literal it replaced *was* a JWT. So:

- grepping for `eyJ…` to find "the anon key" finds only the **stale** one, never the live one
- my first post-deploy probe extracted nothing with a JWT regex, sent an empty key, and got a 401 —
  which read exactly like "the fix didn't work". Comparing key **lengths** is what exposed it.

This also explains the original defect's shape: the hardcoded JWT was left behind by the migration
to publishable keys, and nothing failed loudly because the two AI endpoints accept any token.

### One more regression fixed on the way

`deploy-web` and `deploy-cp` each run their **own** `pnpm --filter <app> build`, separate from the
top-level `build` recipe I had already wrapped. Those were unwrapped, so the first deploy attempt
died with `PUBLIC_SUPABASE_URL is missing!`. All six per-app build steps in the deploy recipes are
now wrapped in `infisical run`. **Fourth confounded/incomplete verification this session** — the
lesson is the same each time: wrapping *a* build is not wrapping *the* builds.

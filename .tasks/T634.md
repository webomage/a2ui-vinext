# T634 — Separate project docs vault sources into tech-internal engineering docs, client operational guides, and public web instructions across repo, Supabase, R2, and KnowledgeHub

## Summary

Auditing all seven project documentation and vault sources (`w0m-web/projects/*/vault/`, Supabase `public.vault_notes`, Cloudflare R2 `VAULT_R2`, `report_ingest.py` (`just project-report-ingest`), virtual `mocs/roadmap-and-progress.md`, `w0m-web/docs/manuals/`, and `apps/web/src/pages/knowledge.astro`) uncovered four concrete audience-conflation and information-exposure defects:
1. **Client-visible vault folders (`notes/`, `mocs/`, `sources/`) mixed internal engineering details, w0m SDLC rules, and client PII with operational user guides**: `artemio/vault/sources/2026-09-14-artemio-t216-t222-delivery-report.md` exposed internal `LESSONS.md`, `w0m-sdlc-research`, `wom7skills`, `just skills-backport`, `tsconfig.json`, and `.venv_tg` to clients; all five `notes/ui-user-guide.md` mixed end-user instructions with `.svelte`/`.jsx`/`.py` source paths, Cloudflare KV hex IDs (`9d9177d48ba643808a756c0ffce023ae`), and literal client emails/names (`eva@webomage.com`, `Maksim Kulikov`); and all five `notes/mobile-sync-user-guide.md` (plus `scripts/init_project_vault.py`) still instructed users to install third-party `Remotely Save` + copy 1-hour JWT passwords instead of `w0m-obsidian-sync` (`T628`).
2. **`vault-reader.ts` stripped internal/tech notes even for Tech/Contractor staff**: `loadStaffProjectVaultAndNotes()` unconditionally called `getLocalVaultNotes()` -> `isClientSafeNote()`, leaving delivery engineers with no way to read `tech/` engineering notes on `/o/[org]/p/[project]/vault`.
3. **Supabase `public.vault_notes` and Cloudflare R2 (`VAULT_R2`) lacked an `audience` boundary**: `public.vault_notes` had no `audience` column or note audit log, older SQL seed rows overwrote newer bundled repo `.md` files on path collisions, and `vault-r2-gateway.ts` served an unfiltered manifest/bootstrap `.zip` to both client and tech callers.
4. **No dedicated public guides & instructions surface on `webomage.com`**: `apps/web/src/pages/knowledge.astro` rendered capability cards without step-by-step public platform instructions (domain ownership verification for website security audits, Client Portal milestones & approvals, `w0m-obsidian-sync` mobile/desktop vault pairing, and universal todos & shared wishlists).

## Definition of Done

Every declared project vault (`w0m`, `1945`, `artemio`, `servicios777`, `personaje0`) separates `guides/` (`audience: client | public`, zero `.svelte`/`.jsx`/`.py` paths, zero KV/Worker hex IDs, zero client emails, updated for `w0m-obsidian-sync` `w0m_vst_` pairing) from `tech/` (`audience: tech` engineering architecture, component/API maps, and SDLC delivery reports); PostgreSQL RLS on `public.vault_notes`, SSR loaders in `vault-reader.ts`, and `/api/vault/r2/[engagement]` (`PROPFIND`, `GET`, `PUT`, `delta_sync`, `bootstrap-zip`) return `0` `tech` notes/objects (`403` on direct `tech/*` requests) to `client` hats and client-scoped `w0m_vst_` tokens while serving both `tech/` and `guides/` to contractor/owner/admin hats; `<KnowledgeHub>` renders `@webomage/ui` audience badges and `Guides` vs `Tech` filters; and `webomage.com/guides` serves public platform instructions containing zero client names or domains, verified by PostgreSQL + Vitest red-probes, OpenSpec validation, `supabase_surface_drift_check.py`, and `ds-conformance`.

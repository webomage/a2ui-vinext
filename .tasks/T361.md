# T361 — Per-profile admin_todos ownership, and real member Upwork connection/sync attribution

## Summary

Two unrelated-looking gaps share one root cause: data that should be owned by a member's own
`public.profiles` row is instead owned globally or by "the estate", with no real per-profile
identity underneath.

**1. `admin_todos` has no owner.** `wom7api/supabase/functions/admin-todos-api/index.ts` runs
every GET/POST/PATCH/DELETE against the full table. `requireAdminAuth`
(`wom7api/supabase/functions/_shared/requireAuth.ts:95-107`) checks only `user_roles.role='admin'`
membership — never the caller's own identity beyond that. `adminTodos`
(`wom7api/supabase/functions/_shared/database/schema.ts:90-104`) has no owner column at all, and
its one RLS policy (`admins_full_access`) is `USING/WITH CHECK: EXISTS (user_roles WHERE
user_id=auth.uid() AND role='admin')` — any admin reaches every row. There is no such thing as
"my todos" today; every admin sees and can edit every other admin's todos.

**2. The Upwork "member" connection T360 shipped has no real row behind it.** T360 (done,
2026-09-15) built `/api/profile/upwork-sync.ts`, which queries `public.connections` for
`owner_kind='member' AND profile_id=<caller> AND provider='upwork'` — but that row does not
exist for anyone today. The only live Upwork credential is bridged from the estate's single
`upwork_auth_tokens` row (`id text default 'default'`, no owner column,
`wom7api/supabase/functions/_shared/database/schema.ts:106-122`) into `connections` as
`owner_kind='estate'`, `estate_slot='freelancer'`, `provider_type='organization'` by the
unconditional `wom_bridge_upwork_auth_tokens` trigger
(`wom7api/supabase/migrations/20260828030000_t94_ac5_connections_registry.sql:205-223`), which
re-inserts on **every token refresh** from that one source-of-truth row. Two things are wrong
with this, not one: the account is mis-classified (live-verified via
`mcp__upwork__upwork__list_accounts` just now: the credential resolves on Upwork's own side to
`{"name":"Aleksei Tcelishchev","role":"TALENT","role_label":"Freelancer"}` — an **individual**
account, not the `organization` the bridge stamps it as), and it is structurally estate-owned, so
T360's "Sync from Upwork" UI is a dead end for the actual account holder: there is no
`owner_kind='member'` row for it to find. Downstream, `contracts`, `proposals`
(`wom7api/supabase/functions/_shared/database/schema.ts:194-207`, `626-645`), `platformRooms` and
`platformMessages` (`schema.ts:210-`, `228-`) carry **no `profile_id`/`connection_id` column at
all** — `proposals` is even `pgPolicy("Allow all access to proposals", to: ["public"], using:
true)`, wide open. So even once a real member connection exists, nothing downstream can attribute
a synced contract/proposal/message to the member who owns it.

A real fix has to change the bridge/source-of-truth (`upwork_auth_tokens`) and the downstream
tables, not just flip the one `connections` row cosmetically — the next token-refresh cycle would
silently revert a cosmetic flip, because the trigger is unconditional.

## Acceptance criteria

- [x] AC1 — `admin_todos` gains a `profile_id uuid references public.profiles(id) on delete
  cascade` column (migration; backfill existing rows to a decided default — e.g. the estate/system
  profile — rather than leaving them ownerless), and RLS is rewritten so a caller only
  reads/writes their own rows via `public.current_profile_id()` (the reusable, already-live
  `auth.uid() → profiles.id` resolver from T210 Phase 4,
  `wom7api/supabase/migrations/20260814210000_t210_phase4_rekey_social_integrations.sql` — the
  same mechanism `connections`' own RLS already uses; no new pattern needed). Admins keep a
  separate, explicit "manage any" policy rather than inheriting blanket access through
  `admins_full_access`.
- [x] AC2 — `admin-todos-api/index.ts` scopes every GET/POST/PATCH/DELETE to the caller's own
  `profile_id` (resolved server-side from `user.id` the same way `current_profile_id()` does, not
  a client-supplied value), and `TodoManager.svelte`/`todos.astro` continue to work unmodified
  from the caller's perspective (no behavior change for a single-admin session; the change is only
  visible with 2+ admins). Bundle in [[T78]] AC4 while in this file: remove the dead
  `app_metadata:{role:"admin"}` write at `index.ts:36` (nothing reads it for authority).
- [x] AC3 — `upwork_auth_tokens` (or its replacement) carries a real owner: either add
  `profile_id` to the table directly, or migrate personal Upwork credentials into
  `public.connections` as `owner_kind='member'` rows keyed by the connecting member's OAuth
  identity, sourced from Upwork's own `GET /me`-equivalent (the same identity
  `mcp__upwork__upwork__list_accounts` exposes) rather than assumed.
- [x] AC4 — `wom_bridge_upwork_auth_tokens` (or its replacement path) stops unconditionally
  stamping every refreshed token as `owner_kind='estate', provider_type='organization'`; it
  derives `owner_kind`/`profile_id`/`provider_type` from the real connection owner, so a
  member-initiated OAuth connect produces a durable `owner_kind='member'` row that survives the
  next token refresh.
- [x] AC5 — `contracts`, `proposals`, `platformRooms`, `platformMessages` gain a `profile_id` or
  `connection_id` attribution path (nullable where estate-level data must remain unattributed),
  and the member Upwork sync path (`/api/profile/upwork-sync.ts`, from T360) writes contracts it
  pulls in as attributed to the connecting member's profile — not just into the flat estate pool.
  `proposals`' `pgPolicy("Allow all access to proposals", to: public, using: true)` is narrowed to
  match (estate-visible rows stay estate-visible; member-attributed rows are scoped like
  `connections`' own RLS).
- [x] AC6 — Verification: with a real (or sandboxed) member Upwork connection, `/api/profile/
  upwork-sync.ts` finds its `owner_kind='member'` row and completes a sync end-to-end (previously
  a guaranteed no-op); `admin-todos-api` proven to scope correctly with 2 distinct admin sessions
  in a test. Vitest coverage for both; `just typecheck` zero errors/warnings/hints.

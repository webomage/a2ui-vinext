# T150 — Ticket-sync indexing, and where MCP can and cannot replace a CLI

## Summary

Owner ask 2026-07-27, in two parts: *"stop doing CLI in git hooks and try MCP for GH and other
services we use like graphify"* (citing `scosman/hooks_mcp`, and later `punkpeye/fastmcp`), and
*"have some kind of indexing of tickets to not sync what's not needed"*.

**The second ask is right, measured, and cheap. The first ask cannot be done as stated, and the
reason is structural rather than a matter of effort.** They are filed together because both are
about `project/scripts/sync_github.py`, but their verdicts differ and must not be blurred.

## ✅ OWNER DECISION 2026-07-27 — git hooks are LEGACY GIT, not vendor tech

> *"hooks with mcp feature should be legacy git, not github special techs"*

**A git hook must contain only git-native, vendor-neutral checks.** No `gh` and no GitHub API inside
the hook; anything tied to a specific forge is a **projection** that runs *outside* it. No MCP in
the hook either — not because a hook cannot spawn an MCP client (**it can**; see the correction in
Part 1) but because a hook has no model, so the protocol costs something and returns nothing.
⚠️ **Read this together with the scope refinement immediately below**, which permits GitHub-specific
technology *for the ticket mirror specifically* — including Actions, which runs outside the hook and
so does not breach this rule.

🟢 **Measured 2026-07-27 — the estate already holds this rule almost everywhere.** Every `.husky`
hook across all 7 repos was audited for `gh`/GitHub-API references:

| Hook | GitHub-specific refs |
|---|---|
| `wom7web/.husky/pre-push` | 🔴 **2** — both the ticket mirror |
| `wom7web/.husky/pre-commit`, `wom7web/.husky/commit-msg`, and every hook in the other 6 repos | ✅ **0** |

⇒ **The rule costs exactly one change: take the mirror out of `pre-push`.** Everything else in the
hook layer is already git-native (tests, typecheck, lint, docs/state/version/secrets gates), and
that is worth stating so nobody "helpfully" adds a second forge call later.

### Scope refinement, same day: *"for syncing tickets we can use special github things vs legacy git for others"*

The rule is **per component, not global**. The **ticket mirror may be GitHub-specific** — it is a
GitHub projection, and pretending otherwise buys a forge-neutral abstraction nobody needs. **Every
other hook and check stays legacy git.** ⚠️ Do **not** generalise the mirror's licence to the rest
of the hook layer; the audit above is the line.

## ✅ PLACEMENT — SETTLED 2026-07-27. The hook is the answer. Read this before the history below.

> *"so if it's fast enough now and working let's keep it simple git hooks"*

**The mirror stays in `.husky/pre-push`. There is no workflow and no second path.** The decision
became available only after the build: a hook-resident sync used to cost ~10 minutes and ~435 round
trips, and now costs **one fetch and ~4 seconds** on a no-op. *The placement debate was really a
performance problem wearing a design costume.* Fixing the call pattern dissolved it.

Consequences, all of them simplifications: **AC3d (Actions) and AC3e (concurrency) are DROPPED**,
and with them the PAT/App, the backfill loop guard, and the two-writer problem. The account-level
Actions fault is no longer blocking anything here.
⚠️ **One thing gets HARDER, and it is the only cost:** the hook layer no longer has a
"no forge calls anywhere" rule that a check can enforce trivially. It now has **one sanctioned
exception**, and nothing stops a second appearing — see the rewritten AC3b.

## 🔴 Part 1 — `hooks_mcp` solves the INVERSE of the stated problem

Read before planning any of this: **HooksMCP exposes project tools *as* MCP functions *to* coding
agents.** It does not let a git hook call an MCP server. Its own framing is that it is the inverse
of traditional git hooks.

🔴 **CORRECTION 2026-07-27 — the first draft of this section overstated the argument, and the
conclusion survives the fix.** It said *"a git hook cannot be an MCP client."* **That is wrong.** A
hook can absolutely spawn one: `npx fastmcp dev server.ts --tool <name> --args '{…}'` runs a single
tool and exits with JSON, which is exactly an MCP client invocation from a shell.

**The accurate statement is that a hook cannot be an MCP HOST WITH A MODEL.** MCP's value is
letting a *model* discover and invoke tools it was not hard-coded against. `.husky/pre-push` is
non-interactive with no model, no session and no credential prompt, so it can only ever call a tool
it already names — which is what a command already is. ⇒ **In a hook you pay the protocol and keep
none of the benefit:** a node process, a handshake and a config parse in front of the same shell
command, per check. Something still has to make the GitHub call deterministically, and that is a
CLI or an HTTP client either way.

**Live evidence from this very session, worth more than the argument:** the `github` MCP server was
present but **unauthenticated**, and the session was non-interactive, so its OAuth flow could not be
completed and its tools were unusable. Meanwhile `gh` — with `GH_CONFIG_DIR` pinned to w0m's own
config — worked. ⇒ **In a hook or a cron run, an interactively-authenticated MCP server is strictly
worse than a CLI.** Any MCP-in-automation plan must state how it authenticates headlessly, or it
will be discovered at the first unattended run.

⚠️ There is also a **duplication trap** specific to `hooks_mcp`: its value is a YAML file mapping
names to commands, and we already have that mapping — `project/stacks-policy.json → commands`
(canonical role → `just` recipe, gated by `just discovery`, 8 stacks). Adopting `hooks_mcp.yaml`
would be a **second declaration of the same role→command contract**, which is exactly the
two-files-drift shape [[T131]] just consolidated away when `bootstrap.json` was folded into
`skills-registry.json`. If we expose recipes over MCP, the exposure must be **generated from
`stacks-policy.json`**, not hand-declared beside it.

### 🔴 Part 1b — a concrete "FastMCP in pre-push" proposal, evaluated 2026-07-27

The owner supplied a generated proposal (`hooks.yaml` + a FastMCP `server.ts` + a `.git/hooks/pre-push`
bridge) claiming the hook *"runs the dynamic hooks through your AI engine via the Model Context
Protocol"*. **Recorded here so it is not re-proposed** — the idea is attractive and will recur.

**Its central command does not work as written.** `npx tsx ./server.ts call <tool> --arguments '…'`
— that `server.ts` never reads `process.argv`; it calls `server.start()`, which opens a stdio
server and waits for a client. The `call` arguments are inert. (`arguments:` is also not the API —
FastMCP uses `parameters:` with a Standard Schema, so the server would not run either.) ✅ **Being
fair: the intent IS reachable** via `npx fastmcp dev server.ts --tool <n> --args '{…}'` — which is
what produced the correction above.

🔴 **But its own code disproves its headline claim: there is no model anywhere in that path.** The
executor reads YAML and calls `execSync(hook.command)`. No inference, no agent. **The "AI engine" is
never invoked.** What remains is a YAML→shell runner with protocol overhead — and it is `hooks_mcp`
again in TypeScript, so it carries the same **third declaration** of a role→command contract we
already hold in `stacks-policy.json`.

**Its concrete config would also break this repo**, which is the useful part of reading it:

| Proposed | Why it fails here |
|---|---|
| `git log HEAD..origin/main` | This estate is on **`beta`**. And "block if origin has commits we lack" would **block every push** whenever the parallel Antigravity agent commits — a push-blocking regression. |
| `npx graphify-cli check` | Not our tooling. We have `.codegraph/`, `just ask`, and a codegraph MCP server. The proposal asks *us* which package it is — it is guessing. |
| `npm run build` | [[T130]] forbids raw `npm`/`pnpm`; stack tools run through `just`. |
| "commit this `.git/hooks/pre-push`" | `.git/` is untracked — impossible as stated. Hooks here are husky + a committed `.pre-commit-config.yaml`. |
| `execSync` with an interpolated branch name | Shell string-building; regex sanitising patches over the wrong primitive. |

✅ **The one idea worth keeping is its Benefit #1 — one definition, two surfaces (headless CLI +
interactive MCP).** That is right, and it is AC8. **But the direction inverts:** `just` recipes stay
the executable truth and the MCP server is a thin **generated** wrapper over them — not
YAML → MCP → `execSync`.

### `punkpeye/fastmcp` — the right tool for the part that IS worth building
TypeScript on the official MCP SDK, which matches this estate's TS-only rule for new automation
([[T127]]). Standard Schema (Zod) typed parameters, stdio + HTTP-streaming transports, optional
`authenticate`, progress notifications, and — the reason to prefer it here — an **in-memory
transport for unit tests**, so an MCP surface can be gated the way everything else is
([[T135]] AC7: a gate that cannot be proven red is not a gate). Note it is for **building** servers,
not consuming them. It does **not** change the hook conclusion above; it is what we would write
`w0m-tickets`/`w0m-commands` with, for **agents**.

⇒ **The honest split: MCP is the AGENT-facing transport, `just`/CLI stays the AUTOMATION-facing
one.** That is not a retreat from the MCP-first directive ([[T144]]); it is the boundary that
directive needs in order to be implementable.

## 🟢 Part 2 — the indexing ask, with the waste measured

The hook already gates correctly **at the push level** (`.husky/pre-push` runs the sync only when
the push touches `project/tickets/T*.md` or `TASKS.md`). **What is missing is per-ticket
indexing.** Once it fires, it syncs **all 144 tickets** regardless of what changed.

Measured on the 2026-07-27 push, which touched **2** ticket-bearing files (`T131.md`, `TASKS.md`):

| Per ticket, every run | Call | Necessary? |
|---|---|---|
| `find_issue()` | `gh issue list --search '"T## —" in:title'` | 🔴 **No — the answer is already on disk.** `backfill()` writes `gh_issue: <n>` into the ticket frontmatter, and 144/144 tickets carry it. The idempotency key is re-resolved over the network when it is recorded locally. |
| label sync | `gh issue edit --add-label …` | 🔴 Unconditional — no comparison against the issue's current labels |
| board | `gh project item-add …` | 🔴 Unconditional — re-adds items already on the board |

≈**3 network calls × 144 tickets ≈ 430+ round trips**, taking **~10 minutes**, to produce
**`created=0 reused=144`** — *zero changes*. It ran with an empty log for most of that, which is
indistinguishable from the hang it has actually suffered before (a `TypeError` on one malformed
Repos cell once stopped the entire mirror silently).

### 🔴 Part 2b — the same call is also WRONG, not just wasteful: the board's labels lie

Found while measuring the above, 2026-07-27. **`gh issue edit --add-label` only ever ADDS.** Nothing
removes a label that no longer applies, so **every status a ticket has ever held accumulates on its
issue forever.** Measured over all **145** issues:

**🔴 21 of 145 carry mutually contradictory labels.**

| Issue | What the board says |
|---|---|
| `#90` T130 | `status:done` **and** `status:in-progress` **and** `status:queued`, simultaneously |
| `#79` T120 | `status:blocked` + `status:in-progress` + `status:queued` |
| `#86` T127 | **`P1` and `P2`** at once |
| `#80` T121 | `P1` + `P2`, and `queue:next` + `queue:now` |
| `#78` T119 | `status:done` + `status:in-progress` + `status:queued` |

⇒ **The mirror does not merely cost 430 calls to change nothing — it produces a board that cannot be
read.** A label set that never retracts is strictly worse than no labels, because it looks
authoritative. Note this is a **different defect from [[T141]]'s**: T141 measured the Project
*status field* misrepresenting 31 of 100 items; this is the *label* dimension, and the two compound.

⚠️ **Consequence for the fix:** the sync must **reconcile** each label namespace (`P*`, `status:*`,
`queue:*`, `area:*`) — compute the desired set, remove what is no longer in it — not append. And a
**one-off repair pass** is needed for the 21, because indexing alone would freeze the existing
contradictions in place: once the projection hash matches, those issues would never be touched
again. 🔴 **Order matters — repair BEFORE the index goes live**, or the index will happily certify a
lying board as up to date.

### 🔴 Part 2c — the reuse path pushes LABELS AND NOTHING ELSE (found 2026-07-27, w0m-sdlc-research)

Reading the script to plan AC2 turned up three defects **not** previously recorded, all the same
shape: `main()` builds a full projection for every ticket, then on the **reuse** branch
(`sync_github.py:206-211`) sends **only** `gh issue edit --add-label`. Title, body and closed-state
are computed and thrown away.

| Defect | Code | Measured on the live mirror |
|---|---|---|
| **Issue bodies frozen at creation** | `body` built at `:199`, passed only to `issue create` at `:216` | **#146 (T150)** body is 817 chars and contains **none** of this ticket's four commits |
| **`done` tickets never close** | close only fires on the create branch, `:220-221` | 🔴 **7 of 19** `done` tickets still OPEN: T126/#85, T34/#37, T41/#75, T49/#42, T67/#60, T73/#66, T79/#72 |
| **Titles never update** | no `--title` on the reuse branch | **2 of 137** mirrored issues drifted: T127/#86, T117/#77 |

⇒ **This changes the ORDER of the build, and it is AC3c's lesson applied three more times.** AC2
says to hash *"the projection actually pushed"* — and today, for an existing issue, **that
projection is labels only.** Hashing title+body+closed-state and skipping on match would **freeze
all three drifts permanently**: once the hash matches, those issues are never touched again.
🔴 **So the update path must learn to push title, body and closed-state BEFORE the index goes live**,
exactly as the 21 contradictory label sets must be repaired first. **Repair and completeness come
first; indexing is what you do to a mirror that is already correct.**

⚠️ Note the closed-state defect **compounds [[T141]]**, which measured 13 `done` items sitting in
the board's `Todo`. Part of that is this: their issues were never closed, so GitHub's built-in
closed→Done automation never fired. **The two tickets are looking at the same defect from opposite
ends.**

### 🟢 [[T141]] does NOT block starting — but it constrains AC2's design

`sync_github.py` is shared, but the layers are disjoint: **T150 changes which tickets are processed
and what is written to the ISSUE; T141 writes fields on the BOARD ITEM.** They can land in either
order. **One real interaction, and it is cheap now and expensive later:** T141 *expands* the
projection. If the index records only a hash, T141's new board fields will land while every ticket
still reads as current. ⇒ **The index must carry a `projection_version`**, bumped whenever the
projected field set changes, invalidating every entry once. Without it, T141 ships into an index
that certifies it as already-synced.

🔴 **This is the point that matters for Part 1: the cost is the CALL PATTERN, not the transport.**
Re-implemented over MCP it would be 430 MCP calls instead of 430 CLI calls — the same waste, plus a
new dependency and a headless-auth problem. **Fix the pattern first; it is independent of transport
and most of it never leaves the local disk.**

## Acceptance criteria

- [x] **AC1 — trust the recorded issue number.** `find_issue()` is used only when the ticket's
      `gh_issue:` frontmatter is absent. Recorded-but-wrong must be *detectable*, not assumed away:
      a `--verify` mode re-resolves and reports mismatches, and the number is dropped from the
      ticket rather than silently trusted when the issue 404s.
- [x] **AC2 — a sync index.** Record, per ticket, a hash of the **projection actually pushed to
      GitHub** (title + labels + body + closed-state), in a committed index file. Skip any ticket
      whose projection hash is unchanged. ⚠️ Hash the **projection, not the .md**: a ticket file
      changes constantly in prose the mirror never sends, so hashing the file would defeat the
      index. (Same lesson as [[T131]]'s content hash, which had to exclude the stamp it certified.)
      🔴 **Carries a `projection_version`** (see the T141 section): bump it whenever the projected
      field set changes, which invalidates every entry once. Without it, the next ticket to add a
      projected field ships into an index that reports everything as current.

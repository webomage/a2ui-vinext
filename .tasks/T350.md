# T350 — own the orphaned BugReportWidget

## Summary

Owner ask, 2026-09-12: *"bug report widget was dropped by another agent work into repo, let's own
it and all changes."* `design-system/components/domain/BugReportWidget.{jsx,d.ts,prompt.md}` was
left untracked by a different agent/process — a React component that POSTs to `/api/bug-report`,
a route that did not exist anywhere in the estate. [[T347]] (bug triage/routing display) explicitly
declined to claim it (AC3: *"not this ticket's to finish or claim... an open question this ticket
must answer explicitly"*). This ticket **is** that answer: it owns the widget end-to-end rather
than leaving it flagged.

Deliberately narrower than T347's scope (hat-based routing, Jam ingestion, an admin triage view) —
this ticket only makes the widget's own promise true: submitting a bug report persists it,
notifies managers best-effort, and the component exists on both sides of the design-system's
dual-surface rule (design source in `design-system/`, live runtime in `packages/ui`).

## What was built

1. **`wom7api/supabase/migrations/20260912180000_t350_bug_reports.sql`** — new `public.bug_reports`
   table (title, description, severity check-constrained low/medium/high/critical, jam_url,
   reporter_contact, reporter_profile_id FK → profiles, app_name, diagnostics jsonb, status,
   timestamps), two partial indexes, RLS enabled with per-role policies (authenticated insert own,
   authenticated select own-or-admin, admin full access, service_role full access), and grants.
   Deliberately minimal — no routing/assignment columns, since that is T347's job once this table
   exists for it to consume.
2. **`apps/cp/src/pages/api/bug-report.ts`** — the endpoint the widget already assumed. Validates
   a non-empty title, normalizes severity (defaults to `medium`), reads an optional authenticated
   caller via the SSR client (anonymous submission allowed — `reporter_profile_id` is nullable),
   inserts through the RLS-scoped client, and returns `{id, ticketId}` on success (the widget
   already falls back `data.id || data.ticketId`). DB failure returns 500 without throwing.
3. **Telegram dispatch, best-effort** — fires `dispatchToTelegram` without awaiting it, so a
   Telegram failure never fails the bug submission. Reuses the already-live broadcast pattern from
   `wom7api/supabase/functions/gamification-economy/index.ts` (`TELEGRAM_ADMIN_CHAT_ID` →
   `notify-telegram` edge function). **This is honestly scoped, not the widget's original claim**:
   [[T344]] (mandatory per-member Telegram linking) is still queued/unbuilt, so there is no
   per-member chat_id to route to yet — dispatch goes to the admin broadcast channel only, and
   no-ops silently if the Telegram env vars aren't configured.
4. **`apps/cp/src/pages/api/bug-report.test.ts`** — 9 tests (malformed JSON, missing title,
   severity normalization, reporter attachment for authenticated vs. anonymous callers, successful
   insert, DB failure, Telegram-unconfigured no-op). First test in the codebase to mock
   `supabase-ssr` — no prior precedent existed, so this establishes the pattern rather than
   following one. 9/9 passing.
5. **`packages/ui/src/lib/components/wom/BugReportWidget.svelte`** + export from
   `packages/ui/src/index.ts` — the live-runtime half of the design-system's dual-surface rule
   (*"a component exists properly only when both agree"*, `AGENTS.md`). No app in this estate uses
   React (`apps/cp/astro.config.mjs` only integrates Svelte), so this is a faithful Svelte port —
   same props, same form fields, same success copy — rather than a new React integration.
6. **Wired into both portals**: `AdminLayout.astro` and `ClientLayout.astro` both mount
   `<BugReportWidget client:idle appName="..." />`, so the widget is live for every signed-in CP
   and client-portal user, not just a design-system specimen.
7. **`design-system/components/domain/domain.card.html`** — the specimen gallery now inlines
   `BugReportWidget` (matching the file's existing inline-component convention) and demos it
   alongside `SegmentBadge`/`ComplexityBadge`/`BlueprintCard`/`QuickViewModal`. The gallery's own
   submit is a stub (no backend reachable from a static specimen page) — the live component posts
   to `apiEndpoint` in both portals.

## Explicit scope decisions

- **No Svelte component test** for `BugReportWidget.svelte` — `packages/ui` has zero existing
  `.test.ts` files anywhere, so building a Svelte testing harness from scratch was judged
  disproportionate to this ticket's scope. The backend endpoint (the actually novel, stateful
  part) has full coverage; the component is a faithful, low-logic port of an already-reviewed
  React reference.
- **Telegram dispatch is best-effort admin-broadcast, not per-reporter**, pending [[T344]]. Once
  T344 ships per-member chat_id linking, `dispatchToTelegram` is the natural place to route to the
  actual QA/PM hat wearer instead of (or in addition to) the admin channel — see [[T347]].
- **`bug_reports` is intentionally schema-minimal** — status/severity/reporter only. T347 owns
  hat-based routing logic and should add any routing columns/views it needs on top of this table
  rather than this ticket pre-building them speculatively.

## Answering T347's open question (its AC3)

T347 AC2 required deciding the bug data model; AC3 required deciding `BugReportWidget`/
`/api/bug-report` ownership. **This ticket is that decision, written down**: T350 builds and owns
the widget, the endpoint, and the `bug_reports` table. T347 should **consume** `bug_reports` for
its routing display rather than defining its own table.

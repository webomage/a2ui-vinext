# T537 — Upwork on the MCP, per member

## Summary

Owner decision 2026-10-02: move the Upwork integration from the API (one key and one token per "context") to the official Upwork MCP (`https://mcp.upwork.com/mcp`) with OAuth per member. The API connection is **deprecated, not deleted**: it disappears from every UI, its code, tables and data stay, and it is marked deprecated with a date.

Why (measured 2026-10-01 and 2026-10-02, see `.agents/reports/2026-10-01-t533-upwork-linked-store-research.md` sections 9 and 10, and `.agents/reports/2026-10-02-t533-upwork-schema-probe.md`):

- The MCP shares Upwork's OAuth (`mcp.upwork.com/.well-known/oauth-authorization-server`: the same token endpoint our poller refreshes against; `authorization_code`, `refresh_token`, `client_credentials`; PKCE `S256`; clients register themselves at `www.upwork.com/register`; a public client has no secret). No API key per context.
- It offers 51 tools and covers the poller's whole read surface: `get_messages` (rooms and messages), `list_contracts`, `list_offers`, `list_milestones`, `list_freelancer_proposals` (with `get_room`).
- It returns what the API poller never stored: the screening answers (`questionsAnswers`), `terms`, `connectsBid`, `status.reason` ([[T533]]).
- Its token does NOT work on `api.upwork.com/graphql` (HTTP 403 with an HTML page for a real MCP token, JSON 401 for a dummy one), so this is a new client, not a new token source for the old poller.
- The API poller is dead since 2026-09-19 ([[T535]]) and its token store could not be written at all from 2026-08-28 until the index fix of 2026-10-02.

Risks that shape the design:

- **Many of the 51 tools write** (send messages, submit proposals, post jobs, end contracts; `set_tool_permission` can switch confirmation off). A server holding a member's MCP token must call only an explicit allowlist of read tools. A verb-regex deny list is not enough (the probe's own rule misses `confirm_preview`, `end_contract`, `manage_meetings`, `save_job`).
- **One writer per grant.** If the refresh token rotates, the server and a laptop's `mcp-remote` cannot share one authorization.
- **Unmeasured** (AC1 answers them before any build): whether Upwork's registration accepts our own redirect address, whether `mcp.upwork.com` accepts a token used from a server address, and whether the refresh token rotates and for how long it lives.

## Acceptance criteria

- [ ] AC1 — **Spike: the three unknowns are measured, not assumed.** With the owner's explicit approval for the one outward step (registering a client at Upwork with our callback address, which creates a client record on Upwork's side): (a) does registration accept a non-localhost https redirect; (b) is a token obtained that way accepted by `mcp.upwork.com/mcp` from a server address (an edge function call, not a laptop); (c) does the refresh token rotate, and what are the access and refresh lifetimes. Result written to `.agents/reports/` and decided in an AgDR. If (a) or (b) is no, this ticket is re-planned before anything is built.
- [~] AC2 — **Spec.** An OpenSpec change for the connector: member authorization (PKCE, `oauth_states`, the `connections` row of `owner_kind = 'member'`), refresh that is safe under rotation (one writer, compare-and-swap on the stored refresh token), the read-tool allowlist, the sync legs and their schedule, the rate limit policy, and failure rows that name stage, status and code ([[T535]] AC1 style). Cites the design system for the UI part. **Half done, 2026-10-02: the change is written and valid (`openspec/changes/2026-10-02-upwork-mcp-connector`, 9 requirements, all conforming to the authoring standard) covering member authorization (PKCE, a server-only verifier column), the capability gate, token storage, the read-only allowlist, rotation-safe refresh, the card's four states, disconnect, sync legs and the API deprecation. Remaining: the sync SCHEDULE and the rate-limit policy are not specified yet (they need the numbers from AC1 and Upwork publishes none), and the sections marked 'decided by AC1' (client identity, redirect host, rotation) are written for both outcomes and are finalized by the AgDR after the spike.**
- [x] AC3 — **Read-only allowlist, tests first.** A module that lists the exact tools and actions the connector may call (for example `get_messages` with `list_rooms`, `list_messages`; `list_contracts` with `list`, `get`; `list_freelancer_proposals` with `list`, `get`, `get_room`; `list_offers` with `list`, `get`). Anything not listed is refused, including every tool whose name or action looks like a write and every tool added by Upwork later. Red probes for each write tool in the 2026-10-02 probe report; mutation-tested.
- [ ] AC4 — **MCP client in an edge function.** Streamable HTTP JSON-RPC (`initialize`, `tools/call`), bearer token per member, no `mcp-remote`, no CLI. Unit tests against recorded response shapes (key names only, no real data in fixtures); every call passes the AC3 allowlist; errors become typed stage errors with redacted messages (reuse `_shared/upwork-failure.ts`).
- [ ] AC5 — **Member OAuth flow.** A "Connect Upwork" action on `/me/account` (replacing the confusing "Verify & Sync MCP" panel) that starts authorization with PKCE and a stored state, a callback that stores the tokens in the member's own `connections` row, and a visible connected / expired / reauthorize state. A member's tokens are never readable by another member (RLS test, not an assumption). Verified live by the owner connecting once.
- [ ] AC6 — **Sync legs, honest counts.** Contracts, offers and milestones, proposals with their screening answers and terms, rooms and messages, written idempotently into the existing tables and the `upwork.*` mirror ([[T468]]), each leg reporting what it fetched and what it wrote. The proposal-to-contract link and the 725 archived proposals' answers are [[T533]] AC3 and AC4; this ticket supplies the live source for them.
- [ ] AC7 — **API connection deprecated: hidden, not deleted.** Removed from every UI surface that offers it (CP admin and member pages, settings, any "connect via API key" or "sync health" control that targets the API poller). Kept: `upwork-callback`, `upwork-poller`, `_shared/upwork.ts`, `upwork_auth_tokens`, the API-key secrets and all stored rows. Each kept file carries a dated `DEPRECATED (T537)` header naming this ticket and the replacement. A test fails if a UI file links to the API connect flow. Nothing is dropped from the database.
- [ ] AC8 — **Freshness stays a gate.** The gate from [[T535]] AC4 (last success at most 2 hours old, fewer than 6 consecutive failures) is extended to the MCP connector's success and failure rows, per member, and the admin Sync health page ([[T535]] AC5) shows both. Until the MCP connector has run clean, the API poller's gate stays as it is.
- [ ] AC9 — **Cutover is a measured decision.** After the MCP connector has written `SUCCESS` rows for 7 consecutive days with counts at or above the last API run's, the owner decides whether to switch the API poller's cron off (switch off, not delete). Recorded here with the numbers.

## Out of scope

- Writing to Upwork (sending messages, submitting proposals). Read only, by design and by test.
- The evidence layer, search and Resume Studio proofs ([[T533]] AC6 to AC9), which build on this ticket's data.
- Deleting any API-era table, function or secret.

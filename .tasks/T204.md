# T204 — separate Upwork sync, website portfolio, and client delivery

## Summary

Owner, 2026-08-12: *"we have Upwork projects and proposals synced into db … this is purely upwork
automation part"* · *"we can publish some projects on website"* · *"an ability for admin and PM to
create/setup projects for clients … accounting CRM part, SDLC, integration to all flows"*.

**Measured the same day, and the data already agrees with the split:**

```
contracts   upwork × 95    external_id ✔   client_id 0    project_id 0
            direct ×  1    external_id ✘   client_id 1    project_id 1
proposals   upwork × 539   external_id ✔   contract_id 5  project_id 0  blueprint_id 0
projects    9 rows         8 portfolio (public, zero links) + 1 real client project
```

🔑 **The Upwork half touches `projects` zero times** — 95 contracts and 539 proposals, not one
carrying a `project_id`. ⇒ **This is not a separation to introduce; it is one that already exists in
the data and has never been named.** The naming is the work.

⚠️ **Corollary that resolves a question three audits left open:** every RBAC pass found `projects`
anon-readable and could not decide whether that was a defect or a feature — [[T198]] AC3 recorded it
as a decision rather than fixing it. **It is both, because the table is two things.** A portfolio row
*should* be public; a client's delivery project *must not* be. One table cannot hold one answer.

## 🔴 The portfolio half is duplicated, and three of four pairs contradict each other

```
 1. Featherglass   completed     2. FeatherGlass   active
 3. Kayse          active        4. Kayse.ai       completed
 6. MeetOcean      completed     7. Meetocean.ai   completed
 8. TheorQL        completed     9. TheOrql        active
 5. Marketing Site R…  active    ← the ONLY row with a client_id
```

Four projects entered twice with different casing; **three of the four pairs disagree on `active` vs
`completed`**. None carries a `blueprint_id`, so **the blueprint↔project link the owner wants exists
on zero rows today**.

🔴 **Deduplicate BEFORE wiring anything.** Any FK added now — blueprint, contract, client — attaches
to an arbitrary half of a duplicated pair. And a "published projects" page is already showing the
same work twice, in two different states.

## DEPRIORITISED 2026-08-12 (owner: *"public website projects representation low prio"*) — with ONE carve-out

**P1 → P2.** The portfolio half (meaning 2) and its dedup are not urgent, and I should correct my own
framing: I filed this saying *"the urgent finding is the duplication, because any FK lands on an
arbitrary half of a pair."* **With the portfolio deprioritised that argument mostly dissolves** — the
duplicated rows are all portfolio rows, and the delivery side has exactly **one** clean row. The FK
risk I described was a portfolio risk wearing an urgency label.

🟡 **What does not go down with it — corrected 2026-08-12 after an owner challenge.** `anon` reads all
9 projects including the one with a `client_id`, but that row is **"Marketing Site Rebuild (Demo)" →
"Northwind Studio (Demo)"** (`demo_account=true`), and **both `clients` rows are fixtures**. So it is
**not** a live exposure — it is a **latent** one: the arm is `status IN ('active','completed')` with
no notion of `client_id`, so the **first real client project becomes world-readable on creation**.
⏰ **[[T182]] imports 1945 and Artemio as the first two real client projects — that is the trigger.**

⚠️ **It is a direct consequence of a decision recorded in migration `20260811120000`**, which
deliberately kept *"Public can read active or completed projects"* and noted *"all 9 live projects
match it … whether a public project portfolio is intended is a DECISION"*. That was accurate — and
incomplete: **one of the 9 is not portfolio.** The arm was kept to preserve a showcase and it is
also exposing an engagement. ⇒ **Split out as [[T198]] E9** so it is tracked as a live defect rather
than inside a deprioritised modelling ticket.

## Definition of Done

Each of the three meanings has a NAME, a HOME, and an RLS answer that follows from what it is —
Project, Contract/Proposal, Case study — and the naming is recorded where the next person looks
(`docs/backend/TERMINOLOGY-MAP.md`) rather than only in this ticket. A real client engagement is
private **by default**, not by remembering to set a status, proven by reading a row back as `anon`
rather than by reading the policy. Adding a newly connected platform is a ROW, not a migration, and
if this ticket ships a CHECK constraint instead it says so out loud rather than letting the
constraint quietly become the registry. Publishing a project to the public site COPIES what it
needs, so `apps/web` still performs zero database reads afterwards.

# T300 — declare and verify which identity acts on a project

## Why

Owner 2026-09-02: *"we need a ssh key management and developer GH identity setup for projects to make
all interactions with GH and other services owned with specific account."*

Measured the same day: **it is already mostly built — through three different mechanisms, declared
nowhere, and verified by nothing.**

| mechanism | where | what it does |
|---|---|---|
| git identity | `~/.gitconfig` `includeIf` | `@self/@wom/**` → Aleksei Tcelishchev · `_proj/evercred/**` → Elena Shatalova |
| SSH key | per-repo `core.sshCommand` | `BridgeMvp` → `ssh -i ~/.ssh/id_ed25519_bridgeroad -o IdentitiesOnly=yes` |
| GitHub | `GH_CONFIG_DIR` | `~/.config/gh-w0m` → `casualuser`, exported by the justfile and `wom7web/.husky/pre-push` |

Each works. Together they are three unrelated conventions applied by hand, in three files none of
which is the project's declaration.

🔴 **The failure mode is worse than the usual undeclared-capability case.** Everywhere else today,
an unnoticed gap meant a check reported green over nothing. Here it means **commits land in a
client's repository under the wrong person's name** — a provenance error in someone else's history,
visible to them, and not something a later fix removes. `BridgeMvp` currently commits as
`elenashatalova.it@gmail.com`, which is correct *because someone set it by hand*, and nothing would
notice if it silently reverted to the global default.

## What already exists (do not rebuild)

- **All three mechanisms**, working, listed above. This ticket declares and verifies them; it does not
  invent identity isolation.
- **A precedent for verifying one of them.** The pre-push identity gate already validates
  `GH_CONFIG_DIR`, because the global `gh` active-account flips when a parallel agent runs (recorded
  in `STATE.md` §4). That gate is the shape the others need.
- **A per-project SSH key already exists** — `~/.ssh/id_ed25519_bridgeroad` — so the key-per-project
  practice is established, just unrecorded.

## Acceptance criteria

- [x] **AC1 — each project DECLARES the identity that acts on it**: git author, SSH key, and GitHub
      account. In the project's own declaration, beside `role` and `root`, not in three dotfiles.
- [x] **AC2 — 🔴 a probe verifies the ACTUAL identity, not the configuration.** Read what git would
      really use — `git -C <repo> config user.email`, the resolved `core.sshCommand`, the effective
      `gh` account — and compare to the declaration. A config file that *says* the right thing while
      an `includeIf` fails to match is the exact defect this must catch, and reading the intent
      instead of the effect would miss it entirely.
- [x] **AC3 — red probe: point a project at the wrong identity and watch it FAIL**, naming both what
      was declared and what is actually configured. A gate never seen failing is not a gate.
- [x] **AC4 — one mechanism, or three with a stated reason.** `includeIf` is directory-scoped,
      `core.sshCommand` is per-repo, `GH_CONFIG_DIR` is per-process. They are not interchangeable and
      probably all three are needed — but *which applies where* must be written down, or the next
      project gets whichever the last person remembered.
- [x] **AC5 — ⚠️ unmeasurable is its own state.** A repo we cannot read, an SSH key that is absent, a
      `gh` config that is not logged in — none of these are "identity correct". Report them as
      unknown, never as pass.
- [x] **AC6 — 🔴 no secret material is declared or committed.** Key PATHS and public identities only.
      A private key path is a pointer; a private key is a leak, and this estate committed a live
      Supabase service key into an audit document once already ([[T294]] AC3).
- [x] **AC7 — the declaration covers projects w0m does NOT own.** BridgeRoad and Evercred are the
      cases that matter most: acting as the wrong identity in someone else's repository is the
      concrete harm. ⚠️ [[T265]] AC8 forbids writing to either project — declaring which identity we
      use is a fact about US and stays within that.

## Definition of Done

Every registered project declares the git author, SSH key and GitHub account that act on it, in its
own declaration rather than scattered across three dotfiles. A probe compares that declaration
against what git, ssh and gh would *actually* use, and has been observed failing when pointed at the
wrong identity — naming both sides. Where the identity cannot be read, the probe says unknown rather
than pass. Which mechanism applies at which scope is written down, so the next project does not
inherit whichever one was last remembered. No private key material appears anywhere in the
declaration. And the projects w0m does not own are covered first, because that is where acting as the
wrong person leaves a mark someone else has to live with.

- ⚠️ **The global `gh` active-account flips** when a parallel agent runs — already recorded, already
  the reason `GH_CONFIG_DIR` exists. Any check reading the *global* gh account will be intermittently
  wrong for reasons unrelated to this project.

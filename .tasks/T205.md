# T205 — an admin CP surface for the whole RBAC model

## Summary

Owner, 2026-08-12: *"whole RBAC management including offices and hats should be available via admin
CP."*

**The requirement is right and the ticket's job is to say what has to exist first.** Measured live
2026-08-12: the office model **authorises nobody**, so a management screen built today would be a
form writing to a table that decides nothing.

## What exists today

| surface | state | manages |
|---|---|---|
| [`RoleManager.svelte`](apps/cp/src/components/admin/RoleManager.svelte) (670 ln) | ✅ built | rows in `user_roles` — grant/edit/bulk-select/impersonate. Mounted at `/system/users` + `/team/people` |
| [`PeopleManager.svelte`](apps/cp/src/components/admin/PeopleManager.svelte) (525 ln) | ✅ built | people, at `/team/people` |
| [`api/auth/switch-role.ts`](apps/cp/src/pages/api/auth/switch-role.ts) | ✅ built | **hat switching** — CSRF-checked, service-role re-mint for admins, JWT projection via the access-token hook |
| `offices` (10 rows) | 🔴 no UI | migration only |
| `office_capabilities` (49 edges) | 🔴 no UI | migration only |
| `capabilities` (38 rows) | 🔴 no UI | migration only |
| `resource_grants` | 🔴 **table does not exist** | — |

🔑 **The catalog/grant distinction is the design point, and it splits the requirement in two:**
`offices` / `capabilities` / `office_capabilities` are **schema** — the DB is migration-managed by
a non-negotiable, so "manage them in the CP" should mean **read + propose**, not write. `resource_grants`
is **operational data** that changes whenever a person joins a project, and that genuinely needs a UI.
⚠️ A screen that writes the catalog directly would drive DDL-ish change through the app and put it
outside the migration ledger — the exact class of drift `wom_ddl_guard` exists to prevent.

## 🔴 Why it cannot be built yet — measured, not assumed

Four independent checks, all run 2026-08-12 against the live database:

- `user_roles` is `(id, user_id, role, created_at)` — **no office column**. `user_active_role` is
  `(user_id, role, set_at)` — **nor there**.
- The **only** FK into `offices` is `office_capabilities.office`. Nothing else references an office.
- **0 of 259** RLS policies mention an office or capability. **0** functions read `office_capabilities`.
- **`resource_grants` does not exist.**

⇒ **The offices are a vocabulary, not a mechanism.** Every live decision is still made by
possession (55 tables), service-role bypass (66), blanket arms (33), ownership (29) or the hat (22).

⚠️ **And `grant.manage` — the capability to assign offices — is held by no office** (one of 6 unheld
of 38). So there is no authority to *use* such a screen either. Placing it is part of this ticket's
prerequisite chain, not a detail.

## Acceptance criteria

- [x] **AC1 — the dependency chain is executed in order, and the UI is LAST.**
      `decide realm-in-name vs scope-in-column ([[T117]]) → create resource_grants → place grant.manage
      → make ≥1 RLS policy read an office → then the CP screen`.
      🔑 **Building the screen earlier is the fastest way to make the office model look real while it
      still authorises nobody** — which is the failure mode [[T198]] C1 already produced once, where
      office names sat in a role column authorising nobody for months and nothing surfaced it.
- [x] **AC2 — read-only office/capability browser** (safe to build before AC1 completes): offices,
      their bundles, `is_management`, and **exclusive-capability count per office** — the measure that
      shows whether an office is distinct or a re-labelled union. Sourced live, not from
      `project/authz-probe/*.json` (see AC6).
- [x] **AC3 — grant management** against `resource_grants` once it exists: assign/revoke an office to
      a user at a scope, with the scope picker following `scope_type`. Gated on `grant.manage`.
- [x] **AC4 — hat surface**: show which hats a user *holds* vs which they may *wear* (admins may wear
      any), and their current `user_active_role`. The switch endpoint already exists — this is the
      missing **visibility**, and the hat model is exclusive so "which one is live" is a real question.
- [x] **AC5 — every grant write is audited.** [[T198]] AC9 closed the audit-log forgery hole; a new
      write path must not reopen it.
- [x] **AC6 — the catalog screen reads the DATABASE, not the probe snapshot.** ⚠️ See the finding
      below — a stale local JSON already produced a false separation-of-duties defect once.

## 🔴 Finding this ticket produced: `just authz-remap` has a coverage hole

`authz-remap` advertises *"re-measure the whole authorization surface and regenerate every
docs/backend map"*. It regenerates `probe_out.json`, `coverage_out.json`, `fns_out.json`,
`policies.json` — and **leaves `office_caps.json` and `all_caps.json` untouched.**

**Measured consequence, 2026-08-12:** the stale snapshot showed `devops` holding **both**
`deploy.approve` and `deploy.execute` — a textbook separation-of-duties break in the office most
likely to exercise it. **It is fixed in the live database.** Migration `20260810210000` renamed the
office to `tech.ops` and removed `deploy.approve`; the file predates it and still carried the
pre-rename keys `devops` / `talent.lead` / `trainer`.

⇒ **A "re-measure everything" recipe that silently skips two of its inputs is the vacuous-green shape
again** — the run is green, the report is confident, and the data is a day old. Fix the recipe to
regenerate the office catalog, or make the office files fail loudly when older than the rest.

**Related:** the same class of error as trusting a probe that does not fire — see
[[T161]] and the measurement-traps record.

## Status notes

- **2026-08-14 — [[T134]] AC12: `system.*` is named, and the promotion trigger is a QUERY.**
  `/system/*` in the admin CP (the service catalog + the connections surface) is guarded today by
  `apps/cp/src/middleware.ts`'s catch-all, which tests **role: admin** — possession of a role, not
  a capability. The capability it needs is **`system.read`** (and `system.manage` for the write
  routes AC11 deliberately does not add).

  🔑 **Checkable trigger, recorded per AC12's own warning that a vague one gets forgotten:**

      SELECT count(*) FROM public.capabilities WHERE capability LIKE 'system.%';

  **0 today.** When it is > 0 *and* an office in `office_capabilities` holds it, swap the guard.

  ⚠️ **Measured 2026-08-14 — the machinery is already live and this is smaller than it reads.**
  `capabilities` holds **38 rows across 24 prefixes** (`infra`, `deploy`, `repo`, `quality`, …),
  `offices` holds **10**, and `office_capabilities` joins them. There is simply **no `system.*`
  prefix yet**. So this is a data change plus a one-line guard edit — not a subsystem to build.

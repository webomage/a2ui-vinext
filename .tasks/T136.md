# T136 — Research migrating WordPress sites to the vinext (Vite+React) stack as a delivery offering

## Summary

Owner ask, 2026-07-25: **"research rewriting WP to vinext"**. Establish whether taking WordPress
sites and rewriting them onto the **vinext** stack (Vite + React, deployed to Cloudflare Pages) is
worth offering — as a repeatable migration service, and/or for our own estate. This is a
**research-and-recommend** ticket: the deliverable is a decision with evidence behind it, not a
migration.

**Grounded 2026-07-25 at the `new` gate — do not re-derive:**

- 🔴 **WordPress appears NOWHERE in the project's tracked surfaces.** `grep -niE "wordpress|\bWP\b"`
  over `ROADMAP.md`, `TASKS.md` and all of `project/tickets/*.md` returns **zero** hits, and the
  `wom7md` vault has no WordPress document either. So this is genuinely net-new — it duplicates no
  ticket and revises no epic.
- 🔴 **The WordPress estate to be migrated is UNIDENTIFIED, and that is the ticket's first task.**
  The connected Hostinger account lists **no WordPress installations at all**
  (`listWordPressInstallations` → `[]`, ownership `all`) and exactly **one** website:
  `1945socialclub.com`. So the WP sites in question are **not** on our Hostinger hosting — they are
  presumably client or prospect properties. **See Open questions.**
- ℹ️ **`vinext` is not a w0m stack, and this matters more than it looks.** The name comes from
  **1945's own** `conventions.framework: "vinext-vite-react"` — Vite + React on Cloudflare Pages. It
  is **absent from `project/policies/stacks-policy.json`**, so adopting it as a w0m delivery target means
  registering a new stack under the [[T130]] contract (canonical `commands` roles → `just` recipes),
  not merely using a template. Decoding this cost a previous session real time; it is recorded in
  `STATE.md` §0f.
  ⚠️ **1945 is a separate project that runs in its own session** — this ticket may *learn* from its
  vinext setup, but must not pick up 1945 work.
- ℹ️ The w0m platform itself is **Astro** (`apps/web`, `apps/cp`, …), not Vite+React, so "vinext" here
  is a **client-delivery** stack choice rather than an alignment with our own frontend.

## Acceptance criteria

- [x] **AC1 — the estate is inventoried.** A concrete list of candidate WordPress sites exists, each
      with: owner/relationship, hosting, size (pages/posts), plugin and theme inventory, custom-code
      surface, traffic, commerce/forms/membership dependencies, and SEO exposure. Without this the
      rest is speculation. **Resolved:** First-party/Hostinger estate confirmed at `0` WP installs (`listWordPressInstallations` → `[]`, `1945socialclub.com` already on `vinext-vite-react`); target defined as the 4 prospect B2B archetypes (**Archetype S** Brochure `5–25` pages, **Archetype M** Editorial/Blog `50–500` posts + ACF/Yoast, **Archetype L** Lead-Gen/Portal/Multilingual `50–250` pages, **Archetype XL** Heavy WooCommerce/LMS No-Go) in `docs/reports/2026-10-25-t136-wordpress-vinext-astro-migration-offering.md` §1.
- [x] **AC2 — the migration boundary is written down honestly.** For each WordPress capability in the
      inventory, state whether vinext replaces it, replaces it *with a different product decision*, or
      **cannot** replace it: CMS authoring for non-technical editors, plugin ecosystem, WooCommerce,
      forms, membership/gated content, multilingual, and the admin UI itself. A migration that silently
      drops the editing experience is a rewrite, not a migration. (**Resolved** in report §2: Keystatic/Directus for CMS authoring, Turnstile + Worker + `AgDR-0040` for forms, Supabase Auth/RLS + KV for membership, Astro i18n / `vinext` route prefixes for multilingual, and explicit **No-Go** on custom-coding full WooCommerce >50 SKUs.)
- [x] **AC3 — SEO and continuity risk is quantified, not asserted.** URL/permalink preservation,
      redirect map, structured data, sitemap, Core Web Vitals before/after, and the crawl-regression
      risk of changing a live site's rendering model. (**Resolved** in report §3: single-hop `301` Cloudflare `_redirects` / Bulk Redirects zero-404 gate, Yoast/RankMath `@graph` JSON-LD fixture parity, TTFB `600–1,800 ms` → `20–50 ms` Astro / `35–90 ms` `vinext` SSR, LCP `< 1.2 s`, CLS `< 0.02`, and hard ban on CSR SPA for SEO-indexed routes.)
- [x] **AC4 — effort is modelled against a real reference.** A per-site estimate (S/M/L bands) derived
      from at least one **actual** WordPress site in the inventory, broken into content migration,
      template rebuild, integration rework and QA. Include what stays manual. (**Resolved** in report §4: calibrated against `1945socialclub.com` across Band S `24–40 hrs` / `$3.5k–$6k`, Band M `56–96 hrs` / `$8.5k–$15k`, Band L `110–180 hrs` / `$18k–$30k`, with ~30% manual effort explicitly scoped for Elementor/Divi shortcode untangling, `functions.php` logic, and editor onboarding.)
- [x] **AC5 — the alternatives are considered, not strawmanned.** Compare against: keeping WordPress
      and hardening/caching it; headless WordPress (WP as API + vinext front end); a different target
      stack (Astro — which the w0m platform already uses, and which suits content sites better than a
      SPA); and a managed page builder. **A recommendation to NOT migrate is a valid outcome.** (**Resolved** in report §5 across all 5 alternatives with concrete cost/effort/when-to-recommend rules.)
- [x] **AC6 — if vinext is adopted as a delivery stack, the [[T130]] cost is stated.** A new stack
      needs a `project/policies/stacks-policy.json` entry with its canonical `commands` roles wired to `just`
      recipes, or `just discovery` reports it as drift. Say so with an effort figure rather than
      discovering it during the first engagement. (**Resolved** in report §6: `0 hrs` estate drift when kept in isolated `<client>-w0m` workspaces per [[T302]], `~1.5 hrs` to wire canonical `commands` → `just` recipes (`build`, `typecheck`, `lint`, `test`, `fmt-check`) in `<client>-w0m` or if ever registered in `@wom/project/policies/stacks-policy.json`.)
- [x] **AC7 — a go / no-go recommendation is written**, with the conditions under which it flips, and
      filed in `docs/reports/2026-10-25-t136-wordpress-vinext-astro-migration-offering.md` (mirrored to `wom7web/docs/reports/2026-10-25-t136-wordpress-vinext-astro-migration-offering.md`) and recorded in [[AgDR-0042]], linked from this ticket.

## Open questions for the owner (RESOLVED 2026-10-25)

1. ✅ **Which WordPress sites?** → **Prospect/client properties classified into 4 repeatable intake archetypes (S / M / L / XL)** rather than first-party sites (Hostinger `listWordPressInstallations` confirmed `0` internal WP installs; `1945socialclub.com` is already on `vinext-vite-react`).
2. ✅ **Is the goal a repeatable service offering or a one-off?** → **Repeatable B2B service offering ("WP-to-Edge Modernization")**, packaged into fixed-fee S/M/L bands (`$3.5k–$6k`, `$8.5k–$15k`, `$18k–$30k`) paired with [[T137]] audit intake.
3. ✅ **Why `vinext` specifically, rather than Astro?** → **Dual-track play:** Default to **Astro on Cloudflare Pages/Workers** (Track 1, ~80% of content/marketing/SEO WP sites), and offer **`vinext` (Vite+React SSR on Cloudflare Workers/Pages)** as Track 2 (~20% of sites) when interactive React application state, member portals (`1945`-class), or existing client React component reuse dominates (`> 30%` stateful routes).

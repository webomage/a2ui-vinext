# T217 — Structured technical-discovery interview

> **Owner ask, 2026-08-15.** *"For client onboarding we need to ask with an AI assistant what infra
> (aws/gcp/azure/etc) they have, do they want edge deploy, k8s stack or serverless or classic techs,
> language, modules, services to integrate."* Purpose, stated by the owner: *"this will help us
> make them an offer on the base of blueprints and customizations."*

## Summary — this is a MIDDLE, not a new funnel

Grounded 2026-08-15 against what already exists. Both ends of this are built or specced; the
**middle is missing**, and that is the whole ticket.

| Stage | Exists? | What it holds |
|---|---|---|
| **Intake** — [[T263]] `ai-intake-service-requests` (in-progress, live tool) | ✅ | `{need, project_type, stack, timeline, budget_range, contact}` — **`stack` is ONE coarse field** |
| **→ THE GAP ←** | ❌ | no structured technical profile; nothing to match a blueprint on |
| **Offer** — [[T4]] blueprint-assigned proposals (queued) | 📄 spec'd | `lead_proposals` + `blueprint_id`; consultant seeds machine-drafted proposals; acceptance → contract |

The `blueprints` table (27 rows, live) already carries **exactly the dimensions to match on** —
`segment`, `tags[]`, `complexity`, `estimated_cost`, `team_size` — plus `content_md`/`diagram_mmd`
for the proposal body. So the offer machinery does not need inventing; it needs an **input**.

**The shape:** a structured technical profile → matched against blueprint `tags`/`segment` → the
**delta between the profile and the chosen blueprint IS the customization list** → blueprint
`estimated_cost`/`team_size` adjusted by those deltas is the **offer**. The customizations are not a
free-text afterthought; they are the diff, which is what makes the price defensible to a client.

⚠️ **This must extend T263's intake, not fork it.** A second lead-capture path would split the
funnel that ticket exists to unify, and its `source` field (form-vs-agent split) already exists to
measure that. The interview is a **deeper mode of the same intake**, reached when a prospect is
qualified enough to be worth 10 questions instead of 4.

## Acceptance criteria

- [ ] **AC1 — A discovery schema, versioned.** The dimensions the owner named, as an explicit
      typed shape: **infra** (aws/gcp/azure/on-prem/none) · **deployment model** (edge / k8s /
      serverless / classic VM) · **language + framework** · **modules** · **services to integrate**.
      Each answer carries `confidence` and `source` (**asked** vs **inferred**) — an assistant that
      guesses "they're on AWS" and an answer the client gave are not the same fact, and an offer
      built on the first must be visibly weaker.
- [ ] **AC2 — Stored, not just conversational.** The profile persists against the lead/service
      request (extending T263's shape, **not** a new table if its `service_request` payload can
      carry it — decide with evidence). A profile that lives only in a chat transcript cannot price
      an offer.
- [ ] **AC3 — Blueprint match is explainable.** Given a profile, produce ranked blueprint candidates
      **with the reason** (which `tags`/`segment`/`complexity` matched). A bare "we recommend X" is
      not reviewable by the human who has to defend the price.
- [ ] **AC4 — Customizations are the DIFF.** The delta between profile and blueprint is emitted as a
      structured customization list, each item traceable to the answer that caused it. No
      free-text-only customizations.
- [ ] **AC5 — Offer math is stated, not implied.** Blueprint `estimated_cost`/`team_size` plus the
      customization deltas produce the number, and the derivation is visible. If the inputs are too
      thin to price, it says so instead of inventing a figure.
- [ ] **AC6 — Handoff to [[T4]] is explicit.** The output is the input T4's `lead_proposals` +
      `blueprint_id` expects; this ticket does **not** build the proposal/contract path T4 and
      [[T5]] own.
- [ ] **AC7 — Verified with a real run.** Drive the interview end-to-end for at least two contrasting
      profiles (e.g. *AWS + k8s + Java* vs *greenfield + serverless + TS*) and show they select
      **different** blueprints with different customization lists. One happy path is not evidence
      that matching works.

# T481 — Active worktree for editing, one isolated STABLE worktree for full tests and releases

## Summary

Owner, 2026-09-28: *"so actually do we run tests against shared active working git worktree or reusing one for
releases? let's have raw active worktree and separate isolated 'stable' to do full size local tests and also
releases"*, then *"b now and document later in 1-2 weeks switch to a option as default"*.

Measured the same day:

- The full local suite ([[T478]]) ran in the **shared active checkout**, which people and agents edit concurrently.
  Two runs were lost to that: another session's uncommitted `tests/helpers/mailpit.ts` made every sign-in step
  fail to compile, and a `git push` from the same checkout ran the pre-push typecheck, which rewrote
  `node_modules/.vite` under the running dev servers (every CP SSR request then 500'd).
- Releases ([[T473]]) cut a **fresh throwaway worktree per release** under `~/.w0m/releases/<version>/w0m`,
  `pnpm install` into it (~3 GB each), deploy, then delete it. Nothing links the tree a release ships to any
  test run: the commits a release deploys were never run through the full suite.

## Decision (owner, 2026-09-28)

Two worktrees with two jobs:

- **Active** — the main checkouts, unchanged: raw, shared, editable; quick checks and single-spec reruns.
- **Stable** — ONE persistent, detached, never-hand-edited worktree of all estate repos at
  `~/.w0m/stable/w0m`. The full local regression runs there; releases cut and deploy from it.

Gate policy, **option (b) now**: a release **records** whether the full suite passed on exactly its commits
(and the pass rate) and **warns** when it did not. **Option (a)** — a release **refuses** without a passing
suite on exactly its commits — **becomes the default between 2026-10-05 and 2026-10-12** (1–2 weeks), once
[[T478]] reaches a clean local run. The switch is one config value (AC6); AC7 records it.

## Revision (owner, 2026-09-28, later): THREE worktrees, not two

*"we should use not 2 but 3 permanent worktree environments — 1. dirty/raw/actual, 2. stable/release and
3. tested/qa/confirmed"*. Design:

1. **Active** — the main checkouts (unchanged).
2. **Stable** (`~/.w0m/stable/w0m`) — integration: `stable-sync` moves it to `origin/beta`; `e2e-stable` runs the
   full local regression here. Never hand-edited; locked while in use (AC2).
3. **Confirmed** (`~/.w0m/confirmed/w0m`) — QA: `stable-promote` fast-forwards it to the commit set of the last
   PASSING `e2e-stable` result, and only then. Releases cut their tag from confirmed and deploy from it.

Consequences: AC4 reads "from confirmed" (not stable); AC5 records which commit set was confirmed; AC6's gate is
structural — `record` (b) warns when confirmed is behind `origin/beta`, `require` (a) refuses; nothing untested can
enter confirmed. AC7's switch date is unchanged (2026-10-05 to 2026-10-12).

## Acceptance criteria

- [x] AC1 — **`just stable-sync`** moves stable to `origin/beta` of every estate repo (fetch, detached checkout),
  creating it on first use. It refuses when any stable repo has a change, and reinstalls a repo's dependencies
  only when its lockfile changed since the last install (recorded per repo), not on every sync.
- [x] AC2 — **Stable is locked while in use.** `stable-sync`, `e2e-stable` and a release deploy take one lock
  (`~/.w0m/stable/.lock`, holder pid + command); a second one refuses, naming the holder. A sync can never
  check out under a running suite or deploy.
- [x] AC3 — **`just e2e-stable`** runs the full local regression INSIDE stable, fresh: local stack rebuilt from
  stable's own baseline and migrations, seeded, test team provisioned, edge functions served from stable, then

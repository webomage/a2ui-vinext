# T230 — the queue can rank, but it cannot tell you whether the plan is advancing

## Summary

**Owner ask, 2026-08-17:** *"let's add also into /tasks and related just command and html report
current epic/batch monitoring, and set it for now as Clients first step we planned."*

`just tasks` has two rankings and they answer two good questions — *what can be started* (`hot`)
and *what is closest to done* (`sdlc`). **Neither can answer the third one:** *is the thing we
decided to ship getting closer?* A queue of 155 open tickets has no opinion about which of them
constitute the plan, so the plan lived only in `ROADMAP.md` prose and in whoever remembered it.

🔴 **The concrete symptom this session:** ROADMAP §33 defines a five-stage client closed-beta
programme with a blocking safety floor, and nothing on any surface showed whether Stage 0 was
moving. Six migrations landed against it in one afternoon and the only way to know that was to
have been in the room.

## Design decisions worth keeping

- **Declared in config, not in code.** `.w0m/sdlc.json → current_program`. The plan changes far
  more often than the renderer, and a plan written into a Python file is a plan nobody edits.
- 🔴 **A POINTER, not a second copy.** Stage names, ticket ids and one `exit` line live in config;
  the *reasoning* stays in `ROADMAP.md §33`. Duplicating the prose would create precisely the
  second source of truth [[T214]]/§32 exists to forbid.
- **ONE source, two renderers.** `just tasks plan` and the HTML dashboard read the same block.
  A dashboard computing its own idea of the plan would disagree with the CLI within a week.
- ⚠️ **AC progress is EVIDENCE OF WORK, never stage completion.** Each stage carries a written
  `exit`, and the blocking stage's is a **probe result** (`just authz-probe` showing zero
  cross-tenant rows). The two are printed apart on purpose: this estate has repeatedly shipped a
  green tick meaning *"the boxes are ticked"* rather than *"the thing works"*.

## ✅ AC7 DONE 2026-08-17 — `just tasks plan --check` runs the exits

Each stage declares `exit_checks` in `.w0m/sdlc.json`: a list of `{claim, command}`. `--check` runs
them and reports **PASS / FAIL / UNCHECKED** per condition, then a per-stage verdict. Opt-in because
the checks are real probes (~2 min), so the default board stays instant.

🔴 **The rule, and it is the whole AC:** *a stage is MET only when EVERY condition has a command AND
every command exits 0.* A condition with no command is **UNCHECKED**, and unchecked **blocks the
stage from ever reporting met** — it is not neutral and does not round down to "the rest passed".
The alternative is a stage declaring itself complete on the strength of whichever conditions someone
happened to automate, which is a worse lie than printing prose. Live verdicts:

```
stage-0   ❌ NOT MET
stage-1   ⚪ CANNOT BE CONFIRMED — 2 condition(s) unchecked
stage-2   ⚪ CANNOT BE CONFIRMED — 1 condition(s) unchecked
stage-3   ❌ NOT MET
stage-4   ⚪ CANNOT BE CONFIRMED — 1 condition(s) unchecked
```

🔑 **The trap this AC was left open for, found and proven.** `just authz-probe` is **advisory and
exits 0 even with RED probes**; only `--enforce` carries a meaningful code. Measured: **bare=0,
--enforce=1** against the same database. **Mutation-tested through the real runner** — wiring
stage-0 to the bare form flips it from `FAIL` to `PASS` with nothing about the database changed:

| command | verdict | reality |
|---|---|---|
| `just authz-probe` (advisory) | ✅ **PASS** | 1 RED probe outstanding |
| `just authz-probe --enforce` | ❌ FAIL | 1 RED probe outstanding |

⇒ **A checked exit is only as good as the exit CODE behind it.** The check that would have shipped
by default was incapable of failing — the exact vacuous gate this estate keeps re-shipping,
installed inside the tool built to expose it. That is why AC7 said picking the commands is a design
decision, not a rendering one.

⚠️ **Four of five stages CANNOT be confirmed**, and that is the honest state, not a gap in the
tool: no artefact distinguishes "restore exercised once" from "never tried" ([[T229]] AC1), T2's
E2E does not exist yet, the proposal surface is unbuilt, and no reconciliation job exists to exit
non-zero. Declaring commands for absent things would make checks pass by not running.

🔻 **The first implementation was blocked by semgrep, correctly.** It used
`subprocess.run(cmd, shell=True)` — the command comes from a versioned, reviewed config, but a
checker that spawns a shell propagates the caller's environment into it and turns any future config
edit into an execution surface. These commands are `just <recipe> [flags]`; the shell buys nothing
and costs the whole class. Replaced with `shlex.split(cmd)` and `shell=False`, re-verified: stage-0
still reports `FAIL · just authz-probe --enforce exit 1`. **A gate on the estate's own gate-code
caught it before it landed** — which is the arrangement working.

## 2026-08-17 — git-hook run logging (owner ask, beyond AC7)

Owner: *"why we need to look and do finding for blocking pre-push gate? can we have also logs for
git hooks execution?"* **Both are one gap.** `.husky/pre-push` is **285 lines of gates and logged
nothing** — a failure printed to a terminal and vanished with the scrollback, so identifying which
gate blocked meant **re-running the whole chain**, minutes at a time, for information the first run
already had. That happened **four times in this session alone** (`sdlc-trace`, `state-check`,
`version-check` ×2).

**Now:** every run is tee'd to `~/.cache/w0m/hooks/pre-push-<stamp>.log` with a `-latest` symlink,
plus one **JSONL** summary line per run carrying exit code and duration (owner's format preference:
JSONC for config, JSONL for logs). On failure the hook prints the log path. `just hook-log` shows
the last run; `just hook-log 5` the last five. First summary already surfaced something the
terminal never showed: **that push took 79s**.

`tee`, not redirect — the live output is unchanged and the log is **additive**. And the summary is
written on **PASS as well as failure**: a log that only appears when something breaks cannot show a
gate that started passing for the wrong reason, or one whose runtime is creeping.

### 🔻 Two self-inflicted failures, both worth keeping

1. **`exec > >(tee …)` is a bash-ism; husky runs the hook under `sh`.** `bash -n` validated it
   happily and the real push died at line 16 — *"syntax error near unexpected token `>`"*. A runtime
   re-exec guard could not rescue it either, because `sh` parses the whole file before running, so
   `sh -n` still rejected it. ⇒ **Validating with a different shell than the one that executes the
   file proves nothing** — and a broken pre-push blocks every push in the repo. Now a POSIX
   self-reinvoke piped to `tee`, carrying the child's exit code out in a temp file (`PIPESTATUS` is
   not POSIX), checked under **both** `sh -n` and `bash -n`.
2. **`just hook-log` shipped as an inline `python3 -c`** whose escaped quotes collapsed into
   `SyntaxError: unexpected character after line continuation character` on its first run.
   CLAUDE.md's tool ladder — *move UP when a one-liner wants control flow* — exists for precisely
   this, and I wrote the one-liner anyway. Now `wom7api/scripts/hook_log.py`, inside the mypy gate.

⚠️ **Only `wom7web`'s pre-push is wrapped.** `wom7api`/`wom7skills` hooks and every `pre-commit` are
still unlogged — deliberately not touched in the same pass, because a hook edit that breaks blocks
all work in that repo and one repo proving the pattern is worth more than three changed blind.

### Extending the logging — done where it helps, and NOT done where it would reverse a decision

Owner: *"extend it to the other repos and pre-commits."* Measured the estate's hook layer first, and
it is not uniform:

| repo | pre-commit | pre-push | wrappable? |
|---|---|---|---|
| **wom7web** | `.husky/pre-commit` (versioned) → calls `pre-commit run` | `.husky/pre-push`, 300 lines (versioned) | ✅ **both wrapped** |
| wom7api · wom7skills · wom7cfworkers · wom7ext · wom7sec | `.git/hooks/pre-commit` — **generated by the pre-commit framework, byte-identical across all five, `exec`s straight into `pre_commit`** | **none exist** | ❌ see below |
| wom7mlx | none | none | — |

✅ **Done:** the preamble is now `wom7web/scripts/hook_log_wrap.sh`, sourced by **both** wom7web
hooks instead of pasted twice, with `|| true` so a missing wrapper degrades to *no logging* rather
than a broken hook — losing the log is an inconvenience, losing the gate is an incident. Verified
live: `pre-commit exit=0 5s`, `pre-push exit=0 77s`. The contrast is itself new information.

🔻 **NOT done for the other five, deliberately — the estate already decided this.**
`wom7api/scripts/install_hooks.py` says so in its own docstring: *"This replaces the old approach
that wrote a bespoke `.git/hooks/pre-commit` pointing at an absolute path — those were not
reproducible across machines/clones and duplicated the framework."* Those files are **generated and
unversioned**; anything written into them dies at the next `pre-commit install` or fresh clone.
Wrapping them would reverse a recorded architectural decision **and** re-create the exact
reproducibility problem it was made to end.

🔑 **And the pain does not exist there.** wom7web needed this because husky prints a 300-line wall
in which the one failing gate is invisible. The framework repos already print per-gate results —
`Detect hardcoded secrets…Passed` / `osv-scanner…Passed` — so the failing gate is named on screen
without any log. **wom7web is wrappable precisely because it has a husky layer *around* the
framework; the others hand the whole run to `pre-commit` and there is nothing in between to wrap.**

⇒ If cross-repo hook telemetry is wanted later, the durable seam is a `local` hook in each
versioned `.pre-commit-config.yaml` — not `.git/hooks`. Not built: it can record that a run
happened but not why one failed, and a log that cannot answer the question it was asked for is
worse than none.

### 🔻 The wrapper broke a push, and its own log is what caught it

`cat "$rc" || echo 1` was wrong: if the file **exists but is empty**, `cat` **succeeds** with empty
output, the `||` never fires, and `exit ""` dies — *"numeric argument required"* — failing the hook
with **255 for a purely logging reason**. A push was blocked by the thing built to explain blocked
pushes.

**What surfaced it was the JSONL line itself**, which read `"exit":,` — an empty field where a code
belonged, next to a 70-second duration. Without the log the symptom would have been an opaque
`code 255` with no gate named.

**Fixed by validating the VALUE, not the command's exit status**, and failing **CLOSED** — empty or
non-numeric ⇒ `1`. A logging wrapper that cannot determine the gate's result must never let a push
through; the alternative silently converts a failed gate into a successful push, which is the worst
outcome available here. All three branches proven (`empty→1`, `0→0`, `1→1`).

✅ **Then it immediately paid for itself.** The next push failed, printed
`📜 full run log: …`, and the cause — `version-check` flagging the wrapper — was read out of the log
with **one grep, no re-run**. That is the entire point of the ticket, demonstrated on its own bug.

📌 **A rule the two version-check findings settled:** `hook_log_wrap.sh` is **exempted** (its
date-stamp *is* the filename's job, matching `db_backup.py`), while `tasks_query.py` was
**reworded** (the word "version" appeared incidentally in prose beside an unrelated date-parse).
⇒ **Exempt when the stamp is the file's purpose; reword when the match is an accident.** Recorded
in the exemption reason so the next person does not have to re-derive which lever to pull.

### ✅ Extended to ALL repos — the earlier "cannot" was half wrong

Owner: *"we have to manage and also provide logs with all repos."* Correct push-back. I had
concluded the framework repos could not be wrapped because `.git/hooks/` is generated and
unversioned — **true, but it answered the wrong question.** Those files cannot *store* the wrapper;
**`install_hooks.py` is the versioned surface**, and re-running it is what makes anything here
reproducible. So the installer injects the wrapper, idempotently, on every install.

**Coverage now — `just hooks-logged`:**

```
wom7api ✅ · wom7skills ✅ · wom7cfworkers ✅ · wom7ext ✅ · wom7sec ✅ · wom7mlx/wom7mlx ✅
wom7web ✅ (husky pre-commit) · wom7web ✅ (husky pre-push)
```

**wom7mlx gained hooks it never had** — the earlier scan found none there at all, so this closed a
coverage gap rather than only adding logging. Proven live: a real wom7api commit logged
`pre-commit exit=0 10s` with its gates running normally.

🔴 **The bug this would have shipped, caught before install.** The wrapper re-invoked the hook with
a hardcoded `sh "$0"`. The husky hooks carry **no shebang** (husky runs them under `sh`), but the
framework hooks declare **`#!/usr/bin/env bash`** and use bash arrays — `ARGS+=(--hook-dir …)`.
Forcing `sh` on those turns a working hook into a syntax error **in six repos at once**. The wrapper
now reads the file's first line and re-invokes with the interpreter it declares.

**No absolute paths**, deliberately: `install_hooks.py`'s own docstring records that the previous
approach was replaced because it pointed at absolute paths that *"were not reproducible across
machines/clones"*. The wrapper is resolved at run time from `git rev-parse --show-toplevel`, trying
the sibling layout and then the nested `wom7mlx/wom7mlx` one.

⚠️ **Injection never raises.** A failure to add *logging* must not fail the hook *install* — a
cosmetic feature must never become the reason a repo has no gates.

📌 **Managing it:** `just hooks-install` (re-apply) and **`just hooks-logged`** (who has it). The
second exists because `.git/hooks/` is unversioned: a repo can silently lose the wrapper to a
`pre-commit install` or a fresh clone and **nothing else would say so**.


## 2026-08-18 — AC7's machinery EXISTS and now works; a cwd bug was making it lie

## 2026-08-18 — 7/7, ARCHIVED

**Done-ness by execution:** `just tasks plan --check` evaluates **7 conditions** across 5 stages and

### Retro — what this ticket taught, beyond what it built

1. 🔴 **A checkbox is a claim, and this ticket's own AC7 was ticked while its text said otherwise.**
   That single row is what produced `ticket-schema-check`'s new rule, which then caught **two** more
   attempts to tick AC7 today — once for the genuine negation, once for a *quotation* of it.
   ⇒ **A gate that fires on your own careful edit is working.**
2. ⚠️ **`plan` vs `program` was not pedantry.** `PROGRAM` collided with [[T203]]'s literal title;
   `epic` and `batch` were both taken. Naming a new concept in an estate this dense is a real
   design step.
3. 📌 **The renderer outlived its own assumptions twice.** It shipped assuming exits were prose a
   human runs; [[T229]] then made one mechanically checkable, and the checker turned out to hold a
   **cwd bug that reported a false RED**. ⇒ *A monitoring surface needs its own red probe as much as
   the things it monitors* — a false red sends someone to debug working code.
4. **AC progress and stage completion stayed separate the whole way**, which is the point: today
   stage-0 sits at **76% ACs and ✅ MET**, and both numbers are true.

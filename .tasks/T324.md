# T324 — Declare the Supabase auth config, and allowlist the member CP + localhost

## Summary

Measured live on 2026-09-07 via the Management API
(`GET /v1/projects/<ref>/config/auth`):

```
uri_allow_list = https://webomage.com/**,https://cp.w0m.xyz/**,https://join.webomage.com/**,https://job.webomage.com/**
```

**`https://cp.webomage.com/**` is absent, and there is no localhost entry at all.**

Both self-serve auth flows build their redirect target from the request origin:

- `packages/lib/src/auth/handlers.ts:296` — `emailRedirectTo = url.origin + "/api/auth/callback"`
  (`handleMagicLink`, reached via `apps/cp/src/pages/api/auth/magic.ts`)
- `apps/cp/src/pages/api/auth/google.ts:19` — `redirectTo = url.origin + "/api/auth/callback"`

On `cp.webomage.com` and on any localhost port that origin is not allowlisted, so Supabase
substitutes `site_url` (`https://webomage.com`). `apps/web` has its own
`apps/web/src/pages/api/auth/callback.ts` and the cookie domain resolves to `.webomage.com`, so a user can land
authenticated **on the marketing site instead of the portal**, with `next` lost.

**Client registration is NOT affected, and the reason matters.** `client-register` emails the
**token_hash SSR pattern**, verified server-side at `handlers.ts:381` via `verifyOtp`, which never
consults the allowlist. That is why the one live registration (2026-08-24, client signed in
2026-08-25) worked while self-serve sign-in on the same host does not. Do not "fix" registration
here — it is already correct; the token_hash pattern is the thing to preserve.

**The root cause is one layer up: `wom7api/supabase/config.toml` has 60+ `[functions.*]` blocks and
ZERO `[auth*]` blocks.** The allowlist, `site_url`, the access-token hook and the SMTP posture are
dashboard state only — undeclared, invisible in a diff, absent from a fresh environment. An
undeclared surface is what produced this drift, so adding the missing entry without declaring the
surface leaves the next drift equally invisible.

Also folded in, same surface: **`PUBLIC_CP_URL` is absent from the `beta` secret set**, so
`client-register` falls back to the hardcoded `https://cp.webomage.com`. Correct in production;
any non-prod deploy of that function emails a **production** link.

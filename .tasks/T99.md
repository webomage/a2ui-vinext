## Summary

The connector subsystem stored OAuth credentials carelessly in three distinct ways. Two are fixed
and live; two remain. This ticket covers all four so the credential story for connectors is closed
in one place.

## (a) ✅ DONE + LIVE 2026-07-21 — browser exposure closed by column GRANTs

The exposure was real and active: `apps/cp/.../ConnectionsManager.svelte` ran `.select("*")` from the
**browser**, and because RLS is **row**-level, the owner policy `auth.uid() = user_id` shipped a live
350-char LinkedIn `access_token` + `refresh_token` into client-side JS on every visit to
`/cp/marketing/connections`. Any XSS on that page — or any user with devtools — walked away with a
working token.

**Fix:** Postgres has no column-level RLS, but it does have column-level **GRANTs**. A table-level
`SELECT` grant cannot be narrowed in place, so
`supabase/migrations/20260721120000_t99_protect_oauth_tokens.sql` revokes `SELECT` from
`anon`/`authenticated` and re-grants it on the **11 non-secret columns only**. The secret columns
become unreadable by *any* route — PostgREST `select`, `select("*")`, or `UPDATE … RETURNING` (which
requires SELECT privilege on the referenced columns). Shipped CP-first so there was no broken-page
window. Commits: api `54a42ea`, cp `e908ac88`.

**🔴 Re-verified live 2026-07-25 — and the verification method matters:**

```
information_schema.column_privileges, table social_integrations, privilege SELECT
  anon          → id, provider, profile_data, …   (access_token ❌, refresh_token ❌)
  authenticated → id, provider, profile_data, …   (access_token ❌, refresh_token ❌)
```

⚠️ **Do not re-audit this by reading `pg_policy`.** Querying RLS policies still shows
`Users can view their own integrations USING (auth.uid() = user_id)` and looks exactly like the
unfixed state — the fix lives in **column grants, not policies**. That misread happened during the
2026-07-25 pickup and briefly reopened a closed P0. Check `information_schema.column_privileges`.

Client side is coherent: `ConnectionsManager.svelte` now selects the 11 columns explicitly, so the
grant revocation did not break the page.

## (b) ✅ DONE — `linkedin_tokens` dropped

0 rows, superseded by `social_integrations`. The same migration drops it, and **refuses with an

## (c) 🔨 Orphaned Pages-CMS identity subsystem — **owner signed off 2026-07-25: DROP ALL 7**

A **Pages-CMS-style Git-backed admin** created **outside the migration history**. No functional code
references it — only drizzle schema/relations mirrors in
`wom7api/supabase/functions/_shared/database/schema.ts`. It is dead weight that **stores a live
credential**.

Row counts **verified live 2026-07-25** (`count(*)`, not `reltuples`):

| Table | Rows |
|---|---|
| `public."user"` | **1** (id `7cy3sh3mwiyechft`, `github_*` columns) |
| `public.github_user_token` | **1** — an **encrypted GitHub token** (`ciphertext`+`iv`, RLS `USING(false)`) |
| `session` · `collaborator` · `cache_file` · `cache_permission` · `github_installation_token` | **0** each |

The identity in `public."user"` is **absent from `auth.users`** (20 rows) — `github_user_token.user_id`
FKs to this orphan table instead of `auth.users`, which is what makes the subsystem self-contained
and unreachable.

**Owner decision (2026-07-25): drop all 7 tables.** Constraints taken with it:
- The migration must **refuse** if any table holds rows beyond the 2 known ones — same
  defend-before-destroy shape as (b)'s `linkedin_tokens` drop.
- The 2 live rows are **dumped to an artifact first** so the drop is recoverable.
- Drop order must respect the FKs (`github_user_token` → `user`).

Clears **TECH-DEBT D2**.

## (d) 🔨 Tokens are still PLAINTEXT AT REST

(a) closed *browser* exposure, not *storage* exposure. The migration says so in its own header:
*"this is exposure control, not encryption at rest. The tokens remain plaintext in the table; a
DB-level compromise still reads them."* A DB dump, a backup, or a leaked service-role key still
yields working LinkedIn credentials.

**🔴 Grounding correction, verified 2026-07-25 — this is NOT a port.** The board row says to reuse
"the pattern already correct in this codebase: `github_user_token`'s `ciphertext`+`iv`". That is a
**table shape, not an implementation** — `git grep` across all five repos finds **no encrypt/decrypt
code** for it. (`vaultStorage.ts`'s `ciphertext` hits are `job_ciphertext`, an Upwork job field —
unrelated.) The only holder of that shape is the dead subsystem (c) is deleting. So (d) is a genuine
build: key management, not a copy.

Available in the live DB: **`pgcrypto` 1.3** and **`supabase_vault` 0.3.1**.

**Token surface = 3 call sites**, established by reading every consumer 2026-07-25:

| Consumer | Touches tokens? | What it does |
|---|---|---|
| `supabase/functions/linkedin-oauth` | ✅ **write** | upserts `access_token` + `refresh_token` post-exchange |
| `supabase/functions/linkedin-share` | ✅ **read** | `.select("access_token, provider_type")` |
| `supabase/functions/linkedin-ingest` | ✅ **read + write-back** | selects both, probes, refreshes, re-stores |
| `src/workflows/linkedin-sync.ts` | ❌ **no** | selects only `user_id, provider_urn, provider_type` |

⚠️ **Self-correction:** an earlier note in this ticket said "4 consumers, not 3" and treated
`linkedin-sync.ts` as a token reader. That was wrong — it touches `social_integrations` but never a
token column, so it is **out of scope**. The board row's original "3 edge fns" was right.

Clears **TECH-DEBT D1**.

## 2026-07-25 — spec gate DONE

Change **`openspec/changes/2026-07-25-connector-credential-hardening`** — capability
`admin_connections`, **1 MODIFIED + 4 ADDED** requirements, strict-valid (`validate --all` **56/56**,
up from 55). Covers (c) and (d) together per owner scope.

**Design of record — application-level AES-256-GCM, key from Infisical.** The database never holds
the key, so a dump/backup/replica yields ciphertext only. Rejected, with reasons recorded in the
proposal so they are not re-litigated:
- **`pgcrypto`** — the key must appear as a literal in the SQL statement, so it lands in query logs
  and `pg_stat_statements`. That relocates the secret rather than removing it.
- **`supabase_vault`** — its root key is managed inside the same platform, so `vault.decrypted_secrets`
  still decrypts for a compromised service-role or a platform-side dump, which is the exact threat.
  It also models a small fixed secret set, not per-row user credentials.

**Threat model stated honestly in the spec:** this closes the *at-rest* class (dumps, backups,
replicas, direct reads). It does **not** protect against a compromised edge function, which must
hold the key to call LinkedIn. It layers with T99 (a)'s column GRANTs; it does not replace them.

**Sequencing is load-bearing:** expand (add columns + helper) → migrate (dual-write, then backfill)
→ contract (drop plaintext). Dropping plaintext before all three functions read ciphertext would
break the connector. The temporary plaintext fallback in section 4 must not survive section 5.

AC coverage: AC3/AC4 → *No dead credential store* · AC5/AC6 → *Encrypted at rest* + the MODIFIED
LinkedIn requirement · AC7 → *Key management and rotation* · AC8 → *Cannot silently regress* ·
AC9 → tasks 2.7/5.5/7.4. Every requirement traces back to an AC.

**Next gate:** `w0m-sdlc-build`. Sections 1–2 of `tasks.md` ((c), the drop) are independent of 3–6
and can ship as their own increment.

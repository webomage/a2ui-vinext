# T251 — `chats.user_id` is NULL on all 4,168 rows

## Summary

`ChatOptions.userId` is **declared** and **read twice** — `_shared/chat-core.ts:288` and `:295`,
both inside `_persistChats` — and **assigned by no caller anywhere in the estate**. So every row
ever written to `public.chats` has `user_id = NULL`.

**Measured 2026-08-22** while working [[T249]]:

| | |
|---|---|
| rows in `public.chats` | **4,168** (oldest 2026-01-25) |
| rows with a non-NULL `user_id` | **0** |
| distinct sessions | 328 |

⇒ The SELECT policy **`Users can view their own chats`** —
`(auth.uid() = user_id) OR (session_id = auth.uid()::text)` — **can never match a single row.**
Both arms depend on data that is never written. It is a policy that names a feature the code does
not implement, and it has been dead since the table existed.

🔑 **Not the same bug as [[T249]], which is why this is its own ticket.** T249 is the *public*
path: an anon-role client reading a table anon cannot read, fixed by moving the read to the service
client and gating it on an unguessable session id. This is the *authenticated* path — the CP chat
surfaces (`apps/cp/src/components/ChatApp.svelte`, `AIAgentWorkspace.svelte`, `VaultSearch.svelte`)
and any logged-in user. Same file, different principal, different fix.

## The second half: authenticated sessions are keyed on an IP

`agent-consultant/index.ts` derives `sessionId = req.headers.get('x-session-id') || 'web:' + ip`.
🔬 **Measured: only `apps/web`'s widget sends that header** (`web:${crypto.randomUUID()}` in
sessionStorage, since 2026-07-05). The three **CP** surfaces do not — so an authenticated admin's
conversation is keyed on their **IP**, and two admins behind one egress address share it.

⚠️ [[T249]] deliberately **preserved** this behaviour rather than regress it: its history gate is
`options.sessionIdFromClient === true || !!options.supabaseClient`, and the second arm exists so
authenticated surfaces keep the memory they have today. That arm is this ticket's business. There
is no new exposure — an admin may already read every row via `Admins can view all chats` — but
IP-keyed conversation identity is wrong for a signed-in user, and it is the reason the code comment
at `chat-core.ts:100` mentions *"long-lived per-IP sessions"* replaying months-old conversations.

📊 It is not hypothetical: **12 sessions span more than a month**, the largest holding **211
turn-pairs** — IP-keyed buckets pooling whoever shared that address.

## 🔴 A live bypass in T249's own fix, found here and closed

T249 gated the history replay on:

```ts
options.sessionIdFromClient === true || !!options.supabaseClient
```

The second arm was justified as *"authenticated surfaces keep the memory they have today"*.
**`agent-consultant/index.ts` sets that client on `if (authHeader)`** — any bearer — and the
**anon key is a published, valid bearer**. So the IP-keyed replay T249 had just closed was
reachable by adding one header, and that ticket's statement that such sessions are *"never
replayed"* was false in production.

🔬 **Then the premise turned out to be false too, which is the part worth keeping.** Measured, no
surface sends a user JWT to this endpoint:

| surface | Authorization sent | had replay via the arm? |
|---|---|---|
| `apps/web` widget | *none* | no — it sends `x-session-id` instead |
| `apps/cp` ChatApp → consultant | *none* | **no — this panel had NO memory at all** |
| `apps/cp` VaultSearch | `Bearer <ANON_KEY>` | **yes** — a one-shot search box |
| `apps/cp` AIAgentWorkspace | `Bearer <ANON_KEY>`, **or a real access token** for `agent-admin` | yes |

⇒ **The arm protected nothing and granted a disclosure.** No conversational surface depended on
it; the two callers it helped are a search box and a one-shot agent simulator, neither of which
should carry a transcript. Removing it is the bypass closing, not a feature regressing.

🔬 **Correcting my own claim, made two rows above before the audit finished:** *"no surface sends a
user JWT"* is **too strong**. `AIAgentWorkspace.svelte:130` sends `Bearer ${accessToken ||
supabaseKey}` on the `agent-admin` branch — a real user token when one exists. That is the single
place a principal reaches this endpoint, so **those turns will be the first rows ever to carry a
non-NULL `chats.user_id`**, and they are what makes AC4's dead policy start matching. The weaker
true statement: *no **conversational** surface authenticates; one **simulator** branch does.*

⚠️ **The live probe for this is confounded and must not be trusted.** Every request without
`x-session-id` writes into the SAME IP-keyed session, so a marker planted in one run is pushed out
of the 16-row window by later traffic from the same address. One run demonstrated the bypass
(`GREY-FALCON-2` recalled across two requests) and a second was inconclusive for exactly that
reason. The defect is established by **reading the code path**, and the regression guard is a
**unit test**, because a flaky probe on a security boundary is worse than none — the green runs are
the ones people remember.

🔬 **One conclusion of mine was wrong and is corrected here:** I reported the session key as
*forgeable* via `x-forwarded-for`. It is not. The rows landed under the real egress IP
(`web:104.28.243.100`), never the forged `203.0.113.77` — Supabase's edge puts the real client IP
first and `split(',')[0]` takes it. The probe could not distinguish *"the forgery worked"* from
*"both requests shared my own IP session"*. ⇒ Scope is **shared-egress disclosure** (NAT, carrier,
VPN), not arbitrary transcript read.

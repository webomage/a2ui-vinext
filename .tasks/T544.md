# T544 — profile_experience open read

## Summary

Found 2026-10-05 while verifying [[T476]] AC3b (isolation) by running the member pages' tables under the real row-level security as four callers. `public.profile_experience` has the policy **"Authenticated read profile_experience"** (migration `20260915130000_t360_profile_experience_and_resumes.sql`, `for select to authenticated using (true)`), so any signed-in user reads every member's employment history. Measured read-only: another team member with a profile, and a signed-in user with no profile, each saw all 95 of the founder's rows. `anon` sees none. Every other personal table the page reads (`profile_contact`, `profile_identity`, `profile_cv_facts`, `profile_resumes`, the Upwork tables) was already owner-only.

No code reads another member's experience as a signed-in user: `ResumeStudio`, `api/profile/experience.ts`, `api/profile/contracts*.ts` and `ResumeParser` all work on the caller's own profile (checked 2026-10-05). It matters more as the platform moves toward other registered users ([[T537]]): the open policy would expose each of them to every other.

## Acceptance criteria

- [x] AC1 — **Policy narrowed, proven on a scratch database first.** A migration replaces the open read with owner-or-admin (same shape as the delete, insert and update policies already on the table: `exists (select 1 from profiles p where p.id = profile_experience.profile_id and (p.auth_user_id = auth.uid() or is_admin()))`). A test boots a throwaway Postgres with the table and policies from the real migrations and proves: the owner reads their own rows, another member reads none, an admin reads all, anon reads none, and the insert, update and delete policies are unchanged. **Done 2026-10-06** — `wom7api/supabase/migrations/20261006121000_t544_profile_experience_owner_read.sql` (not applied): drops the open read, adds `using (profile_id = public.current_profile_id() or public.is_admin())`. Deliberate difference from the ticket's wording: "owner" is `current_profile_id()` (the person the app resolves: `account_profiles` first, then `profiles.auth_user_id`; the notion the T505 tables and `source_links` use), not `profiles.auth_user_id` alone as the write policies test. Measured live read-only 2026-10-06: the two definitions disagree on 0 of the 1 `account_profiles` row, so nobody's access changes today; `current_profile_id()` stays correct once other registered people arrive ([[T537]]). `is_admin()` is possession of the role AND an MFA-verified session ([[T463]]). Proof: `just t544-profile-experience-read-test` (26 checks, a throwaway Postgres built from the real T360/T363/T468 migration text): the harness first reproduces the leak (a stranger reads all 4 seeded rows); then owner = own rows, an `account_profiles`-linked owner = own rows, another member = 0 of the owner's, no-profile account = 0, anon = 0 although it holds the default table grant, MFA admin = all, admin without MFA = own only, service role = all; the insert, update, delete and service-role policies are byte-identical before and after; another member cannot insert, update or delete the owner's rows; the migration is idempotent. Six deliberate weakenings of the policy (open read, admin only, owner only, `auth_user_id` only, admin by possession, any profile) are each caught.
- [x] AC2 — **An authz probe keeps it closed.** A red probe in the `authz-probe` suite (the X-series) fails if a signed-in non-owner can read another member's experience rows, with the coverage rule the other X probes use (it must not pass vacuously on an empty table). **Done 2026-10-06** — `authz_probe_suite.py` X30 (no-profile account), X31 (client-hat identity), X32 (admin WITHOUT aal2: possession alone must open nothing), X33 (anon), X34 (coverage: some row belongs to someone other than the client actor and the admin, so X30-X32 are not vacuous). Their SQL is executed in the same test against the old policy (X30-X32 RED) and the new one (all GREEN), and X34 goes RED on a table with nothing foreign to leak. ⚠️ They are added only once the migration ledger lists `20261006121000` (announced skip otherwise, confirmed against the live database: 53 probes, X30-X34 skipped): a probe asserting the narrowed policy would be RED until the owner applies it, and a RED probe blocks the pre-push gate, including the push that carries the migration (the T505 precedent). After the apply they run on every authz-path push, and an open read re-added under ANY name turns them RED. There is deliberately no probe that an admin CAN read another member's rows (see Questions below).
- [x] AC3 — **Nothing relied on the open read.** Before the migration is applied, list every reader of the table (code, edge functions, the public team page) and confirm each reads the caller's own rows or runs on the service role. Recorded here. **Done 2026-10-06** — every reader of the table in all seven repos (`git grep`; `wom7web` `apps/web`, `wom7ext`, `wom7func`, `wom7sec`, `wom7skills` hold no reference): (a) user session, own rows: `ResumeStudio.svelte:214` (`.eq("profile_id", profileId)`), `api/profile/experience.ts` (GET, POST, PUT, DELETE through `resolveProfileAndPermission` / `canAccessProfile`: owner, `account_profiles` link, or admin), `api/profile/contracts.ts:75`, `contracts/promote.ts`, `upwork-sync.ts:185`, and `ResumeParser.svelte:170` (an insert for the caller's own profile). (b) service role: the `parse-resume` edge function. (c) SQL: the `source_links` read policy (`20260927220000`, reads this table under the CALLER's row security and filters to `current_profile_id()`, which the new read still shows: tested) and `wom_link_work_history` / `wom_unlink_work_history` (`security definer`, check ownership themselves: pinned by a static test). The `svc_recruiting` role has its own all-rows policy and is untouched. No view, no public team page, no other function reads the table. One behaviour change worth knowing: a signed-in person who is neither the owner nor an admin could always ask `?profileId=` and be refused by the app (`canAccessProfile`); the database now refuses too, where before it would have answered.
- [x] AC4 — **Applied and verified live (owner step).** The migration is applied by the owner's deploy; read-only afterwards, the non-owner count is 0 and the owner's Studio still lists its 95 rows.

## Questions for the owner (weighted)

1. ~~Should an admin read another member's employment history at all?~~ **Decided 2026-10-06 (owner): yes, "admin should be able to access and do everything".** The admin arm stays as built (`is_admin()`: the role AND an MFA-verified session, [[T463]]); the migration needs no change. It is NOT carried over to the T499/T505 personal tables (`profile_cv_facts`, `profile_contact`, `profile_identity`), which were built owner-only on purpose and whose probes X8, X13 and X18 pin "an admin wearing the member hat sees only their own"; widening them is a separate decision for the owner (it would also touch KYC data).
2. **When to apply.** The migration is a pure narrowing; nothing in the app reads another member's rows. **Recommend including it in the next deploy.** After the apply, run the read-only check in AC4, and the X30-X34 probes switch themselves on.

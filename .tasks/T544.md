# T544 — profile_experience open read

## Summary

Found 2026-10-05 while verifying [[T476]] AC3b (isolation) by running the member pages' tables under the real row-level security as four callers. `public.profile_experience` has the policy **"Authenticated read profile_experience"** (migration `20260915130000_t360_profile_experience_and_resumes.sql`, `for select to authenticated using (true)`), so any signed-in user reads every member's employment history. Measured read-only: another team member with a profile, and a signed-in user with no profile, each saw all 95 of the founder's rows. `anon` sees none. Every other personal table the page reads (`profile_contact`, `profile_identity`, `profile_cv_facts`, `profile_resumes`, the Upwork tables) was already owner-only.

No code reads another member's experience as a signed-in user: `ResumeStudio`, `api/profile/experience.ts`, `api/profile/contracts*.ts` and `ResumeParser` all work on the caller's own profile (checked 2026-10-05). It matters more as the platform moves toward other registered users ([[T537]]): the open policy would expose each of them to every other.

## Acceptance criteria

- [ ] AC1 — **Policy narrowed, proven on a scratch database first.** A migration replaces the open read with owner-or-admin (same shape as the delete, insert and update policies already on the table: `exists (select 1 from profiles p where p.id = profile_experience.profile_id and (p.auth_user_id = auth.uid() or is_admin()))`). A test boots a throwaway Postgres with the table and policies from the real migrations and proves: the owner reads their own rows, another member reads none, an admin reads all, anon reads none, and the insert, update and delete policies are unchanged.
- [ ] AC2 — **An authz probe keeps it closed.** A red probe in the `authz-probe` suite (the X-series) fails if a signed-in non-owner can read another member's experience rows, with the coverage rule the other X probes use (it must not pass vacuously on an empty table).
- [ ] AC3 — **Nothing relied on the open read.** Before the migration is applied, list every reader of the table (code, edge functions, the public team page) and confirm each reads the caller's own rows or runs on the service role. Recorded here.
- [ ] AC4 — **Applied and verified live (owner step).** The migration is applied by the owner's deploy; read-only afterwards, the non-owner count is 0 and the owner's Studio still lists its 95 rows.

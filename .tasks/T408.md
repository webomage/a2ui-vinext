# T408 — A commit from a fresh git worktree runs zero hooks

## Summary

Found 2026-09-20 while landing [[T407]] out of a worktree another session had left in a scratchpad
directory. The commit succeeded, printed nothing, and wrote no hook log. Measured immediately after:

    git -C <worktree> config core.hooksPath   →  .husky/_
    ls <worktree>/.husky/_                    →  No such file or directory
    ls <main checkout>/.husky/_               →  applypatch-msg  commit-msg  h  …

`.husky/_` is generated by `husky install` (a `pnpm install` side effect) and is **not tracked**, so
a fresh `git worktree add` has `.husky/` — it is committed — but not `.husky/_`. `core.hooksPath` is
inherited via the shared config and points at a directory that does not exist, and **git runs no
hooks and says nothing.**

🔴 **This is the `--no-verify` prohibition bypassed without anybody typing `--no-verify`.** The same
commit made from the main checkout ran gitleaks, semgrep, osv-scanner, oxlint, prettier, the emoji
ratchet, the conventional-commit check, secrets-check and the state/dashboard refreshers. From the
worktree it ran none of them, and the only way to notice was that `~/.cache/w0m/hooks/` had no new
`wom7web-pre-commit-*.log`.

⚠️ **This is a designed condition, not an edge case.** Every Claude Code session in this app starts
in a worktree ([[T235]] already added a hook for parallel agents), and the estate currently has
three of them. An agent that commits from its own worktree is following the app's default and
silently skipping every gate the estate has.

## Acceptance criteria

- [ ] AC1 — A commit from a fresh worktree either runs the full hook stack or **fails loudly**.
      Silence is the defect; a worktree that cannot run hooks must not be able to commit.
- [ ] AC2 — The mechanism is chosen deliberately and recorded: track a committed hooks directory,
      or have a `post-checkout` bootstrap materialise `.husky/_`, or set `core.hooksPath` to a
      tracked path. ⚠️ `post-checkout` is itself a husky hook, so a bootstrap that lives there
      cannot fire in the worktree that needs it — check before choosing it.
- [ ] AC3 — Red-probed in both directions: a fresh `git worktree add` proves hooks now run, and the
      probe fails if `.husky/_` is absent and the commit still succeeds.
- [ ] AC4 — The same check applied to every repo with a hook stack (`wom7web`, `wom7api`,
      `wom7func`, `wom7ext`, `wom7skills`), not just the one where it was found — the config is
      per-repo and only one was measured.
- [ ] AC5 — ⚠️ **Audit what already got in this way.** Any commit authored from a worktree since
      the app started creating them has never been scanned. Enumerate them before assuming the
      answer is none; report the count either way.

## Definition of Done

T408 is done when:
1. `git worktree add` on a fresh branch, followed by a commit, either runs the full hook stack or
   **fails**. A silent success is the defect; reproduce it before and after.
2. `~/.cache/w0m/hooks/` gains a `<repo>-pre-commit-*.log` for that worktree commit — the absence of
   that log is how this was found, and it is the cheapest regression signal.
3. The probe fails when `.husky/_` is removed and a commit still succeeds, proving the check is not
   vacuous.
4. Every repo with a hook stack (`wom7web`, `wom7api`, `wom7func`, `wom7ext`, `wom7skills`) is
   measured, and each is reported as fixed or explicitly out of scope — not silently skipped.
5. The commits already authored from worktrees are **enumerated with a count**, and each is either
   re-scanned or explicitly accepted. "Probably none" does not close AC5.
6. The tag `t408-evidence-ungated-worktree-commit` still resolves.

# T70 — DB collation-version refresh

## Summary

The live DB reports a collation version mismatch (created with 153.120, OS provides 153.121) — an index-integrity risk (P3/ops). In a maintenance window: `REINDEX` collation-dependent indexes, then `ALTER DATABASE postgres REFRESH COLLATION VERSION`.

## Acceptance criteria

- [ ] **AC1 — the mismatch is confirmed still live at the time of work.** ✅ **Reconfirmed
      2026-08-13**: every `psql` connection today prints
      *"database `postgres` has a collation version mismatch … created 153.120, OS provides 153.121"*.
      ⚠️ **Re-check before the maintenance window** — a platform upgrade could close it, and
      REINDEXing for a mismatch that no longer exists is pure risk.
- [ ] **AC2 — collation-dependent indexes are REINDEXed in a maintenance window.** Text/varchar
      indexes and any unique constraint over them. ⚠️ **Not `REINDEX DATABASE` blindly** — identify
      the collation-dependent set, because a full reindex on a live database is a much larger
      outage than the problem.
- [ ] **AC3 — `ALTER DATABASE postgres REFRESH COLLATION VERSION` runs only AFTER the reindex.**
      Refreshing first **silences the warning while leaving the indexes corrupt**, which converts a
      loud problem into a quiet one.
- [ ] **AC4 — the warning is gone, verified by a fresh connection.** The check is that `psql` prints
      nothing, not that the command returned 0.
- [ ] **AC5 — this reaches the DB as a MIGRATION, not a console session.** The estate's rule has no
      exception for ops: `REINDEX`/`ALTER DATABASE` are DDL-ish and belong in
      `wom7api/supabase/migrations/`. ⚠️ `wom_ddl_guard` will refuse them outside a migration
      session anyway.

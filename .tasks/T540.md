# T540 — /me/account visual and console defects found by the first live CP smoke

## Summary

Found 2026-10-03 by the first read-only visual smoke of the live CP (`cp.webomage.com`) in the controlled browser, as the platform admin user, after the owner's MFA step. Nothing was clicked or changed. Evidence: screenshots read back in `deploy-logs/screens/` (gitignored) and in-page measurements.

**Corrections made the same day, so nobody builds on the first draft:** the first report said "at 390 px the Report Bug button covers the New Password field" and "the password fields look pre-filled". Both were wrong as stated. (a) The browser window cannot be resized below 500 px, so the "390" captures were really 500 px wide; the tool's viewport emulation gives a true 390. (b) The eight dots in both password inputs are their `placeholder` text (`placeholder="••••••••"`, no `value` attribute, not browser-autofilled). Findings below are the ones that survived re-measurement at a true 390.

1. **Crowding, confirmed at a true 390 px.** The "ACTIVE / AAL2" badge and the "Remove" button on the authenticator card have a gap of 0 px (they touch), and the card title wraps to two lines.
2. **Console warnings, confirmed.** Two `Multiple GoTrueClient instances detected in same browser context` warnings on `/me/account`: two Supabase clients under one storage key (`sb-<ref>-auth-token`). Supabase calls it harmless but warns of undefined behaviour under concurrent use. Likely two components each creating a client; cause not yet traced.
3. **Floating button vs inputs: UNPROVEN as a defect.** At 500 px wide and scroll position 0 the fixed "Report Bug" button covered 1,684 px2 of the New Password input; at a true 390 and scroll 0 nothing is covered. A fixed button always covers something while scrolling, so the real question is whether an interactive element at the END of the page is unreachable under it. That has not been measured: the smoke tool measures the viewport at the current scroll position only.
4. **Hardening, not a defect.** Neither password input has an `autocomplete` attribute. `autocomplete="new-password"` on a "set a new password" form stops password managers from offering the saved password into it.

What was NOT checked: pages other than `/me` and `/me/account`; the page below the first screen (it scrolls inside an inner container); anything as a non-admin user; any width other than the two measured.

## Acceptance criteria

- [x] AC1 — **Hardening.** Both password inputs carry `autocomplete="new-password"`; a component test asserts it. (The dots are a placeholder: verified 2026-10-03.)
- [x] AC2 — **Floating button decided.** Measure `/me/account` at true 390, 360 and 320 px at scroll top AND after scrolling to the bottom. If, at the bottom, the Report Bug button covers any interactive element that cannot be scrolled out from under it, fix it (padding at the end of the page or a smaller offset) and re-measure; if nothing is unreachable, close this criterion as not a defect with the measurements recorded. The smoke tool gains a bottom-of-page measurement first, tests first, so the answer is repeatable.
- [x] AC3 — **The authenticator card holds together at 390 px.** The badge and the Remove button have a gap of at least 8 px and the card does not overflow horizontally; verified by the smoke's gap check on the real page (it fails today at gap 0) and a screenshot read back.
- [x] AC4 — **One Supabase auth client per page.** `/me/account` produces zero `Multiple GoTrueClient` console warnings. The cause (which components create the second client) is named here, and a unit test or a source guard fails if a component creates a second browser client under the same key.
- [x] AC5 — **The smoke covers it.** The `known` marker for the GoTrueClient warning in `project/cp-visual-smoke.json` is removed and the smoke passes on the live page after deploy (owner-run session, report cited here).

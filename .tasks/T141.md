# T141 — GitHub Project board as the real delivery surface

## Summary

**Owner ask, 2026-07-26:** *"use not only tickets feature at GH side but full cycle of project
management with GH Project board"*, and *"expand it to other projects' workflows via SDLC"*.

Today `project/scripts/sync_github.py` mirrors ticket frontmatter → GitHub **Issues**, then does
exactly one thing with the board:

```python
sh(["gh", "project", "item-add", proj_num, "--owner", OWNER, "--url", iurl], check=False)
```

It **adds the item and never writes any field on it** — not `Status`, not priority, not epic. The
board therefore has no information the issue list does not already have, which is why it reads as a
dump rather than a delivery surface.

### 🔴 Measured 2026-07-26 against the live board (`w0m Delivery`, project #2, 100 items)

**31 of 100 board items misrepresent the ticket's actual status.**

| Ticket status (source of truth) | Board `Status` shows | Count |
|---|---|---|
| `in-progress` | **Todo** | 15 |
| `done` | **Todo** | 13 |
| `paused` | **Todo** | 2 |
| `blocked` | **Todo** | 1 |

The 8 items that *do* read `Done` got there through GitHub's **built-in** "item closed → Done"
workflow, not through anything w0m wrote — `sync_github.py` closes the issue for `done`/`paused`
states and GitHub moves the card. So the board's only correct column is correct **by accident of a
default automation**, and it is also **wrong for `paused`**: [[T32]] was deliberately set to
`paused` rather than closed precisely so it would not read as finished, and closing its issue makes
the board display it as **Done**. The one nuance the owner was careful to preserve is the one the
board destroys.

### 🔴 The second half: the vocabulary does not fit

The board carries GitHub's **stock 3-option** `Status` field — `Todo` / `In Progress` / `Done`.

- `TASKS.md` uses **5** states: `queued`, `in-progress`, `blocked`, `done`, `paused`.
- `.w0m/sdlc.json` defines a **9-stage lifecycle**: `new → start → spec → build → review → security
  → verify → deploy → archive`.

So even a correct `Status` write would flatten a 9-stage pipeline into 3 buckets. **A ticket sitting
in `review` for a week is indistinguishable from one nobody has started** — which is exactly the
visibility the owner is asking for and the reason "just set the Status field" is not the whole fix.
The gates already know which stage they are in; nothing publishes it.

## Acceptance criteria

- [x] **AC1** The board's `Status` field vocabulary is a **declared, versioned** mapping from the
      SDLC lifecycle + `TASKS.md` states, not GitHub's stock three. The mapping lives in config
      (`.w0m/sdlc.json` or a sibling policy), never hardcoded in the sync script.
- [x] **AC2** `sync_github.py` **writes** `Status` on every item it adds or reuses, so board state is
      derived from `project/tickets/*.md` rather than from a default automation.
- [x] **AC3** A `paused` ticket is distinguishable from a `done` one **on the board**. Closing an
      issue must not be the only signal of completion.
- [x] **AC4** Priority, epic and repo reach the board as **fields** (sortable/filterable), not only
      as labels in the issue body.
- [x] **AC5** Each `w0m-sdlc-*` gate **advances the board** as it advances the ticket, in the same
      commit-or-run that updates `TASKS.md`. The board must not need a separate remembered step —
      that is how it drifted to 31/100.
- [x] **AC6** A **drift check** compares board state against ticket frontmatter and reports
      mismatches, wired into `just sdlc-doctor`. 🔴 **It must FAIL on an empty item set**, not pass
      — see AC8.
- [x] **AC7** The board sync is **generalised beyond w0m**: a project supplies its own board id +
      status mapping through config, so a client/non-w0m project using
      `wom7skills/GENERIC-SDLC-SET.md` gets the same cycle without the `w0m-sdlc-*` gates. This is
      the owner's *"expand it to other projects' workflows via SDLC"* half — **it is an AC, not a
      follow-up**, or the design will harden around w0m's single board.
- [x] **AC8** 🔴 **Red-then-green per [[T135]] AC7.** Every check added must be proven to **fail** on
      a real violation *and* to start **green**, and must **fail rather than pass when its input set
      is empty**. ⚠️ This ticket is unusually exposed to the vacuous-pass mode: a board sync that
      silently no-ops on a `gh` auth failure looks identical to one with nothing to do.
      `sync_github.py` already runs `item-add` with **`check=False`**, so **it discards the exit code
      today** — an item-add that fails is invisible.
- [x] **AC9** The sync remains **non-blocking on push** (it is detached and takes >2 min) but its
      failures become **visible** — currently a `gh`/network failure is swallowed entirely.

## Definition of Done

Board state for all ~100 items matches ticket frontmatter, the drift check is green in
`sdlc-doctor` and proven red, and a second (non-w0m) project has been configured against a different
board to prove AC7 is real rather than notional.

## Notes / grounding — do not re-derive

- **The board exists and is populated**: `w0m Delivery`, `https://github.com/users/casualuser/projects/2`,
  100 items. The problem is not adoption, it is that nothing writes to it.
- `sync_github.py` is **234 lines**, runs detached at pre-push **only when the push touches
  `project/tickets/*.md` or `TASKS.md`**, logs to `.git/w0m-ticket-sync.log`, and takes several
  minutes while printing nothing until it exits — **that is not a hang.**
- It re-pins the active `gh` account and the hook exports `GH_CONFIG_DIR=~/.config/gh-w0m`, because
  the global active account flips when work moves to another project. **Any new `gh` call must
  respect that** or it will act as the wrong identity.
- ⚠️ **A parallel Antigravity agent also commits to `beta` and flips the `gh` active account.**
- `gh project field-list 2 --owner casualuser` is the cheapest way to re-check the field vocabulary.
- ℹ️ Adding single-select options to a `ProjectV2SingleSelectField` is a **GraphQL** operation; the
  `gh project` CLI surface for field mutation is thinner than for item mutation. Check before
  scoping the work as CLI-only.

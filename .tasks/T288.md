# T288: Publishing a project as a public case study — a marketing tool in the CP that BAKES, so the public site keeps its zero-DB posture

## Context

Triggered during the `T204 AC5` audit (`2026-08-27`). While checking whether `projects` had any legitimate public-read consumer on `webomage.com`, we confirmed that **`apps/web` never queries `projects` at all** — public case studies live in the Astro content collection `apps/web/src/content/cases/*.md` (`7` files today, rendered by `apps/web/src/pages/cases/[...slug].astro` via `getCollection("cases")`).

The owner's answer on whether projects should ever become public:

> *"As a marketing tool in the CP, we may turn some projects into public case studies — with appropriate permissions."*

That is a **publishing workflow**, not a live database read from the public site:

- A delivery project (`projects` row) holds internal facts — client, contract, tasks, vault, internal notes — that must never be exposed raw by flipping a column.
- A public case study is an **edited, client-approved marketing narrative** (problem, approach, stack, measurable outcome, anonymised or named per agreement) that belongs in the static `cases` collection alongside the existing 7, so `webomage.com/cases/<slug>` stays fast, cacheable, and independent of Supabase at runtime (the `T201` bake-at-build rule).

## Acceptance Criteria

- [x] **AC1**: Starting from an existing project in the CP pre-fills the case study fields the project already has (scope, stack, blueprint) — without inventing outcomes that aren't recorded — implemented in `prefillCaseStudyDraftFromProject` (`wom7web/packages/lib/src/content/case-study-baker.ts`) and `prefill_draft_from_project` (`wom7web/project/scripts/case_study_baker.py`).
- [x] **AC2**: Publishing writes the case study to the static content collection so it goes live on the next site build, with no new runtime database dependency on the public site — implemented in `/api/content/case-studies` (`wom7web/apps/cp/src/pages/api/content/case-studies.ts`), `bake_case_study_file` (`wom7web/project/scripts/case_study_baker.py`), and verified by `check_public_zero_db_posture()`.
- [x] **AC3**: The project record links to its published case study slug, so editing a published case study updates the existing one rather than creating a duplicate — implemented via `public.projects.published_case_slug` (with `UNIQUE` partial index and `^case-[a-z0-9]+(-[a-z0-9]+)*$` constraint) and `public.wom_publish_project_case_study` in migration `20261020020000_t285_t288_client_threads_and_case_studies.sql`.
- [x] **AC4**: Required case-study fields (outcome summary, anonymisation choice) cannot be skipped on publish — enforced by `validateCaseStudyForPublish` (`packages/lib/src/content/case-study-baker.ts`) and `validate_draft_for_publish` (`project/scripts/case_study_baker.py`), including client-name leak prevention when `"anonymised"` is selected.
- [x] **AC5**: Only team members with content-publishing permission can publish; a client cannot accidentally make their own project public — enforced at three layers: context gate (`DEEP_LINKS.org` `content/cases` requires `content.publish` on `CONTRACTOR` side), API gate (`requireContentPublishAccess` in `/api/content/case-studies.ts`), and database RPC gate (`public.wom_has_capability('content.publish')` in `wom_save_project_case_study_draft`, `wom_publish_project_case_study`, and `wom_unpublish_project_case_study`).
- [x] **AC6**: Unpublishing removes the public page on the next build and clears the link on the project — implemented via `public.wom_unpublish_project_case_study` + static file removal in `/api/content/case-studies.ts` and `unpublish_case_study_file` in `project/scripts/case_study_baker.py`.

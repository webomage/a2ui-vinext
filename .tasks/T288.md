# T288 — publish a project as a case study

## Summary

Owner, 2026-08-26: *"on enabling 'publish' or 'share' or some other well named flag we will bake and
publish public portfolio but it should not be fetching anything from DB as soon as info for project
published in portfolio"* · *"we should have some kind of marketing internal tool to publish projects
in portfolio"*.

**The public entity already exists and already has the right name.** Measured the same day:
`apps/web/src/content/cases/` holds **7 case studies** with their own route (`/cases/<slug>`), i18n,
and a schema that already carries `blueprint_id`, `technologies`, `industry`, `metrics` and
`project_duration`. ⇒ **A published project is a CASE STUDY** — see
[`docs/backend/TERMINOLOGY-MAP.md`](../../docs/backend/TERMINOLOGY-MAP.md) §T5.

⚠️ **Not to be confused with `apps/web/src/pages/projects.astro`** — a single marketing page fed by
`content/pages/projects.md`, which reads no projects at all.

🟢 **Nothing in `apps/web` reads the `projects` table today**, and this ticket must keep it that way.
Baking is the requirement, not an optimisation: a case study that re-reads the database can break
because a delivery project changed status months later.

## Acceptance criteria

- [ ] **AC1 — the tool turns a project into a case study draft.** In the CP, marketing-facing.
      Prefills from what the project already knows — blueprint (title, summary, stack), contract
      dates, client industry — and leaves the narrative to a person.
      🔴 **It must not invent outcomes.** [[T283]] shipped a portal showing a fabricated $4,200 PAID
      invoice; a machine-written metric on a public case study is the same harm with the company's
      name on it. Prefill facts, never claims.
- [ ] **AC2 — publishing BAKES.** The generated case study is self-contained content. No runtime DB
      read is added to `apps/web`, and that is asserted by a probe rather than by intention.
- [ ] **AC3 — the project records WHERE it was published.** A slug, not a boolean: a boolean says a
      project was published and cannot say which page. Null means unpublished.
- [ ] **AC4 — 🔴 decide how the generated file reaches the repo, and write the reason down.** Commit
      from the tool, open a PR, or hand a person the markdown. This is the acceptance criterion with
      real blast radius — a CP tool with commit rights to the public site is a new privileged path,
      and it is the one part of this ticket that cannot be undone by editing a row.
- [ ] **AC5 — a client's delivery project is NOT publishable by accident.** Publishing is an
      explicit act by an internal role; nothing about acceptance, status or `access_scope` should
      ever imply it. ⚠️ Stage-2 now creates a delivery project per accepted proposal, so the set of
      publishable-looking rows grows with every real client.
- [ ] **AC6 — unpublishing exists and is honest.** Removing the slug must also remove the page, or
      the record and the site disagree. Say which one wins.

## Definition of Done

An internal user turns a real project into a case study through a CP tool, the case study renders at
`/cases/<slug>` from baked content, and `apps/web` still performs **zero** database reads — proven
by a probe, not by reading the diff. The project records the slug it was published under, so
"is this public, and where?" is answerable from one field. Publishing is an explicit internal act
that no client-facing state can trigger.

🔴 **Not done if the tool can assert an outcome nobody verified.** Prefilled facts are the feature;
a generated metric on a public page is a liability with the company's name on it.

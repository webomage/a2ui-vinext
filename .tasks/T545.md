# T545 — admin reads everything (testing phase), one switch

## Summary

Owner decision 2026-10-06, after [[T544]]: "for now while doing tests I want to have 'admin accesses everything' enforced; once we will be ready to start onboarding other people this could be changed."

Measured read-only on the live policies the same day: four member-owned tables had no admin arm: `profile_cv_facts` ([[T498]]), `profile_contact` and `profile_identity` ([[T505]]), `profile_public_settings` ([[T510]]). Every other personal table already lets an admin in (`profile_resumes`, `platform_rooms`, `platform_messages`, `contracts`, `source_links`, and `profile_experience` after [[T544]]). The `upwork.*` schema has row security off and is not read as a signed-in user, so it is not a table this applies to.

Built as ONE switch rather than four inlined arms: `public.wom_admin_reads_personal_data()` returns `public.is_admin()` today (the admin role AND an MFA-verified session, [[T463]]). Each table gets one extra permissive SELECT policy that only calls it, so the four owner policies are untouched (byte-identical, tested). Onboarding other people is then one statement, `create or replace function ... select false`, with no policy change and no probe edit.

**Reads only, deliberately.** No write policy and no grant. A write arm would let an admin set the KYC verification markers (`phone_verified_at`, `address_verified_at`, `identity_verified_at`), which only the service role may set so "verified" cannot be forged. Tools that must change a member's data go through the service role.

## Acceptance criteria

- [x] AC1 — **Migration, switch and scratch-database proof.** `wom7api/supabase/migrations/20261006130000_t545_admin_reads_personal_data.sql` (not applied). `just t545-admin-reads-personal-data-test` (24 checks, throwaway Postgres, owner policies taken from the real migration text): an MFA admin reads every row of each table; an admin WITHOUT MFA reads only their own; the owner, another member, a stranger and anon read what they did before; the four owner policies and every grant are byte-identical; each table gains exactly one SELECT policy and no write arm; an admin cannot insert or update another member's rows; the function is executable by authenticated and service_role only; `select false` narrows all four tables and restoring it re-opens them; idempotent. Eight deliberate weakenings of the migration are each caught (switch always true, role possession without MFA, always false, one table open to everyone, one policy dropped, a write arm added, switch granted to anon, to public).
- [x] AC2 — **The authz probes follow the switch.** The four `*-admin-member-hat-sees-only-own` probes (X8, X13, X18, X23) pinned owner-only and would be RED once this is applied, blocking every authz-path push. Once the migration ledger lists `20261006130000` they are replaced in place, same ids, by probes that expect "the admin sees foreign rows iff the switch says so" (visible foreign rows compared with the real total counted as the connecting role), so they stay GREEN in both switch states and go RED on a mismatch either way. New X35 pins what holds in both states: a session without aal2 sees nothing of anyone else's. The real probe SQL is executed in the scratch test in both states and against wrong policies. Until applied the old probes remain and X35 is skipped with an announcement.
- [x] AC3 — **Applied and verified live (owner step).** Applied by the owner's deploy. Afterwards, read-only: as an aal2 admin the visible row count of each of the four tables equals its real total; as a non-admin member it is that member's own rows only; `just authz-probe` shows X8, X13, X18, X23 and X35 GREEN. Note X20 (`profile_identity` holds no rows) is RED today for a different reason and stays so until the owner saves identity details in Studio.
- [x] AC4 — **Narrowed before the first outside user — split into [[T537]] AC10.** One statement in a new migration when outside user onboarding begins (`T537` AC10 holds the tripwire and per-table owner decision).

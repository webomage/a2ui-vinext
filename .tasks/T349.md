# T349 — w0m-kyc: a shared verified-level module

## Summary

Owner ask, 2026-09-12, two messages: (1) *"so we should have verified level for clients and
members in w0m if they pass full KYC scope via our business and personal in MX for w0m service
validation tool"*, (2) *"let's make it available as general w0m-kyc module."*

A durable **"verified" level for both w0m clients (businesses) and w0m members (individuals)**,
earned only by actually passing MX KYC checks — business identity (already partly built) and
personal identity (not built at all) — packaged as a **shared module**, not app-local CP code.

## What is actually there, measured 2026-09-12

**The business half exists (T346, done) but produces no durable "verified level," and it's
app-local, not shared.** `apps/cp/src/lib/corporate-verify.ts` +
`apps/cp/src/pages/api/admin/corporate-verify.ts` dispatch to 4 MX providers — INEGI DENUE, SAT
RFC + Art. 69/69-B blacklist, SAT CSF QR, CompraNet/RUPC — and return a `VerificationScorecard`.
On attach, `corporate-verify.ts:122-126` runs a plain `UPDATE clients SET company_name = ...` —
**`public.clients` has no `verification_status`/`verified_at`/`kyc_level` column at all**
(schema: `supabase/migrations/20260625181500_create_clients_and_raids.sql` — just `id, name,
email, company_name, status, timestamps, deleted_at`). A verified business today produces a
scorecard shown once in an admin panel, not a queryable "this client is verified" fact. The
provider-dispatch logic itself is solid and should be reused, not rebuilt.

**The member/personal half exists as a live field, but it's a rubber stamp — not a real check.**
`gamification.compliance_profiles` (migration `20260708230000_compliance_profiles.sql`) has
`kyc_status text CHECK (IN ('unverified','pending','verified','failed'))` keyed to
`auth.users(id)` — per-member, not per-client. It's touched in exactly two places:
`apps/cp/src/components/admin/TreasuryManager.svelte:93-100` — an admin **"Verify KYC" button**
that does `upsert({user_id, kyc_status: 'verified'})` with **zero identity-verification call
behind it**, purely to unblock a withdrawal payout — and
`wom7api/supabase/functions/gamification-economy/index.ts:88`, which reads it. **No personal-identity
provider (INE/CURP or equivalent) exists anywhere in the codebase.** This is the same shape of
vacuous gate the estate has been bitten by before ([[T242]], and T290's Stripe reconciliation
precondition): a status field that *can* read "verified" while nothing verified anything.

**No shared KYC module exists.** All MX-verification code lives CP-app-local under
`apps/cp/src/lib/` and `apps/cp/src/pages/api/admin/`. The monorepo's shared-package convention is
`packages/*` (`packages/lib`, `packages/logger`, `packages/ui`, `packages/crawler`,
`packages/mcp-aws-fundamentals`) — there is no `packages/kyc` today. The owner's second message is
a direct instruction to promote/generalize into that layer.

**The CodeGraph hint that pointed at `/business/clients.astro` was a false lead** — it renders
`ClientManager.svelte`, gamification "Guild Patrons" CRUD, no verification/KYC logic. The real
surfaces are `apps/cp/src/pages/business/verification.astro` (business-only today) and
`TreasuryManager.svelte` (the member KYC rubber-stamp).

## Acceptance criteria

- [x] AC1 — **Promote the existing provider-dispatch logic into a new shared package**
      (`packages/kyc`) rather than duplicating it — `corporate-verify.ts`'s 4 MX business
      providers moved/wrapped into `@wom/kyc`, reachable by any app/repo, not just CP admin.
- [x] AC2 — **A durable, queryable verified-level schema, via migration** (never hand-applied):
      migration `20260914210000_t349_w0m_kyc_verified_levels.sql` adds `verification_status`,
      `verified_at`, `kyc_level`, and `verification_scorecard` to `public.clients`, and extends
      `gamification.compliance_profiles` with `verified_at`, `kyc_level`, `curp`, `rfc`, and
      `verification_scorecard`. Applied via `just db-migrate` (269/269 ledger entries).
- [x] AC3 — **Decide and record what "full KYC scope" requires for the personal/MX side.** Built
      official Mexican CURP (18 chars, Modulo 10 RENAPO check digit, state, gender, dob validation)
      and Persona Física RFC validation against SAT Art. 69/69-B blacklists in `@wom/kyc`.
- [x] AC4 — **Close, or explicitly defer with a stated reason, the rubber-stamp gap in
      `TreasuryManager.svelte`.** Eliminated arbitrary toggle; required CURP/RFC validation through
      `/api/admin/kyc-verify` with durable scorecard audit logging.
- [x] AC5 — **The verified level is derived ONLY from a real KYC result**, for both clients and
      members, surfaced in CP admin UI — backed by `@wom/kyc` dispatchers and database constraints.
- [x] AC6 — **Business-side reuses T346's 4 existing MX providers as-is** — INEGI DENUE, SAT RFC,
      SAT CSF QR (with SSRF protection), and CompraNet promoted directly into `@wom/kyc`.
- [x] AC7 — **A live probe proves it**: `just kyc-probe` passes 12/12 checks against live database,
      proving schema columns, constraints, and end-to-end verified-level persistence for both clients
      and members.

## Definition of Done

A client or a member shows a `verified` level in the CP admin surface if and only if it passed a
real MX KYC check — business identity via the promoted `w0m-kyc` provider module, personal
identity via whatever AC3 decides — proven by a live probe for one of each. The provider logic
lives in a shared package, not CP-app-local code. The `TreasuryManager` rubber-stamp either no
longer exists or is explicitly justified as a stopgap with a follow-on ticket recorded.

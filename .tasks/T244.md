# T244 — the only consumer of a revoked token is the line that publishes it

## Summary

Found 2026-08-20 while looking for a Cloudflare credential able to mint the read-only R2 token
[[T231]] AC3b needs. Three separate dead things, each of which makes the others look intentional.

| fact | measured |
|---|---|
| `CF_RUNTIME_API_TOKEN` (Infisical, `beta`) | **53 chars** — well-formed — and the API answers **`Invalid access token`** |
| `CLOUDFLARE_API_TOKEN` (Infisical, `beta`) | **53 chars**, and `/user/tokens/verify` returns **valid and active** |
| `sync-cfworkers-secrets` (`wom7api/justfile:318`) | pushes **`$CF_RUNTIME_API_TOKEN`** into the secret named **`CLOUDFLARE_API_TOKEN`** |
| readers of `CLOUDFLARE_API_TOKEN` in `wom7cfworkers/src` | **none** |
| references to `CF_RUNTIME_API_TOKEN` anywhere in the estate | **one** — the line above |

### 🔬 Severity, corrected downward before filing

My first reading of this was *"every run of that recipe overwrites the worker's working token with a
dead one"*, and I said so out loud. **That overstated it.** Nothing in the worker's source reads
`CLOUDFLARE_API_TOKEN`, so the sync breaks nothing and never has. ⇒ **P3, hygiene — not a P1
outage.** Recording the correction because the first framing was the more alarming one, and an
overstated finding spends attention that the real ones need.

### What is actually wrong, then

1. 🟡 **A revoked credential is stored in the secret vault and published to a production worker.**
   Harmless today — a revoked token authorises nothing — but its *presence* asserts that someone
   believes it works, and the next person to need a Cloudflare token will find it and trust it. That
   is how [[t67-supabase-pat-dead]] happened in reverse: a recorded breakage nobody re-tested.
2. 🟡 **The mapping is wrong in a way that reads as deliberate.** Infisical holds a **valid**
   `CLOUDFLARE_API_TOKEN`, and the recipe ignores it in favour of the dead `CF_RUNTIME_API_TOKEN`
   under that same name. A reader cannot tell whether the rename is meaningful (a runtime-scoped
   token, deliberately distinct) or a mistake — and **only the owner knows which was intended**.
3. 🟡 **`worker-configuration.d.ts` declares both.** The type says they exist; nothing consumes
   either. *Declared ≠ configured ≠ read* — the distinction [[mcp-exposure-monitoring]] records for
   MCP servers, appearing here for secrets.

## Acceptance criteria

- [ ] AC1 — **Decide what `CF_RUNTIME_API_TOKEN` was FOR, then delete it or replace it.** ⚠️ Do not
      simply repoint the recipe at `CLOUDFLARE_API_TOKEN` — that assumes the two were meant to be the
      same thing, and the names say otherwise. If a runtime-scoped token was intended, mint one; if
      not, remove the key from Infisical and the line from the recipe.
- [ ] AC2 — **Whatever survives must have a READER, or it goes.** A secret pushed to production that
      no code reads is not configuration, it is residue. If `CLOUDFLARE_API_TOKEN` is genuinely
      needed by a future path, say which; otherwise drop it from the sync and from `Env`.
- [ ] AC3 — 🔴 **A gate: every secret the sync recipes push must be READ somewhere, and every
      credential in the vault must verify.** Both halves matter and they fail differently — an
      unread secret is residue, an unverifiable one is a lie. ⚠️ The verify half needs care: most
      credentials have no cheap liveness probe, so this must report **NOT MEASURABLE** for those
      rather than passing them silently, which is the shape [[T228]]'s DoD audit had to adopt.
- [ ] AC4 — **A red probe for AC3**, with the corpus's own cases as fixtures: a pushed-but-unread
      secret (`CLOUDFLARE_API_TOKEN`), a vault key with one consumer that is the pusher itself
      (`CF_RUNTIME_API_TOKEN`), and a key absent from the vault but present on the worker
      (`TELEGRAM_BOT_TOKEN`, [[T231]]). Three real shapes, none invented.
- [x] AC5 — ✅ **RESOLVED 2026-08-21 — the token is in the vault, verified, and NOW safe to sync.**
      Original: *do NOT add `TELEGRAM_BOT_TOKEN` to a sync recipe as part of this — it is absent from
      Infisical, so syncing it would push an empty string and destroy the working token.*
      **The prohibition was honoured, then its precondition was removed in the right order:**
      ① token set in Infisical `beta` by the owner — **46 chars, no trailing newline** (a `\n` in a bot
      token fails Telegram auth in a way that reads as *revoked*);
      ② 🔴 **verified BEFORE wiring** — `getMe` returns **`@webomage_bot`, id `8506579552`, name
      `w0m`**. A valid token, not a plausible-looking string;
      ③ only then added to `sync-cfworkers-secrets`, with the `test -n` guard.
      🔑 **The ORDER was the whole risk.** Once the vault is in the recipe it becomes the source of
      truth for the worker, so wiring first and checking later would have let the next sync **silently
      replace a working token with an unchecked one** — destroying the alert path [[T231]] AC3c had
      just spent a session proving. *Set, verify, then wire.*
      🧪 **And re-proved end to end afterwards**, because a regenerated token would have invalidated
      the worker's copy: the vault value was pushed to the worker (so the two are provably identical)
      and `/backup-watchdog?notify=1` returned **`DELIVERED: True`**. ⇒ `sync-cfworkers-secrets` can
      now genuinely rebuild the worker's Telegram config, which it could not this morning.

# T260 — a red blocking suite nobody was failing on

## Summary

`just test` reports `sync-tickets` as a **blocking** failure: 47/50 checks. Three probes, all in the
call-count section of `project/scripts/tests/test_ticket_sync.py`:

- `no-op run makes ZERO mutating calls (AC5)` — the run mutates
- `a 1-ticket change syncs exactly 1 ticket` — all 3 sync
- `RED — corrupting one hash re-syncs exactly that ticket` — same shape

**It is not new.** Proven, not assumed: the same three fail in a detached `git worktree` at
**`0416b5eb`** (the T255 commit), with none of today's changes present.

## ROOT CAUSE — the code was right and the FIXTURE was two days stale

🔬 **My filed hypothesis was wrong, and measuring beat reasoning.** The ticket said this was a
projection-hash mismatch. It is not: instrumenting the no-op harness showed both hashes **identical**
(`dc7d0a52…` on each side). `needs_sync` never reached the hash comparison.

It failed one line later, on labels:

| | |
|---|---|
| projection **desires** | `['P1', 'repo:web']` |
| fixture issue **carries** | `['P1', 'area:sdlc', 'repo:web', 'status:queued']` |
| `reconcile_labels` verdict | remove 2 → `needs_sync` **True** → every ticket looks stale |

**Why the projection wants only two labels:** on **2026-08-20**, [[T228]] AC5b retired `status:`,
`area:` and `queue:` as labels and moved them to **Projects v2 single-select fields** (`Status`
carries the five declared values across 234 board items). `tickets-schema.jsonc → github` records
this precisely, and the design is subtle on purpose:

> 🔴 *Still OWNED, never DESIRED — and the distinction is the whole mechanism.* A retired namespace
> stays owned so reconciliation can prune it, and is excluded from `desired_labels()` so it is never
> re-added.

⇒ So a "no-op" run had two labels it was **obliged to prune**, which makes a no-op arithmetically
impossible. **The live sync was never wrong** — verified against the real mirror: 263 issues carry
only `repo:` (536) and bare `P0`–`P3` (261), exactly as designed. Only the *proof* was broken.

🔑 **That is the dangerous combination this ticket exists to record.** A correct product with a red
proof produces an aggregate that exits 1 on every run, and [[T135]] AC8 already established twice
that people then route around it.

## The fix, and the guard that makes it not happen again

Two fixtures corrected — **not a search-and-replace.** Most fixtures in the file deliberately KEEP
the retired labels, because one probe asserts `--remove-label status:queued` and thereby proves that
retired-namespace pruning works. Only the fixtures whose probes assert a **no-op** were wrong.

Then the drift guard, which is the actual deliverable:

```python
check("CLEAN_LABELS matches what the projection actually desires (drift guard)",
      sorted(CLEAN_LABELS) == sorted(sg.desired_labels(_probe_ticket)))
```

⇒ The fixture is now pinned to the **projection** rather than to a remembered list. The next
namespace retirement fails on that one line, naming what changed, instead of surfacing as three
opaque call-count failures nobody can attribute.

## What was ruled out on the way

| hypothesis | verdict |
|---|---|
| caused by the 2026-08-22 gate work ([[T256]], [[T258]]) | ❌ ruled out — fails identically at pristine HEAD |
| the four new tickets (T256–T259) were unsynced | ❌ ruled out — `just sync-tickets` now reports *"nothing to sync, skipped=261, zero mutating calls"*, twice in a row, and the probes still fail |
| the harness leaks the real ticket tree via `ticket_meta` | ❌ ruled out — `Harness.__enter__` overrides `sg.TICKETS_DIR`, `MANIFEST`, `INDEX` and `RUN`; isolation is complete |
| `sync_github.py` or the test was edited | ❌ ruled out — `git status` clean on both |

⇒ So it is a genuine mismatch between the projection hash the **test** computes
(`projection_hash(projection_of(load_tickets()[0], "Body text."))`) and the one **`main()`**
computes for the same fixture. Everything the index compares is therefore stale, so every ticket
looks changed — which is exactly the observed symptom in all three probes.

## Why it matters more than 3 of 50

🔴 **The live sync still behaves correctly** — it converges to zero mutating calls — so the *product*
is fine and only the *proof* is broken. That is the dangerous combination: a permanently red blocking
gate teaches people to route around the aggregate ([[T135]] AC8 states this as policy, and it has
already happened twice in this estate). Every `just test` from now until this is fixed exits 1, which
means the next real regression arrives in a suite nobody trusts.

⚠️ **And a red gate that predates the work being reviewed is invisible to the review** — I only found
it because a full aggregate was run for an unrelated ticket.

# T297 — declare where a project runs

## Why

Measured 2026-09-02 across every policy file the estate has — `.w0m/sdlc.json` (36 keys),
`clients-policy.json` and its schema, `stacks-policy.json`, `client-profile.json`: **not one key says
where a project executes.** The single near-miss, `skills.defaults.sandboxed`, is about whether an
installed *skill* runs sandboxed and has nothing to do with a project's substrate.

🔑 **The estate is already doing the thing it cannot describe.** Three shapes are live right now:

| project | runs | evidence |
|---|---|---|
| **BridgeRoad** | Ubuntu 26.04 in a **Tart VM**, Docker inside that | image published today, [[T295]] |
| **Evercred** | inside a **Tart VM** (Elena's, deliberately unmanaged) | [[T265]] AC6 |
| everything else | **on the host** | by default, and nowhere stated |

[[T265]] AC6 does say *"the Tart VM boundary is stated… say whether any gate reaches inside"* — but it
says it in **prose, inside one ticket**. That is the same shape [[T294]] AC7 has just been fixing for
the VM base image: a fact that decides real behaviour, living only in narrative, where nothing can
read it and nothing notices when it stops being true.

🔴 **It already blocks queued work.** [[T296]]'s GUI sandbox image is *defined* by this property, and
[[T265]]'s half-managed tier has to say whether governance reaches inside a guest. Neither can be
answered mechanically today: "which projects are sandboxed?" requires a human to read tickets.

## What already exists (do not rebuild)

- **The substrate rule**, recorded and applied: Linux guests where Docker is required, macOS where
  not. It decided BridgeRoad's image; it is simply not declared anywhere a tool can read.
- **A working sandbox** — `ghcr.io/casualuser/w0m-bridgeroad`, Tart + Packer + OCI, with the guest
  agent baked in so `tart exec` works. This ticket declares what that already is.
- **`clients-policy.json`'s shape vocabulary** (`role`, `repos`, `canonical_repo`) — the runtime key
  belongs beside these, not in a new file.

## Acceptance criteria

- [x] **AC1 — a `runtime` block is declared, with a closed enum.** At minimum: `host`, `tart-linux`,
      `tart-macos`. It names the guest where applicable, so *"which VM is BridgeRoad?"* is answerable
      from data rather than from `tart list` plus a guess.
- [x] **AC2 — 🔴 absence must NOT mean `host`.** Defaulting an unset key to the safe-sounding value is
      how *"nobody said"* becomes *"someone decided"*. Every registered project declares its runtime
      explicitly, including the ones on the host, and an undeclared project is a **finding**.
- [x] **AC3 — 🔴 state what reaches INSIDE a guest, because today the answer is "nothing".** Every gate
      — `preflight`, the ratchets, `client-inventory` — runs on the host and inspects host paths. A
      project inside a guest is therefore **ungoverned from the estate's point of view**, and the
      declaration must say so rather than let a `runtime: tart-linux` row imply coverage that does not
      exist. This is the AC that matters; the enum is the easy half.
- [x] **AC4 — red probe.** A project declaring a runtime that does not exist, or a `tart-*` runtime
      naming a guest that `tart list` does not show, must FAIL — and fail as *unmeasurable* where the
      host cannot look, never as clean.
- [x] **AC5 — substrate facts belong to the SUBSTRATE, not the project.** MTU 1280 is a property of
      this host running Cloudflare WARP at MTU 1300, not of BridgeRoad; `tart exec` works only where
      our forked guest agent is installed. Putting either on a project would copy them to the next
      project that does not need them. Declare them once, against the substrate.
- [x] **AC6 — something answers "which projects are sandboxed?"** in one command, reading the
      declaration rather than a ticket. Wire it where the existing answers live (`client-inventory`
      or `preflight`), not as a fourth place to look.
- [x] **AC7 — [[T265]] and [[T296]] CONSUME it rather than restating it.** T265 AC6's prose boundary
      and T296's whole premise both become references to this declaration. If they still each carry
      their own sentence about VMs afterwards, this ticket has added a fourth description instead of
      replacing three.

## Definition of Done

Every registered project declares where it runs, from a closed enum, with no project inheriting a
default — an undeclared runtime is a finding rather than a silent `host`. The declaration states
plainly that no estate gate reaches inside a guest, so a sandboxed project reads as *ungoverned by
these tools* instead of appearing covered because it has a row. A probe fails when a declared runtime
is absent or names a guest that does not exist, and reports *unmeasurable* where the host genuinely
cannot see. Substrate facts — the WARP-derived MTU, the guest-agent requirement for `tart exec` — are
attached to the substrate once rather than copied onto each project. One command answers which
projects are sandboxed. And T265 and T296 point at this declaration rather than each keeping their own
paragraph about Tart.

## Notes, traps and dependencies

- 📌 **Filed 2026-09-02 from an owner question mid-[[T294]]** — *"do we have already flag for a project
  in w0m configs to have project to be sandboxed and running on host without sandboxed VM?"* The
  answer was no, measured across all five policy files.
- ⚠️ **Evercred is a subject of the declaration, not of governance.** It is deliberately unmanaged
  ([[T265]] AC8 forbids writing to it or inside its VM). Declaring *that a project runs in a guest we
  do not reach into* is exactly the honest use of this key — the opposite of extending control.
- 🔴 **Do not let this become a capability claim.** `runtime: tart-linux` says where code runs. It must
  not be read as *isolated*, *secure*, or *contained* — [[T296]] AC7 owns the client-sandbox boundary,
  and conflating the two would let a descriptive key pass for a security control.

# T381 — Enforce admin authorization in lead-api and guild-api edge functions

## Summary

During an automated AST dead-code and security audit via `code-review-graph` (CRG), an unwired authorization check was discovered in two production Supabase edge functions in `wom7api`:

1. `supabase/functions/lead-api/index.ts:32`: `const isAdmin = async (): Promise<boolean> => ...` is declared at the top of the request handler but is **never invoked** by any action in the switch dispatcher. Highly privileged administrative mutations execute with only `requireAuth(req)` (i.e. any authenticated user with a valid Supabase JWT):
   - `promote_upwork_match`: Creates/upserts external leads from Upwork job matches.
   - `update_lead_status`: Transitions lead lifecycle stages and reassigns lead `owner_id`.
   - `draft_proposal`: Generates commercial client proposals with financial estimates.
   - `accept_proposal`: Accepts proposals, provisions client records, updates lead status to `won`, and creates legally binding draft direct contracts with amounts.
2. `supabase/functions/guild-api/index.ts:45`: `const isAdmin = async (): Promise<boolean> => ...` is similarly declared but unused. Model A hierarchy CRUD was retired under AgDR-0022 with HTTP 410, and active onboarding/certification endpoints operate on `user.id`. Any future administrative certification actions must strictly enforce this guard.

This ticket hardens `lead-api` and `guild-api` by enforcing explicit admin authorization guards (`isAdmin()`) on all administrative operations, failing closed with HTTP 403 Forbidden for non-admin callers, backed by automated red-probe authorization tests.

## Acceptance criteria

- [x] AC1 — **Enforce `isAdmin` in `lead-api` Mutations**: In `supabase/functions/lead-api/handler.ts`, enforced `if (!await isAdmin()) return json({ error: "Forbidden: admin role required" }, 403);` across all administrative actions (`promote_upwork_match`, `update_lead_status`, `draft_proposal`, `accept_proposal`). Calling these actions without `role = 'admin'` or `user.id === 'service_role'` fails closed with HTTP 403.
- [x] AC2 — **Audit and Clean `guild-api` Handler**: In `supabase/functions/guild-api/index.ts`, audited all action handlers (Model A actions retired 410; active actions `enroll_certification` and `complete_onboarding_quest` strictly `user.id`-scoped self-service). Documented the security boundary and pruned the unused `isAdmin` declaration.
- [x] AC3 — **Author Automated Red-Probe Authz Suite**: Created `supabase/functions/lead-api/lead-api.test.ts` verifying that requests to `lead-api` actions with a non-admin authenticated user JWT return HTTP 403 Forbidden, whereas requests with admin user JWT or service_role key succeed, and unknown actions return HTTP 400.
- [x] AC4 — **Quality Gates & AST Validation**: Verified that `just deno-check` and `just deno-test` in `wom7api` pass cleanly. Run `code-review-graph dead-code` to confirm that `isAdmin` is properly referenced and no longer flagged as dead code.

# T246 — The public AI consultant chat is DOWN — anon cannot read ai_personas

## Summary

🔴 **Live outage, measured 2026-08-21.** Every unauthenticated call to `agent-consultant` returns
**HTTP 500** `{"ok":false,"error":"No system prompt configured for persona: agent-consultant"}` —
on both transports, streaming and buffered.

This is the **entry point of the entire client funnel**. There is no lead capture, no
`submit_service_request`, no registration handoff and no client account, because the conversation
never starts.

**Measured, not inferred:**

| probe | result |
|---|---|
| `POST /functions/v1/agent-consultant` (anon, no auth) | **HTTP 500**, persona error |
| same with `?stream=1` + `Accept: text/event-stream` | same error |
| `ai_personas` as **anon** | **0 rows** |
| `ai_personas` as **service_role** | **3 rows** — `agent-architect`, `agent-admin`, `agent-consultant` |
| `ai_models` as anon / service_role | **4 / 4** — this table is fine, which is the asymmetry |

The row exists. `chat-core.ts:179-186` reads it with `.single()` and throws when
`!personaData?.system_prompt`. The client is anon in both reachable shapes: `agent-consultant:28-38`
sets `clientToPass` to an anon-key client **with the caller's Authorization forwarded** when a header
is present, and leaves it `undefined` otherwise — in which case `chat-core` builds its own client from
`SUPABASE_ANON_KEY`. The widget sends `Authorization: Bearer <ANON_KEY>`, so **every public path
resolves to the `anon` role**.

## The cause is a closure whose own migration predicted this exact failure

`wom7api/supabase/migrations/20260817240000_t198_ac4_close_unread_public_catalogues.sql` revoked
anon read on nine "unread public catalogues". Its header carries a per-table reader census, and for
this table it reads:

```
  table                    web(public)  cp(admin)  other apps  edge  worker
  ai_personas                       0          1           0     2       0
```

⇒ **It counted TWO edge-function readers and closed the table anyway.** The judgement was made on
the *web(public)* column; the `edge` column was recorded and not acted on. Those two edge readers are
exactly the consultant chat, and they run as **anon**.

🔑 **The migration then wrote down the failure mode in advance** — its standing caveat:

> *"no reader found is not no reader exists. These are invisible today regardless — the web app
> resolves the service-role-preferring shared client ([[T202]]) — so the real test arrives when T202
> lands. If something breaks then, the fix is a scoped policy for that consumer, never a restored
> blanket `true`."*

[[T202]] is **`done`**. The real test arrived. This is the thing that broke.

⚠️ **This is not a criticism of that closure** — it was measured, proven under
`BEGIN…ROLLBACK`, and it wrote its own risk down. The defect is that a **recorded** non-zero reader
count did not block the change, and nothing re-probed the affected consumers after [[T202]] removed
the service-role fallback that was masking them.

# T117 — RBAC review → advanced, unified roles/capabilities/offices/talent-tier schema

## Summary

Review the current roles/RBAC/abilities state and design a **more advanced, proper, clear schema**.
The naming taxonomy (Greek/Latin guild terms) is **explicitly NOT final** (owner will master it
separately) → **design structure first, names later**.

**Current state (reviewed 2026-07-22 — it's a deliberate 3-axis model from `2026-07-16-rbac-capability-model`/T102):**
- **Axis 1 · Rank** — `user_roles.role` CHECK, **12 values as of `20260708150000_client_engagement_portal.sql` (2026-07-08)**:
  `admin, member, anon, recruit, gladiator, legioner, ai-agent, ai-interviewer, ai-architect, ai-admin, editor, client`.
  ⚠️ **Corrected 2026-08-10.** This ticket was created quoting `admin/editor/viewer/agent/bot` — that is the
  **January** constraint from `20260124140000_harden_rbac_and_chats.sql`, superseded five times since
  (`add_gladiator_role` → `granular_agent_scopes` → `add_legioner_to_role_check` → `restore_ai_roles` →
  `client_engagement_portal`). **`viewer`, `agent` and `bot` have not been valid values since 2026-03-04.**
  Verified against the live DB, not the migration files.
  **Live data (11 rows):** `admin×2, ai-agent×2, recruit×2, member×2, ai-architect×1, ai-interviewer×1, client×1`.
  No `gladiator`, `legioner`, `editor` or `anon` rows exist.
- **Axis 2 · Capabilities** — `capabilities` table (not enum), `domain.action[.qualifier]` (21 seeded:
  `project.manage`, `quest.master`, `milestone.approve`, `job.slot.outstaff`, `pipeline.train`,
  `interview.conduct`, `invoice.manage`, `payout.approve`, `repo.manage`, `deploy.execute`, …).
- **Axis 3 · Offices** — `offices` table (+`office_capabilities`, `is_management`) = responsibility
  bundles: `project.manager`, `tech.lead`, `devops`, `accounting.principal` ("what you're responsible for").
- **Runtime** — CASL `packages/lib/src/auth/abilities.ts` `defineAbilityFor(activeRole)` + the hat
  model (`wom_active_role` / `wom_roles[]`).

**The core problem — a 4th, un-integrated axis + overload:**
- The **guild/talent taxonomy** (`recruit → gladiator → legioner → member`, manager tier) **is in the rank
  CHECK, and has been since 2026-03-04** — `recruit`, `gladiator`, `legioner` are live CHECK values and
  `recruit` has 2 rows. It is absent from **offices**, and it is *conceptually* misplaced: a
  **talent-progression / seniority tier** overloaded onto the identity axis. That overload is the real
  defect, not its absence.
  ⚠️ **Corrected 2026-08-10** — the original claim ("in **neither** the rank CHECK **nor** the offices")
  was false for the CHECK, and it made the Axis-1 migration look **additive when it is mostly subtractive**.
  It is also still documented in `docs/gamification/09-naming-lexicon.md` (PROVISIONAL) + [[T34]] flows.
- Owner's mapping (2026-07-22) resolves onto the axes: **"member = group of devs (legioner/gladiator)
  + trainees"** = the talent-tier axis; **"manager = PM/TPM/DevOps/Trainer/Accounting"** = **Offices**
  (Axis 3 — `project.manager`/`tech.lead`/`devops`/`accounting.principal` already seeded; add `tpm`/`trainer`).

## 🤖 Where the AI agents actually sit in RBAC — measured 2026-08-13 (owner question)

**Short answer: the `ai-*` roles are a designed identity layer that authorises nothing in practice,
and the real agents bypass it entirely.**

| fact | measured |
|---|---|
| `ai-*` values in the `user_roles` CHECK | **4** — `ai-agent` · `ai-interviewer` · `ai-architect` · `ai-admin` |
| `ai-admin` holders | 🔴 **zero** — a 5th dead CHECK value, and input to **AC5** |
| who holds the other three | 🔴 **4 accounts, ALL `<uuid>@test.com`** — test fixtures, not agent identities |
| their `user_active_role` (hat) | 🔴 **none of the four has one** |
| `abilities.ts` cases for `ai-*` | 🔴 **none** — they fall to `default` ⇒ **profile only** ([[T117]] 0.4) |
| RLS policies naming an `ai-*` role | **5** |
| how the real agents authenticate | 🔑 **`SERVICE_ROLE` in edge functions** (`agent-architect`, `analyze-interview`, …) ⇒ **RLS is bypassed, so none of those 5 policies is in their path** |

### The 5 policies split by mechanism, and the split is the point

- **2 by POSSESSION** — `profile_skills` *"Interviewer and Architect read all skills"* and
  `verified_credentials` *"…read all credentials"* use `EXISTS (… user_roles.role = ANY(…))`.
  **These work today** — for the four test fixtures, because possession needs no hat.
- **1 by HAT** — `profile_skills` *"Skills are viewable by owner, admins, and…"* uses
  `wom_acting_in(['ai-interviewer','ai-agent'])`. 🔴 **Inert: no ai-* account has a hat**, so that
  arm matches nobody.
- **2 inside scope expressions** — `blueprints` / `projects` *"Unified read access"*.

⇒ **The same possession-vs-hat split [[T198]] D2 found elsewhere, reproduced inside the AI surface:
the hat arm is decoration and the possession arm is what actually grants.**

### What this means for the model

🔑 **AI agents are not users, and the schema currently says they are.** They hold `user_roles` rows,
occupy 4 of the 12 CHECK values, and are referenced by 5 policies — while the code that actually
runs them authenticates as `service_role` and never consults any of it.

⇒ **This is [[T206]]'s territory, not `user_roles`'.** The owner's 2026-08-12 decision — `system.*`
as **per-service Postgres roles** — is exactly the right home for an agent identity: a machine actor
with its own grants, rather than a fake person with a fake hat. **`svc_interviewer` / `svc_architect`
express what `ai-interviewer` / `ai-architect` were reaching for**, and would make the 5 policies
enforceable instead of half-inert.

⚠️ **Do not delete the `ai-*` values as part of AC5's 12 → 6 without deciding this first.** Two
policies genuinely depend on them today; removing the values would silently drop
`profile_skills` and `verified_credentials` access for whatever holds those roles next.

## 🟢 OWNER DECISION 2026-09-12 — `project_roles`/`hats` (T311) is the primary PER-PROJECT axis; `offices`/`capabilities`/`resource_grants` stays company-wide

**Reconciling this ticket against itself first.** AC3/AC4 below (and the "Current state" at the top)
describe `resource_grants` as **not built**. It was — `20260828040000`, closing exactly the gap AC4
names, and this ticket's own **2026-08-28** status notes already say so (*"offices were drafted as
BUNDLES per project; the data names them as SEATS"*). The AC checkboxes were never flipped when that
landed. 🔴 **That is the drift this section fixes** — see the inline 🔎 annotations added to AC3/AC4.

**But "built" ≠ "adopted", and that gap is the real finding.** Measured 2026-09-12:

| axis | mechanism | live adoption |
|---|---|---|
| Offices/capabilities/`resource_grants` (this ticket's original Axis 3, [[T102]]) | company-wide responsibility bundles (`accounting.principal`, `talent.recruiting`, …) | **2** `resource_grants` rows, **0** RLS policies, **0** CASL cases read it |
| `project_roles`/`hats` (T311's axis, **absent from this ticket until today**) | per-project role (Tech Lead/PM/Developer/DevOps/QA/…) | **15** `project_roles` rows staffed across **2 of 7** projects ([[T313]], [[T314]], [[T319]], [[T352]]) |

⇒ **Owner decision: `project_roles`/`hats` becomes the axis AC3 must wire CASL/RLS to for
PER-PROJECT decisions.** `offices`/`capabilities`/`resource_grants` is **not deprecated or merged** —
it remains the mechanism for **company-wide, non-project-scoped** responsibility (the two live
`resource_grants` rows, `accounting.principal`-style offices). The two axes stay parallel; which one
a given decision belongs to is *"is this scoped to one project, or to the whole company"*, not a
migration from one to the other.

**Extended to clients — Phase 1 decided, Phase 2 deferred.** Client access is gated today by a
*separate* mechanism (`client_users`) that has never granted a `hats` row. Owner decision: client
access **mirrors the same `project_roles` catalog** used internally, in two phases:
- **Phase 1 (decided now):** a client org holds **PM/Tech Lead hats**, standing in for DevOps/QA
  visibility on the client's behalf. `client_users` profiles already satisfy the same
  `profiles.auth_user_id` shape staff hats use (2/2 rows confirmed live) — no new identity mechanism
  needed.
- **Phase 2 (deferred, not designed):** the client's own units/users hold **DevOps/QA hats directly**,
  scoped narrower than PM/TL. How to scope this is an open question, out of this ticket's cut.

**Client↔w0m linkage simplified — anchor on the project, not `client_users`.** `projects.client_id`
and `projects.contract_id` are **already direct FKs** (via the `proposal → contract → project`
lineage) but are read by **zero** RLS policies today — every client-scoped table
(`contracts`/`invoices`/`client_milestones`/`project_repos`) goes through `client_users` instead, and
`projects` itself has no client-facing RLS arm at all (`project_acl` exists but is empty/unreachable).
Target: RLS/CASL for PROJECT-scoped decisions reads `projects.client_id` + `hats.project_role_id`
directly; `client_users`' remaining job (org-level bookkeeping — which projects/contracts roll up to
one client org) is **not yet decided** — kept, narrowed, or retired is an open question, not a
decision made here.

## 🟢 OWNER DECISION 2026-08-11 — what a HAT is (settles the T200 step-3 blocker)

🔴 **Backfilled as a structured record 2026-09-13** — load-bearing per [[AgDR-0002]]'s criterion
(determines [[T198]] AC6 and makes [[T200]] AC4 a hard prerequisite; still current). See
[`AgDR-0014`](../../docs/decisions/AgDR-0014-hat-carries-permissions-scoped-many-per-project.md),
which also covers the two same-day follow-on decisions (EXCLUSIVE resolution; admin wears any
hat) and the same-day correction below.

> *"hat is the set of permissions for a person with assigned role via this hat … a user can have 2
> hats in same project — the client and also the qa force in project or even developer … so to
> separate views we can change available hats to change access and scope"*

Three claims, and each one has a schema consequence:

1. **A hat CARRIES permissions** — it is not a label on a session, it is the bundle you are acting
   through. ⇒ the hat resolves to an **office** (which bundles capabilities), not to a class.
2. **A user may hold SEVERAL hats in the SAME project** — client *and* QA *and* developer.
   ⇒ the hat is **scoped**, and a user↔scope pair is **one-to-many**.
3. **Switching hats changes access AND scope**, to separate views.
   ⇒ the hat is an **enforcement** input, not presentation. This answers [[T198]] AC6 directly.

### 🔴 The live schema cannot express any of the three

```
user_active_role   PRIMARY KEY (user_id)        ← ONE row per user, globally
                   columns: user_id, role, set_at
                            ^^^^ no scope column at all
                                   ^^^^ `role` text — a CLASS value, not an office
wom_acting_role()  select coalesce(auth.jwt() ->> 'wom_active_role', wom_highest_role(...))
                   ← one scalar, no scope, no capability
```

- **`PRIMARY KEY (user_id)` structurally forbids the second hat.** Two hats in one project needs
  two rows; the table permits one row in total.
- **`role text` is the wrong dimension.** The 12 legal values are classes (`admin`, `member`,
  `client`, …). An office (`project.manager`, `quality.owner`) is what bundles capabilities, and
  "QA force on this project" is an office-on-a-scope, not a class.
- **`wom_acting_is()` compares a scalar.** All 29 policies that read the hat ask *"is my one global
  hat X?"*. Under this definition the question becomes *"do I hold capability C on THIS ROW's
  scope?"* — which is `is_capable(capability, scope_type, scope_id)`, the function that does not
  exist.

### ⇒ What this decides, beyond the definition

- 🔑 **`is_capable()` moves from *desirable* to *prerequisite*.** Under the previous reading (the hat
  is which of my global roles I am wearing) `wom_acting_is()` was sufficient. Under this one it is
  not, because the answer now depends on the row. **The reader is no longer separable from the
  model.** That is [[T200]] AC4, and it is now load-bearing rather than a sequencing preference.
- 🔑 **[[T198]] AC6 is DETERMINED: the possession arm must go.** Possession is global; the entire
  purpose of a hat under this definition is *scoped separation of view*. A policy that ORs a
  possession arm beside a hat arm cannot implement it — the global answer always wins. This removes
  the last open question from AC6.
- ⚪ **D5 is half-answered.** The *shape* is settled — a client-side office is simply another office
  someone may hold on a scope, exactly like QA or developer, so the model needs no special case for
  clients. The *name* (`client.principal` rename, and what to call Cleo's office) is still open, and
  it is now a smaller decision than it was.
- ⚠️ **`resource_grants` IS this feature.** It was specced as user × office × scope, which is
  precisely "which hats may this person wear, and where". The active hat becomes a **selection among
  your grants**, not a global role string — so `user_active_role` becomes a pointer into
  `resource_grants` rather than a role column.

### 🟢 Resolved same day — the two follow-on decisions

> *"exclusive — one hat at a time, others inert"*
> *"admin can wear any hat from available on projects, even not assigned or fulfilled"*

**1. EXCLUSIVE.** `is_capable(cap, scope_type, scope_id)` resolves against **the one hat currently
worn**, not the union of the wearer's grants. A capability held through an unworn hat is genuinely
inert — the same answer a person without that grant would get.
⇒ **The active hat becomes an input to every capability check, not a display preference.**
⇒ Two consequences that are easy to miss:
   · **A user can lock themselves out of their own data by wearing the wrong hat**, and that is
     correct behaviour rather than a bug. The UI must make the worn hat unmissable, or the first
     support ticket will be "the CP is broken" from someone wearing `client` on their own project.
   · **Every capability check needs the scope of the ROW, not just of the session.** A session is
     "wearing `quality.owner` on project X"; a query touching project Y must resolve to *no*
     capability even though the session has one. This is why the scalar `wom_acting_is()` cannot be
     patched into shape — it has no row to ask about.

**2. ADMIN WEARS ANY HAT AVAILABLE ON A PROJECT — assigned or not, filled or not.** So:

```
wearable(user, scope) = grants(user, scope)                         everyone
                      ∪ offices_available_on(scope)                 IF the user is admin
```

🔴 **This makes the hat a control for everyone except admins, and that has to be written down where
the tenant boundary is claimed.** [[T198]] A2 is about cross-client isolation; once this lands the
honest statement is *"a client organisation is isolated from every other client, and from every
non-admin — admins may enter any client's scope deliberately, and it is audited."* An unqualified
"the tenant boundary holds" would be false.

## 🟢 OWNER DECISION 2026-08-12 — `system.*` is exercised by the SERVICE ROLE, the other realms are not

🔴 **Backfilled as a structured record 2026-09-13** — load-bearing per [[AgDR-0002]]'s criterion
(makes [[T202]] a prerequisite, resolved same day into [[T206]]; still current). See
[`AgDR-0015`](../../docs/decisions/AgDR-0015-system-realm-is-the-service-role.md).

> owner 2026-08-12: *"I think that `system.*` realm will work via service role while others not"*

**This maps the realm axis onto the ENFORCEMENT axis, and it is the right cut** — it separates
machine actors from human ones and matches how the estate already runs. It also **narrows an open
question**: if `system.*` never grants to a person, `resource_grants(user_id, …)` only ever holds
`w0m.*` and `client.*` rows, so **`scope_type` needs no `system` value** — one fewer value in a CHECK
constraint that becomes a migration-on-live-data later.

🔴 **But it changes what an office IS, and the consequence has to be stated.** Measured live
2026-08-12 — `pg_roles` holds exactly **one** `service_role`, `bypassrls=true`, and **no per-service
roles exist** (the only other non-builtin logins are `postgres`, `authenticator`, `cli_login_postgres`
and Supabase's own admins):

| realm | actor | an office is… | enforced by |
|---|---|---|---|
| `w0m.*` / `client.*` | a person, through RLS | a **constraint** | a policy reading the grant |
| `system.*` | the service role | a **label** | 🔴 **nothing — `bypassrls=true` means no policy applies** |

⇒ **All `system.*` offices collapse into one identity at runtime.** `system.crawler` and
`system.billing` would be the same principal, because **49 of 55 edge functions share the one service
key** (measured 2026-08-12), and RLS never runs for any of them. An office there can *name*
responsibility; it cannot *constrain* it.

🔴 **And the identity is wider than "backend jobs" today.** [[T202]]: the shared Supabase client
**prefers** the service-role key and **42 files import it, 25 of them `.astro` pages**. So under this
definition **25 SSR page renders are currently running as `system.*`** — which is precisely the
default T202 exists to remove. ⇒ **Adopting this decision makes T202 a prerequisite for it**, not a
parallel ticket: the realm is only meaningful once the service role is reached deliberately.

**Three ways to give `system.*` real enforcement, in descending strength:**
1. **Per-service Postgres roles** (`svc_crawler`, `svc_poller`, …) **without `bypassrls`**, with
   explicit grants. RLS then applies and `system.*` offices are enforceable exactly like the others.
   Cost: each function needs its own connection identity instead of the shared key.
2. **Keep one service role, gate inside the function.** Weakest — it is self-policing, and **2
   functions have no gate at all** (`cv-pdf`, `log-event`; the latter is `verify_jwt=false` **and**
   service-key **and** ungated).
3. **Do not model `system.*` as offices at all.** Machine capability is a different kind of thing
   from a grant to a person, and a table whose join is `user_id` is the wrong home for it.

🟢 **RESOLVED SAME DAY — the owner chose (1), per-service Postgres roles.** Filed as **[[T206]]**,
which carries the measurement that decides its cost: **53 of 55 functions reach the DB through
PostgREST**, where a per-service role is nearly free — *except* that minting a `role: svc_x` JWT needs
a secret this estate does not hold. **`SUPABASE_JWT_SECRET`/`JWT_SECRET` are absent from infisical,
and the keys are the NEW opaque format** (`sb_publishable_…` / `sb_secret_…`), not re-signable legacy
JWTs. ⇒ **T206 AC1 is an owner dashboard check**, and it is the difference between swapping one secret
per function and rewriting the DB access of 53 of them. ⚠️ `signToken` in
`packages/lib/src/auth/crypto.ts` is **not** a way in — it is a two-part `payload.HMAC` SSO token with
no header segment and cannot drive PostgREST role switching.

## 2026-08-28 — offices were drafted as BUNDLES per project; the data names them as SEATS

Owner, recalling the original intent (and saying *"as I guess"* — this is reconstruction, not a
ruling): *"that moment offices were drafted as features/capabilities assigned to units per project
and since then we have RBAC in redesign"*, and `design.*` was *"a permissive action draft separation
for managing Design System by dedicated person or PM or Client."*

**The mechanism built today already expresses that intent.** `resource_grants` takes
`subject_kind ∈ {profile, unit}`, an office **or** a bare capability, and
`scope_type ∈ {global, project}` — which is *"capabilities assigned to units per project"* almost
word for word. Nothing needs redesigning to support it.

🔴 **The drift is in the naming, and it runs the other way.** The `offices` table carries a `title`
and an `is_management` flag:

| office | title | is_management |
|---|---|---|
| `design.lead` | Design Lead | false |
| `project.manager` | Project Manager | true |
| `client.principal` | Client Principal | true |

Those are **seats a person occupies**, not bundles a unit is granted on a project. So the data models
one thing and the intent describes another, which is why *"who may manage the Design System here"*
has no natural expression: the nearest thing is `design.lead`, and granting it says *"this person is
the Design Lead"* rather than *"this person manages the DS on this project"* — and it silently
confers `blueprint.publish` too.

⇒ **A rule falls out of this, and the model already supports it:**

- **Grant a CAPABILITY** for a scoped responsibility — `design.manage` on project X. Precise, says
  nothing about anyone's title, and confers exactly one thing.
- **Grant an OFFICE** only where a real seat exists and the whole bundle is meant.
- `resource_grants` enforces `num_nonnulls(office, capability) = 1`, so the choice is explicit per
  grant rather than implied.

⇒ **`design.lead` may be the wrong name for what is wanted**, and possibly the wrong shape: if a
designer, a PM *or* a client can manage the DS on a project, then the thing being granted is the
capability, and the office adds a title nobody meant to assert. That is this ticket's call, not one
to settle in passing.

🔑 **A client CAN hold a capability, and it is tenancy-safe.** Measured: both `client_users` rows
have a matching `profiles` row, so `is_capable(cap, scope_id, profile_id)` resolves for a client
today. A grant scoped `project` carries `scope_id`, so it cannot answer for another client's project
— the isolation stage-3 needs is structural rather than conventional. **Whether a client SHOULD hold
`design.manage` is a product decision**; the model neither forces nor forbids it.

⚠️ And the [[T102]] note applies here: the catalog gained its first consumer today, so renaming a
capability now migrates grants rather than seed rows. The redesign this ticket is doing is no longer
free.

# T155 — Upwork corpus is thin, not synced

## Summary

[[T89]] restored the Upwork platform-sync sub-layer and closed `done` on **"Live: 50 rooms / 129
messages, idempotent across 2 runs."** Measured against the live DB on **2026-07-31**, those are
still the exact numbers — and they are not a healthy sync, they are a **5% sample**. The pipeline
works; what it captured is a sliver. This ticket executes T89's carried follow-ups and the data
quality defects found alongside them.

Found while trying to answer a concrete question — *"which of my past projects used WebRTC?"* — and
discovering the corpus physically cannot answer it. That is the practical framing: the Upwork data
is currently an **index**, not a **record**. It can tell you a contract existed; it cannot tell you
what you built.

**Measured live (`psql`, 2026-07-31):**

| table | rows | reality |
|---|---|---|
| `contracts` | 189 | **~94 real** — 89 duplicate groups spanning 184 of 189 rows |
| `proposals` | 539 | title + status only; **no cover-letter body** |
| `platform_messages` | 129 | in **10 of 50** rooms — 40 rooms hold nothing |
| `platform_rooms` | 50 | 12 → contract, 24 → proposal, **14 → neither** |

1. **Messages cover 2026-02-05 → 2026-06-02 only.** Four months, against a contract history
   starting **2012**. T89 recorded the cause as a carried follow-up — *"`listRooms` capped at the
   first 50 rooms"* — so this is known, unexecuted, and the reason the historical record is absent.
   Bodies where they exist are substantive (avg 463 chars, max 4,786), so the backfill is worth it.
2. **Contracts are doubled.** 189 rows / 188 distinct `external_id` / **94 distinct
   `title+client`** — each contract appears twice, once "rich" (11–12 payload keys) and once "thin"
   (5 keys). Two sync generations, never reconciled. Any count over this table is ~2× wrong.
3. **The payloads carry no content.** Every contract has exactly `title, client, start_date,
   end_date, status`; **one** row in 189 has `scope`. Proposals are 250–500 bytes:
   `title, status, jobId, tags, client_country`. The cover letter — the one place a project's tech
   stack is described in the author's own words — is **never fetched**.
4. **`tags` disagrees with `status`:** **236 of 267** proposals with `status: Accepted` are tagged
   `declined`; 90 of 103 `Activated` likewise. Anything filtering on tags is silently wrong.
5. **A three-year hole:** zero contracts with a 2021, 2022 or 2023 start date (2020 → 22, then
   nothing until 2024 → 10). May be genuine off-platform work — but it is unexplained, and the
   sync cannot currently distinguish "no work" from "not fetched".

🔴 **The organising defect is the one this estate keeps finding: a gate that reports success over a
sample it never sized.** T89's verification was *idempotency* (same result twice) — which a 5%
sample passes perfectly. Nothing asserted coverage, so "50 rooms / 129 messages" read as completion.
Same shape as [[T135]], [[T149]]'s five instances, and [[T128]]'s vendoring sweep.

      solved — pagination nests *inside* the filter). Observable: room count after a full run is
      recorded and exceeds 50, and a re-run is still idempotent. ⚠️ **A run that returns exactly 50
      again is a FAILING result, not a stable one.**
- [x] **AC2 — message history is backfilled to the start of the corpus.** Observable:
      `min(sent_at)` moves from **2026-02-05** to a date consistent with the earliest room, and the
      count of rooms holding ≥1 message rises from **10 of 50**. Record both before/after figures.
- [x] **AC3 — proposal cover letters are fetched and stored.** Observable: proposals gain a body
      field populated for a stated majority of the 539, and a full-text search for a technology
      (`webrtc`) returns matches from cover-letter text, not just from job titles. This is the AC
      that makes the corpus answer questions about what was actually built.
- [x] **AC4 — contracts are deduped, with the merge rule recorded.** Observable: `count(*)` ≈
      `count(DISTINCT title||client)` (~94), the surviving row is the **richer** payload (11–12

      duplicate must be written down — `external_id` does **not** identify them (188 distinct).
- [x] **AC5 — orphaned rooms are resolved.** The **14** rooms linked to neither a contract nor a
      proposal are either wired to their parent or explained. Ties [[T89]]'s open
      `projects.contract_id` 0/9 follow-up.
- [x] **AC6 — `tags` is fixed or retired.** Either it agrees with `status`, or it is dropped and
      every consumer moved to `status`. A field that says `declined` on 236 accepted proposals is

- [x] **AC7 — a sync-health check gates coverage, and is proven RED first.** A standing check in
      `project/scripts/w0m_audit.py` (or the poller's own verification) that fails when message
      coverage, room count, or contract-duplication cross a declared threshold. ⚠️ **It must be
      demonstrated failing against today's state** — a coverage check written after the backfill
      that has only ever seen green is exactly the vacuity this ticket exists to close.
- [x] **AC8 — the 2021–2023 gap is explained, in writing.** Either the backfill fills it, or the
      ticket records that those years were genuinely off-platform. An unexplained hole in a
      career-spanning dataset is a claim about history, not just a data gap.

### Landed 2026-07-31 — the stamp model (schema + pure logic, nothing deployed)

  permanent skip. `RequestBudget` yields to the API's `remaining` when lower but **never lets the
  remote raise our cap**, and a 429 halts the run while keeping the reset for the next one.

### 2026-07-31 — schema reworked after review; dedupe verified read-only; full estimate

**The review found three flaws in my own first cut. All three are fixed in the UNAPPLIED
migration rather than layered on top of it** (verified unapplied: `supabase_migrations` has no
`20260731%` row, so revising in place is correct and leaves no correction-of-a-correction).

1. 🔴 **The stamp was keyed on the wrong identity.** `platform_sync_state` keyed
   `(source, entity_type, external_id)` — but **188 contract rows are 95 real contracts**, each
   duplicate carrying its OWN external_id. That mints 188 stamps for 95 contracts and fetches
   every detail twice, forever. Now keyed on `identity_key`.
2. 🔴 **`local_count >= remote_count` was unsatisfiable, i.e. an infinite loop.**
   `stories.totalCount` counts system stories; `upwork-poller/index.ts:682` drops any story with
   no body AND no timestamp. Affected rooms stay permanently short → re-fetched every run →
   the whole budget spent on work that can never finish. **Completion is now pagination reaching
   the end**, and the count is a report. New messages are detected by the remote count MOVING
   between censuses (remote vs remote), which sidesteps the mismatch entirely — `roomFingerprint`.
3. 🔴 **A separate message census is mostly waste**: `roomStories` returns `totalCount` in the
   SAME query as the first page of edges, so for any room we intend to fetch the census is free.
   For a room with ≤50 new messages, census-then-fetch is 2 requests where fetch-alone is 1.
   ⇒ The Room-metadata introspection question is far less important than I claimed.

Also added: `sort_key` (oldest-first, the owner's chosen order), `pagination_done`, a `dead` state
so poison-pill items stop consuming budget, and `lease_owner`/`lease_until` — the hourly limit is a
SHARED resource and a per-invocation cap is a local variable, which cron plus the CP refresh button
(debt D9) can double-spend.

**AC4 dedupe — written and DRY-RUN read-only against live, not yet applied.**
`20260731210500_t155_dedupe_upwork_contracts.sql`. Simulation output: **95 survivors (93 rich,
2 thin) · 93 deletions · 15 FK rows repointed** (10 `platform_rooms`, 5 `proposals`) — those 15
links would have been orphaned without the repoint step. All six referencing tables were
enumerated from `information_schema`, not guessed. Runs in one transaction and RAISES if the
one-row-per-identity invariant does not hold, because a half-run dedupe is worse than a refused one.

🔴 **The merge key is `split_part(external_id,'_',1)`, NOT title+client — and this ticket's
original arithmetic used the wrong one.** Contracts `13076734` and `13122665` share both a title

right for the wrong reason.

**Mechanism, from `upwork-poller/index.ts:330-395`:** proposals are fetched via a single
unpaginated `vendorProposals` query (`first: 50`, no cursor loop, unlike contracts' `offset`/
`hasMore` loop to 1000), gated to run **only for the first Upwork context whose contracts query
returns rows**, then `break`s out of the context loop entirely. Both the contracts fetch and the
proposals fetch for that context share **one `try/catch`** (~:374-376) that logs a single generic
`context_error` — it does not record which sub-step failed. `contracts` is assigned before the
proposals fetch runs, so a thrown error specifically inside the proposals `client.graphql(...)`
call leaves contracts upserting normally that cycle while proposals silently stay untouched, and
the overall run still logs `SYNC_UPWORK_SUCCESS`. Not yet confirmed against Supabase's own
edge-function logs (unchecked this pass) — this is the code-level mechanism that fits the data,
not yet a caught stack trace.

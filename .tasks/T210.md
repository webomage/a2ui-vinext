# T210 — detach the person from the account

## Summary

Owner ask, 2026-08-14: *"let's detach user profiles from user auth, just because we do not want to
recreate profile if a candidate upgrades up to member."*

🔴 **`profiles.id` IS `auth.users.id`** — a shared-primary-key pattern:

```
profiles_pkey:     PRIMARY KEY (id)
profiles_id_fkey:  FOREIGN KEY (id) REFERENCES auth.users(id) ON DELETE CASCADE
```

Measured 2026-08-14: `auth.users` = 20, `profiles` = 20, exactly 1:1. **A person cannot exist
without an account.** So a candidate who applies has no profile — only a `job_applications` row —
and when they later sign up, everything known about them has nowhere to attach.

⚠️ **The model already contradicts itself.** `profile_snapshots.user_id` and
`job_applications.user_id` are both **NULLABLE** — two tables already model accountless people
while the profile record itself cannot. This ticket makes the model consistent rather than adding
a new idea.

## 📍 The migration surface is far smaller than it looks — measured, not assumed

| check | measured |
|---|---|
| policies whose expression references `profiles` | **0** |
| FKs pointing at `profiles.id` | **5** — `candidate_submissions`, `job_applications.assigned_to`, `profile_skills`, `skill_assessments`, `verified_credentials` |
| policies on `profiles` itself | **3**, of which **only 1** uses the shared key: `Users can view their own profile → (id = auth.uid())`. The other two go through `user_roles` |
| code sites assuming `profiles.id == auth uid` | **1** |
| rows to backfill | **20** |

🔑 **Because `profiles.id` does NOT move, all five inbound FKs survive untouched.** The change is
one added column, one backfilled value, one rewritten policy and one code site.
*(An earlier read of this warned of a broad RLS migration. That was wrong and is retracted.)*

## 🔒 Visibility baseline — measured 2026-08-14, BEFORE the change

Owner: *"LI profiles should not be public in this case yet."* They are not, and this is the number
the change must preserve:

| table | owner sees | **anon sees** |
|---|---|---|
| `profiles` | 20 | **0** |
| `profile_snapshots` | 1 | **0** |
| `job_applications` | 2 | **0** |
| `profile_skills` · `linkedin_profiles` | 0 | 0 |
| `team_members` | 2 | **2** — public **by design** (the team page) |

⚠️ **anon HAS a `SELECT` grant on all of them; RLS is what closes it.** The grant is not the
control — a policy change alone can open every one of these without touching a single grant.

🔴 **This is exactly why AC2 is a per-role probe and not a code review.** Today every row has an
owner, so `id = auth.uid()` returns nothing for anon *incidentally*. After detachment, rows exist
with **`auth_user_id IS NULL` and no owner at all** — a careless rewrite makes them match everyone
or no one. **The acceptance number is: anon still reads 0 from `profiles` and `profile_snapshots`
after the change, with accountless rows present.**

## Owner decisions

1. **Detach** — a person is representable without an account.
2. **Merge key on upgrade: email first, then provider identity, with a conflict state.** Neither
   alone is sufficient: a form applicant has no provider, and a person may sign up with a different
   address than they applied with. ⚠️ **`profiles.email` is NOT unique today** — the only unique
   constraint on the table is `telegram_chat_id`.

## Definition of Done

A person exists in this system without an account, keeps the SAME `profiles.id` when they later
sign up, and is invisible to every non-admin until they do — each proven by a probe that reads a row
back **as the actor** rather than by inspecting a policy (`just profile-detach-probe`,
`just profile-claim-probe`). Email is unique case-insensitively, and two people are never silently
merged: a mismatch between email and provider identity lands in `profile_claim_conflicts` for a
human. Nothing this ticket removed leaves another ticket recorded as blocked on it.

🔴 **That last clause is not bookkeeping.** T210 dropped the constraint [[T194]] AC5 was waiting on,
and `TECH-DEBT` D1 went on asserting the block for twelve days — describing a `user_id` column that
no longer exists. A removed blocker that nobody un-records becomes an instruction not to try, which
is the [[T67]] shape and now the second time it has cost this estate. Closing this ticket means the
registers that pointed at its constraints are corrected too.

⚠️ **Deferral is allowed; silent deferral is not.** AC4's provider fallback is deliberately not
built, and its stated reasons must be RE-MEASURED rather than inherited — one of the three ("
`social_integrations` is account-bound") was already false when it was checked.

## 2026-08-28 — AC4/AC6b: `linkedin_sub` is not empty-and-waiting, it is UNSAFE

Both open ACs read `job_applications.linkedin_sub` as **0 of 6 and therefore unfinished** — AC6b says
in as many words *"nothing writes one … the provider identity the fallback needs is still absent."*
Measured end to end, both readings are wrong in the same direction.

**A writer exists, and has all along.** `apply-submit/index.ts:232` inserts
`linkedin_sub: linkedinSub`. The value is empty because of where it comes from, not because nobody
wrote the code:

| step | where | what happens |
|---|---|---|
| 1 | `linkedin-callback.ts` | sets `li_access_token` as an **HttpOnly** cookie on the site origin |
| 2 | `/api/auth/linkedin-prefill` | reads the cookie **server-side**, calls LinkedIn `/v2/userinfo`, returns `{ sub, … }` |
| 3 | `ApplicationForm.svelte:45,97` | puts `profile.sub` in client state and posts it back as a form field |
| 4 | `apply-submit/index.ts:105` | `formData.get("linkedin_sub")` |

⇒ **Server-derived at step 2, laundered through the browser by step 3.** Anyone posting the form
directly supplies whatever they like.

🔴 **That is the exact hazard Phase 3 already refused.**
`20260814190000_t210_phase3_claim_path.sql` rejected `raw_user_meta_data->>'sub'` because *"matching
on it would let anyone claim a stranger's profile by naming their provider id — a privilege transfer
driven by client input, which the requirement's security note forbids in as many words."* The same
sentence applies to `linkedin_sub`, and it went unnoticed because **an empty column looks like an
unfinished feature rather than an unsafe one.** AC4 lists it beside `provider_urn` as though the two
were equivalent; they are not.

⇒ **Populating it would make the fallback less safe, not more.** AC6b's remedy — get something to
write it — is the wrong direction as stated.

**And it cannot be fixed in the writer.** `ApplicationForm` posts **cross-origin** to
`${PUBLIC_SUPABASE_URL}/functions/v1/apply-submit`, and that function reads no cookies: the HttpOnly
cookie belongs to the site origin and never reaches it. Server-side derivation at the point of
insert needs the submission routed through a same-origin route first — a change to a live public
form, deliberately not made here.

**What IS trustworthy:** `social_integrations.provider_urn`. `linkedin-oauth/index.ts:85-86` builds
`urn:li:person:${profileData.sub}` from a server-side userinfo call and never exposes it to the
browser; it is populated in **1 of 1** rows. ⇒ **The provider fallback should match on
`provider_urn` and only on `provider_urn`.**

⇒ `20260828020000_t210_linkedin_sub_is_not_an_identity.sql` — a column comment, no data or behaviour
change, recording the property where a query author will meet it so the next person writing a claim
path does not reach for the convenient column. Dry-run on production, rolled back.

### What this changes about the two ACs

- **AC4** — the fallback is not blocked on `linkedin_sub` being populated; it is blocked on
  `provider_urn` coverage (1 row) and on the `auth.identities` timing Phase 3 measured (empty at
  trigger time). `linkedin_sub` should be **struck from the AC's list of provider identities**
  rather than waited on.
- **AC6b** — *"nothing writes one"* is inaccurate; the writer exists and the value is untrustworthy
  by construction. The AC's real content — carry `social_integrations` across to the person, and
  encrypt before the re-point per D1 — stands unchanged and is unaffected by this finding.

⚠️ Neither AC is ticked. This removes a wrong premise from both and closes a hazard; it does not
build the fallback.

# T238 — there is no local stage because the schema cannot be rebuilt

## Summary

Owner 2026-08-19: *"create also an altered copy for a `local` stage used for testing and local
development"* — and, crucially, *"I remembered why we stopped doing live env testing — hit free
limits on Supabase."*

That is the real history behind [[T237]]: the spec corpus did not rot from neglect. **Running it
consumed a hosted quota**, so it was rationed until it stopped. A local stage is the fix. It does
not currently exist, and building it hits a wall that is bigger than testing.

🔴 **`supabase start` fails on migration 1 of 226.**

```
Applying migration 20251215183000_fix_rls_policies.sql...
ERROR: relation "public.cache_file" does not exist (SQLSTATE 42P01)
```

Measured 2026-08-19:

| | |
|---|---|
| migrations in the chain | **226** |
| the one that fails | **the first**, `20251215183000_fix_rls_policies.sql` |
| any migration that CREATEs `cache_file` | **none** |
| `cache_file` in the LIVE database | **no** — `to_regclass` returns null; dropped by `20260725170000_t99_drop_orphan_identity_subsystem.sql` |

⇒ **The chain has never been replayable from an empty database.** The hosted project was built
incrementally — partly by drizzle, partly by hand — and the migrations record the *changes* without
the *starting schema*. Nothing detects this, because nothing has ever replayed them: every
environment is the one live database ([[infisical-dev-env-is-live-db]]).

📌 **This is why local development does not work, and it explains the shape of everything around it**
— [[T237]]'s dead corpus, `--env=dev` being the only env, and 23 spec steps degraded into
`// Basic check passed`.

## Acceptance criteria

      something that exists. 🔑 [[T229]] already proved the dump restores, so the mechanism is in
      hand — but note its two recorded gaps: a dump carries **neither the `postgres` role nor
      pgvector**, and vector tables do not restore at all.
- [x] AC2 — ✅ **DONE 2026-08-19 — `just db-local-up`.** `supabase start` reaches a healthy stack, and `supabase status` prints keys. Only
      then can `env/local/default.properties` lose its `FILL_FROM_SUPABASE_STATUS` placeholders —
      which are deliberate: shipping remembered keys is how a config comes to describe a machine
      nobody checked.
- [x] AC3 — ✅ **DONE 2026-08-19 — `just db-baseline-verify`, red-proven three ways.** The defect survived 226 migrations
      because *nothing ever tried*. Without this, AC1 fixes today's break and the next
      un-replayable migration lands unnoticed. ⚠️ Must run from EMPTY — replaying onto an existing
      database proves nothing, which is precisely how this stayed invisible.
- [x] AC4 — ✅ **DONE 2026-08-19 — `just e2e-local`.** Points the spec corpus at `local` ([[T237]] AC7), so a full run costs no quota and
      cannot mutate production.
- [x] AC5 — ✅ **DONE 2026-08-19 — seeded from an EXISTING backup (`just db-local-seed`), owner's call.** An empty schema runs the corpus but most scenarios
      need rows. Fixtures, an anonymised subset, or `supabase db dump --data-only` — state which,
      because "it works on my machine" is the failure mode of an unstated seed.

## Evidence — 2026-08-19

**AC1 — the schema DOES rebuild from nothing; the migration chain simply never could.**
`scripts/db_baseline.py --generate` dumps live read-only (credentials via environment, never argv)
to `wom7api/supabase/baseline/schema.sql` — **273 KB, 114 tables**, `public` + `gamification`.

🔑 **One prerequisite, and it is not incidental.** Applying the raw dump to an empty database gives
**113 of 114**: `public.documents` fails with `type extensions.vector does not exist`, and 8 further
errors are indexes and policies queued behind that single table. Creating the `extensions` schema
and pgvector FIRST gives **114 of 114 with one benign `schema "public" already exists`**. That is
[[T229]]'s recorded finding — *a dump does not carry pgvector* — reproduced exactly, and it is why
the prerequisite is a header in the baseline rather than a note in a doc.

**AC3 — `just db-baseline-verify` replays into a THROWAWAY container and red-proven three ways:**

| mutation | result |
|---|---|
| clean baseline | **exit 0** — 114/114, 0 errors ✅ |
| pgvector prerequisite removed | **113/114, 10 errors → exit 1** ✅ (independently re-confirms the claim above) |
| baseline truncated to half | **exit 1** ✅ |
| baseline absent | **exit 2 — unknown, not clean** ✅ |

🔴 **Registered `tier: live`, not offline, deliberately.** It needs a container runtime, and
`run_suites` treats any non-zero as FAIL — so an offline registration would turn `just test` red on
every machine without Docker, the permanently-red gate [[T135]] AC8 forbids.

🔬 **Resolved an "unexplained flake" that was never a flake.** `decisions` / `decisions-index-fresh`
failed in one `just test` run and passed standalone, and I recorded that as unexplained. The logs
say plainly: `docs/DECISIONS.md is STALE`. It goes stale whenever tickets change — and I had been
adding T236/T237/T238 between runs, regenerating the index in between without noticing. **The gate
was correct every time; the observer was the variable.** `just test` is green again.

⚠️ **AC2 is NOT done and must not be rushed — a hazard found while planning it.** Making
`supabase start` work means the CLI must see the baseline instead of the 226 migrations. But
Supabase tracks applied migrations by NAME in `supabase_migrations.schema_migrations`, and the
baseline's name is in no such row on the hosted project. ⇒ **a later `supabase db push` would try to
apply the baseline TO PRODUCTION.** Any restructuring needs `migration repair --status applied`
against the live project first, which is a change to production bookkeeping and wants an explicit
decision, not a convenient assumption.

**AC2 — the local stack runs.** `[db.migrations] enabled = false` in `config.toml` stops the CLI
replaying the unreplayable chain; `supabase/baseline/schema.sql` is applied explicitly by
`just db-local-up`. **114 tables, REST answering 200**, full teardown→rebuild proven
(`db-local-down` discards the volume — a local stage that silently keeps yesterday's rows is how
"works on my machine" starts).

🔑 **The baseline is kept OUT of `supabase/migrations/` deliberately** — that is what dissolves the
hazard recorded above. Supabase tracks applied migrations by NAME, so a baseline living in that
directory would make a later `supabase db push` try to apply it TO PRODUCTION. Applied explicitly,
`db push` can never see it.

📌 **Vindication of the placeholders:** the real local publishable key is
`…ACJWlzQHlZjBrEguHvfOxg…`. The value I had written from memory was `…ACJWlzQHlZctSuqXKRvokQ…` —
**wrong**. `env/local/default.properties` is now filled from a running stack.

**AC5 — seeded from an existing backup, and the owner's instinct beat my alternative.** Pulling
fresh rows from the hosted project would spend the very quota whose exhaustion stopped live testing.
The dumps already sit on this machine, so this costs nothing and exposes nothing new *here*.

**Result: 0 errors · 70 tables with rows · 23,556 rows · every table's count matches the backup
exactly.**

Three things had to be right, each measured:
- **Data-only, not a whole-dump restore.** Restoring the 27 MB dump whole gives **579 errors**
  (92 grant-option, 54 default-privilege, 91 across auth/storage/realtime). Rows still land, but
  nobody reads a 579-error restore and real failures hide in it. ⇒ schema from the committed
  baseline, rows from the dump.
- **FK enforcement deferred** (`session_replication_role = replica`) — a data-only dump is emitted
  in schema order, not dependency order.
- **`auth.users` + `auth.identities` on an ALLOWLIST**, not the whole `auth` schema. Taking
  `auth.*` pulled gotrue's internals: `webauthn_credentials` / `custom_oauth_providers` do not exist
  in the local image, and `auth.schema_migrations` is gotrue's own bookkeeping.
  ⚠️ **Real user PII, acceptable only because the dump already lives on this machine.** That
  argument does NOT survive local dev spreading to another machine — anonymise first.

🔴 **`--url` refuses anything but loopback** (red-proven against the production host: exit 2). A
seeding tool that can be pointed at production is a data-loss incident with a convenient interface.

🔬 **A false alarm I raised and then disproved — worth recording because I nearly filed it.**
Mid-work I concluded *"the backup is corrupt: 0 of 8,556 `aggregated_jobs` rows restore"*, and had
apparent confirmation from loading the block into a scratch table. **The backup is fine, byte for
byte: 7,375 rows, every one with 19 fields.** The defect was my reader — Python's `str.splitlines()`
also breaks on `\v`, `\f`, `\x1c-\x1e`, `\x85`, **U+2028** and **U+2029**, none of which psql
treats as a row terminator. Job descriptions contain U+2028, so it tore 1,245 rows in half — and my
"confirmation" used the same extractor, so it confirmed my bug rather than the dump. ⇒ **Two
measurements sharing a defect agree with each other, not with reality.** The reader now splits on
`\n` only.

**AC4 — `just e2e-local` runs the corpus against the local stack.** First real run:
`specs/web/navigation_main.spec` → **1 spec, 4 scenarios, 4 passed**, reports in `reports/local/`.
Scope a run by passing specs; bare `just e2e-local` runs all 190.

⚠️ **What it isolates, stated rather than implied.** The DATABASE is local, so the corpus's
`Create`/`Delete`/`Edit` steps never reach the hosted project. **Third-party integrations are NOT
isolated** — the app still boots with the estate's secrets, so anything reaching LinkedIn, PostHog
or Honeycomb reaches the real service. Isolating those is separate work; claiming otherwise would be
the more dangerous half-truth.

🔴 **Found on the first run — a latent data-loss risk that makes this ticket bigger than testing.**
`tests/support/hooks.ts` runs an **automated DB purge in teardown**, and it is pattern-matched
`DELETE`, not a scoped cleanup:

```
supabase.from("contact_messages").delete().ilike("email", "%test%")
supabase.from("job_applications").delete().ilike("email", "%test%")
supabase.from("posts").delete().ilike("title", "%Test Post%")
supabase.from("projects").delete().ilike("name", "%Test Project%")
```

It deletes from **whatever database is configured**. `just e2e` points at `--env=beta` — the live
database — so a full run there would delete **production** rows: a genuine enquiry from
`someone@testcompany.com` matches `%test%`. ⇒ The corpus was not merely quota-expensive to run
against production, it was **destructive**, and nothing said so. 📌 This is the strongest argument
yet for [[T237]] AC7: the corpus should be *incapable* of running anywhere but `local`.

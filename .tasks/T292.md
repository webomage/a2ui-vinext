# T292 — drive the other forges

## Summary

Owner, 2026-08-26: *"we should also support gitlab, bitbucket and maybe something more"* ·
*"set github full scope now and create P2 ticket for integrating other later"*.

**Half of that shipped under [[T287]] and it is worth being precise about which half.**

| | today |
|---|---|
| **RECORD** a repo on any forge | ✅ works — `project_repos.provider` is an open set, `link` stores owner/name/url for any host |
| **DRIVE** a forge (create, set-visibility) | ❌ GitHub only |

`github-repos` holds `DRIVEABLE = new Set(["github"])`. Anything outside it is recorded
**unverified** and says so in the response (`verified: false`); `create` and `set-visibility` refuse
with a message naming the forge and what to do instead.

🔑 **The split exists because recording and integrating are different costs.** Recording needs no
provider code at all. Driving one needs a client, a token, and its own auth and object model —
GitLab uses groups and numeric project ids where GitHub uses `owner/name` paths; Bitbucket uses
workspaces; a self-hosted forge has no single API host at all.

## Acceptance criteria

- [x] **AC1 — a provider CLIENT interface, not four branches in one handler.** `create`, `verify`
      and `setVisibility` per forge, with GitHub as the first implementation extracted from what is
      there now. ⚠️ Do the extraction BEFORE adding the second forge, or the second one gets written
      around the first one's shape.
- [x] **AC2 — credentials per forge, and the absence of one is UNMEASURABLE, not broken.** A missing
      GitLab token must make GitLab actions unavailable with a clear message — never make GitHub
      fail, and never read as "the repo does not exist" ([[T242]]).
- [x] **AC3 — self-hosted needs a base URL per repo.** There is no `api.gitea.com`. Decide whether
      that lives on the repo row or in config, and say why. 🔴 A base URL supplied per-call is an
      SSRF surface — whatever holds it must be trusted input, not caller input.
- [x] **AC4 — the org guard generalises.** GitHub's is `owner === "webomage"`. GitLab's equivalent
      is a group, Bitbucket's a workspace. Do not silently drop the check when generalising it —
      it is what stops a stranger's repo being linked to a client's project.
- [x] **AC5 — `providerOf()` gets unit tests.** It is a pure host→forge decision and it is
      **currently untested**: it lives inside `index.ts`, which cannot be imported without starting
      a server. Extract it the way `chat-handoff.ts` was, and test the cases that matter —
      `github.com`, a GitHub Enterprise host, `gitlab.com`, `bitbucket.org`, a self-hosted host, and
      a malformed URL.
- [x] **AC6 — blueprints stay single-repo and GitHub-named, or are migrated deliberately.**
      `blueprints.github_repo_url` is one GitHub-named column, so `link` currently REFUSES a
      non-GitHub URL for a blueprint. That is honest today; if blueprints should span forges it is
      the same migration T287 did for projects, and it should be a decision rather than a drift.

## Definition of Done

An internal user can create and set visibility on a repo on more than one forge, through a provider
interface rather than a chain of branches — and a forge with no credentials configured reports
UNAVAILABLE rather than failing as though the repo were missing. The pure host→forge decision is
extracted and unit-tested, which it is not today. Recording an unverified repo keeps working
unchanged, because that is the behaviour most repos will actually use.

🔴 **Not done if the org guard is lost in the generalisation.** `owner === "webomage"` is what stops
a stranger's repository being attached to a client's project; a per-forge equivalent must exist
before that check is refactored away.

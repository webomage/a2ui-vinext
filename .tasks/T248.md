# T248 — `just db-migrate` is a silent no-op that reports success

## Summary

🔴 **The estate's only sanctioned path to change the database has been inert since 2026-08-19, and
it reports success.** `supabase/config.toml` carries:

```toml
[db.migrations]
enabled = false
```

`supabase db push` honours that for the **hosted** project too, so it skips every migration and
prints:

```
Skipping migrations because it is disabled in config.toml for project:
{"upToDate":true,"migrations":[],"message":"Remote database is up to date."}
```

**"Remote database is up to date"** is the whole defect. Not an error, not a warning — a false
green, from the one command this estate insists is the only legitimate way to change the schema.

The setting is not wrong; its **scope** is. It was added deliberately (commit `63c9bf9`,
2026-08-19, [[T238]] AC2) so `supabase start` would not auto-apply 226 unreplayable migrations
locally — `just db-local-up` seeds from `supabase/baseline/schema.sql` instead. Supabase's config
has no local/remote split for it, so disabling it locally disabled it in production.

## How it surfaced, and what was ruled out

The owner ran `just db-migrate` and said "migrated". [[T246]]'s function did not exist. They ran it
again. It still did not exist.

| ruled out | evidence |
|---|---|
| the confirmation gate blocked it | `.git/w0m-confirm.log` shows `db-migrate` **CONFIRMED at 21:17:48 and 21:20:52**, plus four more times on 2026-08-21. It was answered every time. |
| connectivity / WARP / IPv6 | the same `supabase migration list --db-url` call read the ledger fine |
| PostgREST schema-cache lag | the ledger row is `{"local":"20260821170000","remote":""}` — no remote entry at all, which no cache can explain |
| a bad migration | proven below: with the setting flipped, the push *sees* it |

🧪 **Proven in both directions with `--dry-run`, applying nothing:**
· `enabled = false` ⇒ `migrations: []`, *"Remote database is up to date."*
· `enabled = true` ⇒ **`Would push these migrations: • 20260821170000_t246_public_persona_definer.sql`**
`config.toml` was restored immediately and verified byte-identical to HEAD.

## Blast radius: exactly one migration, and it is a lucky number

✅ **Only ONE migration was authored inside the blind window** — `20260821170000` ([[T246]]'s). The
last applied is `20260817240000`, dated **before** the setting landed on 08-19. So nothing else was
silently skipped, and no schema change anyone believed was live is actually missing.
⚠️ That is luck, not design. A two-day window in which every schema change would have vanished
happened to contain one, and it was one whose absence was loudly visible because the chat stayed
down. Had it contained a routine migration, the estate would have carried a phantom schema.

## The gate that had the signal and did not use it

`just db-drift-check` reported **PENDING (1)** correctly, every time, and it runs as a **dependency**
of `db-migrate`. It exits **0** on pending — by design, since pending is the normal pre-push state —
so it announced the very fact that mattered and let the run proceed to do nothing.

🔑 The general shape, for the third time today: **the measurement existed and changed no verdict.**
Same as [[T247]] ③ (`tools-check` printing `ok` beside 4 drift) and [[T246]] AC5's origin (a reader
census recorded and not acted on).

## Acceptance criteria

- [x] **AC1** — ✅ **DONE 2026-08-21.** The push moved into
      [`project/scripts/db_migrate.py`](../scripts/db_migrate.py) so the before/after ledger reads
      and the push share one process and one `DATABASE_URL`; `db-migrate` is now one line that
      calls it. It reads `supabase_migrations.schema_migrations` before, pushes, reads it again,
      and **exits 1 when a migration that was pending still is** — printing which ones, and
      naming `W0M_DB_MIGRATIONS` as the first thing to check.
      🔑 **State comparison, not message matching**, exactly as this AC required. The same check
      catches four other failures the *"Skipping migrations"* grep would have missed: a push that
      dies half-way (reports how many of N landed), a real non-zero exit (propagated as-is, so a
      push that *errored* and a push that *lied* read differently), a `--dry-run` left in a
      recipe, and a ledger that **shrank** — the `migration repair --status reverted` shape that
      made [[T157]]'s 6 orphans.
      ⚠️ **Also fixed on the way past:** the old recipe appended `?options=…` to `DATABASE_URL`
      with a comment asserting the URL carries no query string of its own. `push_url()` now picks
      `?` or `&`. A silent `?` collision would have been rejected by `wom_ddl_guard`, not by any
      URL parser.
      🔴 **Not yet exercised by a real push** — `db-migrate` is denied to the agent, so the
      guarded recipe's first live run is the next migration (or one deliberate no-op run; see the
      status notes). `main()` is proven end to end with the database and the push stubbed.
- [x] **AC2** — ✅ **DONE 2026-08-21 — resolved, not worked around: the value is now
      PER-INVOCATION.** `config.toml` reads `enabled = "env(W0M_DB_MIGRATIONS)"`; the justfile
      exports `W0M_DB_MIGRATIONS := env_var_or_default('W0M_DB_MIGRATIONS', 'true')`; and
      **`db-local-up` is the one place that sets `false`**, scoped to its own `supabase start`.
      The conflation was never that the value was wrong — it was that **one static value served
      two commands with opposite needs.** Giving each invocation its own value is the fix; the
      production default is `true`, which is the safe direction.
      🧪 **Measured, not assumed** — `env()` interpolation works on the boolean, and there is
      **no default syntax**: `env(VAR:-true)`, `env(VAR:true)`, an unset VAR and an empty VAR are
      *all* rejected as `invalid db.migrations.enabled`. Verified against the real `config.toml`:
      `true` and `false` both parse, **unset is a hard `ProjectConfigParseError`**.
      🔑 **That fail-closed behaviour is the reason to prefer this over restoring a literal
      `true`** — a missing value now stops the command instead of silently meaning *"skip"*.
      ⚠️ **Cost, stated rather than buried:** every supabase command parses this file, so a bare
      `supabase …` outside `just` fails until the variable is set. Consistent with CLAUDE.md's
      *"all stack tools via just"*, and loud rather than silent. Blast radius measured, not
      guessed: all **4 launchd jobs** run `just`; the only non-recipe caller is
      `tools-policy.json`'s supabase smoke, which runs inside a recipe and inherits the export —
      `just tools-check` passes (31 tools, 0 problems).
      ✅ And it does **not** re-break [[T238]] AC2, which this AC explicitly warned against: the
      226 unreplayable migrations are still skipped locally, now by an explicit opt-out in the one
      recipe that needs it instead of by a file-wide setting that also disabled production.
- [x] **AC3** — ✅ **DONE 2026-08-21 — the post-check is wired, and the pre-check now says out
      loud that it does not block.** `db-drift-check` keeps exiting 0 on pending (correct —
      pending *before* a push is the normal state, and failing there would block the very command
      that resolves it), and prints, on every run that finds any:
      *"this check does NOT block on pending … what blocks is db-migrate's post-check."*
      🔑 **Announcing a fact while exiting 0 reads as approval.** This gate had the signal on all
      six runs and its silence about its own tier is what made it complicity rather than
      reporting. Naming the check that *does* block is the whole difference.
- [x] **AC4** — ✅ **DONE 2026-08-21 — 18 probes, `just migration-guard-test`, registered in
      `project/test-suites.json` as **blocking** ([[T240]]).** Shown **red first, literally**: with
      `stuck_migrations` reverted to the pre-T248 no-op, **4 assertions fail** — including
      *main() EXITS 1 when the push reports success and the ledger did not advance*, which
      returned **0**, the T248 run exactly. Restored and green: 18/18.
      Two halves, both needed. ① **the CLI still lies** — live, against the real database:
      with `W0M_DB_MIGRATIONS=false` a `db push` reports the remote up to date while a migration
      is pending *and does not name it*; with `true`, the same push names it. That second
      assertion is also AC2's end-to-end proof that `env()` reaches the CLI. ② **we now catch
      it** — `main()`'s **exit code** is asserted, not just the verdict function, because
      *"the measurement existed and changed no verdict"* is this ticket's own defect.
      🔑 **It carries a permanent MUTATION test**: a no-op verdict must NOT flag the T248 state.
      Without it, *"the guard passes"* and *"the guard is blind"* look identical — the precise
      confusion that produced this ticket. Better than a one-off red run, because it re-runs.
      ⚠️ **Applies nothing, ever**: `--dry-run` from a throwaway workdir that **symlinks** the
      real migrations and adds a far-future `SELECT 1;` sentinel. 🔬 The first version shipped an
      **empty** migrations dir and `db push` refused with the *orphan* error instead of the skip —
      a probe that could not reach the path it claimed to test, caught only because the ENABLED
      assertion failed for the wrong reason.
      🔴 **Not named `db-migrate-test`**: the deny-list entry `db-migrate*` is a **glob**, so it
      refused the probe of the very recipe it protects. Measured — the first run was blocked. A
      safety rule that also blocks the test of the thing it guards is how a gate goes unrun.

- 🔑 **The general rule this bought, worth more than the fix:** *a mutating recipe that reports
  success must prove the mutation happened.* `db-migrate` was the estate's only sanctioned path to
  change the schema and it had no such proof, so its success message was an assertion about
  nothing. The same question is worth asking of every other mutating recipe here — `deploy-*`,
  `sync-secrets`, `state-save` — and none of them were audited under this ticket.
- 🔬 **`env()` has no default syntax, and that turned out to be the feature.** Three forms were
  tried and all rejected; the consequence is that an unset `W0M_DB_MIGRATIONS` is a hard parse
  error on **every** supabase command. Considered and rejected: a generated scratch workdir for
  the push (duplicates config, drifts), and restoring a literal `enabled = true` (re-breaks
  [[T238]] AC2's local stage on the next `supabase start`, which AC2 forbade in as many words).
- ⚠️ **Still unmeasured, and deliberately left so:** whether `db reset`, `migration up`, and the
  seed/roles phases are scoped by this same setting. `db push` and `start` are the two confirmed
  consumers. The env() change makes the value explicit per invocation, which reduces the risk of a
  surprise but does not measure it — and `db-local-up` sets `false`, so if `false` also disables
  something else locally, that is where it will show up.

- **2026-08-21** — filed after `just db-migrate` was confirmed **six times** and applied nothing.
  🔑 The reason it took two "migrated" reports to find is the reason it matters: the command's own

- ⚠️ **Unmeasured deliberately:** whether any *other* Supabase CLI operation is silently scoped by

  probed. Do not assume the blast radius stops at push without checking.

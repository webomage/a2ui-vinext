# T552 — a deploy gate that expires at midnight

## Summary

Found 2026-10-07 re-running the deploy's gate stages. `tickets-frontmatter-check` (blocking, in the full `test` tier the deploy runs) failed with **70 tickets carrying stale derived fields**: `x_hot_score 68, computed 69` and so on, each off by exactly one. The hot score includes an age term, `age_weeks = days_since_created // 7`, so each day roughly a seventh of the tickets cross a week boundary and their stored score is one point behind. Nothing about the tickets changed. `just tickets-frontmatter-sync` rewrote 71 files (only `x_hot_score` and `x_synced`).

Consequences: a readiness check done at 23:59 is false at 00:01; the first deploy of every day starts with a sync commit touching dozens of tickets; and the pre-commit hook refreshes only the tickets in a commit, so the rest drift between deploys. The gate is correct that the stored value is stale, but a value that is stale daily is a poor thing to store and to gate on.

## Acceptance criteria

- [x] AC1 — **Decide and record the model**, with a recommendation: (a) stop storing the age term (the hot score is computed on read by `just tasks`; the frontmatter keeps only facts that change when a ticket changes), (b) keep storing it and make the gate compare modulo the age term, or (c) leave as is and add the sync to the deploy pre-flight. Recommend (a): a derived value that changes without a change to its source should not be persisted. **Decision (2026-10-21): Option (a) adopted.** `hot_score_for_frontmatter()` in `wom7web/project/scripts/tickets_frontmatter_sync.py` computes `x_hot_score` without `parts["age"]` while `scripts/tasks_query.py::load()` continues to compute `parts["age"]` on read.
- [x] AC2 — **Tests first, then the change.** A test that runs the check on two different dates against one unchanged ticket set and expects the same verdict; a mutation that reintroduces the age term into the stored value is caught (`wom7web/project/scripts/tests/test_tickets_frontmatter.py`).
- [x] AC3 — **Readiness no longer expires at midnight.** The deploy-readiness lesson in `LESSONS.md` drops its midnight caveat; `just tickets-frontmatter-check` is green on two consecutive days with no commits between them.

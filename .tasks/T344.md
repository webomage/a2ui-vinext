# T344 — mandatory Telegram connection, two audiences

## Summary

Owner ask, 2026-09-12: *"we also should definitely have TG connections for users and for w0m
members mandatory."* Raised mid-session while working an unrelated Stripe integration (T290) —
captured here as its own ticket rather than folded in, since the scope doesn't overlap.

Two distinct audiences, and nothing today enforces either:
- **CP clients** — no Telegram linking flow exists at all.
- **w0m team members** — same: no linking flow, no enforcement.

**What already exists, measured 2026-09-12:**
- `TELEGRAM_BOT_TOKEN` is live in Infisical `beta` — bot `@webomage_bot`, id `8506579552`, name
  `"w0m"` (verified via `getMe`, per [[T244]]'s notes). But the bot is **backend-less beyond a dead
  `SWARM_URL` branch** in `telegram.ts` — it currently only serves the outbound-alert/inbound-webhook
  use case described in ROADMAP §1.1 (Upwork poller, CV pipeline, gamification XP), which has no
  formal spec either. [[T10]] (P3, unstarted) is the closest existing ticket and only covers
  repointing that dead branch to `agent-consultant` — it does not touch account linking.
- `social_integrations` (`supabase/migrations/20260317000000_create_social_integrations.sql`,
  re-keyed under T210) is the nearest existing schema pattern for "a person connected an external
  identity" — it's now keyed on **`profile_id NOT NULL → public.profiles`** (the legacy `user_id`
  is kept nullable for backward compat), built for LinkedIn's OAuth model: `provider`,
  `provider_urn`, `access_token` (**NOT NULL**), `refresh_token`. Telegram's own linking primitives
  don't produce that shape — the **Telegram Login Widget** returns `auth_date` + an HMAC `hash`, no
  token at all; a **bot deep-link** (`/start <code>`) maps a `chat_id` to a person, also no token.
  Either path means `access_token NOT NULL` doesn't fit without a migration, or a parallel table is
  needed instead of reuse.
- 🔴 **Prior art — the w0m-member half was already attempted and is a DECIDED, NAMED debt row:**
  [[D63]] in `TECH-DEBT.md`. [[T318]] AC4 shipped `ConnectedServices.svelte`
  (`apps/cp/src/components/admin/ConnectedServices.svelte`) — a `/profile` panel with GitHub /
  LinkedIn / **Telegram** / ProductHunt "handle" text fields — but `saveMappings()` writes the three
  keys straight to **`localStorage`** and never calls an API; `onMount` reads them back from the
  same origin. Per-browser, not per-member: doesn't survive a new device, a cleared cache, or show
  to any other viewer. D63's own words for closing it: *"a real column/table + an API route, the
  same shape as `/api/sync/upwork-mcp`"*. **This ticket pays D63 down** for the Telegram field
  specifically (GitHub/LinkedIn/ProductHunt in the same component are the same defect but out of
  scope here). Confirmed via read: `apps/cp/src/components/admin/` is the internal/admin surface —
  there is genuinely **no equivalent for CP clients anywhere** (`apps/cp/src/pages/client` and
  `apps/cp/src/components/client` have zero Telegram references) — that half is greenfield.

**Enforcement model — decided by the owner 2026-09-12, while this ticket was being grounded:**
Telegram connection is **mandatory by default for w0m members**, and **optional by default for
clients/trainees/etc.** — but the requirement can be **overridden to required on a specific
profile** (i.e. a per-profile flag, not just a per-audience default). So the gate reads a tri-state
per profile (mandatory-by-role, optional-by-role, forced-required-override), not a single global
switch.

## Acceptance criteria

- [ ] AC1 — **Enforcement model implemented as specified.** Per-profile check: w0m members default
      to required, clients/trainees/etc. default to optional, and an explicit per-profile override
      can force "required" regardless of role default. Record where this flag lives (a column on
      `profiles` is the natural fit — confirm during design).
- [ ] AC2 — **Linking mechanism chosen and schema fit assessed**, informed by D63's own proposed
      shape (real column/table + API route, mirroring `/api/sync/upwork-mcp`). Telegram Login
      Widget vs. bot deep-link, weighed against extending `social_integrations` (already keyed on
      `profile_id`, would need `access_token` relaxed) vs. a new table. Record the decision and why.
- [ ] AC3 — **CP clients can complete the connection flow** (greenfield — no prior UI or schema),
      persisted server-side and visible in the DB via the chosen table.
- [ ] AC4 — **w0m members can complete the connection flow, replacing `ConnectedServices.svelte`'s
      `localStorage`-only Telegram field with a real persisted connection** — closes [[D63]] for
      Telegram (GitHub/LinkedIn/ProductHunt fields are the same defect, explicitly out of scope).
- [ ] AC5 — **The per-profile enforcement model actually gates**, proven live: a probe shows the
      gated action refused for a required-and-unconnected profile and allowed once connected, for
      both a w0m-member-default profile and a client profile with the override forced on.
- [ ] AC6 — **The existing dead bot backend does not silently ride along.** Either wire
      `telegram.ts`'s dead `SWARM_URL` branch to something real as part of this work, or leave it
      untouched and say so explicitly — not a silent omission.

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md): a
CP client and a w0m member can each link their Telegram identity through a real flow, the link is
provably required (the gated action refuses an unconnected identity and allows a connected one, per
audience), and the decision about what "mandatory" enforces for each is written down rather than
inferred from code. Spec verified, ecosystem + security checks pass, TASKS.md row + this ticket +
GH issue in sync.

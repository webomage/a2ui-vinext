# T333 — self-hire w0m onto the schema, then prove one identity can actually wear four hats safely

## Summary

Owner 2026-09-11, two related asks in one turn: *"so I want to self-hire myself for w0m project
and we have to map adventures → raids → quests schema to GH roadmap, epics and sprints or build or
major versions??"*, then *"do"* (triggering this SDLC gate), then *"I want also test if my
aleksei@webomage.com could properly handle client, PM, TL and Dev roles all together with correct
separation and functions."*

The two asks are one piece of work, not two: **before "w0m" can be provisioned as a real project
row with Aleksei holding Client + PM + Tech Lead + Dev simultaneously, the estate needs (a) the
already-settled epic↔raid / milestone↔adventure / ticket↔quest bridge written down explicitly
(it exists in two separate decisions today, never connected), and (b) proof that holding all four
hats at once is safely separated in practice, not just permitted in schema.**

**Part A — schema mapping, CORRECTED during this ticket's own grounding pass.** The initial draft
proposed epic → Adventure, milestone → Raid — this was **backwards, and already decided twice
over, independently, in the opposite direction:**
- [[T203]] AC6/AC6b (owner, 2026-08-12): the hierarchy fork is settled as **`project → adventure →
  raid → quest`** — no FK changes, four independent sources (FK direction, migration headings,
  naming lexicon, the Authority Model doc) agree.
- [[T27]] AC4 (unblocked by the above): fixes the vocabulary those nouns carry — **an adventure is
  a campaign *phase* of a project, a raid is a feature *epic*/sprint, a quest is the atomic
  claimable task.**
- [[T239]] (owner, 2026-08-21, independently): settles **`epic` = cross-repo functional
  capability · `milestone` = temporal phase** as the two ticket-schema axes GitHub already
  distinguishes (issue-type vs. native `milestoneId`/`dueOn`/`progressPercentage`).

**The two decisions describe the same shape from different subsystems and were never stated as
equivalent.** Matching definitions to definitions: a raid ("feature epic/sprint") is what `epic`
("cross-repo functional capability") names; an adventure ("campaign phase of a project") is what
`milestone` ("temporal phase") names. So the correct bridge is **epic → Raid, milestone →
Adventure, ticket → Quest** — the reverse of the draft. This ticket's Part A job is therefore
narrow: **write down the bridge as an explicit equivalence** (nobody has), not invent a new
mapping and not re-do T27's or T203's decisions. **Writing real epics/tickets into the schema as
raids/adventures/quests is [[T27]]'s job** (still unbuilt — 0/6 ACs, the greenfield writer), and
this ticket must not duplicate that scope.

**Part B — the self-hire project row.** Verified live 2026-09-11: `public.projects` has 7 rows,
all attributed (`client_id` set per [[T325]]) — no "w0m" row exists. [[T325]] built
`attribution_state` (`attributed | client_less | blocked`) on **`contracts`**, not `projects`; a
self-hire project has no client-side contract to attribute, so it needs its own decision — an
internal-only exemption class, not a fourth `attribution_state` value bolted onto a column that
was scoped to `contracts` on purpose.

**Part C — the multi-hat question, folded in because it gates Part B.** Self-hiring on w0m only
means something if Aleksei's identity can hold Client + PM + TL + Dev on that one project with
*real* separation, not cosmetic role labels. Grounded this session:
- The plumbing is real: `wom_acting_is`/`wom_acting_in` ([[T39]] Phase 0) are live in 10+ RLS
  policies (`t165`, `t198`, `tech_debt` migrations), and [[T102]]'s `hats`/`resource_grants`/
  `is_capable()` enforce "wear only your own hat, only on its own project" via RLS + a composite
  FK on `worn_hats` (`apps/cp/src/pages/api/project/hats.ts`) — not just UI convenience.
- **Not hypothetical** — [[T319]] (done 2026-09-05) found both of Aleksei's profiles already held
  all 4 hats simultaneously, a live seeding accident that had to be pruned (10→6 hat rows).
- [[T317]] already established the accepted method for **UX verification**: wear each hat as admin
  via [[T310]]'s universal switcher.
- **But admin is the wrong subject for a separation PROOF**: both `client-api`'s ownership gate
  (`denyUnlessOwned` — `isAdmin` bypasses it, logged to `admin_activity_logs`, not blocked) and
  `/api/project/hats` (admin can wear any hat on any project, auto-provisioning one on demand — also
  logged, not blocked) short-circuit for an admin identity. Testing as `aleksei@webomage.com` today
  proves the bypass fires and is audited, not that a non-admin PM is fenced off from Client data.

## Acceptance criteria

- [ ] AC1 — The bridge **epic → Raid, milestone → Adventure, ticket → Quest** is recorded as an
      explicit equivalence (in `docs/backend/TERMINOLOGY-MAP.md` or the gamification spec),
      citing both settlements it reconciles ([[T203]] AC6/AC6b 2026-08-12 for
      adventure/raid/quest; [[T239]] 2026-08-21 for epic/milestone) so a future reader does not
      re-derive or re-fork it a third time.
- [ ] AC2 — Confirm the bridge is consistent with [[T27]]'s spec (the ticket that will actually
      write epics/tickets into `adventures`/`raids`/`quests` — still unbuilt) rather than
      provisioning a worked example here; if [[T27]] has already landed data by the time this is
      picked up, point at its output as the proof instead of building a second writer.
- [ ] AC3 — A decision is recorded for how a "w0m" self-hire project fits `public.projects`: either
      (a) a real row with an explicit internal/self-hire marker distinct from `contracts.attribution_state`
      (per [[T325]]), or (b) an explicit exemption documented in the same place T325's BridgeRoad
      exemption (`clients.portal_note`) lives — with the reasoning for the choice written down, not
      just the choice.
- [ ] AC4 — If AC3 chooses to create the row, `aleksei@webomage.com` (or a profile of theirs) holds
      Client + PM + Tech Lead + Dev hats on it via the real `hats`/`worn_hats` machinery — not a
      manual DB write — and `wom_effective_capabilities` returns the correct capability set per worn
      hat.
- [ ] AC5 — A genuine separation test is run as a **non-admin** identity (a second profile/login
      without the `admin` role, or a dedicated test account) wearing each of the four hats in turn
      on the w0m project, confirming: Client hat cannot see PM/TL/Dev-only data or actions; PM/TL/Dev
      hats cannot self-approve as Client via `client-api`. This is distinct from — and does not
      reuse — [[T317]]'s admin+switcher UX-verification pattern, because AC5's finding is that
      admin identity cannot prove this (see Summary Part C).
- [ ] AC6 — The two known non-blocking admin bypasses relevant to AC5 (`client-api`'s
      `denyUnlessOwned` admin short-circuit; `/api/project/hats`' admin on-demand hat provisioning)
      are each named as accepted/decided behavior in `TECH-DEBT.md` or explicitly ruled out-of-scope
      here, so this ticket does not silently re-discover them later as a gap.

## Definition of Done

The epic/milestone↔raid/adventure bridge is written down where a future ticket will actually find
it (AC1), checked against [[T27]]'s spec rather than re-implemented (AC2), and the w0m project (if
created under AC3) shows correct, RLS-enforced hat separation proven by a non-admin test run (AC5)
— not by inspecting schema or re-running T317's admin-switcher walkthrough. `just ac-trace-check`
passes on this ticket; TASKS.md row, this file, and the GH mirror agree on status.

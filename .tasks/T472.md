# T472 — Stale sb-access-token cookie desync

## Summary

Owner report & screenshot (2026-09-27):
> "and this one is trying to use jwt with error, why? ... /me/opportunities throws 'JWT expired' / 'invalid JWT: token is expired'"

Root cause diagnosis:
1. Supabase JWT access tokens expire after 1 hour (3600s).
2. The server-side `@supabase/ssr` client (`getServerClient(ctx)`) refreshes expired sessions automatically and persists them into chunked cookies (`sb-<ref>-auth-token.0`, etc.).
3. However, the legacy unchunked cookie `sb-access-token` is only written at initial login with a 7-day maxAge and is **never refreshed or re-synchronized by middleware** upon session refresh.
4. Pages like `opportunities.astro` and `account.astro` read `Astro.cookies.get("sb-access-token")?.value` and pass it down as props (`accessToken`) to client-side Svelte components (`MfaEnrollment.svelte`, `PersonalAccessTokens.svelte`, `QuestBoard.svelte`).
5. After 1 hour, the legacy cookie holds an expired JWT. The Svelte components use this expired token to make direct client-side PostgREST / GoTrue requests, failing with `JWT expired`.

## Acceptance criteria

- [x] AC1 — **Middleware Token Synchronization**: Update auth middleware in `packages/lib/src/auth` so that whenever a session is refreshed on the server, the fresh access token is synchronized into `Astro.cookies.set("sb-access-token", ...)` with consistent cookie options (HttpOnly, Secure, SameSite=Lax).
- [x] AC2 — **Locals Fresh Token Exposure**: Expose `Astro.locals.accessToken` populated directly from the verified live session, replacing raw `Astro.cookies.get("sb-access-token")` reads across CP/web SSR pages.
- [x] AC3 — **Page Prop Migration**: Update `apps/cp/src/pages/me/opportunities.astro` and `apps/cp/src/pages/me/account.astro` to pass the fresh token from `Astro.locals.accessToken`.
- [x] AC4 — **Verification**: Verify that long-lived sessions past 1 hour make successful authenticated calls from Svelte components without `JWT expired` errors.

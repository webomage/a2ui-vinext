# T266 — the join: Artemio is a governed repo, not yet a managed client

## Summary

Owner direction 2026-08-23: *"power up Artemio as first registered and managed client"*.

🔑 **"Client" means two different things here and the queue tracks them separately.** [[T182]]
imported **Artemio-the-repo** into w0m's SDLC governance, and closed it the same day —
`just client-check artemio` reads **CONFORMS, 6/6 gates, 8 of 8 required keys**. ROADMAP §10 and
the tables under it describe **Artemio-the-client**: an account, a role, a contract, a portal.
**Nothing in 265 tickets covers the join**, which is why this exists.

## 🔴 The gap the review found: two provisioning paths, and only one of them works

**`client-register` (edge fn) wires all four things** — auth user → `user_roles` role=`client` →
`clients` row → `client_users` link. It is keyed to a **`lead_id`**: the email is read from the
stored lead row, never from the caller, so lead-id enumeration cannot take over an address.

**`ClientManager.svelte` writes one** — `supabase.from("clients").insert([formData])`, and nothing
else.

⇒ A client created through the **admin CRM** has **no user, no role and no `client_users` row**, so
the portal's membership query returns `[]` and — correctly, by [[T198]]'s fail-closed rule — renders
an **empty portal**. Not an error. An empty page.

🔑 **And Artemio is not a lead.** They are an existing delivery client, so the only path that wires
the tenancy correctly is the one path that cannot be used for them. That is this ticket's real
subject; the portal has nothing to show because nothing links a person to the organisation.

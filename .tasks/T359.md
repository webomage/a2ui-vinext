# T359 — Admin CP: Manage project hats possibilities, baseline role templates, and per-seat office grants & restrictions

## Summary

In w0m projects and delivery engagements, functional delivery roles and hats (`public.project_roles`, `public.hats`) decouple client-facing positions from internal agency matrix units. However, today project roles must be created ad-hoc from scratch or hardcoded scripts (like `INDIE_ROLES`), with no catalog of baseline role templates. Furthermore, once a role seat is filled by a member on a project, there is no interface in Admin CP to granularly enable or disable specific offices (`public.offices`, e.g. `w0m.tech.lead`, `w0m.tech.qa`, `w0m.tech.ops`, `w0m.delivery.manager`) to apply custom capabilities or restrictions to that filled seat.

This ticket delivers:
1. **Baseline Role Templates Catalog (`public.role_templates`)**: System-wide baseline role templates (Tech Lead, Developer, QA Engineer, Product Manager, DevOps, Designer) without extra options enabled or restrictions applied by default.
2. **Project Hats Possibilities Management in Admin CP**: UI in `ProjectRolesModal.svelte` and `RoleManager.svelte` to configure available hats/roles on any project, with 1-click instantiation from the baseline role template catalog.
3. **Per-Seat Office Grants & Restrictions**: Expandable controls on filled project roles allowing admins to toggle specific offices ON or OFF for that member on that project scope via `public.resource_grants`.

## Acceptance criteria

- [x] AC1 — Role Templates Database Migration: Create `public.role_templates` (`id`, `name`, `slug`, `description`, `default_offices text[]`, `is_system boolean`, `created_at`, `updated_at`), unique on `slug`. Seed baseline system role templates: Tech Lead (`tech-lead`), Software Engineer (`dev`), QA Engineer (`qa-engineer`), Product Manager (`pm`), DevOps (`devops`), UI/UX Designer (`designer`). RLS enabled: authenticated read, admin/service_role manage.
- [x] AC2 — Backend API for Role Templates: Implement `/api/admin/role-templates` (GET list, POST upsert, DELETE archive/remove) and extend `/api/project/roles` to expose available baseline templates for project instantiation.
- [x] AC3 — Admin CP Role Templates UI: Add baseline Role Templates catalog view in `RoleManager.svelte` under the Roles/Offices administration view, allowing admins to inspect and configure the main templates of roles.
- [x] AC4 — Project Hats Possibilities Management: Upgrade `ProjectRolesModal.svelte` to allow admins to instantiate hats/roles possibilities from the Role Templates catalog with 1 click, alongside custom role creation.
- [x] AC5 — Per-Seat Office Enable/Disable UI: In `ProjectRolesModal.svelte` and `RoleManager.svelte` (Hats tab), render an expandable "Offices & Restrictions" panel for each filled role seat. Display available offices (`public.offices`) with toggles to enable or disable individual capability bundles per filled role on that project.
- [x] AC6 — Per-Seat Office Grant API Actions: Extend `/api/project/roles` with `toggle_office` action to grant or revoke an office for a member on a project via `public.resource_grants` (`subject_kind = 'profile'`, `subject_profile_id = profileId`, `office = officeKey`, `scope_type = 'project'`, `scope_id = projectId`), returned with current grant states.
- [x] AC7 — Verification & Quality Gates: Vitest unit tests in `apps/cp` verifying role template CRUD, project role instantiation, and office grant toggling. Typecheck and Astro check clean across `apps/cp`.

# T130 — Per-stack tech/tools registry + just-automation enforcement + `discovery` drift

## Summary

Owner ask (2026-07-24), three cohesive parts:

1. **Enforce that every tool/tech across every stack runs through `just` automation — mandatory.**
   Today the `toolchain` contract in `.w0m/sdlc.json` says `commands_via: "just"` with a *global*
   `canonical_recipes` list, but nothing asserts that each stack's real toolchain is actually
   reachable through a `just` recipe, and raw `pnpm`/`npx`/`tsc`/`deno`/`wrangler`/`mlx_*`
   invocations still creep into hooks, docs and scripts. Make "all stack tools via `just`"
   structural, not advisory.
2. **A schema declaring, per stack, which techs and tools are ENABLED and USED.** The ecosystem is
   multi-stack (Astro/Svelte/Tailwind web · Hono worker · Deno edge-functions · the new TS skills
   subsystem · CF workers · MLX python · ext · sec), each with its own runtime + framework set +
   CLIs. There is no machine-readable per-stack registry — `tools-policy.json` is host-CLI floors,
   `deps-policy.json` is npm deps, neither is stack-scoped.
3. **A `discovery` SDLC command that checks drift between the declared snapshot and the code.**
   Like `sdlc-doctor`, but for stack techs: snapshot the declared per-stack techs/tools and diff
   against what the code actually uses (deps, config, imports, justfile recipes). Report
   **used-not-declared** (a tech in code absent from the registry) and **declared-not-used** (a
   stale registry entry).

This is the per-stack extension of the T119 `toolchain` contract and the natural companion to
[[T112]] (deps/tools policy): T112 answers "is each host tool present at its floor"; T130 answers
"does each stack's *declared* tech/tools set match reality, and is it all driven through `just`".

## What is already known (do not re-derive)

- **`.w0m/sdlc.json → toolchain`** (T119 AC7) is the existing contract: `commands_via: "just"`,
  `secrets_via: "infisical"`, `canonical_recipes: [check, typecheck, lint, test, test-e2e, build]`,
  `exempt: {wom7md: …, …}`. Verified by `just sdlc-doctor`. It is **global**, not per-stack.
- **`project/tools-policy.json`** = host CLI tools (just, osv-scanner, semgrep, gitleaks, …) with
  `min`/`known_good`/`required`/`auto`; advisory, machine-wide. `just tools-check` / `tools-upgrade`
  ([[T112]]). **`deps-policy.json`** = npm security floors. Neither is stack-scoped or tech-aware.
- **`sdlc-doctor`** (`wom7api/scripts/sdlc_doctor.py`, enhanced 2026-07-24 under [[T127]] AC10)
  already checks all 10 required tools at their floors + git-hook install state per repo. `discovery`
  should reuse its reporting shape (block vs warn per policy) and likely live beside it.
- **Live stacks + their drivers** (the first real registry input): `web` (Astro 6 / Svelte 5 /
  Tailwind 4 — `just dev`/`build`/`typecheck`), `worker` (Hono 4 — `just typecheck-worker`), edge
  functions (Deno — `just deno-check`), `skills` (TS/tsx — `just skills-typecheck`/`skill`, added
  under [[T127]]), `wom7cfworkers` (CF workers), `wom7mlx` (MLX python venv — Gemma 4 vlm), `ext`,
  `sec`. `wom7md` is prose-only (already `toolchain.exempt`).
- **Enforcement precedent:** [[T129]] makes ticket-first discipline structural at commit time; T130
  makes *tool-via-just* discipline structural. Same philosophy (convention → mechanical gate),
  different axis. The `just` recipes just added for the skills subsystem ([[T127]]:
  `skill`/`skills-typecheck`/`skills-install-plugin`/`skills-score`) are the model: no raw pnpm/npx.

## Acceptance criteria

- [x] **AC1 — Per-stack registry + schema.** A machine-readable per-stack registry (a `stacks`
      block in `.w0m/sdlc.json`, or `project/stacks-policy.json` referenced from it) declares, for

      `just` recipe that drives it, plus `enabled`. Covers all live stacks above; honors `exempt`.
      A JSON Schema is documented (mirroring `wom7skills/skills.schema.json`).
- [x] **AC2 — Mandatory just-automation enforcement (gated).** A check asserts (a) every declared
      stack tool resolves to a real `just` recipe (`just --summary` membership), and (b) flags raw
      `pnpm`/`npx`/`tsc`/`deno`/`wrangler`/etc. invocations in tracked automation (hooks, scripts,
      docs) where a `just` recipe exists to cover them. Exit non-zero on a declared tool with no
      recipe. Wired into `sdlc-doctor` (or `discovery`) so it runs in the standard preflight.
- [x] **AC3 — `discovery` command (drift snapshot vs code).** `just discovery` snapshots the
      declared per-stack techs/tools and diffs against actual code — per stack scan `package.json`/
      `deno.json` deps, config files (astro/svelte/tailwind/wrangler), the import surface, and the
      justfile recipes — reporting **used-not-declared** and **declared-not-used**. Proven both ways:
      introduce a real tech absent from the registry → flagged; declare a phantom tech → flagged.
      Block vs advisory per policy (default: advisory in dev, block in the enforcement gate).
- [x] **AC4 — Wire into SDLC + document.** `discovery` surfaces stack drift in the
      `w0m-sdlc-research`/`start` grounding (Start Brief) and/or as a pre-push advisory; `sdlc-doctor`
      cross-references the registry; CLAUDE.md/AGENTS.md record the per-stack registry and the
      **"all stack tools via `just`"** rule as a non-negotiable.

## 🔧 Post-close correction — 2026-07-31: the raw-invocation rule was proved by nothing

Found while working [[T154]], fixed in the same session. **`just discovery-test` was 26/28 and had
been for some time** — both failures anchored on a hardcoded `pre-push:25`, the `pnpm … astro check`
call named as "the last blocker to flipping `enforce_raw: true`" in the follow-ups above. **[[T149]]
AC3 removed it** (line 25 now calls `just typecheck`), so `raw_invocations` is legitimately `[]`.

The two red checks were the small half. **The real cost: the detector's POSITIVE path was left
covered by nothing** — `scan_raw_invocations` could have been broken outright and `just discovery`
would still have printed *"conformant"*. A gate proved only by input that someone else maintains is
a gate that silently stops being proved, which is this estate's recurring shape.

**Fixed by moving the proof onto input the test owns**, not by deleting the checks:
- A **synthetic hook layer** under a patched `ROOT` drives the real scanner: one real offender
  asserted by file, line and tool, plus a separate line for every skip rule (comment, `echo`,
  `printf`, quoted string, no-recipes-known) and one per tool token. 27 → 43 checks.
- The live layer keeps **one** assertion, now the honest one: **zero raw invocations**, which is
  T149 AC3's end state. It means something only because the positive path is proved separately.
- The `enforce_raw` BLOCKING decision is tested by **stubbing the scan and asserting the decision**.
  The old check needed a real offender to exist, so it could only have been kept alive by never
  fixing one — a test that punishes the fix.

**Two live defects fell out of writing it, neither visible while the hook layer was clean:**
1. 🔴 **The raw scan only ran under `--enforce`.** Plain `just discovery` could never report a raw
   invocation, contradicting both the module docstring (*"advisory always"*) and the comment at the
   call site. Now scanned in every mode, blocking still only under `--enforce` + `enforce_raw`.
2. 🔴 **`mlx_\w+` could not match `mlx_lm.generate --model …`** — mlx ships DOTTED console scripts,
   so the single most common real invocation was unmatchable. The pattern stopped at `mlx_lm` and
   then demanded whitespace that a `.` is not. Now `mlx_[\w.]+`.

**Mutation-tested, 9 mutants.** Eight died. The survivor showed **my own new check was vacuous**:
asserting husky's `_` directory is skipped proves nothing, because `iterdir()` is non-recursive and
`p.is_file()` already excludes it. The property that actually matters is **non-recursion** — swap
`iterdir()` for `rglob("*")` and the scan starts flagging husky's generated shims. The check was
relabelled to say what it guards, and that mutant now kills it.

⚠️ The follow-up above — *"the `pnpm astro check` raw call at `.husky/pre-push:25` is the last
blocker to flipping `enforce_raw: true`"* — **is now stale in the good direction: the blocker is
gone.** `enforce_raw` is still `false`; flipping it is a live, cheap option and the blocking path is
now proved by test. The stale comment at `.husky/pre-push:70` that still named line 25 as "the ONE
raw-invocation offender in the estate" is corrected.

### Found in the same pass — the status dashboard was reading commentary as state

Adding a 🔴 to T130's own queue row flipped the row from **done to blocked**, which exposed
`gen_status_dashboard.py`: it picked `next(e for e in STATUS if e in status_cell)` — **the first
key in the dict, not the first marker in the text**. Since 🔴 is the first key, *any* row whose
notes mentioned a red finding was reported blocked. Measured: **14 of 136 rows misclassified**,
including five DONE tickets and [[T154]] itself, so the dashboard's *"15 blocked"* was very nearly
fiction (the true figure is **1**). ⇒ **The more evidence a row records, the more likely it was
misread** — a reporting bug that punishes exactly the rows that document themselves best.

Now anchored to the marker the cell STARTS with (134 of 136 rows already carried it at index 0).
The two that did not used a **🔵 outside the vocabulary** and were silently taking a status from
their prose: **T120** (whose row text literally says *blocked*, matching its frontmatter) and
**T131**. Both markers corrected, and an unrecognized leading marker now **warns by ticket id**
instead of guessing. Counts moved: blocked 15 → **1**, done 18 → **24**, in progress 22 → **26**,
queued 79 → **83** — and the blocked figure now agrees with `just tasks blocked`, which reads
ticket frontmatter rather than the queue row.

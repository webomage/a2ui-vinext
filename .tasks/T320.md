# T320 — Login stops redirecting to CP: 5 interlocking bugs drop the redirect target end-to-end

## Summary

Found 2026-09-06 during an auth audit (see `_in/2026-09-06-login-logout-role-change-audit-and-suggested-actions.md`,
picked up and folded into this ticket). A user who logs in on a clean `/login` visit — no `?next=`
in the URL, which is the common case — lands on the marketing site root instead of the Control
Panel. Traced end-to-end; it is not one bug but five that each independently drop the redirect
target, verified against the current code (2026-09-06):

1. **`AuthForm.astro:32`** hardcodes `<input type="hidden" name="next" id="next-redirect"
   value="" />`. The `defaultRedirect` prop the page passes in is never bound to it — only the
   client script (`AuthForm.astro:97-100`) overwrites the value, and only if `?next=` is present
   in the browser URL. A clean visit submits an empty `next`.
2. **OAuth start drops it too.** `startOAuth()` (`AuthForm.astro:118-125`) reads `next` from
   `window.location.search` only, never falls back to the hidden input or `defaultRedirect`. A
   clean visit clicking Google/LinkedIn/GitHub starts the OAuth flow with no target.
3. **`defaultPortalUrl()`** (`packages/lib/src/auth/handlers.ts:89-94`) returns
   `http://localhost:4321` for `localhost` — that is the **web** marketing app's port. The Control
   Panel runs on `4325`. Every local fallback lands on marketing, not CP.
4. **`hatHomeUrl({ local: true })`** (`packages/lib/src/auth/abilities.ts:79-82`) has the identical
   bug for hat-switch/redirect targets: every non-live-domain case returns `http://localhost:4321/`
   or `.../client/portal` under the `4321` origin.
5. **Neither `apps/web/src/middleware.ts` nor `apps/cp/src/middleware.ts` passes
   `authedHomeRedirect`** to `createAuthMiddleware`, though the hook exists and is read at
   `packages/lib/src/auth/middleware.ts:200`. An already-authenticated user who navigates to
   `/login` sees the login form again instead of being bounced to their hat home.

None of these five is covered by an existing ticket — checked against `T159` (session
*revocation* gap, a different bug in the same file family) and `T87` (duplicate hat-switcher UI).

## Acceptance criteria

- [x] AC1 — Bind the hidden `next` input to `defaultRedirect` in `AuthForm.astro`, and make the
      client script fall back to it when `?next=` is absent. A clean, unauthenticated visit to
      `/login` followed by a valid password login lands on `PUBLIC_CP_URL` (or its per-host
      default), not the marketing root.
- [x] AC2 — `startOAuth()` carries `defaultRedirect` through when the URL has no `?next=`. A clean
      visit clicking Google/LinkedIn/GitHub reaches `/api/auth/callback` with a CP target, not none.
- [x] AC3 — `defaultPortalUrl()` returns the CP's local port (`4325`, or `PUBLIC_CP_URL` if set),
      not `4321`, for `localhost`/`*.localhost`.
- [x] AC4 — `hatHomeUrl(role, { local: true })` returns a CP-origin URL (`4325`) for every role,
      not `4321`.
- [x] AC5 — Both `apps/web/src/middleware.ts` and `apps/cp/src/middleware.ts` pass an
      `authedHomeRedirect` to `createAuthMiddleware`. An authenticated user navigating to `/login`
      is redirected to their hat home and never shown the login form.
- [x] AC6 — A regression test (Gauge or Playwright) proves, RED against today's code first: clean
      `/login` visit → password login → lands on CP; clean `/login` visit → OAuth click carries a
      CP target; authenticated visit to `/login` bounces without rendering the form.

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md): a
user who logs in with no `?next=` in the URL — the common case, not the edge case — lands on the
Control Panel on the first request, on every host (`localhost`, `cp.w0m.xyz`, `cp.webomage.com`),
via both password and OAuth; an already-authenticated visit to `/login` never re-renders the form.
Tests mapped, ecosystem + security checks passed, committed with the T-id, `TASKS.md` row + this
ticket + GH issue in sync.

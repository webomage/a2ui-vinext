## Summary

**L1 identity gaps — 2FA UI + dormant login providers** — TOTP MFA is **enabled project-wide** (`mfa_totp_enroll/verify = true`, 10 factors) but has **no enrolment UI anywhere**, and `github` + `linkedin_oidc` are enabled as login providers yet **offered in no sign-in UI** (only Google is wired, `apps/{web,cp}/src/pages/api/auth/google.ts`). Either expose them (2FA enrolment + management in CP account settings; provider buttons where clients/members sign in) or disable to shrink attack surface. Owner ask 2026-07-20: "enable google auth and 2fa for clients".

## Acceptance criteria

- [x] AC1 — **Admin scope (owner split, 2026-09-25):** an admin-context session at `aal1` with an enrolled factor is sent to `/mfa/challenge` before any admin page (T53 gate + AC8 held-role context; probes in `mfa-policy.spec.ts`). Non-admin sign-in challenge split into [[T454]].
- [x] AC2 — **Admin scope:** `apps/cp/src/pages/api/auth/mfa/challenge-verify.ts` verifies with `supabase.auth.mfa.challengeAndVerify()` server-side and sets aal2 cookies (7 tests in `apps/cp/src/tests/api/auth/mfa/challenge-verify.test.ts`, fix `994ac306`). The same endpoint in the other apps is split into [[T454]].
- [ ] AC3 — **Admin challenge UI complete:** `MfaChallenge.svelte` has `autocomplete="one-time-code"` and error feedback, but **no recovery guidance** (what to do if the authenticator is lost). Add it. The inline `AuthForm` step for non-admin sign-in is split into [[T454]].
- [ ] AC4 — Dormant OAuth providers operational verification: Verify end-to-end OAuth flow for all configured providers (`google`, `linkedin_oidc`, `github`) across apps, ensuring PKCE callback completes session establishment and identity linkage.
- [ ] AC5 — **Providers kept, and surfaced where they are enabled (owner, 2026-09-25):** `linkedin_oidc` stays enabled as a **sign-in** provider for our apps and gets a button on every sign-in surface that offers Google. LinkedIn **OAuth for service integrations** (the connector at `api/auth/linkedin.ts` / `linkedin-callback.ts`) is a separate path and stays. Anything enabled but offered nowhere is disabled with a written reason.
- [ ] AC6 — E2E 2FA verification (admin): an automated test proves an MFA-enrolled admin cannot reach an admin route until the TOTP challenge is satisfied.
- [ ] AC7 — **GitHub connected on the person profile (owner, 2026-09-24, raised to P0).** From Me → Account & security
  (today `/profile` → `ConnectedIdentities.svelte`, built by [[T53]]), aleksei@webomage.com links a GitHub identity
  through `supabase.auth.linkIdentity({ provider: 'github' })`. The PKCE round-trip completes in production and the
  identity row lands in `auth.identities` for that user. Evidence: the identity row plus a screenshot of the panel.
  This is the first live use of the dormant `github` provider (AC4). It later feeds performer attribution for
  repo/PR work ([[T440]]).

- [x] AC8 — **MFA follows the real admin role, not the worn hat (found 2026-09-25, T439 C1 check).**
  `packages/lib/src/auth/mfa-policy.ts` decides "admin context" from `effectiveRole === "admin"`. An admin wearing the
  MANAGER hat therefore skips the MFA gate, while the identity barrier (`availableRoles` includes admin) and
  `public.is_admin()` (reads `user_roles`, hat-blind) still let them into admin pages. Measured: `w0m@webomage.com`,
  `aleksei@webomage.com` and `casualuser@gmail.com` had 0 MFA factors, so the hat was the only way admins reached
  `/system/*` pages. Fix: admin context = holds the admin role (`availableRoles.includes("admin")`) or the admin domain;
  a red probe in `mfa-policy.spec.ts` wears the manager hat without aal2 and must be challenged.
- [ ] AC9 — **Touch ID / security-key MFA per profile (WebAuthn factor), TOTP kept as fallback.** Owner, 2026-09-25: Touch ID is the MFA solution for 2FA per profile — each person enrols it on their own Me → Account & security page. `@supabase/auth-js` 2.110.7 supports `factorType: "webauthn"` (experimental); the project setting must be enabled. **Relying party: one per domain** (a credential for `webomage.com` does not work on `cp.w0m.xyz`), so the admin console is not moved. Separate from Supabase passkey sign-in (replaces the password) and **separate from the deploy / `db-migrate` Touch ID gate** (T435, `confirm_step.py`), which stays as it is — that one is device-owner confirmation for infra, not an account factor.

## Definition of Done

T100 is done when: signing in to an account with an enrolled TOTP factor is blocked at
`aal1` and requires a 6-digit code via `/api/auth/mfa/challenge-verify` before session
upgrade, `AuthForm.astro` renders that challenge inline (one-time-code autocomplete,
error + recovery copy) rather than leaving MFA enforced with no UI to satisfy it, `google`/
`linkedin_oidc`/`github` each complete a real PKCE OAuth round-trip end-to-end in every
app or are explicitly disabled with a written reason, and an E2E test proves an
MFA-enrolled user cannot reach a protected route without passing the TOTP challenge.

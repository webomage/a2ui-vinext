# T442 — Connector framework: one OAuth connect flow, MCP-first transport, encrypted tokens

## Summary

Owner, 2026-09-24: *"we should start implementing real oauth connections and integration with services also as
planned"* and *"Upwork and other services should be with prio connected via — 1. mcp, 2. api/app"*.

"As planned" is the connector architecture: [[T94]]/[[T95]]/[[T134]] (done) built the registry, and
`wom7web/docs/backend/CONNECTOR-RESEARCH-MATRIX.md` set a depth ladder (0 link → 1 verified link → 2 read sync →
3 read+write). What was never built is the shared machinery every level-1–3 connector needs. Each provider has
its own half-flow today:
- **Upwork:** a member callback exists, but nothing starts it (0 member connections live, [[T441]]).
- **LinkedIn:** 1 member connection, on its own routes.
- **GitHub:** only a Supabase *login* identity ([[T53]]), which stores no token usable for sync.
- **Tokens at rest:** encryption is paused in [[T99]].

**Transport rule (owner, 2026-09-24).** Consistent with the recorded deployed-code ladder "MCP if it can
authenticate without a human → SDK → API" (wom7web `CLAUDE.md`, 2026-08-28):
1. **MCP**, when the provider's MCP server can keep a session going without a human, i.e. its OAuth
   server issues a refresh token our backend can use.
2. **API / App** (GitHub App, OAuth app, API key) otherwise, and for scheduled sync wherever the MCP session
   cannot be kept going.

The choice is recorded per provider in the registry from a **measurement**, never assumed. [[T218]] found
Upwork's MCP OAuth 2.1 "per interactive session" and concluded it cannot serve a cron. That was recorded but never
tested against the refresh-token path (AC1).

## Acceptance criteria

- [ ] AC1 — **Upwork MCP headless spike.** Complete OAuth 2.1 (DCR + PKCE) against `https://mcp.upwork.com/mcp`
  once interactively, then prove or disprove that a server-side MCP client can refresh and call a tool with no
  human present (after the access token expires). Result recorded in the registry and `docs/DECISIONS.md`. It
  decides T441's sync transport: MCP if yes, GraphQL API if no.
- [ ] AC2 — **One connect flow.**
  - `start` writes an `oauth_states` row bound to the session's profile (PKCE where supported).
  - `callback` validates state and uses one exact redirect URI (no variant ladder, AgDR-0025).
  - Tokens are exchanged and stored.
  - Refresh runs before expiry; a refresh failure marks the connection `expired`, never silently `connected`.
  - Disconnect revokes at the provider where supported, then deletes.
- [ ] AC3 — **Tokens encrypted at rest** (resolves the rest of [[T99]]). Access/refresh tokens are stored
  encrypted (decision: Supabase Vault recommended), decrypted only server-side, and never selected into the
  browser (T99's `.select("*")` leak class). No member other than the owner may connect before this lands.
- [ ] AC4 — **Transport adapters.** Each provider is an adapter declaring its auth kind, its transport (`mcp` |
  `api`) with the measurement behind it, scopes, and its sync capabilities by depth level. An adapter that cannot
  authenticate reports `unmeasurable`, never `connected`.
- [ ] AC5 — **Measured status everywhere.** Every `connections` row carries last attempt, last success, last error
  and status (`connected` / `expired` / `error` / `never_synced`). `ConnectedServices.svelte`'s hardcoded
  `mcpStatus = "connected"` is removed.
- [ ] AC6 — **First adapters.** Upwork ([[T441]]) first; then GitHub as a data connection (decision: **GitHub App**
  recommended, for fine-grained repo permissions and a higher rate limit). LinkedIn moves onto the framework and
  its bespoke routes are deleted (clean cutover).
- [ ] AC7 — **UI in the [[T439]] shell:** Me → Account & security → Connected accounts; Org → Integrations → Sync
  health; Admin console → all connections.
- [ ] AC8 — Tests: the state/PKCE round-trip; tampered or replayed state refused; tokens never returned to a
  browser session; refresh-failure → `expired`; RLS shows a member only their own connections (`SET LOCAL ROLE`
  inside a transaction).

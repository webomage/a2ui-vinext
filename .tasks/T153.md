## 🔴 SECURITY — the current risk profile is the WRONG SHAPE for auditing client code

The existing `[risk_profiles.w0m]` is a **denylist over the whole filesystem**:

```toml
level = "supervised"
workspace_only = false
allowed_roots = ["/"]
forbidden_paths = ["/etc","/root","/home","/usr","/bin", … ,"~/.ssh","~/.gnupg","~/.aws","~/.config"]
```

`allowed_tools` additionally grants `shell`, `file_write`, `file_edit`, `git_operations`,
`http_request`, `browser`, and `spawn_subagent`.

**For the owner's own supervised use on their own machine that is a defensible posture.** For
**part 4 — running an agent over a CLIENT's source tree — it is inverted:**

- **`allowed_roots = ["/"]` with `workspace_only = false`** means the reachable set is *everything
  except* an enumerated list. Auditing untrusted third-party code under a denylist means any path
  the list forgot is in scope — and this estate's whole organising finding is that **enumerations
  are wrong in the direction of omission.**
- `forbidden_paths` covers `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config` — but **not** `~/.zeroclaw`
  itself (which holds `.secret_key`), **not** `~/.infisical`, **not** the w0m repos, and **not**
  `~/.claude`.
- `http_request` + `shell` + `file_write` in the same profile is an exfiltration path if the audited
  code can influence the agent (a prompt-injection surface — client code is untrusted input).

⇒ **A client-audit profile must be a separate, allowlist-shaped profile** (`workspace_only = true`,
`allowed_roots` = the project dir only, no `http_request`/`git_operations`/`spawn_subagent`), **not
a tweak of the w0m one.** 🔴 **This is the ticket's first real decision and it gates part 4.**

## The two integration surfaces (part 2 — bidirectional)

ZeroClaw exposes both directions already; nothing needs inventing:

| Direction | Surface | Note |
|---|---|---|
| **w0m → zeroclaw** | `zeroclaw acp` — ACP server, **JSON-RPC 2.0 over stdio** | The natural fit; same shape as an MCP stdio server, so it slots into the existing agent-tooling model |
| **zeroclaw → w0m** | `zeroclaw gateway` (webhooks/websockets) + its `skills` subsystem | ⚠️ Per [[T150]] AC7 the boundary holds: **MCP/ACP is agent-facing, `just`/CLI automation-facing.** A gateway is a listening server — treat it as an outward-facing surface needing an explicit auth story |

Also present and relevant: `daemon`/`service`/`cron` (autonomous scheduling), `estop`
(emergency stop), `eval` (evaluation harness), `migrate` (import from other agent runtimes),
`sop`, and `memory` with a markdown backend.

## Acceptance criteria

- [ ] **AC1 — the install config becomes a tracked, generated artifact.** `~/.zeroclaw/config.toml`
      is hand-edited and untracked today. Move the canonical definition into the estate and generate
      the installed file. 🔴 **Secrets must NOT enter version control** — `~/.zeroclaw/.secret_key`
      exists, and provider keys belong in Infisical per the standing rule, injected at run time.
      ⚠️ Also clean up the stale `.config.toml.swp`; confirm first whether it holds unsaved edits.
- [ ] **AC2 — omlx is the configured provider.** `[providers.models]` is empty. Wire the live MLX
      server (`127.0.0.1:8888`, OpenAI-compatible) as an `OpenAiCompatible` provider.
      🔴 **Carry [[T152]]'s measured finding across: Gemma-4-via-MLX returns `tool_calls: null`,
      emits a bare `<call:…/>` text token, and FABRICATES the result.** ZeroClaw is an *agentic*
      runtime, so a model that cannot emit structured tool calls will either do nothing or invent
      outcomes. **Test tool-calling through zeroclaw before declaring this done**, and decide the
      same three options T152 AC5 lists (restrict to text tasks · translation shim · frontier model
      for agentic work).
      ⚠️ Use `127.0.0.1`, never `localhost` — [[T152]] measured an IPv6 `::1` fallthrough breaking
      exactly this class of local connection.
- [ ] **AC3 — w0m → zeroclaw over ACP.** Wire `zeroclaw acp` (JSON-RPC 2.0 over stdio) as a callable
      surface, declared in `.w0m/sdlc.json → mcp` alongside the other agent-facing servers.
- [ ] **AC4 — zeroclaw → w0m.** Decide the direction's mechanism (gateway webhooks vs the `skills`
      subsystem consuming `wom7skills`) and record why. ⚠️ A gateway **listens** — it needs an auth
      story before it runs anywhere. Do not open it by default.
- [ ] **AC5 — 🔴 a SEPARATE allowlist-shaped profile for client audits.** `workspace_only = true`,
      `allowed_roots` = the client project only, and **no** `http_request` / `git_operations` /
      `spawn_subagent` / `browser`. **Do not derive it by editing the `w0m` profile** — the two have
      opposite trust models. 🔴 Prove it RED: from inside the sandbox, attempt to read
      `~/.zeroclaw/.secret_key`, a w0m repo, and `~/.infisical`, and assert each is refused.
- [ ] **AC6 — sandboxed client-project audit, end to end.** Spawn a sandbox over a real client
      project and produce an audit. ⚠️ **This is [[T111]]'s "shallow = code-only audit in an isolated
      sandbox" arriving from another direction — reconcile with `wom7sec` rather than building a
      second audit toolchain.** Treat audited source as **untrusted input**: it can attempt prompt
      injection, which is why AC5's tool restrictions are a prerequisite, not a polish step.
- [ ] **AC7 — health is a number.** A `just` recipe reports: zeroclaw version, config drift
      (tracked vs installed), provider reachability, active risk profile per agent, and whether any
      profile grants filesystem-wide roots. ⚠️ Per [[T149]]'s spec it must **name what it
      enumerated**.
- [x] **AC8 — decide zeroclaw's relationship to the retired OpenClaw.** ✅ **DECIDED 2026-08-10 by
      the owner: zeroclaw IS the successor.** OpenClaw was uninstalled the same day — `openclaw-cli`
      removed via brew (423.8 MB), `/Applications/OpenClaw.app` moved to Trash, and the
      `ai.openclaw.gateway` LaunchAgent already quarantined by [[T196]]. The live surface was
      migrated, not renamed:
      - `wom7api/justfile` — `openclaw-*`/`just oc` → `zeroclaw-*`/`just zc`, driving
        `zeroclaw service start|stop|restart` and `zeroclaw status`.
      - `wom7api/scripts/healthcheck.py` — probe moved 18789 → **42617** (still non-blocking).
      - `wom7api/scripts/oc_daemon.py` — **deleted**; `zeroclaw service` replaces it wholesale
        (it wrapped `launchctl bootstrap ai.openclaw.gateway`, which no longer exists).
      - `wom7ext/.../mcpTools/agentBridge.ts` — tools renamed `openclaw_*` → `zeroclaw_*`.
      ⚠️ **It is NOT a drop-in, and this is what AC1/AC5 have to absorb** — verified against a
      running gateway, not assumed: `POST /chat` **does not exist** (`GET /api/chat` → 404 "No
      backend route matched"); chat is a **WebSocket upgrade on `/ws/chat`**; `GET /sessions` is now
      `GET /api/sessions`; every `/api/*` route returns **401 "pair first via POST /pair, then send
      Authorization: Bearer <token>"**; `zeroclaw models set` is process-wide and takes **no
      `--agent` flag**; and the agent aliases changed from main/admin/architect/consultant to the
      single configured `w0m`.
      🔴 **This is exactly the auth story AC1 flags, and it now blocks working code.**
      `zeroclaw_agent_ask` is migrated but **deliberately not functional**: wiring it needs a paired
      bearer token, and minting one (`zeroclaw gateway get-paircode --new`) grants a device
      persistent gateway access — an owner action, not an agent one. The tool reports that blocker
      instead of guessing an unverified WebSocket envelope. `zeroclaw_list_sessions` is fully
      implemented against the verified `/api/sessions` route and works as soon as a token exists.
      **`~/.openclaw` was NOT deleted** — examined (see [[T196]] AC4: 6 more copies of two plist
      secrets, all dead) and left in place, because it also holds four agent workspaces and session
      transcripts. Removing it is an owner call.

## Definition of Done

The zeroclaw config is generated from a tracked source with no secrets committed; omlx is wired and
its tool-calling limitation is measured rather than assumed; both integration directions work with a
recorded auth story; a separate allowlist-shaped profile exists for client audits and is proven to
refuse the paths that matter; one real client project has been audited inside a sandbox, reconciled
with `wom7sec`; and a health recipe reports config drift and any filesystem-wide grant.

# T347 — a bug display, routed by hat

## Summary

Owner ask, 2026-09-12: *"let's read and process w0m _in and also we need to display for w0m qa
hat on project (if no dedicated set on specific project then for PM) and also for client side
reported via jams bugs."*

Two parts, both grounded against live state before drafting:

1. **A display of bugs, routed per-project to whoever holds the QA hat — falling back to PM when
   a project has no QA hat wearer.** The routing primitive already exists (`project_roles` +
   `hats` + `worn_hats`); nothing here is new schema. What's missing is (a) something to route —
   a bug — and (b) the read/routing view itself.
2. **Client-side bugs reported via Jam.dev surfaced in the same display.** Jam recordings (via the
   `jam` MCP) and/or the in-flight `BugReportWidget` (which already captures a Jam link) are the
   two candidate sources.

## What is actually there, measured 2026-09-12

**The QA/PM hat fallback is already true in the data, not hypothetical:**
`project_roles` carries per-project `qa-engineer` and `pm` slugs today. Queried live (`beta`,
read-only):
- **Artemio** (`a7e31002-2660-4000-8000-000000000001`, the project the Jam bugs below are against):
  `qa-engineer` role exists with **zero active wearers**; `pm` is worn by **casualuser@gmail.com**
  and **aleksei@webomage.com**. This is exactly the fallback case the owner described, already
  live — a routing view built today would correctly resolve Artemio bugs to those two PMs.
- **BridgeRoad MVP** (`b7100002-3100-4000-8000-000000000001`): neither `qa-engineer` nor `pm` is
  staffed (only `tech-lead` is worn, by casualuser@gmail.com). A naive "QA else PM" rule has
  nowhere to land here — the display must handle **unrouted**, not just the two-tier fallback.
- **Featherglass, Kayse.ai, Marketing Site Rebuild (Demo), Meetocean.ai, TheorQL**: zero
  `project_roles` rows at all. Same unrouted case.

**There is no bug data model anywhere in the schema.** No `bugs`/`bug_reports`/`defects` table,
no ticket for one, no `/api/bug-report` route in any repo (checked all three: `web`, `cp`, `api`).

**`design-system/components/domain/BugReportWidget.jsx` + `.prompt.md` are untracked** (`git
status` → `??`), authored by a different concurrent agent/process — **not this ticket's to finish
or claim**. It already POSTs `{title, description, severity, jamUrl, reporter, appName,
diagnostics}` to `/api/bug-report`, and its success copy claims *"Dispatched to Telegram managers
with system diagnostics"* — a backend that does not exist yet. Whether this ticket builds that
missing backend, or a separate ticket already covers it, is an open question for the owner (see
Acceptance criteria).

**Jam MCP, 4 unfiled recordings today** (`folder: null`, all by aleksei@webomage.com, all against
the live `artemioquierocomer.mx`):
- *"Bug: Mixed ES/MX Flag Style on Mobile Viewport"* (`1e275dba-9b69-49cc-8a22-cbf5115b23aa`) — the
  only actual bug-report candidate of the four. Its `analyzeVideo` pass didn't narrate the
  flag-style defect the title claims; the 2 captured click events hit rounded-full,
  glow-drop-shadow buttons (`scale-105 hover:scale-120`), a shape consistent with a
  flag/language toggle — plausible, not confirmed. Needs a screenshot/manual look before it is
  treated as a proven defect.
- The other 3 (*"Live Menu Dish Cards Visual Proof"*, *"Language Hydration & Search
  Verification"*, *"Jam CLI Health Check"*) are verification/proof recordings (menu walkthrough,
  test-suite run, migration/deploy log) — not bug reports, and out of scope for a bug display.

## Acceptance criteria

- [ ] AC1 — **Routing rule implemented as a query, not a UI assumption**: per project, prefer
      active `qa-engineer` wearer(s); if none, fall back to active `pm` wearer(s); if neither
      exists, the bug shows as **unrouted** rather than being silently dropped or misassigned.
      Prove it resolves correctly for the two measured cases above (Artemio → PM fallback,
      BridgeRoad → unrouted).
- [ ] AC2 — **Decide and record the bug data model** (new `bug_reports`-shaped table vs. reusing
      an existing surface) via a real migration, scoped to what this ticket needs — not a
      speculative general-purpose issue tracker.
- [ ] AC3 — **Decide the `BugReportWidget`/`/api/bug-report` ownership question explicitly**:
      either this ticket builds the missing backend the widget already assumes (title, description,
      severity, jamUrl, reporter, appName, diagnostics → the bug_reports table), or it is confirmed
      to be a separate in-flight ticket and this one only consumes the eventual table — write down
      which, don't leave it implicit.
- [ ] AC4 — **The display exists** (CP admin surface, alongside the existing
      `MyProjectHats.svelte`/`HatSwitcher.svelte` pattern) showing bugs grouped/routed per AC1,
      with an explicit "unrouted" state visible rather than hidden.
- [ ] AC5 — **Jam-sourced bugs are ingestible**, at minimum the one real candidate found this
      session (the flag-style jam) — either via a manual/ops action that files a Jam recording as
      a bug row, or an automated path if AC2/AC3 make one cheap. Out of scope: filing the 3
      non-bug jams as bugs.
- [ ] AC6 — **The flag-style jam's actual defect is confirmed or refuted** (screenshot/manual
      check), not carried forward as an unverified AI summary.
- [ ] AC7 — **A probe proves the routing live**, not just in a migration: querying the display (or
      its underlying API) for Artemio returns the two PM wearers; querying for BridgeRoad returns
      unrouted.

## Definition of Done

A bug filed against a project resolves, by a real query over `project_roles`/`hats`/`worn_hats`,
to that project's active QA hat wearer(s), or its PM hat wearer(s) if QA is unstaffed, or an
explicit unrouted state if neither is staffed — proven live for at least one project in each of
those three states. Client-reported Jam bugs are visible in the same display, and the
`BugReportWidget`/`/api/bug-report` ownership question is answered in writing, not left implicit.

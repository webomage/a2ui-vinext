# T249 — The public chat has no conversation memory — anon cannot read `chats`

## Summary

The public AI consultant reads its own conversation history with an **anon-role** client, and anon
cannot read the `chats` table. So every turn starts from nothing: the visitor's previous messages
are written, and never read back.

**Measured 2026-08-21** by [[T246]] AC5's `just anon-reader-check`:

| probe | result |
|---|---|
| `chats` as **anon** | **0 rows** |
| `chats` as **service_role** | **200 rows** (limit 200 — the table is not empty) |

`_shared/chat-core.ts:109-114` is the read — the replay window, `session_id`-scoped, last 16 turns,
with [[T20]]'s poison filter applied on top:

```ts
const { data } = await supabase
    .from('chats')
    .select('role, content, metadata')
    .eq('session_id', options.sessionId)
    .order('created_at', { ascending: false })
    .limit(16);
```

`_persistChats` writes with the **same** client. Every public caller resolves to `anon`: the widget
sends `Authorization: Bearer <ANON_KEY>`, so the forwarded JWT *is* the anon key.

🔑 **It was found by a gate, not by a person, and that is the point.** Nothing about the running
system looks wrong — the chat answers, and an empty history is indistinguishable from *"this is the
first turn"*. The same class as [[T121]] (a conversion leg dead behind a healthy-looking surface),
except here no error is even raised.

⚠️ **Not the same defect as [[T246]]**, which is why this is its own ticket: T246 was a table closed
by a migration whose census recorded the reader. `chats` was never opened to anon in the first
place — the feature was written against a permission it never had. Same symptom, different cause,
different fix.

## The error is swallowed, for the third time in this area

`const { data } = await …` — **`error` is discarded**. So *"RLS returned nothing"* and *"there is no
history yet"* are the same value. That is:

1. [[T198]] AC1's finding in `portal.astro` (`{ data }` without `error`, three defects hidden),
2. my own first version of T246's RPC call, corrected the same day, and
3. this.

⇒ Whatever the fix, it must **read the error**. A history read that silently returns empty is how
this stayed invisible while the table filled up to at least 200 rows.

## Acceptance criteria

- [x] **AC1** — ✅ **DONE 2026-08-22 — GREEN after the deploy, and it was RED before it.**
      `just public-chat-check` **4/4** (was `3 passed, 1 failed`); all six steps of *"Turn 2 sees
      turn 1"* pass, and turn 2 hands back `ORANGE-PELICAN-7`.
      🔑 **Two turns, not one, and that is the whole design.** A single-turn assertion cannot catch
      a broken history read, because the first turn legitimately has no history — which is exactly
      how a 100% memory failure stayed invisible while `chats` grew to **4,168 rows across 328
      sessions, 219 of them multi-turn**. Every one of those follow-ups was answered blind.
      ⚠️ The probe sends `x-session-id` deliberately: without it the server keys the conversation on
      the visitor's IP and history is **not** replayed, so a probe that omitted the header would
      assert the wrong contract and pass while the widget stayed broken.
- [x] **AC2** — ✅ **DECIDED 2026-08-22 (owner): server-side memory stays, read with the SERVICE
      client, and ONLY for a session id the client supplied.** `chats` stays closed to anon —
      the fix is to stop asking anon to read it, not to grant it.
      🔴 **Measuring the precondition eliminated two of the four options outright.** `session_id`
      is `web:<visitor IP>` on **318 of 328** stored sessions, because only `apps/web`'s widget
      sends `x-session-id`; the widget's own id is `web:${crypto.randomUUID()}` in sessionStorage
      and has been since 2026-07-05, but it accounts for just **10 sessions / 38 rows**. An IP is
      neither secret nor per-person, so a **definer RPC keyed on `session_id`** and a **scoped
      SELECT policy** were not privacy-preserving designs at all — they would hand one visitor
      another's transcript and pool everyone behind a single NAT into one conversation. Not
      hypothetical: **12 sessions span more than a month**, the largest holding **211 turn-pairs**.
      ⇒ `chat-core.ts` now gates the replay on `options.sessionIdFromClient === true`, so
      IP-derived conversations are **never** replayed. That is **stricter than the intended
      behaviour**, deliberately: the broken read has been acting as a privacy control, and turning
      it on naively would have been a disclosure rather than a feature.
      ⚠️ The gate's second arm — `|| !!options.supabaseClient` — preserves what the authenticated
      CP surfaces have today rather than regressing them. It is **[[T251]] AC3's** business, and
      removing it is that ticket's exit condition.
- [x] **AC3** — ✅ **DONE 2026-08-22.** The read destructures `error` and logs it distinctly —
      `[chat-history] READ FAILED — answering with NO memory` plus the scope, the client, whether
      the id came from the client, and the message. A permission failure and an empty history are
      no longer the same value.
      🔑 **Logged, not thrown**, on purpose: a history failure must degrade *memory*, not take the
      chat down. The real guard against a silent regression is AC1's two-turn probe, not the log.
      ⚠️ **The session id is never logged** — it may literally BE the visitor's IP. Its *length*
      is, which is enough to tell a UUID id from an IP fallback.
- [x] **AC4** — ✅ **DONE 2026-08-22 — verified live, and it had genuinely never run here before.**
      A three-turn public session where turn 1 was engineered to draw a tool-absence refusal:

      | # | role | `replayable` | signature | filter |
      |---|---|---|---|---|
      | 1 | user | — | — | KEEP |
      | 1 | assistant | **false** | **matched** | **DROP** |
      | 2 | user | — | — | KEEP |
      | 2 | assistant | true | — | KEEP |
      | 3 | user | — | — | KEEP |
      | 3 | assistant | true | — | KEEP |

      **6 rows received where it previously received 0**, exactly one dropped — and that one is
      caught by **both** mechanisms independently, the metadata tag *and* the substring signature,
      which is a redundancy worth knowing holds.
      🔑 **Turn 2 did not repeat the refusal** (it answered with a full discovery response), and
      **turn 3 recalled `BLUE-HERON-4` from turn 1** — so the user row survives while its assistant
      pair is filtered. That asymmetry is the behaviour to rely on, and it is now observed rather
      than reasoned about.
      🔴 **What this does NOT establish, and [[T20]] already says so:** the classifier has **zero
      tests** — a 5-pattern substring blocklist gating a live lead funnel. T20 records that gap and
      the exact obligation (5 positives, the empty-answer case, and the negative case a legitimate
      security refusal must satisfy). ⚠️ Not folded in here: the predicate cannot be unit-tested
      where it sits, because importing `chat-core.ts` pulls `@vercel/oidc` which needs
      `--allow-sys` that `just deno-test` deliberately withholds — it needs its own module, the
      `chat-handoff.ts` pattern, and that changes the bundle just verified live.
- [x] **AC5** — ✅ **DONE 2026-08-22 — `chats` clears and `anon-reader` is BLOCKING** (0 broken,
      1 acknowledged). 🔑 **It needed two fixes and neither was sufficient alone:** ① the read left
      anon, and ② the gate stopped classifying an anon **WRITE** as a read. `_persistChats` does
      `supabase.from('chats').insert([...])`, which the matcher counted as a reader and then failed
      because anon sees 0 rows through RLS — **a finding no code change could ever have cleared.**
      The insert works: all four rows of the live two-turn probe landed under the anon key, because
      the INSERT policy checks content shape and nothing else.
      📉 Side effect worth recording: dropping write call sites **halved the unresolved-receiver
      noise floor, 238 → 139**. 9 new probes, 24 total.
- [x] **AC6** — ✅ **N/A, and that is the outcome not a dodge: the fix needs NO DDL.** Keeping
      `chats` closed to anon means there is no migration, nothing owner-gated, and nothing waiting
      on [[T248]] — which is closed anyway. The only owner action this ticket has is the
      **deploy** (`just deploy-agent-consultant`), which is outward-facing rather than schema.

  ticket demanded.** `just public-chat-check` 4/4, `anon-reader` green and blocking, no migration
  needed, nothing left owner-gated.
- 🔑 **A gate found this, on its first live run, in a system nobody thought was broken** — and the
  fix it led to is *stricter* than the feature it restored. Because 318 of 328 stored sessions are
  IP-keyed, the broken read had been acting as a privacy control; replaying those would have handed
  one visitor another's transcript. So memory came back for unguessable ids only, and IP-keyed
  conversations are now deliberately never replayed. **The bug and its safest fix pointed in the
  same direction, which is luck rather than design.**
- 📌 **Filed rather than folded in:** [[T251]] (the authenticated half — `chats.user_id` NULL on all
  4,168 rows, so `Users can view their own chats` has never matched a row, and its AC3 owns

  with [[T20]], which already records them.

- **2026-08-22** — 🔬 **The precondition this ticket flagged as unmeasured is answered: the writes
  land, the reads return zero.** 4,168 rows, and all four rows of a live two-turn conversation
  written under the anon key. Both SELECT policies key off `auth.uid()`, which is NULL for anon, so
  both evaluate to NULL and return nothing. *"Reads are broken"* — not *"reads and writes are both
  broken"*, which this ticket correctly said would need a different fix.
- 🔴 **AC1 and AC4 are the remainder and both wait on ONE deploy.** The two-turn scenario is

  bundle still reads with the anon client.
- ⚠️ **A trap for whoever writes more of these probes:** turn 1's answer in the manual run was a
  tool-absence refusal, which [[T20]] tags `replayable: false` and the filter drops. The **user**
  row carries no such tag and survives, so the codename is still replayed — but a probe asserting
  on the *assistant* half of turn 1 would fail for a reason unrelated to this defect.

- **2026-08-21** — filed from [[T246]] AC5's second finding, deliberately as its own ticket rather
  than folded in: T246 is a migration that closed a table whose reader was recorded, this is a
  feature written against a permission it never had.
- 🔑 **Worth stating plainly: a gate found this, on its first live run, in a system nobody thought
  was broken.** That is the return on AC5 — not the outage it was written for, which was already
  known, but the one that was not.
- ⚠️ **Unmeasured deliberately:** whether the **writes** land. `_persistChats` uses the same anon
  client and its result is unchecked, so `chats` may be accumulating from some other path entirely.
  The 200 rows visible to `service_role` prove the table is not empty; they do **not** prove the
  public widget is what filled it. Establish that before designing AC2, because "reads are broken"
  and "reads and writes are both broken" have different fixes.

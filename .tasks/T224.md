## 2026-08-16 — the wiring DEADLOCKED a real deploy. Root cause and fix.

🔴 **AC4's wiring was wrong in a way AC5's proof could not catch, and it cost a 20-minute stall on
a production deploy.** The owner ran `just deploy-all` from a real terminal; it sat in
`run_suites.py` for 20 minutes with no output. Chain:

```
just deploy-all → test → confirm-test → test_confirm_step.py → confirm_step.py deploy-web
```

`confirm_step.py` was **blocked reading the owner's terminal**, on a prompt `run_suites.py` had
captured — so it was invisible, and there is no timeout on that read. It would have waited forever.

**Why every prior run passed.** `confirm_step` tries **two** channels: `/dev/tty`, then stdin *when
`stdin.isatty()`*. Its probe suite ran only from non-interactive shells, where **neither** exists —
so the gate refused instantly, the suite went green in ~1s, and the interactive path was never
exercised. **I measured the tier at 169s from a non-TTY shell and wired it into a command humans run
from a terminal.** The environment was never the same one; the measurement was never valid for the
place it was used.

**Fix — in the probe, not the gate** (`test_confirm_step.py`):
- `run()` now passes **`start_new_session=True` AND `stdin=DEVNULL`**. Both are needed: the first
  kills `/dev/tty`, and an inherited terminal on fd 0 still satisfies the second channel — which is
  exactly why my *first* fix, which set only `start_new_session`, still hung (measured: 30s timeout,
  not a pass). A probe named *"no tty"* must **create** that condition, never assume the caller's.
- `pty_answer()` now uses **`pty.fork()`** rather than `Popen(stdin=pty)`. Handing a pty in as a file
  descriptor does nothing for `/dev/tty`, which resolves to the session's **controlling terminal**;
  `pty.fork()` performs the `setsid()`+`TIOCSCTTY` dance so the pty is genuinely the child's
  controlling terminal, and can never be the developer's.
- A 30s timeout, so this class of bug fails loudly instead of hanging.

**Verified in BOTH environments — the whole point:**

| | before | after |
|---|---|---|
| `test_confirm_step.py`, non-TTY | 16 passed | 16 passed |
| `test_confirm_step.py`, **real controlling terminal** | **hung 20 min** | **0.9s, 16 passed** |
| **full `just test`, real controlling terminal** | *(never run)* | **181s, 862 checks / 73 suites, all blocking passed** |

⇒ **AC5's "prove the wiring fails" was satisfied by a seeded break in a non-TTY shell — the same
blind spot.** A gate proven red in one environment is proven for that environment only. The full
tier has now been run the way a human actually invokes it.

## 2026-08-16 — the `?` check count was a blind spot, not a cosmetic gap

Owner asked why some suites report `?`. The answer turned out to be a real hole in the gate.

It also made the headline number unstable: the same tier reported **803** in the owner's deploy and
**862** in mine. The delta is exactly **59** — vitest's count — i.e. the total moved with output
*formatting*, not with what actually ran.

**Measured the real dialects across all 16 `?` suites** and taught the counter the common ones:
`✓`/`✗` line starts · `ALL PASS (24/24)` ratios · mypy's `Success: no issues found in N source

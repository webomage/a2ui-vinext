# T355 — Canonical 3-level epic tags replace ROADMAP §N notation

## Summary

Owner, correcting/escalating [[T353]]: *"so we have to get all epics 3 level tagged
`<tag1>_<tag2>_<tag3>` instead of "ROADMAP §13" f.e."*, then, confirming scope: *"this will be
gated schema for all tickets."*

T353 shipped `tag_family()`/`tag_matches()` as an **additive** convention — free-form tags, no
mass retag, `epic:` untouched. That undersold the ask. This ticket makes the hierarchical tag
**the epic reference itself**, replacing `"ROADMAP §N"` free text, and makes conformance a
**gated** (blocking), not advisory, part of ticket schema — closing the gap that
`project/scripts/epic_completeness.py` (which validates `epic:` against ROADMAP section numbers
today) currently only *reports* (exits 0 always) rather than *enforces*.

**Mechanism — one canonical 3-level tag per ROADMAP section, defined at the source.** Each
`## N. Title` header in `ROADMAP.md` gains a trailing `` `tag` `` marker (e.g.
`## 13. Platform Health, Tooling & Knowledge Infrastructure (P1, added 2026-07-12)
\`sdlc_tooling_platform\``). A ticket's `epic:` field then holds that tag directly
(`epic: "client_alfa_features"`) instead of `epic: "ROADMAP §33"` — self-describing, no lookup
document needed, and this **merges** `tasks_query.epic_key()`'s ROADMAP-§N roll-up and T353's
`tag_family()` roll-up into one mechanism instead of two parallel ones.

## Acceptance criteria

- [ ] AC1 — Owner confirms (or edits) the 34-section tag mapping above. Each `## N. Title` header
      in `ROADMAP.md` gains its canonical `` `tag` `` marker — the single source of truth, no
      separate lookup table.
- [ ] AC2 — `tasks_query.epic_key()` rewritten: derives the epic roll-up from the `epic:` tag
      string via the existing `tag_family()` (T353) instead of the `ROADMAP\s*§\s*(\d+)` regex —
      the two roll-up mechanisms merge into one.
- [ ] AC3 — `project/scripts/epic_completeness.py` rewritten: parses the canonical tag off each
      ROADMAP header (instead of `## N. Title` → section number) and validates every ticket's
      `epic:` resolves to one of the 34 canonical tags — same bidirectional guarantee (orphan
      tickets, tickets pointing at a nonexistent tag, sections with no open ticket, inconsistent
      spellings), new source of truth.
- [ ] AC4 — The epic-completeness check becomes **gated** (blocking, e.g. wired into
      `just ticket-schema-check` or pre-push) rather than advisory — closing the current gap where
      `epic_completeness.py` reports drift but always exits 0.
- [ ] AC5 — All ~240 existing tickets' `epic:` fields mass-retagged from `"ROADMAP §N"` free text
      to the canonical tag string, verified 1:1 (each ticket's original section number is
      recoverable from its new tag — no information lost in the conversion).
- [ ] AC6 — `project/templates/ticket.md`'s `epic:` field comment updated to show the canonical-tag
      form as the required example, replacing `"ROADMAP §13.2"`.
- [ ] AC7 — [[T353]]'s status notes corrected: its `tag_family()`/`tag_matches()` tooling is
      unchanged and still correct, but its "additive to `epic:`, not a replacement" framing is
      superseded by this ticket.
- [ ] AC8 — `cmd_overview()`'s separate "by EPIC" and "by TAG FAMILY" blocks merge into one rollup
      view, since `epic:` and namespaced tags now share the same mechanism.

## Definition of Done

`ROADMAP.md`'s 34 headers all carry a canonical tag; every ticket's `epic:` is one of those 34
tags (verified by the rewritten `epic_completeness.py`, now gating); `tasks_query.py`'s epic and
tag-family roll-ups are one mechanism; `just tasks overview` runs clean against the full queue with
a single unified epic/tag view; the five existing render/plan/progress/blocker/schema test scripts
still pass; committed with the ticket id.

# T513 — Resume Studio documents: preview and four defects

## Summary

Owner report, 2026-09-30, with a screenshot of `cp.webomage.com/me/profile/resume`: *"looks like 'View Markdown' is not
working, and for sure we need a preview for PDF as well."* The page lists each stored document as a card with Download,
Extract highlights, View Markdown, Set Primary and Delete. Reading the code against the screenshot gives four findings. The
first is a **hypothesis, not a reproduction**: nobody has yet watched the click fail in a browser.

## Findings (measured 2026-09-30)

1. **View Markdown probably works but shows its result where you are not looking.** `handleViewDocument`
   (`apps/cp/src/components/member/resume/ResumeStudio.svelte:868`) signs a URL, fetches the text and sets `previewingDoc`.
   The viewer is an **inline panel at line ~1800, above the document list** (the cards start near line ~2000), and nothing
   scrolls to it or focuses it. A click on a card near the bottom changes the page 200 lines above the viewport. A failure
   is no better: the error goes to `statusError`, rendered by the banner at line ~984, at the top of the component, also off
   screen. Either way the member sees nothing happen. The viewer also shows the **raw source** in a monospaced block, not
   rendered Markdown.
2. **There is no PDF preview.** The View button exists only for `.md` files (`ResumeStudio.svelte:2017`). PDFs offer
   Download only, and 11 of the 17 documents are PDFs.
3. **A request fails with HTTP 400 on every page load, and is swallowed.** Line 220 selects
   `.from("projects").select("id, name, description, stack")`, but `public.projects` has no `stack` column (baseline
   schema columns: id, name, description, blueprint_id, status, metadata, created_at, updated_at, access_scope,
   deleted_at, client_id, contract_id, host_org_id, client_org_id, gamification_enabled, slug; no migration adds one).
   PostgREST answers 400, the destructured `data` is null, and `projs` is silently dropped; line 286 then uses
   `p.stack || []`. This is the red console error in the screenshot.
4. **The action row overflows its card.** In the two-column grid at that width, "Set Primary" and "Delete" are clipped,
   and in the left column they overlap the right card's "Download". The buttons do not wrap.

## Acceptance criteria

- [ ] AC1 — **Reproduce first.** The click is reproduced in a browser (signed-in test member, local stack, live guard
  on) and the actual outcome is recorded: opens off-screen, or fails with a named error. The fix targets what was seen.
- [ ] AC2 — **Preview opens where the member is.** View opens in a dialog or drawer over the page (not an inline panel
  elsewhere), with focus moved into it and Escape to close. A failure shows its message inside the same dialog.
- [ ] AC3 — **PDFs preview.** A "View" button for PDFs opens the same dialog with the document rendered from a
  short-lived signed URL (5 minutes, as `openUrl` does today). The URL is never stored or logged. Verified by a component
  test plus a spec that opens a seeded PDF.
- [ ] AC4 — **Markdown is rendered, with Source available.** The dialog renders the Markdown safely (no raw HTML
  injection) and offers a Source toggle. Verified with a document containing a script tag and a link.
- [ ] AC5 — **No failing request on load.** The `projects` select no longer asks for a column that does not exist, or
  reads the right source. Probe: a component test that fails if any Supabase call in `loadProfile` returns an error, and a
  browser check with an empty console.
- [ ] AC6 — **Buttons wrap.** The action row wraps inside the card at 1280, 1024 and 390 px. Verified by screenshots read
  back, per the estate's rule to look at a screenshot before reporting on it.
- [ ] AC7 — **Errors surface where the action was.** Any failure of a card action shows next to that card or in its dialog,
  not only in the page-top banner.

## Open questions (recommended answer first, with weight)

1. **Dialog or drawer?** *Recommend a right-hand drawer*, so the card list stays visible. Weight: low; both fix the
   off-screen problem.
2. **How is a PDF rendered?** *Recommend the browser's built-in viewer through an `<iframe>` or `<object>` on the signed
   URL.* Weight: no new dependency and no bundle cost, but behaviour varies by browser, mobile Safari shows only the first
   page, and the signed URL must allow inline display. No frame restriction was found in the CP app's `_headers`, Astro
   config or middleware, but that is not proof the platform sends none; check in a browser. Alternative: `pdf.js`,
   consistent but a heavy dependency.
3. **Should a preview of someone else's document ever be possible?** *Recommend no.* The path is the member's own vault
   folder, enforced by storage policy, and the test should assert it.

# T67 — Rotate + purge leaked Supabase management PAT

## Summary

`wom7api/scripts/get_keys.py` has a hardcoded live-format `sbp_…` Supabase **management** PAT, tracked since 2026-01-26 (`b3d5c10`). No `.gitleaks.toml` rule catches the `sbp_` format, which is why it slipped past the hooks.

**Owner action (blocking): rotate/revoke the PAT in the Supabase dashboard and confirm it's dead.** Then: remove the literal from `get_keys.py` (read from env) or delete the one-off script; purge it from git history; add an `sbp_[a-f0-9]{40}` rule to `.gitleaks.toml` and propagate to all wom7 repos. NOT the same leak as the 2026-07-12 DB-superuser incident.

## Resolution (2026-07-17)

✅ **Owner rotated/revoked** the token (`sbp_8a54…`) plus all other classic PATs — verified **dead** (Supabase mgmt API now returns **403** for it).
✅ **Code:** `get_keys.py` reads `SUPABASE_ACCESS_TOKEN` from env; exits clearly if unset (`ddd644e`).
✅ **gitleaks:** `wom-supabase-management-pat` rule (`sbp_[a-f0-9]{40}`) added + propagated to all 6 wom7* repos (verified it fires on the leaked format).

**Blast-radius check:** git remotes are all SSH and gh CLI uses OAuth (`gho_`) — no git/gh breakage. `sync_github.py` uses the gh CLI, unaffected. The only classic-PAT consumers are two **manual** Supabase management scripts (`get_keys.py`, `sync_supabase_secrets.py`); neither is wired into `just deploy`, so automated deploys are unaffected.

**Optional, non-blocking follow-ups (not required to close):**
- Infisical still stores the dead `sbp_8a54…` under `SUPABASE_ACCESS_TOKEN` (403). Refresh it with a new token **only if** you still use `get_keys.py` / `sync_supabase_secrets.py`; otherwise consider deleting those one-off scripts. Local `dev_secrets.json` likely holds the dead copy too.
- History purge is now hygiene only (value is dead). Worth doing so `gitleaks detect` (full-history) stays clean under the new rule; pre-commit (staged-only) is unaffected. ⚠️ Don't force-push pre-rewrite local branches.

## 🔬 CORRECTION 2026-08-17 — the PAT is NOT dead, and this ticket is why an agent would think so

**Re-measured through `SUPABASE_ACCESS_TOKEN` as stored in Infisical today**, three calls, all
**HTTP 200**:

Every measurement in [[T229]] came through this token, both on 2026-08-16 and again today.

⇒ **Two claims above are false and are corrected here rather than deleted**, because the record of
what was believed matters as much as the fact:
- *"verified dead (Supabase mgmt API now returns 403)"* — it returns **200**.
- *"Infisical still stores the dead `sbp_8a54…` under `SUPABASE_ACCESS_TOKEN` (403). Refresh it…"*
  — the stored token **works**; there is nothing to refresh.

🔴 **The lesson, which is the durable part:** a recorded breakage has no expiry, and this ticket is
`done`, so nothing was ever going to re-check it. It had become an instruction to avoid a working
tool — and [[T229]] AC7 exists precisely because the next agent would have skipped the Management
API believing it dead. **Re-measure before acting on a recorded breakage.** Same shape as
[[T127]]'s AC6/AC7 being read as open months after they closed.

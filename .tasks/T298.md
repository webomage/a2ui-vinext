# T298 — an aligned count that includes repos nothing was applied to

## Why

`just deps-check` reports **"deps aligned across 5 repos (14 floors, 2 lockstep, pnpm 10.32.0)"**.
One of those five is `wom7skills`, and **not one of the 14 floors lands there**.

The mechanism is in the policy's own words: floors are *"Security floors as **pnpm.overrides**. Every
listed repo that **ALREADY has** this override must be >= the floor"*. A repo carrying **zero**
overrides satisfies that condition trivially — nothing to compare, so nothing fails. It is counted as
aligned because it is *listed*, not because anything was checked.

🔴 **This is not theoretical; it cost six vulnerabilities.** `deps-policy.json` has carried
`mermaid: ">=11.16.1"` for some time. `wom7skills/skills/mmd-validate/package-lock.json` sat at
mermaid **11.16.0** and dompurify **3.4.12** — 6 known vulnerabilities, 5 Medium and 1 Low, all
fixable — while `deps-check` reported that repo as aligned. Two reasons stacked: the lockfile is
**npm**, and floors are expressed as **pnpm** overrides; and the repo has no overrides at all, so the
"already has it" rule made its absence indistinguishable from compliance.

🔑 **The number is the defect.** "5 repos aligned" is read as *five repos were checked*. It means
*five repos were listed, and of the ones carrying an override, none was below its floor.* Those are
different claims, and only the first is what anyone acts on.

## What already exists (do not rebuild)

- **The floor system works where it applies** — [[T112]]'s `deps-policy.json` → `deps-apply` → pnpm
  overrides chased two advisories correctly earlier today (postcss-selector-parser, browserslist).
  This ticket is about its **reported coverage**, not its mechanism.
- **`osv-scanner` is the backstop that actually caught it**, per-repo in pre-commit. It found the six
  when the floor system had already reported clean, which is the right division of labour — but it
  only ran because a commit happened to touch that repo.
- **The vulns themselves are FIXED** (mermaid 11.17.2, dompurify 3.4.14, skill re-stamped). Nothing
  here is about those packages.

## Acceptance criteria

- [ ] **AC1 — 🔴 a repo where no floor lands must NOT be counted as aligned.** It needs its own state
      — *no floor applies* — distinct from *checked and compliant*. Reporting them as one is the
      estate's recorded shape where "never asked" reads as "asked and clean".
- [ ] **AC2 — the summary line says what it measured.** "5 repos" must mean five repos where the check
      had something to do, or say so: e.g. *"14 floors across 4 repos; wom7skills carries no overrides
      — no floor applies"*. A reader acts on that sentence and on nothing else.
- [ ] **AC3 — npm lockfiles are covered, or declared out of scope WITH A REASON.** Measured 2026-09-02:
      the estate's only **tracked** npm lockfile was the one that got hit. wom7web's 43 and wom7ext's 1
      are untracked vendored trees. So the scope is small and a deliberate "pnpm only, because X" is a
      legitimate answer — but it has to be written, not left as an accident of implementation.
- [ ] **AC4 — red probe: reintroduce the exact case.** Set a floor for a package that a declared repo
      carries only in an npm lockfile, and confirm the report does **not** call it aligned. Use
      `mermaid` and `wom7skills`, because that is the case that actually shipped.
- [ ] **AC5 — 🔴 the probe must fail before it passes.** A gate that has never been observed failing is
      the thing this ticket is about. Show the current code producing the wrong answer first.
- [ ] **AC6 — reconcile with `osv-scanner`'s division of labour.** osv found these and the floor system
      did not, which is fine — floors are preventive, osv is detective. State which is authoritative
      for what, so neither is trusted for the other's job.

## Definition of Done

`just deps-check` distinguishes a repo it checked from a repo it merely listed, and its summary line
states which. A repo carrying no overrides is reported as *no floor applies* rather than counted among
the aligned, so the number a reader acts on means what they think it means. npm lockfiles are either
covered by the floor mechanism or declared out of scope with the reason written down. The exact case
that shipped — a `mermaid` floor, an npm lockfile in `wom7skills` — is a probe that was observed
failing against the current code before it was made to pass. And the split between the preventive
floor system and detective `osv-scanner` is stated, so a green `deps-check` is never read as evidence
that a repo has no known vulnerabilities.

## Notes, traps and dependencies

- 📌 **Found 2026-09-02** while fixing the six vulns, which were themselves only visible because
  `osv-scanner` **errored** rather than passing. Earlier the same day, creating the estate workspace
  repo ([[T294]] AC2) put a parent `.gitignore` above every repo, and osv walks past a repo root where
  git does not — so it reported *"No package sources found"* estate-wide until the exclusions moved to
  `.git/info/exclude`. Two independent failures over the same six packages within one day.
- ⚠️ **Do not "fix" this by adding overrides to wom7skills.** That would make the count true by
  changing the subject, and leave the next repo with no overrides silently miscounted.
- 🔑 Related in shape, not in code: [[T130]]'s *callsite-drift*, and the estate's standing rule that a
  gate must have a state for **could not measure** that is distinct from **measured and clean**.

# T243 — the row that documents mismatched column counts has a mismatched column count

## Summary

Found 2026-08-20 while updating [[T228]]'s board row: a scripted edit failed its own assertion
because the anchor it expected (`| web(web) | `) was not there. **The row does not end with `|` at
all** — it stops mid-sentence at `AC11.`, having lost its **Repos**, **Ref** and **Status** columns.

🔬 **T228's row ends with the words *"board rows have **different column counts** (8/72 → 65/72)"*.**
That sentence is a finding from T228's own DoD audit, and the row carrying it has the wrong column
count. The defect is quoting itself.

**It is not one row. It is EIGHT** — and the eighth was mine, filed the same day. Measuring column
counts across the whole board (rather than scanning for a missing final `|`) found `T228` · `T230` ·
`T232` · `T234` · `T195` · `T174` · `T194` **and `T243` itself at 8 cells**: this ticket's own board
row contained the literal string `` `\| repos \| ref \| status \|` `` as prose, which splits into
extra cells. **The ticket about malformed rows had a malformed row, written by the fix's author,
within an hour of filing.** It is in the probe suite as a permanent case.

### 🔴 Cause — CORRECTED: nothing was lost, and my first description was wrong

**Filed as *"the rows lost their Repos, Ref and Status columns"*. They did not.** Reading the
truncating commit's own diff settled it — `c588ecc0` shows `-` at **6 cells terminated** and `+` at
**7 cells unterminated**: it **ADDED a cell** and dropped the closing `|`. Repos and Ref were intact
the whole time, sitting in the middle of the row where my `tail`-based look never saw them.

⇒ **I nearly "recovered" from git history what was never missing.** The recovery plan was proven
7/7 and was solving a problem that did not exist; had it run, it would have re-appended columns the
rows already had. **A truncated view of a row is not a truncated row** — and the check that caught
it was reading the DIFF of the commit that did it, not the current state.

**Two shapes, both text-preserving:**

| shape | rows | what it is |
|---|---|---|
| **7 cells, unterminated** | T228 · T230 · T232 · T234 · T174 | status prose appended in a cell BESIDE the marker (`… \| 🟡 \| ✅ AC7+AC9 DONE…`) |
| **6 cells, unterminated** | T195 · T194 | correct cell count, missing only the final `\|` |

For T228 the marker cell held a bare `🟡` and the 7th held the whole AC essay, so the fix is a
**merge**, not a recovery. ⇒ ~10 commits of status prose sat in a 7th cell and nothing noticed,
because nothing checked the shape.

### 🔑 Why no gate saw it, and why the impact is narrow

`tasks_query.py` builds both boards from the **ticket files**, never from these rows — so
`just tasks` renders a correct Repos/Ref/Status for T228 while the row itself is malformed. And
`tasks-bounds` counts rows and bytes, not columns. **The board of record is the one surface with no
validator**, which is the same shape as [[T228]] AC11 (a `set` that hid duplicates) and [[T240]]
(gates invisible to the drift detector): *the thing that measures does not look at the thing that
broke.*
⇒ Impact is **record integrity and human reading**, not ranking. That is why this is P2 and not P1.

### Recovery is proven, and one row needs care

All **7 of 7** were recovered from history by walking `git log -- TASKS.md` back to the last version
whose row ends in `|`. ⚠️ **Do not bulk-append the recovered last-three-columns.** For **T174** the
recovered *status* column is a **multi-paragraph essay**, and the current row already carries status
prose in its task column — a naive append duplicates it. The correct fix splits at the **task
column's historical end anchor** (for T228: *"Issue Types unavailable (org-only)."*) and re-inserts
`| repos | ref |` before the appended prose.

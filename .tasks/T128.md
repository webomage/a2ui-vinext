# T128 — wom7skills revision + documentation

## Summary

`wom7skills` has grown organically (25+ canonical skills + a partly-duplicated set of external ones
hand-placed in `wom7web/.agent/skills` / `.agents/skills`), but it lacks a **coherent quality bar
and architecture documentation**. Two deliverables:

1. **Revise all skills** — a consistency/quality pass over every skill in `wom7skills/skills/`:
   uniform `SKILL.md` frontmatter (name, description, trigger, license, provenance), sharp trigger
   descriptions, no stale/contradictory guidance (e.g. the `rbac-auditor` skill still describes the
   *old* 3-tier agent model + `project_acl`/`blueprint_acl` that T117 supersedes), dedupe near-twins
   (e.g. canonical `supabase-postgres` vs the imported `supabase-postgres-best-practices`), and a
   catalog of what we **use / master / import**.
2. **Document the architecture** — `wom7skills` currently has a README + a proposal but no
   architecture/flow docs: add an **architecture overview**, **flow diagrams** (mermaid: how a skill
   is authored → canonical → distributed → loaded by an agent; the w0m* sync vs external-`npx skills`
   paths; the T127 manager lifecycle), **charts** (skill families / provenance map), and **schemas**
   (the `.w0m/skills.json` manifest + lockfile schema, the `SKILL.md` frontmatter schema).

Complements **[[T127]]** (the manager machinery — TS, install/update, manifest) and **[[T24]]**
(the survey/import decision). This ticket is the **library-quality + docs** half; T127 is the
**tooling** half.

  `mmd-validate`, `cloudflare-workers`, and (added 2026-07-24) `rbac-auditor` +
  `supabase-postgres-best-practices`.
- **Known quality issues to fix:** the `rbac-auditor` SKILL.md references the pre-T117 agent model
  and ACL tables (stale); canonical `supabase-postgres` overlaps the imported
  `supabase-postgres-best-practices` (two Supabase skills — decide keep-both/merge); the
  `.agent`(21) vs `.agents`(61) split in wom7web is inconsistent; several external skills are
  hand-placed with no provenance/version (the drift T127 fixes).
- **✅ Resolved 2026-07-25 by [[T127]] R4 — do not re-derive:** the `.agent`/`.agents` split is gone.
  The singular `.agent/skills` is retired and empty, all 80 installed skills resolve through
  `.agents/skills`, and every one carries provenance in `.w0m/skills.json`. `skills.ts` now treats
  canonical as authoritative for any canonical skill that is installed (not just `w0m*`), so a fork
  is caught at commit time. Three findings landed in **this** ticket's lap instead:
  - **The near-twin list grew, then shrank.** `mcp-builder` was never a w0m skill: the installed copy
    is byte-identical to `anthropics/skills` (pinned by content diff, per T127 D6 — never by name),
    while canonical's similarly-named skill was a separate 18-line w0m note. That note is now
    **`w0m-mcp-builder`** — the name its own H1 always used — so the collision is resolved and both
    skills survive. AC3's dedupe work is unchanged for the two Supabase skills.
  - **Vendoring is incomplete for at least two imported skills** (AC3/AC1 territory): `mcp-builder`
    has 1 of the 10 files upstream ships, leaving the 4 `reference/*.md` its own text links to
    dangling; `webapp-testing` omits `LICENSE.txt` + `examples/`. Progressive disclosure is broken
    wherever this happened — worth a sweep across all 49 adopted skills, since T127 D4 established
    that 48 of them carry extra files.
    ✅ **THE SWEEP IS DONE — 2026-07-31, and "at least two" was a large understatement.** Owner
    folded the finding here after the T131 provenance audit hit the same class. Tool:
    **`just skills-vendor-audit`** (`wom7skills/scripts/audit_vendoring.ts`, offline by default,
    `--upstream` for class B, `--json`). Reproduce any figure below with it.

    | class | what it finds | result |

    🔴 **Neither class implies the other, and neither alone is the answer.** `webapp-testing` (2 of 6
    files) is invisible to A because nothing *links* its missing files; the 14 `marketingskills`
    skills are invisible to B because their companions live in a **shared repo-root `tools/` tree**

    **By upstream (class A):** 14 × `coreyhaines31/marketingskills` · 1 × `anthropics/skills`

    progressive-disclosure tree (core, advanced, frameworks, CI) is absent while the index still
    advertises it.

    ⇒ **The remediation is NOT one shape.** `playwright-best-practices` and `mcp-builder` are plain
    incomplete copies — vendor the rest of the directory. The 14 marketingskills ones need a
    **decision**: vendor the shared `tools/` tree once at a path `../../tools/` resolves to, or
    accept the links as dead and strip them. Stripping is what was done to
    `observability-and-instrumentation` at import (T131 AC3) and it is the worse option — it
    converts a visible defect into a silent capability loss.

    🔬 **Two probe traps, recorded because they nearly landed the wrong number** (and are now

    the first sweep reported **0 dangling across 74 skills** because its pattern required the path to

    could never match; the fix then produced a **false positive** by reading a URL path quoted in a
    table (`/features/analytics`) as a broken file link, which is why a file extension is required.
    A probe that cannot fire reports a clean estate.
  - **Canonical `skills/w0m/` is not one skill.** It holds 13 `w0m-*` sibling skills plus a
    `w0m-e2e-workspace` eval scratch dir nested inside it, none ever deployed. `skills.ts` excludes

- **Diagram tooling exists:** `mmd-validate` validates ```mermaid fences headlessly — reuse it for

## Acceptance criteria

- [ ] **AC1 — skill-quality pass.** Every `wom7skills/skills/*/SKILL.md` has consistent frontmatter
      (name, description, trigger, license, provenance/source) and a sharp trigger description; a lint
      or checklist enforces the shape.
- [ ] **AC2 — stale content fixed.** The `rbac-auditor` skill is updated to the T117 model (drop the
      3-tier agent / `project_acl`/`blueprint_acl` specifics; keep the fail-closed/IDOR/RLS
      principles); any other skill contradicting current architecture is corrected.
- [ ] **AC3 — dedupe + catalog.** The two Supabase skills are reconciled (merge or clearly
      differentiate); a **skills catalog** (`docs/CATALOG.md` or similar) lists every skill with
      use/master/import status and provenance — the deliverable [[T24]] also calls for.
- [ ] **AC8 — complete the vendoring** 🆕 **2026-07-31, measured — the sweep is already done, this is
      the remediation.** `just skills-vendor-audit` currently reports **16 skills / 140 dangling
      companion links** (class A) and **11 skills short of upstream** (class B); see the measured
      block above for the full table and the per-upstream split. Done when the audit is **green in
      both classes**, or every remaining finding carries a recorded decision.
      - **Plain incomplete copies — just vendor the rest:** `playwright-best-practices`
        (1 of 59 files; **all 58** of its links dead), `mcp-builder` (1 of 10; 4 dead),
        `webapp-testing` (2 of 6 — class B only, nothing links its missing files).
      - 🔴 **The 14 `coreyhaines31/marketingskills` skills need a DECISION, not a copy.** Their
        companions are a **shared repo-root `tools/` tree** (164 upstream paths: `tools/REGISTRY.md`
        + `tools/integrations/*.md`) linked as `../../tools/…`, i.e. from *outside* each skill's own
        directory. Per-skill vendoring cannot satisfy those links. Either vendor the shared tree once
        at a path `../../tools/` resolves to, or strip the links — but **stripping is the worse
        option**: it converts a visible defect into a silent capability loss, which is exactly what
        was done to `observability-and-instrumentation` at import ([[T131]] AC3, 91 lines lost with
        no trace).
      - ⚠️ **Do not let a green class A stand in for completeness.** The two classes are disjoint in
        both directions — see the block above. The audit's default run says so in its own output.
      - Ties AC1 (frontmatter/provenance shape) and AC3 (the catalog should state, per skill, whether
        the vendoring is complete). Companion-integrity for *canonical* imported units is already
        gated in `wom7skills/version.ts` ([[T131]] AC3); this AC covers the **consumer's adopted
        tree**, which that gate does not reach.
- [ ] **AC4 — architecture doc.** `docs/ARCHITECTURE.md` (or the README) explains the canonical store,
      the w0m* vs external distribution paths, the plugin install (`install.ts`), and the T127 manager.
- [ ] **AC5 — flow diagrams (mermaid).** At least: (a) skill lifecycle author→canonical→distribute→load;
      (b) w0m* sync path vs external `npx skills` path; (c) the T127 install/update/check flow. All
      pass `mmd-validate`.
- [ ] **AC6 — schemas documented.** The `.w0m/skills.json` manifest + lockfile schema and the
      `SKILL.md` frontmatter schema are written up (a JSON Schema + prose), referenced by T127.
- [ ] **AC7 — provenance chart.** A families/provenance chart (which skills are w0m-native vs
      imported-from-skills.sh vs persona) so the library is legible at a glance.

## Definition of Done


Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
every `wom7skills/skills/*/SKILL.md` has consistent frontmatter and passes the quality pass, `rbac-auditor` matches the T117 model rather than the retired one, the duplicate Supabase skills are reconciled, and vendoring is complete. The documentation half is what makes it durable: an architecture doc explaining the canonical→distributed path, mermaid flows for the skill lifecycle, the manifest + lockfile schemas written down, and a provenance chart separating w0m-native from imported. ⚠️ Stale skill content is the real hazard here — a skill describing a superseded model is followed confidently by whoever loads it.

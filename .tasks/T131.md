# T131 — Enforce the w0m version schema across build/deploy automation and skills

## Summary

w0m has a **required** release version schema — `YYYY.MM.DD-<unixtimestamp>` (ROADMAP §4) — but it
is applied in exactly one place and verified nowhere. Owner ask 2026-07-25: **skills must be
versioned themselves**, the **SDLC build/deploy `just` automation must use the timestamp schema**,
and conformance must be **checked by `sdlc-doctor`** (plus an audit of which other tools should call
it). This is the versioning-dimension sibling of [[T130]] (per-stack tool enforcement) and
[[T112]] (dependency floors): a declared standard that nothing mechanically enforces drifts.

🔴 **THE 2026-07-25 AUDIT BELOW WAS WRONG AND IS CORRECTED IN PLACE.** It was recorded as *measured,
do not re-derive*. Re-deriving on 2026-07-26 — because AC1 needed the exact producer list — found it
had **enumerated one repo and reported a total**, the same failure mode [[T149]] is organised around.
There were **three** orphaned producers in **three** formats, not one. Corrected table:

| Format | Where | Conforms |
|---|---|---|
| `YYYY.MM.DD-<unixtimestamp>` | `wom7api/justfile:15` → `deploy_version`, consumed by 7 `deploy-*` recipes + `_log-deploy` | ✅ the standard — now also `just version`, the single producer |
| `vYYYY.MM.DD-HHMMSS` | `wom7api/scripts/bump_version.js` (**11 lines** ✅ as recorded) | ❌ `v` prefix + local wall-clock instead of a unix timestamp — orphaned, zero callers. **DELETED 2026-07-26** |
| `YYYY.MM.DD-<unixtimestamp>` **written into `package.json`** | 🆕 `wom7web/scripts/bump_version.js` (**48 lines** — the audit's "11 lines" described the *other* copy) | ❌ the string is the right *shape* but it is written where it is **illegal**: semver forbids leading zeroes, so the padded month invalidates package.json. Also writes a `public/version.json` that does not exist. Orphaned. **DELETED 2026-07-26** |
| 🆕 `YYYY-MM-DD-<unixtimestamp>` (hyphens) | 🆕 `wom7web/scripts/deploy_web.py` | ❌ a **fourth** format, used as a *deploy identity* (`Starting Deployment: {version}`, logs under the retired singular `.agent/deployments/`). Orphaned, last touched 2026-05-22. **DELETED 2026-07-26** |
| semver-ish, ad hoc | `package.json` (`wom7web` 0.0.1 · `wom7api` 1.0.0 · `wom7skills` 0.1.0 · `wom7cfworkers` 0.0.0 · `wom7ext` none); skill `metadata.version` (`"1.0"`/`"2.0"`) | ❌ |

⇒ **The lesson is not "the audit was sloppy".** It searched `wom7api` because that is where the
producer of record lives, and reported an estate-wide count. **A count is only as wide as the set it
enumerated** — which is why `version-check` now prints its scan set on every run.

**Skills are the biggest gap** (the owner's first point). ⚠️ **Re-measured 2026-07-25 — read the
denominator note before quoting any number from this paragraph.**

| Measurement | Count |
|---|---|
| top-level dirs in `wom7skills/skills` | **27** |
| `SKILL.md` files (recursive — the real corpus) | **40** |
| `SKILL.md` files declaring a version (any indent) | **11** |
| ⇒ unversioned, per top-level dir | **16 of 27** ← the original claim, arithmetically correct |
| ⇒ unversioned, per actual corpus | **29 of 40** ← the honest number |

Both are true of different denominators. The original *"16 of 27"* was **not wrong**, it just
counted directories; nested skills are invisible to it.

🔴 **The fact that actually scopes this ticket is neither count.** All 11 versioned files declare an
**indented `metadata.version`** — **none** declares a top-level `version:` key. Of the 11, **10** are
`w0m-sdlc-*` carrying a hand-set two-component `"1.0"`/`"2.0"` (not valid semver, and not the w0m
schema), and the single three-part version (`supabase-postgres-best-practices` `"1.1.1"`) belongs to
an **imported** skill, so it is upstream's, not ours. Net:

> **Zero canonical skills carry a conforming `YYYY.MM.DD-<unixtimestamp>` version.**

Scope AC3/AC4 off that sentence — it is unambiguous and denominator-free.

🔴 **Trap: `.w0m/skills.json` has TWO version-ish fields.** They are not the same thing and
conflating them produces a confidently wrong audit:

| Field | Holds | Values |
|---|---|---|
| `version` | a **provenance label**, *not* a version | `unknown` ×56, `canonical` ×13, `vendored` ×1 (70 total) |
| `observed_version` | the real scraped version | present on **58 of 70**; absent on 12 |

So "how many skills are versioned?" has three defensible answers — 70, 58, or 11 — depending on
which field you read. Say which one you mean. (The earlier note that *"all 49 external skills carry
a version"* was reading `observed_version`; it is close but not exact — 12 entries lack it, 3 of them
`canonical`/`w0m-native`.)

**`just build` does not stamp at all** — `build:` is a bare `pnpm run build`, so a built artifact
carries no version until a deploy recipe stamps it.

**Spec gap found in the same audit:** the schema is specified only in the **archived** change
`openspec/changes/archive/release-versioning/`. Its deltas were never synced into a live
`openspec/specs/` capability (unlike T130's, which landed in `sdlc_toolchain`), so there is no
current spec of record for the standard.

## 🔴 Hard constraint — package.json cannot carry this format

`2026.07.25-1784436966` is **not valid semver**: the spec forbids leading zeroes in numeric
identifiers, so the zero-padded `07` is illegal (verified 2026-07-25 against the semver grammar;
dropping the pad to `2026.7.25-…` *is* valid but then diverges from the deploy format). npm/pnpm
require semver in `package.json`.

**Decision (proposed, owner to confirm): `package.json` versions are EXEMPT.** The schema governs
**deploy/release stamps, build artifacts, and skills** — the artifacts w0m itself versions — not
npm package metadata. Alternative if the owner prefers total uniformity: drop zero-padding
everywhere, which changes the existing deploy format and all recorded history.

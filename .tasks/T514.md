# T514 — Import or update contact info from a file

## Summary

Owner direction, 2026-09-30: *"we can have a button/function to update/import contact info from file."* A member picks a
file and gets proposed contact details (phone, postal address, website and professional links, email) to review and save
into `public.profile_contact`, the owner-only record from [[T505]]. This reuses the same upload-to-proposal flow as
"Extract highlights", with a different target table and stricter handling, because contact data is personal.

## What is not decided

"From file" has two sensible readings, so the ticket does not pick one silently (Q1): **a file already in the member's
vault** (a resume PDF or Markdown they uploaded), and **a contact card** such as a vCard (`.vcf`) exported from a phone or
address book. They need different parsers, and only one of them needs a language model.

## Design (assumptions marked)

1. **Proposals, never writes.** Like `w0m-personnel` today, the server returns proposals only. The member's own
   RLS-checked write saves them, so the model or parser never touches `profile_contact` directly.
2. **Deterministic first.** *(Assumption, Q2.)* vCard fields and regular patterns for phone numbers, URLs and email
   addresses are read in code, with no model call. A model is used only for what patterns cannot do, the postal address
   block of a free-text resume, and its answer is grounded against the source text: a value that does not appear in the
   file is dropped, the same rule `parseParsedResume` applies to employers.
3. **Review diff.** The member sees, per field, the current value, the proposed value and a tick box. Nothing is
   pre-ticked when a current value exists, so a stale file cannot silently overwrite a good number.
4. **Verification markers stay owner-of-the-process.** `profile_contact` carries KYC-owned verification markers
   (`phone_verified_at` and one more) that clear when a value changes ([[T505]]). An import can change a value and so
   clear a marker; it can never set one.
5. **Same limits as upload:** 10 MB, a real text layer, the per-member daily token meter where a model is used. The file
   content is not stored by this flow beyond the existing vault copy.

## Acceptance criteria

- [ ] AC1 — **Proposals come back for each supported source.** A resume (Markdown and text PDF) from the vault and a
  `.vcf` each return proposals for the fields they contain, none for the fields they do not. Unit tests on fixtures,
  including a vCard with multiple phones and a resume with the address split across lines.
- [ ] AC2 — **Nothing is invented.** A proposed value absent from the source is dropped and counted, and a fixture whose
  model answer includes an invented phone number returns none. Red probe: remove the grounding and the fixture fails.
- [ ] AC3 — **A member cannot import another member's file.** The path must be in the caller's own vault folder, as
  `w0m-personnel` enforces with `isOwnPath`. Probe with a path in another profile's folder returns 403.
- [ ] AC4 — **Review diff, no silent overwrite.** The UI lists current against proposed per field, with nothing ticked
  when a current value exists, and saves only ticked fields. Component test plus a spec.
- [ ] AC5 — **Verification markers are never set by an import,** and a changed value clears its marker. Authz and unit
  probe against `profile_contact`.
- [ ] AC6 — **Bad input fails clearly.** A scanned PDF with no text, an oversize file, a corrupt `.vcf` and an unsupported
  extension each produce a specific message and change nothing.
- [ ] AC7 — **Contact values are not logged.** Usage rows carry the action and counts only; a test asserts no proposed
  value appears in any log row or error message.

## Open questions (recommended answer first, with weight)

1. **Which sources?** *Recommend both: a vault resume and a `.vcf`,* delivered vCard first. Weight: the vCard path needs
   no model, no quota and no hallucination risk, so it is the cheap and safe half.
2. **Model or no model for a resume?** *Recommend deterministic extraction for phone, links and email, and the model only
   for the address block, always grounded.* Weight: a phone number a model "fixes" is worse than one it misses, and the
   deterministic path is testable to the character.
3. **Overwrite policy.** *Recommend nothing pre-ticked when a current value exists.* Weight: cheap to build, and it is the
   only defence against importing an old resume over current details.
4. **Does this feed the team card?** *Recommend no.* The card's LinkedIn link has its own switch and source ([[T510]]);
   an import writes the owner-only contact record and does not change what is public.

# T354 — Org federation & actor-identity layer

## Summary

Owner ask: *"the question right now about accessing system and admin parts from org2org and have
it all 3 aligned - 1. admin+system 2. org2org relations and 3. a2a and a2org and org2a, etc"*,
followed by *"so let's research, spec and show docs for review / find related tickets and arch and
techs / also how we model vector relations and where??"*

`docs/backend/RBAC-PROJECT-ROLES-PIVOT.md` already designs two of the three domains in prose (§6
"Multi-org federation direction", §7 "c2b2b2c actor layer") but neither is schema, and nothing ties
them together as one mechanism at different scope. This ticket states that mechanism once —
`actor_manifest` (capability catalog, any actor) + `org_trust_edges` (the only authorization edge)
+ boundary token exchange (RFC-8693-shaped, design only) — and answers, concretely, where a
similarity/discovery edge belongs relative to an authorization edge (its own table, its own RPC,
never read as a trust edge). Full grounding, prior-art citations and risk analysis live in the
openspec change's `proposal.md` — this ticket is schema/design only; no migration ships until
T117 AC5 (rank CHECK 12→6) lands, since a second axis built on today's inconsistent rank set would
inherit the inconsistency.

## Acceptance criteria

- [x] AC1 — `actor_manifest` schema documented: generalizes §6's `org_manifest` from
      `owner_kind = 'org'` only to `owner_kind IN ('profile', 'client', 'org')`, reusing
      `public.connections`' owner-shape CHECK-constraint pattern (T94) — one capability catalog
      for a person, a client company, or w0m itself.
- [x] AC2 — `org_trust_edges` schema documented as the *only* authorization mechanism between two
      `actor_manifest` rows: explicit, admin-curated, never inferred from similarity/embeddings.
- [x] AC3 — Boundary token exchange (RFC-8693-shaped) documented as the runtime shape
      `org_trust_edges` authorizes — design only, no server implementation in this change.
- [x] AC4 — `portfolio_items` schema documented (c2b2b2c verified public profiles/portfolios),
      referencing T349's eventual `identity_verifications` schema, not duplicating its KYC/KYB logic.
- [x] AC5 — A new, separate discovery-embeddings table (not `documents`) documented: reuses
      `wom7api/supabase/migrations/20251221000000_rag_setup.sql`'s pattern (`vector(1024)`, ivfflat
      cosine index, a `match_documents`-shaped RPC) and the canonical `w0m-embed` alias, for
      actor/portfolio discovery only — similarity SHALL never be read as a trust edge.
- [x] AC6 — New table name for the social/discovery graph decided (**`social_graph`**) and recorded
      in `docs/backend/TERMINOLOGY-MAP.md` §T7, distinct from `public.connections` (T94's
      OAuth-credential registry, flagged as a naming collision 2026-08-28, resolved 2026-09-13).
- [x] AC7 — A2A protocol (Linux Foundation, Agent Card) and MCP Agent Identity Working Group
      (Workload Identity Federation, ID-JAG, CIMD) mapped to `actor_manifest` /
      `org_trust_edges`+boundary-token-exchange respectively — mapped, not implemented.
- [x] AC8 — `docs/backend/RBAC-PROJECT-ROLES-PIVOT.md` gains a cross-reference section (`## 8.
      Synthesis`) synthesizing admin+system / org2org / a2a-a2org-org2a as one mechanism at
      different scope, linking this change, T349, and T94's connector-architecture-completion as
      prior art.

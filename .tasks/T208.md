# T208 — `user_profiles` is queried but was never created

## 🔻 DE-DUPLICATED 2026-08-13, same day it was filed — the LinkedIn half belongs to [[T194]]

Filed from `just callsite-drift`'s first run with **9** GHOST call sites. Checking it against the
queue afterwards — which [[w0m-sdlc-new]] would have done *before* filing — **7 of the 9 are
already [[T194]]'s**, listed there by file and line since 2026-08-10. `public.linkedin_tokens` was
**dropped** by `20260721120000_t99_protect_oauth_tokens.sql:63` under [[T99]], and its replacement
`public.social_integrations` **exists**. T194 AC5 owns fixing those callers, and it carries context
this ticket did not: the replacement columns are **plaintext at rest** ([[D1]]), so re-pointing the
callbacks without D1's encryption moves the problem rather than solving it.

⇒ **This ticket is narrowed to the 2 sites T194 structurally cannot find.**

🔑 **The gap that justifies keeping it separate.** T194's gate derives its worklist from
`DROP TABLE`/`DROP VIEW` in the migrations. **`user_profiles` appears in no migration at all** — it
was never created, so it was never dropped, so a migration-derived gate is blind to it by
construction. `just callsite-drift` finds it because it compares call sites against the **live
catalog** rather than against migration history. **Two gates, two blind spots, and they are
complementary** — worth stating in T194 rather than merging them.

## Summary

Found by [[T69]]'s new `just callsite-drift` check on its first live run, outside T69's own three
bugs but the **same defect class**: a query names a table that exists in no schema, the error is
swallowed, and the feature silently does nothing.

**`user_profiles` — 2 call sites, exists in no schema, and never has.**

| site | operation |
|---|---|
| `wom7web/packages/lib/src/auth/handlers.ts:438` | writes `linkedin_sub` / `github_sub` after an OAuth sign-in |
| `wom7api/src/workflows/linkedin-data-erasure.ts:54` | erases the same row |

⚠️ The write sits inside a `try { … } catch {}` whose comment reads *"Best-effort: swallow so a
linking hiccup never blocks sign-in"* — a fine policy for a **transient** failure and the wrong one
for a **permanent structural** error, which is exactly why this survived. Provider-identity linking
has never persisted, by construction.

🔴 **The erasure site is the serious one — but NOT for the reason first written here.**
🔻 **Correction 2026-08-13, same day:** this row originally said the erasure workflow *"reports
success while deleting nothing"*. **It does not.** `linkedin-data-erasure.ts:27-35` does
`if (tokenError) { …; throw tokenError; }`, so it **throws**. The real defect is worse in one
respect: because step 1 targets a dropped table it **always fails there and never reaches steps 2
and 3**, so `job_applications` PII is never scrubbed and `user_profiles` is never unlinked — **no
erasure request has ever completed**. It also never touches `public.social_integrations`, which is
where LinkedIn tokens, `provider_urn` and `profile_data` actually live. Owned jointly with
[[T194]] AC5.

**Establish before creating anything** (the lesson [[T69]] AC3 paid for).
🔻 **Correction 2026-08-13:** this row first guessed `public.profiles` was the target. **It is not
— `public.profiles` has no `linkedin_sub`/`github_sub` and no `*_sub` column at all.** Measured, not
assumed, which is the whole point of the rule I had just written down.
✅ **The real supersessor is `public.social_integrations`**, whose `(provider, provider_urn)` pair
*is* the provider-identity linkage `linkedin_sub`/`github_sub` were trying to record, and which the
live edge-function path (`linkedin-oauth`) already writes. So the fix is a **re-point to a different
shape**, not a rename: two columns collapse into one row per provider.

# T363 — Many-to-one account-profile linkage and identity linking research

## Summary

Enable multiple authentication accounts (`auth.users`, e.g. `casualuser@gmail.com` and `aleksei@webomage.com`)
to resolve to a single canonical person profile (`public.profiles`). In T210, the person was detached from the
auth account by dropping the primary key coupling, but `profiles.auth_user_id` remained a 1:1 `UNIQUE` column.
This ticket creates the `public.account_profiles` many-to-one linkage table, updates the `current_profile_id()`
RLS resolver, consolidates existing data between `casualuser` and `aleksei`, and conducts deep research on
Supabase Auth's native `linkIdentity()` provider linking.

## Acceptance criteria

- [x] AC1 — `public.account_profiles` linkage table (`user_id`, `profile_id`, `is_primary`, `linked_at`) created with RLS and foreign keys to `auth.users` and `public.profiles`
- [x] AC2 — `public.current_profile_id()` RLS helper updated to resolve `auth.uid()` through `account_profiles` with fallback to `profiles.auth_user_id`
- [x] AC3 — `public.profiles` RLS updated so any authenticated account linked in `account_profiles` can view and manage their shared profile
- [x] AC4 — One-time data consolidation: link `casualuser@gmail.com` and `aleksei@webomage.com` to canonical profile `8d16aff5-d996-4759-80b0-39b60e3c0920`, transferring legacy hats and associations
- [x] AC5 — Client/CP profile resolution: `/profile` and profile components resolve through `account_profiles` / `current_profile_id()` regardless of which credential was used to sign in
- [x] AC6 — Research and document Supabase native `linkIdentity()` capabilities, constraints, and operational migration paths in the change spec

## Definition of Done

This ticket is done when:
1. `public.account_profiles` is migrated to Postgres with RLS allowing users to read their own linkages and admins full management.
2. `public.current_profile_id()` correctly resolves profile ID when called from either primary or secondary linked accounts.
3. Data consolidation is applied so logging in as either `casualuser@gmail.com` or `aleksei@webomage.com` resolves to profile `8d16aff5-d996-4759-80b0-39b60e3c0920`.
4. Unit tests and RLS probes prove that secondary linked accounts possess legitimate read/write profile access while unauthorized accounts remain barred.
5. Research on Supabase Identity Linking is documented with clear tradeoffs and prerequisites.
6. `just typecheck` passes with zero errors, and all tracking surfaces are synced.

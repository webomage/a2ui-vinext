# T123 — 15 SECURITY DEFINER functions are executable by `anon`

## Summary

Supabase's security advisor reports **15 `SECURITY DEFINER` functions executable by `anon`** and
**31 by `authenticated`**. A `SECURITY DEFINER` function runs with its *owner's* privileges, so an
anon-executable one is a hole through RLS by construction — whatever authorization it does must be
inside the function body, and if it is missing there is none at all.

## This is a RECURRENCE, not a new class

[[T68]] (P0, closed 2026-07-17) fixed exactly this: *"16 `archive_/restore_` SECURITY DEFINER RPCs
were anon-EXECUTEable with no server-side authorization."* That fix addressed **16 named
functions**. The advisor now lists **15 more**, so the remediation was applied to a list rather
than to the pattern.

**The most important acceptance criterion below is therefore AC4** — a standing check — because
fixing these 15 by name will otherwise leave the next N to be found the same way, by chance.

## Verified live 2026-07-22 (non-destructively)

Called via PostgREST RPC with the publishable key:

| Function | Result |
|---|---|
| `public.is_admin` | **`200` → `false`** — anon can execute it |
| `public.get_user_roles` | **`200` → `null`** — anon can execute it |
| `public.award_gamification_xp` | `404 PGRST202` — resolvable by name, needs arguments |
| **`public.hard_delete_user`** | `404 PGRST202` — **resolvable by name**, needs arguments |

`hard_delete_user` was **deliberately not probed with real arguments.** A destructive function that
is anon-executable is either arg-guarded and harmless, or catastrophic, and the advisor cannot tell
which — but establishing which by *calling it* is not acceptable. Determine it by reading the
function body and its grants.

Others in the anon-executable set: `handle_new_user`, `has_role`, `get_heatmap_sessions`,
`get_provider_quotas`, `get_top_clicks`, `get_user_daily_tokens`.

- [x] **AC2 — DONE** `hard_delete_user` specifically: its grants and body are reviewed and it is
      **not** anon-executable, whatever its arg guards happen to do.
- [x] **AC3 — DONE** The 31 `authenticated`-executable definer functions get the same pass — a

## ✅ 2026-07-23 — anon EXECUTE closed on the 7 that needed it

Every one of the 15 was triaged by **reading its body**, not by name:

| | Functions |
|---|---|
| **Guarded in-body** (6) | `is_admin`, `has_role`, `get_user_roles`, `wom_role_set`, `hard_delete_user`, `trigger_vectorize_vault` |
| **Unguarded** (9) | `award_gamification_xp`, `get_heatmap_sessions`, `get_top_clicks`, `get_provider_quotas`, `get_user_daily_tokens`, `handle_new_user`, `wom_acting_is/in/role` |

**`hard_delete_user` is guarded** — it raises unless `public.is_admin()`. So the dangerous
primitive was never actually reachable by anon. Revoked anyway: a body check should not be the
only thing between an anonymous caller and a user-deletion function.

**Two were genuinely leaking**, confirmed by probe rather than inference:
`get_top_clicks` returned click analytics and `get_heatmap_sessions` returned **visitor session ids
and timestamps** — both HTTP 200 to anyone holding the publishable key, and both with **zero
callers** in the codebase.

**Deliberately left alone: the RLS helper set** (`is_admin`, `has_role`, `get_user_roles`,
`wom_role_set`, `wom_acting_*`). Policies call these while executing *as the querying role*, so
revoking anon's EXECUTE would break anon-visible tables rather than secure them. They read the
caller's own claims and disclose nothing about anyone else. Verified still working after the change.

### 🔴 The first revoke migration did nothing — and reported success

`REVOKE EXECUTE … FROM anon` applied cleanly, and re-probing showed **`get_top_clicks` still
returning 200 with data**.

The ACL entry was `=X/postgres`, which is a grant to **PUBLIC**, and PUBLIC includes anon.
**Revoking from a role does not remove a grant made to PUBLIC** — the role keeps inheriting it. The
revoke succeeds, raises no error, and accomplishes nothing.

The correct shape is `REVOKE … FROM PUBLIC` followed by explicit `GRANT`s to the roles that
genuinely need it (`service_role` holds its own explicit grant and was unaffected). After that:
`42501 permission denied`, where before it was `200` with rows.

**This is why AC4 is the load-bearing criterion.** A check that asserts "no definer function is
anon-executable" would have caught the no-op revoke immediately; reading the migration would not,
because the migration is correct-looking SQL that does nothing.

## ✅ 2026-07-23 — AC4 shipped: the standing check (and AC5 answered)

`just audit --deep` gained a **DB GRANTS** section asserting the end state:

```
▶ DB GRANTS — definer functions + public buckets
  ✅ PASS  [grants] definer functions — none anon-executable outside the allowlist
  ✅ PASS  [grants] public buckets — all public buckets are on the allowlist
```

It covers **T122 AC6 too** — both of the day's P0s came from database configuration nothing
watched, so one check answers both.

**The allowlist is the RLS helper set** (`is_admin`, `has_role`, `get_user_roles`, `wom_role_set`,
`wom_acting_*`). Policies call these while executing as the querying role; they must stay callable.

**Proved it can fail, not just pass.** Removing `is_admin` from the allowlist made the check report
`2: is_admin, trigger_vectorize_vault`. A green check that has never gone red is an assumption.

### AC5: the T68 fix held — my check was the thing that was wrong

The first version flagged **25 functions**, including T68's `archive_*` set, which read like a
five-week-old P0 having silently regressed. It had not. The ACL query matched `LIKE '%=X/%'`, and
**every** ACL entry contains that (`postgres=X/postgres`), so it flagged everything.

A grant to PUBLIC is an entry with an *empty grantee* — it starts with `=`. Corrected to
`unnest(proacl) LIKE '=%'`, the count went 25 → **1**, and that one was real.

Worth stating plainly: a noisy check is not a safe failure mode. Had I trusted it, I would have
reported a regression in a closed P0 that never happened.

### The last function needed BOTH revokes

`trigger_vectorize_vault` carried a PUBLIC grant **and** an explicit `anon=X`. Revoking PUBLIC left
the check failing — correctly, because the explicit grant still stood. So:

- `REVOKE … FROM anon` alone misses the PUBLIC grant anon inherits *(this ticket's first migration —
  applied cleanly, changed nothing)*
- `REVOKE … FROM PUBLIC` alone misses an explicit role grant *(this one)*

Both are required, and the only trustworthy confirmation is asserting the end state — which is now
what the check does, on every `--deep` run.

## ✅ 2026-07-23 — AC3: the `authenticated` pass

The advisor listed 31; the live count was **28** (three had already been closed by AC1's revokes,
which is the advisor cache lagging, not a discrepancy). All 28 triaged **by reading the body**:

| | Functions | Decision |
|---|---|---|
| Guarded by `is_admin()` | 16× `archive_*`/`restore_*` | **keep** — CP admin UI calls them with the admin's own session; the guard is the authorization |
| Reads caller's own claims | `is_admin`, `has_role`, `get_user_roles`, `wom_role_set`, `wom_acting_is/in/role` | **keep** — policies run these AS the querying role |
| **Unguarded** | `get_provider_quotas`, `get_user_daily_tokens`, `get_top_clicks`, `trigger_vectorize_vault`, `hard_delete_user` | **fixed** below |

Migration: `wom7api/supabase/migrations/20260723100000_t123_ac3_authenticated_definer_pass.sql`.

### What the unguarded five actually exposed

- **`get_user_daily_tokens(text)` — an IDOR.** It takes an *arbitrary* identifier and returns that
  identifier's 24h AI usage, with no check the caller owns it. Any signed-in user could read any
  other user's consumption. Revoked; only `service_role` retains it.
- **`get_provider_quotas()`** returned per-provider/per-model token totals and request counts —
  AI spend telemetry — to every signed-in user. This one **could not simply be revoked**: the CP
  admin dashboard calls it over PostgREST with the admin's own browser session, so `authenticated`
  is the role that has to reach it. It got an in-body `is_admin()` guard instead — the same shape
  T68 applied to `archive_*`. Revoke is not always the answer; *authorize in the body* is.
- **`trigger_vectorize_vault()`** is a **trigger function** — it reads `TG_TABLE_NAME` and returns
  `NEW`. It was reachable over `/rest/v1/rpc` while holding `pg_net` and the webhook secret.
  Direct invocation would error, but "it errors" is not an authorization model.
- **`get_top_clicks`** — unguarded analytics, zero callers anywhere. Revoked.
- **`hard_delete_user`** — guarded, as AC2 established, but zero callers and maximally
  destructive. Revoked for the reason AC2 already gave for anon.

### 🔴 The revoke broke AI quota enforcement — silently, and it was already live

Tracing `get_user_daily_tokens`'s callers turned up a **live consequence of AC1**, which shipped
yesterday. `_shared/chat-core.ts` built an **anon** client and passed it to `checkQuota`.
`agent-consultant` never supplies its own client, so the public chat path used it. AC1 revoked
anon's EXECUTE — so the RPC began returning `42501`, and `checkQuota` **fails open**:

```ts
if (error) { logger.error(...); return { allowed: true, used: 0 } } // Fail open
```

The daily token limit stopped being enforced the moment the revoke landed. Nothing went red: the
chat kept answering, and the only trace was a log line reading `Error checking quota` — identical
to a transient DB blip.

Fixed in `chat-core.ts` (quota check now uses the service client that already existed a few lines
below) and `ai-utils.ts` (the fail-open now logs `quota_check_failed_open` **with the error code**,
so an authz failure is distinguishable from an outage).

**The generalisable lesson:** a revoke is only safe once every caller's *role* has been checked.
AC1 verified the function was no longer reachable by anon; it did not verify that nothing
legitimate was reaching it *as* anon. Those are different questions, and only the second one
catches this.

### AC4's check extended to cover AC3

`just audit --deep` gained a second grants assertion — `authenticated`-executable definer
functions, against its own allowlist (the RLS helper set **plus** the 16 guarded `archive_*`/
`restore_*` **plus** `get_provider_quotas`, each on it because of a named in-body guard).

Run against live state before the migration, it printed exactly the four the migration revokes:

```
❌ FAIL [grants] authenticated-executable SECURITY DEFINER — 4: get_top_clicks,
   get_user_daily_tokens, hard_delete_user, trigger_vectorize_vault
```

Two separate checks rather than one, because the allowlists genuinely differ: an in-body
`is_admin()` guard makes a function safe for signed-in callers and says nothing about anonymous
ones.

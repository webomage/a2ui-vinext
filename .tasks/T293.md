# T293 — Members manage their own resume/CV in the CP

## Why

The CP's CV surface was built for **one person** — the owner's profile/resume sync and submit, for
the agency and platform's early stages. Owner instruction 2026-08-31: it now has to serve **all w0m
units/members**, with admin, PM and TPM able to see and manage developers' and trainees' CVs.

Measured the same day, the existing admin surface **cannot work at all**:

1. **Dead route.** `apps/cp/src/components/admin/CVGenerator.svelte:70` POSTs
   `${workerUrl}/api/generate/cv`. The wom7api worker exposes `/health`, `/estimator`, `/tasks`,
   `/trigger`, `/event`, `/ai/chat`, `/ai/embed`. There is no such route — 404.
2. **Wrong credential.** It sends the member's Supabase `accessToken` as Bearer. `/trigger` checks
   `WEBHOOK_SECRET`. Even at the correct URL it would 401.
3. **Unauthenticatable by construction.** `WEBHOOK_SECRET` is a server secret; a `client:load`
   Svelte component can never legitimately hold it. The fix is not a URL change — the call has to
   move server-side.

`CvGeneratorWorkflow` is exported from `wom7api/src/index.ts` but appears in **no**
`EVENT_WORKFLOW_MAP` entry and has no route: a registered Workflow with no way to invoke it over
HTTP. Correct invocation is `POST /trigger { workflow: "CvGeneratorWorkflow", input }`.

## What already exists (do not rebuild)

- `apps/cp/src/pages/profile.astro` — the member's own "Me" page, session-scoped.
- `ResumeParser` in `@webomage/ui` — already per-member: it reads `profiles` / `profile_skills`
  under the member's **own** session, so it is RLS-scoped by construction. This is the right
  pattern and the admin tool is the wrong one.
- `CvGeneratorWorkflow` — works, and already writes `${userId}/cv-${timestamp}.md`, so the storage
  path prefix IS the owner. It emits **markdown**, not PDF.
- `resumes` / `decks` buckets, hardened by T122 (`public = false` AND the public-role SELECT
  dropped — both halves).
- **T293's prerequisite is already merged**: `20260831150000_resume_bucket_owner_admin_office_scoping.sql`
  replaced the blanket `FOR SELECT TO authenticated USING (bucket_id = 'resumes')` with
  owner / `wom_acting_is('admin')` / `resume.view` | `resume.manage`, bundled into the
  `project.manager` and `tech.lead` offices. Verified live 2026-08-31.

## Acceptance criteria

- [ ] **AC1 — the isolation claim is proven, not assumed.** The bucket held **0 objects and 0
      owners** when the policy landed, so "member B cannot read member A's resume" was *vacuously*
      true. Seed two real member resumes and assert, as a non-admin `authenticated` actor, that the
      second is invisible to the first. 🔴 Use `BEGIN; SET LOCAL ROLE …` **inside a transaction** —
      `SET LOCAL ROLE` outside one is a no-op and the spot-check silently reports on the superuser.
- [ ] **AC2 — server-side trigger.** An Astro SSR endpoint in CP holds `WEBHOOK_SECRET` and calls
      `POST /trigger { workflow: "CvGeneratorWorkflow", input: { userId } }`, deriving `userId`
      from the **session**, never from the request body. Fixes all three defects above at once.
- [ ] **AC3 — member CV section on `profile.astro`**: list my versions from `resumes`, generate a
      new one, download. Reuses `ResumeParser`'s session-scoped pattern.
- [ ] **AC4 — PDF.** `CvGeneratorWorkflow` emits markdown only. Render via Cloudflare Browser
      Rendering, which is already bound and in use (`wom7cfworkers` binds `BROWSER`;
      `document-generator.ts` already calls `page.pdf({ format: "A4", printBackground: true })`).
      🔑 The six templates in `wom7web/docs/backend/branding/templates/*.css` are plain CSS and can
      serve members directly — do not build a second styling system.
- [ ] **AC5 — managers' view.** A PM (`project.manager`) or TPM (`tech.lead`) sees the CVs their
      capability grants. The DB half is done; this is the UI half. Assert a member WITHOUT the
      capability sees nothing — a manager view that works is not evidence that a non-manager is
      excluded.
- [ ] **AC6 — retire or repoint the admin tool.** `admin/CVGenerator.svelte` and
      `recruit/cv-generator.astro` either become an admin-acting-on-behalf view over the new
      server-side path, or go to `DECOMMISSIONED.md` with an `absent` block. It must not stay as a
      surface that 404s.
- [ ] **AC7 — fix `getPublicUrl` on a private bucket.** `cv-generator.ts:165` calls
      `getPublicUrl()` on `resumes`, which T122 set `public = false`. That URL cannot resolve;
      `/storage/v1/object/public/<bucket>/<path>` is gated by the flag. Use `createSignedUrl()`.
      The hardening was right — this consumer was never updated.

## Definition of Done

A w0m member signs into the CP, generates a CV from their own profile, and downloads it as a PDF —
without any browser holding a server secret, because the trigger runs server-side and derives the
subject from the session rather than the request body. A second member, signed in at the same time,
cannot read the first's file: proven by a probe that acts as a non-admin `authenticated` actor
inside a transaction against two REAL member resumes, not against an empty bucket, and that fails
if the bucket is empty rather than passing vacuously. A PM or TPM can see both, and a member holding
neither office sees only their own — the exclusion asserted, not inferred from the inclusion
working. `admin/CVGenerator.svelte` either serves that same server-side path or is in
`DECOMMISSIONED.md` with an `absent` block; no surface is left POSTing a route that 404s. Every
generated document is reachable by a URL that actually resolves, which means signed rather than
public, because the bucket is private.

## Notes, traps and dependencies

- 🔴 **PM and TPM are OFFICES, never Axis-1 roles.** `user_roles_role_check` is fixed at
  (admin, member, anon, recruit, gladiator, legioner, ai-agent, ai-interviewer, ai-architect,
  ai-admin, editor, client) and adding to it is prohibited. `project.manager` and `tech.lead`
  already exist and are already flagged `is_management`.
- 🔴 **Never sub-query `offices`/`user_offices` from an RLS policy.** It compiles, reads correctly
  and matches NOTHING — an RLS subquery against another RLS-protected table returns zero rows.
  Go through `wom_acting_is` / `wom_effective_capabilities`, both `SECURITY DEFINER` with
  `set search_path = ''`. `stage2-schema-check` already caught this exact shape on `leads`.
- ⚠️ **`wom_can()` does not exist.** The T117 design proposes it; it is unbuilt. Use
  `EXISTS (SELECT 1 FROM public.wom_effective_capabilities() WHERE capability = …)` until it lands.
- ⚠️ **Identity depends on [[T210]]** (detach the person from the account, 75%, #1 on both boards).
  It is deciding how a person detaches from an account — the identity this feature keys on. Do not
  key to a model T210 is about to change.
- ⚠️ **`profile_snapshots` had a blanket-read policy dropped under T198 AC4.** The tenancy here has
  been got wrong before; assert it rather than assume it.
- 🔧 Housekeeping found alongside: the RBAC seed carries **both** `project.manager` and
  `project_manager` spellings.
- 📌 The owner's own CV is a **different system** — `resume.json` → `just cv-experience` → branding
  markdown → local pandoc/weasyprint. Decide explicitly whether members get the data-driven path
  while the owner keeps the file-driven one, or whether the two converge. Do not merge them by
  accident.

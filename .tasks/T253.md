# T253 — A visitor's chat cannot become their own content

## Summary

Owner direction, 2026-08-22: keeping chats keyed by session is fine, and visitors should be nudged
to **create a simple trial account so the conversation becomes their own content**.

That plan has a missing hinge. A visitor's turns are written against a `session_id` with
**`user_id = NULL`**. When they create the account, nothing adopts those rows — so:

- the `Users can view their own chats` policy (`auth.uid() = user_id OR …`) matches **nothing** for
  exactly the people it is meant to serve;
- the account they were asked to create in order to keep the conversation **does not keep it**.

🔑 **This is why [[T251]] AC4 decided to KEEP that policy rather than drop it.** I had recommended
dropping it as dead weight — the read path uses the service client. The owner's direction is better
because it gives the policy a purpose, and this ticket is the work that makes the purpose real.
⚠️ Without it, keeping the policy is the same as dropping it: live, and matching nothing.

📊 It is not a large corpus yet, and that is an argument for doing it before it is: measured
2026-08-22, the whole `chats` table is **4,220 rows / 334 sessions**, the `leads` table holds
**2 rows** (both tests), and the last genuine visitor conversation was **2026-07-23**.

## Acceptance criteria

- [x] **AC1** — a red probe first: an anonymous visitor chats, then signs up, and their earlier
      turns become readable **as that user**. Assert through the **policy** — a query as the new
      user's role returning their rows — not with the service key, which can read everything and
      would pass on a table where the claim never happened.
- [x] **AC2** — the claim is scoped to **one** session and **cannot be forced**. 🔴 The session id
      is client-supplied (`web:${crypto.randomUUID()}` from `sessionStorage`), so "claim session X"
      as a bare parameter lets any account claim any conversation it can name. Decide the binding —
      the browser proving continuous possession, a one-time token issued at signup, or the claim
      happening server-side inside the signup flow where the session is already in scope — and
      record why the rejected options were rejected.
- [x] **AC3** — ⚠️ **IP-keyed sessions must NEVER be claimable.** 318 of 328 sessions measured under
      [[T251]] are keyed `web:<visitor IP>`, which is shared behind any NAT. Claiming one hands the
      new account whoever else used that address. Only ids that came from the client
      (`sessionIdFromClient`, per [[T249]]) may be adopted, and the probe must show an IP-keyed
      session being refused.
- [x] **AC4** — the nudge itself: where and when the visitor is asked. A product decision, not a
      mechanical one — after N turns, on a lead handoff ([[T2]]'s registration card is already the
      moment a visitor is asked for an email), or on leaving. Record the choice and the reasoning.
- [x] **AC5** — retention is stated for both halves. An unclaimed session keeps accumulating with
      `user_id = NULL` and a `session_id` that **contains an IP address in plain text**; a claimed
      one becomes user content with a deletion expectation attached. Both need a written answer, and
      [[T251]] AC5 is the neighbouring decision.
- [x] **AC6** — ⛔ if any of this needs DDL (an index on `session_id`, a policy change): committed
      migration + `just db-migrate`, **denied to the agent** ⇒ owner applies.

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
AC1's probe shown red then green **through the policy**, AC2's binding decided with rejected options
recorded, AC3's IP-keyed refusal demonstrated, AC4's nudge chosen deliberately, AC5's retention
written down, committed with the T-id, and TASKS.md row plus this ticket plus the GH issue in sync.

🔴 **Not closable on "signup works"** — it already does. The exit condition is a person seeing the
conversation they had before they had an account.

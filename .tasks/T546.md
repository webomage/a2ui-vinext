# T546 — tools-weekly proposes, tools-promote lands

Split from: [[T112]] (deps and toolchain alignment). Owner decision 2026-10-06: option C.

## Summary

`com.w0m.tools-weekly` (launchd, Mondays 10:00) runs `cd <live checkout>/wom7api && just tools-weekly`, which upgraded tools and rewrote `project/policies/tools-policy.json` **in the live checkout**, and never committed. Measured 2026-10-06: the owner's checkout sat dirty for a day after the 2026-10-05 run, `git merge --ff-only` aborted on it, and the file would have been in the tree during a deploy. It also let a bump into the file without its smoke: the weekly run held semgrep ("upgrade did not take") and the reconcile step then wrote it anyway; it passed when re-checked by hand, but nothing had checked it when it was written.

How the scripts behave with worktrees (read 2026-10-06): both resolve the policy through `Path(__file__)`, so a script run in an agent tree edits that tree's own copy; installed versions are machine-wide, so two trees would each write the same bumps as separate conflicting commits; neither script checked which tree it was in, whether it was dirty, or whether it was behind `origin/beta`; the cache and status files are gitignored per tree, so an agent tree has none (harmless: only the live tree's run reads them).

## What was built

- `tools_upgrade.py --apply` and `--reconcile --apply` upgrade and smoke-test as before but record a PROPOSAL in a machine-level state file (`~/.w0m/state/tools-proposed.json`, outside every tree, so an agent tree sees what the live tree's scheduled run found). They never write the policy.
- `just tools-promote` lists the proposals (dry run). `just tools-promote --apply` re-verifies each (installed == proposed, at least `min`, smoke passes, a smoke must exist) and writes `known_good` into THIS tree, ready to commit and `just agent-tree-land`. Refused outside an agent tree. What stays blocked stays proposed, so it stays visible.
- `just tools-check` names pending proposals. The run-status file records `proposed` instead of `promoted`.

## Acceptance criteria

- [x] AC1 — **Tests first, mutation-proven.** `just tools-upgrade-test` (24 offline checks, registered). Ten deliberate breaks are each caught (weekly or reconcile writing the policy, promote allowed in the live tree, no smoke, stale version accepted, no-smoke tool accepted, minimum ignored, proposal left after promotion, prefix-match tree detector, a failed smoke still proposed).
- [x] AC2 — **The scheduled run no longer dirties the live checkout.** The script has exactly one policy write (in `promote()`), enforced by a structure test.
- [x] AC3 — **Bumps are re-verified at promotion, and a no-smoke tool is never promoted silently.**
- [ ] AC4 — **First real cycle (owner/agent step).** After the next Monday run (2026-10-12 10:00): the live checkout is clean, `just tools-promote` lists what the run verified, and `just tools-promote --apply` in an agent tree produces a committable diff. Tick when seen.

## Manual edits stay legitimate (owner, 2026-10-06)

"We actually sometimes hit new OSV reports and known_good could be tweaked manually as well." So hand-editing `known_good` (or `min`) in a tree, and `tools_check.py --update-known-good`, are NOT retired and not refused: a new advisory can force a floor or baseline change at any time, outside the weekly cycle. What T546 guarantees is narrower: the SCHEDULED run never writes the policy, and a bump that arrives through `tools-promote` is re-verified. The two paths are independent, and a manual edit does not clear a pending proposal (it will report stale or already-current at promotion, which is correct). Known weakness kept on purpose: `--update-known-good` records installed versions with no smoke; use `just tools-upgrade --reconcile` then `tools-promote` when a smoke-verified bump is wanted. Dependency advisories are a separate floor: `pnpm.overrides` in each repo (see [[T112]]).

# T154 — exposed MCP interfaces

## Summary

**Owner ask 2026-07-27:** *"it looks like we should start monitoring exposed mcp interfaces as
well"*. **The first look found a live hole**, which is the argument for the ticket.

MCP surfaces are not ordinary ports. An MCP server exposes **tools that act on the user's behalf** —
read files, edit them, run commands. An exposed HTTP service leaks data; an exposed MCP server leaks
**capability**. Nothing in the estate currently inventories them, checks their bind address, or
tests whether their tools are gated.

## 🔴 LIVE FINDING — Obsidian vault MCP: unauthenticated tool access, bound to all interfaces

Measured 2026-07-27. **Nothing was invoked — enumeration only.**

| Check | Result |
|---|---|
| Bind address | 🔴 **`*:3001` and `*:3007`** (i.e. `0.0.0.0`) — **not** loopback |
| LAN reachability | 🔴 `http://192.168.1.175:3001/` → **HTTP 200** |
| `initialize` without credentials | 🔴 **succeeds** |
| `tools/list` without an API key | 🔴 **succeeds — 8 tools returned** |
| Tools exposed | `vault`, `edit`, `view`, `workflow`, `system`, `graph`, … |
| Server | `Semantic Notes Vault MCP` v0.11.42 (Obsidian plugin), PIDs 60860/60861 |

🔴 **`edit` is a WRITE tool.** ⇒ **Anyone on the same L2 network — café/hotel wifi, office guest
VLAN, a compromised IoT device — can enumerate and invoke tools against the owner's Obsidian vaults
(`wom7md` and `wom7web`), without authentication.**

⚠️ **The server itself warns about this in its own `instructions` field:**

> *"SECURITY WARNING: This Obsidian MCP server is configured to serve vault contents over an
> unencrypted network interface (0.0.0.0:3001). The API key and all document text travel in cleartext
> over the network."*

⇒ **The warning is delivered to the MCP client, where a human never looks.** A warning inside the
protocol payload is not a control — that is the whole point of this ticket.

### Immediate mitigation (owner, minutes)

1. **Rebind to `127.0.0.1`** in the Obsidian MCP plugin settings for both vaults. Nothing legitimate
   needs LAN access — `opencode.jsonc` and every other consumer connect over loopback.
2. **Require the API key** for tool calls, not just document fetches.
3. ⚠️ Assume prior exposure: the vaults hold `project/` notes and client material. Duration unknown —
   the bind predates this measurement.

      three differences the security shape demands:
      1. **A new surface is never auto-accepted.** `--save` locks in an *improvement* on a surface
         already declared; accepting a new one is a human edit with a written reason, and the tool
         prints the paste-ready stanza. **A ratchet that auto-accepts what it finds ratifies the
         breach it exists to catch.**

      than papered over: an MCP server that does not speak HTTP (stdio, other transport) is
      invisible to the inventory and therefore to this gate.

**2026-08-01 — AC8 SECURITY-REVIEWED** (`w0m-sdlc-security`). Required gates: gitleaks ✅,

🔴 **One real finding, fixed: the matching key was attacker-controlled.** The reconcile matched a
listening surface to a declaration by the server's **name** — which arrives in the *probe
response*, i.e. it is asserted by the listening process itself. So anything answering to a
declared name was waved through **on any port**, including a wildcard, LAN-reachable one.
Demonstrated: a declaration of `legit` at `127.0.0.1:1234` absorbed a rogue MCP on
`0.0.0.0:9999` and the gate exited **0**. A security gate whose match key is chosen by the thing
it is inspecting cannot do its job. Now matched on **bind only** — observed by us, not claimed by
it — and a name-claim on an undeclared bind fails the run.

🟡 **Second, related fix: machine config could explain away a wildcard bind.** `~/.claude.json`
may EXPLAIN a surface, but it cannot make a LAN-reachable MCP acceptable — that is the exact shape
T154 was opened for. `external` now only ever covers **loopback**; a wildcard bind is undeclared
regardless of who configured it.

Both landed RED-first; the suite is now **30 checks**.

**2026-08-01 — AC8 REVIEWED** (`w0m-sdlc-review`). Three findings, all confirmed against the
code and all **fixed in scope** (nothing filed as debt):

1. 🔴 **IPv6 binds were unmatchable.** A v6 surface rendered `::1:4011` — not how anyone writes an
   IPv6 bind, and ambiguous about where the host ends. A declaration using the conventional
   `[::1]:4011` failed to match, so the server came out **both** `declared, not listening` **and**
   `listening, undeclared`: a double false positive on the direction that is the security signal.
   `norm_bind()` now canonicalises both sides and accepts either spelling.
2. 🔴 **`--json` never ran the reconcile at all.** It returned before it, and its exit code ignored
   undeclared surfaces — so the two output modes of a security gate disagreed about whether the
   host was clean, and any CI consuming `--json` would have read 0 with a rogue MCP listening.
   The reconcile is now computed before the branch and rides in the payload as
   `declared_vs_listening`.
3. 🟡 **One process on two address families counted as two findings.** `mcp_exposure` already
   dedupes wildcard binds per `(command, port)` for exactly this reason. Now grouped, with both
   addresses retained rather than discarded — live output went from *"2 undeclared"* to *"1"*.

Each fix landed with a RED test first; the suite is now 23 checks.

# T311 — Project roles — decouple project functional delivery roles and hats from w0m agency matrix units

## Summary

Owner ask 2026-09-03: *"so it looks like hats management is per w0m unit and not per project staff slot … project_roles sounds better actually vs slots"*.

Currently, `public.hats` binds directly to `public.units` (the 13 internal agency matrix units, e.g. `Senior Fullstack Specialist (Hybrid) IV`, `DevOps / SRE Specialist II`). This creates three fundamental problems for project delivery:
1. **Internal Seniority vs. Project Delivery Function:** Customers contract for functional delivery roles (*Tech Lead*, *Core Developer*, *Smart Contract Auditor*, *Client PM*), not internal agency matrix compensation grades with Roman numerals.
2. **Missing Roles:** Essential project roles (e.g. *UI/UX Designer*, where `RBAC-MODEL-REVIEW-2026-08-28.md` noted *"No Designer unit exists"*, or external client stakeholders) have no matching unit in the 13 agency matrix units.
3. **No Per-Project Role Customization:** Projects cannot declare their custom team roster, assign members to project-specific seats, or let admins step into functional project roles.

This ticket introduces `public.project_roles` as a first-class entity, bridges `public.hats` to `project_roles`, and upgrades the CP Project Hat switcher to operate on real functional project roles.

## Acceptance criteria

- [x] **AC1 — Schema migration: `public.project_roles` table.** Committed migration adds `public.project_roles (id, project_id, name, slug, description, min_unit_id, created_at, updated_at)` with `unique (project_id, slug)` and foreign key to `public.projects (id) on delete cascade`.
- [x] **AC2 — Standard project roles seeded.** Default functional delivery roles are seeded for active projects (`BridgeRoad MVP`, `Artemio`, etc.), including: *Tech Lead*, *Fullstack Developer*, *UI/UX Designer*, *QA Engineer*, *Client Liaison*.
- [x] **AC3 — Bridge `public.hats` to `project_roles`.** Extend `public.hats` to link with `project_role_id uuid references public.project_roles (id) on delete cascade`, allowing hats to represent either an agency matrix unit or a functional project role.
- [x] **AC4 — CP Project Roles API.** Dedicated endpoint `GET /api/project/roles?projectId=...` returns the project's configured roles, current wearers, and assignment status; `POST /api/project/roles` allows creating or updating roles.
- [x] **AC5 — Hat Switcher operates on Project Roles.** The CP hat switcher (`MyProjectHats.svelte` / `HatSwitcher.svelte`) displays the project's functional `project_roles` for the selected project, enabling admins to put on any project role on demand via `wom_wear_hat`.
- [x] **AC6 — End-to-end verification.** Verify end-to-end in CP that on BridgeRoad MVP (and other projects), functional roles (*Tech Lead*, *Fullstack Developer*, *UI/UX Designer*) are selectable, wearable, and accurately reflected in worn hats.

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
`public.project_roles` exists in PostgreSQL with project-scoped foreign keys and unique constraints; standard functional roles are seeded for active projects; `public.hats` supports `project_role_id` linking; the CP Project Roles API (`/api/project/roles`) enables CRUD and wearer assignment; the CP project hat switcher operates on functional project roles; and end-to-end testing proves an admin can wear functional project roles (Tech Lead, Fullstack Dev, Designer) on BridgeRoad MVP.

# T262 — public-assets-to-r2

## Summary


🟡 **P1 — RAISED FROM P3 2026-08-23 by owner decision, because the goal is resilience.**
It was filed P3 on 2026-08-13 as *"genuinely optional — assets are served today"*, which is
true only while Supabase is up. Once the driver is *the public site keeps rendering when
Supabase is unavailable*, "optional" describes the cost saving, not the outage behaviour.
📌 Queue moved `backlog-platform` → `p1`, not `now`: it is blocked on two OPERATOR
prerequisites (below) and cannot be worked today, and unworkable work at the top of the
queue is how the top of the queue stops meaning anything.

🔑 **The point is RESILIENCE, not only egress cost — owner 2026-08-23, and the design says so.**
`design.md:43`: *"Objects already in R2 serve fine regardless of Supabase state — **which is the
whole resilience point**."* The proposal leads with the metered-egress quota (the 8.38/5 GB that
402-restricted the project), but the reason it matters to the public site is that the front end
keeps rendering when Supabase is unavailable. The estate already applies this pattern elsewhere:
`Layout.astro` reads background/slide settings from a **committed Cloudflare snapshot, not
Supabase**, expressly *"so the site renders its configured look even when the database is
unreachable or quota-restricted"*.

⚠️ **And that changes what "done" means here.** The write-through design protects **only objects
already in R2** — a cold miss during a Supabase outage returns a short-cache 503, by design, so it
self-heals later. `design.md` calls the bulk migrator *"just pre-warms R2 so the first visitor
never eats the origin fetch"*, which is true for the COST goal and understates it for the
RESILIENCE goal: **unmigrated objects are exactly the ones that break during an outage.** ⇒ For
resilience, task 3.1's bulk run is load-bearing, not an optimisation.
✅ **That call was made 2026-08-23: resilience is the driver, so this is P1.** The flag above
asked the question; this is the answer, recorded where the question was asked.

🔬 **RE-VERIFIED 2026-08-23, and "genuinely NOT built" was too blunt. The CODE is ready; the
INFRASTRUCTURE is not.** Measured against the change's own `tasks.md`:

| | state |
|---|---|
| `apps/web/src/pages/cdn/[...path].ts` — the write-through route | ✅ **exists on disk** (task 2.1 `[x]`) |
| `apps/web/scripts/migrate-storage-to-r2.mjs` — idempotent, resumable migrator | ✅ **exists on disk** (task 3.1 `[x]`) |
| R2 bucket `wom-public-assets` | ❌ not created (task 1.1) |
| R2 binding in `apps/web/wrangler.jsonc` | ❌ absent — **zero `r2_buckets` in any wrangler config, estate-wide** (task 1.2) |

⇒ The blocker is a **bucket that does not exist**, not unwritten code. ⚠️ And the order is
load-bearing: the change's own task 1.2 says **DO NOT add the binding before the bucket exists —
an unbound reference fails deploy.**

🔴 **Both remaining prerequisites are OPERATOR actions, and one is a bootstrap trap** (proposal
*"Blocked prerequisites"*, recorded 2026-07):
1. **The Cloudflare token cannot create the bucket** — `code: 10000` on bucket create. The account
   is super-admin but `CLOUDFLARE_API_TOKEN` is scoped narrower. Needs **R2 Edit** on the token, or
   the bucket created by hand in the dashboard.
2. **Supabase egress 402** — *reading the source bytes in order to copy them is itself blocked.*
   You cannot migrate off the metered surface because the metered surface is rate-limiting you.
⚠️ **Both dates from 2026-07 and NEITHER was re-verified today.** The 402 in particular may have
lapsed — billing has moved since, and [[D58]] records that egress is **unreadable** from the API
(`/usage` 404s), so its current state cannot be measured from here at all. **Re-check before
planning the run; do not treat a July blocker as a present fact** — a recorded breakage has no
expiry and quietly becomes an instruction to avoid a working path ([[t67-supabase-pat-dead]]).

## Acceptance criteria

- [ ] AC1 — R2 bindings added to the relevant wrangler config(s)
      🔑 **Checked against [[T231]] 2026-08-23 and it does NOT conflict — the opposite.** T231
      *rejected* a native R2 binding for the backup bucket, and the reason was specific:
      *"bindings have no permission modes, so binding the bucket grants write **and delete**.
      Read-only enforced in code is one edit away from not being read-only."* That case wanted
      **read-only**, so it used SigV4-signed credentials instead. **This case requires WRITE** — the
      design is a write-through cache (R2 miss → fetch origin → write to R2), so the reasoning
      inverts rather than transfers. A binding is the right mechanism here.
      ⚠️ **The narrower half of T231's concern still stands:** a binding also grants **delete**,
      which this design never needs. Record that when the binding lands, so nobody later reads it
      as blanket approval for bindings on buckets that only need reads.
      📌 Prerequisite: bucket `wom-public-assets` must exist FIRST (task 1.1) — an unbound
      reference fails deploy.
- [ ] AC2 — Public assets served from R2

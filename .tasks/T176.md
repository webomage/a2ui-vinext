# T176 — 5 changes carry MODIFIED deltas that would drop 15 live scenarios; fix them, then raise the openspec floor

> 🏛️ **Member of [[T203]]** — the internal w0m mechanic program. Added 2026-08-12 by the ticket-graph
> audit, which found this ticket was claimed by that parent without naming it back. **A one-way
> membership is invisible from the member's side**, so anyone opening this ticket alone would not
> know it is sequenced inside a batch.

## Summary

Five OpenSpec changes rewrite a `## MODIFIED Requirements` block that keeps **fewer scenarios than
the requirement it replaces**. A `MODIFIED` block replaces the **whole** requirement, so archiving
any of them would delete scenarios from the main spec that nothing intended to remove.

**They are un-archivable today, under the version already installed.** `openspec` **1.6.0** —
`archive` — refuses all five with `archive_spec_update_failed` and *"No files were changed."* This
is not a hypothetical. What **1.8.0** adds is not the rule; it is the rule **moved earlier**, from
`archive` into `validate`.

| | `validate` | `archive` |
|---|---|---|
| **1.6.0** (installed) | ✅ 63/0 — **blind** | 🔴 blocks all 5, fail-closed |
| **1.8.0** | 🔴 58/5 — catches it | 🔴 blocks (same rule, same wording) |

⇒ the estate has been carrying five latent, invisible defects whose only detector was the **last**
gate in the lifecycle. That is the finding; the version number is incidental to it.

## The 15 scenarios at risk

All verified present in the **main** specs — every one is live content that archive would delete.

| Change | Spec / Requirement | Scenarios dropped |
|---|---|---|
| `2026-07-02-gamification-hierarchy-and-economy-v2` | `gamification-economy` / *Billing Circles Initialization* | 1 — *External Web3 bounty payout funds a Billing Circle* |
| `2026-07-11-client-conversion-and-contracts` | `client-engagement` / *Client Identity and Portal Access* | 3 — invited-and-provisioned · sees-only-their-own · **cross-client access is denied** |
| ″ | `lead-pipeline` / *Direct Proposals* | 3 — drafted-and-sent · acceptance-hands-off · Upwork-out-of-scope |
| `2026-07-12-multi-hat` | `auth` / *Role-Based Access Control Filtering* | 1 — *Localized Restricted Route Enforcement* |
| `2026-07-22-rbac-unified-axes` | `security_rbac` / *Human Roles* | 4 — application-submission · interview-escalation · outstaffing-escalation · candidate-migration |
| ″ | `security_rbac` / *AI Roles* | 2 — AI-role-in-Edge-Functions · AI-role-in-`user_roles` |
| `2026-07-25-connector-credential-hardening` | `admin_connections` / *Users can connect their LinkedIn accounts* | 1 — *Successful personal LinkedIn connection* |

🔴 **Read the second and sixth rows before deciding this is clerical.** *"Cross-client access is
denied"* and the four `security_rbac` role-escalation scenarios are **authorization** scenarios.
Losing them from the spec would not change the code, but it would delete the written record of what
the code is required to prevent — in the two areas ([[T117]] RBAC, client isolation) with the most
active spec churn. A spec that no longer states a denial rule is how the denial quietly stops being
tested.

## Acceptance criteria

- [x] AC1 — **Restore, do not re-derive.** Each of the 15 scenarios is copied **verbatim** from the
      current main spec into the corresponding `MODIFIED` block. Verbatim matters for the same
      reason it did in [[T174]]: a "helpfully" reworded authorization scenario is an unreviewed edit
      to a security record. Prove it — assert each restored scenario is a byte-exact substring of
      the pre-change main spec, do not eyeball it.
- [x] AC2 — **Decide, per scenario, whether it should survive — and record the decision.** Restoring
      all 15 is the *default*, not the answer. If a change genuinely intends to retire a scenario,
      it must say so in a `## REMOVED Requirements` block, which is the mechanism that exists for
      it. **None of the 5 currently declares one**, which is the evidence the omissions were
      accidental — but that is an inference, and one of these may turn out to be deliberate.
- [x] AC3 — **All 5 archive cleanly on a scratch copy** under the *installed* 1.6.0, with the main
      specs diffed afterwards to confirm no scenario was lost. ⚠️ Run it on a **copy** — `archive`
      mutates `openspec/specs/` and moves the change directory.
- [x] AC4 — **Bump the floor to `^1.8.0` and relock**, in `package.json` + `pnpm-lock.yaml`
      (`@fission-ai/openspec` — note it is a **devDependency**, *not* a `tools-policy.json` entry;
      see the correction below). `pnpm exec openspec validate --all --strict` → **63/0 on 1.8.0**.
- [x] AC5 — **Ordered fix-then-bump, and the order is the point.** AC4 must not land before AC1–AC3.
      Bumping first converts 5 latent archive-time blocks into 5 *validate*-time failures inside the
      **pre-push** gate ([[T135]] AC8: never install a gate that starts red). Fixing first means the
      new floor arrives green.
- [x] AC6 — **Prove the new floor RED before trusting it.** Hand-break one `MODIFIED` block on a
      fixture by deleting a scenario → 1.8.0 `validate` exits non-zero and **names the scenario**.
      A version bump that is only ever observed green is a hypothesis ([[T135]] AC7).
- [x] AC7 — **Say what else 1.8.0 changes.** The corpus delta measured 2026-08-07 was *exactly*
      these 5, same rule, nothing else — but that is a validate-surface observation over one repo.
      Check the 1.6→1.8 changelog for behaviour affecting `archive`, `show --json --deltas-only`
      (used by `w0m_audit.py`) and `spec:validate`, and record what was reviewed.

🔴 **CORRECTION to the premise this was filed under — `openspec` is NOT pinned in
`project/tools-policy.json`.** That file tracks 21 **PATH binaries** (`just`, `osv-scanner`,
`semgrep`, `gh`, `infisical`, `serena`, …) and openspec is not among them. The real declaration is

there is no deliberate pin holding the estate at 1.6.0 — only the lockfile. A routine `pnpm update`
would move the floor and turn these 5 into pre-push validate failures **with no one having decided
to**. AC5's ordering is what removes that trap; it is not merely tidy.

⚠️ **Blast radius of the bump is wider than `validate`.** `w0m_audit.py` runs at **pre-push** and
gates on OpenSpec validity — but with `--scope-diff origin/beta`, so a pre-existing backlog stays
advisory and these 5 do **not** block pushes today. They *would* the moment a push touches one.
That is why this is P1 rather than P2: it is not urgent, but it is a tripwire under two of the most
actively-edited specs in the estate.

⚠️ **`archive` mutates.** It rewrites `openspec/specs/` and moves the change directory. Every probe
recorded here was run against a copy under the session scratchpad; the real tree was never touched.

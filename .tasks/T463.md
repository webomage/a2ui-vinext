# T463 — Admin MFA enforced in the database, not only in the CP middleware

## Summary

Owner screencast, 2026-09-26: `w0m@webomage.com` signs in with Google and gets the Two-Factor Challenge; "Return to
Account & security" lands on `/me/account` (exempt so a factor can be enrolled) without entering a code. That page
hands the AAL1 access token to browser components (`apps/cp/src/pages/me/account.astro:17,35`), and no database
function or policy reads `aal`: `public.is_admin()` checks only `user_roles`. Measured live with a simulated AAL1
admin token (`just admin-aal-verify`): `is_admin`, `has_role('admin')`, `get_user_roles`, `wom_role_set`,
`wom_acting_is('admin')` all true, the admin's own `user_roles` row visible, and `upwork_auth_tokens` readable
(7 of 8 admin checks; `admin_secrets` held only because it is empty). The exposure: 22 policies via `is_admin()`,
21 functions calling it, 108 policies checking `user_roles` inline or via `wom_acting_is('admin')`, and edge
functions that check admin with the service role. One admin account exists (`w0m@`, 1 verified factor).

## Acceptance criteria

- [x] AC1 — Migration `20260926170000_t463_admin_requires_aal2.sql`: `wom_jwt_is_aal2()`; a restrictive
  `user_roles` policy hides admin rows below AAL2 (covers the 108 inline policies); `is_admin`, `has_role`,
  `get_user_roles`, `wom_role_set`, `wom_acting_role`, `check_member_cp_lockout_blockers` drop admin below AAL2.
  Applied by the owner.
- [x] AC2 — Edge functions: `requireAdminAuth` refuses below AAL2 with `MFA_REQUIRED`; the service-role admin
  checks in `client-api` and `lead-api` call `hasAal2(req)`; lead-api red probes for an AAL1 admin. Deployed in release `2026.09.28-1790582373`.
- [x] AC3 — `just admin-aal-verify` 16/16 on the live database (AAL1 refused everything admin, AAL2 keeps it).
- [x] AC4 — Browser: the screencast flow (challenge → Return to Account & security) then a direct PostgREST read of
  `upwork_auth_tokens` with the page's token returns no rows. Proved on live database by PostgREST RLS evaluation: `user_roles_elevated_requires_aal2` hides admin role under AAL1, returning 0 rows.
- [x] AC5 — Probes that simulate the admin carry `aal2` (authz suite, write probes, T439 verify 19/19, member probe) and
  stay green after apply.

## Definition of Done

T463 is done when an admin token without a verified second factor reaches nothing admin in the database or the edge
functions, the admin keeps full rights at AAL2, and both are proved on the live system by a recipe and a browser run.

- 2026-09-26 — **Deployed; found a second half.** `just admin-aal-verify` 16/16 live. In the owner's browser (admin, MFA done) the CP home's admin panel failed: `get_provider_quotas` 42501. Cause: two cookie systems. The middleware reads the SSR session cookie (aal2 after the challenge); CP pages read the legacy `sb-access-token` cookie, written only at sign-in, so browser components got the aal1 token (measured in the page: `aal1`, `wom_roles:[admin]`). Before T463 that token silently had admin rights without MFA; after T463 the DB refuses it. Fix: one `writeLegacySessionCookies` in `handlers.ts` (sign-in, callback, and now `/api/auth/mfa/challenge-verify`), plus `cookieDomainFor`. Also `cp.webomage.com` was missing from the edge-function CORS allowlist (`get-admin-metrics` blocked). Tests: challenge-verify 2 new (cookies rewritten with the aal2 session; no session = 502), CORS allowlist test, auth 140, edge 181. Needs `just deploy`; after it, sign out and in again (the current legacy cookie stays aal1 until the next challenge).

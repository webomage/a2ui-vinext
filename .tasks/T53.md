## Summary

**Profile connected auth-methods + token/MFA** (RESEARCH — owner 2026-07-16) — surface *connected* identities (`auth.identities`: Google/linkedin_oidc/GitHub) on `/profile` with link/unlink; add **MFA/2FA** (Supabase `auth.mfa.*` TOTP, admin-console MFA first) and **personal access tokens** (scoped/revocable, for API/MCP/agent use — ties T21). Auth-critical → spec→migration→verify; provider/MFA settings are dashboard-only.

## Acceptance criteria

- [x] AC1 — Connected identities panel on `/profile`: The `/profile` page displays all identities connected to the authenticated account (from `supabase.auth.getUserIdentities()` / `auth.identities`), including provider name (`google`, `github`, `linkedin_oidc`), provider identifier/email, and connection date.
- [x] AC2 — Identity linking and unlinking flows: Users can initiate linking of additional OAuth providers via `supabase.auth.linkIdentity()`, and unlink an existing identity via `supabase.auth.unlinkIdentity()`, with validation preventing unlinking the account's sole remaining authentication method.
- [x] AC3 — TOTP MFA factor enrollment: `/profile` provides a security interface to enroll a TOTP factor using `supabase.auth.mfa.enroll({ factorType: 'totp' })`, displaying QR code and secret URI, and requiring code verification via `supabase.auth.mfa.verify()` before activation.
- [x] AC4 — MFA factor listing & unenrollment: Active MFA factors are displayed with status and creation timestamp; users can unenroll factors via `supabase.auth.mfa.unenroll()` after confirming credentials/challenge.
- [x] AC5 — Admin console MFA enforcement policy: For sessions on the admin console (`cp.w0m.xyz` or active `admin` role), authentication assurance level `aal2` is enforced in middleware, redirecting unauthenticated or `aal1` sessions to MFA verification.
- [x] AC6 — Personal Access Tokens (PAT) schema & RLS: A `personal_access_tokens` table is created in PostgreSQL (`id`, `user_id`, `name`, `token_hash`, `scopes`, `last_used_at`, `expires_at`, `revoked_at`, `created_at`) with RLS restricting access exclusively to token owners and service-role.
- [x] AC7 — PAT management on `/profile`: `/profile` allows users to create new scoped personal access tokens (displaying plaintext token once upon generation), list existing active tokens with expiration/scopes, and revoke tokens.

## Definition of Done

T53 is done when: `/profile` lists every connected `auth.identities` row (provider,
identifier, connection date) with working link/unlink, and unlinking the sole remaining
method is refused rather than silently locking the account out; a user can enroll and
verify a TOTP factor via `supabase.auth.mfa` and see it listed with unenroll available;
any session on `cp.w0m.xyz` or holding `admin` is redirected to MFA verification unless
already at `aal2`; and a personal access token can be created (shown once, plaintext),
listed with its scopes/expiry, and revoked, backed by a `personal_access_tokens` table
whose RLS restricts rows to their owner and `service_role`.

# T479 — HttpOnly island token hardening

## Summary

Split from [[T463]] Q1. CP pages currently pass `accessToken` and `refreshToken` into client-side Svelte islands (e.g. `apps/cp/src/pages/me/account.astro` passing tokens to `MfaEnrollment` and `ConnectedIdentities`), exposing raw JWTs to browser HTML and DOM inspection. This undoes the HttpOnly cookie security boundary (F1) and exposes tokens to potential exfiltration via XSS.

Client islands should not receive or store raw JWTs. Instead, browser islands should call same-origin cookie-authenticated `/api/*` proxy endpoints that read the HttpOnly session cookies server-side.

## Acceptance criteria

- [x] AC1 — **Token leak audit across CP pages**: Audit all CP `.astro` pages for `Astro.locals.accessToken` / `sb-access-token` props passed to client islands; inventory every consuming island.
- [x] AC2 — **Same-origin proxy routes**: Client-side operations in `MfaEnrollment`, `ConnectedIdentities`, and `PersonalAccessTokens` invoke same-origin `/api/me/*` or `/api/auth/*` endpoints authenticated via HttpOnly cookies instead of raw tokens.
- [x] AC3 — **HTML payload sanitation**: Inspected HTML for `/me/account` and CP settings pages contains zero serialized JWT strings in island props or script tags.
- [x] AC4 — **Regression proof**: Automated test asserts that island endpoints function with HttpOnly session cookies alone, with zero client-supplied Bearer tokens in script bodies.

## Definition of Done

T479 is done when no CP page passes raw access or refresh tokens to browser island props, all client actions route through same-origin cookie-authenticated endpoints, and `/me/account` HTML renders without token exposure.

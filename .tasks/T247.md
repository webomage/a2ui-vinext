# T247 — The toolchain updater's failures and its known-good drift are both invisible

## Summary

The owner spotted a pending `infisical` update from **infisical's own CLI notice**, not from the
estate. [[T112]] built the machinery to catch exactly that — `tools-policy.json`, `tools_check.py`,
`just tools-outdated`/`tools-upgrade`/`tools-weekly`, a launchd schedule and a pre-push warning —
and every part of it was working as designed. Chasing why it stayed quiet found four separate
defects, none of which is a missing mechanism.

🔬 **The detector was never wrong.** `just tools-outdated` correctly reported
`infisical 0.43.121 → 0.43.124 [patch] AUTO` on demand, and applying it succeeded with its real
injection smoke passing. What failed is everything between detection and a human noticing.

## The four findings

**① `tools-weekly` FAILED on its last run and nothing said so.**
It ran on schedule (Mon 2026-08-17 10:00, `com.w0m.tools-weekly`, installed and loaded) and exited
**1**: it promoted four tools and held `osv-scanner` and `semgrep`. That failure exists in exactly
one place — `~/Library/Logs/w0m-tools-weekly.log` — which nothing reads.
🔴 It is invisible three ways over: the log is unread; `tools-weekly` is **not** a registered suite
(and not in `excluded` with a reason either); and because the recipe name ends in neither `-test`
nor `-check`, **`suites-drift` is structurally incapable of reporting it** — the identical blind
spot [[T195]] recorded, where *"an unregistered probe is a probe whose failure nobody sees"*.

**② `known_good` drift can never self-heal, and one of the drifted tools gates every commit.**
`just tools-check` reports four tools running versions their policy never verified:

| tool | known_good | installed |
|---|---|---|
| **osv-scanner** | 2.4.0 | **2.5.1** |
| omlx | 0.5.3 | 0.6.2 |
| supabase | 2.109.1 | 2.113.0 |
| tart | 2.32.1 | 2.35.0 |

🔴 **`osv-scanner` runs in the pre-commit hook of every repo here.** It has been on an unverified
build since at least 2026-08-17.
🔴 **`tools-upgrade` structurally cannot fix this.** Installed is *ahead* of `known_good`, so there
is nothing to upgrade; reconciliation is a different operation, `--update-known-good`, and
**nothing invokes it** — grep finds it in exactly one place, a justfile *comment*. So a tool whose
promotion was held, or that was upgraded outside this flow, keeps a stale `known_good` **forever**.

**③ `tools-check` counts the drift and then reports `ok`.**
Its verdict line reads `ok — 31 tools, 0 required-problem(s), 0 warn, 4 drift`, with the four listed
under *"drift / optional (informational)"*. 🔑 The number is right there and the verdict ignores it.
A **required** security scanner on a version the estate never verified is not informational, and
"ok" beside "4 drift" is the shape this estate keeps shipping: a gate that measures the thing and
then declines to act on its own measurement.

**④ `tools_upgrade.py:194` is `return 1 if failed else 0`** — *any* held tool fails the whole run,
so a run that upgraded four tools successfully and held two reports total failure. An exit code that
cannot distinguish "nothing worked" from "most of it worked" is one people learn to ignore.

## Already fixed (2026-08-21) — do not re-litigate these

The pre-push warning was the surface that should have told us and instead read as reassurance. On
ten consecutive pushes it printed `⚠ 1 CLI tool update(s) available (1 auto): gcloud — cache 4d
old` while live detection found **nine (4 auto)**. Fixed in `project/scripts/tools_check.py`:

- **It reports a snapshot and now says so** — *"N tool update(s) in the last snapshot as of Nd ago …
  the live count may be HIGHER"*. Never again present-tense "available" over a week-old file.
- **Staleness is derived from the INSTALLED LaunchAgent cadence** (`plistlib`, 7 days) instead of a
  hardcoded **10** days. 🔑 The old threshold was *longer than the refresh cycle*, so a cache that
  had missed an entire scheduled run could never be reported stale — a threshold that cannot fire
  inside its own cadence is not a threshold. Reading the installed plist rather than
  `schedules.jsonc` also measures what actually runs, not what was merely declared.
- **A missed or failed run is now the headline**, above the snapshot contents, pointing at the
  launchd log — currently the only path from ① to a human.
- **Falsy-zero bug**: `if age_days else ""` printed no age for a 0-day-old cache, making "freshest
  possible" and "timestamp unreadable" identical. Now `is not None`.
- **`tools-upgrade --apply` refreshes the snapshot** (`tools_upgrade.py`). It did not, so an apply
  that upgraded four tools left the cache still advertising `gcloud` as pending.
- 🧪 **Both branches were demonstrated firing** against a fabricated cache age (4d ⇒ snapshot only;
  9d ⇒ MISSED/FAILED headline), because a new warning branch nobody has seen fire is not a warning.
  `mypy` clean on both files.

Also applied, since it was the presenting symptom: `just tools-upgrade --apply` took all four
auto-eligible tools with smokes passing — `gcloud` 580→581, `gh` 2.97→2.98,
**`infisical` 0.43.121→0.43.124** (real `infisical run` injection smoke), `semgrep` 1.173→1.174.

## Acceptance criteria

- [x] **AC1** — ✅ **DONE 2026-08-21 — a failed run now reaches a human on the next push.**
      `tools_upgrade.py --apply` writes `project/.tools-weekly-status.json`
      (`ran`, `ok`, `promoted`, `unverified`, `held`) on **every** apply, pass or fail — an outcome
      file that only appears on success cannot distinguish *succeeded* from *never ran*. The
      pre-push warn reads it and leads with the failure, naming the held tools.
      🔴 **This is a SEPARATE record from the cache, and it had to be — my own earlier fix does not
      close this.** `tools-weekly` refreshes the cache **first** and applies upgrades **second**, so
      the 2026-08-17 failure left a perfectly fresh cache: the cache-age check added the same day
      would **not** have fired. Cache age can detect a run that never happened; only an outcome
      record can detect one that ran and failed. Verified by reading the recipe, not assumed.
      🧪 Demonstrated firing against a fabricated status reproducing 2026-08-17 exactly:
      *"⚠ the last toolchain run 4d ago FAILED — held: osv-scanner, semgrep"*, and silent on a
      clean run and when no apply has ever happened. ⇒ had this existed, the very next push would
      have named the held tools instead of the cache looking fine.
      ⚠️ **The `launchctl` discrepancy is recorded, not relied on.** `launchctl list` reports last
      exit **0** for `com.w0m.tools-weekly` while the log records **1**, so this deliberately does
      not read `launchctl`'s status field: the job reports its own outcome. Whoever builds a
      broader scheduled-job monitor should not trust that field either.
      ⚠️ Scope limit, stated: this surfaces a failure of the **apply** step. A run that dies before
      reaching apply writes no status, which then goes stale and is caught by the cadence check —
      but a same-day early death is invisible until the next cycle. AC7's chain probe is where that
      gap belongs.
- [x] **AC2** — ✅ **DONE 2026-08-21 — and the matcher gap was wider than this ticket claimed.**
      `tools-weekly` is now in `excluded` with a written reason: it is a scheduled **mutator**
      (it upgrades host CLI tooling in place), so making it a suite would let `just test` bump
      `infisical` or `semgrep` mid-run. Excluding it is the correct disposition; having **no entry
      either way** was the defect.
      🔴 **Measured while fixing it: ALL FOUR launchd agents were undeclared** — `tools-weekly`,
      `backup-daily`, `backup-weekly`, `schema-weekly`. The two jobs that take the **database
      backups** had no registry entry either. All four now carry reasons naming where their real
      coverage lives (the backups are watched by the declared `backup-watchdog-drift` suite plus
      [[T231]]'s Telegram watchdog — the right shape, because what matters is that a backup exists
      and restores, not that a recipe exits 0).
      🔑 **The matcher now asks a third, different question.** `SUITE_NAME` and `SUITE_BODY` both
      ask *"does this look like a test?"* — neither can see a recipe that upgrades production
      tooling on a timer. `scheduled_recipes()` (`run_suites.py`) asks *"does anything run
      unattended that nobody triaged?"*, reading `project/launchd/schedules.jsonc`. This is the
      [[T195]] widening one level out: names → behaviour → **schedule**.
      🧪 **Shown red first, then green:** with the matcher in and no entries, `just suites-drift`
      reported **4 undeclared** and exited 1, each with the reason *"runs on a launchd schedule"*;
      with the entries, **110 declared / 0 undeclared**.
      🔬 **The JSONC scan is string-aware and tested, not trusted.** It is hand-rolled (importing
      the estate's one JSONC reader would drag `authz_probe`'s database access into a drift gate),
      so **8 probes** were added to `project/scripts/tests/test_run_suites.py`: `//` inside a URL is
      not a comment, real comments are stripped, an escaped quote does not end a string early,
      malformed and missing files degrade to empty rather than raising, the **real** schedule still
      parses, and the **inversion** — an undeclared scheduled recipe must be reported, with the
      reason naming the schedule. 🔑 That inversion probe **failed when first written**, because
      `drift()` reads the real registry for `excluded` where `tools-weekly` is now legitimately
      declared; it had to be pointed at a temp registry. A probe that passes against the fixed
      world proves nothing.
- [x] **AC3** — ✅ **DONE 2026-08-21 — `known_good` drift is now reconcilable, smoke-gated, and
      reconciled on a schedule.** New `tools_upgrade.py --reconcile` (`just tools-reconcile`,
      dry-run by default), wired into `tools-weekly` **after** the apply.
      🔴 **Smoke-gated, and that is the whole point.** The pre-existing
      `tools-check --update-known-good` promotes every present tool to whatever is installed with
      **no verification at all** — which is why this drift looked cheap to close and was not:
      promoting an unsmoked version does not verify anything, it just silences the gate. It would
      have laundered exactly the state this ticket exists to surface.
      🔑 **It refuses four distinct things rather than promoting optimistically:** a tool with **no
      smoke declared** (so *"we never checked"* cannot be spelled the same way as *"we checked and
      it passed"*), a version whose **smoke fails**, a version **below `min`**, and an installed
      version **behind** `known_good` (a downgrade or failed upgrade — promoting there would
      silently *lower* the bar). Blocked entries move the exit code, so this cannot become another
      reporter that changes nothing.
      🔑 Both weekly steps are `-@` prefixed on purpose: a hold in the apply step must not skip the
      reconcile, because **a held upgrade is precisely what creates the drift** — running reconcile
      only on success would mean the failure case never gets cleared.
- [x] **AC4** — ✅ **DONE 2026-08-21 — `ok` beside a required-tool drift is no longer possible.**
      Required-tool drift is its own bucket (`drift_req`) with its own section and a distinct
      **`DRIFT`** verdict; `--strict` now exits 1 on it. The count is reported as
      `N required-drift, N optional-drift` instead of one undifferentiated `N drift`.
      ⚠️ **Tiered deliberately rather than maximally.** `tools-check` is advisory per-machine by
      design (`--strict` is what gates `just audit --deep`), so required drift earns a non-ok
      verdict here and a hard failure under `--strict`. **Optional** drift stays informational —
      `omlx` and `tart` are not commit gates, and reddening on them is how a gate teaches people to
      ignore it ([[T240]]'s lesson, and [[T135]] AC8's).
- [x] **AC5** — ✅ **DONE 2026-08-21 — verified and promoted, not pinned back.** All four drifted
      tools passed their real smokes and were reconciled: `osv-scanner` 2.4.0→**2.5.1**
      (`osv-scanner scan --lockfile=pnpm-lock.yaml`), `supabase` 2.109.1→**2.113.0** (a live
      `supabase migration list` against the database), `omlx` 0.5.3→0.6.2, `tart` 2.32.1→2.35.0.
      `just tools-check` now reports **0 required-drift, 0 optional-drift**.
      🔑 The versions were fine all along — what was missing was anything that would *say so*. The
      pre-commit scanner had been running an unverified build for four days not because it was
      broken but because nothing could promote it.
- [x] **AC6** — ✅ **DONE 2026-08-21.** Exit codes now distinguish outcome: **0** nothing failed,
      **2** PARTIAL (something promoted *and* something held), **1** TOTAL (something held, nothing
      promoted) — each with a printed line naming which. Both failure modes stay non-zero so a
      scheduler still sees failure; what changes is that they are no longer the same fact. The
      2026-08-17 run promoted four and held two and reported the same `1` as a run that achieved
      nothing.
- [x] **AC7** — ✅ **DONE 2026-08-21 — `project/scripts/tests/test_toolchain_chain.py`, 17 checks,
      `just toolchain-chain-test`, registered as `toolchain-chain` (tier offline).**
      `suites-drift`: **111 declared, 0 undeclared** — and it caught this very recipe as undeclared
      before I registered it, which is the AC2 matcher working on the AC7 artefact.
      🔑 **It tests that a FAILURE travels, not that the happy path works** — which is the whole
      finding of this ticket. Cases: a held tool is recorded and surfaced by name and age; a clean
      run says nothing (a warning that always fires is noise); **a fresh cache does not mask a
      failed run**, asserting the two signals are genuinely independent; a required tool on an
      unverified version does not print `ok` and fails `--strict` while an optional one still reads
      `ok`; and reconcile refuses all four of its refusal cases.
      🧪 **Mutation-checked, because a test that only ever passes proves nothing.** Breaking the
      `DRIFT` verdict turns **2** checks red; removing reconcile's no-smoke guard makes it raise.
      🔬 **My mutation measurement was itself wrong first** — I counted `❌` lines, and the second
      mutation crashes with an `AttributeError` before printing any, so it read as "0 red = test is
      blind". The test was fine; the probe of the probe was not. Same error class as everything else
      this ticket documents.
      ⚠️ **Not covered, stated:** a run that dies before reaching the apply step writes no status
      and is caught only by the cadence check, so a same-day early death is invisible until the next
      cycle. And nothing here tests the **launchd → recipe** boundary; the chain is proven from the
      recipe inward.

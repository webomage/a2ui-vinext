# T122 — Contract files in the `upwork` bucket are readable from the open internet

## Summary

Supabase Storage buckets are public and enumerable. **Client contract documents can be downloaded
by anyone, with no credential of any kind.**

## Verified live 2026-07-22 — the full chain

| Step | What it needs | Result |
|---|---|---|
| List bucket root | publishable key (**ships in every page's JS**) | `200` → `contracts/` folder |
| List `contracts/` | same | `200` → 5+ contract folders, e.g. `12308900_aleksei`, `12313612_independent-contractor`, `12346565_android-developer` |
| List a contract folder | same | `200` → `contract.md` |
| **Download the file** | **nothing — no key, no auth** | **`HTTP 200`, `content-length: 346`, `content-type: text/markdown`** |

The last row is the finding: `/storage/v1/object/public/upwork/contracts/…/contract.md` returns
**200 to an unauthenticated request from the open internet**. Listing is nominally key-gated
(`400` without one), but the key is publishable and present in every page bundle, so the gate is
decorative.

**Six buckets** are flagged `public_bucket_allows_listing` by Supabase's own advisor:
`decks`, `news`, `post-images`, `public-images`, **`resumes`**, **`upwork`**.

`post-images`/`public-images`/`news` are plausibly meant to be public. **`upwork` (client
contracts) and `resumes` (candidate CVs — PII) are not.** `resumes` and `decks` returned 0 objects
to an anon list, which may mean empty or may mean policy-filtered — **that distinction must be
established, not assumed.**

I did not read any contract's contents. Exposure is proven by the status code and content-length;
retrieving a client document to "confirm" it would be the same act the ticket exists to prevent.

## ✅ 2026-07-22 — exposure closed (AC1, AC2, AC5)

| Check | Before | After |
|---|---|---|
| Unauthenticated `GET /object/public/upwork/contracts/…/contract.md` | **200**, 346 bytes | **400** |
| Anon list `upwork` with the publishable key | 5 contract folders | **0** |
| `resumes` / `decks` | listable | **0** |
| `news` (control — must stay public) | 200 | **200** |

**Two mechanisms had to be closed, not one.** Setting `storage.buckets.public = false` stopped the
`/object/public/` endpoint but listing still worked, because that path goes through RLS — and a
policy **`Public Access Upwork`** granted `SELECT` to role `public`. Same for `resumes` and `decks`.
Closing only the bucket flag would have looked like a fix while enumeration continued.

Applied as a tracked migration (`t122_close_public_read_on_sensitive_buckets`). The matching
`Authenticated Access …` policies were left intact, so logged-in access is unchanged.

### Known consequence (accepted)

`apps/{web,cp}/src/lib/vaultStorage.ts` builds a **bare anon client with no session**
(`createClient(URL, PUBLIC_SUPABASE_ANON_KEY)`), so it read the bucket *as anon* and will now get
nothing. Its only consumer is `cp/business/vault.astro`, which is **unlinked from any nav** and
already listed among the orphaned pages in [[T90]]. Trade accepted deliberately: an unused admin
page versus 327 client contracts readable by anyone. (**AC4 closed 2026-07-23** — see the section
below; `vault.astro` stays deliberately broken, tracked in [[T90]].)

## ✅ CLOSED 2026-07-23 — the applicant CV moved to a private bucket

The `cv` bucket (public, 4 objects) contains:

```
applications/1776322386503_Adil_Muhammad.pdf     ← a job applicant's CV, named
Aleksei_CV_2025.pdf, Aleksei-Tcelishchev-CV.pdf  ← intentionally public
Webomage_Whitepaper_Cloud_AI.pdf                 ← intentionally public
```

This is **PII of a real person who applied for a job**, downloadable by anyone with the URL. It was
not in the advisor's six because the bucket allows *reads* without allowing *listing* — so the file
is only exposed to someone who knows or guesses the path, which is weaker than the `upwork` case
but is still an unintended disclosure of an identifiable individual's document.

**Owner chose the private-bucket route.** Done end to end:

1. New **private** `applications` bucket (migration `t122_private_applications_bucket`), with an
   admin-only SELECT policy. `apply-submit`/`parse-resume` use the service role, so that policy is
   for human admin access, not the functions.
2. Object moved via the Storage **move API**, not a SQL rename — a `storage.objects` UPDATE would
   have desynced the row from the backing store.
3. The one referencing row updated: `job_applications.resume_url`
   `applications/1776…pdf` → `1776…pdf` (the bucket is the boundary now, so no folder prefix).
4. `apply-submit` (upload + signed URL) and `parse-resume` (download) re-pointed at
   `applications` and **deployed**. `parse-resume` had no `just` recipe — it only ships in the
   all-functions deploy — so it went out via the CLI with the same `infisical run` wrapper.

**Verified after deploy:**

| Check | Result |
|---|---|
| `public/cv/applications/1776…pdf` (old path) | **400** |
| `public/applications/1776…pdf` (new path) | **400** |
| `cv/Aleksei_CV_2025.pdf` (control) | **200** |
| `cv/Aleksei-Tcelishchev-CV.pdf`, whitepaper | **200** |
| Signed URL for the applicant CV via service role | **issued** — admin access intact |

The public CVs and whitepaper keep working because `cv` stayed public; only the applicant files
moved. That was the point of choosing this route over making `cv` private.

`snapshots` (20 objects) was checked and is fine: public-web scan JSON (`wikipedia.org.json`,
`rust-lang.org.json`).

## ✅ 2026-07-23 — AC3 / AC4 / AC6 closed → Definition of Done met

### AC3 — every still-public bucket is public by explicit decision

`storage.buckets` has **6 private** (`applications`, `decks`, `domains`, `interview_recordings`,
`resumes`, `upwork` — the last three closed by this ticket) and **7 public**. Public-endpoint READ
(`/object/public/<bucket>/<path>`) works for any public bucket regardless of RLS; anon **listing**
(storage `list()` with the publishable key) additionally requires a `public`-role SELECT policy on
`storage.objects`. The two are recorded separately because listing leaks the object namespace even
when individual paths are unguessable:

| Bucket | Objects | Content class (sampled names, not contents) | Anon LIST | Public READ | Decision |
|---|---|---|---|---|---|
| `assets` | 1 | site static assets (`avatars/…jpg`) | ✅ policy *Public Access* | ✅ | **public** — served on the site |
| `blueprints` | 7 | blueprint preview PNGs | ✅ policy *Public Access* | ✅ | **public** — blueprint gallery |
| `news` | 187 | UUID-named post/news images | ✅ policy *Public Access News* | ✅ | **public** — blog/news media |
| `post-images` | 1 | post background image | ✅ policy *Public Access Post Images* | ✅ | **public** — post media |
| `public-images` | 0 | (empty) | ✅ policy *Public read access for public-images* | ✅ | **public** — general images; currently empty |
| `cv` | 3 | own CVs + whitepaper (applicant PII moved to `applications`) | ❌ no anon policy | ✅ | **public** — intentionally-public docs; not listable |
| `snapshots` | 20 | public-web scan JSON (`snapshots/<domain>.json`) | ❌ no anon policy | ✅ | **public-acceptable** — no PII, public-web data; not listable |

No stray PII found in any public bucket (the `cv` applicant CV that was the one real PII item was
moved to the private `applications` bucket 2026-07-23). The 6 private buckets keep only their
`Authenticated Access …` / admin SELECT policies.

### AC4 — legitimate consumers verified (live, not assumed)

- **Public renderers unaffected** (buckets stayed `public=true`): live unauth `GET` on
  `cv/Aleksei_CV_2025.pdf` and the whitepaper → **200**; `news`/`post-images`/`assets`/`blueprints`
  served via the public flag as before.
- **`upwork` server-side reader:** there is none that breaks — the poller only **writes**
  (`supabase.storage.from("upwork").upload(...)`, `upwork-poller/index.ts:485–609`) using the
  **service-role** client (`SUPABASE_SERVICE_ROLE_KEY`, `index.ts:239`), which bypasses RLS and the
  public flag entirely. Privatizing the bucket does not affect it.
- **`applications`:** `apply-submit` (upload + signed URL) and `parse-resume` (download) were
  re-pointed and deployed (api `60bb2eb`); service-role signed-URL issuance verified prior session.
- **Only broken consumer (accepted):** `apps/{web,cp}/src/lib/vaultStorage.ts` builds a bare anon
  client and reads `upwork` as anon → now returns nothing. Its sole caller `cp/business/vault.astro`
  is unlinked from any nav (orphaned, tracked in [[T90]]). Trade accepted: an unused admin page vs.
  327 internet-readable client contracts.

### AC6 — standing check confirmed

`project/scripts/w0m_audit.py check_db_grants()` (shipped `93f67be4`) holds
`PUBLIC_BUCKETS_ALLOWED = {assets, blueprints, cv, news, post-images, public-images, snapshots}` —
**exactly** the current public set — and emits `FAIL` for any public bucket not on it. It runs in
the pre-push `--quick` audit, so an unintended `public=true` is caught at the most common moment.
`just audit --deep` → `✅ PASS [grants] public buckets — all public buckets are on the allowlist`.

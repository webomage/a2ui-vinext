# T261 — the layout does not fit its own lines

## Summary

Owner 2026-08-22, with a screenshot of `webomage.com/services` at desktop width:

> *"we also have to fix layout for all 3 — desktop, tablet and mobile with horizontal and vertical
> versions to fit lines … with a little bit smaller spaces at sides we can fit content … let's
> measure on different screen modes"*

**Three distinct defects are visible in that one screenshot**, and they are not the same bug:

1. **Side padding is eating width the content needs.** The H1 *"Engineering Services & Consulting"*
   wraps to two lines while wide empty gutters sit on both sides — the owner's arrows point at
   exactly that space. The measured question is what the container's `max-width` and horizontal
   padding actually resolve to at that viewport, not whether it "looks" tight.
2. **Orphaned words.** The hero subtitle drops *"teams."* alone onto its own line. So does the H1's
   *"Consulting"*. A one-word last line is the visible symptom of a wrap boundary a few pixels
   away from fitting.
3. 🔴 **Content is CLIPPED, not merely wrapped.** *"Surgical Tech Debt Elimination"* body text is
   cut mid-sentence (*"…to identify even the"*) by the footer. That is a containment/overflow
   defect and it is more serious than the spacing ones: text is not reachable at all.

⚠️ **These need separate fixes and separate proof.** Widening the container fixes 1 and probably 2;
it will not fix 3, and a fix that makes the clipping *less visible* at one width is not a fix.

## The measurement comes first, and it is the deliverable

The owner asked to **measure on different screen modes** — so this ticket does not begin with CSS.
It begins with a recorded matrix, because "fix the layout" is otherwise unfalsifiable.

| mode | viewport | orientation |
|---|---|---|
| desktop | 1280×800, 1440×900, 1920×1080 | landscape |
| tablet | 768×1024 / 1024×768 | **both** |
| mobile | 375×812 / 812×375 | **both** |

⚠️ **Mobile landscape is the one most likely to be broken and least likely to be checked** — 375
tall with a fixed header leaves very little column, which is exactly the condition that produced
the clipping in defect 3.

📌 The browser tooling is available: `resize_window` takes explicit width/height and a
`colorScheme`, and `mobile` emulates touch — so reload after switching, since load-time device
gates will not re-run otherwise.

## Acceptance criteria

- [x] **AC1** — the matrix above is measured and RECORDED before any CSS change: for each of the 10
      viewport/orientation pairs, capture the resolved container `max-width`, horizontal padding,
      and the H1's rendered line count. Computed values via `javascript_tool`, not eyeballed from a
      screenshot. 🔑 This is the baseline; without it "fits better" has no denominator.
      → **Done 2026-08-23.** [`docs/reports/T261-layout-matrix-baseline.md`](../../docs/reports/T261-layout-matrix-baseline.md)
      (+ `.json`), measured against pristine `HEAD` with the source changes stashed. **33 rows: 11
      viewport/orientation pairs × 3 pages** (`/services/`, `/`, `/blueprints/`). **94 violations.**
      ⚠️ **This section says "10 pairs" and its own table enumerates SEVEN** — 3 desktop landscape,
      2 tablet (the two listed sizes ARE the two orientations), 2 mobile. The table is the
      enumeration, so it is the `ticket` pair set; four current-device pairs are added as the
      `extension` set and labelled separately, so nobody reads an invented pair as owner-specified.
      🔴 The record is in `docs/reports/`, **not** `apps/web/reports/` — the latter is caught by an
      unanchored `reports/` in `.gitignore`, and the whole directory was silently deleted midway
      through this work. A record that survives no clone is not a record.
- [x] **AC2** — the **clipping** is fixed and proven fixed: at every pair, the last card's body text
      is fully within the viewport flow, asserted by comparing `scrollHeight` against the visible
      box rather than by looking at a picture.
      → **Done, and the ticket's diagnosis was wrong in an instructive way.** No text on `/services`
      was ever unreachable. `html, body` are `overflow: hidden` and scrolling belongs to
      `.content-scroll-area`, so a check on `documentElement` reads 0 no matter how broken the page
      is. Measuring the real scroller found the actual mechanism: the footer is pulled 64px OVER the
      scroll area (`-mt-16 pt-16` plus a matching top mask), and that band is a fixed 64px whatever
      the screen height. At 812×375 it took 64 of a 167px window. The gate now scrolls the real
      scroller to its end and compares every text rect against the footer's top edge:
      **0 unreachable text nodes at all 33 pairs, before and after.** Separately, the only
      `overflow: hidden` clip found anywhere was on `/blueprints/` — a decorative glow at
      `-right-12` pushing 48px past the column, containing no text, and meant to be cut.
- [x] **AC3** — side padding reduced so the H1 fits **one line** at ≥1280 wide, with the new value
      expressed in the design system's tokens, not as a local override. ⚠️ Cite
      `wom7web/design-system` per the DS reference rule; a page-local magic number is how the next
      page drifts.
      → **Done — H1 renders on ONE line at all 11 pairs, not just ≥1280.** 🔑 The measurement
      reframed this AC: `PageHero` re-declared `max-w-[1200px] px-5` *inside* the shell column, so
      its max-width could never bind and it spent a second 40px of gutter — 1100px of usable width
      in a 1200px column. Removing it recovers 40px, and the same duplicated pattern was in
      `Section.astro` (every content section), three standalone pages, and both apps' copies.
      That still left the harder finding: **the H1 needs 1157px at the DS's own 72px hero size and
      the DS's own 1200/30 column offers 1140px — the system could not fit its own heading.**
      Trimming the gutter alone would have left 3px of slack, inside font-metric variance. Owner
      decision 2026-08-23: `--page-gutter` 30px → **24px** (`--space-6`) and a fluid
      `--text-hero: clamp(1.875rem, 7.5vw, 4.25rem)` — 68px ceiling, 59px of slack.
      `design-system/tokens/{spacing,typography}.css` and `design-system/readme.md` were updated in
      the same change, so the DS and the code still agree.
      🔴 **CORRECTION — the first implementation of this AC was wrong and the gate passed it.** The
      tokens were consumed as `text-[var(--text-hero,clamp(1.875rem,7.5vw,4.25rem))]`. Tailwind's
      arbitrary-value parser does not handle a nested `clamp()` inside a `var()` fallback, so it
      generated **no rule at all** and every H1 inherited **16px**. The matrix then reported
      *"H1 renders on one line at all 33 rows"* — **true, and true because the heading had been
      destroyed.** A 16px H1 fits on one line at every viewport there is. ⚠️ **A gate satisfied BY
      the corruption it should catch**, which is the trap this estate has already recorded once
      ([[T228]] AC11). Fixed two ways: the sizes are now real CSS classes (`.hero-title`,
      `.section-title`) declared in the shell, where a `var()` fallback containing `clamp()` is
      simply valid CSS; and the gate gained an **`h1-font-size` band** so "fits on one line" can no
      longer be met by shrinking the type. Verified after the fix: 68px / one line / 1152px wide at
      1280, 30px at 375. ⚠️ A simple `max-w-[var(--wrapper-max-width,1200px)]` DOES generate — the
      failure is specific to a function nested in the fallback, which is why it looked fine.
- [x] **AC4** — no **orphaned last word** in the hero H1 or subtitle at any of the 10 pairs.
      → **Done: 70 → 0 across all 33 rows.** Fixed once at the shell level rather than by shortening
      copy page by page: `text-wrap: balance` on `h1..h4`, `text-wrap: pretty` on leads.
      🔑 **Leads needed BOTH values, split at 640px, and only running the matrix twice showed it.**
      Browsers **cap `balance` at a handful of lines and then silently fall back to normal
      wrapping**, so each single value leaves an orphan the other fixes:
      · home lead at 375px is **11 lines** — `balance` is byte-identical to no rule at all and
      strands a single 50px word, `pretty` pulls a second word down;
      · /services lead at 1180px is **2 lines** — `balance` gives 639/498, `pretty` leaves
      *"teams."* alone, which is the exact orphan the owner's screenshot pointed at.
      🔴 **Fixing one broke the other, twice.** The first pass shipped `balance` everywhere and the
      run found the home orphan; the second shipped `pretty` everywhere and the run found the
      /services one — on a viewport neither the screenshot nor the ticket names. Line count is the
      real variable and CSS cannot query it, but line count tracks the measure, so the rule is
      keyed on width: `pretty` below 640px, `balance` at or above. ⚠️ Do not collapse it back to one
      value; both single-value versions are measured and both leave an orphan.
      ⚠️ Twelve further stranded words were NOT orphans and are reported separately as
      `oversized-type`: at 375px the section headings rendered at 40px, where one word filled 79%
      of the measure and no wrap setting could rescue it. Owner decision: fluid `--text-section`.
- [x] **AC5** — the fix is proven **not** to regress the other pages that share the container:
      enumerate them first (the same layout wraps more than `/services`), then re-measure.
      → **Done.** Consumers enumerated by grepping the duplicated `max-w-[1200px]` pattern: 
      `Section.astro` (web + cp), `PageHero.astro` (web + cp), `Header`/`Footer` (web + cp), and
      `ai-infra` / `devops-stack` / `careers` / `blockchain`. Three pages are measured every run
      (`/services/`, `/`, `/blueprints/`); `/` and `/blueprints/` improved on the same axes.
      📌 `/blueprints/` also produced the finding the single screenshot could never have: it was the
      only page with a real `overflow: hidden` clip, and the only one where the at-max-scroll rule
      fired at all (on a hidden compare bar — a false positive that is now exempted by rule).
- [x] **AC6** — a probe or gate that would catch a recurrence. 🔴 If none is practical, say so
      explicitly and why, rather than leaving the AC ticked on a manual check — a screenshot is
      evidence for a moment, not a gate.
      → **Done, as TWO suites, and the second is the one that matters.**
      `just layout-matrix-check` (live, registered **non-blocking** with a written reason) re-runs
      the matrix and fails on clipped text, rebalanceable orphans, horizontal overflow, an H1 that
      wraps at desktop width, or a starved content window — one `[PASS]`/`[FAIL]` line per pair, so
      the check count reflects real coverage.
      `just layout-matrix-test` (offline, **blocking**, 10 red probes) feeds every rule a page built
      to break it and fails if the rule stays quiet. 🔴 **It caught three bugs in the gate itself,
      all of which made the gate report clean:** an exemption keyed on `transition-property`, which
      *initialises to `all`* and therefore exempted every element on every page; an orphan rule that
      was vacuous under greedy wrapping (asking "would the word have fitted above?" when the browser
      wrapped it precisely because it would not); and a horizontal-overflow check read off
      `documentElement`, which `overflow: hidden` makes structurally incapable of firing.

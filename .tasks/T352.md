# T352 — a real fallback hat, not just a display preference

## Summary

Owner ask, 2026-09-12: *"I've got some more clear pictures for devops and qa - they are possible
to be added as project roles and even from client side so belongs to non-manager level like Devs
if they are not fullfilled then atomatically assigned forcible devops to TL and QA to PM."*

Grounded before drafting (read `apps/cp/src/pages/api/project/roles.ts` and `hats.ts` in full,
plus the `hats`/`worn_hats`/`project_roles` migrations):

1. **QA already exists as a project role** (`qa-engineer`, seeded on Artemio/BridgeRoad by
   [[T311]]). **`devops` has never existed as a `project_roles` row** — zero rows, any project,
   ever. ⚠️ **Correction from this ticket's own first draft**, caught by `w0m-sdlc-research`: a
   grep for "devops" DOES hit the schema, but as two unrelated, prior things, neither of which is
   this axis. (a) A **global `user_roles.role` value** in `project_deployment_rbac.sql`
   (2026-07-08) — dead on arrival: `user_roles_role_check` never allowed `'devops'` or
   `'project_manager'`, so those policy arms authorize nobody and always have (**[[D4]]**, decided
   debt, unrelated to this ticket — not paid down here). (b) A **global `public.offices` slug**
   bundling security capabilities (`infra.manage`, `deploy.execute`, `repo.manage`,
   `project.deploy`) — renamed `devops → tech.ops` under [[T117]] (2026-08-10) specifically
   *because* "PM/TPM/DevOps are offices, never Axis-1 roles" (that migration's own comment).
   **Offices are a global security-capability axis; `project_roles`/`hats` is a per-project
   delivery-staffing axis — different job, different table, and this ticket only touches the
   second one.** Nothing here renames or touches `tech.ops`.
2. **`project_roles` is freeform** — `ProjectRolesModal.svelte`'s "+ New Role" lets an admin type
   any name today. Nothing schema-level blocks a "DevOps" role from being created right now; what's
   missing is it being a *recognized, fallback-aware* slug the way `tech-lead`/`pm`/`qa-engineer`
   already are.
3. **Client-side hat-holding already works, unexercised.** Every `auth.users` row — including a
   `client_users`-linked one — gets a `public.profiles` row via the `on_auth_user_created` trigger
   (`profiles.id = auth.users.id`), and `hats.profile_id → profiles.id`. `roles.ts`'s GET handler
   pulls `from("profiles")` with no filter, so client profiles already appear in the assignment
   picker. Nothing here needs new schema — only confirmation, a proof, and (optionally) a UI label
   so an admin can tell a client contact from a team member when assigning.
4. **"Non-manager, like Devs" is not an enforced tier today.** `project_roles.min_unit_id` reads
   like a seniority gate in [[T311]]'s migration comment, but neither `roles.ts` nor `hats.ts`
   compares a profile's own unit against it — it only pre-fills a default `unit_id` when a hat is
   provisioned. The only real gate is *who may assign a role* (admin-only), not *who may hold one*.
   Nothing to build for this part; it's a labeling/expectation statement, not a missing mechanism.
5. **The genuinely new piece: `hats` currently records only deliberate assignments.** [[T347]]'s
   AC1 (QA unstaffed → falls back to PM) is a *read-time display preference* — it computes a
   routing answer for the bug-triage view, it does not write anything. This ticket is different in
   kind: the owner wants an actual **persisted** hat row that appears wherever `hats`/`worn_hats`
   are read (staffing views, future routing, [[T347]] itself), not a value computed only inside one
   query.
6. **"Unfulfilled" means *holding*, not *wearing*.** `hats.is_active` is who holds a role;
   `worn_hats` is which ONE of a person's held hats they're currently wearing per project (one row
   per profile+project — a PM who also holds Dev still wears only one at a time). Fallback logic
   must key off **no active `hats` row for the role**, not "nobody happens to be wearing it right
   now" — the latter would make almost every multi-hat project look unstaffed.

      ✅ `20260912200000_t352_hats_is_fallback.sql`, verified live (`not null`, default `false`).
- [x] AC3 — A trigger (or trigger-invoked function) on `public.hats` keeps fallback hats in sync,
      keyed by project + role slug: when a project's `devops` role has zero active, non-fallback
      holders, every active non-fallback holder of that project's `tech-lead` role gets an active
      `is_fallback = true` `devops` hat; symmetric for `qa-engineer` → `pm`. The moment a real
      (non-fallback) holder is assigned to the unfulfilled role, every fallback hat for that
      project+role is deactivated/removed — a fallback is provisional, never permanent once real
      staffing lands.
      ✅ `20260912210000_t352_fallback_trigger.sql` (`wom_recompute_role_fallback` +
      `wom_sync_role_fallback` trigger). Retraction-on-real-staffing and reappearance-on-unstaffing
      both proven live, in-transaction, by `t352_fallback_hat_probe.py`.
- [x] AC4 — No cron needed: the trigger fires on insert/update/delete of `hats` rows touching
      `devops`/`qa-engineer`/`tech-lead`/`pm` on the affected project, so the fallback state is
      always current without a scheduled job.
      ✅ `after insert or update or delete on public.hats` — no scheduled job anywhere.
- [x] AC5 — Client-side hat-holding is proven, not just asserted: a probe (or test) shows a
      `client_users`-linked profile can hold and wear a `hats` row for a project role today with no
      schema change, and the admin assignment UI (`ProjectRolesModal.svelte`'s profile picker)
      visibly distinguishes a client-linked profile from an internal team profile.
      ✅ Probed live (demo client holds a real hat, `wom_wear_hat` succeeds under RLS, `worn_hats`
      row created) — no schema change needed. `roles.ts` now exposes `is_client` per profile;
      `ProjectRolesModal.svelte` appends `— client` to a client-linked profile's option label in
      both the per-role staffing picker and the indie-provisioning picker.
- [x] AC6 — A live probe proves the fallback correctly resolves in each of the three states for at
      least one real project: (a) role staffed for real → no fallback hat exists; (b) role
      unstaffed, fallback target staffed → fallback hat exists and is marked `is_fallback`; (c)
      neither the role nor its fallback target is staffed → no fallback hat, stays genuinely
      unstaffed (not silently invented from nothing).
      ✅ All three states proven by `t352_fallback_hat_probe.py` (10/10 checks): (a) BridgeRoad
      devops after a real holder is inserted, (b) BridgeRoad devops fallback to the tech-lead
      holder (via the backfill migration for pre-existing rows), (c) BridgeRoad qa-engineer stays
      at zero rows since neither qa-engineer nor pm is staffed there.
- [x] AC7 — [[T347]] is updated to consume this ticket's real fallback hats for its QA→PM routing
      display instead of computing its own query-time preference, and to note DevOps→TL is now
      also a resolvable fallback state for any future DevOps-relevant display.
      ✅ T347's own Status notes updated 2026-09-12 to say its future AC1 routing query should read
      `hats`/`is_fallback` directly rather than re-deriving the preference, and to record DevOps→TL
      as a resolvable fallback state.

## Definition of Done

A project with an unstaffed `devops` role but a staffed `tech-lead` shows a real, queryable
`hats` row for `devops` (flagged `is_fallback`) held by the tech lead — and the same for
`qa-engineer` falling back to `pm` — proven live for at least one project in each of the three
states in AC6, with the fallback automatically retracted the moment real staffing replaces it. DevOps
exists as a canonical, seeded role. Client-side profiles are confirmed and visibly distinguishable as
assignable hat-holders through the existing admin UI.

🟢 **2026-09-12 — Review gate: one confirmed correctness fix, one file verified clean, one process

- **Fixed** — `roles.ts`'s `assign` action upserted a `hats` row without setting `is_fallback` in
  the payload. PostgREST's generated `ON CONFLICT DO UPDATE` only sets columns present in the
  payload, so re-assigning a profile that already held a fallback hat for that exact
  (profile, role, project) triple silently left `is_fallback=true` stale — an admin's deliberate
  assignment would still read (and later behave) as an auto-fallback. Added `is_fallback: false`
  to the upsert payload. `unassign` was checked and is unaffected (hard `DELETE`, no stale-row
  path); the trigger's own upsert in `20260912210000_t352_fallback_trigger.sql` was checked and is
  correct as written (its payload/ON CONFLICT DO UPDATE both explicitly set `is_fallback = true`).
- **Verified clean, no fix needed** — `hats.ts`'s three `hats`-table writes (lines ~369, 416-424,
  468-477) are plain `.insert()`, never `.upsert()`/`onConflict`; an omitted `is_fallback` on a
  plain INSERT falls through to the column's `not null default false`, so there is no
  stale-value path there. The wear-only path that reuses an `existingHat` also correctly leaves
  `is_fallback` untouched — wearing a hat doesn't change who holds it or why.

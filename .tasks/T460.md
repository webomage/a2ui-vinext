# T460 — Research: group training in one engagement

## Summary

Owner, 2026-09-26 (T458 Q30): training runs through engagements, like delivery. An engagement joins exactly two orgs
(contractor and client), so a trainer teaching several people from several personal orgs needs one engagement per
trainee today. The owner can imagine one engagement where a trainer teaches several persons from several personal orgs,
and asked for it as a P2 research item, not part of the base model.

## Acceptance criteria

- [x] AC1 — Compare: one engagement per trainee (today's model) vs an engagement with several client-side orgs vs a
  cohort grouping several two-party engagements; for each, what access each trainee has to the others' work.
  - **Evidence:** Completed 3-model architectural comparison and 8-surface access-control matrix across Model A (One Two-Party Engagement per Trainee), Model B (Multi-Client Engagement M:N join), and Model C (`training_cohorts` Container Grouping $N$ Two-Party Engagements) in `.agents/reports/2026-10-25-t460-group-training-engagement-models-research.md` §2 (mirrored in `wom7web/docs/reports/2026-10-25-t460-group-training-engagement-models-research.md`) and `docs/decisions/AgDR-0049-group-training-cohort-over-two-party-engagements.md`. Proved that Model B leaks private submission repos (`project_repos_client_select_own`), tuition contracts (`contracts_client_select_own`), invoices, and grades across all trainees sharing `engagement_id`, breaks `<contractor>.<engagement>.<client>` addressing (`AgDR-0028` §2), and couples dropout/pause `engagements.status`, whereas Model C preserves 100% two-party isolation per trainee while sharing the cohort syllabus vault (`cohort_vault_id`) and classroom feed.
- [x] AC2 — Check the Backstage shape of each (an engagement `Group` has one parent; the client is an annotation).
  - **Evidence:** Verified against `@backstage/catalog-model` and `wom7web/project/scripts/catalog_models.py` (`GroupSpec`, `normalize_entity_ref()`) in `.agents/reports/2026-10-25-t460-group-training-engagement-models-research.md` §3 and `AgDR-0049` §Decision.2. Showed that Model B breaks singular `w0m.dev/client` entity-ref normalization and mixes external principals in one hat `Group`, whereas Model C maps natively to Backstage's `Group` hierarchy (`trainer-org` → `Group(spec.type: cohort)` → `Group(spec.type: engagement, w0m.dev/client: <trainee-personal-org>)` → `Group(spec.type: hat)`) with zero custom kinds or schema changes.
- [x] AC3 — Recommend, with a weighted decision; if built, it is its own ticket.
  - **Evidence:** Evaluated Models A, B, and C across 5 weighted criteria in `.agents/reports/2026-10-25-t460-group-training-engagement-models-research.md` §4 and recorded in `AgDR-0049`: Model C (**Training Cohort Grouping $N$ Two-Party Engagements**, score **4.80 / 5.00**) and Model A (**Two-Party Base Primitive**, score **4.25 / 5.00**) defeat Model B (Multi-Client Engagement M:N, score **1.60 / 5.00**). Model B is permanently rejected; Model A remains the active base primitive today; Model C is locked in `AgDR-0049` to be built when the first multi-personal-org training batch is scheduled (0 `kind = 'training'` rows exist in production today, avoiding dead schema per `AgDR-0025`).

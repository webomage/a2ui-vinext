# T206 — per-service Postgres roles

## Summary

Owner decision 2026-08-12, choosing between three backings for the `system.*` realm ([[T117]]):
**per-service Postgres roles, without `bypassrls`, with explicit grants.**

**This is the strongest of the three and the only one that makes `system.*` offices mean anything** —
RLS then applies to machine actors exactly as it does to people, and an office in `system.*` becomes
a constraint a policy can read rather than a label.

## The problem it fixes, measured live 2026-08-12

`pg_roles` holds **exactly one `service_role`**, `bypassrls=true`, and **no per-service roles exist**.
So today:

- **51 of 55 edge functions present the same service key** — `system.crawler` and `system.billing`
  would be the same principal at runtime, and no policy runs for either.
- **49 hold it while 21 also declare `verify_jwt=false`**; `log-event` is `verify_jwt=false` **and**
  service-key **and** has no in-function gate.
- `service_role` is 1 of only 3 roles in the whole cluster with `bypassrls` (the others are
  `postgres` and Supabase's own admins).

⇒ **Every one of the 66 tables whose enforcement mechanism is "service" is unprotected against any
actor holding that one key**, and the audit surface cannot distinguish them.

## 🔑 The pivotal unknown — it decides whether this is cheap or a rewrite

**The good news, measured:** **53 of 55 functions reach the database through PostgREST**
(`createClient`), and exactly **1** uses a direct pg driver (via `_shared`, the only `DATABASE_URL`
reader). PostgREST is the path where per-service roles are *nearly free*: `authenticator` does
`SET ROLE` from the JWT's `role` claim, so a service identity is

```sql
CREATE ROLE svc_upwork NOLOGIN;
GRANT svc_upwork TO authenticator;
-- then explicit GRANTs + RLS policies naming svc_upwork; no bypassrls
```

…and the function swaps `SUPABASE_SERVICE_ROLE_KEY` for `SVC_UPWORK_KEY`. **No new connection
string, no password, no infrastructure change.**

🔴 **But that requires minting a JWT with `role: svc_upwork`, and this project cannot do that today.**
Measured:

- **No JWT secret is available.** `SUPABASE_JWT_SECRET` and `JWT_SECRET` are both **absent** from
  infisical `dev` (98 secrets present, neither among them).
- **The keys are the NEW opaque Supabase format, not legacy JWTs** — `PUBLIC_SUPABASE_ANON_KEY` is
  `sb_publishable_…` (46 ch) and the service key is `sb_secret_…` (41 ch). Legacy keys were long
  HS256 JWTs you could re-sign; these are opaque tokens resolved by Supabase's gateway.
- ⚠️ **`signToken` in `packages/lib/src/auth/crypto.ts` is NOT a JWT** — it is a two-part
  `payload.HMAC` custom token for the SSO handoff, with no header segment. It cannot drive PostgREST
  role switching, and should not be mistaken for a way in.

⇒ **AC1 is to establish which of these is true, before any other work:**

| if… | then the cost is |
|---|---|
| the legacy JWT secret is still retrievable (dashboard → API → JWT Settings) | 🟢 **cheap** — mint per-service JWTs, swap one secret per function |
| Supabase's new key system can bind a secret key to a custom Postgres role | 🟢 **cheap** — create keys per service identity |
| neither | 🔴 **expensive** — per-service identity needs `LOGIN` roles + passwords over a direct connection, i.e. **rewriting the DB access of 53 functions** |

⚠️ **I cannot read this** — it is a dashboard/management-API fact and the Supabase management PAT has
been dead since 2026-07-17 ([[T67]], 403). **It is an owner check, and it gates the estimate, not the
design.**

## Acceptance criteria

- [x] **AC1 — establish the minting path FIRST** (table above). Everything else is scoped by it.
      Record the answer in this ticket; do not start AC3 before it.
- [x] **AC2 — 🔴 [[T202]] is a PREREQUISITE, not a parallel ticket.** The shared Supabase client
      **prefers** the service-role key across **42 importers, 25 of them `.astro` pages**, so **25 SSR
      page renders currently run as the service role**. Splitting machine identities while page
      renders still hold the master key moves the problem rather than fixing it — and the new roles
      would be strictly *weaker* than the one every page already has.
- [x] **AC3 — derive the service identities from what functions TOUCH, not from their names.**
      ⚠️ The target is roughly 6–10 identities, **not 49**. The apparent groupings from the live list
      (`upwork-poller`/`upwork-callback`/`get-upwork-status`; `job-ingest`/`linkedin-ingest`/
      `profile-ingest`/`gamification-ingest`; `stripe-checkout`/`stripe-webhook`/`process-payout`;
      the `agent-*`/`generate-*` set; the telegram set) are a **hypothesis from naming** — the real
      grouping is the set of tables each function writes, and naming has already misled this estate
      once this week (see the note below).
- [x] **AC4 — every new role is created WITHOUT `bypassrls`,** and each gets explicit `GRANT`s plus
      RLS policies naming it. A role with `bypassrls` reproduces the exact defect being fixed.
- [x] **AC5 — red probes before the migration.** For each new identity, a probe that proves it
      **cannot** reach a table outside its grant. Follows [[T198]] AC8's pattern; without them a role
      that silently retains broad access is indistinguishable from one that was scoped correctly.
- [x] **AC6 — the one direct-pg consumer** (`_shared`, the only `DATABASE_URL` reader) needs a `LOGIN`
      role with a password regardless of AC1's answer. Smallest piece; do not let it block the other 53.
- [x] **AC7 — `log-event` is fixed or explicitly accepted.** It is the worst cell measured:
      `verify_jwt=false` + service key + no in-function gate. A per-service role narrows it; it does
      not close it.
- [x] **AC8 — retire the shared key from function code once identities exist**, and gate that no new
      function imports it. Until then the new roles are additive and prove nothing.

## Why this is P1 rather than P2

It is the only backing that makes `system.*` real, **and it is load-bearing for three other tickets**:
[[T117]]'s realm model has no enforcement without it, [[T205]]'s CP surface would display offices that
still constrain nothing, and [[T199]] F3's finding (49 of 55 functions holding the key) is precisely
this problem counted a different way.

## ⚠️ Note for whoever picks this up

**Do not group functions by name.** In this same session a stale local snapshot was read as a live
separation-of-duties defect because an office had been *renamed* (`devops` → `tech.ops`) and the file
still carried the old key — the pattern is [[T205]]'s finding, and the general rule is in the
measurement-traps record: **never identify a thing by the name it supplies.** Group by measured table
access.

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
At least 6 distinct per-service Postgres roles (`svc_*`) exist in `pg_roles` without `bypassrls` (`bypassrls=false`), granted to `authenticator` with least-privilege table grants partitioned by measured function touchpoints. Automated red probes (`just authz-service-roles-test`) verify each role cannot read or mutate tables outside its assigned domain. Edge functions bind to their respective service role tokens or transaction role contexts, with `log-event` hardened against unauthenticated writes, retiring the monolithic `service_role` key from machine runtime callers.

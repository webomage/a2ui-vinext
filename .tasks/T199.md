# T199 — the authorization layers with no owner and no gate

> 🏛️ **Member of [[T200]]** — the authorization core batch. Added 2026-08-12 by the ticket-graph
> audit, which found this ticket was claimed by that parent without naming it back. **A one-way
> membership is invisible from the member's side**, so anyone opening this ticket alone would not
> know it is sequenced inside a batch.

## Summary

[[T198]]'s coverage survey (2026-08-11) established that **authorization in this estate is decided in
five places** — a table `GRANT`, an RLS policy, a `SECURITY DEFINER` function, an edge function's own
code, and an application route. It found live defects in two of them, which stayed in T198. This
ticket takes the other half of that finding: **four layers that are now measured but that nothing
governs, tracks, or checks.**

None of these is a confirmed exploit today. Each is a surface where the *next* change is unreviewable
because nobody has written down what the current state is supposed to be. That is the same shape as
[[T192]] (an autoload surface generated for a year with one of 31 governed) and [[T196]] (a retired
product's LaunchAgent that every repo-scoped gate was structurally blind to).

🔑 **The unifying defect: all four are closed today by a default, not by a decision.** A default
cannot be reviewed, cannot be tested, and does not survive the next migration.

## 📍 The four layers

### 🟠 F1 · Storage — 7 of 13 buckets are public, and the object policies were never read

```
bucket                 visibility   objects
assets                 PUBLIC             1
blueprints             PUBLIC             7    ← 3 blueprints are access_scope=internal
cv                     PUBLIC             3
news                   PUBLIC           187
post-images            PUBLIC             1
public-images          PUBLIC             0
snapshots              PUBLIC            20
applications           private            1
decks                  private            0
domains                private            8
interview_recordings   private            0
resumes                private            0
upwork                 private          327
```

No authorization pass has ever included storage. **The `blueprints` bucket being public is
[[T198]] B1 one layer down**: the row-level tiering `access_scope` expresses has no counterpart on the
object, so an internal blueprint's assets are served to anyone with the URL regardless of what the row
says. That specific coupling is tracked as T198 E5; **this ticket owns the layer** — the
`storage.objects` policies behind all seven public buckets are unmeasured.

⚠️ **Precedent to apply, not rediscover:** closing an exposed bucket needs **both** `public=false`
**and** dropping the public-role `SELECT` policy — the flag gates path-reads, RLS gates listing.
Moving objects goes through the Storage API, never SQL. That was learned the hard way on a previous
bucket and the standing check is `PUBLIC_BUCKETS_ALLOWED` in `w0m_audit`. ⇒ **F1's job is to make
that check the authority on which buckets may be public**, rather than a list someone remembers.

### 🟠 F2 · The definer surface — 32 functions, 7 executable by `anon`, no inventory

```
45 functions in public · 32 SECURITY DEFINER · 24 EXECUTE to authenticated · 7 EXECUTE to anon

  get_user_roles()   has_role(text)   is_admin()   wom_role_set()
  wom_acting_role()  wom_acting_is(text)   wom_acting_in(VARIADIC text[])
```

A `SECURITY DEFINER` function runs as its owner, so it is a hole through RLS by construction — that
is the point of it, and it is why the set needs to be a reviewed list rather than a side effect of 45
migrations. The seven anon-executable ones are the authorization primitives themselves, the same
wrappers T198's correction found doing real work in 10 policies.

🔴 **Do not "harden" this by revoking grants.** Revoking `anon` `EXECUTE` on a definer RPC has already
broken a live caller in this estate once — the AI daily-quota check was failing **open** because a
caller running as `anon` could no longer reach the function. ⚠️ And `CREATE OR REPLACE FUNCTION`
**resets ACLs**, so a grant is only as durable as the next migration that touches the function.
⇒ **F2 is an inventory plus a gate, not a revocation.**

### 🟠 F3 · The edge fleet — 30 of 55 functions have no declared JWT posture

```
on disk                             55
hold SUPABASE_SERVICE_ROLE_KEY      49
declared in supabase/config.toml    25      →  30 undeclared
verify_jwt = false (declared)       19
verify_jwt=false + no in-fn gate     2      cv-pdf (read-only proxy, no key) · log-event
  └─ …and holding the service key    1      log-event
```

For 30 of 55 functions the auth posture is **whatever the platform defaults to** (`verify_jwt=true`),
recorded nowhere in the repo. That is not currently a hole — the default is the safe one — but it
means a reviewer cannot tell an intentional public endpoint from an unconsidered one, and 49 of the 55
hold the service key, so the blast radius of getting one wrong is total.

`log-event` is the one function that is unauthenticated, holds the service key, and has no
in-function gate: it inserts into `analytics_events` (3,871 rows) with no origin check, shared secret
or rate limit. Defensible for a beacon; undefended either way.

⚠️ **The measurement trap is recorded because it will recur:** the detector that produced this table
returned **3 false positives out of 4** on its first run — `chat-internal` checks an
`x-internal-key` header, `contact-submit` verifies hCaptcha, `cv-pdf` holds no key at all. A `gate:
false` verdict is a candidate to open, never a finding. Any gate built for F3 must encode that.

### 🟡 F4 · Untracked tables, closed by an accident of RLS semantics

```
_t155_contracts_backup_20260731    188 rows   0 policies    (contracts itself holds 96)
_t155_fk_backup_20260731            18 rows   0 policies
platform_sync_state                684 rows   0 policies
platform_rate_budget                 0 rows   0 policies
```

RLS enabled with **zero policies** denies every non-owner role, and the probes confirm 0 for both
`anon` and a signed-in user. So these are closed — **by a semantic default, not by a decision.** One
`CREATE POLICY … USING (true)` — the shape 38 tables already carry — would open them.

🔴 **A [[T157]] migration left a 188-row copy of the contract table in `public`**, larger than
`contracts` itself, and it appears in no inventory, no retention rule and no ticket. It is a second
copy of commercial data whose lifetime nobody owns.

running.

live dependency of something outside this repo (`trigger-hatchet-workflow` and

or (c) source that exists in another repo. Deleting a function that something still calls converts a
governance gap into an outage. **Identify the caller first**, per orphan.

## Related finding — the grant layer is two regimes, and neither is written down

Measured in the same pass and belonging with the above, though it is not one of the four:

- In `public`, **`anon` holds table-level `SELECT` on 98 of 100 tables**. The grant layer provides no
  defence at all; RLS is the only gate, everywhere.
- In `gamification`, **the only grantee is `postgres`** — not `anon`, not `authenticated`, not even
  `service_role`. RLS is on for all 15 tables with 27 policies, 8 of them `Authenticated read …
  USING true`, and **none can ever evaluate**.

⇒ **Two opposite regimes, and the safety of each rests on the thing the other ignores.** A single
`GRANT SELECT` to `authenticated` on `gamification` — the most ordinary thing to do while building a
wallet page — opens eight blanket policies at once.

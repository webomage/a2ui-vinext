# T164 — Govern the full host CLI surface and report toolchain health in the health report

## Summary

Owner ask 2026-08-05: *"let's have all this tools managed in w0m stack with versions check in
project health tooling part report — it's kind of part of sdlc."*

Prompted by a measured host↔VM tool inventory (54 common dev CLIs probed): the **host has 49,
`tools-policy.json` governs 17**. Tool version drift is therefore invisible to the health
surface, and the checker that does exist is wired into nothing.

**The mechanism already exists and works — this ticket closes three gaps around it, it does not
rebuild it.** `project/tools-policy.json` + `project/scripts/tools_check.py` are healthy: live
run 2026-08-05 reported *17 tools, 0 required-problems, 0 warn, 1 drift* (infisical 0.43.114 vs
known-good 0.43.111), with per-tool `min`/`known_good`/`required`/`source`/`auto`/`smoke` and
`just tools-check` / `tools-outdated` / `tools-upgrade` / `tools-weekly`.

**Gap 1 — coverage.** 20 host CLIs are ungoverned: `ansible bat cargo cmake direnv docker go
helm java kubectl ncdu pip3 podman psql redis-cli ruff rustc sqlite3 uv yq`. ⚠️ The policy's
stated scope is *"host CLI tools the w0m workflow **depends on**"*, so this list must be
**filtered against real usage**, not added wholesale — `bat`/`ncdu` are almost certainly not
workflow deps, and adding them would turn an accurate policy into noise. Evidence sources:
`project/stacks-policy.json` → `commands`, the `justfile` recipes, and the git hooks.

**Gap 2 — reporting.** `just health` → `wom7api/scripts/healthcheck.py` is **live-endpoint
health only** (`fetch_with_latency`, `check(label, url, expected_codes, sla_ms)`). It has no
tooling section, and neither health script references `tools-policy.json` (verified by grep).

**Gap 3 — SDLC wiring.** `tools_check` is referenced **only** by `tools_upgrade.py` and as a
descriptive entry at `.w0m/sdlc.json:337`. **No git hook and no SDLC gate calls it.** Drift is
invisible unless a human remembers to run it — which is the opposite of a standing check.

🔑 **Research finding that constrains the design: there are already TWO health surfaces, and
they are different things with confusingly similar names.**

| Recipe | Script | Reports |
|---|---|---|
| `just health` / `check-status` | `wom7api/scripts/healthcheck.py` (17.5 KB) | endpoint latency / expected codes / SLA |
| `just health-check` | `wom7web/project/scripts/health_check.py` (6.2 KB) | deployed app `/api/health` + version/commit (T22 AC3) |

**Do not add a third.** Extend or unify; a `just health*` family with three members and no stated
division of labour is worse than the current gap.

## Acceptance criteria

- [ ] AC1 — **Coverage decided by evidence, not by what happens to be installed.** Every
      ungoverned CLI that a `just` recipe, a `stacks-policy.json` `commands` entry, or a git hook
      actually invokes is either added to `tools-policy.json` (with `min`, `known_good`,
      `required`, `source`, `auto`, and a `note` justifying it) or recorded as deliberately
      out-of-scope with a reason. The probe used to decide is committed and re-runnable.
- [ ] AC2 — **`just health` includes a toolchain section** — tool, installed version, `min`,
      `known_good`, verdict — rendered alongside endpoint health and read from
      `tools-policy.json`. No second source of truth for tool versions.
- [ ] AC3 — **No third health command.** The two existing surfaces are either unified behind one
      entry point or their scopes are documented in-repo so a reader knows which reports what.
      `just --summary` alone does not count as documentation (it is inert — [[T130]]).
- [ ] AC4 — **Wired into the SDLC.** The check runs from a gate and/or hook without anyone
      remembering to invoke it, advisory-by-default with `--strict` semantics matching existing
      gates. A required tool missing or below `min` becomes visible automatically.
- [ ] AC5 — **Project-agnostic** — paths and commands read from `.w0m/sdlc.json`, nothing
      hardcoded, per the config-driven convention.
- [ ] AC6 — **The gate is proven to fail.** A deliberately-bad policy entry produces a red, so a
      green is evidence rather than a vacuous pass. Recorded the way `just state-doctor-test` and
      `just discovery-test` prove theirs.

# T763 — Google re-login after sign-out silently reuses the previous Google session

## Summary

Owner-measured bug (2026-11-17): after signing out and choosing "Continue with
Google" to sign in with a *different* Google account, Google silently
re-authorizes the previously authorized Google session — no account chooser is
shown — and the callback restores the same w0m account, then prompts for the
(unchanged) MFA code. The user cannot switch Google accounts.

Root cause: `handleOAuthStart`
(`packages/lib/src/auth/handlers.ts`) calls
`supabaseClient.auth.signInWithOAuth({ provider, options: { redirectTo } })`
with **no `queryParams.prompt`**. Google's authorize endpoint reuses
its active session cookie by default and skips the chooser.
`handleLinkIdentityStart` (T476) already solved this exact problem for
identity linking with `queryParams: { prompt: 'select_account' }` — the same
parameter was never applied to the sign-in path.

Fix: in `handleOAuthStart`, pass `prompt: 'select_account'` for `google`
(scoped to google — `select_account` is a Google OAuth parameter and passing
it to LinkedIn OIDC/GitHub risks provider-side validation errors). Server-side
sign-out cookie purge is already complete (T78).

## Acceptance criteria

- [ ] AC1 — `handleOAuthStart` with `provider=google` includes
      `queryParams: { prompt: 'select_account' }` in the `signInWithOAuth`
      options; `linkedin_oidc`/`github` requests are unchanged; after landing,
      sign-out → "Continue with Google" shows Google's account chooser (owner
      verifies on live stage at next deploy).
- [ ] AC2 — `packages/lib/src/auth/handlers.spec.ts` asserts the new options
      for google and the unchanged options for the other providers; the auth
      handler suite passes.

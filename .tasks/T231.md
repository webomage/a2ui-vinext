# T231 — the backups are proven, but they are local, manual and single-copy

## Summary

**Owner ask, 2026-08-18:** *"we can schedule backups triggering and performing at CF side and store
backup also on CF."*

[[T229]] closed 7/7 and left exactly three things undone, all of them recorded as debt: **D57** the
backup is not scheduled, **D58** two limits are unmeasurable, **D59** the Storage copy has no
restore path. This ticket attacks the first and third, and adds the thing neither T229 AC covered:
**the only copy of both backups lives on one laptop, in `wom7api/supabase/backups/`.** A dump proven
to restore is worth nothing if the disk holding it dies with the machine that made it.

## What is already TRUE and must not be re-derived

- `just db-backup` → a version-matched `pg_dump`; `just db-restore-verify` **proves it restores**
  (114/114 tables, 6/6 content tables byte-identical).
- `just storage-backup` → all **555 Storage objects / 53.9 MB**, sha256-manifested.
- `just backup-freshness` → goes red when either artefact passes its declared age.
- ⚠️ The dump needs a **`postgres` role** and **pgvector** to restore; both are preflighted.

## 🔴 Constraints MEASURED 2026-08-18 — design inside these, do not rediscover them

1. **All 5 Cloudflare cron slots are used.** Workers Free allows **5 per ACCOUNT** and
   `wom7cfworkers/wrangler.jsonc` declares exactly five (`*/15`, `*/30`, `0 8 * * *`, `0 */6 * * *`,
   `0 14 * * SUN`). A sixth is refused with **code 10072**. ⇒ **A new cron is not available. Ride an
   existing slot** — the daily `0 8 * * *` and the weekly `0 14 * * SUN` are the natural hosts, with
   the handler branching on `event.cron`.
2. **`wom7api` must NOT gain a cron.** Its `triggers.crons` is `[]` by decision, recorded in
   `wom7api/CLAUDE.md`, because wom7cfworkers owns the schedule.
3. 🔴 **A Worker cannot run `pg_dump`.** It is a native binary; there is no Workers equivalent, and
   re-implementing it in SQL would produce a backup whose fidelity nobody has tested — the opposite
   of what T229 established. **This is the crux of the design and AC1 exists to settle it.**
4. **GitHub Actions is NOT an escape hatch** — 339/339 runs `startup_failure` on this account.
5. The Supabase Management API has **no dump endpoint** and **no usage endpoint** (both 404).

## AC6 — the blast-radius review, 2026-08-20

🔬 **The AC's framing is slightly wrong, and the correction is the finding.** It reads *"the Worker
**needs** credentials that can read the whole database … that **makes** this Worker the most
privileged thing in the estate"* — future tense, as though backup duty would confer the privilege.

**Measured: it already has them.** `wom7cfworkers/src/index.ts` reads `env.SUPABASE_SERVICE_ROLE_KEY`
today, in the scheduled handler, and has since long before this ticket. ⇒ **The Worker is already
the most privileged thing in the estate.** Backup duty does not create that condition; it inherits
one nobody decided on.

**The surface, measured:**

| property | state |
|---|---|
| holds `SUPABASE_SERVICE_ROLE_KEY` | ✅ **yes, already** — full RLS bypass on every table |
| declared `routes` in `wrangler.jsonc` | **none** ⇒ reachable on its `workers.dev` subdomain |
| HTTP auth | a single shared bearer, `WEBHOOK_SECRET`, checked at **4** entry points |
| R2 bindings | **none** — the mirror is not in the Worker at all today |
| what actually mirrors to R2 today | **local Python** (`backup_push_r2.py`) driven by launchd (`com.w0m.backup-daily` / `-weekly`) |

⇒ **Today's blast radius:** one leaked or mis-compared `WEBHOOK_SECRET` on an internet-reachable
Worker yields **full database access**. That is a live, pre-existing exposure and it is independent
of backups. 📌 It belongs in [[T233]]'s security-posture composition, not buried here.

🔴 **The tension AC3 must resolve, stated rather than decided quietly.** This ticket exists to remove
a single point of failure — *backups that only exist because one laptop ran a cron*. But the current
local path has a property the Worker path destroys: **the credentials live on one machine that is
not internet-reachable.** Moving production into the Worker trades a laptop-availability risk for a
credential-exposure risk, and those are not the same kind of risk:

- **keep local (today):** backups stop when the laptop is off. Credentials never leave it.
- **move to the Worker:** backups are machine-independent. A bearer-gated internet endpoint gains
  the ability to read every table and write the backup destination — including, if it can write R2,
  the ability to **overwrite good backups with bad ones**.

⚠️ **A backup system whose credentials can destroy the backups is not a backup system.** If AC3
proceeds, the R2 credential must be **write-only to a versioned or immutable prefix**, never
delete-capable — otherwise the mirror becomes the fastest path to losing both copies at once.

**Recommendation, for the owner:** AC1 already chose *"this machine produces, the Worker mirrors"*.
Keep that. The Worker should mirror **Storage only** (which it can already read), with an R2
credential scoped to write-and-not-delete, and the Postgres dump stays local. That preserves
machine-independence for the half that needs it without widening the database blast radius at all.

## 2026-08-18 — the producer is scheduled (AC1, AC5 done)

Two agents declared in `project/launchd/schedules.jsonc` and **installed**:

```
com.w0m.backup-daily    daily 03:15    just backup-daily     loaded
com.w0m.backup-weekly   Sun   04:00    just backup-weekly    loaded
```

**Proven end to end, not assumed:** `just backup-daily` ran non-interactively and produced
`backup_20260818_191727.sql` at **28,398,432 B**, pruned, and reported both surfaces fresh.

### Three things had to change first, and each is a decision worth keeping

1. **The generator could only express WEEKLY.** `StartCalendarInterval` always carried `Weekday`.
   It is now optional — launchd reads an absent key as *every* — so omitting it gives a daily agent.
   ⚠️ **Daily is not a preference:** `max_age_days.postgres` is **7**, so a weekly dump sits exactly
   on its own limit and one missed run is instantly stale. Existing agents emit byte-identical
   plists (verified).

2. 🔴 **`_confirm` requires a TTY, and a launchd job has none** — a gated recipe would have
   **aborted**, so the gate would not have protected anything, it would have silently produced no
   backups. `backup-daily`/`backup-weekly` call the scripts directly. **This is a considered
   decision, not a bypass:** the consent already happened in a *stronger* form, because these run
   only because an agent is declared in a **versioned file reviewed in a diff**. A tty prompt is
   consent nobody can audit later; a committed schedule is consent with a `git blame`. ⚠️ The
   interactive `db-backup`/`storage-backup` stay confirm-gated — reaching for the scheduled pair by
   hand to skip a prompt *would* be the bypass.

3. **Retention had to exist before a schedule did.** ~28 MB a dump + ~54 MB a copy is ~2.5 GB a
   month unpruned — a disk-full incident with a date on it. `backup_prune.py` keeps the newest N,
   **refuses `--keep 0`**, and deletes only names matching the stamp pattern the freshness gate
   reads, so it can never become a general deleter pointed at a folder.

## 2026-08-18 — the scheduled run PUSHED but never re-verified (owner caught it)

**Owner: *"we have to reverify uploaded backup presence after upload done, right?"*** — correct, and
it was a real gap.

`push()` calls `head_object` immediately after upload and compares `ContentLength`, so the scheduled
run proved **an object of the right size exists according to R2's metadata**. 🔴 **That is not the
same as the bytes coming back**, and this file's own docstring already said so — *"a size match is
not integrity, and `head_object` only ever tells you what R2 believes."* The `--verify` round trip
existed but ran **only when a human typed it**.

⇒ **A capability that exists but is not wired into the automated path is not a capability the
automation has.** The same failure shape as the dangling `LESSONS.md` pointer earlier today: the
thing was built, and nothing reached it.

✅ **Fixed** — `backup-daily` and `backup-weekly` now run `--verify` after the push:

```
pushed      postgres/backup_20260818_231458.sql   28.4 MB ✅ size confirmed by R2
✅ postgres/backup_20260818_231458.sql            28.4 MB · sha256 matches after download
```

⚠️ **R2 egress is free**, so the daily ~80 MB round trip costs seconds and nothing else — there is no
cost argument for skipping it.

📌 **Pinned by a probe that reads the justfile itself** and asserts both recipes contain `--verify`,
**mutation-proven**: deleting the line from `backup-daily` turns the suite red (16 checks). Without
that probe the line could be dropped for speed some future afternoon and every run would still print
green.

### ⚠️ The design constraint I refused to trade away

`backup_freshness.py` was deliberately **credential-free and network-free** so it is safe on every
push. Making it always talk to R2 would have taken that away. So the remote check is behind `--r2`
— **and the absence is STATED**, because a report that quietly omits the offsite copy reads as
*"backups are fine"* when the only thing inspected was a laptop:

```
⏭️  OFFSITE NOT CHECKED — this run covers the local disk only. Use --r2 to include r2://wom7-backups
✅ every LOCAL backup surface has a recent, non-truncated artefact.
```

The success line is **scoped to what was actually checked** (`every LOCAL…` vs `every backup surface
(local + offsite)`). ⇒ `--r2` without credentials **exits 2 rather than skipping quietly** — an
unchecked remote copy must never read as a healthy one.

Both scheduled recipes now run it with `--r2`, pinned by a probe that counts the occurrences in the
justfile. **All five backup suites green.**

# T35 — Multi-hat — multi-role & active context

## Summary

Users hold multiple roles but act under ONE active role at a time; switching drops the
others' privileges (CTO-as-client). Today `user_roles` is multi-role but middleware
collapses to highest-precedence (`client` never wins). Change: active-role resolution
(server-verified ∈ set, signed claim), a role/workspace switcher, RLS keyed to the
effective role, and unify with admin impersonation (a "hat" = effective (user,role);
role-switch = own hat, impersonation = another user's hat), audited, §14-bound. NEVER
union privileges. Spec written to the authoring standard.

## Acceptance criteria

- [x] AC1 — Active-role resolution (server-verified ∈ set, signed claim)
- [x] AC2 — Role/workspace switcher; RLS keyed to the effective role
- [x] AC3 — Unified with admin impersonation (role-switch = own hat, impersonation = another user's hat), audited
- [x] AC4 — Privileges NEVER unioned across roles

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
An administrator or multi-role member can switch their active operating context between global roles and project-scoped delivery roles (`project_roles`) via `/api/auth/switch-role` and `/api/project/hats`. While acting under a non-admin role, admin privileges are strictly suppressed in middleware/CASL, and the CP viewport (in both `AdminLayout` and `ClientLayout`) persistently renders an ambient amber status bar with the active hat name and a 1-click 'Exit to Admin' control. Administrative role overrides are logged to `admin_activity_logs` with actor attribution, previous role, and target role metadata. Existing CP components (`RoleSwitcher`, `HatSwitcher`, `MyProjectHats`) operate cleanly with zero regressions.

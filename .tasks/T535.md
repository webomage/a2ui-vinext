# T535 — The Upwork poller is dead and nobody knows

## Summary

Found 2026-10-01 while researching [[T533]] (read-only, `admin_activity_logs` and token metadata; no token text was read).

- `SYNC_UPWORK_SUCCESS` ran 48 times a day until 2026-09-19 (41 that day). From **2026-09-19 20:00 UTC** every cron run has ended in `SYNC_UPWORK_FAILED`: **582 consecutive failures, one every 30 minutes, to 2026-10-01 22:30**.
- Every failure carries the same message, "Could not authenticate any Upwork connection contexts. Check auth tokens." The row records no cause (an expired refresh token, a rejected grant, a network error and a decryption error all look the same).
- The newest `upwork_auth_tokens` row expired on 2026-09-20 02:30 UTC (11.8 days ago); the row was last updated 2026-09-19 02:30. The estate `freelancer` connection in `public.connections` expired 2026-09-18. So refresh has not succeeded since.
- Even the last good runs synced `proposals: 0` and `messages: 0` (only contracts and rooms were touched), because the proposal leg imports only new items.
- **Nothing noticed.** [[T155]]'s standing gate checks coverage (duplicates, cover-letter share, status tags, room ceiling, message count), not freshness; T155 itself recorded "zero `SYNC_UPWORK_FAILED` since 2026-08-14". No ticket, gate or alert covers a stale sync. The Me pages keep rendering the old rows, which looks healthy.

Why it matters now: the owner wants proposals, messages and contracts linked and processed ([[T533]]); none of that stays current while the feed is down, and a member sees stale data without being told.

## Acceptance criteria

- [x] AC1 — **The failure row says why.** Each failed run records, per connection context, the stage that failed (`load_tokens`, `decrypt`, `refresh`, `graphql`), the HTTP status and the provider's error code, never a token or a secret. Unit tests first for the recording function, with red probes proving a token-shaped string in an error message is redacted.
- [x] AC2 — **Diagnosed from the new row.** One run after AC1 is deployed names the cause (for example `refresh` with `invalid_grant`). Recorded in this ticket's notes.
- [ ] AC3 — **Revived (owner step).** The owner re-authorizes Upwork if the cause is a dead refresh token (an interactive OAuth sign-in: not something an agent can do). Verified by the next cron run writing `SYNC_UPWORK_SUCCESS` and the token row's `updated_at` moving.
- [x] AC4 — **Freshness is a gate.** `upwork_sync_health.py` (T155) gains two required checks: the last success is at most 2 hours old, and fewer than 6 consecutive failures. Tests include a fixture of 582 failures, which must fail, and a fixture of one failure after a success, which must pass. The check runs where the other T155 gates run.
- [ ] AC5 — **Visible.** The admin Sync health page shows "last success" and "consecutive failures" and turns red past the same thresholds; `just state-brief` or the hot list names a stale sync while it lasts.
- [ ] AC6 — **Caught up.** After AC3, a run brings contracts, rooms and messages current and the counts are recorded; the proposals leg's "only new items" rule is checked against [[T533]] AC3 (the backfill of the archived proposals' answers is done there, not here).
- [ ] AC7 — **Token persistence is proven, not assumed.** After the owner re-authorizes (AC3), the next refresh moves BOTH `public.connections.updated_at` and `public.upwork_auth_tokens.updated_at` for the `freelancer` slot. If only the legacy table moves, the write to `connections` is failing (the poller logs it and carries on) and the cause is found and fixed before AC3 is called done. Measured 2026-10-02 before the fix: the legacy row was last refreshed 2026-09-19 02:30, the `connections` row 2026-09-17 02:30, and the poller reads `connections` FIRST. Suspect, unproven: `saveTokens` upserts with `onConflict` naming columns of a PARTIAL unique index (`connections_estate_slot_uq` has `WHERE owner_kind = 'estate'`), which PostgREST cannot target. One fact against it: the `connections` row did move on 2026-09-17, so some write to it worked once.

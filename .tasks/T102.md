## 2026-08-28 — model review: [`RBAC-MODEL-REVIEW-2026-08-28.md`](../../docs/design/RBAC-MODEL-REVIEW-2026-08-28.md)

🔴 **The one that needs a decision, not a fix:** `is_capable()` resolves through

## 2026-08-28 — `wom_effective_capabilities()`, and what the owner's override proposal costs

Owner asked the question the model could not answer: *"how do we know what the specific hat wearer
at the moment can do and what can't?"* — **it could not.** `is_capable()` takes one capability by
name, so an admin granting a hat could not see the result and a reviewer could not check one.

⇒ `wom_effective_capabilities(scope, profile)` returns the whole set **with provenance** — direct or
via which unit, bundled by which office, at what scope. It earns itself immediately:

```
applicant.manage    direct  -             -
blueprint.publish   unit    design.lead   Solutions Architect (CTO)
design.manage       unit    design.lead   Solutions Architect (CTO)
design.view         unit    design.lead   Solutions Architect (CTO)
```

🔑 Granting `design.lead` to mean *"manages the DS here"* also confers **`blueprint.publish`**. That
side effect was invisible until the set could be listed, and it is the concrete case for granting a
**capability** rather than an office — the argument [[T117]] was making in prose now has evidence.

### The proposal: *attach `is_capable()` to the hat*, and *enable/disable features per hat*

**Half of it already works.** A `profile`-scoped grant on a project adds a capability beyond what the
unit confers — `applicant.manage` above is exactly that. **No schema change needed for "additional".**

🔴 **"Disable" does not exist, and cannot mean anything yet.** There is no deny — measured, **zero**
policies in the estate express a negative permission, and `resource_grants` is additive because the
07-16 proposal defines effective rights as the **union**. And there is no *worn* hat:
`user_active_role` is one row per user holding a role name, with no project and no unit;
`hats.is_active` means **granted**, not worn. So a person holds every hat at once, and disabling a
capability on the PM hat leaves it granted through the engineer hat on the same project.

⇒ **The two halves are coupled: per-hat disable requires hat-scoped resolution first.**

**Order, if this is the direction:**

1. **An active hat**, keyed `(user_id, project_id) → hat` — a person can be on several projects at
   once, so one row per user cannot hold it. That is the same structural limit `PRIMARY KEY
   (user_id)` imposed in [[AgDR-0011]].
2. **Narrow `is_capable()` to the worn hat** rather than the union — and decide what happens off a
   project, where there is no hat.
3. **`resource_grants.effect ∈ {allow, deny}`**, deny winning. ⚠️ Negative permissions invert
   debugging: *"why can X do Y"* is a lookup, *"why can't X"* is a proof that no deny exists anywhere
   in the union. `wom_effective_capabilities()` is what makes that survivable, and it should list
   denies beside allows **before** any deny is written.

⇒ Steps 1–2 also settle the acting-role conflict this ticket's review recorded — narrowing to the
worn hat **is** the strict-hat position applied to the capability axis.

Full analysis: [`RBAC-MODEL-REVIEW-2026-08-28.md`](../../docs/design/RBAC-MODEL-REVIEW-2026-08-28.md).

## 2026-08-28 — Phase 1 & 2: the hat you are WEARING is the one that grants

The owner's model, stated in full: *"there could be multiple hats for same person on project like
PM + Developer … hat is the actual role of w0m unit in project, **activated at the moment** …
switching/wear/puton hat should change available apps and parts in cp clearly to not make a user to
have a guess what's the role/hat he has active right now."*

Held ≠ worn. That one distinction is the whole phase, and it is what makes *disabling* a feature on
one hat mean anything: if effective rights were the union of every hat a person holds, a Developer
hat with `deploy.approve` removed would still deploy through their PM hat, and the switcher would be
decoration.

**`20260828050000_t102_worn_hat.sql`** adds `worn_hats`, keyed `(profile_id, project_id)` — one hat
on per engagement, and a person on four projects wears four. `project_id` is **NOT NULL**: off a
project there is no hat, and the class axis governs. You cannot wear a hat you do not hold, or wear
one on the wrong project, because `worn_hats` carries a **composite FK to `hats(id, profile_id,
project_id)`** rather than a trigger — the rule is a constraint, so there is no code path around it.

🔴 **A defect caught before it shipped.** The first draft narrowed `is_capable()` to the worn hat but
left `wom_effective_capabilities()` counting every held hat. Those two are the enforcer and the thing
a menu is rendered from; had they disagreed, the CP would have offered actions the database then
refused, which reads as a broken feature rather than a wrong grant. Both now carry the identical
worn predicate, and the dry-run asserts them **together** on every transition rather than separately.

**`20260828060000_t102_hat_switching.sql`** is the switch: `wom_my_hats(project)` (every hat held
there, which is worn, and what each *would* grant if worn — so the pick shows its consequence
first), `wom_wear_hat(hat)`, `wom_take_off_hat(project)`. The two writers are **SECURITY INVOKER on
purpose** — `worn_hats` already has `with check (profile_id = current_profile_id())` and the
composite FK, so a definer would only add a second copy of a rule that can drift from the first.
T289's lesson applies in this direction too: fewer definers, less to audit.

Measured on the live schema in a rolled-back transaction, as `authenticated` with the actor asserted:

| | result |
|---|---|
| held but not worn → `design.manage` | **false** — holding is not wearing |
| wearing hat A | **true**, and `deploy.approve` (hat B's) **false** |
| switched A → B | `design.manage` **false** in `is_capable` *and* in `wom_effective_capabilities` |
| took the hat off | false, and the effective set is **empty** |
| wearing a hat you do not hold | rejected by the composite FK |
| wearing one on another project | rejected by the composite FK |
| two hats worn at once | rejected by the PK |
| `wom_wear_hat` on someone else's hat | rejected — RLS hides it, so the lookup *is* the check |

# T551 — duplicate migration version

## Summary

Found 2026-10-07 while re-measuring deploy readiness after agy landed [[T461]]. Two migration files carried the same 14-digit version: `20261006120000_t461_hat_management.sql` (agy) and `20261006120000_t544_profile_experience_owner_read.sql` (this session, [[T544]]). Both had been landed correctly in their own right, a few hours apart, by two agents each picking a timestamp.

The version is the ledger key (`supabase_migrations.schema_migrations.version`). `db_drift_check.local_migrations()` and `db_migrate` both build a `version -> filename` dict, so the later-sorted file replaced the other: `just db-drift-check` listed **four** pending migrations where **five** existed (T461's was invisible), and `supabase db push --include-all` would have hit a duplicate key in the middle of the deploy, after the confirm prompt and after the earlier migrations had been applied. A second effect: the T544 authz probes switch on when the ledger lists their version, so applying the T461 migration alone would have turned them on against an unapplied policy (RED, blocking every authz-path push).

No gate looked at the fact. The `LESSONS.md` entry "two agents picking the next free id collide" (T531, 2026-10-03) is the same shape for ticket ids, and is closed by `agent-tree-land` for tickets only.

## What was done

- Renumbered the T544 migration to `20261006121000` (both were unapplied, so nothing in the ledger changed) and updated every T544 reference. agy's T461 file and tests keep their version.
- `db_drift_check.py` now checks versions first, before any database access: `duplicate_versions()` names every colliding file, the full check exits 1 on a collision (and `db-migrate` runs this check as a dependency), and `--versions-only` runs just this, offline, in about a second.
- Registered as the pre-push suite `migration-versions` (recipe in `wom7api/justfile`, which is what the runner reads) with a 19-check self-test.
- Added `just migration-new <name>` (`db_drift_check.py --new <name>`) which fetches `origin/beta` and reads both `origin/beta` (`git ls-tree`) and local `supabase/migrations/*.sql` to allocate the next free 14-digit timestamp version (`next_migration_version` / `create_migration`), and added `check_tree_migrations()` in `wom7web/project/scripts/agent_tree.py` so `just agent-tree-land` refuses any `wom7api` branch whose migration version collides with `origin/beta` or duplicates a version in `HEAD` (including on push-race retry).

## Acceptance criteria

- [x] AC1 — **Collision resolved before the deploy.** The T544 migration is `20261006121000`; `just db-drift-check` lists five pending (T543, T535, T461, T544, T545); T544, T545 and the authz probe tests pass against the new name.
- [x] AC2 — **Tests first, mutation-proven.** `just migration-versions-test` (19 checks). Seven deliberate breaks are each caught (never finds a duplicate, reports only one file, empty directory passes, missing directory passes, `--versions-only` ignored, check moved after the ledger read, warn-only), plus the real scenario: a second file dropped onto an existing real version fails the CLI and the suite.
- [x] AC3 — **It runs where the collision is made.** `migration-versions` is a blocking offline pre-push suite.
- [x] AC4 — **Prevent the collision, not only detect it.** Decide how an agent picks a free timestamp (the same problem as ticket ids): `just migration-new <name>` (`db_drift_check.py --new <name>`) takes the next free 14-digit version across `origin/beta` and local migrations at creation time, and `check_tree_migrations()` in `agent_tree.py` enforces migration version uniqueness on `agent-tree-land` (including push-race retry), verified by 19 checks in `test_migration_versions_unique.py` and 59 checks in `test_agent_tree.py`.

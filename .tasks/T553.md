# T553 — T461 write path

## Summary

Found 2026-10-07 in the pre-deploy review of migration `20261006120000_t461_hat_management.sql` ([[T461]]). T461's status note says "Delivered & Verified (All 7 ACs Complete)". Measured, it is not: the CP team tab can read but cannot write. The migration is safe to apply (it creates five tables, seeds four collections, replaces three functions with the same signatures, touches no existing data) and was applied in the 2026-10-07 deploy; this ticket is about what it leaves unusable.

**Evidence** (local Postgres, one rolled-back transaction; the migration applied, then writes were tried as role `authenticated` with JWT claims, which is what the CP routes use: `getSupabaseServerClient` = anon key plus the person's cookies, RLS applies):

| Write | Caller | Result |
|---|---|---|
| `hat_collapse_rules` insert | any signed-in member | denied by RLS |
| `custom_hats` insert | any signed-in member | denied by RLS |
| `hat_assignment_log` insert | any signed-in member | denied by RLS |
| `hat_collections` insert | any signed-in member | denied by RLS |
| the same three tables | a caller holding the admin role at aal2 | **still denied** |
| `hat_collections` insert | admin at aal2 | allowed (the only write path that exists) |

Only SELECT policies exist on `custom_hats`, `hat_collapse_rules` and `hat_assignment_log` for `authenticated`; the write policies are `service_role` only. So in the shipped UI: creating a custom hat and editing fallback rules return a 500; applying a collection through `/api/project/collections` ignores the insert errors and reports success while writing no rules; the audit log is never written (its insert is wrapped in a try that only warns). The unit tests mock the Supabase client, so none of this showed.

## Related defects found in the same review

1. **Authority lives only in the API.** QH1 (a PM cannot mint a peer PM), QH4 (a tech lead assigns only dev and devops) and QH5 (sensitive offices root-only) are enforced in `roles.ts` and nowhere in SQL. Granting plain write policies to `authenticated` would let a PM write `custom_hats.offices` directly and bypass QH5. The write path has to enforce them in the database.
2. **The audit log can block staffing.** `hat_assignment_log.worn_hat_id references hats(id)` has no `on delete`. The fallback trigger deletes fallback hats. Reproduced locally: after an audit row references a fallback hat, assigning the real hat fails with `ForeignKeyViolation` on `hat_assignment_log_worn_hat_id_fkey`, so the retraction rule (QH-fallback) aborts the staffing statement.
3. **Default privileges.** The migration creates the five tables and never revokes, so `anon` and `authenticated` hold INSERT and DELETE on all five (measured: `has_table_privilege` true). RLS keeps `anon` at 0 rows and blocks writes today, so nothing leaks, but the T505 pattern (`revoke all ... from public, anon, authenticated`, then grant what is needed) is not followed.
4. **Possession-based admin checks.** The policies and `wom_can_staff_project` test `user_roles.role = 'admin'` directly, not `is_admin()`, so they ignore the aal2 requirement ([[T463]]).
5. **Blanket reads.** `custom_hats` and `hat_collapse_rules` are `using (true)` for every authenticated user, which `authz_blanket_gate` will report as undeclared once applied (advisory today). Project-scoped data should be readable by project members.
6. **Behaviour change on apply:** the dev-to-tech-lead and designer-to-pm collapse pairs go live and fallback hats now carry the target role's office; both fire only on future hat changes.

## Scope correction, 2026-10-07 (measured on the live catalog after the deploy)

The first version of this ticket said only the three new tables cannot be written. The live policies show the whole non-admin staffing path is dead, which is the feature's purpose:

| Table the API writes | Live write policy for `authenticated` | Consequence for a PM or tech lead (not an MFA admin) |
|---|---|---|
| `hats` (assign, retract) | `Admins manage hats`: `is_admin()` only | assigning or retracting a hat is denied |
| `worn_hats` | own rows only | fine |
| `project_roles` (a custom hat creates its role) | `wom_jwt_is_aal2() AND wom_acting_in(admin, manager)` | denied for a PM |
| `resource_grants` | `is_admin()` only | denied |
| `custom_hats`, `hat_collapse_rules`, `hat_assignment_log` | none (select only) | denied for everyone, MFA admin included |

So the Team tab works for exactly one situation: an MFA admin assigning a hat on the old tables. The rules the tab advertises (a PM staffs the team, a tech lead staffs dev/devops, compose custom hats) cannot run for the people they are for.

**A second defect in the API's own rule (QH1).** `checkStaffingAuthority` lets a PM assign `pm` only if "the actor is the organization owner", but the code sets `isOrgOwner = true` when the host org has ANY `org_units` row; it never compares the row to the actor. Once the write path exists this would let any PM mint a second PM on any project whose host org has a unit, which is the exact escalation QH1 forbids. `wom_can_staff_project`'s own owner test (a person in an org unit of the host org holding admin or manager) is the correct predicate and is not what the API uses.

### Revised plan (AC1 stands: definer RPCs, owner decision)

The write path becomes one set of `security definer` functions, each checking `wom_can_staff_project` and the QH rules INSIDE the function, writing the audit row in the same transaction, `search_path = ''`, executable by `authenticated` only, and the tables get no write grants for `authenticated`:

1. `wom_staff_hat(project, profile, role_slug)`: assign. QH1 (`pm` only by root or the host-org owner, using the real predicate), QH4 (a worn tech-lead hat may assign dev, devops, fullstack-dev only), no self-escalation beyond what the caller's worn hat grants.
2. `wom_retract_hat(project, hat)`: retract, same authority; a fallback hat retracts through the trigger as today.
3. `wom_compose_custom_hat(project, slug, title, description, offices, collapses_into)`: creates the `custom_hats` row and its `project_roles` row; offices must exist in `offices`; sensitive offices (`deploy.execute`, `infra.manage`, `secret.use.prod`) root only (QH5).
4. `wom_set_collapse_rule(project, role_slug, collapses_into, on_staffed)`: the devops invariant (never `keep_fallback`) also enforced here.
5. `wom_apply_collection(project, collection)`: add-only, atomic, reports the counts it actually wrote (the API today reports success while writing nothing).

The API routes call the RPCs and surface their errors (no `await` without an error check). The audit-log foreign key becomes `on delete set null`; `anon` and `authenticated` lose the default table privileges on the five tables; reads become project-scoped instead of `using (true)`; admin checks use `is_admin()`. Tests are scratch-database tests as role `authenticated` with JWT claims (the T544 pattern), one per QH rule and one per direct-write denial, with mutations that remove each rule.

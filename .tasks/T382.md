# T382 — Adopt withServiceRole least-privilege transaction switching in edge functions

## Summary

Ticket [[T206]] (Stage-1 RBAC Hardening) delivered database migration `20260917120000_t206_per_service_postgres_roles.sql` establishing scoped database roles (`svc_ai`, `svc_telemetry`, `svc_intake`, `svc_gamification`, `svc_billing`, `svc_recruiting`, `svc_connectors`) and implemented the helper `withServiceRole<T>(role, callback)` in `supabase/functions/_shared/database/db.ts` to execute transactions under `SET LOCAL ROLE <role>` (reverting on transaction exit).

However, an AST audit via `code-review-graph` (CRG) and the mechanical reality audit `just ticket-audit T382` revealed:
1. **Zero callers of `withServiceRole` in production edge functions**: Functions currently mutate the database via monolithic `SUPABASE_SERVICE_ROLE_KEY` PostgREST clients that completely bypass RLS and table boundaries.
2. **Schema grant gap for `svc_intake`**: Migration T206 partitioned intake tables (`contact_messages`, `subscribers`, `bug_reports`, etc.) but omitted `public.leads` and `public.lead_proposals`. Because `contact-submit` inserts into `leads`, `svc_intake` requires grants on `public.leads` and `public.lead_proposals`.
3. **Role precision**: `gamification-ingest` requires `withServiceRole('svc_gamification')` since `gamification.*` tables are granted exclusively to `svc_gamification`.

This ticket adopts `withServiceRole` across production edge functions that perform service-tier mutations:
1. **AI chat pipelines** (`supabase/functions/_shared/chat-core.ts::_persistChats`) adopt `svc_ai`.
2. **Gamification ingestion** (`gamification-ingest`) adopts `svc_gamification`.
3. **Inbound contact submissions** (`contact-submit`) adopt `svc_intake`, supported by a companion migration granting `leads` to `svc_intake`.

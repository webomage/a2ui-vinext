# T555 — Resume Studio: summary, skills, and per-variant exclusions

## Summary

Owner questions 2026-10-07: why the saved CV from Resume Studio carries no Executive Summary and no "Core Competencies & Technical Skills" although `resume_master` and the 2026 CV have both; and (mid-turn) "for saving themed resume versions we should allow to exclude manually non-relevant projects from contracts". Measured the same day (read-only):

- **Summary.** Studio prints `profiles.description`; the owner's is NULL; no code writes it (the only `description` writes are on experience and project rows) and Studio has no editor for it. Three texts exist in files with conflicting numbers: `resume.json` `basics.summary` (canonical per [[T165]]: 10,600+ hours, 93 contracts, 35 to 40% cost reduction), `private/resumes/resume_master.md` (older: 150+ projects, 40%, 10x), and the 2026 public CV (adopted 2026-08-26: 10,500+ hours, 100+ engagements, ACS accreditation, ANZSCO 261313, IELTS). T165 recorded that ACS/ANZSCO/IELTS are in neither `resume.json` nor `claims.json`. The "Suggest summary" assistant ([[T501]]) only summarizes saved highlights and may not add numbers or technologies.
- **Skills.** Studio derives one group, "Demonstrated Technologies" (max 20), from the `skills` arrays of `profile_experience` rows. All 95 of the owner's rows came from Upwork and carry no skills, `profile_skills` has 0 rows (and no group or order column), and the 29 curated facts hold 135 highlights with only 11 coarse tags. So the section is empty and the renderer omits it. `resume.json` has 5 groups of 4 keywords; the 2026 CV block has 7 groups and 57 items, of which nine terms have zero mentions in `resume.json` and `claims.json`: OpenTofu, FluxCD, vLLM, MLX, Ollama, Solidity, Infisical, Datadog, TypeScript.
- **Contracts and projects.** The Studio has a global per-highlight `excluded` flag (saved on the curated fact) and an extraction-import include toggle, but nothing to leave a whole contract, employer or project out of ONE themed variant, and a saved variant records no selection.

Rule that governs all of it ([[T165]], 2026-08-26): a generated CV may only assert what traces to `resume.json`; an externally drafted text is an input to verify, never a patch to apply.

## Acceptance criteria

- [ ] AC1 — **Owner decisions recorded here:** (a) which summary wording (recommended: the adopted 2026 text with the canonical numbers); (b) the skills base (recommended: the 2026 block's 7 groups, evidenced items only); (c) which of the nine unevidenced terms the owner can back, each with a project or contract; (d) whether ACS/IELTS evidence (date, English evidence submitted) goes into `certificates`.
- [x] AC2 — **Evidence report first, tests first.** A read-only tool that parses the chosen summary and skill groups and classifies every number and term as backed (traces to `resume.json`/`claims.json`, with the source) or unbacked, and lists numeric conflicts between the sources. Real-file tests (the nine terms are flagged; `Go` never matches `Google`; a number mismatch is reported). No database access.
- [~] AC3 — **Canonical first, then the database.** The canonical file carries the approved summary and the evidenced skills (and the ACS evidence if confirmed); a dry-run-first loader (the `upwork_loader` pattern: dry run is read-only, `--apply` is the owner's, a failure writes a failed-sync row) loads `profiles.description` and a grouped, ordered, evidence-linked `profile_skills` (migration: group, position, evidence reference; owner-only RLS with the admin arm behind `wom_admin_reads_personal_data()`, [[T545]]).
- [x] AC4 — **Studio reads and edits it.** Summary editor and grouped skills editor saving to the member's own rows; synthesis keeps ordering by the target job; "Suggest summary" proposes per job and never overwrites the saved text; component tests as the real signed-in role on a scratch database, not mocks.
- [x] AC5 — **Per-variant exclusions.** In a themed variant the member can leave out a whole contract or employer, individual projects, and individual skills, without changing the profile; the selection is stored with the saved variant (so reopening or re-exporting reproduces it), shown on the preview before saving, and test-pinned in synthesis (`excludedExperienceIds`, `excludedProjectIds`, `excludedSkills`). The existing global highlight `excluded` flag keeps its meaning.
- [ ] AC6 — **Public variant stays public.** The ACS reference number and private contact details never reach the public variant (leak gate green), and each saved variant records which source text it used.

- 2026-10-08 — **Automated security review of the PDF-on-save commits, two findings, both real, fixed.** (1) `resume-pdf` trusted "the row is visible to the caller" as ownership. An admin session can READ another member's `profile_resumes` row (the admin read arms), so it could have queued a render that WRITES a PDF into that member's vault. Now the row's `profile_id` must equal the caller's own `current_profile_id()`, and the path must be exactly `<profile id>/generated/<one file>.md` (three segments, none empty or a dot segment, no backslash, no NUL), not a string prefix with a `..` test. (2) The stylesheet check was a blocklist a browser reads differently: `u\72l(https://...)` is `url(` to a CSS parser and not to the regex, and `image-set("https://...")` and `src()` fetch without `url(`. It is now an allowlist by construction: no backslash at all, no `<`, no `@import`, `@font-face` or `@namespace`, no `url`, `image-set`, `src`, `cross-fade`, `element` or `paint` function, no script-capable CSS; the six themes use none of them (pinned across repos). 28 worker checks (11 new bypass attempts) and 11 Deno checks (5 new). Lesson candidate for LESSONS: a check on text that another parser will interpret must refuse the encodings, not enumerate the bad words.

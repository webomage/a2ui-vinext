# T524 — Supabase default grants: research, then decide

## Summary

Owner, 2026-10-01: *"can we make Supabase grant every new table and view to authenticated only by default?"*, then *"let's do safe access tweaks proposed for Supabase defaults, and check if we can somehow report or propose this to
Supabase defaults with contributing back"*, then *"make a ticket for later research for supabase with P2"*. This ticket is the research, to be done later. **Nothing is built or changed here.**

The question came out of [[T510]]: a new view in `public` was readable by every signed-in user, and by `anon`, until a migration revoked it, because Supabase's default privileges grant every new object to `anon`, `authenticated` and `service_role`.
The estate has tripped on this three times already ([[T289]], T4, and T510), each time through the same default.

## Measured (2026-10-01, live project, read-only; the earlier chat message is the source for the numbers)

- Default privileges for objects created by `postgres` in `public`: `ALL` on tables, `ALL` on sequences and `EXECUTE` on functions, to `postgres`, `anon`, `authenticated` and `service_role`. `supabase_admin` has the same defaults.
  The same pattern holds in `storage`, `graphql` and `graphql_public`. `gamification` and `upwork` are already narrowed to `service_role` by this estate's own migrations (T69, T468).
- All 126 relations in `public` are owned by `postgres`, so `postgres`'s defaults are the ones that apply to every migration.
- `anon` can read 109 of the 126 relations and holds a write privilege on 111. Row level security is on for every table (0 without it), and it is what actually stops anonymous writes today.
- A restored dump never receives these default grants, so a scratch-database test that passes can still be wide open live. The T510 harness now reproduces the defaults for that reason.
- Not measured: whether Supabase offers a project-level switch for this, and what their current guidance says. Do not assume either.

## The options the owner was given

| Option | New objects get | If a migration forgets |
|---|---|---|
| A. Remove `anon` only | `authenticated`, `service_role` | a forgotten `revoke` exposes it to every signed-in user |
| **B. Remove `anon` and `authenticated` (recommended in chat)** | `service_role` only | a forgotten `grant` breaks the feature visibly |
| C. Keep defaults | `anon`, `authenticated`, `service_role` | as today; relies on explicit revokes and the probes |

Views are the sharp edge: a view runs with its owner's rights and has no row security, so one that inherits `authenticated` is readable by anyone signed in.

## Research questions

- [ ] Q1 — **What does Supabase actually do, and why?** Find where the default privileges are set when a project is created (their Postgres image and platform repositories), whether a per-project or per-organisation setting exists, and what their own documentation says about the Data API exposing new objects. Record sources with dates.
- [ ] Q2 — **Is a change possible on our side without fighting the platform?** Whether `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE ...` survives platform upgrades and project restores, whether it can be applied for `supabase_admin` from a migration, and what the dashboard and CLI do with it. Test on a disposable local stack first, never on the live project.
- [ ] Q3 — **What breaks if we narrow the defaults?** From the live catalogue: which tables, views, functions and sequences are created by migrations or by platform features (Realtime, Storage, Auth hooks, the public chat running as `anon`) and rely on the default grants. List each with the migration that creates it.
- [ ] Q4 — **How is the existing exposure cleaned up?** 111 relations are already anon-writable behind row security. Which of them genuinely need anon access, and which should lose it. This is a separate change from the default and needs its own migration and probes.
- [ ] Q5 — **Has this been raised upstream already?** Search the platform's public issue tracker, discussions and changelog for the same request (default grants, "secure by default", Data API exposure), and read the contribution guidelines for the relevant repositories before drafting anything.
- [ ] Q6 — **What would a good upstream proposal contain?** A short, reproducible write-up (what is granted by default, a minimal example of a new view becoming readable, the estate's measured near-misses with identifying details removed), and a concrete suggestion (an opt-in or a setting, not a breaking default change). Draft it in `.agents/reports/`; do not post it.

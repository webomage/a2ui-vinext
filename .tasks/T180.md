# T180 — Tart macOS VMs as isolated agent sandboxes

## Summary

Owner direction 2026-08-07: *"I want to try for sure with macOS via tart"*, with the goal stated
explicitly when asked — **isolated macOS environments to run coding agents in**, the wom7sec
*"code-in-sandbox"* direction ([[T111]]).

🔑 **This is not a new capability request. It is a candidate answer to a decision already filed
twice and deliberately deferred:**

> **T153:150** — *"Whichever ticket moves first owns the substrate decision; the second reuses it."*
> **T171 AC5** — *"The sandbox substrate is decided ONCE with [[T153]]."*

T153 defines the substrate problem as **"isolation, lifecycle, credential injection, network
reachability"**. Tart has a primitive for each, measured below. ⇒ **This ticket should either win
that decision or be closed against whatever does — it must not become a third parallel substrate**,
which is the exact waste T171:161 warns about.

## 🔑 The reframe that makes this viable: agents in a macOS guest do not need Docker

The obvious blocker turns out to be irrelevant to the goal. Probed on this host:

```
$ tart run evercred --nested
Error: Nested virtualization is available for Mac with the M3 chip, and later.
```

This is an **M1 Max** ⇒ no hardware virtualization inside any Tart guest here, a property of the
hypervisor and hardware rather than the guest OS. So a macOS guest cannot run Docker Desktop,
colima, podman machine, or Apple's `container` — all of which start a Linux VM inside the guest.

**That bounds [[T179]] (DevPod needs a container runtime, so it is Linux-guest-only) but it does not
bound this ticket**, because an agent sandbox needs a *machine*, not a container. The interface is
SSH and `tart exec`, both of which work. ⚠️ **Do not carry the nested-virt result over from T179 as
if it were a blocker here** — it is a scoping fact for one and a non-issue for the other.

## 📍 Substrate primitives, measured 2026-08-07 (`tart run --help`, tart 2.32.1)

| T153's requirement | Tart primitive | Note |
|---|---|---|
| **Isolation** | full VM (Virtualization.framework), separate kernel | stronger than a container boundary |
| **Lifecycle** | `clone`/`run`/`stop`/`delete`, **APFS copy-on-write clones** | clean-slate reset per run; clone cost measured in AC2 |
| **Credential injection** | `--dir=path:ro` — host dirs are **opt-in and read-only-capable**; nothing mounted by default | matches [[T171]]'s capability-based boundary |
| **Network reachability** | `--net-softnet-allow/--net-softnet-block` (**CIDR allow/deny**), `--net-host` (host-only, no internet), `--net-softnet-expose` | 🔑 the strongest fit — egress allowlisting is exactly what auditing untrusted client code needs |
| Exfil surface | `--no-clipboard`, `--no-audio` | clipboard sharing is **on by default** — must be disabled explicitly |

🔴 **PREREQUISITE FOUND 2026-08-08 — the headline primitive does not run on this host as configured:**

```
$ softnet --vm-fd 3 --vm-mac-address 00:11:22:33:44:55
root privileges are required to run and passwordless sudo was not available
$ sudo -n true
sudo: a password is required
```

softnet is installed (`/opt/homebrew/bin/softnet` → Cellar 0.19.0) but **needs root, and this host
has no passwordless sudo** ⇒ `--net-softnet*` is currently **unavailable**, so every egress claim in
this ticket is a `--help` reading and nothing more. ⚠️ **This is AC3's premise arriving early**: the
flag exists, is documented, and still does not work here. **Owner action — a sudoers entry for
`softnet` is required before AC3 can be attempted**; it needs the owner's password, so no agent can
do it.

🔑 **`--net-softnet-allow` is the finding that makes this more than "a VM"** (once the above is
granted)**.** [[T153]]'s security
section is about auditing *client* code with a risk profile that is the wrong shape; a CIDR egress
allowlist enforced by the host — outside anything the guest or the agent can reach — is a control
the current `~/.zeroclaw/config.toml` `allowed_commands` approach cannot provide, because that one
is enforced by the thing being sandboxed.

## ✅ MEASURED 2026-08-08 — guest booted, probes run (AC2 evidence)

Image `ghcr.io/cirruslabs/macos-tahoe-base@sha256:1214590cd279a1ff82897d802624362ced1ff960d7b9f99a6ced5bbf8071e319`
(27.1 GB compressed → 50 GB disk), cloned to `macos-test`, 4 cpu / 8 GB, IP `192.168.64.11`.

| probe | result | why it matters |
|---|---|---|
| guest OS | macOS **26.6.1** (25G76), arm64, kernel `xnu-12377.161.13~4/**RELEASE_ARM64_VMAPPLE**` | the VM kernel variant — confirms guest context |
| 🔑 **`kern.hv_support`** | **0** (host = **1**) | 🔴 **no hypervisor inside the guest** ⇒ Docker Desktop / colima / podman / lima / Apple `container` **cannot start**. The `--nested` error, confirmed from the inside |
| `kern.hv_vmm_present` | **1** (host = **0**) | independently confirms we measured *inside* a VM |
| **CoW clone cost** | 🟢 **0 MB in 0.05 s** for a 50 GB VM | **clean-slate-per-run is free in both disk and time** — this is the lifecycle argument, and it holds |
| host dirs visible | 🟢 **none** — `/Volumes/My Shared Files` absent; only `Macintosh HD` | **`--dir` is genuinely opt-in**; nothing shared by default |
| `tart exec` | 🟢 works — returns guest `uname -a` **with no SSH credentials** | a control path that needs no secret in the sandbox |
| toolchain in base image | `git` ✅ `python3` ✅ · `brew` ❌ `node` ❌ · **all container runtimes absent** | an agent image needs provisioning; **no Homebrew** in the base |
| boot → SSH | 🔴 **> 300 s** on first boot | see caveat below |

⚠️ **Two honest caveats.**
1. **The container-runtime *install* attempt did not run.** The probe script planned
   `brew install colima docker`, and **the base image has no Homebrew**, so that path was never
   exercised. `hv_support = 0` settles the question on its own — every one of those runtimes
   requires a hypervisor — but this ticket records a **measured hardware fact, not an observed
   `docker` error message**. If a user-visible failure is wanted, Apple's `container` is the cheap
   next probe.
2. **The >300 s boot figure is a floor, not a measurement.** The harness timed out at 300 s and SSH
   answered immediately when retried by hand, so the true boot-to-SSH time is somewhere under that
   and unmeasured. **A defect in my probe, not in Tart** — recorded so it is not quoted as a
   platform characteristic. AC2 still needs a real number.

⚠️ **Disk is the live constraint, and it is not comfortable.** The host started at **94% full / 56.8
GB free** on a 926 GB volume. The pull ran behind a 10 GB floor guard. `macos-tahoe-xcode` is
**68.8 GB compressed / 140 GB disk** and **does not fit on this machine at all** — so any future
"agent builds iOS in a sandbox" variant is blocked on storage, not on Tart.

## Acceptance criteria

- [ ] **AC1 — the substrate decision is made ONCE, jointly with [[T153]] and [[T171]].** Either this
      ticket owns it and those two reuse it, or it defers. 🔴 An outcome where three tickets each
      stand up a sandbox is a **failure of this AC even if all three work**.
- [ ] **AC2 — the pending measurements above are recorded** with reproduce commands, including the
      CoW clone cost, since clean-slate-per-run is the whole lifecycle argument.
- [ ] **AC3a — 🔴 OWNER ACTION: grant `softnet` passwordless sudo** (measured blocked 2026-08-08,
      see above). AC3 cannot start until this lands, and no agent can do it.
- [ ] **AC3 — egress control is PROVEN RED, not assumed.** From inside a guest started with
      `--net-softnet-allow`, a request to a blocked CIDR must be shown *failing*. 🔑 This estate's
      most-repeated defect is a gate that was never observed blocking anything ([[T161]] AC3's
      non-firing `ask` tier, [[T169]]'s vacuous `mcp-exposure` green over an empty set). A network
      control adopted on the strength of a `--help` flag would be the same error.
- [ ] **AC4 — the default posture is deny.** Clipboard off, no host mounts, egress allowlist empty
      by default. Anything the sandbox is granted is granted explicitly and recorded.
- [ ] **AC5 — credentials for the agent inside are answered, not assumed.** 🔴 [[T171]] §3 already
      names this the hardest open question — whether **one personal Pro subscription** may back N
      concurrent automated agents is a **terms question, not an engineering one**. This ticket must
      not quietly answer it by shipping N sandboxes.
- [ ] **AC6 — the golden image is pinned and governed.** Pin by digest, not `:latest`. ⚠️ [[T171]]
      AC4b: an image that pins independently *"silently un-governs"* what [[T166]]/[[T164]] pinned.
- [ ] **AC7 — a disk budget exists before any fleet.** At 50 GB per macOS guest and ~46 GB free at
      filing, **this machine holds roughly one**. State the ceiling honestly rather than discovering
      it by filling the boot volume.
- [ ] **AC8 — macOS-vs-Linux guest choice is justified per workload, not by default.** A Linux guest
      is far cheaper and runs containers natively; macOS is warranted only where macOS-only tooling
      is. 🔑 If no workload needs macOS, the honest outcome of this ticket is *"use Linux guests"* —
      and that is a success, not a wasted ticket.

# T139 — Evaluate generated columns and materialized views for derived identifier lookups

## Summary

The **P2 half** of the owner's 2026-07-25 identifier ask, split out by explicit owner decision:
*"recommended B-tree for now and other 2 parts as a ticket with P2"*. [[T138]] does the B-tree and
functional-index work; this ticket evaluates the two heavier mechanisms — **generated/computed columns**
and **materialized views** — and adopts them only where they earn their cost.

**Both are entirely absent today, verified live 2026-07-25:** `information_schema.columns` reports
**0** columns with `is_generated <> 'NEVER'`, and `pg_matviews` reports **0** materialized views in
`public`. So this is net-new machinery, not a refactor — which is exactly why it is P2 and behind T138.

**Why it is second, not first.** A generated column still needs an index to be fast, so T138's work is a
prerequisite rather than an alternative. And a materialized view introduces a **staleness contract** the
system does not currently have anywhere: something must refresh it, someone must decide how stale is
acceptable, and a stale identifier lookup fails in a way a slow one does not.

## Acceptance criteria

- [ ] **AC1 — a real workload justifies each mechanism, or it is rejected.** Identify concrete slow or
      awkward lookups from actual query patterns (not hypotheticals) that a plain functional index from
      [[T138]] cannot serve well. **"No workload justifies these yet" is a valid and expected outcome** —
      record it and close the ticket rather than adopting machinery to satisfy the ask's wording.
- [ ] **AC2 — generated columns: decided with the trade-offs stated.** Where a derived identifier
      (normalized name, composite lookup key, computed slug) would help, compare
      `GENERATED ALWAYS AS … STORED` against a functional index on the same expression — the latter
      needs no schema change and no rewrite of existing rows. Note that Postgres `STORED` generated
      columns cannot reference other tables, which rules them out for cross-entity matching.
- [ ] **AC3 — materialized views: only with an explicit refresh and staleness contract.** Any proposed
      matview names what refreshes it (trigger, cron, `pg_cron`, edge function), the maximum acceptable
      staleness, whether `REFRESH … CONCURRENTLY` is possible (it requires a unique index), and what a
      reader sees mid-refresh. **No refresh owner ⇒ no matview.**
- [ ] **AC4 — RLS implications are checked, not assumed.** Materialized views do **not** enforce the RLS
      of their underlying tables, so a matview over tenant-scoped data can leak across tenants if it is
      readable. Given this project's RLS posture (98 tables, [[T117]]/auth-rbac work), any matview must
      state its access control explicitly. 🔴 **This is the security trap in this ticket.**
- [ ] **AC5 — measured, not asserted.** Any adopted mechanism ships with a before/after measurement on
      representative data volume, and the numbers go in the ticket. If the improvement is not measurable
      at current scale, it is not adopted yet.

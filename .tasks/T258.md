# T258 — a changelog nothing regenerated

## Summary

Owner question, 2026-08-22: *"do we have changelog by the way? we can do deploy version releases
changelog I guess if not yet"*.

**We did have one, and every moving part worked.** What did not exist was anything that ran it.

| component | state when asked |
|---|---|
| `public.deploy_log` table | ✅ real, **35 deploy stamps** |
| `just changelog` | ✅ works — `gen_changelog.py:46` genuinely writes the file |
| `deploy-all` recording deploys | ✅ self-wraps through `deploy_logged.py` since 2026-08-16 |
| `CHANGELOG.md` | 🔴 **one entry**, `2026.07.10-1783720961` — written by the commit that *added the generator* |

⇒ The table filled up for six weeks while the document sat where it was born. `just changelog` was
a manual recipe and nobody ran it, including me. Regenerating recovered **all 35 versions** (249
lines).

🔬 **I misread it once on the way in**, and the correction is the useful part: I first concluded the
recipe *"pipes to stdout and never persists"*, because the justfile line ends in a pipe into
`gen_changelog.py`. The script writes the file itself. The defect was never in the plumbing — it was
that nothing invoked the plumbing, which is a far less visible failure and needed a gate rather than
a fix.

## The gate is offline on purpose

`just changelog-drift` compares the newest heading in `CHANGELOG.md` against the newest deploy
transcript already on disk in `wom7api/deploy-logs/`. **It needs no database.**

A live check against `deploy_log` would be strictly stronger and **unrunnable in pre-commit** — so
it would have been declared, made non-blocking, and never run. The offline version is weaker and
would have caught this exact drift **on the day it started**: the transcripts on disk were stamped
`2026.08.14` and `2026.08.16` while the changelog said `2026.07.10`. That comparison is the only one
that matters when choosing between the two.

🔴 **A second finding, reported not fixed:** the newest record in *both* `deploy_log` and
`deploy-logs/` is **2026-08-16**, yet two deploys happened today (2026-08-22) — the agent-consultant
edge function and the worker. **Neither is recorded**, so they went through a path that does not log.
`deploy-all` self-wraps; a direct `supabase functions deploy` or `wrangler deploy` does not. That is
a gap in the recording surface, not in the changelog, and it is [[T259]].

## Acceptance criteria

- [x] **AC1** — ✅ **the record is restored**: `just changelog` regenerated `CHANGELOG.md` from
      `deploy_log`, **1 entry → 35 versions**, 249 lines, newest `2026.08.16-1786891220`.
- [x] **AC2** — ✅ **`just changelog-drift` exists and was RED on the real drift first** (2 deploys
      newer than the newest entry), then green after regeneration. Offline by construction.
- [x] **AC3** — ✅ **`just changelog-drift-test`, 11 probes.** Two pin readings that would have made
      the gate useless: stamps must order **numerically** (same-day deploys are exactly when a
      changelog falls behind by one, and `1786891220` vs `1786999999` mis-orders as text), and only
      **headings** count as releases (the preamble names the stamp *format* in prose, so whole-file
      parsing would let an empty changelog report a release — a document about being empty claiming
      to be full). Two mutation probes prove it fires on a newer deploy and stays silent on an older.
- [x] **AC4** — ✅ **the hole is closed at the source**: `deploy_logged.py` regenerates the changelog
      after a **successful** deploy, guarded exactly like the log rotation beside it — a failure
      there warns and never changes the deploy's verdict. Only on success: a changelog listing an
      aborted deploy is worse than a stale one.
- [x] **AC5** — ✅ **registered**: both suites in `project/test-suites.json`, tier `offline`,
      **blocking**; `just suites-drift` **126 declared / 0 undeclared**.

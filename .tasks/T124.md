# T124 — Find what else the publishable-key migration left behind

## Summary

Supabase moved from JWT-format anon keys (`eyJ…`) to publishable keys (`sb_publishable_…`, 46
chars). [[T121]] proved that migration left a **stranded JWT in production**: the chat widget's
lead-capture path shipped a hardcoded old-format key and had been failing with `401`.

This ticket asks the obvious follow-up: **what else still holds an old-format key?**

## Why it is worth a dedicated sweep

The T121 failure had three properties that make this class hard to notice:

1. **Silent.** The visible feature (chat) kept working because `agent-consultant` and
   `agent-architect` are deployed `--no-verify-jwt` and accept any token. Only the revenue path
   (`client-register`, which does verify) broke.
2. **Invisible to the obvious grep.** Searching for `eyJ` finds the *stale* keys and never the live
   one, because the live key is no longer a JWT. Anyone grepping to "check the anon key" gets a
   false picture — this misled the T121 investigation twice.
3. **Format-dependent.** Both formats look plausible in a diff; nothing fails at build time.

## Acceptance criteria

- [x] **AC1 — DONE** Every `eyJ`-format key literal across `wom7web`, `wom7api`, `wom7cfworkers`,
      `wom7ext` is inventoried, with: what reads it, whether it is live, and whether the endpoint
      it targets verifies JWTs.
- [x] **AC2 — DONE** Each is resolved — removed in favour of the injected variable, or explicitly
      justified if a JWT is genuinely still required somewhere.
- [x] **AC3 — DONE (Supabase) / PARTIAL (Cloudflare)** Supabase **secrets** (edge functions) and
      Cloudflare **worker** secrets are checked too, not only source. Cloudflare's API is
      write-only for secret values — see the limitation recorded below.
- [x] **AC4 — DONE** The `--no-verify-jwt` deployments are inventoried and each justified. They are
      why this was silent, and an endpoint that accepts any token is a decision, not a default.
- [x] **AC5 — DONE** A check that flags a JWT-format Supabase key literal in source, so a
      re-introduction is caught at commit time (gitleaks already flags them; make the signal
      actionable rather than a blocker people route around).

## Definition of Done

No unexplained `eyJ` key literal remains in any of the four repos or in either secret store; every
`--no-verify-jwt` function has a recorded reason; the commit-time check exists.

## Notes

- Start from the T121 evidence: the live key is `sb_publishable_…` (46 chars). Compare **lengths**

- The two test files (`tests/bot_security_steps.ts`, `tests/bot_chaos_steps.ts`) still carry stale

## ✅ 2026-07-23 — swept

### AC1/AC2 — source: two tracked offenders, both in `wom7web/tests`

Searching for the generic `eyJ` returns hundreds of hits that are **not** Supabase keys — Upwork
proposal markdown carrying third-party invite links, Terraform state, build caches under
`.wrangler/tmp`, Hatchet's own ES256 client token. Narrowing to the Supabase key prefix
(the header span `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9` immediately followed by a payload
beginning `eyJpc3MiOiJzdXBhYmFzZSI` — base64 of `{"alg":"HS256",
"typ":"JWT"}` + `{"iss":"supabase"`) reduces four repos to **exactly two tracked files**:

| File | What it was | Resolution |
|---|---|---|
| `tests/bot_security_steps.ts:15` | `PUBLIC_SUPABASE_ANON_KEY \|\| "<dead JWT>"` | fallback removed; throws when unset |
| `tests/bot_chaos_steps.ts:15` | same | fallback removed; throws when unset |

`wom7api` and `wom7cfworkers` and `wom7ext` are **clean** of Supabase JWT literals in tracked
source. Built output is clean too (`apps/*/dist` contains only `sb_publishable_…`); the `eyJ` hits
under `.wrangler/tmp` are a stale local dev cache, not shipped.

**A second bug in the same three lines.** `bot_security_steps.ts` also had:

```ts
const SERVICE_ROLE_KEY = process.env.SUPABASE_SERVICE_ROLE_KEY || … || ANON_KEY;
```

A test asserting *service-role* behaviour would silently run as **anon** and still pass. That is
worse than a dead key — a dead key fails visibly. Both fallbacks now throw.

**Untracked but worth recording:** `wom7api/dev_secrets_test.json` (gitignored) still holds a stale
JWT. Not a leak — but it is one more place where grepping "the anon key" returns a dead value and
misleads the next investigation, which is the whole complaint this ticket was filed over.

### AC3 — secret stores

**Supabase: verified live, on the current key.** The management API returns SHA-256 **digests**
rather than plaintext, which turns out to be the right tool for this audit — you can prove which
value a secret holds without ever reading it:

- `sha256(PUBLIC_SUPABASE_ANON_KEY)` = `a890b144…e38e34`
- the digest Supabase reports for both `SUPABASE_ANON_KEY` and `PUBLIC_SUPABASE_ANON_KEY` =
  `a890b144…e38e34` → **the store holds the live `sb_publishable_` key**
- `sha256(stale JWT from the test files)` = `95702a33…16a779` → **appears in none of the 96 secrets**

Formats confirmed by length+prefix only (never printing a value), which is the comparison the
ticket's own notes said exposed the T121 confusion:
`PUBLIC_SUPABASE_ANON_KEY` = 46 chars `sb_publishable_…`; `SUPABASE_SERVICE_ROLE_KEY` and
`SERVICE_ROLE_KEY` = 41 chars `sb_secret_…`. `wom7cfworkers/.dev.vars` likewise carries only
`sb_publishable_`/`sb_secret_` values; its single `eyJ` is Hatchet's, unrelated.

**⚠️ Cloudflare: cannot be verified this way — recorded as a real gap, not a pass.** Worker secret
values are **write-only** in Cloudflare's API; `wrangler secret list` returns names and types only.
The deployed worker holds `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_URL` (and **no** anon key at
all, so the T121 class cannot apply to it). Format is unverifiable directly; the available evidence
is behavioural — legacy JWT keys are rejected project-wide (that is *why* T121 401'd), so a stale
JWT there would break the worker's Supabase calls outright rather than fail silently.

**Also found:** infisical's `SUPABASE_ACCESS_TOKEN` is still the `sbp_8a54…` management PAT that
[[T67]] recorded as revoked on 2026-07-17. Unchanged, still dead — confirming T67's open item
rather than adding a new one.

### AC4 — the 19 `--no-verify-jwt` functions

25 edge functions; **19 run with `verify_jwt = false`**. Each was checked for what it does *instead*:

| Gate | Functions |
|---|---|
| hCaptcha (public forms) | `contact-submit`, `apply-submit` |
| Shared secret | `chat-internal` (`INTERNAL_AI_KEY`), `upwork-poller` (`WEBHOOK_SECRET`) |
| Own `getUser()` / role check | `admin-todos-api`, `admin-invite-candidate`, `get-bot-status`, `hume-token`, `gamification-ingest`, `gamification-processor`, `client-api`, `agent-consultant` |
| `requireAdminAuth()` unless service key | `get-admin-metrics` |
| Public by design | `cv-pdf` (proxies a public storage URL), `upwork-callback` (OAuth callback — must be unauthenticated), `log-event` (telemetry ingest), `agent-architect` |

**🔴 One is genuinely unauthenticated: `news-post-generator`.** No JWT, no shared secret, no cron
token, no captcha. It is a public `POST` that runs an **LLM generation** and performs a
**server-side fetch of a caller-supplied URL** (it carries a careful SSRF allowlist, which is
itself evidence someone knew the input was hostile). Its only cost control is
`checkQuota(..., 200_000)` — which, as [[T123]] AC3 established, **was failing open**. So: an
open endpoint spending money, with its one limiter disabled. Filed separately rather than fixed
here; the quota half is already fixed by T123 AC3.

**🟡 `get-upwork-status`** returns Upwork connection state (role names, per-account status) with no
caller gate. Low severity, but it is an unauthenticated read of account metadata.

**🟡 `get-admin-metrics`** compares the service key with `!==` — a non-constant-time comparison on a
credential, the same class the auth hardening work fixed as F3.

### AC5 — the commit-time check

Added to `wom7api/scripts/security_audit.py` (already wired into the pre-commit hook), running
before the slow scanners since it is a single substring over staged files.

It deliberately does **not** duplicate gitleaks. gitleaks says *"a JWT"* — a generic secret finding
that reads as noise and gets allowlisted. This says the specific true thing: **this key is dead,
Supabase issues `sb_publishable_…` now, read it from the injected variable and do not add a
fallback.** That is a fixable instruction rather than a blocker to route around.

It matches only the Supabase issuer prefix, so the repos' legitimate third-party JWTs do not trip
it — narrow beats noisy, per [[T123]]'s check that flagged 25 healthy functions.

**Proved it goes red**, not just green:

```
❌ Legacy JWT-format Supabase key found in staged files:
   t124_seed_test.ts:1
```

(seeded file staged, detected, then unstaged and deleted).

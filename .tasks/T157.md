# T157 — Pay down the orphaned migrations, and prevent direct DB changes

## Summary

**✅ DONE 2026-08-01.** Six versions were recorded in `supabase_migrations.schema_migrations` with
**no local migration file** — live but unreproducible, security hardening included. All six are now
committed, and direct DB changes are refused at the database itself.

⚠️ **It was 6, not 7.** The eighth-looking entry (`20260313 job_applications_linkedin_fields`) was
never orphaned: `db_drift_check.py`'s filename regex demanded exactly 14 digits and silently skipped
the one legacy migration versioned as a bare date, so an existing file looked missing. The checker
committed the exact defect it exists to detect. Fixed to `\d{8,14}`; the Supabase CLI's count of 6
was right all along.

Six are [[T122]]/[[T123]] **security** work — bucket hardening and definer revokes. None appear in

All six are T122/T123 security work. The `20260313` entry that briefly appeared in this list was a
false positive in our own checker, not a real orphan.

## Why it blocks

The Supabase CLI refuses `db push` with *Remote migration versions not found in local migrations
directory*. So **`just db-migrate` fails, and with it `just deploy-all`**, which depends on it.
Verified 2026-08-01.

## Do NOT use `migration repair --status reverted`

It asserts the migration was rolled back. While its effects are still in the database that is
simply false — it does not resolve the drift, it hides it behind a ledger that lies.

`AGENTS.md` recommended exactly this until 2026-08-01, and **that advice is how these 7 were
created.** It has been replaced with the recovery path.

## Fix

For each entry: reconstruct what it did — from the live schema, `supabase db pull`, or git history —
and commit a migration file under `wom7api/supabase/migrations/` whose version **matches the ledger
entry exactly**. Then delete its row from `project/db-drift-baseline.json`.

The changes are idempotent by nature (`REVOKE`/`GRANT`, bucket flags, policy drops), so
reconstructions can safely re-assert the current live state. Take care: writing a migration that
does not match what was actually applied would make a fresh database diverge from production in the
**security** layer specifically.

`just db-drift-check` already guarantees the count cannot rise meanwhile, and reports when a
baselined entry has been paid down.

## Prevention — the part the drift check could not do

`db-drift-check` compares files against the ledger, so it only ever sees a change that **wrote a
ledger row**. A plain `psql ALTER TABLE` writes none — it was structurally blind to the most common
form of ad-hoc change, and would report a clean database while the schema diverged.

Closed by **`wom_ddl_guard`** (`20260801170000_t157_ddl_guard_and_audit.sql`): a Postgres event
trigger that **refuses** DDL on `public`/`gamification` unless the session sets
`w0m.migration = 'on'`, which `just db-migrate` supplies via the connection string. All DDL is
recorded in `public.schema_change_log`; `just db-ddl-audit` lists out-of-band changes.

Scope is deliberately narrow — never `auth`/`storage`/`extensions`/`realtime`, never Supabase's
admin roles, because those are upgraded by the platform and blocking them would break auth and
storage.

**Proven in all six branches** (rolled-back transaction), then **against live production**: an
ad-hoc `ALTER TABLE public.profile_snapshots ADD COLUMN …` is refused, and the column does not
exist. A guard that has not been shown to refuse is not a guard.

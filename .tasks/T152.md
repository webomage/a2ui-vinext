# T152 — Dual-agent SDLC: Claude **and** OpenCode

## Summary

**Owner directive 2026-07-27:** *"deep Claude skills and tools and openspec provisioning to support
also opencode and gemma4 via omlx for small tasks offloading"*, *"we have to make wom7skills and sdlc
compatible with both Claude and Opencode"*, and *"we need also mastered Opencode config here to
support required skills and tools properly there"*.

Today the w0m toolset assumes **one** agent runtime. `wom7skills` ships `SKILL.md` units that Claude
Code discovers; the `w0m-sdlc-*` gates are Claude skills; `.w0m/skills.json` governs
`.agents/skills`. **OpenCode uses a different provisioning model entirely** — `AGENTS.md` for
instructions, a plugin for tool interception, its own `opencode.json` for models/providers/MCP. None
of that is currently produced from the canonical library, so a second runtime means a second
hand-maintained surface, which is the two-declarations-drift shape [[T149]] exists to kill.

✅ **The owner's Gemini conversation was supplied as a PDF** (*"Migrating Claude Code to OpenCode"*,
3pp) after the `/app/<id>` link proved unfetchable. **Its architectural claims are folded in below —
and the one that matters most was verified by measurement rather than taken on trust.**

**4. ~~Two of the three declared MCP servers are dead.~~ 🔧 CORRECTED — they are LIVE, and my first

## 🔴 THE BLOCKER — Gemma 4 via MLX cannot call tools, and it FABRICATES the result

The owner's stated goal is *"gemma4 via omlx for small tasks offloading"*. The supplied PDF warns of
a **function-calling gap**: local open-weight models often don't implement OpenCode's tool-calling
API, so they print code instead of executing it. **I tested it rather than trusting it, and reality
is worse than the warning.**

Sent a standard OpenAI tool-call request to the live server (`gemma-4-12b-coder-fable5-composer2.5-4bit`,
one `get_weather` function, `tool_choice: auto`):

```
tool_calls:     null
finish_reason:  stop
content:        <call:get_weather/>The weather in Paris is currently partly cloudy
                with a temperature of 21°C.
```

⇒ **Three separate problems, and the third is the dangerous one:**
1. The server **accepts `tools` without error** — so a caller gets no signal that tool use is
   unsupported. It fails open.
2. `tool_calls` is **null**; the model emits a bare text token `<call:get_weather/>`. It clearly
   knows *a* tool syntax, but the server never parses it into the OpenAI shape OpenCode requires.
3. 🔴 **It then INVENTED the answer** — "partly cloudy, 21°C" — with no tool ever invoked. **A
   fabricated result that reads exactly like a successful tool call.** This is the estate's
   organising failure mode in its most dangerous form yet: not a count over a partial set, but a
   *confident answer over no data at all.*

⇒ **"Small task offloading" must be re-scoped, and this is the ticket's central design decision.**
Gemma-4-via-MLX is viable for **text-in/text-out** work where the output is inspected — summarise,
classify, rewrite, draft. It is **NOT** currently viable for **agentic** work, and pointing SDLC
gates at it would produce plausible fabrications. Options, in order of soundness:
- **(a) Restrict offloading to non-tool tasks** and say so in config. Cheapest, honest, available now.
- **(b) Put a translating middleman in front** (LiteLLM / Ollama / vLLM) that emulates OpenAI
  function-calling, or a small shim parsing `<call:…/>` into `tool_calls`. ⚠️ A shim that
  mis-parses re-creates problem 3 silently — it needs the red-probe discipline of [[T149]].
- **(c) Keep a frontier model for agentic work**, offload only (a). Probably the real answer.
🔴 **Whatever is chosen, the fail-open behaviour must be closed:** a request carrying `tools` to a
backend that cannot honour them must **error**, never return prose.

## 🔴 AGENTS.md SILENTLY OVERRIDES CLAUDE.md — and w0m has both

Per the PDF: **if OpenCode finds `AGENTS.md`, it ignores `CLAUDE.md` entirely** (to avoid loading
overlapping rule files). `wom7web` has **both**. So every non-negotiable that lives only in
`CLAUDE.md` is **invisible to an OpenCode session**. Measured coverage:

| Rule | `CLAUDE.md` | `AGENTS.md` | OpenCode sees it? |
|---|---|---|---|
| Never `--no-verify` | ✅ | ✅ | yes |
| SDLC mandatory | ✅ | ✅ | yes |
| Infisical for secrets | ✅ | ✅ | yes |
| **No `Co-Authored-By` trailers** | ✅ | 🔴 **absent** | **NO** |
| **Conventional Commits + ticket id** | ✅ | 🔴 **absent** | **NO** |
| **Skills governed via `.w0m/skills.json`** | ✅ | 🔴 **absent** | **NO** |

⇒ **An OpenCode agent would write attribution trailers and non-conventional commit messages, and
would hand-place skills — all three explicitly prohibited.** The commit-msg hook catches the format,
but nothing catches the trailer. **This is live today**, not a future risk, since OpenCode is
installed and configured.

⚠️ Also: **OpenCode does not scan `.claude/commands/`**. `wom7web/.claude/commands/opsx` exists and
would simply not be available; OpenCode wants `.opencode/commands/` (none exists). And per the PDF,
OpenCode's model is **Commands (what) / Agents (who) / Skills (knowledge, loaded on demand — not
executable)**, so a Claude skill that *acts* does not port as-is: it becomes a skill **plus** a
command shortcut invoking `skill({name})`.

## 🔬 LIVE SESSION EVIDENCE 2026-07-27 — owner screenshot + root causes verified

A running OpenCode session (`Gemma4 Coder MLX`, OpenCode 1.18.6, 10,033 ctx, $0.00) was supplied.
**It reproduces the synthetic finding above in anger, and its MCP panel gave three exact faults.**

### 1. The tool-calling gap, reproduced live — and the diagnosis is sharper than "no tools"

Asked to *"list all macos apps in this folder"*, the model produced a **Plan**, then printed
`import os, glob / def list_mac_apps(): …` and `curl` lines **as chat text**, and finished:
`Build · Gemma4 Coder · 1m 6s`. **Nothing executed.**

🔴 **But the second exchange is the informative one.** Asked *"what tools do we have?"* it answered
**correctly and specifically** — `webfetch`, `task`, `codegraph_explore`, `read/grep/glob`,
`edit/write/todowrite` — and emitted `<skill>…</skill>` tags **as literal text**.
⇒ **OpenCode IS advertising its tools, and the model DOES know them by name.** The failure is
narrower than "local models can't do tools": the model cannot emit the **structured call format**
OpenCode parses, so it renders the invocation as prose. That matters, because it means a
**format-translation shim is a plausible fix** (option (b) in AC5) rather than a rewrite — the
intent is present, only the encoding is wrong.

### 2. `graphify` MCP — the configured command does not exist

Panel: `graphify  MCP error -32000: Connection closed`. Cause found:

| | |
|---|---|
| `opencode.jsonc` runs | `["graphify", "mcp", "serve"]` |
| Reality | 🔴 **`graphify mcp serve` is not a subcommand** — it falls through to *"Run 'graphify --help'"* |
| The real server | **`graphify-mcp`** (a separate binary = `python -m graphify.serve`), flags `--transport {stdio,http}` `--graph PATH` |

**Fix:** `"command": ["graphify-mcp", "--transport", "stdio"]`. ⚠️ Ties to [[T151]]: the graph it
would serve is **250 commits stale**, so connecting it is necessary but not sufficient.

### 3. `wom7md` / `wom7web` MCP — an IPv6 fallthrough, not a dead server

Panel: `SSE error: Unable to connect. Is the computer able to access the url?` **The servers are
healthy.** Measured:

| Probe | Result |
|---|---|
| `POST 127.0.0.1:3001/mcp` (proper `initialize`, Accept: json+event-stream) | ✅ **200**, `content-type: text/event-stream`, `mcp-session-id` issued |
| `http://[::1]:3001/mcp` | 🔴 **refused** |
| `localhost` resolves to | **`127.0.0.1` AND `::1`** |
| `GET /sse` (legacy transport) | 404 — Streamable HTTP only |

⇒ **The config says `http://localhost:3001/mcp`. `localhost` resolves to `::1` as well as
`127.0.0.1`, Obsidian binds IPv4-only, and Node clients commonly try `::1` first** — producing a
connection error that reads as "server down" when the server is fine.
**Fix: use `127.0.0.1`, not `localhost`, in `opencode.jsonc`** for both entries.
🔴 **This is the third time in two days a healthy service was reported dead by a probe aimed at the
wrong thing** (cf. my own `/v1/models` error above). ⚠️ **AC8's health recipe must resolve and try
every address a hostname yields**, or it will reproduce this exact false negative.

⇒ **Net: of 4 declared MCP servers, 1 works (`codegraph`), 3 fail — and all three are CONFIG faults
with known one-line fixes, not missing capability.** That is a much cheaper starting position than
the ticket's original framing.

## Why this is a [[T149]] child, not a standalone

The epic's rule is *one toolset, generated from one canonical source*. A second agent runtime is the
sharpest possible test of it: either `wom7skills` **generates** the OpenCode surface from the same
registry that feeds Claude, or the estate maintains two skill libraries that drift. [[T131]] already
built the versioning/provenance machinery this needs; [[T127]]'s manifest already decides which
skills a target receives. **This is a new consumer, not a new library.**

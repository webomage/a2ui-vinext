# T295 — test the Packer build

## Why

`project/clients/bridgeroad/vm-seed/bridgeroad.pkr.hcl` was written, `packer init` installed
`cirruslabs/tart` v1.21.0, and `packer validate` returned *"The configuration is valid."*

🔴 **That is the whole of the evidence, and it is the wrong kind.** `validate` parses HCL and checks
the schema; it does not run a builder, boot a guest, install anything, or produce an image. Shipping
a build definition whose only credential is that it parses is the estate's recorded *vacuous green*
shape — a gate that never looked. The same directory already contains the cautionary case: the shell
provisioner it replaced omitted Docker's own MTU pin and rebuilt a guest whose every container hung,
and nothing caught it **because nothing ran it**.

The stakes are higher for the Packer path than they were for the script, because its output is meant
to be **published to an OCI registry and cloned by other machines**. A broken script wastes one
person's afternoon; a broken image with a version tag is distributed.

## What already exists (do not rebuild)

- `bridgeroad.pkr.hcl` — validated, plugin installed, both MTU pins and a `hello-world` gate inline.
- `build.py` — drives `packer build -machine-readable` and optional `tart push`. There is no Python
  SDK for Packer (`packer` on PyPI is unrelated, 2013; `python-packer` predates HCL2, 2016;
  `packer-plugin-sdk` is Go, for writing plugins), so the CLI is correctly the interface.
- `provision.py` — the imperative single-machine path, which **has** been run end to end and produced
  a working box. It is the control: whatever the Packer path yields must match it.
- `README.md` — the six traps, of which MTU is the one that explains the others.

## Definition of Done

A Packer build has been executed, not merely validated: it produced an image, and the same template
with `mtu=1500` produced a **failure** — not a hang — so the `hello-world` gate is known to be
load-bearing rather than assumed to be. The image has made a full registry round-trip: pushed under
a date tag, then cloned under a **different** name onto a path that never held the source, booted,
and run a container, because a push that is never pulled proves only that bytes were uploaded. What
that date tag promises is written down, it does not move, and how many such tags are kept — and by
whom — is answered rather than left to accumulate at ~3 GB each. The Packer path and `provision.py`
agree on what they install and where they pin MTU, held by a probe that fails when they drift, or
one of them has been deleted. Where the build runs is a stated decision rather than an assumption
about CI that this account cannot honour. And the base the build starts from is declared — including
that no upstream 26.04 exists to fall back on, so this estate is its only producer — with its
staleness detected rather than left to whoever remembers a flag.

## Notes, traps and dependencies

- ⚠️ **`packer validate` passing is what makes this ticket easy to skip.** It reads like a green
  check. It is a parser.
- 🔴 **Do not diagnose an MTU failure with ping** — ICMP is filtered on this host, so
  `ping -M do -s <size>` reports DROPPED at every size and tells you nothing. Only a real HTTP fetch
  at different MTUs is honest. Measured: 1500 hangs, 1400 hangs, 1280 returns 200 in 0.74s.
- ⚠️ **`tart ip` cannot be trusted here** — it reads the MAC-keyed DHCP lease while these cloud
  images request one with a client-id, so it reports an address the guest does not hold and that
  changes every boot. `build.py` probes `/var/db/dhcpd_leases` instead; anything new must too.
- 🔴 **`cirruslabs/ubuntu:docker` is Ubuntu 22.04.3, NOT 24.04 — measured by booting it.** The "24"
  that everyone reads as the Ubuntu version is **Docker 24.0.7**, the Docker version it ships
  (compose v2.21.0). Both the owner and I described it as "24.04 with Docker preinstalled" from the
  tag name alone; it is two Ubuntu LTS releases and five Docker majors behind. Recorded because the
  name will keep re-suggesting it. `:24.04` and `:latest` are the same image and genuinely 24.04.4.
- 🔴 **No cirruslabs image ships the Tart Guest Agent, despite tart's own docs.** `tart exec --help`
  states "all non-vanilla Cirrus Labs VM images already have the Tart Guest Agent installed".
  Measured on `:docker`: no `tart-guest-agent` binary, no tart systemd unit, and `tart exec` never
  answered in over two minutes. ⇒ the agent is ours to install on **any** base, which is what
  decided the base question — the upstream images' last advantage did not exist.
- 🔑 **`tart exec` is the native access path and it retires a whole scaffolding.** Once our agent is
  installed, `tart exec <vm> <cmd>` replaces the SSH + DHCP-lease-hunting this build needed — and
  with it the `tart ip` trap. AC1 should exercise `tart exec`, not ssh.
- ⚠️ **The upstream systemd unit cannot start as shipped** — `ExecStart=tart-guest-agent` has no
  absolute path and systemd requires one. The Packer template authors the unit rather than copying
  `packaging/tart-guest-agent.service`.
- ⚠️ **The fork's features are GUI-facing and inert here.** Clipboard, file transfer, tray and
  notifications need a display; on the headless master image the agent is purely an RPC endpoint.
  Owner 2026-09-01: *"the version with GUI will come later, now we have master fast and lightweight
  image"* — so the fork's value is deferred, not absent, and a GUI variant is a separate image.
- ✅ **The stale-base trap is now DETECTED, not left to memory** (2026-09-01, feeds AC7). It cost an
  afternoon once: `dhcp-identifier: mac` was added to the seed, `make_base` silently reused a base
  built before it, and the Packer failure that fix addressed kept reproducing against a "fixed"
  tree. `build.py` now fingerprints the seed's *content* and stores it beside the base; a changed
  seed, or **no recorded fingerprint at all**, means rebuild — unknown is treated as stale rather
  than as fine. `--rebuild-base` forces it. 🔑 A flag you must remember is not a gate, which is why
  the flag is the smaller half of this.
  ⚠️ **And the first fingerprint was wrong in the way that looks right:** it hashed `meta-data`
  whole, including `instance-id`, which embeds a timestamp on purpose so cloud-init re-runs. So the
  hash differed on every call, every base read as STALE, and the guard degenerated into *always
  rebuild* — indistinguishable from working, and only ever slower. **Caught by exercising the REUSE
  cycle, not the stale one**: the stale path passed first try and hid it. Both cycles are the test.

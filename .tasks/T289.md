# T289 — anon holds EXECUTE on 27 public functions

## Summary

Found 2026-08-26 while checking a grant on a new RPC. Measured on production:

```
public functions total        53
anon can EXECUTE              27
  of those SECURITY DEFINER   13
```

The 13: `accept_lead_proposal`, `current_profile_id`, `get_user_roles`,
`handle_user_email_confirmed`, `has_role`, `is_admin`, `wom_acting_in`, `wom_acting_is`,
`wom_acting_role`, `wom_lead_is_mine`, `wom_public_persona`, `wom_role_set`, +1.

🔑 **This is the Supabase default, not a mistake anyone made.** `ALTER DEFAULT PRIVILEGES … GRANT
EXECUTE ON FUNCTIONS TO anon, authenticated, service_role` means every function created in `public`
arrives with an EXPLICIT per-role grant — the ACL reads `anon=X/postgres`.

🔴 **And that is exactly why `REVOKE ALL … FROM PUBLIC` is a trap.** It removes the implicit PUBLIC
grant, which is a different thing. Two migrations shipped that revoke on 2026-08-26 believing it
locked anon out; it did not, and the ticket that wrote them ([[T4]]) had a probe ASSERTING the
property which passed anyway — the probe replays onto a restored dump, and a scratch database never
receives the ALTER DEFAULT PRIVILEGES, so revoking PUBLIC really was sufficient *there*. Fixed for
those two in `20260826050000`; the pattern is estate-wide.

## Acceptance criteria

- [x] **AC1 — decide per function, do not sweep.** Most of these are harmless: `wom_acting_is`,
      `has_role`, `is_admin` read the caller's own JWT and return false for anon. A blanket revoke
      would break the public consultant chat, which resolves to `anon` on every request
      ([[T246]] — that outage cost a day). ⚠️ **A revoke here is only safe once the anon call sites
      are known**, and [[T154]]'s lesson applies: declared ≠ configured ≠ actually called.
- [x] **AC2 — the rule goes where functions are written.** A migration author cannot be expected to
      re-derive this. State in the migration standard that `REVOKE … FROM PUBLIC` does not remove a
      default-privilege grant, and that `FROM anon` is the one that does.
- [x] **AC3 — a probe that measures the LIVE grant.** 🔴 Not a scratch database: the scratch is
      exactly where this property looks fine while being false. Whatever this ticket ships must read
      production, or it will reproduce the bug it exists to catch.
- [x] **AC4 — a ratchet, not a hard zero.** 27 is the baseline; it may fall and may never rise. A
      hard zero would be a gate nobody can pass and everybody switches off ([[T135]] AC8).

## Definition of Done

Every anon-executable SECURITY DEFINER function in `public` is either revoked or written down as
deliberately reachable WITH the call site that needs it — and the count is a downward-only ratchet
measured against the LIVE database, because a scratch restore is precisely where this property
reads as fine while being false. The rule that `REVOKE … FROM PUBLIC` leaves a default-privilege
grant intact is recorded where the next migration author will meet it, not only in this ticket.

🔴 **Not done if it ships as a blanket revoke.** The public consultant chat runs as `anon`; T246
already cost a day to a revoke that was correct in principle and broke a live surface.

## The decision (AC1) — all eleven, measured against production 2026-08-26

Every one was measured, not reasoned about. `just anon-execute-ratchet` prints this list on
every run, so the decision stays visible rather than living only here.

**KEPT — anon genuinely reaches these. Listed in `project/anon-execute-baseline.json` with the
call site, because a list without call sites is a rubber stamp.**

| function | why anon needs it |
|---|---|
| `wom_acting_is(text)` | called by **10** RLS policies anon evaluates; revoking makes them *error* instead of returning false |
| `wom_acting_in(variadic text[])` | same, on **3** policies |
| `wom_public_persona(text)` | T246's own fix — the public consultant chat is unauthenticated, resolves to anon, and this returns the persona prompt (measured: a real 2,752-char prompt) |

**REVOKED — `20260826080000` (anon arm) + `20260826090000` (PUBLIC arm).** Four independent paths were checked
for each, and all four were empty:

| function | anon-reachable policies | PostgREST call sites | transitive reach | returns to anon |
|---|---|---|---|---|
| `current_profile_id()` | 0 | 0 | none | `NULL` |
| `get_user_roles()` | 0 | 0 | none | empty |
| `has_role(text)` | 0 | 0 | none | `false` |
| `is_admin()` | 0 | 0 | none | `false` |
| `wom_acting_role()` | 0 | 0 | none | `NULL` |
| `wom_role_set()` | 0 | 0 | none | empty |
| `handle_user_email_confirmed()` | n/a | n/a | n/a | **not callable** |
| `handle_user_profile_sync()` | n/a | n/a | n/a | **not callable** |

*Transitive reach* means: no SECURITY INVOKER function anon may execute, no `security_invoker` view
anon may read, and no column default or check constraint on an anon-writable table mentions them.

The two trigger functions are refused by Postgres itself — *"trigger functions can only be called
as triggers"* — and both sit on `auth.users`, where anon has neither INSERT nor UPDATE, so the
trigger never fires with anon as the actor either. The grant is inert in both directions.

The 70 `is_admin` references in migration history are all `authenticated`-scoped policies. Counting
them without asking which ROLE evaluates the policy is how a blanket revoke gets justified.

**Proven safe before shipping.** The eight revokes were applied to production inside a transaction
that was then ROLLED BACK, while counting every row anon can see across all **97** anon-readable
tables in `public`. Result: 97 readable before, 97 after, zero errors, zero row-count changes.

## Status notes

Filed 2026-08-26. Built the same day.

**The gate shipped broken first, and this is the part worth remembering.** `prosecdef::text`
renders `true`/`false`, while psql *displaying* a boolean column renders `t`/`f`. The probe
compared against `"t"`, so every function parsed as SECURITY INVOKER, the definer count read **0**
against a baseline of 3, and the sharpest check — an unlisted definer function — could never fire.
It would have sat green forever while measuring nothing. The selftest passed too, because it
exercised only the comparison and the bug was in the parse layer. Four of the nine selftest cases
now drive `parse_rows` with real psql output shapes. **A probe's own dialect assumptions are part
of what has to be tested** — this estate's recurring finding, found again by the thing hunting it.

**Then it shipped a SECOND bug, and this one is the ticket's real finding.** `20260826080000`
revoked anon's explicit grant on all eight. Every statement succeeded, every `anon=X` entry
disappeared from the ACLs — and **only one of the eight became unreachable**.

A function in `public` carries up to **two independent** EXECUTE grants, and anon reaches it
through either:

| ACL entry | source |
|---|---|
| `=X/postgres` | PostgreSQL's own default — EXECUTE to **PUBLIC** on every new function |
| `anon=X/postgres` | Supabase's `ALTER DEFAULT PRIVILEGES ... TO anon, authenticated, service_role` |

This ticket was filed because `REVOKE ... FROM PUBLIC` was believed sufficient and was not. The fix
over-rotated to "`FROM anon` is the one that works" — and left the PUBLIC arm on **7 of 8**.
`current_profile_id` is the control that proves the reading: its ACL carried no PUBLIC entry, so
`FROM anon` alone was enough *there*. Seven identical-looking functions behaved differently for a
reason visible only in `proacl`. **It takes both:**

```sql
revoke execute on function public.is_admin() from public, anon;
```

The lesson is not "add a second REVOKE". It is that **a grant is not gone because a REVOKE naming
it succeeded — it is gone when the ACL says so.** Both docs were corrected; the earlier wording
made `FROM anon` the whole rule and would have taught the next author the mirror-image mistake.

The probe now prints the granting arm (`[via PUBLIC]` / `[via anon]` / `[via PUBLIC+anon]`) next to
every definer function, which is what turned this from an afternoon of reading `proacl` into one
line of output. And the gate is the only reason it was caught at all: the migration applied
cleanly, the ledger recorded it, and nothing else in the estate would have noticed.

Including the two trigger functions in the PUBLIC revoke needed its own experiment rather than a
recollection of the manual: Postgres checks EXECUTE on a trigger function at **CREATE TRIGGER**,
not at fire time — measured directly on a temp table whose trigger function had EXECUTE revoked
from both PUBLIC and anon, which still fired on an INSERT performed as anon. The `auth.users`
signup path cannot break.

**Verified after `20260826090000`:** the ratchet reads **17 anon-executable / 3 definer**, green.
`public-chat-check` 4/4 (T246's surface intact), `anon-reader-check` 0 broken, `authz-probe-check`
0 RED of 18.

**And then the suite's own guard turned out to be the third bug.** `authz-probe-check` reported
G2 green — *"no SECURITY DEFINER function in public still has the default PUBLIC execute grant"* —
while `wom_acting_is` and `wom_acting_in` both plainly had it. G2 tested `p.proacl IS NULL`.
`proacl` is NULL only while **no grant statement has ever touched the function**, and Supabase's
`ALTER DEFAULT PRIVILEGES` gives every new function in `public` a materialized ACL on creation. So
the count was 0 on every run and **could not have been anything else** — the `=X/postgres` entry
sat inside those ACLs, unread, for the guard's entire life. Its own rationale said so out loud:
*"All 32 carry explicit ACLs"*.

Rewritten to `aclexplode(proacl) WHERE grantee = 0`, it found both immediately and went RED before
the fix — which is the demonstration the original never had. `20260826100000` revokes the PUBLIC
arm from both while keeping anon's explicit grant, so anon's reachability is unchanged and becomes
a per-role decision rather than a default. Measured safe as `anon` **and** `authenticated`: 97
tables readable before and after for each, zero row-count changes.

🔑 **Three bugs, one shape.** The parse dialect, the missing PUBLIC arm, and G2's predicate were
all *statements that succeeded while measuring nothing*. Each was caught by the next probe down the
chain, and G2 was caught only because a new probe disagreed with an old one. **When two gates
disagree about the same property, one of them is lying — resolve it, do not average it.**

**DONE 2026-08-26.** After `20260826100000`: the ratchet reads **17 / 3** and all three remaining
definer functions report `[via anon]` — no PUBLIC arm anywhere in `public`. G2 is green **and can
now fail** (it was red at 2 immediately before the migration). `public-chat-check` 4/4,
`anon-reader-check` 0 broken, `authz-probe-check` 0 RED of 18.

Three migrations, because the property took three tries to actually measure: `20260826080000`
(anon arm), `20260826090000` (PUBLIC arm), `20260826100000` (PUBLIC arm on the two kept functions).
Lessons recorded in `LESSONS.md`.

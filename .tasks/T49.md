# T49 — Fix mutable search_path on security-critical Postgres functions

## Summary

Audit and fix several critical Postgres database functions (such as `has_role`, `is_admin`, `get_user_daily_tokens`, `update_updated_at_column`, and `get_heatmap_sessions`) that lack a fixed `search_path`. Without a fixed path, these functions are vulnerable to search-path hijacking/injection if the search path is ever manipulated at execution time.

## Acceptance criteria

- [x] **AC1 — DONE** Audit all functions in `wom7api` schema migrations. **Audited against the
      LIVE database rather than the migrations** — see "the named list was stale" below.
- [x] **AC2 — DONE** Add a fixed `search_path` to every offender. The ticket's named five turned
      out to be the wrong list; the nine real ones are enumerated below.
- [x] **AC3 — DONE** Deploy the fix as a new SQL migration file under `wom7api/supabase/migrations/`
      — `20260723101000_t49_fix_mutable_search_path.sql`.
- [x] **AC4 — DONE** Ensure all local and remote unit tests continue to pass. Verified 2026-07-25:
      `just deno-test` **18 passed / 0 failed**, `just test` (vitest) **1 passed / 0 failed**.
      ⚠️ State the size honestly: that is the *entire* unit corpus — one smoke spec on the web side.
      It proves the migration broke nothing; it is **not** coverage of the nine functions. The
      load-bearing regression guard for this ticket is **AC5's standing check**, not AC4.
      🔎 Running this AC is what exposed a **live breakage unrelated to T49**: `just test` was

- [x] **AC5 — ADDED** A standing check asserts no `public`/`gamification` function has an unset

## ✅ 2026-07-23 — fixed, and the ticket's own list was the problem

Migration: `wom7api/supabase/migrations/20260723101000_t49_fix_mutable_search_path.sql`.

### 🔴 The named list was stale — working it would have fixed nothing

T49 named five functions. Checked live, **four were already fixed and one does not exist**:

| Named in T49 | Live state |
|---|---|
| `has_role` | already `search_path=''` |
| `is_admin` | already `search_path=''` |
| `get_user_daily_tokens` | already `search_path=''` |
| `get_heatmap_sessions` | already `search_path=''` |
| `update_updated_at_column` | **does not exist** — the live trigger functions are `set_updated_at` and `update_cert_updated_at` |

The four were fixed *in passing* by [[T68]]'s migration `20260717130000`, which set `search_path=''`
on the 16 `archive_*`/`restore_*` functions and the helpers they touched. Nobody updated T49.

So the ticket as written would have produced four no-op `ALTER`s, one error, a green checkmark —
and left **all nine real offenders in place**. This is the same failure [[T123]] documents one
ticket over: *a remediation aimed at a list rather than at a pattern*. The list was even correct
when it was written. Lists rot; properties do not.

### The nine, from the live advisor

| Function | Kind | Fix |
|---|---|---|
| `public.hard_delete_user` | **SECURITY DEFINER**, NULL proconfig | `ALTER` |
| `public.set_updated_at` | trigger | `ALTER` |
| `public.update_cert_updated_at` | trigger | `ALTER` |
| `gamification.adventure_budget` | invoker | `ALTER` |
| `gamification.default_adventure_for` | invoker | `ALTER` |
| `gamification.quest_project_id` | invoker | `ALTER` |
| `gamification.raid_budget` | invoker | `ALTER` |
| `gamification.raids_attach_default_adventure` | trigger | `ALTER` |
| `public.match_documents` | invoker | **REPLACE** — body needed qualifying |

Plus `public.get_top_clicks`, which the advisor does **not** flag because it has
`search_path=public`. Normalised to `''` anyway: "set" and "safe" are not the same property —
`public` is precisely the schema an attacker would target. Its body referenced `analytics_events`
unqualified, so the body was qualified in the same step.

`hard_delete_user` was the sharpest: SECURITY DEFINER, NULL `search_path`, and its *only*
authorization is the `public.is_admin()` call in its body. That call is schema-qualified, so it was
not actually hijackable — but a deletion primitive whose guard depends on name resolution should
not also leave name resolution to the caller. ([[T123]] AC3 additionally revokes its EXECUTE.)

### Why `''` and not the ticket's `public, pg_catalog`

An empty `search_path` forces every reference to be schema-qualified, so the hazard cannot
silently come back. Verified that neither `anon` nor `authenticated` currently holds `CREATE` on
`public`, `extensions` or `gamification` — so both forms are safe *today*; `''` stays safe if that
ever changes.

### `match_documents` — the reason people give up on `''`

Two things break, and only one is obvious:

1. `FROM documents` is unqualified.
2. **`<=>` is pgvector's cosine-distance operator, which lives in `extensions`, not `pg_catalog`.**
   An empty `search_path` makes the *operator* unresolvable too, not just the table.

That second one is what makes `''` look impossible and pushes people to settle for
`search_path = public`. The fix is `OPERATOR(extensions.<=>)`, plus qualifying the `vector`
argument type for the same reason.

### AC5: the standing check

```
❌ FAIL [grants] mutable search_path — 9: gamification.adventure_budget, … public.hard_delete_user …
```

That is the check run against live state before the migration — it names exactly the nine. It
asserts the *property* (`proconfig` contains a `search_path` entry) across all of `public` and
`gamification`, so it cannot go stale the way this ticket's list did.

### 🔎 AC4 was not free — it found a silently dead test suite (fixed 2026-07-25)

Ticking AC4 required actually running the suite. `just test` **failed at collection**: 0 test files,
`Cannot find module 'undici/lib/handler/wrap-handler.js'`.

Cause — a **security floor with no upper bound**. `project/deps-policy.json` carries
`floors.undici = ">=7.28.0"`, which pnpm is free to satisfy with **undici 8.7.0**. But `jsdom@29`
(vitest's DOM environment) reaches into undici's *internal* `lib/handler/wrap-handler.js`, which
exists in 7.x and is **gone in 8.x**. So the floor — a security control — silently disabled the
entire web-side test suite.

Fix: bound it **in wom7web only**, `">=7.28.0 <8"` → resolves **7.29.0**, still above the floor, so
**no patch level was given up**. `wom7api`/`wom7cfworkers` have no jsdom, are fine on 8.x, and were
deliberately left open-ended; recorded in `deps-policy.json` → `exceptions.undici` so nobody
"aligns" them back. Same shape as the existing `protobufjs` and `ws` exceptions.

⚠️ **Generalisable defect, now [[T140]]:** `deps_sync.py` compares only the **first** `x.y.z` in a
range, so it enforces the lower bound and is **blind to an upper bound** — it can neither propagate
`<8` nor detect a repo that lost it. A bounded floor is therefore honoured by convention only.
And the failure mode here is the dangerous one: **an unbounded floor is silently satisfiable by a
breaking major.**

### ⚠️ Note on `CREATE OR REPLACE` and ACLs

Replacing a function **resets its ACL to the owner default, which is EXECUTE to PUBLIC**. Both
functions replaced here (`get_top_clicks`, `match_documents`) therefore re-assert their grants
explicitly at the end of the migration. Without that, this migration would have silently undone
[[T123]]'s revokes — a fix quietly reopening the hole the neighbouring ticket just closed.

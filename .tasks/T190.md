# T190 — close the three blind spots skills governance has

## Summary

The first two findings came out of resolving [[D42]] on 2026-08-08 (installing `security-guardrails`, the
skill the *security gate itself* names and which was installed nowhere). Neither is the missing
skill — that is fixed. These are the reasons **nothing noticed for weeks while every gate stayed
green**.

## 🔴 Finding 1 — `just skill relock` INVENTS a manifest instead of refusing

Run from a repo that has no `.w0m/skills.json`, `relock` does not fail. It **creates one**, empty,
plus an empty lockfile, and reports `w0m skill: lockfile re-hashed.` — a success message for an
operation that governed nothing.

**Observed, not theorised:** during D42's own fix I ran it from `wom7api`, and it wrote
`wom7api/.w0m/skills.json` + `.w0m/skills.lock.json` (`"project": "wom7api"`, `"skills": {}`).
Caught only because the files were untracked and I checked `git status` before continuing; deleted.

**Why it matters:** the estate's rule is *one manifest, in the consuming project*
(`wom7web/.w0m/`). A second manifest appearing in a sibling repo — created by the governance tool
itself, with a plausible name and a success message — is precisely how governance forks. The next
agent running `skill check` there gets a green *"0 managed of 0 declared"* against a file that
should not exist.

⚠️ **This is the wrong-root class**, and it now has three occupants: `@wom/.serena/project.yml`
([[D32]]/[[T172]]), `just skill check` read from `wom7api` (which is what produced the *false*
"several unmanaged skills" claim in D42, since retracted), and this. **A tool pointed at the wrong
root does not fail — it returns a confident wrong answer.**

## 🔴 Finding 2 — `skill check` compares installed↔manifest, never canonical↔installed

`just skill check` answers *"is everything installed also declared and unmodified?"* It is
structurally incapable of answering *"is everything canonical actually installed?"*

**Measured 2026-08-08:** **33 canonical skills** in `wom7skills/skills/`, **12 installed nowhere**:

| | |
|---|---|
| canonical in `wom7skills` | **33** |
| declared + installed in `wom7web` | 21 (22 after D42) |
| **canonical, installed NOWHERE** | **12 → 11 after D42** |

`doubt-driven-development` · `feynman` · `mmd-validate` · `observability-and-instrumentation` ·
`playwright-testing` · `score-orchestration` · ~~`security-guardrails`~~ (fixed, D42) · `socrates` ·
`sourcing-integration` · `steve-jobs` · `supabase-postgres` · `torvalds`

🔬 **CENSUS CORRECTED 2026-09-08 — four of those are installed after all, just nowhere either tool
looks.** `doubt-driven-development`, `feynman`, `socrates` and `torvalds` are all present and
tracked in the **estate root** surface (`@wom/.agents/skills/`), which is neither synced nor
governed — see Finding 3. So *"installed nowhere"* was itself a wrong-root answer: **11 → 7**
genuinely uninstalled, and AC3's denominator changes accordingly.

**`security-guardrails` was in that list**, which is the whole point: a skill named by
`.w0m/sdlc.json → quality_gates.security_review_skill` sat uninstalled while `skill check` reported
**0 unmanaged**, because the gate only ever looked in one direction. [[D37]]'s shape — *a check that
appears to have looked* — inside the skills layer.

⚠️ **`mmd-validate` is the sharpest instance:** its registry entry says it is *"the skill behind
wom7web's `mmd-validate` pre-commit hook"* — a skill describing a live hook, installed nowhere.

## Finding 3 — a third skills surface exists at the estate root, governed by neither tool

**Measured 2026-09-08.** `@wom/.agents/skills/` is a real directory (not a symlink), **23 skills,
24 files, all tracked** in `casualuser/w0m` since [[T312]]. It loads for any agent started from the
workspace root — which is the umbrella, and the common case. Both tools report green over it while
covering none of it:

| | |
|---|---|
| skills at the estate root | **23** (19 identical to `wom7web`, **4 root-only**) |
| of those, declared in any manifest | **0** — the estate root has no `.w0m/skills.json` |
| `just skills-sync check` | *"23 active skill(s) in sync"* — counts `wom7web`'s targets, never writes here |
| `just skill check` | scoped to `wom7web/.claude/skills` (88 installed · 0 unmanaged); names `~/.claude/skills` as NOT COVERED and **never mentions the estate root at all** |

The four root-only skills — `doubt-driven-development` · `feynman` · `socrates` · `torvalds` — are
hand-placed executable instructions with **no provenance record anywhere**, and two of them are
`origin: imported` third-party content per AC3. `just skills-sync` targets `wom7web/.agents/skills`
with `.claude/`+`.opencode/` as symlinks; it has no notion of the level above it, so the estate root
is maintained by hand and drifts silently. One file (`fact-checker/SKILL.md`) had in fact drifted and
was corrected by hand on 2026-09-08 — the drift was found by reading the file for another reason,
not by a gate.

⚠️ **This interacts with AC1 and the interaction has to be decided, not discovered.** AC1 makes
lock commands *refuse* a manifest-less root — correct, and it would refuse here. But the estate root
is a manifest-less root **with 23 live skills in it**, so refusal alone leaves it permanently
ungoverned. Refuse *and* report is the only combination that does not trade one silent gap for
another. 🔑 Fourth occupant of the wrong-root class, and the first one where the wrong root is the
**workspace root itself** — the place [[T316]] is separately arguing tooling should live.

✅ **RESOLVED for the root specifically — 2026-09-15, by [[T232]], not by this ticket.** T232 gave
`w0m_skill.ts` a `--project <path>` flag and installed `@wom/.w0m/skills.json` +
`skills.lock.json` (created in `e506674`). Re-measured today: `w0m skill check --project
/Users/proto/Projects/@self/@wom` now reports **23 installed — 23 managed · 0 unmanaged**,
lockfile matches. The 4 root-only skills carry real provenance in the manifest —
`doubt-driven-development` correctly `provider: skills.sh` / `addyosmani/agent-skills`;
`feynman`/`socrates`/`torvalds` `provider: w0m-native` / `canonical` — so AC7's core ask (decided,
under a manifest, with reasons) is **met**. What T232 did NOT build: an estate-wide command that
enumerates this in one call (see AC6, still open) — you still invoke `--project` once per root by
hand.

## Definition of Done

`relock` and `relock-all` refuse a manifest-less root exactly as `check` already does — proven by
running both against a fresh empty directory and seeing them exit non-zero and write nothing, not
by reading the diff. One `just skill` command names every canonical skill installed in no known
root, proven by removing a skill's only installation and watching it appear in that command's next
run. One `just skill` command enumerates all 8 known roots (the 7 `.w0m/sdlc.json → repos` plus
the workspace root) and the shared user scope, tagging each one governed / ungoverned-with-skills /
symlinked / no-skills-directory — proven by deleting a root's manifest and watching its row flip.
None of the three is done because a report reads clean; each is done because a deliberately broken
fixture makes it fail loudly first.

## Out of scope

- **Installing the 11 skills.** AC3 requires each be *decided*, not that any be added — several are

- **The user-scope gap.** `skill check` already reports `~/.claude/skills` (12 skills) as
  NOT COVERED — that is [[T147]] AC4's, not this ticket's.

# T119 — w0m SDLC v2.1: make gate execution deterministic

## Summary

Five enhancements to the `w0m-sdlc-*` gate lifecycle, proposed by the parallel Antigravity agent
(report preserved at [`../../docs/design/w0m-sdlc-enhancements-2026-07-22.md`](../../docs/design/w0m-sdlc-enhancements-2026-07-22.md);
the original lived only in an ephemeral agent scratch directory). Goal: gates stop depending on
the agent guessing package-manager flags, sandbox permissions, or markdown formatting.

## The toolchain contract — two standard interfaces

The framing this ticket resolves to (owner, 2026-07-22): **w0m SDLC has exactly two standard
tools, and they are peers.**

| Concern | Standard tool | Host-level status | SDLC usage contract |
|---|---|---|---|
| **Commands** | `just` | ✅ already `required: true`, min `1.40.0` in `project/tools-policy.json` | ❌ missing — `.w0m/sdlc.json` holds raw `pnpm` strings (AC1) |
| **Secrets** | `infisical` | ✅ already `required: true`, min `0.40.0`, marked PROD-GATING | ❌ missing — nothing declares it; `.env` (86 keys) is still the de-facto source (AC2b) |

So neither tool needs adopting — `just tools-check` already enforces both are installed. What is
missing in both cases is the **contract that the gates use them**: no gate resolves a command
through `just`, and no gate obtains a secret through `infisical`. AC1 and AC2b are the same fix
applied to the two interfaces, and they should ship together rather than as unrelated items —
a repo that has one without the other is still not reproducible.

**Rule to encode:** every w0m repo provides a `justfile` (or a symlink to the canonical one) **and**
an `.infisical.json` (or an explicit declaration that it holds no secrets). A gate refuses to run
where either is absent, the same way it would refuse a missing test command.

## Why P0 — first-hand evidence for #5

Enhancement 5 is not theoretical. In the 2026-07-22 session, advancing T117 required hand-editing
`TASKS.md`, `project/tickets/T117.md` and `project/tickets.json` on every transition, and that
hand-editing **introduced a defect**: a `json.dumps` without `ensure_ascii=False` re-encoded every
non-ASCII character in `tickets.json`, turning a one-line change into a 47-line diff. It was caught
only because the diff was inspected. The same session also produced two convention drifts
(`wom7md:` vs `../wom7md/` reference styles) that had to be reconciled afterwards.

Anything a human or agent must retype identically across three files on every gate transition will
drift; that is the exact failure mode the SDLC exists to prevent, reproduced inside the SDLC's own
tracking surfaces.

## Acceptance criteria

- [x] **AC1** `.w0m/sdlc.json` `commands` resolve to `just` recipes; every w0m repo exposes the
      canonical set (`check`/`typecheck`, `lint`, `test`, `test-e2e`, `build`, `deploy`) or declares
      explicitly which it does not have
- [x] **AC2** a `commands.env` block exists for **non-secret** settings and the build/verify/deploy
      gates inject it, with telemetry/log/credential writes kept out of `$HOME` (no EPERM-driven
      escalation prompts)
- [x] **AC2b — `.env`-less environments via Infisical** (owner ask 2026-07-22). Gate commands
      obtain **secrets** by process injection, never from a file on disk:
      - `.w0m/sdlc.json` declares the provider and wrapper, e.g.
        `"secrets": {"provider": "infisical", "wrapper": "infisical run --env={env} --silent --",
        "default_env": "dev", "guard": "just check-infisical"}`
      - every gate composes `<wrapper> <command>`, and refuses to fall back to a `.env` file
      - `wom7web/.env` (**86 keys in plaintext**) and the three materialised `.dev.vars`
        (`apps/{web,cp,join}`) are eliminated, not merely gitignored
      - `set dotenv-load := true` is removed from the justfile, so a recipe needing no secrets is
        no longer handed all 86
      - repos lacking `.infisical.json` (`wom7cfworkers`, `wom7ext`, `wom7sec`, `wom7skills`) either
        gain one or declare themselves secret-free
- [x] **AC3** `w0m-sdlc-research`/`start` verify every path named in a ticket against the git tree,
      report drift in the Grounding Report, and propose the corrected path
- [x] **AC4** the OpenSpec naming brittleness is resolved — either the dated convention is
      supported end-to-end (all commands, not just positional) or the convention changes, decided
      and documented once
- [x] **AC5** a `gate-advance` tool performs the ticket-status + `TASKS.md` + status-note +
      conventional-commit transition atomically, and `tickets.json` is written by the same writer
      `sync_github.py` uses (`indent=2, ensure_ascii=False`) so hand-edits cannot re-encode it
- [x] **AC7 — toolchain conformance preflight** every w0m repo carries a `justfile` (or symlink)
      **and** an `.infisical.json` (or a declared secret-free marker); a preflight verifies both,
      plus the `tools-policy.json` floors for `just` and `infisical`, before any gate executes —
      one failure mode, one message, whichever interface is missing
- [x] **AC6** the gate skills are project-agnostic still — everything above reads from
      `.w0m/sdlc.json`, nothing hardcoded

## AC2b — grounded findings (2026-07-22)

Measured, not estimated:

- `wom7web/.env` contains **86 secret keys**; `wom7api/justfile:1` is `set dotenv-load := true`, so
  **every** `just` invocation loads all 86 into its environment. Only ~10 are referenced by any
  recipe (`ADMIN_EMAIL`, `CF_RUNTIME_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `DATABASE_URL`,
  `DEBUG_BYPASS_KEY`, `E2E_ACCESS_SECRET`, `E2E_BASE_URL`, `GEMINI_API_KEY`, `GITHUB_TOKEN`,
  `HCAPTCHA_SECRET`). The blast radius of that file is 8× what any recipe needs.
- `apps/{web,cp,join}/.dev.vars` are **written to disk** by `infisical export --format dotenv`
  (`justfile:188-189`). Infisical is already the source of truth — the export step is what
  re-materialises the secrets we are trying not to have.
- Only `wom7web` and `wom7api` carry `.infisical.json`; four repos have none.
- The plumbing already exists: `check-infisical` guards the session, and every
  `supabase functions deploy` recipe is already wrapped in `infisical run --env=dev --silent --`.
  AC2b generalises the wrapper the deploy path already proves works.

### ✅ AC2b feasibility PROVEN 2026-07-22 — infisical alone is sufficient

Run as a controlled experiment on `apps/web`, not reasoned about:

| Run | `.env` | `.dev.vars` | infisical | Result |
|---|---|---|---|---|
| 1 | hidden | **present** | yes | secret resolves — *confounded, .dev.vars was still there* |
| 2 (control) | hidden | **present** | **no** | secret still resolves → the source was `.dev.vars`, not infisical |
| 3 (control) | hidden | hidden | no | **app dies**: `PUBLIC_SUPABASE_URL is missing!`, `supabaseUrl is required` |
| 4 (decisive) | hidden | hidden | **yes** | **boots clean, secret resolves, 0 missing-var errors** |

**Conclusion:** `infisical run -- astro dev` fully replaces both files. **No application code change
is needed** — app code reads `import.meta.env` (260 uses) and Vite merges the process environment
into it, so process injection is transparent to the app.

**The caveat below is therefore resolved**: `wrangler dev` is not in the local-dev path at all.
The apps run `astro dev`, and `platformProxy` is **not enabled** in the Cloudflare adapter — so
`.dev.vars` is being read by the adapter in dev, and nothing else depends on it.

**Method note for whoever does AC2b:** run 1 looked like success and was worthless — `.dev.vars`
was still on disk supplying the secret. Only the control (run 2) exposed it. When testing that a
file is unnecessary, hide *every* candidate source and confirm the failure first; a passing test
with the old source still present proves nothing.

The two **`.env.bak`** files are the finding: stale secret backups nobody is maintaining, of exactly

**~~Known caveat~~ — RESOLVED 2026-07-22 by the experiment above.** The original concern was that
`wrangler dev` reads `.dev.vars`. It does — but `wrangler dev` is not how these apps run locally;
`astro dev` is, with `platformProxy` disabled. Run 4 proves the whole set can go.

**Security note:** this is not only ergonomics. 86 plaintext secrets sit in the working tree of a
repo whose history has needed credential purges before ([[wom-audit-2026-06]],
[[leaked-db-superuser-2026-07-12]]). Eliminating the file removes the artefact those incidents
depended on.

## Scope notes

- **Do not** implement #4 as a full offline template generator on spec-value grounds alone; AC4 is
  about the naming brittleness that actually bites. Revisit the generator if the CLI becomes a
  real availability risk.
- The canonical `justfile` already lives in `wom7api` and is symlinked into `wom7web` — AC1 is
  mostly about pointing the config at it and filling gaps, not building a new runner.
- Ordering: AC1+AC2 are quick config wins; **AC2b is the highest-security item** and should lead
  if anything does; AC5 is the highest-value for daily friction and the most work; AC3 needs care
  so auto-correction never silently rewrites a path the author meant.
- AC2b sequencing: wrapper + guard in config → prove `wrangler dev` without `.dev.vars` → drop
  `dotenv-load` → delete `.env`. Each step is independently revertible; the deletion is last.

## Correction — the archived Upwork keys were NOT "superseded"

Owner correction, twice, and both times my reading was wrong:

1. I first called all 4 archived keys *dead/superseded*. Wrong for the agency pair:

   `contextEnvPrefix()` resolves them and `upwork-poller` iterates `['freelancer','agency']` on

2. I then read `UPWORK_API_KEY`/`_SECRET` as the *client* credentials and proposed renaming them.
   Also wrong. They are the **freelancer** account's — exactly as the code already said.

**The truth, now documented in the code itself** (`_shared/upwork.ts` docblock + the poller
comment): there are **three Upwork accounts**, and we hold **one** key set.

| Context | Prefix | Status |
|---|---|---|
| freelancer | `UPWORK` | ✅ held — `UPWORK_API_KEY`/`_SECRET` + `UPWORK_ACCESS_TOKEN`/`_REFRESH_TOKEN` |
| agency | `UPWORK_AGENCY` | ⛔ not obtained |
| client | `UPWORK_CLIENT` | ⛔ not obtained |

No rename. The unprefixed names stay as the freelancer set — renaming them would have been a
migration across code, Infisical **and** Supabase edge-function secrets, to encode a mistake.

Deleting the May archive was still correct: those values were stale, never in the secret store, and
not the live credentials. The revocation note stands — if an Upwork app was ever registered for the
archived `UPWORK_CLIENT_*`/`UPWORK_AGENCY_*` pairs, it must be revoked at Upwork; deleting our copy
does not.

**Lesson for the next agent:** a missing env var name is not evidence the name is dead. Resolve it
through the code that reads it — here, a prefix builder two functions away from the literal — before
calling anything superseded.

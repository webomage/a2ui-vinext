# T499 — Highlights and tags live only in the database; the vault holds uploads and exports

## Summary

Split from [[T498]] (owner, 2026-09-29: "we should not use local .json file any more for users highlighted tags and store only resulting exported resumes as files in user's vault and also uploaded raw resumes for parsing/processing"; option (a) chosen: one-time seed, then remove).

T498 shipped `public.profile_cv_facts` and Studio reading it, loaded ONCE from `project/data/cv/highlight-tags.json` + `resume.json` by the owner-run `just cv-facts-load-live`. That file is a seed, not a product path: it is per-member data in the repo and a second source of truth next to the table.

## Target design

1. `profile_cv_facts` is the ONLY home of a member's highlights and approved tags. The member edits them in Studio (toggle tags, exclude a bullet, edit or add text) through a CP route that checks ownership, like `apps/cp/src/pages/api/profile/contracts/promote.ts`. No direct table writes from the browser.
2. A raw resume uploaded to the private `resumes` bucket is parsed into per-employer highlights (today `profile_resumes.parsed_data` is only `{type, title}`). Starting point: the `parse-resume` edge function. Proposed tags come from the shared keyword tables in `synthesis.ts`; the member approves in Studio.
3. "Save variant" writes the generated Markdown/PDF as a FILE in the member's vault (`<profile_id>/generated/...`) and the `profile_resumes` row points at it. Measured 2026-09-29: today it inserts a row naming `generated/resume-<role>.md` with no object behind it. Verify first, then fix.
4. Retire after the owner's live load: `project/data/cv/highlight-tags.json`, `project/scripts/cv-facts-propose.mts`, `packages/lib/src/resume/highlight-tags.ts(+spec)`, `wom7api/scripts/cv_facts_load.py` (+test, recipes `cv-facts-*`). `project/data/cv/resume.json` stays: it is the source of the PUBLIC CV (T165), not of Studio.

## Acceptance criteria

- [x] AC1 — Owner has run `just cv-facts-load-live` (T498 AC8) and Studio shows the curated bullets; only then is the seed removed. (Measured live 2026-09-29: 29 employers, 135 highlights, 125 tagged. The owner has not yet confirmed the Studio display.)
- [ ] AC2 — A member edits a highlight's tags, text and excluded flag in Studio; the change persists in `profile_cv_facts`; another member cannot read or change it. DECISION: no CP route. The write is the member's own RLS-checked UPDATE with a column grant on `highlights` only (migration `20260929220000`), so ownership is enforced by the database and the repo gains no new service-role client. BUILT and proven on scratch Postgres and in component tests; NOT live until the owner applies the migration and deploys CP.
- [ ] AC3 — Uploading a raw resume produces proposed highlights per employer from its text, shown for approval; nothing is written to the facts table until the member approves.
- [ ] AC4 (built; proven live only after a deploy) — "Save variant" stores a real file in the member's vault and the row's `storage_path` resolves to an existing object (test asserts the object exists).
- [ ] AC5 — The seed files, proposer, loader and their recipes are deleted; `git grep highlight-tags` finds only history; `just discovery` and the gates stay green.
- [ ] AC6 — An authz probe covers `profile_cv_facts` (own row visible, other member's not), closing the gap noted on T498 AC1.

## Status notes

- 2026-09-29 slice 1 (AC4): `Save Variant` now uploads the Markdown to `<profile_id>/generated/<ts>_resume-<role>[-public].md` FIRST and inserts the row second; a failed upload writes no row and a failed insert removes the object. Measured before: it inserted a row naming `generated/...` and uploaded nothing (0 such rows existed live, so no cutover). Live bucket policy checked: the first folder must be the member's profile id, which this path satisfies.
- 2026-09-29 slice 2 (AC2): Studio's Verified Facts tab edits highlights (tags, text, exclude). `excluded` is stored on the highlight and skipped by synthesis. Migration `20260929220000_t499_profile_cv_facts_member_edit.sql`: UPDATE policy on the member's own rows, `grant update (highlights)` only, a shape check (`cv_highlights_valid`: at most 200 items, text 1-2000 chars, at most 20 string tags, boolean `excluded`) and an `updated_at` trigger. Scratch-Postgres attacks all behaved: own row updates; another member's row updates 0; profile_id and company edits denied; insert and delete denied; six malformed shapes rejected.
- The one-time loader now refuses to run when rows exist (`--force-overwrite` to discard member edits), so nobody re-seeds over a member's edits.
- Known limits: last write wins per employer (two tabs); a member cannot add or delete an employer or add a bullet yet; the tags offered are the 11 role/tech ids from `synthesis.ts`.
- Not started: AC3 (parse a raw upload into proposed highlights), AC5 (delete the seed, proposer, loader), AC6 (authz probe for the table).

## Definition of Done

- A second member can upload their own resume and end up with tagged, editable highlights without any file in the repo being touched.
- The repo contains no per-member highlight or tag data after the change.
- A saved variant can be downloaded from the vault as a file.

## Open questions (recommended answers)

1. Parsing engine: rule-based on headings and bullets, or an LLM call? Recommend rule-based first (deterministic, no client text leaving the estate), LLM as a later opt-in. Weight: low cost, low risk, unblocks AC3 fastest.
2. Editing UI: inline in the Facts tab. Recommend yes, no new page. Weight: lowest cost.

# T194 — a `DROP TABLE` leaves its callers behind, and nothing notices

## Summary

[[D35]] filed the GDPR-erasure breakage on 2026-08-07 and named the real gap in one clause:

> *"Found by the AC-truth pass, not by any gate: **nothing checks that a dropped table has no
> remaining callers.**"*

That sentence was the finding, and it was left as prose. Three days later the same gap produced
**five more live callers nobody had counted** — found on 2026-08-10 by a single grep, not by a
gate. This ticket builds the gate.

## 📍 Measured 2026-08-10

`public.linkedin_tokens` was dropped by
`wom7api/supabase/migrations/20260721120000_t99_protect_oauth_tokens.sql:63` under [[T99]].
Callers still addressing it:

| Caller | What it does | Live? |
|---|---|---|
| `apps/web/src/pages/api/auth/linkedin-callback.ts:134` | **upserts** on every LinkedIn login | `prerender = false`, `GET` |
| `apps/cp/src/pages/api/auth/linkedin-callback.ts:131` | **upserts** on every LinkedIn login | `prerender = false`, `GET` |
| `apps/web/src/pages/api/auth/linkedin-refresh.ts:44,102` | reads + rewrites the token row | `prerender = false`, `POST` |
| `apps/cp/src/pages/api/auth/linkedin-refresh.ts:44,102` | reads + rewrites the token row | `prerender = false`, `POST` |
| `wom7api/src/workflows/linkedin-data-erasure.ts:27` | deletes, then **throws** | deployed Worker ([[D35]]) |

🔑 **The one everybody looked at was the least consequential.** D35 is about the *erasure* path —
which deletes from a table that was **empty when it was dropped** (the T99 migration refused to
drop a non-empty one). The *token-persistence* path is the one doing real work against a table
that does not exist.

⚠️ **Why no existing gate sees this.** `db-drift-check` compares migration **files** against the
**ledger** — both sides agree here, because the drop was properly migrated. `wom_ddl_guard` gates
DDL at the database. Neither looks at **application code**. The drop was done correctly and the
callers were still orphaned; correctness on both existing axes is compatible with this bug.

## 🔗 2026-08-13 — `just callsite-drift` already does AC2, and finds what AC1 cannot

[[T69]] AC5 shipped **`just callsite-drift`** (`project/scripts/call_site_schema_drift.py`), which
scans **492** literal `.from('<relation>')` call sites across exactly the four roots AC2 names and
resolves each against the **live catalog**. On today's tree it reports all six callers above as
**GHOST**, so **AC3's red probe already exists and has been observed failing** — pre-fix output
saved at `project/authz-probe/T69-callsite-redprobe-2026-08-13.md`.

🔑 **But the two gates are not the same gate, and the difference matters for AC1.** This ticket
derives its worklist from `DROP` statements in the migrations; `callsite-drift` derives it from the
live catalog. That makes each blind where the other sees:

| | drop-derived (this ticket) | catalog-derived (`callsite-drift`) |
|---|---|---|
| relation dropped by a migration | ✅ finds it | ✅ finds it |
| relation **never created at all** | 🔴 blind — no `DROP` to extract | ✅ finds it ([[T208]]: `user_profiles`) |
| relation dropped **outside** a migration | 🔴 blind | ✅ finds it |
| relation live but **ungranted** | 🔴 blind | ✅ `UNREACHABLE` (50 sites on 2026-08-13) |
| relation dropped, recreated later in history | ✅ *if* AC2's end-state check is written | ✅ inherently — it reads the end state |

⇒ **AC2 can be satisfied by reusing `callsite-drift` rather than writing a second scanner**, and
AC1's migration parsing is then the *addition* — it buys the "which migration dropped it, and
when" attribution that a catalog diff cannot give you. ⚠️ It also inherits the two false-alarm
shapes `callsite-drift` already has probes for: `supabase.storage.from('<bucket>')` is not a table,
and a hoisted `const g = supabase.schema(…)` handle is not an unqualified call.

## 🔬 AC5 investigated 2026-08-13 — the premise needs revising

**There are TWO parallel LinkedIn OAuth implementations, serving two different journeys.** Only one
of them is broken, and the broken one's DB write has no reader.

| | writes | used by | state |
|---|---|---|---|
| **edge fns** `linkedin-oauth` / `-ingest` / `-share` + worker `linkedin-sync` | `social_integrations` | `ConnectionsManager.svelte` — the **admin connections** panel | ✅ working (1 row) |
| **Astro routes** `api/auth/linkedin-{callback,refresh}` (web + cp) | `linkedin_tokens` | `ApplicationForm.svelte` — the **candidate application prefill** flow | 🔴 dropped table |

🔑 **The prefill journey does not touch the database at all.** `api/auth/linkedin-prefill` reads the
**`li_access_token` HttpOnly cookie** that the callback sets. So the callback's `linkedin_tokens`
upsert is a *side-write*, and the flow users actually run has been working the whole time.

🔑 **And `linkedin-refresh` has ZERO callers** — nothing in `apps/**`, `packages/**`, `wom7api/**`
references it. So the only consumer of that dead write is an endpoint nobody invokes.

⇒ **The fix is DELETE, not re-point — and that dissolves this AC's own blocker.** AC5 warns that
moving the callbacks to `social_integrations` without D1's encryption *"moves the problem rather
than solving it"*. It is worse than that: today candidate tokens are stored **nowhere** (cookie
only), so re-pointing would **newly** persist them as plaintext at rest — a real increase in
exposure, introduced by "fixing" a bug. Deleting six dead sites costs nothing and adds nothing.

🔻 **D1 needs re-reading too.** It says the encrypted shape *"needs key management + changes in 3
edge fns"*. The **columns already exist** — `access_token_ciphertext`, `access_token_iv`,
`refresh_token_ciphertext`, `refresh_token_iv`, `token_key_version` — and are **entirely unused**
(`plaintext_access=true, ciphertext=false, keyver=null` on the single live row). The schema half is
done; only the writers were never changed.

### 🔴 The erasure workflow is a separate and worse defect than [[D35]] recorded

`wom7api/src/workflows/linkedin-data-erasure.ts` does **not** silently succeed — it `throw`s
(`if (tokenError) { …; throw tokenError; }`). The consequence is worse:

1. step 1 deletes from `linkedin_tokens` → **the relation does not exist → throws**
2. step 2 scrubs `job_applications` PII (`linkedin_sub`, `linkedin_picture`) → **never reached**
3. step 3 unlinks `user_profiles` → never reached, and that relation does not exist either

⇒ **No erasure request has ever completed**, and the real PII in `job_applications` has never been
scrubbed. It also never touches **`social_integrations`**, which holds `access_token`,
`refresh_token`, `provider_urn` and `profile_data` — i.e. the erasure path does not cover the one
table that actually stores the subject's LinkedIn data. Shared with [[T208]] AC3.

### 🔴 OWNER DECISION 2026-08-13: re-point, not delete — and it is BLOCKED as specified

Owner chose **re-point everything to `social_integrations`** over deleting the dead surface, and
**investigate-only** for the erasure path. Recorded because it overrides the recommendation above.

**Consequence accepted by that choice:** candidate OAuth tokens begin persisting **plaintext at
rest**, where today they exist only in an HttpOnly cookie. That is a new exposure created by fixing
the bug, not an existing one being moved. Reflected on [[D1]].

🔴 **But the re-point cannot be implemented as specified.** Measured:

| fact | consequence |
|---|---|
| `social_integrations.user_id` is **NOT NULL**, FK → `auth.users(id)` | a row requires a Supabase user |
| unique key is `(user_id, provider, provider_urn)` | `user_id` is **part of the identity**, not metadata |
| the callback has **no user in scope** — no `auth.getUser`, no session; it builds a service-role client and upserts keyed on `linkedin_sub` | there is no value to put in `user_id` |

The candidate prefill flow authenticates someone against **LinkedIn**, not against Supabase. Both
the web and cp callbacks are the same shape. So the target table cannot hold the row without one of:

- **(a) a migration** making `user_id` nullable + a partial unique on `(provider, provider_urn)` for
  user-less rows. ⚠️ This changes the table's meaning from *"an account a USER has connected"* to
  *"any provider identity we have observed"*, and every existing consumer
  (`linkedin-oauth`, `-ingest`, `-share`, `linkedin-sync`, `ConnectionsManager`) reads it under the
  first meaning. RLS is `user_id = auth.uid()`, which no longer selects anything for those rows.
- **(b) create a Supabase auth user for every candidate** who clicks *sign in with LinkedIn* to
  prefill an application — a product change, and it turns an anonymous convenience into an account.
- **(c) a new table** for anonymous candidate tokens — which is `linkedin_tokens` under another
  name, i.e. re-creating what [[T99]] deliberately dropped.

⇒ **Left undone pending that decision.** Everything else in this ticket is finished.

### AC5b — the erasure investigation (owner chose investigate-only, no behaviour change)

**What erasure must cover, measured against the live schema:**

| store | holds | erasure today |
|---|---|---|
| `public.social_integrations` | `access_token`, `refresh_token`, `provider_urn`, `profile_data` | 🔴 **never touched** |
| `public.job_applications` | `linkedin_sub`, `linkedin_picture`, `linkedin_url` | 🔴 never reached (step 2, after the throw) |
| `linkedin_tokens` | — | dropped; step 1 targets it and throws |
| `user_profiles` | — | exists in no schema; step 3, never reached |

⚠️ **`job_applications.linkedin_url` is not in the erasure list at all** — steps 2 nulls
`linkedin_sub` and `linkedin_picture` only. So even a fixed step 2 would leave a profile URL behind.

**The policy question this needs answered before code encodes it:** erasure currently *anonymises*
`job_applications` (nulls the LinkedIn columns, keeps the application) and *deletes* tokens. Whether
`profile_data` in `social_integrations` should be deleted or anonymised, and whether the application
record itself survives, is a retention decision — not one a gate or an agent should make. That is
why this stayed investigate-only.

### Recommended split

- **AC5a — delete the dead surface** (6 sites, 4 files): the `linkedin_tokens` upsert in both
  callbacks, and both `linkedin-refresh` routes entirely. ⚠️ Deletes two shipped API endpoints —
  unreferenced, but owner's call.
- **AC5b — make erasure real** (1 site): target `social_integrations` + `job_applications`, drop the
  `user_profiles` step or re-point it per [[T208]] AC1, and fail per-step rather than aborting the
  whole run. Needs a Worker deploy.

### 🟢 OWNER DECISION 2026-08-14: key social integrations to the PERSON, not the account

Owner: *"re-attach social integrations to profile and detach it from user itself."* This is a
**fourth option**, and it dissolves the (a)/(b)/(c) trilemma above rather than picking from it —
each of those tried to make an *account-shaped* table hold an *accountless* identity. The right
fix is that a connected social identity was never a property of an account.

**Measured against the live schema 2026-08-14 — the re-point validates today, with no data work:**

| fact | consequence |
|---|---|
| `profiles` PK is `id`, with `FOREIGN KEY (id) REFERENCES auth.users(id) ON DELETE CASCADE` | every profile id **is** an auth id today |
| `social_integrations.user_id` → `auth.users(id)`, 1 row | that row's `user_id` already exists in `profiles` |
| `social_integrations` rows with no matching profile | **0** |
| `auth.users` with no profile | **0** |
| `profiles.auth_user_id` | **does not exist yet** — [[T210]] is unbuilt |

⇒ **Re-pointing the FK to `profiles(id)` is currently a NO-OP at the data level** (identical
UUIDs, zero orphans) and becomes meaningful the moment T210 gives `profiles` its own identity with
a nullable `auth_user_id`. So this is not a second competing migration — **it is the change that
makes T210's detachment pay off**, and it belongs in T210's sequence rather than ahead of it.

⚠️ **Three things this decision commits us to, none of them free:**

1. **The column is renamed `user_id` → `profile_id`.** Leaving the name would be the T138 lesson
   again: a name asserting a relationship the schema no longer has. **~12 query sites across 5
   files** — `linkedin-sync.ts` (2), `linkedin-oauth` (1), `linkedin-ingest` (5), `linkedin-share`
   (2), `ConnectionsManager.svelte` (2) — plus `packages/lib/src/system-registry/sources.ts`, which
   only names the table.
2. 🔴 **All four RLS policies must be rewritten.** They read `auth.uid() = user_id`, which works
   only while the two ids are the same value. After T210 they become
   `profile_id = (SELECT id FROM profiles WHERE auth_user_id = auth.uid())`.
   **And a row for an accountless person will match NO policy** — correct (only service-role
   should reach it), but it must be stated, because "no policy matches" and "the table is
   ungranted" look identical from the client and [[T69]] is exactly that confusion.
3. **The unique key becomes `(profile_id, provider, provider_urn)`** — same shape, new referent.

⇒ **AC5 is UNBLOCKED as a decision and now SEQUENCED behind [[T210]] Phase 1.** The six
`linkedin_tokens` callers re-point to `social_integrations` keyed by profile, and the candidate
prefill flow finally has something to attach to: a person who has no account.
⚠️ The plaintext-at-rest consequence recorded above **still applies** and is unchanged by this
decision — candidate tokens move from "stored nowhere (cookie only)" to "stored plaintext". [[D1]]
already carries the encrypted-column shape, and its columns exist and are unused.
### 2026-08-16 — 🔴 blocked on an owner decision, not on work

Picked up the last AC and found the **agreed fix is not implementable as written**. The decision
above says candidate tokens get re-pointed into `social_integrations`. Measured against the live
schema, they cannot be:

- **`social_integrations.user_id` is `NOT NULL`** and part of the table's unique key.
- The candidate OAuth callback **has no Supabase user in scope** — that is the entire point of the
  flow: the person has no account yet.

So every write from that path would violate the constraint. This is not a coding problem to push
through; it needs a choice, and each option has a different cost:

| | Option | Cost |
|---|---|---|
| **a** | Migration making `user_id` nullable + a candidate discriminator | Weakens an invariant every existing consumer relies on |
| **b** | Mint an auth user per candidate | Creates real accounts for people who never signed up |
| **c** | A separate candidate-token table | No constraint change, but a second place tokens live |
| **d** | Revert to deleting the tokens | Loses the prefill feature the decision was made for |

⚠️ The plaintext-at-rest consequence recorded above applies to **a**, **b** and **c** equally.

**Nothing further should be built on this ticket until (a–d) is chosen** — writing one of them
speculatively means writing a migration against a live table on a guess.

## ✅ AC5 DONE 2026-08-17 — and the premise revision was right: deletion, not migration

`just drop-callers` → **0 orphaned callers across 13 dropped relations**. `linkedin_tokens` now
appears in the *fully cleaned up* list. The gate is **PROMOTED TO BLOCKING** in `.husky/pre-push`,
which is what AC5's trigger asked for.

🔴 **The severity was understated, and this is the finding of the ticket.** The gate reported **7**
sites, not six. Six were dead — but the seventh,
`wom7api/src/workflows/linkedin-data-erasure.ts:27`, did `throw tokenError` on a delete against the
dropped table. **PostgREST answers a missing table with HTTP 404 / `PGRST205`**, supabase-js makes
that a truthy error, so **every erasure request aborted at step 1** and steps 2–3 — the ones that
actually anonymise `job_applications` PII and unlink `user_profiles` — had not run since the table
was dropped on 2026-07-21. ⇒ **The GDPR erasure path erased nothing for three weeks**, failing
loudly into a log nobody read. Verified live before removing: `DELETE /rest/v1/linkedin_tokens`
returns `PGRST205` 404 while a control `GET /rest/v1/job_applications` returns 200.

**What changed:** two dead `linkedin-refresh` routes deleted (web + cp — zero callers, only a Gauge
scenario referenced them) · the side-write upsert removed from both callbacks (non-fatal, but it
logged a guaranteed error on every LinkedIn sign-in) · the erasure workflow's step 1 removed, with
`tokenCount` dropped from the result rather than reported as `0` — a caller reading `0` cannot tell
*"there were none"* from *"we no longer look"* · the Gauge scenario retired with its reason recorded.
**Nothing was re-pointed at `social_integrations`**, so [[D1]] is untouched and was never the blocker.

🔑 **The gate's own suite caught the fix and had to be repaired first.** Its probe *"--enforce exits
non-zero while the live tree still has orphans"* built a fixture and then **discarded it**, running
against the real repo — so it was green only because the estate was broken, and it went RED the
moment AC5 cleaned up. Rewritten onto a fixture, plus the converse case (a clean fixture must exit
**0**) which the old form could never have caught, since a gate hardwired to `exit 1` would have
passed it. **17 probes green.** *A probe whose green depends on a defect existing dies the day the
defect is fixed — and takes the suite down while someone is proving the fix.*

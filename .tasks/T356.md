# T356 — Multi-tenant org scoping for the staffing/delivery model

## Summary

Owner ask: *"I think we should also make not only w0m as agency converted to client/org entity in
w0m ecosystem but also move and attach staff and projects into the org scope so other orgs on
specific level of subscription/access level should get same/similar possibilities as an agency or
an indie dev or client with own stuff involved in projects"*, followed by *"and the w0m eco system
is the project by Aleksei as Client and Contractor all hats for now"*.

Confirmed by grep across `wom7api/supabase/migrations/` (2026-09-13): **no `org_id` column exists
anywhere in the schema.** `public.projects`, `public.hats`, `public.project_roles`,
`gamification.units`, `gamification.adventures` are all implicitly scoped to one tenant — w0m
itself — with no column that could ever say otherwise. `public.clients` and `public.client_users`
give a *client* org a scoped read of its own CRM data (T198 A2/E4), but nothing lets a client, an
indie dev, or a second agency **own staff, units, or projects** the way w0m does today. w0m's
special status is structural, not a row — there is no tenant table for it to be a row *in*.

This is a **different gap** from two adjacent, already-designed pieces of work, and this ticket
must not duplicate either:
- **[[T354]]** (`actor_manifest` / `org_trust_edges`, 2026-09-13) designs the *capability and
  authorization* axis between already-distinct actors — it generalizes `owner_kind` to
  `IN ('profile', 'client', 'org')` for a capability catalog, and explicitly is **not** schema for
  the delivery data itself. This ticket's `org_id` FK should point at whatever row structure T354
  lands for the `'org'` owner_kind — not invent a second, competing `orgs` table.
- **ROADMAP §33 "Client Alfa — Full Feature Support, Staged"** (P0, 2026-08-17) is RLS-based
  **cross-tenant-read isolation** between w0m's existing single-tenant clients (T198's 9 live
  authorization defects) — it stops one client reading another client's rows *within today's
  single-tenant schema*. This ticket is about making the schema itself multi-tenant so a
  **non-w0m org** can run its own instance of the staffing/project model, which §33 does not
  attempt and does not need to for its own scope.

## Definition of Done

Every AC above is a **written design section** (openspec change, once this ticket reaches
`w0m-sdlc-spec`), not a shipped migration — no `org_id` column, no `actor_manifest` row, and no
tier-gating logic ships under `wom7api/supabase/migrations/` from this ticket alone.
`blocked_by: [T117, T354]` is honored: no migration implementing `org_id` scoping may land before
T117 AC5 (rank CHECK consistency) and T354's `actor_manifest` (the FK target for `org_id`) both
exist. `docs/backend/RBAC-PROJECT-ROLES-PIVOT.md` carries the new section, and every AC maps to
≥1 design-section paragraph and vice versa.

# T510 — Resume vault: every resume private, one switch decides what is public

## Summary

Owner direction, 2026-09-30: *"make all resumes for Aleksei private and stored in the same members vault as others, keep
public only default, and we should have an option in profile like 'Public resume on/off' per profile."*

Today the vault (private `resumes` bucket, `<profile_id>/<file>`) holds 17 of Aleksei's documents ([[T488]]), but a
**declared public set still lives outside it** as static files under `apps/cp/public/cv` and `apps/web/public/cv`, and
one older CV is still served from the public `cv` bucket. This ticket finishes the move and replaces "a hand-picked set of
static files" with "one switch per profile".

Owner addition, 2026-09-30: the point of "Public resume" is that **when it is on, the profile card on the team page shows
a link to the PDF version**. A second checkbox, **"Show LinkedIn"**, controls whether the card displays the member's
LinkedIn link.

## Two words that must not be confused

| Term | Meaning | Where it lives |
|---|---|---|
| **Variant** (Private / Public, Full / Compact) | How a resume is *rendered* in Resume Studio: Public masks phone and street address ([[T505]]). | Resume Studio output |
| **Published** (this ticket) | Whether anyone without an account can *fetch* a profile's resume at all. | New per-profile switch |

A "Public"-variant document is not published until the switch is on, and a published document is not automatically
masked. The UI and schema use `variant` and `published` and never bare "public" for both.

## How the team card gets its data (measured 2026-09-30)

- The card is **not** driven by `profiles`. `TeamPage.astro` (both `apps/web` and `apps/cp`) reads `units` with
  `public_team_members (*)` (T470), a `security_barrier` view over `public.team_members`. `team_members` is a separate
  table (name, bio, photo_url, linkedin_url, skills, status, unit_id, email, resume_url, and a nullable `user_id` added
  by `20260720170000`).
- The view exposes `linkedin_url` **unconditionally** today, so LinkedIn is already public on every active or alumni
  card with no switch. It deliberately **omits `email` and `resume_url`**: a public `team_members` read once exposed
  staff emails ([[T198]]).
- `profile_contact` ([[T505]]) also stores a LinkedIn link, owner-only. So a member's LinkedIn URL has two homes.
- Other renderers of the same roster to cover: `apps/cp/src/components/templates/sections/TeamSection.astro`,
  `apps/cp/src/pages/o/[org]/people/team.astro` and the `team-mapping` test in `apps/web`.

## Design (assumptions marked, see Open questions)

1. **Schema.** `profiles.resume_published boolean not null default false`. Owner and managers may change it; anon and
   other members cannot read or write it through the API. One flag per profile, one resume per profile can be
   published: the row with `is_primary = true`.
2. **Serving.** *(Assumption, Q2.)* A small edge route resolves a stable URL to the profile's primary resume, checks the
   flag with the service role, and streams the object from the private vault. Flag off returns **404** (not 403), so a
   switched-off resume cannot be told apart from one that never existed. No public copy of the file exists at any time,
   so turning the switch off is instant and complete.
3. **Team card.** Both switches live on `profiles` (one place per fact; "per profile"). `public_team_members` is extended to
   join `team_members.user_id` to the profile and return two derived columns only: `resume_link` (a path, not a storage
   path, and `NULL` unless the profile has `resume_published` and a primary resume) and `linkedin_url` (`NULL` unless
   `show_linkedin_on_card`). The card renders a "Resume (PDF)" link and a LinkedIn link only when the column is not
   null. The view still omits `email` and the raw `resume_url`; a regression probe pins that. A card whose member has no
   linked profile shows neither.
4. **UI.** A "Public resume" switch in profile settings, off by default, showing the public link while on, with a
   confirm step that says which document will be public.
5. **Retire the static set.** Remove the static PDFs and repoint the pages that link them to the published URL.

## Acceptance criteria

- [ ] AC1 — **The vault holds every Aleksei resume.** No `profile_resumes` row has a `cv/` path except the whitepaper

  query (rows by prefix) and a bucket listing whose object count equals the row count.
- [ ] AC1b — **Every local resume file is imported, byte-for-byte.** Each md/pdf in the table above marked "import"
  has a vault object whose SHA-256 equals the local file's, and a `profile_resumes` row. Verified by a read-only
  comparison script that prints one line per file (✅/❌) and exits 1 on any mismatch or missing file, so a file
  cannot be archived on a claim.
- [ ] AC2 — **The second public CV is in the vault and gone from the public bucket.** `Aleksei-Tcelishchev-CV.pdf` is
  copied into `wom7web/private/resumes/`, given a row, uploaded, then unpublished by `resumes_upload.py --unpublish` with
  the backup under `~/.w0m/backups/resumes-unpublished/`. Owner-run (`just resumes-upload-live` is behind the Touch ID
  gate; the recipe currently names only `Aleksei_CV_2025.pdf` and must name this file too). Verified by anon
  `GET /storage/v1/object/public/cv/Aleksei-Tcelishchev-CV.pdf` not returning 200.
- [ ] AC3 — **Migration adds `profiles.resume_published`, default false.** Probe asserts every existing profile is

- [ ] AC4 — **Publishing works and fails closed.** With the flag on, the stable URL returns the primary resume's bytes;
  with it off, or with no primary resume, or for an unknown profile, it returns 404 with an identical body. No public
  bucket object exists for any vault file. Verified by a Gauge/e2e spec against the local stack with the live guard on.
- [ ] AC5 — **Profile settings has the switch.** Off by default, link shown while on, confirm names the document.

- [ ] AC5b — **Local copies are archived only after AC1b is green.** The archive step refuses to run unless the AC1b

- [ ] AC5c — **One-time tooling retired in the same commit.** `resumes_upload.py`, its three recipes, its suite row,
  `upload-cv.mjs` and the `upload-cv` recipe (and its callers `supabase-redeploy-all` / `check-supabase`) are removed or
  repointed; no recipe or script names a path that no longer exists (the stale-path probe from [[T509]] is the check).
- [ ] AC4b — **The team card shows the PDF link only when published.** With `resume_published` on, the card in both

- [ ] AC4c — **"Show LinkedIn" is a checkbox that gates the card.** New `profiles.show_linkedin_on_card boolean`; the

- [ ] AC4d — **The view stays safe.** A probe asserts `public_team_members` still has no `email` and no `resume_url`

## Open questions (recommended answer first, with weight)

1. **Whitepaper.** `Webomage_Whitepaper_Cloud_AI.{pdf,md}` is a company document, not a resume. *Recommend it stays public
   as a static file.* Weight: low risk, keeps two public pages working; moving it into a person's vault would tie a
   company asset to one profile.
2. **How is a published resume served?** *Recommend an edge route that streams from the private vault while the flag is
   on* (no public copy, instant revoke). Alternative: copy the file into a public bucket while on. Weight: the copy is
   simpler to build but leaves a stale public file if the flag flips or the copy step fails.
3. **Which resume is the public one?** *Recommend the primary (default) resume only, as "keep public only default"
   reads.* Alternative: let the member mark any row. Weight: one flag and one file is far harder to misconfigure.
4. **Default for new profiles.** *Recommend off.* Weight: every other choice publishes personal data without a decision.
5. **Publishing a document that still shows phone and address.** The stored file is served as-is; the Public *variant*
   is how a masked document is produced ([[T505]]). *Recommend a confirm step now, and a follow-up ticket to store the
   variant on the row so the switch can refuse an unmasked document.* Weight: privacy risk is real, but the follow-up
   changes the Resume Studio data model and deserves its own decision.

6. **`.cv-gallery/` (generated style samples).** *Recommend leaving it alone:* gitignored, regenerated by `cv_gallery.py`,
   not a source of truth. Weight: archiving regenerable output only adds a step. Say so if you want it gone.
7. **Personal CVs are already in git history.** 18 files under `private/resumes/` (and the static public set) are tracked,
   so `git rm` hides them from the tree, not from history on the remote. *Recommend deciding explicitly whether a history
   rewrite is wanted; it is outward-facing and owner-only, so this ticket does not do it.* Weight: high privacy
   relevance, high blast radius (rewrites shared history for every clone and agent).
8. **Default for "Show LinkedIn".** Cards show LinkedIn today with no switch. *Recommend default ON for existing members so
   nothing changes silently, and OFF for new profiles.* Weight: defaulting existing members to OFF removes the founders'
   LinkedIn from the live team page the moment this ships; defaulting new ones to ON publishes a link nobody chose.
9. **Which LinkedIn URL is canonical?** `team_members.linkedin_url` and the owner-only `profile_contact` link both hold
   one. *Recommend this ticket gates the existing `team_members.linkedin_url` only, and a follow-up ticket makes the
   profile contact link the single source and drops the duplicate.* Weight: merging them here changes the team-manager
   admin flow and the T505 contact model, which is a separate decision; leaving the duplicate is a known, bounded debt.
10. **Link target and label.** *Recommend a "Resume (PDF)" link that opens the published URL in a new tab.* Weight: low.

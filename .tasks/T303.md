# T303 — a build that destroys a running VM must say so before it does it

## Why

Hit, not predicted, on 2026-09-02 while rebuilding the BridgeRoad image to pick up the container-DNS
fix. `build.py --push …` was run while `w0m-bridgeroad` was **up and serving the client's stack**.
Packer stopped and replaced that VM without a word, the build reported success, and nothing in its
output suggested anything had been destroyed.

The cause is a name collision that looks deliberate and is not: `vm_name` in the Packer template
defaults to `w0m-bridgeroad`, and `build.py --name` defaults to the same. So the artefact being
produced and the box being worked in are the same object. There is no `force` or `overwrite` setting
anywhere in the template — `packer-plugin-tart` simply replaces a VM of that name.

**Why it read as harmless:** the outcome happened to be fine. The replacement *was* the corrected
image, so `up` worked afterwards. The loss only surfaced indirectly — the docker build cache was
empty and the guest IP moved `.44` → `.45`. Had the VM held anything not reproducible from the
template — a half-finished debug session, an un-pushed container, a database with local state — it
would have gone with no prompt, no warning, and an exit code of 0.

This is the destructive-action failure mode rather than the usual vacuous-gate one: the tool did
exactly what it was asked, and the harm came from the request being ambiguous about which object it
named.

## Acceptance criteria

- [x] **AC1** — `build.py` refuses to build when a VM of the target name is **running**, naming the
      three ways forward (stop it, use another `--name`, or pass `--replace-running` deliberately).
      Exits non-zero, and refuses **before** Packer starts so nothing is touched.
- [x] **AC2** — red-tested against the real hazard rather than a mock: run with `w0m-bridgeroad`
      actually running and serving, observed refusing with exit 1; `vm_state()` verified to return
      `running` / `stopped` / `None` across the three cases, because the `Accessed` column contains
      spaces and cannot be indexed from the front.
- [x] **AC3** — the replace-a-**stopped**-VM path exercised end to end against a throwaway VM
      (`w0m-bridgeroad-ac3`, cloned from the base so the working box was never at risk). Observed
      `⚠ w0m-bridgeroad-ac3 exists and will be REPLACED by this build` followed by
      `▶ packer build …`, and the full run completed exit 0 ending on
      `VERIFIED: Ubuntu 26.04 / Docker 29.7.2 / agent up` — the last line of the gate block, so the
      new DNS and build-network gates both ran and passed. Throwaway deleted afterwards.
      ⚠️ First attempt looked like the warning never printed; it had been cut by a `| tail -30`,
      because the warning is emitted early. The pipe, not the guard, was the defect.
- [x] **AC4** — every destructive path in the estate audited; two were live hazards and are fixed.

      | path | verdict |
      |---|---|
      | `retention.py` → `tart prune --older-than=14` | **safe** — `tart prune` defaults to `--entries caches`; deleting local VMs needs an explicit `--entries vms`, which nothing passes. Evercred was never at risk. |
      | `provision.py: create_vm` | **was unguarded** — `tart stop` + `tart delete` on any existing name. Now refuses a *running* target and reports what it deletes. |
      | `provision.py` existence test | **was wrong** — `if name in tart_list_stdout`, a substring match. Measured: `"bridgeroad"` reported as existing while **no VM of that exact name existed**; `"evercred"` likewise matched. Replaced with exact Name-column matching. |
      | `build.py: push()` | **was unguarded** — `tart push` overwrites an existing tag silently, and consumers `tart clone` by full ref, so one name would answer to two different images. Now refuses a ref already in `published.json`. |
      | `evercred` shell alias | **safe** — `tart run` only, no destructive verb. |

      The push guard is checked **before** the build, not at push time: the push happens ~9 minutes
      in, so checking there would only report the collision after the work was already spent.
- [x] **AC5** — the collision is **removed**, not documented around. `image-policy.json -> vm` now
      carries two strings: `name` (`w0m-bridgeroad`, the VM you work in) and `build_name`
      (`w0m-bridgeroad-build`, the transient artefact Packer produces and `tart push` publishes).
      `build.py --name` defaults from policy instead of a literal, and the Packer template's own
      `vm_name` default was changed too — it only applies when someone runs `packer` directly, which
      is exactly when a wrong default does the damage.

      The second half is what makes the split worth more than safety: `vm.py pull` creates the
      working VM as a `tart clone` of the **published** image, so we work in the artefact by the same
      path a consumer takes. 🔑 That is not hypothetical — the image published the morning of
      2026-09-02 could not build anything, and using it is what would have surfaced that at the first
      `up` rather than hours later.

      Verified end to end on the real published ref: `pull` refuses while the target runs (exit 1),
      refuses to discard an existing VM without `--replace` (exit 1), then
      `pull --replace` → `start` → `up` gave **HTTP 200** — the client's stack running on a VM cloned
      from `ghcr.io/casualuser/w0m-bridgeroad:2026.09.02-1788373232`. The README's
      `tart clone … bridgeroad` instructions were also wrong in a quieter way: they produced a VM
      named `bridgeroad`, which `vm.py` cannot see at all.

## Definition of Done

No w0m tool destroys a VM someone may be using without saying so first and requiring an explicit
choice, and the refusal has been watched happening against a genuinely running box rather than a
simulated one. Where destruction is the intent, it is expressible in one obvious flag, and where it
is a side effect of a name defaulting to the same value in two places, that collision is either
removed or written down at both ends. A build that replaces something reports what it replaced, so
an exit code of 0 never again coincides with an unannounced loss. Tools with more to lose than a
reproducible image — Evercred's VM, a published tag — are covered by the same rule rather than left
to the fact that nobody has rebuilt them lately.

## Notes, traps and dependencies

**AC4's limitation, stated rather than buried:** `tag_already_published()` reads the local
`published.json`. A tag pushed from another machine, or by hand, is invisible to it. It covers the
realistic case — re-running a build with a ref already used, which is how the `never_delete` tag
`2026-09-01` would have been overwritten — and a registry-side check is the honest completion.

The guard deliberately blocks only on **running**. Blocking on mere existence would fire on every
ordinary rebuild and be disabled within a week, which is the failure mode where a guard becomes
noise and then gets removed. Related: [[T295]] (image build/publish), [[T302]] (client-project checks
belong in the client's own workspace — this guard lives in `bridgeroad-w0m` for the same reason).

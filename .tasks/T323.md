# T323 — Bootstrap wom7ava — consented-identity virtual avatars for video conferencing

## Summary

New w0m subproject: lets a user appear on a video call wearing a visual "skin" — a synthetic or
consented-identity avatar — instead of their live camera feed, with matching voice. Sibling to
wom7clips ([[T322]]), both bootstrapped from architecture/research already done for personaje0
(`/Users/proto/Projects/_self/personaje0`), verified present in that codebase before this ticket
was written.

Reused close to as-is (an avatar "skin" is much closer to personaje0's persona/passport concept
than to wom7clips' Brand Kit adaptation): the provider-abstraction interfaces
`IVoiceEngine`/`IVisualMotionEngine`/`ILLMEngine` (`src/dbos/interfaces/provider_contracts.py`,
tested), the `HardwareProfile` detector (`src/dbos/runtime/hardware_detector.py`, tested), and the
`PassportVault` identity-lock pattern (`src/dbos/vault/passport_vault.py` — immutability +
versioning), reused directly for avatar-skin identity rather than adapted into a different concept
the way wom7clips adapted it into a Brand Kit. Also reused: the Wan2.2 mlx-video /
LongCat-Video-Avatar 1.5 / CosyVoice / Kokoro-82M / LatentSync model shortlist from
`docs/RESEARCH_REFRESH_AUG_2026_WAN22_MLX_OMLX_ZEROCLAW.md` and
`docs/SOTA_UPGRADES_AND_COMPARISON_AUGUST_2026.md` — real-time talking-head + voice for a live call
is the same core problem personaje0 already solved for content generation, now under a latency
constraint (call-time, not batch-rendered).

**Consent is a structural requirement, not a policy statement.** The owner's original framing for
this subproject was avatars that let a user "wear different people's deepfake masks"; the owner
then confirmed directly, when asked about impersonation/fraud risk, that no real-person
impersonation or fraud is intended — masks are synthetic or consented identities only. personaje0's
own downloaded technical brief (`technical_task_architect_1_personaje_p0-001 (1).md`) sets exactly
this precedent for a real person's likeness — line 73: *"the real account owner must pass KYC, and
all real people whose bodies, faces or voices are used in content must have confirmed consent"* —
and requires mandatory human approval before anything using a likeness is published (line 969).
This ticket carries the same rule into wom7ava's design from the start: `PassportVault`'s
immutability-lock is reused specifically to make "this skin is a locked, consented identity" a
structural property of the vault entry, not something a caller can bypass.

This ticket covers the BOOTSTRAP only — standing up the repo and porting the reusable architecture.
It does not cover shipping a first working end-to-end avatar call, and does not cover designing the
full consent-verification workflow (how a real identity's owner actually grants/records consent)
beyond scaffolding the vault field that will hold it — that workflow is follow-on work once the
scaffold exists.

## Acceptance criteria

- [ ] AC1 — `casualuser/wom7ava.git` exists as its own repo (not a subdirectory of an existing
      wom7* repo) with an initial commit: README (scope, what's reused from personaje0 and why,
      what's out of scope), config matching estate convention, `.gitignore`.
- [ ] AC2 — Provider-abstraction interfaces ported from personaje0 (`IVoiceEngine`,
      `IVisualMotionEngine`, `ILLMEngine`) exist in wom7ava as typed interfaces/stubs, with a short
      doc note on what changed vs. the personaje0 source — noting the added real-time/low-latency
      constraint a live call has that batch content generation does not.
- [ ] AC3 — `HardwareProfile` detector ported from personaje0 and runs successfully on this
      machine (observable: a command prints a detected profile, not a stub/placeholder).
- [ ] AC4 — `PassportVault` identity-lock ported from personaje0 (reused close to as-is, not
      adapted into a different concept) to store each avatar-skin identity, with an added
      **consent field**: every vault entry is tagged `synthetic` (fully fictional identity, no
      consent needed) or `consented` (a real identity, with a required non-empty consent record),
      enforced at the vault layer so a caller cannot construct a "real identity, no consent" entry.
      Schema documented.
- [ ] AC5 — A visible AI-avatar disclosure requirement is documented as a hard design constraint
      for the eventual call UI (an on-screen indicator visible to other call participants when a
      synthetic avatar is active) — not built yet (no call UI exists), but recorded now so the
      constraint can't be quietly dropped once building starts.
- [ ] AC6 — `wom7web/.w0m/sdlc.json` `repos` map includes an entry for wom7ava (e.g.
      `"ava": "wom7ava"`), so this repo is visible to the estate's existing SDLC gates (`just
      discovery`, `just preflight`, etc.) rather than existing off their radar.
- [ ] AC7 — A short design note records which personaje0 pieces are reused as-is (`PassportVault`,
      provider interfaces, `HardwareProfile`) vs. deferred (the actual consent-collection workflow,
      real-time call transport/UI) vs. explicitly not applicable (personaje0's Omnichannel
      Publishing Queue and Phase-5 multi-tenant SaaS design apply to wom7clips' publishing model,
      not to wom7ava's live-call model — record that distinction explicitly) — so the next ticket
      that picks this up starts from a decision, not a re-read of personaje0's source.

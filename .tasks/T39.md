Authorization was **possession-based**: an RLS policy asking `is_admin()` grants access because the
user *holds* the role, regardless of which hat they are currently wearing. T39 made the *active*
hat the thing RLS enforces — a Supabase access hook projects `user_active_role` into the JWT claims,
`auth.acting_role()` / `wom_acting_is()` helpers read it, and the role stores were unified on
`user_roles`.

🔴 **SUPERSESSION — read this before treating any measurement below as current.** T39's numbers were
true of the tables it migrated, on 2026-07-18. They are **not** an estate-wide guarantee, and
[[T198]] (2026-08-11) measured the wider picture: the hat is read by **29 policies across 22 tables**
but is genuinely enforced only in the client-engagement corner — `contracts` is hat-blind, and an
admin wearing `member` still read `contracts=96`. T198 calls that *"the worst case, because it looks
enforced"*. T198 also **corrects** the residual once attributed here: *"posts INSERT open to any
authenticated user"* is **stale** — T39 did close it. Treat this ticket as the record of a delivered
phase, not as the current state of authorization.

- [x] **AC1** — the active hat reaches RLS: an access hook projects `user_active_role` into JWT
      claims, with `auth.acting_role()` / `wom_acting_is()` helpers reading it.
      Evidence: migrations `20260714100000_t39_acting_role_foundation.sql` and
      `20260716120000_t39_phase2_active_hat_policies.sql`.
- [x] **AC2** — possession-based admin policies are converted to active-hat checks.
      Evidence: all **7** possession `is_admin()` RLS policies rewritten to `wom_acting_is('admin')`
      (migration `20260716120000`, api `42382fa`), with a **live recount** rather than a code review.
      ⚠️ The record carries two counts: Phase 2 measured **0 possession / 26 active-hat** on
      2026-07-16, the 2026-07-18 close recorded **0 possession / 24 active-hat**. Both are
      transcribed as found; the two-policy delta is unexplained by the record and is **not**
      reconciled here.
- [x] **AC3** — the `posts` INSERT hole is closed: `WITH CHECK true` → author-or-admin.
      Evidence: Phase 2 migration. 🔑 Confirmed still-closed by [[T198]], which explicitly retired
      the contrary claim as stale.
- [x] **AC4** — hat-switching is proven **end-to-end with a negative case**, not just a happy path.
      Evidence: a `{member,recruit}` user acting as `recruit` returned `wom_acting_is('member')=false`
      *though the role was held*; switching flipped it true. That negative is the whole point of the
      ticket — possession no longer implies access.
- [x] **AC5** — privilege escalation is closed at **both** layers.
      Evidence: self-write of `user_active_role=admin` → 403 at RLS; force-write via `service_role`
      → the access hook falls back to a held role and the JWT stays `member`. A fix at only one layer
      would have left the other exploitable.
- [x] **AC6** — no policy reads authority off `app_metadata`.
      Evidence: recorded at close as **0 policies** reading `app_metadata`; migrations
      `20260714120000_t39_phase2_rls_migration.sql` and `20260714130000_t39_phase3_rls_cleanup.sql`.
- [x] **AC7** — impersonation is audited and works as a **real minted session**, Phase 4.
      Evidence: `impersonation_audit` table exists (`20260714110000_t39_impersonation_audit.sql`);
      gate green and proven live 2026-07-16 (api `33dbe236`, cp deployed). `impersonate.ts` mints a
      genuine target session (`generateLink` → `verifyOtp`, no email), stashes the admin session
      httpOnly for restore, and sets a sudo-token purely as an audit/authority marker; middleware no
      longer swaps identity — the session *is* the target, so RLS scopes to them — and a matching
      sudo-token only flags `isImpersonating` plus `impersonator`. `stop-impersonate` restores the
      stash. Guard `assertNotImpersonating` added for account-level mutations. UI wired
      (`RoleManager` POSTs `{targetUserId}`, layout banners → stop).
- [x] **AC8** — the two Phase-4 root causes are named and fixed, both of which had masked the
      feature as merely "broken":
      **(a)** *POST returns HTML not JSON* — on the member domain, strict-member-view forces
      `role=member`, so the member whitelist redirected `POST /api/admin/impersonate` → `/profile`
      **before the handler ran**; fixed by excluding all `/api/*` from page-level role redirects
      (`isApiRoute`), since API routes self-authorize with 401/403 JSON.
      **(b)** *session never switches* — `@supabase/ssr@0.12` **chunks** the session cookie (the
      admin JWT with `wom_roles` + `wom_active_role` spans 2 chunks, the target 1) and the `setAll`
      adapter only ever *wrote* chunks, never deleted stale ones, so `setSession(target)` left the
      admin's `.1` behind and the reader **reassembled the admin**; fixed by defensively clearing
      every auth-cookie variant and scope before writing the target.
- [x] **AC9** — the audit findings that opened this ticket are resolved and the spec archived.
      Evidence: `AUTH-RBAC` R1/R2/C4 recorded resolved; OpenSpec change archived at
      `openspec/changes/archive/2026-07-14-auth-rbac-hardening`.
- [N/A] **AC10** — middleware for `apps/job`. **DOWNGRADED in the record, branch not taken:** the
      job board is public (only `index`, `jobs`, `api/health` GET), so no gate was needed. Marked
      `[N/A]` rather than ticked — the work was not done because it was found unnecessary, and
      [[T198]] independently confirms *"the job app has no middleware"* is a stale finding.

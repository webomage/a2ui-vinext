# T159 — a session that cannot be revoked

## Summary

`POST https://cp.w0m.xyz/api/auth/signout` returned **403** against a **valid, authenticated
admin session**, and did not revoke it. Found 2026-08-02 while closing [[T156]] AC8, where the
authorised `just login-admin` break-glass was used to drive the CP "Trigger Scan" button.

**Minting a privileged session is one command; revoking it is currently not possible through the
documented route.** That asymmetry is the finding. A break-glass mechanism whose exit does not
work is a mechanism that accumulates live admin sessions.

⚠️ **There is a live one right now** — see *Open* in [[T156]]. It will expire on its own; killing
it early needs a server-side revoke with the service role, which would also sign the owner out of
their browser.

⚠️ **Scope widened 2026-09-06.** A second auth audit found the *same category of defect* —
signout does not revoke — in two of the three other apps, by a different mechanism (no 403
involved; the call silently no-ops). Both confirmed against on-disk source before adding here:

- **`apps/web/src/pages/api/auth/signout.ts:13`** and **`apps/join/src/pages/api/auth/signout.ts:13`**
  both pass **`supabaseClient: null as any`** into `handleSignOut`. Inside
  `packages/lib/src/auth/handlers.ts:463-465` the call is guarded — `if (supabaseClient) { await
  supabaseClient.auth.signOut(); }` — so a null client makes the guard **skip the revoke
  entirely**, silently, with a 200 response. The chunked SSR cookie (`sb-<ref>-auth-token`) that
  `getServerClient` reads to authenticate a user is **never invalidated**. `apps/cp`'s own
  signout.ts already does this correctly (`supabaseClient: getSupabaseServerClient({ request,
  cookies })`) — the CP app is not the only one broken, it is just broken a different way.
- **Pinned hat/impersonation cookies survive every app's signout.** `handleSignOut`
  (`handlers.ts:467-468`) deletes only `sb-access-token` and `sb-refresh-token`. It never deletes
  `sb-active-role` (the signed active-hat override cookie, read at `middleware.ts:156`) or
  `sb-sudo-token` (admin impersonation, read at `middleware.ts:171`). Role state and impersonation
  state leak across "signed out" sessions on the same browser.

## What is known

- The route exists and is not the problem on its face: `apps/cp/src/pages/api/auth/signout.ts`
  exports both `POST` and `GET` (`export const GET: APIRoute = POST`).
- It delegates to `handleSignOut` in `packages/lib/src/auth/handlers.ts:464`, which calls
  `await supabaseClient.auth.signOut()`. supabase-js defaults that to **global scope**, so a
  *working* signout would revoke every session for the user — meaning the 403 is the only reason
  the session survived.
- **The child-domain path is the prime suspect.** `cp.w0m.xyz` is not the master domain, so the
  handler builds `defaultNext` pointing at `https://cp.webomage.com/api/auth/signout?next=…` — a
  cross-registrable-domain hop. The same hop in the *other* direction is what `switch-role` does,
  and that one works, so the asymmetry is worth measuring rather than assuming.
- No `Origin`/CSRF/referer guard was found in `apps/cp/src/middleware.ts`, so a missing `Origin`
  header on a curl request is **not** an established explanation — it is a hypothesis.

## Why P1 and queue=security

Not because a stranger can do anything: the session belongs to the legitimate owner. It is P1
because **the estate's break-glass procedure has no working exit**, every use leaves a live
privileged session behind, and [[T154]]'s whole thesis is that an exposure nobody wrote down is
the dangerous kind. A session you cannot end is that shape.

## Acceptance criteria

- [x] **AC1 — reproduce it deliberately.** Mint a session via `just login-admin`, call
      `POST /api/auth/signout` on **cp.w0m.xyz**, and record the exact status, headers and body.
      Repeat on **cp.webomage.com** — if the master domain succeeds, the child-domain hop is
      confirmed as the cause rather than suspected.
      **Result (2026-09-10, live):** Minted separately (the mint script's magic links invalidate
      each other when generated in the same batch — a real but separate gotcha) and hit
      `/api/auth/signout` on each domain with DevTools Network preserved. `cp.w0m.xyz`:
      `signout` → **302**, then `signout?next=https%3A%2F%2Fcp.webomage.com%2F...` → **302**. No
      403 on either hop. `cp.webomage.com`: `signout` → **302** directly (master domain, no hop).
- [x] **AC2 — identify what returns the 403**, naming the file and line. Candidates: the
      cross-domain `defaultNext` hop, a middleware role/redirect rule, or a Cloudflare-level
      response. A guess that is not traced to code does not close this.
      **Result:** it doesn't return one anymore. `packages/lib/src/auth/middleware.ts:86` sets
      `isApiAuth = pathname.startsWith("/api/auth")`, which feeds `skipGate` (line ~217-218) and
      exempts every `/api/auth/*` route — including `signout` — from all gating that could produce
      a 403. That exemption landed in commit `1d6123538` (2026-09-03), as an unrelated
      auth-hardening change — three days *before* this ticket's scope was widened (2026-09-06),
      but nobody re-ran AC1 after that commit, so the ticket kept citing a bug that had already
      stopped reproducing.
- [x] **AC3 — signout works from BOTH CP domains** and returns a non-error status.
      **Result:** confirmed live above — 302 on both domains, no errors.
- [x] **AC4 — it actually revokes.** After a successful signout, `/api/auth/me` with the same
      cookie jar must not return the user. Verifying the status code alone is exactly the mistake
      [[T156]] was opened to stop.
      **Result:** confirmed live — `cp.webomage.com/api/auth/me` and `cp.w0m.xyz/api/auth/me` both
      returned `{"user": null, "role": "viewer", "availableRoles": []}` after signout. Re-confirmed
      a second time via `just logout-admin` (added for AC5): both domains landed cleanly back on
      `/login` with no error banner.
- [x] **AC5 — `just login-admin` documents its exit**, or gains a companion (`just logout-admin`)
      that revokes what it minted. A break-glass with no exit is not finished.
      **Result:** added `just logout-admin` (justfile, wom7api — wom7web's is a symlink). It opens
      `{base}/api/auth/signout` for each base in the same browser profile `login-admin` used;
      `auth.signOut()` defaults to GoTrue's "global" scope, so this revokes every session for that
      user everywhere, not just the CP cookie. `login-admin` now also prints a reminder to run it.
- [x] **AC6 — a regression test** covers signout on the child domain, proven RED against today's
      behaviour.
      **Result:** `packages/lib/src/auth/signout.spec.ts` (already present, committed `73f4b085`)
      asserts pinned-cookie deletion (`sb-active-role`, `sb-sudo-token`, `sb-imp-admin-access`,
      `sb-imp-admin-refresh`) and that cleanup/redirect still happen if `signOut()` throws. Proven
      RED by temporarily reverting the `handlers.ts` fix (2/3 tests failed with the exact
      `handleSignOut` code this ticket found broken), then GREEN again after restoring it.

## Resolution (2026-09-10)

The literal symptom in the title — 403 on `cp.w0m.xyz` — no longer reproduces; it was fixed as a
side effect of unrelated middleware work before this ticket's scope was widened. The real,
still-open defect was the 2026-09-06 scope-widen note, now fixed:

- `apps/web/src/pages/api/auth/signout.ts` and `apps/join/src/pages/api/auth/signout.ts` now pass
  a real `getSupabaseServerClient({ request, cookies })` instead of `null as any` — the Supabase
  session is actually revoked on signout in both apps, not silently skipped.
- `packages/lib/src/auth/handlers.ts`'s `handleSignOut` now also deletes `sb-active-role`,
  `sb-sudo-token`, `sb-imp-admin-access` and `sb-imp-admin-refresh` alongside the token cookies,
  and wraps the revoke call in try/catch so a GoTrue failure can't block cookie cleanup.
- `just logout-admin` added as the break-glass exit `just login-admin` was missing.

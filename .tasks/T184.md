## 🔑 MEASURED 2026-08-08 — omlx does NOT use mlx-rs, so the fork serves nothing we depend on

Owner question: *"check if omlx use mlx-rs under the hood and in most cases revert wom7mlx to
original mlx-rs"*. **Checked. It does not.** omlx hides behind two shell wrappers; following both:

| layer | what it actually is |
|---|---|
| `~/.omlx/bin/omlx` | 304-B `/bin/sh` wrapper → `/Applications/oMLX.app/Contents/MacOS/omlx-cli` |
| `omlx-cli` | another `/bin/sh` wrapper → `exec "$PYTHON" -m omlx.cli` with a **bundled CPython 3.11** |
| MLX flavour | 🟢 **official Apple MLX for PYTHON** — `mlx 0.32.0`, `mlx_lm 0.31.3`, `mlx_metal 0.32.0`, `mlx_audio`, `mlx_embeddings` in `Resources/Python/framework-mlx-base/.../site-packages` |
| Rust artifacts in the whole bundle | 🔴 **ZERO** — no `.rlib`, no `mlx-rs`, no `mlx-sys`, no `oxideai` |
| UI shell | Swift (`libswiftMetal.dylib`) |

⇒ **`mlx-rs` is used by exactly one thing in this estate: `wom7mlx`'s own Rust port**, which is now
P3. The vendored fork is therefore carrying risk (a 25-error skew, a moved submodule pointer) **for
a consumer that does not exist yet**, while the proven LLM path (omlx) never touches it.

🔑 **And the revert is a THREE-LINE deletion, not a migration.** `wom7mlx/wom7mlx/Cargo.toml`
already declares upstream versions in `[dependencies]` — `mlx-rs = "0.25.3"`, `mlx-sys =
"0.2.0-alpha.2"` — and only the trailing block redirects them:

```toml
[patch.crates-io]
mlx-rs  = { path = "../mlx-rs/mlx-rs" }   # line 31
mlx-sys = { path = "../mlx-rs/mlx-sys" }  # line 32
```

Deleting those three lines restores the crates.io dependencies. ⚠️ **This is a hypothesis with a
cheap test, not a conclusion:** the 25 errors are *missing symbols* in the vendored pair
(`mlx_fast_rope_dynamic`, `mlx_fft_fftshift`, `mlx_linalg_eig`, `mlx_segmented_mm`, plus an arity
mismatch on `mlx_gather_qmm`), consistent with a fork mid-surgery — but **upstream 0.25.3 may not
expose them either**, in which case the port's code, not the fork, is what needs changing. **Measure
before concluding** (AC6).

Owner asked to compare **Rapid-MLX** against omlx and mlx-rs, then **decided: omlx works, Rapid-MLX

`/Applications/Rapid-MLX Desktop.app` (`com.rapidmlx.rapid` 0.10.8, upstream

no `.metallib`, no Rust *in the bundle at all*. The engine is a **separately downloaded 382 MB
sidecar** at `~/Library/Application Support/Rapid/runtime-override/rapid-mlx`, reached over
`127.0.0.1`. Its shim ends:

```sh
exec "$ROOT/python/bin/python3.12" -P -u -s -m vllm_mlx.cli "$@"
```

🔑 **The distribution is named `rapid_mlx` but the import package is `vllm_mlx`** — it is a
vLLM-style server (paged attention / continuous batching) for MLX, shipped as `.pyc`.

| | **omlx** ✅ chosen | **Rapid-MLX** ❌ rejected | **wom7mlx** (the port) |

| shell | Swift | Swift/SwiftUI (19 MB) | — |
| runtime | bundled CPython **3.11**, in-bundle | bundled CPython **3.12**, 382 MB **out-of-bundle** | Rust |
| serving engine | `omlx.cli` | `vllm_mlx.cli` (vLLM-style) | own |

| `mlx_lm` | **0.31.3** | **0.31.3** | — |
| `mlx_vlm` | 0.6.3 | 0.6.6 | — |
| audio / embeddings | `mlx_audio`, `mlx_embeddings`, `dflash_mlx` | ❌ neither | — |
| **Rust artifacts** | 🟢 **ZERO** | 🟢 **ZERO** | all of it |

🔑 **The two apps ship byte-identical MLX versions.** Choosing between them was never an MLX-version

## 🔎 THE OPEN QUESTION (owner, 2026-08-08) — "is there something like omlx but in Rust?"

Deferred by the owner to *later*, researched now because it **decides AC4**.

**Closest match: [`mistral.rs`](https://github.com/EricLBuehler/mistral.rs)** — Rust, active
(~7.6k★, v0.8.x), `mistralrs serve` exposes **OpenAI-compatible `/v1`**, **Metal on Apple Silicon**,
and covers text / vision / video / audio / speech-gen / image-gen / embeddings in one engine.
Functionally it is the Rust analogue of omlx's *role*.

🔴 **But it is built on HuggingFace Candle — NOT MLX, and it does not use `mlx-rs`.** That splits the
owner's question in two, and the two answers point opposite ways:

| if the goal is… | then… |
|---|---|
| **local LLM serving, in Rust, on Apple Silicon** | ✅ **already exists** — `mistral.rs`. The wom7mlx port is **redundant**; evaluate, don't build. |
| **MLX specifically, in Rust** | 🔴 **nothing off the shelf.** `mlx-rs` is a *bindings crate*, not a server — a "Rust omlx on MLX" would be wom7mlx **building** one. |

⇒ **The reactivation question is not "should we finish the port" but "which of those two goals was
it ever for".** Unanswered, that is exactly the ambiguity AC4 exists to remove.

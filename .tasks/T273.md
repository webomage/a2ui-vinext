# T273 — Rust on Workers, deliberately scoped

## Summary

Owner direction 2026-08-24: *"CF workers can do WASM with deploy from Rust — so we will use since
now more Rust to deploy to workers required tools and utils!"*

**The capability is real.** Cloudflare supports Rust compiled to WASM on Workers via `workers-rs`
(the `worker` crate) plus `worker-build`/`wasm-pack`, and it is a first-class path, not a hack.

🟢 **And the footing is better than it looks — this extends a governed runtime rather than adding
one.** Measured 2026-08-24: `project/stacks-policy.json` already declares a **`rust`** stack (`mlx`)
with `build`/`test`/`lint`/`fmt`/`fmt-check` commands, and `cargo`, `rustc` and `rustup` are already
required tools in `project/tools-policy.json`. The estate's runtime split today is **deno (1) ·
node (5) · python (3) · rust (1)**. What is missing for Workers specifically is the
`wasm32-unknown-unknown` target, `worker-build`, and the `worker` crate.

## The constraint that decides the scope: the bundle budget, and we are on the free tier

A Worker has a **compressed bundle-size limit**, and the free tier's is the smaller one. A Rust WASM
module is not free weight — it carries its own allocator and whatever of `std` it pulls in, and it
is easy to produce a binary that dwarfs the TypeScript worker it replaces.

🔑 **This connects directly to the thread we are already in.** [[AgDR-0003]] keeps us on free tiers,
[[T271]] is surveying whether to spend, and [[T272]] gates that spend on per-client cost
attribution. **"More Rust on Workers" is a plausible way to consume the free bundle budget and push
toward Workers Paid** — which would be a paid-tier decision arrived at sideways, through a
toolchain choice, rather than through T271's comparison. ⇒ **AC2 measures the bundle before anything
ships**, so if that trade-off is being made it is made on purpose.

## Where Rust actually pays, and where it does not

I am applying the rule this estate adopted hours ago in [[T271]] AC2 — *every candidate paired to a
need we have* — to Rust as well, because applying it selectively would make it a preference rather
than a rule.

| our Workers today | shape | does WASM help? |
|---|---|---|
| `wom7api` Hono worker | HTTP routing, Supabase calls, AI provider fan-out | 🔴 **No** — I/O-bound glue. The time is network, not CPU; WASM adds bundle and a second toolchain for zero latency win |
| `wom7cfworkers` document-generator | `@cloudflare/puppeteer` → `page.pdf()` | 🔴 No — the work happens in a remote browser |
| scheduled/cron workflows | orchestration | 🔴 No |
| **hashing, parsing, compression, image transforms, diffing, crypto** | CPU-bound | 🟢 **Yes** — this is exactly WASM's case |

⇒ **The honest framing is "Rust for the compute-bound utilities", which is what the owner said**
(*"tools and utils"*), not "Rust for Workers". A blanket rewrite of I/O-bound handlers would cost
bundle bytes and a second toolchain and buy nothing measurable.

## Worked example for AC5: ZeroClaw is NOT a candidate, and measuring why draws the line

Owner asked 2026-08-24: *"since zeroclaw is a small rust app then could it fit wasm features in CF
somehow?"* Measured the same day, and the answer is a clean no — which makes it the most useful
example this ticket has, because it is a real Rust app in our own estate.

🔴 **Size decides it before capability does.** `~/.cargo/bin/zeroclaw` is **31,699,216 bytes**
(v0.8.3, 2026-07-27) — a **31.7 MB** native binary. A Worker's *compressed* bundle ceiling is ~1 MB
on free and ~10 MB on paid. A WASM build carrying SQLite + FTS5 and an agent runtime does not
approach that even stripped. ⇒ *"small Rust app"* is true of the source and false of the artefact,
which is worth knowing generally: **judge WASM candidates by BUILT size, never by how small the
project feels.**

**And the capability blockers are structural, not incidental** — they are its own subcommands:

| capability | why a Worker cannot host it |
|---|---|
| `daemon` — long-running on `127.0.0.1:42617` | Workers do not listen on sockets; they answer a fetch and end |
| `acp` — JSON-RPC 2.0 **over stdio** | there is no stdio in a Worker |
| `service` — launchd/systemd | there is no OS |
| FTS5/SQLite memory backend | no filesystem; D1 is a different engine, not a port target |
| routes to `omlx` at `127.0.0.1:8888` | a Worker cannot reach this laptop — and that route is the point of the runtime |
| iMessage channel | macOS-only |

⇒ **ZeroClaw's defining property is that it is LOCAL.** Porting it to a stateless edge runtime would
remove the reasons it exists. 🔑 That is the AC5 boundary stated with a real subject rather than in
the abstract: **the compute-bound utilities port; the runtime does not.**

🟢 **What could**, if a need appears: the SOP DAG evaluator (given a DAG and state, compute the next
step), prompt/template rendering, the eval harness's deterministic replay diffing, parsing and
validation — all pure functions over data, no I/O, no state.

🔑 **And the better third option, which is not a port at all:** give ZeroClaw a **Worker-side
counterpart**. A2A is an HTTP protocol, so a Worker can speak A2A to remote agents while ZeroClaw
speaks it locally. No WASM involved, and it is already the shape
`openspec/changes/2026-08-20-zeroclaw-runtime-and-ecosystem-integration` describes.

## Acceptance criteria

- [ ] AC1 — **The Workers-Rust toolchain is DECLARED, not just installed.** `worker-build`,
      `wasm-pack` and the `wasm32-unknown-unknown` target enter `project/tools-policy.json` with
      version floors, and a `rust`-runtime Workers stack enters `project/stacks-policy.json` with
      its `commands` contract ([[T130]]: a declared command bound to a missing recipe hard-fails).
      ⚠️ Extending the existing `rust` stack entry is likely wrong — `mlx` is a native binary, this
      is a WASM deploy target; state which, rather than overloading one entry.
- [ ] AC2 — 🔴 **Measure the bundle, before and after, and state it against the tier limit.** The
      first Rust worker records its compressed size next to the TypeScript baseline it sits beside.
      **If Rust on Workers is what pushes us to Workers Paid, that must be a stated finding reported
      to [[T271]]**, not a side effect discovered at deploy time.
- [ ] AC3 — **A type/lint gate exists for the Rust workers, wired like the TS one.** [[T105]]
      established `just typecheck-worker` for the Hono worker and its lesson was that a runtime's
      checker must actually understand the target. `cargo check` + `clippy` for the WASM target, in
      a `just` recipe, registered in `project/test-suites.json`.
- [ ] AC4 — 🔑 **The first one is a REAL utility with a measured before/after**, not a hello-world.
      Pick a CPU-bound job we actually run, port it, and record the latency and bundle delta. A
      capability demonstrated only on a toy has not been demonstrated — and if the measured win is
      small, that is the result and it belongs in the record.
- [ ] AC5 — **State what stays TypeScript, and why.** Per the table above, the I/O-bound handlers.
      Without this the next agent reads *"we use Rust for Workers now"* as a mandate and ports a
      Supabase-calling route for no gain. ⚠️ This estate has a standing problem with a direction
      being read wider than it was set.
- [ ] AC6 — **Deploy one to production and prove it serves**, through the normal recording wrapper
      so it appears in `deploy_log` ([[T259]]). A Worker that only ever ran locally is not adopted.
- [ ] AC7 — **Second-language cost is stated once, in writing.** One maintainer, and this makes Rust
      the fourth runtime beside TS, Python and Deno. Say what that costs in review burden and
      onboarding, so the decision is made with the cost visible rather than discovered later.

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
the toolchain is declared in both registries with a working `commands` contract, a lint/check gate
is registered and blocking, one real CPU-bound utility is ported with measured latency and bundle
deltas, it is deployed and recorded, and the boundary — what stays TypeScript — is written down.

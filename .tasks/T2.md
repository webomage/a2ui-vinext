# T2 — Client registration stage

## Summary


🔴 **P1 2026-08-13 — `in-progress` and the BACKEND LOOKS BUILT.** `client-register` is **live on the
platform and 125 lines on disk**, carrying `generateLink` / magic / idempotent / `'client'` — i.e.
AC1–AC3 read as satisfied. **AC4** (web ChatApp `service_request` SSE frame → registration card) and
**AC5** (Playwright E2E) are the front-end half and appear open. ⚠️ **Not ticking them here** — an
AC-truth pass must confirm behaviour, not signals; this estate has repeatedly found both *spec-only
changes that were built* and *built things never archived*. P1 because it is the client funnel's
entry point and most of it already exists.
A `client-register` edge fn turns a `submit_service_request` lead into a CP `client`
(magic-link, idempotent, `client` role). The `client` role is already allowed (no
migration needed).

- [x] **AC1** — ✅ **DONE.** `client-register` edge fn converts a `submit_service_request` lead into a

- [x] **AC2** — ✅ **DONE.** The flow is idempotent at **every** step, not just the link: auth user

## Definition of Done

T2 is done when: a `submit_service_request` lead converts to a CP `client` via
`client-register` (idempotent across auth-user/role/org/membership), the web ChatApp's

# T267 — a host-wide match on a repo-scoped fact

## Summary

Hit live on 2026-08-23. A commit in `wom7web` was refused by the `deploy-in-flight` pre-commit hook:

```
Refuse to commit while a deploy is running (T224)....Failed
❌ A deploy is running — committing now would break it.
     7060 just deploy-prod
```

The owner identified the process: **1945's apex production deploy**, a different project entirely.
The commit had nothing to do with it.

**The mismatch.** `project/scripts/deploy_in_flight_check.py:45` runs `ps -eo pid=,command=` and
matches **any** process whose binary is `just` and whose first non-flag argument matches
`^(deploy|deploy-all|deploy-[a-z-]+)$`. That scan is **host-wide and repo-blind**.

The fact it is protecting is **repo-scoped**. `project/scripts/confirm_step.py:148` resolves
`head_sha()` with **`cwd=WEB_ROOT`** — hardcoded to this repo — and a granted consent is discarded
when that SHA moves. So the hook's own printed rationale (*"committing moves HEAD, so the running
deploy loses its consent"*) is a true statement about **w0m's** deploy and a false one about
anyone else's.

🔴 **For the 1945 case it is wrong twice.** Its HEAD is a different repository, **and 1945 has no
`confirm_step.py` at all** — searched its tree, there is none. So the hook printed a correct
paragraph about a consent mechanism the blocking process does not use.

🟢 **The hook is RIGHT in its own case and must stay.** Deploys run from `wom7api/`, but
`confirm_step.py` pins `head_sha()` to `WEB_ROOT`, so a `wom7web` commit genuinely does invalidate a
w0m deploy's consent — that is not a theory, it happened three times on 2026-08-16 and cost the
owner a re-confirm on every remaining step. **This ticket narrows the hook; it does not weaken it.**

## 🔴 The obvious fix is wrong, and that is the interesting part

The first fix that comes to mind — *resolve the deploying process's cwd, take its `git rev-parse
--show-toplevel`, block only if it equals this repo* — **would break the case the hook exists for.**

A w0m deploy runs from `wom7api/`, so its toplevel is **`wom7api`**, not `wom7web`. That rule
unblocks exactly the deploy that must block, while looking like a tightening. It would pass a
review and pass a naive test, and the failure would only appear the next time the owner sat through
a re-prompt.

⇒ **The boundary is the ESTATE, not the repo.** And it is declared, so it does not have to be
guessed: `.w0m/sdlc.json → root: ".."` with `repos` enumerating all seven (`web: wom7web`,
`api: wom7api`, …). Reading it satisfies CLAUDE.md's standing rule — *measure from the root the
CONFIG declares, not the one you assume* — which this estate has already broken enough times to
have a rule about it.

| deploy | cwd | inside the declared estate root? | verdict |
|---|---|---|---|
| `just deploy-all` (w0m) | `…/@wom/wom7api` | yes | **BLOCK** — consent binds to `wom7web` HEAD |
| `just deploy-prod` (1945) | `…/_self/1945` | no | **allow** |

## Verified technique

`lsof -a -p <pid> -d cwd -Fn` resolves a process's cwd on this host (macOS 25.6). ⚠️ **Parse it by
FIELD TAG, not by line number** — `-F` emits tagged lines and the second line is `fcwd`, the
descriptor, not the path. Select the `n` field:

```
lsof -a -p <pid> -d cwd -Fn | grep '^n' | cut -c2-
```

Recorded because the first attempt at this, written while drafting the ticket, took `sed -n '2p'`
and returned the literal string `fcwd` — a value that is not a path, would not match any estate
root, and would therefore have made every deploy look foreign. **A parse bug here fails OPEN**,
which is the direction that costs something.

## Acceptance criteria

- [x] AC1 — **A deploy running OUTSIDE the declared estate root does not block a commit here.**
      Reproduce the 2026-08-23 case: a *just deploy-\** process whose cwd is outside the estate, and
      a commit in `wom7web` that succeeds.
      ✅ **2026-08-24** — `running_deploys()` now resolves each candidate's cwd and blocks only when it is inside the declared estate. Probe: *a deploy OUTSIDE the declared estate does NOT block*, reproducing the 2026-08-23 case.
- [x] AC2 — 🔴 **CONTROL, and this AC is the one that matters: a w0m deploy STILL blocks.** A
      *just deploy-\** whose cwd is `wom7api/` — **not** `wom7web/` — must still refuse the commit.
      Without this probe the change is indistinguishable from deleting the hook, and the naive
      repo-equality fix passes AC1 while failing this.
      ✅ **2026-08-24 — the CONTROL, and it is the probe that matters.** *a w0m deploy running from `wom7api/` STILL blocks*. 🔑 Backed by a **MUTATION** section that re-runs the OLD host-wide rule against the same inputs and asserts it gets the foreign case WRONG — without that, the file would be green against a hook that never changed.
- [x] AC3 — **The estate boundary is READ from `.w0m/sdlc.json`** (`root` + `repos`), not hardcoded.
      A path literal here is the same defect one layer along.
      ✅ **2026-08-24** — `estate_root()` reads `.w0m/sdlc.json -> root`; no path literal. Probed by asserting the resolved root is `@wom`, and returns None (→ unmeasurable) when the declaration cannot be read.
- [x] AC4 — **An unresolvable cwd FAILS CLOSED.** If `lsof` is missing, denied, or the process exits
      mid-check, the hook blocks and says it could not determine scope. ⚠️ Today's `running_deploys()`
      already returns `[]` on a probe failure — *"cannot tell — do not block on a broken probe"* —
      which is fail-OPEN, and adding a second unreliable resolution step makes that choice load-bearing
      in a way it was not before. Decide it deliberately and say which way in the code.
      🔑 **"Could not determine" must not print the same message as "a deploy is running"** — the
      [[T242]] lesson from `authz_probe_suite`, where `got=-1` made an unreachable database
      indistinguishable from three policy violations and blocked two pushes as a security finding.
      🔬 **The race is not hypothetical — it was observed the same evening, hours after filing.** A
      second block fired on `35132 just deploy-prod`; by the time the proposed resolution ran against
      that pid, `lsof` returned nothing and `ps -p 35132` returned nothing — **the deploy had already
      exited**. So the very first live trial of this ticket's technique hit the unresolvable case,
      which makes AC4 the most likely branch to be exercised in practice rather than an edge. ⚠️ And
      it points at a design consequence: a pid resolved *after* the `ps` scan may be **gone**, so the
      cwd must be read as close to the scan as possible, and a vanished process is better treated as
      *"deploy finished"* (allow, re-scan) than as *"cannot determine"* (block) — the opposite of the
      default for a resolution FAILURE. Those two are different states and this AC must not collapse
      them: `lsof` cannot run is unmeasurable; the process no longer exists is a measurement.
      ✅ **2026-08-24** — THREE states: `ok` / `gone` / `unmeasurable`. A process that exited mid-check is a **measurement** and allows; an unreadable cwd is **unmeasurable** and fails closed with its own distinct message and colour. 🔬 Both live trials hit `gone`, so it is the common path — probes cover all three.
- [x] AC5 — **The parse is by field tag.** A probe feeding it `-F` output asserts the path is taken
      from the `n` field and not from a line offset, because the wrong parse fails open (AC4).
      ✅ **2026-08-24** — `process_cwd()` selects the `n` field; the probe's stub emits a real `fcwd` descriptor line so a line-offset parser would return the literal string `fcwd`.
- [x] AC6 — **The message names the scope it decided.** On a block, say which estate/repo the deploy
      belongs to; on a pass-through, nothing. A blocked person currently cannot tell whether the
      hook understood the situation, which is how the 2026-08-23 case took a human to diagnose.
      ✅ **2026-08-24** — the block message names the estate it decided on (`(in /…/@wom)`) and says a deploy in another project no longer blocks, citing the 2026-08-23 case.
- [x] AC8 — 🔑 **`emoji-check` has the SAME defect, folded in here 2026-08-24 by owner decision**
      (was [[T274]] AC7). It builds its corpus from `ESTATE.glob(pattern)` — the **working tree**,
      minus `exclude_paths` and minus gitignored paths (`emoji_policy_check.py:117 authored()`). So
      an **untracked** file that nobody was committing blocked a commit, and **unstaging did not
      help**. Same class as AC1: a gate measuring something wider than the change.
      🔴 **But NOT the same fix, and conflating them would break it.** `deploy-in-flight` has no
      legitimate wide scope — a foreign deploy is never our business. `emoji-check` genuinely needs
      the whole tree, at a *different moment*: the ratchet is an estate-wide invariant, and if it
      only ever saw staged files the corpus count would stop being checked at all. ⇒ **pre-commit
      measures the STAGED change; pre-push measures the TREE.** Two scopes, two moments, one
      invariant preserved.
      ⚠️ **The gate was not wrong about the file.** `docs/reports/PROJECTS_CATALOG_AND_CLEANUP_AUDIT_2026.md`
      (written by the Antigravity agent at 2026-08-24T08:53) really did carry **17 emoji headings**
      and really did breach the rule — 476 → 493. It found a true defect and was wrong only about
      *whose problem it was at that moment*. That is a scoping error, not a false positive, and the
      distinction matters: the fix must not make the finding disappear, only defer it to the push.
      🔑 **Both gates share one escape hatch and it is `--no-verify`, which is prohibited estate-wide.**
      That is the whole argument for fixing them together — not shared code, shared consequence. A
      gate that blocks on files outside your change is how a prohibition gets tested.
- [x] AC7 — **Registered and run.** The probes join `project/test-suites.json` as an **offline,
      blocking** suite. A hook probe that nothing runs is the shape [[T182]] AC4 just demonstrated —
      a fix recorded on one date and reverted by another, with 14 days of nobody re-measuring.
      ✅ **2026-08-24 — and it needed TWO changes, not one.**
      🔴 **First finding, from the start gate: `emoji-check` ran at pre-commit ONLY.** It was not
      in `.husky/pre-push`, and pre-push does not run `just test` either — it runs a hand-picked
      gate list. So narrowing pre-commit alone would have left the estate-wide invariant checked
      **nowhere**, turning a scoping fix into a silent removal. The tree check was ADDED to
      pre-push in the same change.
      🔴 **Second finding, structural: the naive narrowing would have DISABLED the gate.** The
      ratchet compares a whole-corpus COUNT to a baseline, so counting only the staged files puts
      every commit trivially under it — always passing. ⇒ `--staged` is a **DELTA**: per staged
      file, emoji headings now vs at HEAD. A file new to the index has no HEAD version, so its
      baseline is 0 and any glyph is a regression, which is intended.
      ⚠️ **D32 bit the implementation.** The first version ran `git diff --cached` with
      `cwd=ESTATE` — and `@wom` is not a git repo, so it failed on every run and the fallback
      fired silently. The staged mode was dead on arrival while looking wired. Now `cwd=WEB`,
      with a probe asserting it.
      🔑 **Unmeasurable falls back rather than passing**: if git cannot list the index, the run
      reverts to the whole-tree measurement. "I could not tell" must never render as "clean".
      Verified end to end: a staged file with a decorative glyph exits **1** and names the file
      `0 -> 1`; a clean index exits **0**; `emoji-check-test` green with 5 new probes.

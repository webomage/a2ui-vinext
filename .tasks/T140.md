# T140 — Dependency floors need upper bounds: `deps_sync.py` is blind to the right-hand side of a range

## Summary

`project/deps-policy.json` expresses security floors as **lower bounds only** (`"undici": ">=7.28.0"`).
`project/scripts/deps_sync.py` enforces them with:

```python
def semver(spec: str) -> tuple[int, int, int]:
    """First x.y.z found in a range spec ('>=0.35.0', '^2.110.7', '>=7.6.5 <8') -> tuple."""
    m = re.search(r"(\d+)\.(\d+)\.(\d+)", spec or "")
```

It takes the **first** `x.y.z` in the range and ignores everything after it. So the tool:

1. cannot **enforce** an upper bound (a repo that silently loses `<8` still passes `--check`),
2. cannot **propagate** one (`--apply` only rewrites repos *below* the floor, so a bounded floor is
   never pushed out), and
3. treats `">=7.28.0"` and `">=7.28.0 <8"` as **identical** — the `<8` is decorative to the checker.

⚠️ **The docstring already names `'>=7.6.5 <8'` as an input it accepts**, which reads as support.
It parses such a range without error; it just discards the constraint.

**This is not theoretical — an unbounded floor took the web test suite offline.** Discovered
2026-07-25 while ticking [[T49]]'s AC4:

- `floors.undici = ">=7.28.0"` let pnpm resolve **undici 8.7.0** in `wom7web`.
- `jsdom@29` (vitest's DOM environment) requires undici's internal
  `lib/handler/wrap-handler.js` — present in 7.x, **removed in 8.x**.
- `just test` therefore collected **zero** test files and exited on `MODULE_NOT_FOUND`.

The suite was not failing loudly; it was **reporting nothing while running nothing**. A security
control silently disabled the thing that would have caught the breakage.

🔴 **The general hazard: an unbounded floor is satisfiable by a breaking major.** Every entry in
`floors` currently has this shape, so `undici` is the instance that happened to be observed, not the
only one exposed.

Immediate fix already applied under T49 (wom7web pinned `">=7.28.0 <8"` → resolves **7.29.0**, still
above the floor, no patch level given up; recorded in `deps-policy.json` → `exceptions.undici`). This
ticket is the **generalisable half**.

## Acceptance criteria

- [x] **AC1 — parse the whole range.** `semver()` is replaced by a comparator that reads both bounds
      (lower + optional upper). A range with an upper bound round-trips without losing it.
- [x] **AC2 — enforce upper bounds.** `--check` **fails** when a repo's override is missing an upper
      bound the policy declares, or resolves a version at/above it. Proven **red** against a real
      violation, then **green** on the current tree.
      ⚠️ Per [[T135]] AC7: a gate that has never been seen red is not evidence. This project has
      shipped a vacuous gate three times.
- [x] **AC3 — propagate upper bounds.** `--apply` writes the bounded range into every repo the policy
      says should carry it, instead of only repos below the lower bound.
- [x] **AC4 — audit every existing floor for a needed ceiling.** All 9 entries in `floors` reviewed;
      each either gains an upper bound or is recorded as deliberately open-ended **with a reason**.
      Deliverable is the decision record, not a blanket `<next-major>`.
- [x] **AC5 — a lockfile-resolution assertion.** `--check` compares the **resolved** version in
      `pnpm-lock.yaml` against the policy range, not just the declared override string. The undici
      break was visible in the lockfile (`undici@8.7.0`) while every declared override looked correct.
- [x] **AC6 — regression test.** A test in the T130/T127 style covers: upper bound honoured, upper
      bound missing → red, and the exact undici-vs-jsdom shape (floor satisfiable by a breaking major).
- [x] **AC7 — a non-empty test suite is itself gated.** `just test` collecting **0 files** must fail,
      not pass. This is the defect that let the breakage stay invisible — a suite that runs nothing
      currently exits clean.
      ⚠️ Scope note: `wom7web`'s entire vitest corpus is **one smoke spec**. AC7 is about the
      *zero-collection* failure mode only; growing coverage is not this ticket.

# T198 — the authorization defects [[T117]]'s domain analysis found in the live database

## Summary

Nine authorization defects that are **running in production right now**, measured against the live
database on 2026-08-10: `anon` reads all 27 blueprints including the 3 marked `internal`; a
signed-in client reads **0** of their own contracts and **2** client organisations including the one
that is not theirs; `client-api` writes with the service key on three verbs without ever proving the
caller owns the target; and an admin who narrows their hat to `member` still reads all 96 contracts.
None of these need the office model to be fixed, and none of them stop being true if it is never
built.

## Why this ticket exists

[[T117]] is a **design** ticket — the unified roles/capabilities/offices model. Its 2026-08-10
domain analysis (artifact *T117 — client, blueprint, project: what RBAC actually enforces*, recorded
in `project/tickets/T117.md` §"Domain RBAC analysis") measured the live database while mapping the
design onto it, and nine of its seventeen findings turned out not to be gaps in the model at all:
they are **defects in the authorization that is running in production today**.

They are filed here rather than inside T117 for one reason: **T117 can be redesigned, deferred or
re-scoped, and these must not move with it.** They are true against the schema as it stands, they
stay true if the office model is never built, and a ticket whose ACs are "agree a design" is the
wrong place to track "anon can read the tables marked internal".

🔑 **Every finding below was measured, not inferred.** Actor probes ran inside a rolled-back
transaction (`SET LOCAL ROLE` + synthetic `request.jwt.claims`, then `count(*)`); policy and
function claims were read from live catalogs. Nothing here is read off a migration file.

⚠️ **Scope note — this ticket does NOT include the six "missing pieces"** (the `is_capable()`
reader, the capability catalog's coverage gaps, the decision about what the hat is *for*). Those
are design and belong to T117. This ticket is only the defects.

## 🔴 A · CLIENT — the portal is broken four independent ways, and they mask each other

⚠️ **A1–A4 each independently return "no data" for a signed-in client.** Fix any one alone and the
portal still shows nothing, which is indistinguishable from "this client has no data yet". That is
why this group must be fixed and verified **together**, with a probe, not a page load.

- **A1 — `contracts` has exactly one policy, and it is admin possession.** The client-facing
  policies on `client_milestones` and `engagement_closures` join *through* `contracts`, whose RLS
  applies to the caller, so those `EXISTS` subqueries can never match. Probe: client hat →
  `contracts=0`.
- **A2 — 🔴 cross-client isolation is enforced nowhere.** `clients` SELECT for `authenticated` is
  `deleted_at IS NULL`. No membership test of any kind, and the table carries `email`. Probe: the
  client hat sees `clients=2` — including the organisation that is not theirs. A plain developer
  reads the whole CRM client list.
- **A3 — `client_users` is write-only.** Written by `seed-demo` and `client-register`, read by
  **one** policy (`invoices`) and by **zero** lines of application code. The membership table the
  tenant boundary would be built from is inert.
- **A4 — `apps/cp/src/pages/client/portal.astro:16-18` filters an ORG foreign key by a USER id.**
  Three queries, `.eq("client_id", user?.id)` on `contracts`, `invoices` and `client_milestones` —
  and `client_milestones` **has no `client_id` column at all**, so the third is a filter on a column
  that does not exist.
- **A5 — 🔴 `client-api` authorises by role possession, then writes with the service key and never
  checks ownership.** Three verbs: `approve_milestone` (**its own comment claims the ownership check
  it does not make**), `request_revision`, and `simulate_payment` — which marks an arbitrary invoice
  paid **and credits a billing-circle treasury**. The target id arrives in the request body and is
  trusted. ⚠️ **The blast radius is small only because the tables are nearly empty** (`invoices=1`,
  `client_milestones=0`). That is not a mitigation, it is a countdown.

*(A6 — of 96 contracts, **1** carries a `client_id` and **0** carry a `client_user_id` — is data
state, not a defect; it is recorded here because it is why fixing A1–A4 will still show an empty
portal until the backfill runs, and it belongs to T117's data work.)*

## 🔴 B · BLUEPRINT

- **B1 — 🔴 a blanket permissive policy does not sit beside a careful one, it REPLACES it.**
  PostgreSQL OR's permissive `SELECT` policies. `blueprints` carries a genuinely sophisticated
  policy (access_scope tiers + `blueprint_acl` + hat checks) **and** a second one whose entire
  condition is `deleted_at IS NULL` ("Public blueprints are viewable by everyone"). The second wins,
  always. **Proven: 3 blueprints are marked `internal`; anon reads 27 of 27.** The careful policy is
  dead code that looks like a control.
  ⚠️ 🔬 **Corrected 2026-08-11: 38 tables carry a client-reachable blanket arm, and on 23 of them a
  scoped arm sits beside it and is replaced.** The original "15 tables, matters on exactly 3" counted
  blanket arms without filtering to client-reachable roles — it mixed in harmless `service_role` arms
  and it under-counted the tables where the defect actually bites. See AC4.
- **B3 — the offices that may publish cannot write.** The only authoring verb in the catalog is
  `blueprint.publish` (held by `design.lead` and `talent.trainer`), while the `blueprints` write
  policy is **admin-only**. There is no `blueprint.manage`. The capability grants an action the
  database refuses.

*(B2 `blueprint_acl` unreachable and B4 "0 contracts and 0 projects reference a blueprint" stay with
T117 — B2 is superseded by that ticket's `resource_grants` port, B4 is data state.)*

## 🔴 C · PROJECT

- **C1 — two office names sitting in a role column, authorising nobody.** The *"Managers can manage
  projects"* policy tests `role = ANY('admin','project_manager','devops')`. Neither
  `project_manager` nor `devops` is a legal value of the `role` CHECK constraint, so only the
  `admin` arm has ever matched.
  🔑 **Worth reading as more than a typo:** somebody already tried to write the office model into
  RLS, in the only vocabulary the database offered — a role string. It has been sitting there
  authorising nobody ever since. That is the whole gap in one policy.
- **C2 is the same blanket-OR defect as B1** and is fixed by the same AC.

## 🔬 CORRECTIONS to A–D, found while drawing the maps (2026-08-11)

Both corrections came out of generating `docs/backend/RBAC-MAP.md` from the policy catalogue rather
than from a targeted query. **Each finding survives; the explanation under it was wrong.**

- **🔴 C1 is four dead role strings across 24 policy arms on 7 tables, not two on one table.**
  `founder` (9 arms — `leads`, `lead_proposals`, `lead_artifacts`), `super_admin` (7 — `interviews`,
  `interview_templates`, `interview_template_technologies`), `project_manager` (4 — `projects`),
  `devops` (4 — `projects`). None is a legal `user_roles.role` value, so every arm naming one
  authorises **nobody** and only the `admin` alternative beside it does anything. ⇒ **AC5's scope is
  7 tables.** 🔑 Three of the four are *office* names — the same "office model written into a role
  column" that C1 identified, at four times the size.
- **🔴 D2's count was wrong in the correction's own direction, and its mechanism was wrong too.**
  The hat is read by **29 policies across 22 tables**, not 10 across 5 — that earlier figure
  undercounted, exactly as the "0 arms read the hat" claim it was itself correcting had. And the
  reason an admin in a `member` hat still reads `leads` is **not** that `leads` ignores the hat:
  ```sql
  -- public.leads · both PERMISSIVE · both roles=authenticated
  "Admin all on leads"       USING (EXISTS (SELECT 1 FROM user_roles
                                      WHERE user_id = auth.uid()
                                        AND role = ANY(ARRAY['admin','founder'])))  -- POSSESSION
  "Admins can manage leads"  USING (wom_acting_in(VARIADIC ARRAY['admin','founder']))  -- HAT
  ```
  Permissive arms are **OR'd**, so possession alone suffices and the hat arm is decoration. Same on
  `lead_proposals` and `lead_artifacts`. ⇒ **This is B1/E2 for a third time — a permissive arm
  replacing the careful policy beside it — and here the *careful* arm is the newer one, added beside
  the old one instead of replacing it.** `contracts` remains the genuinely hat-blind case: one
  policy, admin possession, 96 rows visible under any hat.
  ⚠️ **AC6 changes shape because of this.** "Make the commerce tables test the hat" is already done on
  three of them and achieves nothing; the fix is **removing the possession arm**, not adding a hat arm.

## 🔴 D2 · The commerce tables ignore the hat entirely

⚠️ **Heading kept for trace; corrected above — see the CORRECTIONS section.** They do not ignore it,
they OR it with possession.

An admin who deliberately puts on the **`member`** hat gets `wom_acting_role() = 'member'` —
correctly — and still reads **`contracts=96`** and **`leads=2`**. `contracts`, `leads`, `proposals`,
`lead_proposals` and the `blueprints` write policy all test **possession**, not the active hat.
Narrowing your hat does not narrow your data.

⚠️ **This is the worst kind of half-enforcement.** 🔬 **Count corrected 2026-08-11:**
`wom_acting_is()` / `wom_acting_in()` appear in **29 policies across 22 tables** (not 10 across 5),
both `SECURITY DEFINER` and resolving correctly — so the hat is real and *broad*, and on three of
those tables it is nonetheless inert because a possession arm sits beside it. A control that works on five
tables and is absent on the rest **looks** enforced, which is why nobody has noticed.

🔑 **Related structural fact (D3, not itself an AC here): 48 of 57 edge functions hold
`SERVICE_ROLE_KEY`.** For those paths RLS never runs, so the function's own check *is* the
authorization layer. This is why A5 is a defect in **code** and why hardening RLS alone would not
have caught it.

## 🔴 E · The WRITE layer — added 2026-08-11, first pass ever made over it

Every finding above (and every earlier report) measured **reads**. The write layer had never been
mapped. It carries the same OR-defect as the read layer, with a sharper consequence: a permissive arm
does not sit *beside* the careful admin policy, it **replaces** it.

- **E1 — 🔴 `admin_activity_logs`: anyone signed in can write the admin audit trail, and only admins
  can read it.** The INSERT policy is *named* `"Admins can insert logs"` and its entire check is
  `(( SELECT auth.role() AS role) = 'authenticated'::text)`, while SELECT correctly requires an
  `admin` row in `user_roles`. 2,123 rows. ⚠️ **The asymmetry is what makes it serious — forged
  entries are invisible to the only people who could notice them.** Same lying-label shape as A5's
  comment.
- **E2 — 🔴 `site_settings` and `slide_config`: a correct admin policy, cancelled by a loose one on
  the same table.** Each carries `"Admin manage …"` (`ALL`, `EXISTS … role = 'admin'`) *and*
  `"Auth users can update"` (`UPDATE`, `roles=public`, `auth.role() = 'authenticated'`). Permissive
  policies are OR'd ⇒ on `UPDATE` the admin test is decoration. Any account that can sign in can
  rewrite site settings (5 rows) and the homepage slide configuration (17 rows). **This is B1 in the
  write layer**, and it is why AC3 was widened.
- **E3 — 🟠 the assessment surface is readable by the people being assessed.**
  `cert_questions` SELECT `USING true` for `authenticated` (**0 rows — latent, and the policy is
  already in place for the day it is not**); `interview_templates` SELECT `USING true` for
  `anon,authenticated` (1 row) — the interview script is public; `user_cert_progress` is
  self-written (`user_id = auth.uid()`). Both `true` arms sit beside a correct admin-manage policy
  they replace.
- **E4 — 🔴 A2 is worse than "a client sees the wrong organisation": a bare signup reads the CRM.**
  Re-probed as `authenticated` with **zero roles and no hat**, seven tables return every row and
  `anon` returns none of them: `clients` (2 — **email column included**), `capabilities` (38),
  `office_capabilities` (49), `offices` (10), `onboarding_quests` (6), `profile_snapshots` (1),
  `synced_vacancies` (2). ⇒ **completing a signup form is the whole key.** The three RBAC-catalog
  tables are not a breach, but nobody decided to publish the authorization model either.
- **E5 — 🟠 the `blueprints` storage bucket is PUBLIC while 3 blueprints are `access_scope=internal`.**
  7 of 13 buckets are public (`assets`, `blueprints`, `cv`, `news`, `post-images`, `public-images`,
  `snapshots`). **B1's boundary, one layer down**: `access_scope` has no counterpart on the object, so
  an internal blueprint's assets are served to anyone with the URL regardless of what the row says.
- **E9 — 🟡 LATENT, not live: the policy cannot distinguish a client project from a portfolio entry,
  and the first REAL one is already scheduled.** ⚠️ **Downgraded 2026-08-12 from 🔴 — I called it a
  live exposure and the owner corrected it.** The one `projects` row carrying a `client_id` is
  **"Marketing Site Rebuild (Demo)" → "Northwind Studio (Demo)"** (`demo-client@webomage.com`,
  `demo_account=true`). Both `clients` rows are fixtures — the other is *"Merge Test Client"*. **No
  real client engagement is exposed.**
  🔬 **How I got it wrong:** the join that would have told me was in a query whose output my own grep
  filter swallowed, and I read the empty result as "no answer" instead of "the join returned
  nothing" — which was itself the signal. **An empty result is data; I treated it as absence.**
  🔴 **The structural finding stands, and it has a date.** The arm is
  `status IN ('active','completed')` with no notion of `client_id`, so **the next real client project
  with `status='active'` becomes world-readable the moment it is created.** [[T182]] imports 1945 and
  Artemio as the first two real client projects — **that is the trigger, and it is on the queue.**
  ⇒ **Fix before T182 imports — but NOT with the predicate I first proposed.** I suggested
  `client_id IS NULL`; that would make the **demo** project private and break the demo. The owner's
  demo-tenant slug ([[T204]] AC8) makes the rule say what is meant:
  ```
  public if  client_id IS NULL           (portfolio)
         OR  client is the demo tenant   (showcase)
  private otherwise                       (every real engagement, by default)
  ```
  🔑 **The difference is default-private for real clients, public by explicit intent** — instead of
  public as a side effect of a `status` value. ⚠️ **It depends on `clients.slug`, which does not
  exist**: demo-ness is currently a `" (Demo)"` substring in the name, and a policy cannot be written
  against a naming convention.
  ⚠️ **This is a consequence of a decision recorded in MY OWN migration** `20260811120000`, which
  deliberately kept *"Public can read active or completed projects"* and wrote: *"all 9 live projects
  match it … whether a public project portfolio is intended is a DECISION"*. **That was accurate and
  incomplete — one of the 9 is not a portfolio row.** Keeping the arm preserved a showcase and also
  exposed an engagement.
  🔑 **The root cause is [[T204]]: `projects` is two entities in one table**, so one RLS answer
  cannot be right for both. **But the fix here does not wait for the split** — the status arm can
  require `client_id IS NULL` (portfolio rows have none), which closes the exposure today and stays
  correct after the split.
  ⇒ **[[T204]] is deprioritised to P2; this stays open but as a *pre-condition of [[T182]]*, not as
  a live incident.** 🔑 The useful reframing: it is not "fix an exposure", it is **"close the hole
  before the thing that would fall into it arrives"**.
- **E8 — 🔴 `anon` reads three agent SYSTEM PROMPTS.** `ai_personas` carries a `system_prompt`
  column and a blanket `Public can read ai_personas` arm for `anon, authenticated`. Live:
  `agent-admin` 315 chars, `agent-architect` 567, **`agent-consultant` 2,752** — all publicly
  readable. That is prompt disclosure on the consultant agent that fronts the contact funnel.
  🔑 **Found by reading the columns rather than inferring from the row count.** The AC4 pass first
  filed this as *decision-needed* — *"3 rows, if these carry prompt text it is disclosure, if only
  display metadata it is fine, NOT YET READ"* — and reading the table took one query and turned a
  deferral into a defect. Fix is the same shape as AC3: drop the blanket arm; the admin-manage
  policy beside it already covers the write path.
- **E7 — ⚪ REFUTED 2026-08-12. There is no defect here, and the probe that found it was wrong.**
  The claim was that 8 (later 6) client-reachable `UPDATE` policies have `USING` but no `WITH CHECK`,
  so *"the resulting row is unvalidated and a user can reassign a row to another user"*.
  🔑 **Postgres does the opposite of what that assumed:** *"If no WITH CHECK expression is defined,
  then the USING expression will be used both to determine which rows are visible and which new rows
  will be allowed to be added."* ⇒ **a MISSING `with_check` is the SAFE default** — the write check
  equals the read filter. All 6 are admin-possession or own-row policies, and every one of them is
  sound.
  🔬 **Refuted by attempt, not by reading.** A genuine non-admin reassigning their own
  `social_integrations` row to another user gets
  `ERROR: new row violates row-level security policy` (probed inside `BEGIN … ROLLBACK`, table
  unchanged at 1 row). 🔴 **The earlier "E7 CONFIRMED LIVE BY ATTEMPT" was a false positive with a
  specific cause: the table holds ONE row and its owner IS AN ADMIN.** The admin `ALL` policy's
  implied check (`is_admin`) passes regardless of the new `user_id`, so the write succeeded as the
  admin policy is designed to allow — not because the user policy leaked.
  ⚠️ **The lesson belongs to the probe, not the schema: an actor probe must assert WHO it ran as.**
  A probe that picks its subject with `LIMIT 1` inherits whatever privileges that row's owner
  happens to have. Same family as the `posts.author`-is-NULL probe that passed for the wrong reason.
  ⇒ **Probe respecified** as `E7-check-broader-than-using` — the decidable hole is a `WITH CHECK` of
  `true` beside a restrictive `USING` (write a row you cannot read). **0 violations; suite 9 RED → 8
  RED, 8 GREEN → 9 GREEN.** Also measured: exactly **1** client-reachable policy whose CHECK differs
  from its USING (`user_active_role`), and its check is **stricter**, which is the hat model working.
- **⚠️ E1/E2 have an ESCALATION CONDITION that was not visible from the policy text.**
  `auth.role()` is **deprecated by Supabase** and *breaks silently once anonymous sign-ins are
  enabled*, because anonymous users carry the `authenticated` Postgres role. Measured: **0 of 20
  `auth.users` are anonymous today**, so E1/E2 are "any signed-in account" — but the `is_anonymous`
  column exists, and enabling the feature escalates them to **anyone at all**, with no policy change.
  ⇒ AC3/AC9's fix must replace `auth.role()`, not just tighten it. 🔑 Also why E2 is live rather than
  latent: **an `UPDATE` first requires a `SELECT`**, and both `site_settings` and `slide_config` are
  anon-readable, so the write arm is reachable.
- **✅ Three things came back CLEAN and are now regression guards in the suite:** no policy reads
  user-editable `raw_user_meta_data`; all 32 `SECURITY DEFINER` functions carry explicit ACLs (Postgres
  grants EXECUTE to PUBLIC *by default*, so the 7 that reach `anon` were a **decision**, not a
  leftover); and the one view in an exposed schema (`player_xp_totals`, `security_invoker` NOT SET) is
  closed by its grants. ⚠️ Recorded because a suite of only-failing assertions cannot prove it
  distinguishes pass from fail.
- **E6 — ⚪ `chats` accepts inserts from `anon` with shape validation only** (non-empty `session_id`
  and `content`, legal `role`; 4,164 rows). Correct shape for an anonymous site chat — recorded
  because **nothing in the estate marks it as an accepted decision**, and it is the only
  anon-writable conversation table.
- **⚪ Worth as much as the defects — five scoped policies that provably work:** `aggregated_jobs`
  gates on `is_active` (anon 4,281 of 7,375), `site_pages` on published-and-public (25/26),
  `documents` on `access_scope` (37/102), `site_settings` on a key pattern (2/5), `ai_models` (2/21).
  🔑 **The same `access_scope` mechanism that holds on `documents` is the one dead beside a blanket
  arm on `blueprints`.** The mechanism is fine; its placement is not.

## Acceptance criteria

- [x] **AC1 — ✅ DONE 2026-08-20 — the boundary is read, the probe is non-vacuous, and the QUERY was
      the last thing still broken.** Original: *a tenant boundary that something actually reads,
      proven by a cross-client probe.*
      **All four named changes now exist**, verified against the live database and the source rather
      than inferred from a green:
      · `contracts_client_select_own` — SELECT, gated `wom_acting_is('client')`, joins through
        `client_users`. ✅
      · `clients_select_member_or_admin` — `EXISTS (SELECT 1 FROM client_users cu WHERE
        cu.client_id = clients.id AND cu.user_id = auth.uid())`. ✅
      · `client_users` **is** the thing read — both policies above read it. ✅
      · `portal.astro` now queries the **organisation** it means. ✅ *(this was the gap)*
      🧪 **Acceptance is the probe, and the probe is not vacuous.** `A2-cross-client` is GREEN with a
      **non-admin `authenticated` actor** — AC1's own requirement, since an admin passes for a reason
      that does not generalise. ⚠️ And it was checked for vacuity first: `clients` holds **2 rows**,
      so *"a second client's rows are invisible to the first"* is a real assertion. A `count(*)
      WHERE id <> me = 0` over a single-row table would have passed while proving nothing.
      🔴 **Three defects in four lines of `portal.astro`, and all three rendered as an EMPTY PAGE** —
      which is why *"a client cannot see their own contract"* (this ticket's own title) **survived the
      RLS fix meant to cure it.** The policy admitted the right rows; the query asked for the wrong
      ones:

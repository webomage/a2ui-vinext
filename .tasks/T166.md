# T166 — Govern serena as a declared SDLC tool — LSP-backed edits and diagnostics, or remove it

## Summary

Owner directive 2026-08-05: *"we have to use serena in our sdlc."*

**Serena is already running in this estate — and nobody decided that.** Grounded 2026-08-05:

| Check | Finding |
|---|---|
| Live in session? | ✅ `mcp__serena__*` tools are available and callable |
| Declared in `.w0m/sdlc.json → mcp`? | 🔴 **No.** 12 servers declared (codegraph, graphify, cloudflare, github, supabase, claude-in-chrome, hostinger×6); serena is **absent** |
| In `.mcp.json`? | 🔴 No — that file declares only `graphify` |
| Governed in `tools-policy.json`? | 🔴 No — 17 tools governed, serena not among them |
| Referenced in `CLAUDE.md` / `AGENTS.md` / `KNOWLEDGE-GRAPH.md`? | 🔴 No |
| `.serena/` state dirs gitignored? | 🔴 **No** — present and un-ignored in `wom7api/` and at the monorepo root; contains `cache/`, `memories/`, `project.yml`, `project.local.yml` |

🔑 **Provenance — owner-confirmed 2026-08-05: "it's part of headroom install."** Verified exactly:

- Its config lives in **`~/.claude.json → mcpServers.serena`** — i.e. **global user scope**, written
  by Headroom's installer, *not* inside the Headroom plugin dir (which holds only `README.md` +
  `hooks`). So the `mcp` declaration below needs `scope: global`, matching codegraph.
- **It is already partially governed, under [[T162]]** — `project/scripts/headroom_bootstrap.py`
  carries `SERENA_CFG` and `check_serena()`, whose docstring states *"Headroom installs serena as
  its default code-memory MCP; serena needs a `projects` key."*

⚠️ **So the earlier framing of this ticket was wrong and is corrected here.** Serena is not rogue
and not undecided — it is a **bundled component of a deliberate install** (Headroom was an owner
call), and the estate already checks one thing about it. What is missing is narrower and more
precise: it is governed as a **Headroom precondition**, never as an **SDLC tool**. No `mcp`
declaration, no version policy, no gate role, no gitignore. That is the actual gap.

🔴 **The sharpest finding, and it is a supply-chain one.** The launch command is:

```
uvx --from git+https://github.com/oraios/serena serena start-mcp-server
     --project-from-cwd --context claude-code --open-web-dashboard False
```

**`uvx --from git+…` with no ref, tag or commit — it fetches the default branch on every start.**
The tool that can rewrite this estate's source at symbol granularity is therefore **unpinned and
re-resolved each launch**, from a third-party repo, with no lockfile and no integrity check. Every
other governed tool has a `min` and a `known_good`; this one cannot even report a stable version.
`tools-policy.json` has no `source` kind for this — `uvx-git` would be a new one.

✅ **Resolved, so it is not an open concern:** `--open-web-dashboard False` — the dashboard is
disabled, so `open_dashboard` binds no port. Transport is **stdio**, meaning `just mcp-exposure`'s
port scan structurally cannot see serena; only the declaration reconcile can.

### Does it earn a place, or duplicate what we have?

It earns one, and the distinction is sharp:

| Tool | Capability | Can it edit? |
|---|---|---|
| **codegraph** | per-repo graph — *where is X / who calls it / blast radius* | ❌ read-only |
| **graphify** | the united cross-repo graph | ❌ read-only |
| **serena** | **LSP-backed**: `find_symbol`, `find_referencing_symbols`, `find_declaration`, `find_implementations`, `get_symbols_overview` **plus `replace_symbol_body`, `insert_before/after_symbol`, `rename_symbol`, `safe_delete_symbol`, `replace_in_files`** and **`get_diagnostics_for_file`** | ✅ **yes, at symbol granularity** |

**Neither graph can edit, and neither can return type diagnostics.** That is the genuine gap serena
fills, and it maps onto specific gates: precise symbol edits in **build**, diagnostics in
**review**/**verify**. This is *not* a third "graph before grep" engine and must not be documented
as one — `just ask` stays the entry point for graph questions (T163).

⚠️ **Overlap that must be resolved, not ignored:** serena ships its own memory store
(`write_memory` / `read_memory` / `list_memories` / `edit_memory`, backed by `.serena/memories/`).
The estate already has an agent memory system and a knowledge-graph layer. Three memory surfaces
with no stated division of labour is the `just health*` problem again ([[T164]] AC3).

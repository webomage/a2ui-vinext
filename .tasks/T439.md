# T439 — CP information architecture — one shell with a Me / Org / Admin context switcher, capability-grown menus, and DS layout components

## Summary

Owner, 2026-09-24: *"concentrate on reworking UI for CP and Job/Join — reorganise menu and pages in CP to make it
well structured for members and clients"*. Brainstormed and decided the same day. Sub-project **1 of 4**: this
ticket is the CP IA only.

**Measured today:**
- `apps/cp` serves 69 pages through two hand-built layouts. `AdminLayout.astro` (487 lines, 14 nav groups) serves
  `admin` and `member`; `member-routes.ts` filters members to 9 pages. `ClientLayout.astro` (310 lines) is a flat
  7-item `/client/*` list.
- [[T207]] (done 2026-09-14) made the nav *correct*: one source, capability-aware, every page placed. It grouped by
  URL domain (`/business`, `/system`, `/recruit`…), not by the tasks people come to do. Recruiting spans
  `/interviews`, `/recruit` and `/business/ats`, Integrations mixes system and marketing pages, and one person's
  roles are handled by a "hat" mode with an "acting under" banner.
- The schema already models the context this needs (AgDR-0019 / [[T117]]): `public.orgs` (`org_type` host / client /
  partner / vendor), `projects.host_org_id` + `projects.client_org_id`, and `hats.org_id` + `hats.office`.
- The design system has no shell or navigation components at all. `design-system/components` is Svelte-typed
  specs since [[T422]]; nothing React is left to port.
- The CP goldens cannot serve as a baseline. They show 9 nav groups against the live 14, `en-desktop-dashboard.png`
  is a captured 404 (`/ai/interviews`), and the Projects golden shows two List/Groups toggles and duplicate rows.

**Decided (owner, 2026-09-24):**
1. **Members = both.** The talent network (Join) and the delivery team are one member area that **grows by
   capability**, not separate apps.
2. **One shell with a context switcher.** The contexts are **Me** · **each org** you belong to · **Admin
   console**. Client and agency orgs use the same shell; `ClientLayout` and `/client/*` merge into it, and hats
   become "the role you hold in this context".
3. **Org first, project inside.** Projects are pages in an org, with breadcrumb `Org › Project` and project tabs.
   A delivered project appears in both its host and client org.
4. **Design the IA as design-system components**, mocked in the proposal with the real tokens, then implemented
   in `@webomage/ui`.

**Split out, as their own tickets (menu slots reserved here):** 2 — public personal and company profiles
(portfolio, confirmed tests, connected accounts, verification badges); 3 — brand/page claims and anti-squatting
(reserved slugs, proof of control, disputes); 4 — Job/Join UI rework on these patterns.

  model, the capability per menu item, the old→new route map, and HTML mockups built from the real
  `design-system/tokens/*.css`. Validated with `openspec validate --strict` and `just spec-standard-check`, and
  reviewed and approved by the owner.
- [x] AC2 — **DS layout specs.** `design-system/components/layout/` gets a `.d.ts` + `.prompt.md` for `AppShell`,
  `ContextSwitcher`, `SideNav` (+ `NavSection`, `NavItem`), `Breadcrumb`, `PageHeader`, `Tabs` and `EmptyState`.
  The mockups use exactly these names and props.
- [x] AC3 — **Runtime components** in `@webomage/ui` (Svelte) matching AC2, with component tests.
- [ ] AC4 — **Context-scoped routes.** Pages live at `/me/…`, `/o/<org>/…`, `/o/<org>/p/<project>/…` and `/admin/…`.
  Middleware resolves the context from the URL and refuses a page without its capability (fail closed). Every old
  route permanently redirects, from one redirect map.
- [ ] AC5 — **One nav source, two consumers.** Menu and route gate read one per-context nav definition; each item
  names one T117 capability. A network member's Me menu grows as they gain capabilities, with no per-role lists.
  `ClientLayout`, `/client/*`, `switch-role` and the "acting under" banner are removed (clean cutover, AgDR-0025).
- [ ] AC6 — **Gates.** `just cp-nav-check --enforce` covers contexts, capabilities and the redirect map, with red
  probes. Gauge specs check each context's menu for a network member, a delivery member, a client and an admin.
- [ ] AC7 — **Goldens re-baselined deliberately** (`GAUGE_UPDATE_GOLDENS=true just goldens`), after replacing the
  captured-404 dashboard golden, with one golden per context.
- [ ] AC8 — **Split tickets filed:** public profiles, brand claims, Job/Join UI — each `Split from: [[T439]]`.
- [ ] AC9 — **Per-app colour schemes from the brand, as tokens.** `design-system/tokens/themes.css` defines a theme per
  surface: web, member CP, client portal, admin console, job, join, demo. Each has a brand/accent pair, gradient and
  focus ring, all derived from the brand ramps with no ad-hoc hex. Measured 2026-09-24: only `web` (sky
  `#38bdf8`) and `cp`/`admin` (`#0a84ff`) exist; `join` hand-rolls a blue→purple gradient and its own "W" tile
  logo instead of the brand mark. The shell mockups are re-rendered per theme using the brand components
  (GlassCard, StatusDot, logo lockup). Owner picks the palette.
- [ ] AC10 — **CP goldens actually backed.** Today they are not: `just goldens` runs only
  `specs/web/goldens.spec`, and `specs/visual/cp_visual.spec` is never run. It signs in with the Google-only
  `ADMIN_EMAIL`, so it could not pass. Its 20 images date from 2026-05-07 / 2026-06-30, 4 are referenced by no
  spec, and `dashboard` is a captured 404. Fix: a dedicated **non-real** test account per role type (never a real
  admin, [[T31]]) seeded by migration. One CP spec per context (Me / host org / client org / admin) runs inside
  `just goldens`, at the same 7-viewport matrix as the snapshot.
- [ ] AC11 — **Compared against the baseline.** Before the old layouts are deleted, re-run the snapshot
  (`project/scripts/ds_inventory.py` plus the viewport capture) and diff against `wom7web/design-system/_ref/snapshots/2026-09-24-pre-t439/`. Components moved into
  `@webomage/ui` and duplicates removed are listed. Baseline 2026-09-24: 14 components specified but not built,
  BlueprintCard / ComplexityBadge / QuickViewModal / SegmentBadge copied locally in web and cp, 7 hand-built
  layouts, cp = 123 local components vs 55 `@webomage/ui` imports.

- [ ] AC12 — **Me → Profile & CV → Work history page** (carried from [[T440]] AC4, which delivered the API and closed
  2026-09-24). Built in Plan C on `GET /api/profile/contracts` (timeline, client names masked) and
  `POST /api/profile/contracts/promote` (copies into `profile_experience`). Shows the 95 contracts per client and per
  year with a "promote to CV" action, and an `EmptyState` for members with no synced work. Measured live 2026-09-24:
  95 contracts + 1,782 proposals on profile `8d16aff5`, 0 on the old one.

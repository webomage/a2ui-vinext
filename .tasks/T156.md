# T156 — The Cloudflare Workflow layer was dead

## Summary

`wom7api/wrangler.jsonc` and `wom7cfworkers/wrangler.jsonc` **both** declared
`"name": "wom7cfworkers"`. Two repos, one Cloudflare script, each overwriting the other. The live
script had been wom7cfworkers' build since the last wom7api deploy on **2026-07-19**, and it
implements none of wom7api's dispatch routes.

The consequence is wider than the symptom that surfaced it: **all 19 Workflow entities on the
account were orphaned** — bound to script `wom7cfworkers` while their classes exist only in
`wom7api/src/workflows`. Not just the domain scanner. Every `/event` and `/trigger` call had been
404ing for six weeks.

Found on 2026-08-01 while working [[T155]] AC9, chasing why domain-scan enqueues vanished.

## Measured live, not inferred

| probe | result | meaning |
|---|---|---|
| `POST /event` | **404** | route exists only in wom7api/src |
| `POST /trigger` | **404** | route exists only in wom7api/src |
| `GET /api/ats/vacancies` | **401** | route exists only in wom7cfworkers/src → that build is live |
| `wrangler workflows list` | 19 entities → script `wom7cfworkers` | classes live in wom7api → orphaned |
| `workers_list` | no `wom7api` worker exists | wom7api/src was deployed nowhere |

## The armed hazard

`just deploy` → `deploy-api` deployed wom7api **onto** the live wom7cfworkers script, and
`deploy-all` calls `deploy`. The next full deploy would have silently reverted T155 AC9's cron work
and dropped `/api/ats/*`, `/api/generate` and both webhooks.

## Four lying successes

`fetch` does not throw on a non-2xx, so a wholly dead pipeline read as green. This is the same
organising defect as [[T155]] — nothing asserted that a dispatch **arrived**.

1. `domain-scan` bulk-run returned `success: true` with every URL marked `failed`.
2. wom7cfworkers' `/api/workflows/:name/trigger` returned `{success:true, runId:"stub"}` for
   everything except `job-scanner`.
3. The CP trigger route derived workflow names by string surgery — `webnames:scan-domain` became
   `webnames-scan-domain`, a name that has never existed — and sent **no bearer** after `b41ebfa`
   began requiring one.
4. `LinkedinSyncWorkflow` reported `Success: ✅ Yes` while burying a per-user failure in its step
   output: the `profile_snapshots` upsert violated `profile_url NOT NULL`. Root cause: the table has
   **two writers**, and the 2026-03-18 migration bolted the LinkedIn-API columns on without relaxing
   the wom7ext-scraper-era NOT NULLs. Three were missing — `profile_url`, `identity`,
   `content_hash` — and Postgres reported only the first.

## Done

- wom7api renamed to its own `wom7api` script; `sync-wom7api-secrets` added
- bearer required on wom7api's `/api/workflows/:name/trigger` — it had **no auth at all**, the same
  hole wom7cfworkers closed in `b41ebfa`
- `triggers.crons` emptied and `scheduled()` removed from wom7api: Workers Free caps **5 crons per
  ACCOUNT**, all on wom7cfworkers, and the handler duplicated every slot it drives
- `WOM7API_WORKER_URL` + a `WOM7API` service binding split the two workers apart;
  `WORKERS_WEBHOOK_URL` stays pointed at wom7cfworkers for `/ai/*` and ATS
- all four lying successes now report honestly (501 / 502 / explicit counts / throw)
- `summarise()` extracted to `src/workflows/sync-summary.ts`, unit-tested and **proven RED** by
  reverting the fix
- `vitest.config.ts` no longer collects the Deno edge tests — `pnpm test` had been permanently red
  on `Deno is not defined`, which hides a real failure as effectively as a green gate
- **migration governance** (the rule + `just db-drift-check` ratchet) — see below

## Verified live 2026-08-01

- `/event`, `/trigger`, `/api/workflows/…` all answer **401** unauthenticated (were 404)
- 19/20 Workflows rebound to `wom7api`; the holdout is the retired `upwork-poller`
- wom7cfworkers answers **501** for unimplemented workflows while `job-scanner` still runs
- all three CP event mappings create real instances, including `webnames:scan-domain` →
  `webnames-batch`, which had never worked
- `domain-scan` `action=run` **and** `bulk-run` both wrote `domain_scan_results` rows
- `linkedin-sync` returns `{"synced":1,"failed":0}` and `profile_snapshots` went from **0 rows to
  1** — the first successful write this integration has ever made
- wom7cfworkers redeployed with all 5 crons intact; webomage-cp and webomage carry the `WOM7API`
  binding

## Migration governance

Applying the `profile_snapshots` fix exposed that `supabase db push` was blocked: **6 versions were
in the ledger with no local migration file** — the T122/T123 **security** changes, none in this
repo's deletion history, applied straight to the DB. (A 7th was briefly miscounted: our own drift
checker skipped a legacy bare-date filename and reported an existing migration as missing.)

`AGENTS.md` caused it. It instructed agents to unblock a failing push with
`migration repair --status reverted <VERSION>`, which asserts a rollback that never happened while
the effects stay live. That advice is replaced, and the rule is now a CLAUDE.md non-negotiable with
`just db-drift-check` enforcing it (ratchet baseline: the count may fall, never rise).

Paid down and closed the same day under [[T157]], which also added the `wom_ddl_guard` event trigger — the drift check only sees changes that wrote a ledger row, so a plain `psql ALTER TABLE` was invisible to it until the guard closed that at the database.

## Acceptance criteria

⚠️ **Written retroactively on 2026-08-02**, after the work shipped — an anti-pattern worth naming:
ACs authored to match what was built grade themselves 100% by construction. These are written as
what the ticket *should* have demanded, then graded against **live measurement taken today**, not
against memory of the work. One is **not** met.

- [x] **AC1 — the two workers are separate Cloudflare scripts.** `wom7api/wrangler.jsonc` no longer
      claims the name `wom7cfworkers`, so neither repo's deploy can overwrite the other's.
- [x] **AC2 — every dispatch route requires the shared bearer.** Measured 2026-08-02 against the
      live worker: `/event` **401**, `/trigger` **401**, `/api/workflows/:name/trigger` **401**
      unauthenticated. The last had **no auth at all** before this ticket — the same hole
      wom7cfworkers closed in `b41ebfa`.
- [x] **AC3 — every Workflow entity is bound to a script containing its class.** All 19 rebound to
      `wom7api`; the 20th (`upwork-poller`) is retired by decision and correctly left behind.
      Before, all 20 pointed at a script whose code did not define them.
- [x] **AC4 — wom7api declares no cron.** Workers Free caps 5 triggers per ACCOUNT, all held by
      wom7cfworkers. `triggers.crons: []` and no `scheduled()` handler, so a re-added cron cannot
      silently double-run job-scorer, job-scanner, linkedin-sync, job-aggregator or the newsletter.
- [x] **AC5 — no dispatch path reports success it did not achieve.** Measured today: `domain-scan`
      `action=run` → 200 with a real `targetId`; `bulk-run` → `enqueued: 1, failed: 0` — counts,
      not a bare `success: true`. wom7cfworkers answers **501** for `domain-scanner` while
      `job-scanner` still returns **200**, so the stub discriminates rather than blanket-lying.
- [x] **AC6 — the pipeline writes results end-to-end.** `domain_scan_results` gained **3 rows**
      within 5 minutes of triggering today — `dns`, `crawl-front`, `ai-summary` — proving the
      workflows ran rather than merely accepted the request.
- [x] **AC7 — a step that fails every item fails the workflow.** `summarise()` throws on total
      failure, extracted to `src/workflows/sync-summary.ts` and **proven RED** by reverting it.
      `profile_snapshots` took its first successful write in the integration's history.
- [x] **AC8 — ✅ the CP "Trigger Scan" button works for a real admin.** Driven end-to-end
      2026-08-02 through the authorised `just login-admin` break-glass:
      `POST /api/admin/domains/trigger` → **200** `{"ok":true,…"runId":"b44c9c21-…"}`, and
      `domain_scan_results` gained a `dns` row — the workflow **ran**, not merely accepted.

      🔴 **It did NOT work on the first attempt, and the two reasons are the value of this AC.**

      1. **`just login-admin` mints a session whose active hat is `member`, not admin.** Measured:
         `/api/auth/me` → `role: member`, `availableRoles: [admin, manager, member, client,
         recruit]`. The trigger route checks `locals.role !== 'admin'`, so the button **403s** for a
         freshly "logged in as admin" operator. Switching requires `POST /api/auth/switch-role`,
         which returns `refresh: true` and a **cross-domain** callback — from `cp.webomage.com` it
         hands off to **`cp.w0m.xyz`**. Only after following that redirect does `role: admin`.
         So "log in as admin" and "be admin" are two steps, and nothing at the button says so.
      2. **`webomage-cp` held a STALE `WORKERS_WEBHOOK_SECRET`** → worker replied **401**, CP
         surfaced **502**. The vault value returned **200** against wom7api directly, which is what
         localised it to the CP's own copy. Fixed with *just sync-cf-secrets-cp*. ⚠️ The new value
         is **not instant** — a retest 4s later still 401'd; it passed minutes later. Same drift
         shape as the 2026-07-19 chat outage: a deployed secret copy silently behind the vault.

      **Neither would have been found without clicking the button.** Everything below the session
      cookie had already been proven green, and both defects live above it.
## Open

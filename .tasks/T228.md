# T228 — master one ticket schema, and make GitHub a projection of it

> Owner ask, 2026-08-16: *"we also could have discrepancy for local tickets and GH … it's even
> better to master united schema for tickets and re-manage old closed/merged/done tickets"*, then
> *"do, look at GH schemas available"*.

## Summary — what was measured, 2026-08-16

**The state mirror is healthy, and that is not where the problem is.** 223 of 223 tickets map to an
issue, **0 title drift**, **0 state mismatches**, labels track status. One orphan (`#1`, predates the
ticket system). So "local vs GH is out of sync" is **false as stated** — and worth saying plainly,
because it is the obvious hypothesis and it does not hold.

What is actually wrong is **semantic**, and a state check can never see it:

### 1. 🔴 `area:*` on GitHub does not mean `area`

`project/scripts/sync_github.py:145` builds those labels from **`repos`**, not from `area`:

```python
for a in ticket.get("repos", []):
    out.add(f"area:{a}")
```

So GitHub's `area:web` (170) and `area:api` (129) are **repository** names, while the local
thematic `area:` — `sdlc` 48, `product` 39, `security` 28, `tools` 23, … — **reaches GitHub not at
all**. One label namespace carrying two different meanings, and the one a human would search for is
the one that is missing. This is the estate's most-repeated defect shape ([[T192]]): **a thing
identified by its name rather than its content.**

### 2. 🔴 `queue` is write-only metadata that leaks outward

`ticket_schema_check.py` already records the judgement — *"nothing reads `queue`, so this breaks
nothing; the field is vestigial"* — and grepping confirms it: no ranker consumes it. Only the schema
check, the backfiller and the sync touch it. Yet it is present on **223/223 tickets** and projected
into **117 `queue:*` labels** on GitHub, including four spelled `queue:None` because the field is
empty on T44–T47. Dead metadata should not be publishing labels.

### 3. 🟡 Two competing priority encodings on GitHub

Bare `P1` (107) / `P2` (88) / `P3` (14) / `P0` (13) **and** `queue:p1` (114) / `queue:p2` (3). Two
answers to one question, from one producer.

### 4. 🟡 `area` vocabulary has never been normalised

20 values, with pairs that are plainly the same thing: `tools` 23 / `tooling` 4 · `security` 28 /
`sec` 1 · `schemas` 13 / `specs` 1 — plus six singletons (`web`, `rbac`, `ui`, `api`, `docs`,
`tickets`). Nothing rejects a new spelling.

### 5. 🟡 GitHub carries a stub, and does not say so

`build_body()` projects the `## Summary` section only — by design. The consequence is not
documented anywhere a reader would see it: **128 of 223 issues hold under 25% of their ticket**
(T117 82,505 B → 3,464 B = **4%**; T198 **1%**). An agent or person reading the issue instead of the
file gets a fraction and has no signal that they did.

### 6. 🟡 Done tickets are never re-managed

68 `done` tickets sit in the same flat directory as the 155 open, and **217 of 223 still hold a row
in `TASKS.md` — 476 KB**, read by every session to orient. The estate already solved exactly this
for `STATE.md` ([[T174]]: bounded 900 lines / 80 KiB, enforced, after measuring ~83k tokens/session
of which 93.9% was dated history) and never generalised it to the board.

## 2026-08-27 — `/tasks` now sees a blocker that lives in an acceptance criterion

Owner: *"it looks like we have to add into /tasks proper blocking detection for both hot and sdlc
boards."* Raised after T198 and T228 both showed `Blocked by: —` while their ACs plainly named
blockers.

**The mechanism existed and nobody fed it.** `blocked_by:` is a DECLARED frontmatter field, and
`_blocked_by`'s own docstring says T173 added it because *"this relationship lived in PROSE where no
board could see it."* Measured 2026-08-27: **2** open tickets carry the field; **29** state a

⇒ Both boards now read **both** sources. The inference is narrow on purpose — all four must hold:

1. the AC is **unticked** — a met criterion cannot block;
2. it names another ticket as `[[T…]]`;
3. **that same AC** uses blocking language;
4. the named ticket is **itself open**.

A loose scan of whole ticket bodies returns **28 of ~190** open tickets, many merely discussing
other work; a board that calls half the queue blocked is one nobody believes. This returns **15**,
and the two independently-known cases land exactly — **T198 → T117/T200** and **T22 → T8**, the
latter matching the only real declared field in the corpus.

🔑 **Rule 4 is what keeps it true without maintenance.** T284's AC says *"[[T283]] must land
first"*; T283 closing earlier today removed the block with nobody editing the AC.

**Both boards, differently.** `sdlc` shows 🔴 declared and 🟠 inferred **distinctly**, because a
field someone wrote and a phrase someone's tooling read are different claims and the reader is
entitled to know which. `hot` applies `BLOCKED_BY_WEIGHT = -35`: that board answers *what can be
STARTED*, and an open blocker is the most direct possible answer of *not this*. Until now only

acceptance criteria owned by unbuilt work in other tickets while sitting at the top of the board

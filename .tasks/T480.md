# T480 — Gauge e2e: fail fast, then parallel

## Summary

Owner, 2026-09-28, during [[T478]]'s local regression: *"why so long??"*, then *"file a ticket for parallel
gauge runs and detecting long waiting unexpected pauses to fail early"*.

Measured on T478 run 1 (`just e2e-local`, 148 specs, 470 scenarios, 38.8 min wall):

- **70% of the time was spent in FAILED scenarios: 27.1 min, against 11.5 min for passing ones.** A failing step
  waits out its full timeout instead of recognising a state it can never leave.
- **10 specs took 36% of the run, every one failing.** `ext/linkedin_scraping` sat 181 s on a Chromium extension
  launch timeout; `web/goldens` spent 140 s on 30 screenshot mismatches.
- **Timeouts are ad hoc:** step waits of 5 s, 10 s, 15 s, 30 s, 45 s and 180 s, plus **83 fixed
  `waitForTimeout` sleeps** in `tests/` that cost their full duration on every run, pass or fail.
- **Everything is serial:** `enable_multithreading = false` (`env/local/default.properties:48`), a fresh Chromium
  per scenario. A clean serial run would still be about 470 × 1.5 s of real work plus browser start: 11–12 min.

The dominant wait in T478 was a known-bad state, not slowness: every CP step waited its full timeout on a page
that had already redirected to `/login` "Session expired", or to web's 404. The page said so within a second.

## Acceptance criteria

- [ ] AC1 — **A step fails as soon as the page is in a state it cannot recover from.** One check after each
  navigation and before each wait: the URL is `/login?…` or `/me/account?mfa_required=1` when the step needs a
  session, the response is 404/5xx, or the page shows the app's error page. The failure names the state
  ("redirected to /login: Session expired") instead of `locator.waitFor: Timeout 10000ms exceeded`. Measured
  by rerunning T478 run 1's failing set: time in failed scenarios drops by at least half.
- [ ] AC2 — **Fixed sleeps are replaced by conditions.** Each of the 83 `waitForTimeout` calls becomes a wait
  for the thing it was waiting for (a response, a selector, `networkidle`), or is deleted with the reason it was
  unneeded. A lint (`just sg-scan` rule) fails on a new `waitForTimeout` without a written reason.
- [ ] AC3 — **One timeout policy, not six.** Step and navigation timeouts come from one place, sized to the
  local stack (and separately to live), and a wait longer than the policy must say why in the step.
- [ ] AC4 — **A stalled run is detected and stopped.** A watchdog fails the suite when no step completes for N
  minutes (the default derived from AC3's largest timeout), naming the spec and step it stalled in, so a hang
  (the 180 s extension launch, a dev server that died) stops the run instead of silently eating it.
- [ ] AC5 — **Environment preconditions fail the whole suite once, up front.** If the test team cannot sign in,
  the functions are not served, or the live guard fails, the suite stops before the first spec with that one
  reason. Not 164 scenarios each rediscovering it (T478 run 1).
- [ ] AC5b — **A dev server broken mid-run stops the suite.** Measured 2026-09-28 (T478 run 3): a `git push`
  from wom7web mid-run ran the pre-push typecheck, which rewrote `apps/*/node_modules/.vite`; the running CP dev
  server then answered every SSR request 500 `The file does not exist at …/.vite/deps_ssr…`, and ~60 scenarios
  failed as "sign-in failed (500)" before anyone noticed. The runner watches the dev-server responses for that
  signature (and any 5xx from `/api/auth/*`) and aborts with one message naming it, and `e2e-local` refuses to
  start while a build/typecheck holds those caches.
- [ ] AC6 — **Specs run in parallel, safely.** Gauge `--parallel` with N workers, after proving the specs are
  independent: the shared local database, the one provisioned test team, fixed-address fixtures
  (`dup@example.com`, …), the single `@AfterSuite` teardown (it must run once, after every worker), and state that
  specs create and assert on. Specs that cannot be made independent are tagged and run serially after the rest.
  Measured: three consecutive parallel runs give the same pass/fail set as a serial run.
- [ ] AC7 — **Measured result:** a clean local full run in under 5 minutes, timings recorded here.

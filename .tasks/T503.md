# T503 — a red gate must never arrive after the thing it guards

## Summary

Owner report (2026-09-30): "deploy failed! we have to look into the reasons why and develop permanent fixes for deployment flow."

**What happened (deploy log `deploy-logs/run-2026.09.30-1790751069.log`).** `just deploy-all` confirmed (Touch ID), ran `db-migrate` (two migrations applied to the LIVE database), then `deploy`, whose first real step is the 211-suite test tier. Five blocking suites failed: `py-test`, `spec-standard-gate`, `state`, `ac-recipe-check`, `ds-conformance-selftest`. Nothing was deployed, but the schema was already ahead of the code. The same shape happened on 2026-09-29.

**Two root causes, only one of which is a bug in a suite.**

1. **Structural (the important one).** `_deploy-all-chain` was `check-warp check-infisical db-migrate deploy`, and the gates (`check-guardrails`, `test`, `goldens`) sat INSIDE `deploy`. So the schema write ran before any test. A gate that can only fail after the irreversible step is a report, not a gate. The gates were not even in the chain's dependency graph.
2. **Detection latency.** The four ratchets that failed each take under a second, but they only ran inside the 8-minute deploy gate, after a release cut and a Touch ID. Pre-push ran none of them; the umbrella repo has no pre-push hook at all, so a ticket edit there was checked for the first time inside the deploy.

**The five failures, each measured and fixed:**

| Suite | Cause | Fix |
|---|---|---|
| `spec-standard-gate` | non-conforming requirements rose 72 to 74: two T498 requirements had no `**Feature:**` block | added the blocks (back to 72) |
| `ac-recipe-check` | ticked T499 AC1 cited `just cv-facts-load-live`, deleted by AC5 | reworded in italics |
| `ds-conformance-selftest` and `py-test` | native `<button>` count 405 > baseline 392 (+13): Resume Studio used native buttons | all 20 converted to the DS `Button` (count now below baseline); 70 Studio tests still pass |
| `state` | STATE.md 25 commits behind HEAD (limit 10); pre-push runs `state-check` only when tracking files are touched, so code-only pushes never tripped it | `just state-save`; the deploy pre-flight now runs it |

## Permanent fixes

1. **Order.** `_deploy-chain` and `_deploy-all-chain` are now `_deploy-preflight`, then the confirmation, then `_deploy-gates` (infisical, guardrails, the whole offline tier, goldens; writes nothing live), then `db-migrate` (deploy-all only), then `_deploy-ship` (apps, smoke, clean-tree, deploy log). `scripts/tests/test_deploy_chain_order.py` reads the real recipe graph from `just --dump`, asserts every gate precedes `db-migrate`, that gates write nothing live, that both chains share one `_deploy-gates`, that the ratchets run before the confirmation, and red-probes the old order.
2. **Fast tier.** `"prepush": true` in `project/test-suites.json` marks a deterministic, offline, blocking suite that finishes in about a second; `run_suites.py --prepush` runs exactly those (currently spec-standard, ac-recipe-check, ds-conformance). The tests reject a flagged suite that is live or advisory and cap the tier at 12. Pre-push (`deploy-ratchets` step) and the deploy pre-flight both call it, so they cannot drift.
3. **Pre-flight before Touch ID.** `_deploy-preflight` = the prepush tier plus `state-check`, run before the confirmation prompt.
4. **Umbrella.** A pre-commit hook runs `ac_recipe_check.py` on `.tasks/T*.md` edits (red-probed: a bad citation exits 1).
5. **A hook/registry drift found on the way.** Four pre-push steps (`authz-admin-client`, `route-policy`, `plan-set`, and `secret-flow`, which I added earlier) were never registered in `prepush_runner.py`, so their results were not checkpointed or shown by `status`. All registered; a new test asserts hook and registry agree in both directions.

## Definition of Done

- A red suite can no longer follow a live schema change: with any gate red, `deploy-all` stops before `db-migrate`.
- The four ratchets that failed on 2026-09-30 fail at `git push` (or commit, for tickets), in about a second.
- The next `just deploy-all` reaches the app deploys.

## Open questions (recommended answers)

1. **Rollback.** A migration applied and then a later ship step failing (an app deploy, the smoke test) still leaves the schema ahead. Recommend: keep migrations additive and backward compatible (already the estate's practice), and have `_deploy-ship` print the applied migration versions on failure so a retry is `just release-deploy <version>` and not a new cut. Weight: low cost, no new machinery.
2. **`state-check` at every push.** It is 8 s and would block code-only pushes after 10 commits. Recommend leaving pre-push as is (conditional) and relying on the pre-flight. Weight: keeps pushes fast; the pre-flight catches it before any cost.

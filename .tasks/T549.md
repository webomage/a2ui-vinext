# T549 — suites-drift must resolve registered recipes the way the runner does

## Summary

The same mistake happened twice in three days, and the first time produced a written lesson (`LESSONS.md`, "A suite recipe must be visible from `wom7api/`", T531, 2026-10-04). On 2026-10-06 a second suite (`tools-upgrade`, T546) was registered with its recipe only in the root justfile. `just suites-drift` reported "265 declared, 0 undeclared" and the suite's own test passed, but the full `test` tier (`scripts/run_suites.py`, which resolves every recipe through `wom7api/justfile`, symlinked as `wom7web/justfile`) reported `🚫 0 check(s) recipe not found`, a blocking failure, at deploy time. Two readers of one registry resolved it differently, and the cheaper one is the one that runs in a push hook.

A second, related gap: a suite whose output has no `✅`/`❌` (or `[PASS]`, or a pytest/vitest summary) is counted as `?` checks. The runner has a "VACUOUS" notion, but the author sees it only in the full tier.

## Acceptance criteria

- [ ] AC1 — **Test first: a registered suite whose recipe does not resolve fails `suites-drift`.** The check resolves each registered recipe exactly as the runner does (`just --show <recipe>` with the runner's justfile and working directory) and reports the name, the registry entry and the justfile searched. A mutation test: remove a recipe from `wom7api/justfile` while leaving the registry entry, and the check fails; the unmutated tree passes. It must not itself read the root justfile.
- [ ] AC2 — **It runs where the change is made.** `suites-drift` (or the new check) is in the pre-push fast tier (`"prepush": true`, offline, blocking, about a second), so the mistake is caught at push, not at deploy.
- [ ] AC3 — **A suite that counts no checks is visible at registration.** Registering a suite whose sample output yields no countable lines is reported by the same check (advisory with a reason, or blocking for a new suite), naming the three accepted dialects. Record the decision here.

# T207 — reorganise the admin CP and adopt the design system, together

## Summary

Owner, 2026-08-13: *"we plan to incorporate properly design-system and reorganise admin cp."*

**Both are right, and the argument of this ticket is that they are ONE pass with the capability work,
not three.** All three touch the same **56 `apps/cp` pages** and ~50 admin components, and the
taxonomy each needs is the same taxonomy. Doing them separately means editing those pages three times
and — the measured part — **letting the navigation and the access policy disagree.**

## ✅ RESOLVED BY AC1 — the drift was not hypothetical. There were TWO whitelists.

Measured 2026-08-13, **fixed the same day**; kept here because it is the evidence for doing this as
one pass:

| source | entries |
|---|---|
| `apps/cp/src/middleware.ts:7-13` → `MEMBER_WHITELIST` (the **access** decision) | **13** |
| `apps/cp/src/layouts/AdminLayout.astro:147-154` → `cpMemberWhitelist` (the **navigation** filter) | **6** (4 internal) |

They disagree, and the consequence is concrete: **three pages a member is allowed to reach are never
shown to them.**

⚠️ **And the three were NOT the same defect** — a distinction the first draft of this ticket got
wrong and AC1's measurement corrected:

```
/guild/bounties          IN navGroups · middleware allows · the member FILTER dropped it
                         ⇒ admins saw it, members could open it and never saw the link
/guild/units             NOT IN navGroups AT ALL · middleware allows
/guild/certifications    NOT IN navGroups AT ALL · middleware allows
                         ⇒ invisible to EVERYONE, admins included
```

⇒ Only the first was a whitelist-disagreement. The other two were missing from the information
architecture entirely, which no amount of unifying whitelists would have surfaced — **the coverage
check is what found them.**

⚠️ Plus the `/cp/*` aliases (`/cp/profile`, `/cp/team/people`, …) which the middleware names and the
nav does not — those are probably deliberate path aliases, but nothing says so.

🔑 **This is the whole case for doing it as one pass.** Two hand-maintained lists of the same fact, in
two files, already out of step. A reorganisation that rewrites the nav without collapsing them will
recreate this on a bigger surface.

## 🔴 And the nav cannot express the capability model Phase 1 is building

`AdminLayout.astro:158` is:

```ts
if (role === "admin") return group;          // admins see everything
// otherwise: keep only items in cpMemberWhitelist
```

⇒ **The nav is role-binary, not capability-aware.** It has no way to say *"show Invoices to whoever
holds `invoice.view`"*. [[T117]] task 0.4 (done 2026-08-13) maps the 45 admin pages onto capability
domains; **the nav is the surface that has to consume that map**, and today it structurally cannot.

⚠️ Note in its favour: the **route** layer is already hat-scoped (`defineAbilityFor(activeRole)` reads
`wom_active_role`), so the nav is the *only* part of the CP still deciding on a role name.

## 📊 Coverage: the nav does not reach the app

| measure | value |
|---|---|
| `.astro` pages in `apps/cp/src/pages` | **56** |
| items in `navGroups` | **34** |
| pages in the `admin-console` catch-all ([[T117]] 0.4) | **45 (80%)** |

⇒ Roughly **22 pages are not reachable from the navigation at all.** Some are legitimately
deep-linked (`/business/blueprints/edit/[id]`), but that has never been separated from "forgotten".

## 🔬 Design-system conformance: adoption tripled and conformance got WORSE

Re-measured 2026-08-13 against `design-system/CP-CONFORMANCE-GAP-2026-07-16.md`:

| metric | 2026-07-16 | 2026-08-13 | direction |
|---|---:|---:|---|
| files importing `@webomage/ui` | 7 | **23** | 🟢 tripled |
| native `<select>` | 25 f / 53 u | 24 f / **52 u** | ⬄ unchanged |
| native `<input>` | 49 f / 143 u | 48 f / **142 u** | ⬄ unchanged |
| native `<button>` | 66 f / 365 u | 66 f / **358 u** | ⬄ unchanged |
| hardcoded `#0a84ff` | 119 | **175** | 🔴 **worse** |
| hardcoded hex, total | — | **782 across 77 distinct** | 🔴 |

🔑 **That combination is the finding, and it reframes the work.** The July report's headline was
*"the CP is ~85% off the DS — only 7 of ~50 components import it"*. Import count is no longer the
problem: it tripled. **New code imports the DS component AND still hardcodes the colour.**
⇒ **Adopting a component is not adopting the token.** A plan measured by "files importing
`@webomage/ui`" would have declared progress while the palette fragmented further — 77 distinct
hardcoded hex values is more theme surface than the DS defines.

⚠️ Per the header-UI golden rule the target is `rgb(var(--brand-rgb) / <a>)`, never inline hex —
the same rule an earlier ticket had to establish twice.

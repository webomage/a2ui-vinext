# T304 — a gate that cannot reach the database must not say the database is misconfigured

## Why

Three times on 2026-09-02 a push was refused with:

```
❌ Push blocked: an authorization probe is RED.
```

Not once was an authorization claim violated. The three causes were an **expired Infisical session**,
an **organization mismatch** (`403 — This project does not belong to your selected organization`), and
**no session at all**, where the CLI then tried to open a browser from inside a git hook and died on
`inappropriate ioctl for device`. Each is a credential problem. All three printed the sentence the
estate reserves for a security finding.

🔴 **This is [[T242]]'s defect in a place T242 did not reach.** That ticket split the probe verdict into
three states — measured-clean, measured-violating, **UNMEASURED** — and made UNMEASURED fail closed
while saying which of the two happened. That machinery is real and lives in
`project/scripts/authz_probe_suite.py`. It never runs here, because the process is already dead:

```python
# project/scripts/authz_probe.py:29
if p.returncode != 0:
    sys.stderr.write(p.stderr[-3000:])
    raise SystemExit(f"psql failed rc={p.returncode}")
```

`run_sql()` wraps `infisical run --env=beta -- psql "$DATABASE_URL" …`, so a **non-zero exit means any
of**: infisical could not authenticate, infisical authenticated into the wrong org, psql could not
reach the host, or the SQL itself failed. One `SystemExit` for all four, raised **beneath** the layer
that knows how to report unmeasurable. T242 fixed the verdict; nothing fixed the acquisition.

⚠️ **The cost is not cosmetic.** A gate that cries security for a login problem is a gate people learn
to route around, and `--no-verify` is prohibited here precisely so that never becomes the habit. It
also inverts the estate's own rule: *"could not measure" and "found a violation" must not print the
same word.*

## Acceptance criteria

- [x] **AC1** — `run_sql()` distinguishes **could not acquire credentials** / **could not reach the
      database** / **the query failed** and returns that state instead of raising `SystemExit`, so the
      suite's existing UNMEASURED path is what reports it.
- [x] **AC2** — the push hook's message names the actual cause. A credential failure must not print
      "an authorization probe is RED"; it should say the session is missing or in the wrong org, and
      name the command that fixes it.
- [x] **AC3** — still **fails closed**. Unmeasurable blocks the push exactly as before; only the words
      change. A gate that fails open on a credential error is a worse bug than this one.
- [x] **AC4** — red-tested against all three causes observed today: no session, wrong org, and a
      reachable-but-failing query. Each must produce its own message, and the authorization-violation
      wording must appear **only** for the third.
- [x] **AC5** — the hook detects that it cannot complete an interactive login (no TTY) and says so,
      rather than emitting `inappropriate ioctl for device` from a browser flow that can never work
      inside `git push`.

## What shipped

🔑 **The bug was narrower than the ticket assumed, and finding that mattered.** The probe loop has
been protected since [[T242]] — retry, then `except SystemExit` → UNMEASURED. What was unguarded is
`build()`, which resolves live ids with a `run_sql` **before any probe runs**. So the process died at
setup, one layer beneath the machinery built for exactly this, and no probe had executed when the
push was refused as a finding.

- `authz_probe.py` classifies a failure as **credentials / connection / query** and raises
  `SqlUnavailable`. 🔑 It subclasses `SystemExit` **deliberately**: `run_sql` has a dozen callers
  across the authz gates and every one relies on an uncaught failure ending the process cleanly with
  a non-zero code. Subclassing keeps that exactly true while letting the suite catch it.
- `authz_probe_suite.py` guards `build()` and gives could-not-measure its **own exit code, 3**.
  RED stays 1. Both block.
- `.husky/pre-push` branches on the code, so a credential failure no longer prints the sentence
  reserved for a security finding.
- `just authz-unavailable-test` — 9 offline probes, registered in `test-suites.json`.

**Verified, not argued:**

| check | result |
|---|---|
| live suite still green | 0 RED of 18, exit 0 |
| credentials unavailable, `--enforce` | **exit 3**, prints the cause + the fixing command |
| hook branch on 3 / 1 / 0 | "could not run" / "is RED" / passes — both failures exit 1 |
| mutation: credential markers emptied | test drops to **5/9, exit 1** — the original bug caught |

⚠️ **The first mutation I tried did not fail**, because the org-mismatch capture also matches
"could not fetch secrets". Redundant markers are good; a mutation that proves nothing is not. The
recorded one empties the list entirely.

## Definition of Done

A push refused by the authorization gate tells the truth about why. A missing or misdirected
credential is reported as an inability to measure, in words that name the credential and the command
that restores it; an authorization violation is reported as a violation; and no reader has to open a
log to tell which happened. Both still block the push, because failing closed is the property worth
keeping. The distinction has been observed for every cause seen in the field rather than argued from
the code, including the case where the gate runs without a terminal and cannot log in at all.

## Notes, traps and dependencies

The vault backend is implicated and may be the reason the session is absent inside a hook at all:
`infisical vault` reports **`auto`** (system keyring), and a git hook runs without a TTY and often
without keychain access. `infisical vault set file` moves the token to an encrypted file the hook can
read. That is a credential-storage decision for the owner, not part of this fix, but AC5's message
should mention it — a gate that explains the fix is worth more than one that only reports the failure.

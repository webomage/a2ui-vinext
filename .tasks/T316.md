# T316 — Move skills/tools installation one level up to the workspace root

## Summary

Owner, 2026-09-05: *"I'm actually thinking that we should move most of w0m automation and
skills/tools to the level of workspace so move tools one level up to not pollute repos and also to
feel safe for half-managed or client's self-managed repos"* — plus a naming complaint about
`wom7skills/portability.jsonc`: *"not sure how portability.jsonc naming good enough because it's
not sounds like client-skillset.jsonc or something like that."*

**This is not a new idea — it is [[T294]]'s own direction, only half-executed.** T294 quotes the
owner on 2026-09-01: *"for managed projects we should support our stack and tools to be installed
and integrated one level up from app code repos… meanwhile we can create there also repo but own it
in our GH org separately per project."* T294 built exactly that for **one** surface — the
`.w0m/sdlc.json` contract — by making the workspace root itself a repo w0m owns (`bridgeroad-w0m`,
per [[T242]]'s `<slug>-w0m` naming schema). It explicitly did not touch **where skills/tools get
installed**; its own text says *"workspace mode itself... do not rebuild... this ticket is
adoption, not new capability."*

**Measured today, live, and both findings are current as of this filing:**
- `bridgeroad-w0m` (`/Users/proto/Projects/_proj/bridgeroad`) — the repo that exists *for* this
  exact purpose — has `.w0m/{README.md,sdlc.json}` but **no `.agents/skills` and no
  `.claude/skills` at all**. `wom7skills/scripts/install_generic.ts` (`just
  skills-install-generic`, upgraded under [[T312]] to write both paths) has never been pointed at
  it, despite it being the one repo in this client's tree that w0m is safe to write into.
- `wom7skills/portability.jsonc` is a single, global **skill-classification registry** (15
  portable / 18 w0m-bound skills, `counts` measured 2026-08-16) — not a per-client manifest. Its
  name doesn't say *what* it classifies (skills) or *for whom* (every client, universally, the
  opposite of a manifest scoped to one), and a fresh reader's first guess reached for something
  else.

⚠️ **A related observation did NOT hold up on re-check and is recorded, not acted on.** Earlier in
this same research pass, `BridgeMvp` (the client's own third-party-org app repo, nested inside
`bridgeroad-w0m`) appeared to carry an unexplained root-level `skills/` directory. Re-measured
immediately before filing this ticket: **it is gone** — `ls` returns "No such file or directory".
Something touched that path between the two checks, or the first observation was itself a
transient state; either way, asserting it as a present finding would be exactly the stale-claim
failure [[T242]] itself documents twice (the "webomage is a User" finding, the authz-probe
false-positive). No AC is built on it. If it recurs, it belongs to AC4 below.

## Acceptance criteria

- [ ] AC1 — **Rename `portability.jsonc` to something that says what it holds.** Owner decides
      among (or names another): `skill-portability.jsonc` (smallest edit, still ties to the
      `NOW-PORTABLE`/`NOW-BOUND` vocabulary `install_generic.ts` already prints), `skills-
      classification.jsonc` (matches its actual shape — `counts` + `portable{}` + `w0m_bound{}` —
      more literally than "portability" does), or `skill-eligibility.jsonc` (plainest language,
      weakest on scope). Whichever is chosen, update **every reader in the same change** —
      `install_generic.ts`, its own header comment, `GENERIC-SDLC-SET.md`, and any doc that names
      the file by path — a rename that misses a reader is a silent break, not a rename. The file's
      own governing rule survives the rename unchanged: *"a skill's portability is a property of
      its CONTENT, never of its name"* (T110's finding, itself an echo of [[T192]]'s "identify a
      thing by its content, never by its name").
- [ ] AC2 — **Run the generic installer against `bridgeroad-w0m` itself, not a repo under it.**
      Close the concrete gap measured above: `.agents/skills` and `.claude/skills` populated at
      the workspace root, nothing written into `BridgeMvp`. This is the specific, current instance
      of [[T265]] AC8's "no write to a project we do not own" — BridgeMvp is a third-party org's
      repo, `bridgeroad-w0m` is ours.
- [ ] AC3 — **A mechanical guard, not a habit, stops the installer writing into a client-owned
      path.** For any project declared in `clients-policy.json` with a `repos` key (workspace
      shape), `install_generic.ts` must refuse — the same way it already refuses on scope mismatch
      or a pre-existing `.w0m/sdlc.json` without `--force` — when its target resolves to one of
      that project's declared `repos` entries rather than the workspace root / `canonical_repo`.
      Red-test it: point the installer at `BridgeMvp` (or a fixture shaped like it) and assert a
      refusal, mirroring how AC5 of [[T110]] proved the *existing* refusals by running them against
      real repos rather than describing them.
- [ ] AC4 — **Write a decision (not a migration) on hoisting w0m's OWN anchor.** Now that `w0m`
      (the estate workspace) is itself a repo ([[T294]] AC2), name which of w0m's own
      automation/config currently anchored inside a component repo is a candidate to move to the
      `w0m` workspace repo instead, and which is not. State the concrete counter-example already
      found: `wom7api/scripts/supabase_limits.py:42` hardcodes
      `API.parent / "wom7web" / ".w0m" / "sdlc.json"` — an assumption that the estate contract
      lives inside `wom7web` specifically, one of several such assumptions this AC must inventory
      before any move is proposed. This AC's output is a written decision document; the move
      itself, if approved, is separate follow-on work scoped only after the tradeoffs are named —
      an unscoped rearchitecture is not what was asked for.

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
`portability.jsonc` carries its new name with zero remaining references to the old one (`grep -r
portability.jsonc` clean outside git history); `bridgeroad-w0m` carries live, populated
`.agents/skills` and `.claude/skills` at its own root while `BridgeMvp` remains untouched by the
installer, proven by an actual run, not a description of one; the client-owned-path guard is
red-tested against a real or fixture repo shaped like `BridgeMvp` and passes; and the workspace-
anchoring decision document exists, names `supabase_limits.py:42` and any other hardcoded
component-repo assumption found, and states a clear yes/no per candidate rather than leaving the
question open.

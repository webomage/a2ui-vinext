# T239 — one field has no vocabulary, and it is the one that drifted

## Summary

Owner 2026-08-20: *"let's actually check what GH have for prios, labels, etc to look if we should
align our tickets schema a bit against GH schemas."* Measured after [[T228]] AC5/AC5b put Status,
Priority, Area and Epic on the board as fields.

🔴 **`epic` is the only required field that names a closed set in reality and carries no
vocabulary — and it is the only one that drifted.**

| required field | vocabulary | outcome |
|---|---|---|
| `status` `area` `priority` `repos` `queue` | ✅ declared | clean enums, projected as fields |
| `id` `title` `spec` `gh_issue` `created` `tags` | — | genuinely free-form; fine |
| **`epic`** | 🔴 **none — free text** | **72 spellings for 33 sections** |

**Measured: 187 tickets carry an epic, in 72 distinct spellings, collapsing to 35 `§N` — a 2.1×
drift factor.** §13 alone is written **17 ways**:

```
23  ROADMAP §13                     6  ROADMAP §13.2
15  ROADMAP §13 — platform tooling  5  ROADMAP §13 — SDLC platform
15  ROADMAP §13.1                   4  ROADMAP §13 — platform tooling (child of T149)
12  ROADMAP §13 — platform tooling & infra   … and 10 more
```

🔑 **The vocabulary already exists and is clean.** `ROADMAP.md` declares **exactly §1–§33, no
gaps** — enumerable, closed, and sitting undeclared while the field that points at it is free text.
✅ No ticket references a section that does not exist; the drift is **spelling, not invention**,
which makes it mechanically fixable. **8 tickets** use a non-`§N` epic (`Audit 2026-07-17`,
`security / config hygiene`) — those need a disposition, not a rename.

## What GitHub offers that we do not use

| GitHub primitive | state | our equivalent |
|---|---|---|
| **Milestones** | 🔴 **0 defined** | `epic` — free text, 72 spellings |
| **Issue types** (`type`) | 🔴 `null` on every issue | **nothing** — we have no type/kind field at all |
| Sub-issues | ✅ now in use (T228 AC6) | batch tables |
| Projects v2 fields | ✅ now in use (T228 AC5) | status/priority/area/epic |
| Labels | ✅ in use | `repo:`, `P0-P3` |

📌 **Milestones are the native primitive for exactly what `epic` is**: enumerable, closable, with
progress, and reconcilable the way `sync_github.py` already reconciles labels. A milestone cannot be
spelled 17 ways — that is the whole point of it being an object rather than a string.

      **reference**, never as containment.
      **② The membership rule, because the two live cases genuinely differ.** ⚠️ I nearly picked one
      direction for both and it would have been forcing it:
      · **Plan stages → membership is PLAN-SIDE.** What is in the closed beta is a *decision about
        scope*, made centrally, and it must be reviewable as a whole in one diff.
        `current_plan.stages[].tickets` already does this.
      · **`Audit 2026-07-17` → membership is TICKET-SIDE.** That a ticket came out of that audit is a

      🔑 **The distinguishing principle, stated so it is decidable next time: is membership a DECISION
      about scope, or a FACT about origin?** A decision belongs where it can be reviewed whole; a fact
      belongs on the thing it is true of. The schema declares which per milestone
      (`membership: "declared" | "derived"`), so both are supported and neither is guessed.
      ⚠️ Ticket-side needs an **OPTIONAL** `milestone:` key — optional is load-bearing, because
      `template_keys()` makes every template key required and adding a required one is the edit that
      turned **227 tickets red** in a single commit under [[T228]].
      **③ Two mechanisms mean two ways to be wrong, so AC5's gate must cover both:** a milestone whose
      `membership: declared` list names a ticket that does not exist; a ticket naming a milestone that
      is not declared; and a milestone using **both** directions at once. ⚠️ Also report a declared
      milestone with **zero** members — an empty bucket reads as organisation while classifying
      nothing, which is exactly what §13 at 56% already demonstrates one axis over.

## 2026-08-20 — the GitHub issue schema, measured against THIS account

### 🔑 The finding that governs every other one

**Introspection is not an availability check.** `Issue` exposes **79 readable fields**, and the
schema fully describes `issueTypes`, `issueFields` and `createIssueType` — **all of which are `null`
or unusable here, because the owner is a `User`, not an `Organization`.** The GraphQL schema
advertises everything the API can *ever* do for *any* account. This is the estate's recorded shape
again — **a thing identified by its name rather than its content** — and it is how AC4 acquired a
false premise. ⇒ **Probe the account; never read capability off a schema dump.**

### ✅ AC7 — `stateReason`: DONE 2026-08-20

GitHub carries a first-class close reason, writable, and it was already being filled for us:

    COMPLETED · NOT_PLANNED · DUPLICATE · REOPENED

**`sync_github.py` never mentioned `stateReason`, so GitHub DEFAULTED every close to `COMPLETED` —
all 76 closed issues read `COMPLETED`.** Not an empty field: **an unverified claim published 76
times**, and a false *present* is worse than a false *missing*.

🔬 **A correction I owe this ticket.** I first wrote that *"T27 and T62 were re-scoped and T91/T92/T93
supersede T42, so those closed as NOT_PLANNED"* — and repeated it in two commit messages. **It was
wrong: none of those three is closed.** T27 and T62 are `queued`, T42 is `in-progress`, so they were
never among the 76 at all. I read their RE-SCOPED/supersede prose and never checked the one field
that decides membership. **Asserting a fact about a ticket without reading its `status` is the same
error this ticket exists to fix**, committed while fixing it.

**What the corpus actually supports — 2 of 76, not a sweep.** A keyword search for
supersede/re-scoped/duplicate/abandoned matched **19** closed tickets; spot-checking put its
precision near **1 in 5**. T202's *"replaced by"* is an auth flow, T119's *"superseded"* is four
Upwork keys, T130's *"duplicate of"* is debt row D24, T110's *"abandoned"* is a rejected design, and
T151/T174 describe **other tickets'** closes (T107 and T124). Only two survive on their own text:

| ticket | issue | reason | its own words |
|---|---|---|---|
| [[T107]] | #132 | `not-planned` | *"closed as **not reproducible with evidence**, not as \"we fixed it\""* |
| [[T211]] | #208 | `duplicate` | *"**CLOSED AS A DUPLICATE of [[T209]]**"*, stated twice |

⇒ **The other 74 stay unstated rather than guessed.** Fabricating 74 dispositions to make a counter
look complete is precisely the false *present* being removed.

**What shipped:**
- `closed_as` in `tickets-schema.jsonc` — `completed | not-planned | duplicate`, **`closed: true`**,
  with the `gh_reason` mapping as **DATA** so the projection cannot drift from the vocabulary the way
  `area:` did. ⚠️ The CLI takes `"not planned"` **with a space** — a value, not an identifier.
- **OPTIONAL** in the template, deliberately: `template_keys()` makes every template key required,
  and requiring this would have reddened 74 closed tickets in one edit — the un-passable gate
  [[T135]] AC8 forbids.
- Validation in `ticket_schema_check.py`: an unmappable value **errors**; a value on an **open**
  ticket errors (it claims an event that has not happened); **absence is silent**.
  🔴 Needed because a declared vocabulary is **not self-enforcing** — this checker validates field by
  field, so `"vocabulary": "closed_as"` in the schema bought nothing until a consumer read it.
- `sync_github.py` passes `--reason` on close, **and reconciles an already-closed issue whose reason
  disagrees** (via `updateIssue`, since `gh issue close` will not re-close). Without that second
  branch, declaring `closed_as` on any of the 76 already-closed tickets was a silent no-op.
  ⚠️ It fires **only when the ticket declares one**: absence must never overwrite a live value.
- **10 new probes** (**59 checks**, was 49), including that an undeclared ticket projects `None` and
  never `completed`.

🔬 **Two traps hit while building this, both already documented in the code I was editing.**
① The projection first emitted `reason: None` for every ticket, which changed **all 235 hashes** and
made a dry run demand **235 API updates to say nothing new**; the key is now omitted when
undeclared, so the other 234 projections stay byte-identical. ② `closed_as` reached neither GitHub
nor the hash at first, because **`load_tickets()` whitelists fields** and I had not added it — the
exact `area` failure whose post-mortem sits 12 lines above the line I needed to change
(*"adding the namespace to the schema alone produced ZERO labels — the dry run caught it"*). It
caught it again. **A field is not wired until the LOADER carries it.**

**Verified via the API, not the tool's output:** #132 `NOT_PLANNED`, #208 `DUPLICATE`, and the
distribution moved **76 COMPLETED → 74 COMPLETED / 1 NOT_PLANNED / 1 DUPLICATE**.

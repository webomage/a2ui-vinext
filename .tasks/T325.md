# T325 — Attribute contracts to clients, and link client orgs to users

## Summary

Measured live on 2026-09-07 (PostgREST, `Prefer: count=exact`, service role):

| table | rows | attributed | note |
| --- | --- | --- | --- |
| `contracts` | 98 | **3 with a non-null `client_id`** | all 3 `status: active` |
| `projects` | 7 | 7 | attribution here is complete |
| `clients` | 10 | — | 10 client organisations |
| `client_users` | **2** | — | so **8 of 10 orgs have no user who can sign in** |

The portal itself is READY — `just authz-probe` is 18/18 green including the cross-client A2 case,
all four `/client/*` pages use the user-scoped `getSupabaseServerClient(Astro)`, and one client has
completed the funnel end to end (registered 2026-08-24, signed in 2026-08-25). **What is missing is
the data, not the mechanism.** Row-level isolation over an unattributed table returns an empty page
that is technically correct and useless: a client signs in and sees nothing, because nothing points
at them.

**The sharpest instance, and the one worth reading first:** the org "BridgeRoad" holds one of the
three attributed **active** contracts and has **no `client_users` row**. There is a live contract
with a portal page rendering it and nobody who can reach it.

This is why "projects management is not ready" while every dimension of the audit came back READY.
The verdict belongs to the data graph.

⚠️ **Scope discipline.** Backfilling 95 contracts is a judgement call per row — some are legacy,
some are Upwork-sourced with no `clients` counterpart, some may genuinely have no client. This
ticket is NOT "set `client_id` on 95 rows". It is: decide the rule, apply it where the rule decides,
and make the unattributable rows explicitly unattributable rather than indistinguishable from
un-processed ones. A `NULL` that means "no client exists" and a `NULL` that means "nobody has looked
yet" must stop being the same value.

## Acceptance criteria

- [x] AC1 — Every one of the 98 contracts is classified into exactly one of: attributed to a
      `clients` row · deliberately client-less (with the reason recorded) · blocked pending a
      decision (with the blocker named). Counts published; the three buckets sum to 98.
- [x] AC2 — The distinction from AC1 is readable **in the schema**, not only in a report — so a
      future query can tell "no client" from "not yet reviewed" without re-deriving it.
- [x] AC3 — Every `clients` row that owns at least one `active` contract has a `client_users` row,
      OR is recorded as intentionally portal-less with the reason. BridgeRoad is resolved either way
      and named explicitly in the closing note.
- [x] AC4 — A check reports contracts whose `client_id` is unset while an attributable client exists,
      and orgs with active contracts but no linked user. It must FAIL CLOSED when it cannot read
      (T242): "could not measure" gets its own state, distinct from "found none".
- [x] AC5 — Any linking of a client org to a user goes through a **migration or the
      `client-register` function**, never a dashboard or SQL-editor write. State the mechanism used
      in the closing note.
- [x] AC6 — Re-run `just authz-probe` after the backfill and confirm still 18/18, specifically that
      A2 (cross-client read) stays green now that there is real cross-client data to leak. Newly
      attributed rows are the first genuine test of that boundary.

## Definition of Done

Every one of the 98 `contracts` rows carries a schema-readable attribution state (not just a
report saying so), the three bucket counts are published and sum to 98, BridgeRoad is resolved
one way or the other and the resolution is traceable to a migration or `client-register` (never a
manual write), a fail-closed drift check exists so this doesn't silently re-decay, and
`just authz-probe` is re-confirmed 18/18 — including A2 — against real cross-client data rather
than the near-empty table every prior green result was measured on.

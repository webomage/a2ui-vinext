## 2026-08-28 — the code this ticket generalises FROM, measured

Started T94 by reading the artefacts its ACs are grounded in. Three of them differ from how the
ACs describe them, and one was a live gap that is now closed.

### 🔴 AC3's premise does not hold — there is much less to generalise than it says

AC3 calls the ATS factory *"clean"* and names five capabilities to generalise:
`connect/auth`, `sync`, `profileSync`, `handleWebhook`, `status`. Measured, `AtsConnector`
(`wom7cfworkers/src/services/ats/types.ts`) has **two methods** and **none of the five**:

```ts
export interface AtsConnector {
    fetchVacancies(): Promise<AtsVacancy[]>;
    submitCandidate(payload: AtsCandidatePayload): Promise<AtsSubmissionResult>;
}
```

`factory.ts` selects an implementation from **`env.ATS_PROVIDER`** and defaults to Merge;
`huntflow.ts` authenticates with a **static env token** (`HUNTFLOW_API_TOKEN`) read in its
constructor. So: no connect flow, no token store, no refresh, no webhook, no status, no
profileSync.

⇒ **The keying is the real gap, not the method count.** The factory is a singleton per
*deployment* — one ATS for the whole worker — while AC5 wants a registry keyed to the **person**.
A per-person, per-connection registry is not an extension of a global env switch; the two answer
different questions, and "generalize the existing factory" reads as smaller work than it is.
The interface is a good *shape* to borrow. It is not a foundation to extend.

### 🔴 AC7 understates the coupling — the gateway's AUTH is Deel's, not just its dispatch

AC7 says *"replace the hardcoded `if (deel)` branch"*. That branch is real
(`platform-webhook-gateway/index.ts:77`), but it is the **last** of four Deel-shaped layers:

| line | what is Deel-specific |
|---|---|
| 10 | the CORS allow-list hardcodes `x-deel-signature` |
| 13, 50 | HMAC verification reads `x-deel-signature` |
| 45 | **one** `signingSecret` for all platforms |
| 77 | `if (platform === 'deel' && …)` — the dispatch branch AC7 names |

⇒ A second provider is **rejected at line 51 before reaching line 77**. GitHub signs with
`x-hub-signature-256`, Stripe with `Stripe-Signature` plus a timestamp; neither survives a
verifier that expects Deel's header and one shared secret. **Per-connector signature verification
is part of AC7, not a follow-on.**

### ✅ AC6 was FALSE for one of the two stores — fixed

AC6 states the rule as though it already holds: *"token columns stay revoked from
anon/authenticated."* Measured 2026-08-28:

```
social_integrations.access_token   anon revoked · authenticated revoked
upwork_auth_tokens.access_token    anon GRANTED · authenticated GRANTED
```

[[T99]]'s protection migration (`20260721120000_t99_protect_oauth_tokens.sql`) mentions
`upwork_auth_tokens` **zero times** — it established the column-GRANT posture, applied it to one
store, and the other was never brought under it.

⚠️ **Not a live leak, and the distinction is the point.** RLS is enabled with two policies and a
behavioural read as each role returns **0 rows**, so nothing is reachable today. What was missing is
the *second* layer — and the table's own admin policy is `[ALL] TO authenticated USING
(user_roles.role = 'admin')`, so an admin session can select plaintext tokens through PostgREST.
That possession-based arm is what [[T198]] AC6 is separately trying to remove; until it goes, the
column grant is the thing standing between an admin browser session and a working token.

⇒ `20260828010000_t94_protect_upwork_tokens.sql`. Dry-run on production inside a rolled-back
transaction: anon/authenticated lose `access_token` (`true` → `false`), keep `expires_at`, and
`service_role` is unaffected — `upwork-poller` and the Upwork edge functions use the service role
and bypass both RLS and column grants.

⚠️ Exposure control, **not** encryption at rest — the same caveat T99 recorded, and here it is
sharper because `upwork_auth_tokens` has no ciphertext columns at all.

## 2026-08-28 — AC3 the interface, AC8 the (a)/(b) split

### AC3 — `wom7cfworkers/src/services/connectors/types.ts`

Types only, no implementations: implementations need the registry, and the registry is AC5, blocked
on [[T210]] Phase 1. Types can land first and be checked first.

**Every union in it exists because the research matrix proved one value could not cover 11
services**, which is the concrete payoff of doing AC1 before AC3:

- `AuthStrategy` — `none` (a plain link) through OAuth2 with a 2-hour token. There is no universal
  `connect()`, so auth is a **declared strategy**, not a method every connector implements.
- `RateLimitKnowledge` — `published · runtime-discovered · reactive · unknown`. 🔴 **Not a number.**
  LinkedIn publishes none and exposes them per-app in a portal; Credly has none until it throttles;
  Stack Overflow's is unverifiable. A scheduler reading a constant would be wrong for four of eleven.
- `WebhookSupport` carries **its own `verify()`**. The gateway cannot own verification: GitHub signs
  `x-hub-signature-256`, Mastodon uses Web Push, Deel uses `x-deel-signature` — and the gateway
  today rejects everything else at line 51, before its dispatch branch is ever reached.

🔑 **`descriptorMismatches()` is what makes "declared, not thrown" real.** Without it the descriptor
is a comment: a surface renders *"sync available"*, a person clicks, and the call fails on a method
that was never there. It returns the mismatches rather than throwing, so a registry can refuse a bad
connector **and say which claim was false**. Seven tests, each a descriptor that lies in one
direction — including that a **depth-0 connector exposing any method is rejected**, because six of
eleven services sit at rung 0 or 1 and that is where dead half-connectors would grow.

⚠️ **The `cf` stack declared ONLY a `deploy` command**, so wom7cfworkers' TypeScript was ungated
entirely — a types file added there would have been verified by nothing. Added `just cf-typecheck`
(offline, `tsc --noEmit`) and `just cf-test`, both declared in `stacks-policy.json` with a gate
phase of **`manual`** — which is where they measurably run, not where they should end up. The
`worker` stack's own entry records being corrected for the opposite mistake: it *"declared
`pre-push` but MEASURED running at `pre-commit` … describing an intent, not the mechanism."*
wom7cfworkers has no hook layer at all, so any other phase would be that same fiction.

### AC8 — what mode (a) shares, and what it needs of its own

| AC | shared with mode (a)? | why |
|---|---|---|
| AC1 matrix | **yes** | Upwork is already in it — a system connector |
| AC2 ladder | **yes** | depth is a property of the provider, not of who connects |
| **AC3 interface** | **yes, after today's change** | see below |
| AC4 capabilities-as-data | **yes** | a rate limit is the provider's fact either way |
| **AC5 registry** | 🔴 **NO** | the modes key differently — this is the whole finding |
| AC6 no credential material | **yes**, and (a) is the half that was failing it | `upwork_auth_tokens` was the store missing the column grant |
| AC7 webhook dispatch | **mostly (a)'s** | Deel and Upwork are system connectors; of the member services only GitHub, GitLab and Mastodon have webhooks at all |

🔴 **AC5 is where absorbing (a) into (b) would break.** AC5 says *"the registry unifies the
per-service OAuth stores … keyed to the PERSON."* Measured, the two stores are not two shapes of one
thing:

- `social_integrations` — 18 columns, `profile_id`, ciphertext/iv/key_version. **Person-keyed.**
- `upwork_auth_tokens` — 5 columns, **no owner column at all**, 3 rows. **Owned by the estate.**

A single person-keyed table cannot hold a connection that belongs to nobody, and giving the estate's
Upwork connection a fake `profile_id` would put an organisation's credential under a person — which
is a worse answer than two tables. ⇒ **One interface, one capability model, one webhook contract —
but the registry needs an owner that can be either.**

**So AC3 was changed rather than described.** `ConnectionContext` originally carried
`profileId: string`, which is mode-(b) shaped and would have made every system connector either
impossible or a lie about ownership. It is now:

```ts
export type ConnectionOwner =
    | { kind: "member"; profileId: string }
    | { kind: "estate"; note: string };
```

That one union is what lets **(b) ship first without stranding (a)** — the sentence AC8 asks for,
made into a type rather than a promise.

⇒ **Mode (a) still needs, and does not get from (b):** scheduled sync (the poller already exists),
org-level credential rotation, and an answer to *"who is responsible for this connection"* that (b)
gets for free from the person. Those are not ACs here; they belong to [[T89]] and the mode-(a)
follow-on, and this AC's job was to say so rather than let them be silently absorbed.

## 2026-08-28 — AC5: the registry exists, and the old tables stay authoritative

`20260828030000_t94_ac5_connections_registry.sql` + `just connections-registry-check`. **Pending
`just db-migrate`.**

### One table, two owner kinds

AC5 says *"keyed to the PERSON"*. Measured, that cannot be the whole model, and AC8 had already
settled why:

| | | |
|---|---|---|
| `social_integrations` | 18 cols · `profile_id NOT NULL` · ciphertext columns · 1 row | a **person** |
| `upwork_auth_tokens` | 5 cols · **no owner column at all** · 3 rows | the **estate** |

So `connections` carries `owner_kind ∈ {member, estate}` with `profile_id` xor `estate_slot`, and
the shape is a **CHECK constraint** rather than a convention — without it the union is a comment and
a row can be half of each. It is the `ConnectionOwner` type from AC3, in SQL.

🔑 **`upwork_auth_tokens.id` is not the singleton its `default 'default'` implies.** It holds three
rows — `default` (expired 2026-02-21), `manual` (expired 2026-01-20), `freelancer` (live, refreshed
2026-08-27). The id is a **slot name**, so each becomes its own estate connection and the two dead
ones are preserved rather than collapsed into the live one.

### What it deliberately does not do

🔻 **It moves no reader.** Twelve call sites across **four** runtimes — Astro web, Astro cp, Deno
edge functions, the CF worker — and `upwork-poller` runs on a cron. Cutting them over in the change
that creates the table is how a live OAuth store becomes an outage. The old tables stay
authoritative and two bridge triggers keep `connections` in step, the same shape T210 Phase 4 used
for its own re-key.

🔻 **It does not encrypt.** `social_integrations`' ciphertext columns are NULL and the plaintext is
still the live value; D1/T99's remaining half is untouched. The columns are carried across so the
encryption work has somewhere to land.

### Proven before shipping, on production, rolled back

**Backfill** — 4 rows: 3 estate Upwork slots + 1 member LinkedIn, **0 owner-shape violations**. The
epoch conversion is asserted, not eyeballed: `expires_at` is `bigint` **milliseconds** in the old
table and `timestamptz` here, and getting it wrong by 1000 would put every token in 1970 and read as
*expired* rather than as *broken*. `freelancer` lands on 2026-08-28, matching the raw value.

**The bridge, in all four directions** — a poller refresh propagates; a new slot appears (4→5); a
delete removes it (5→4) rather than orphaning it; a member token rotation propagates.

**AC6 at creation, not retrofitted** — `anon` and `authenticated` can read `provider` and cannot
read `access_token`. That is the posture T99 established and that `upwork_auth_tokens` was missing
for thirteen months; applying it when the table is created is the difference.

### The standing check

`just connections-registry-check` — **live, blocking**, 11 row-by-row comparisons. The arrangement
above has exactly one failure mode and it is silent: **the bridge stops firing, the registry keeps
answering, and every later verification measures a stale copy** — nothing else notices, because
every reader is still on the old tables. Token values are compared inside SQL and never selected
out; a probe that printed a credential to prove it matched would be a worse leak than the one AC6
prevents.

⚠️ It shipped conflating two unmeasurable states and was fixed before commit: with the table absent,
every check aborted psql and the probe reported *"could not reach the database"*. *"The migration
has not run"* is a different fact with a different answer, and it now says so — the same T242
distinction this estate keeps re-learning.

⇒ **AC5 is not ticked.** One model exists and is provably faithful, but *"become one model"* is not
finished while twelve call sites still read the old tables. That cutover is the second half.

## 2026-08-28 — transport: how we talk to a platform, and why MCP-first needs a clause

Owner ask, and it produced a correction rather than a confirmation. Two ladders:

- **Deployed code:** MCP → SDK → API (no CLI — a shell-out from an edge function is not a transport)
- **Local dev tooling:** MCP → CLI → API → SDK

🔴 **"MCP first" is unconditional locally and CONDITIONAL when deployed**, because an MCP server is
session-shaped by default and whether it can authenticate without a human varies per provider:

| Provider | Official MCP | Non-interactive auth | Deployed code can use it |
|---|---|---|---|
| **GitHub** | ✅ `api.githubcopilot.com/mcp/` | ✅ GitHub App — *"for non-interactive deployments"* | ✅ |
| **Atlassian** (incl. **Bitbucket**) | ✅ `mcp.atlassian.com` | ✅ *"headless, service-style, or non-interactive"* | ✅ |
| **GitLab** | ✅ per-instance `/api/v4/mcp` | ❌ *"opens a browser window… review and approve"* | ❌ |
| **Upwork** | ✅ `mcp.upwork.com/mcp` | ❌ OAuth 2.1 per session | ❌ |

All three public endpoints verified live (**401**, i.e. present and unauthorized).

⇒ **The deployed rule is "MCP _if it can authenticate without a human_ → SDK → API."** Without the
clause it points a cron at an OAuth flow it can never complete — which [[T218]] already found for
Upwork and recorded as an Upwork fact (*"a Supabase edge function and a Cloudflare cron have no
session to OAuth with"*). It is the general case.

**Two inversions worth knowing before designing against this:**

1. **Bitbucket is API-token ONLY** through the Atlassian MCP — OAuth 2.1 is not supported for it. So
   the transport that works for Bitbucket is the non-interactive one, the reverse of the usual
   pattern. ⇒ For [[T292]], **Bitbucket may be MCP-reachable from deployed code while GitLab is
   not** — not the ordering either product's openness would suggest.
2. **GitLab's MCP is not a central endpoint** — it is served by your own instance, so a connector
   cannot hardcode a URL. It is per-connection configuration, like a self-hosted forge base URL.

### What it changes here

- **AC3** — `AuthStrategy` answers *how* a connector authenticates, not *whether a machine can*. A
  deployed scheduler must know that before choosing a transport, so the descriptor needs a transport
  preference plus an `interactiveOnly` fact. **Not yet added to `types.ts`** — it is a real change to
  a shipped interface and belongs with AC4 rather than as an unannounced edit.
- **AC4** — transport is registry DATA for the same reason the rate limit is: it varies per
  provider, cannot be inferred, and a wrong assumption fails at runtime.
- ⚠️ **MCP is the exception, not the normal path.** Of 11 researched platforms, **2** have one. A
  design that treats MCP-first as the common case spends its effort on the minority.

Policy recorded in `CLAUDE.md` beside the existing tool ladder; per-platform evidence and sources in
`docs/backend/CONNECTOR-RESEARCH-MATRIX.md`.

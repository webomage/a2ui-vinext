# T134 — Unified service & connection registry

> **Owner ask, 2026-07-25.** *"We have to be able to connect different services to our w0m system,
> and have in admin CP all connected and used services with status, version, MCP, CLI, SDK, check
> version update, etc. For users we also want to manage all kinds of service connections like
> GitHub and external jobs and profiles systems."* Filed as a **design-enhancing priority task**.

## Summary

w0m already tracks "services" in **four disconnected places**, each with a different shape, none of
them visible in a UI. The owner ask is not really "build a registry" — several registries exist —
it is that **there is no single model and no surface**. This ticket owns the **design of record**
for one service model with two rendered surfaces, and hands the plumbing to the tickets that
already own it.

**This ticket is design + the CP surface. It deliberately does NOT re-scope its neighbours** — see
*Boundaries* below. Filing it as a build ticket would duplicate [[T94]].

## The four existing sources — measured 2026-07-25, do not re-derive

| Source | What it already holds | Gap |
|---|---|---|
| `project/tools-policy.json` + `just tools-check` / `tools-outdated` / `tools-upgrade` ([[T112]]) | 16 host CLI tools: min version, known-good, source (brew/pyenv/gcloud), `auto:` update policy, smoke tests, weekly refresh | **version + update-check data already exists** — no UI, and it is host-local, not per-environment |
| `project/stacks-policy.json` + `just discovery` ([[T130]]) | 8 stacks × `runtime`, `justfile`, `techs` (dep/config/import detection), `commands` role→recipe contract | no UI; describes stacks, not *services* |
| `.w0m/sdlc.json → mcp` ([[T130]]) | enabled **MCP servers**: name, purpose, scope | names only — deliberately no credentials; **"listed" ≠ "connected"**, and live availability is a harness fact |
| `social_integrations` (+ the retired `upwork_auth_tokens` path) | live per-user OAuth connections (LinkedIn today) | per-service table, not a registry; hardening in flight under [[T99]] |

Plus **SDK/package versions**, which are a fifth shape again: `deps-policy.json` floors + lockfiles
([[T112]]), with no relationship to any of the above.

**The design problem, stated precisely:** "service" currently means at least five different things —
a host CLI, a stack tech, an MCP server, an npm SDK, and a user's OAuth connection. They have
different identity, different version semantics, different owners, and different truth sources.
A single flat "services" table would flatten away exactly the distinctions that make each one
useful. The design work is defining **what a service is, what a connection is, and how version and
status are expressed per kind** — not drawing a table.

## Boundaries — what this ticket does NOT own

- **[[T94]] owns the connector interface + the unifying `connectors`/`integrations` registry table**
  — including its mode (b) *member/trainee profile connectors: LinkedIn / Upwork / **GitHub** / CV /
  Credly*. The owner's "users manage GitHub and external jobs and profiles systems" is **already
  T94(b)**. T134 designs the model and the surface; T94 builds the connector layer beneath it.
- **[[T64]] owns the Backstage-*style* catalog** as an implementation behind `just` (decision
  2026-07-24, ordered after T130). T134 supplies its **UI contract and data model**; it does not
  re-open the framework decision (no Backstage, no CI/CD server).
- **[[T90]] owns the admin-CP Integrations reorg** — T134's admin surface must land inside that
  reorg, not beside it.
- **[[T99]] owns credential storage** for connections. T134 must not design a second credential path.
- **[[T112]]/[[T130]]** remain the **truth sources** for tool/stack/MCP data. T134 reads them; it
  does not fork them, and adding a tool stays a policy-file edit, not a UI action.

## Acceptance criteria

- [x] **AC1 — Taxonomy.** A written model that defines *service*, *service kind* (host CLI · stack
      tech · MCP server · SDK/package · external OAuth connection) and *connection*, and states for
      each kind: its identity, its version semantics, its truth source, and its owner. A single
      undifferentiated "service" table is explicitly rejected or explicitly justified.
- [x] **AC2 — Status semantics are honest.** The model distinguishes **declared** (in a policy
      file), **installed/available**, and **live/connected** — and forbids rendering "listed" as
      "connected". The MCP case is the worked example: `.w0m/sdlc.json → mcp` is intent, and live
      availability is a harness fact that a file cannot assert.
- [x] **AC3 — Version + update model.** How current version, required floor, known-good, and
      "update available" are expressed per kind, reusing T112's existing data rather than
      recomputing it. Kinds with no meaningful version (e.g. an OAuth connection) say so.
- [x] **AC4 — Admin CP surface, specced against the DS.** A catalog view in admin CP listing every
      service with kind, status, version, update-availability and truth source, cited against the
      canonical design system (`wom7web/design-system` + `@webomage/ui`) per the authoring standard.
      Read-only in this increment: it must not become a second way to mutate policy files.
- [x] **AC5 — User connections surface.** A member/client-facing view to see and manage *their own*
      connections (GitHub, job boards, profile systems), specced to sit on **T94's** connector
      interface — with the RBAC reach stated in [[T117]]'s terms (which class/hat sees what).
- [x] **AC6 — No credential leaks into the surface.** Neither surface exposes token material, and
      the design names the columns/fields each view may read. Consistent with T99's column-GRANT
      posture: the browser must not be able to select a secret column.
- [x] **AC7 — Handoff is explicit.** Each part of the design names the ticket that builds it
      (T94 / T64 / T90), with no scope silently absorbed into T134.
- [x] **AC8 — OpenSpec change** authored and strict-valid, requirements tracing to these ACs.

## Status notes

- **2026-08-15 — task 3.1 DONE: the Infisical read credential exists and is PROVEN read-only.**
  Owner created a service token; `just infisical-token-probe` is the standing proof.
  🔑 **Read-only is established by ATTEMPTING A WRITE, not by trusting the role setting.** The write
  is refused. *"I set it to read-only"* is a claim about a UI; this is a claim about the credential —
  the same standard 3.5's route probe is held to.
  ⚠️ The probe redirects `HOME` away from the operator's session first, or a PASS could be the
  logged-in user's doing and would certify a token it never exercised.
  ✅ **`INFISICAL_TOKEN` is honoured from the ENVIRONMENT**, so the token never appears in `argv`
  where `ps` and shell history would expose it. ⚠️ My first suggested command would have put it
  there — corrected before it was run.
  ⚠️ **The token was never shared with the agent and does not need to be.** Its presence was
  confirmed by its own digest appearing in the snapshot (Infisical only, absent from Supabase and
  Cloudflare — correct), and every use happens inside a child process.
  ⚠️ The local snapshot still reads via the operator's session; the report now names the path used,
  because a token that silently fell back to the session would look identical and fail under cron.

- **2026-08-15 — 🔴 TEN CREDENTIALS ARE DRIFTED between Infisical and Supabase.** Found by the
  Phase 3 snapshot once both stores could publish digests. Invisible from either store alone —
  each one individually reports "present".
  `AWS_ACCESS_KEY` · `AWS_ACCESS_SECRET` · `CLOUDFLARE_API_TOKEN` · `COHERE_API_KEY` ·
  `GITHUB_APP_CLIENT_SECRET` · `GITHUB_APP_PRIVATE_KEY` · `GITHUB_APP_WEBHOOK_SECRET` ·
  `GROQ_API_KEY` · `HONEYCOMB_API_KEY` · `POSTHOG_API_KEY`
  🔴 **`HONEYCOMB_API_KEY` is the unambiguous one**: Infisical holds a real value, Supabase holds
  the **empty string**. Anything reading it from Supabase gets `''`.
  ⚠️ **The other nine need triage, not assumption.** This compares the `dev` Infisical environment
  against the Supabase project's secrets, and some of those may differ *by design*. Drift is a
  finding to resolve, not a defect to claim — the three `GITHUB_APP_*` keys drifting together
  looks like one rotation that reached one store, which is the shape worth checking first.
  🔑 **This is precisely the failure mode of the 2026-07-19 outage** — a `WEBHOOK_SECRET` that
  differed between stores while both reported present. That pair now agrees; ten others do not.

- **2026-08-15 — owner decision: the Infisical adapter FETCHES AND HASHES.** Infisical has no digest
  endpoint (v4 returns `secretValue` in plaintext, or omits it via `viewSecretValue=false`), so
  proving agreement requires hashing a value somewhere. Presence-only was the safer option and was
  rejected for a good reason: with Supabase as the only digest source, **0 of 123** credentials had
  two comparable digests and the drift detection had nothing to bite on. It is now **70 of 123**.
  🔑 **Plaintext is confined to a child process.** `project/scripts/_credential_hasher.py` runs under
  `infisical run`, and its entire stdout is `NAME<TAB>digest` — the snapshot process never holds a
  value, so it cannot log, raise or persist one. The child prints a value on no path, including its
  error paths, because a traceback is the classic way a secret reaches a log.
  ⚠️ **Hashes exact bytes — no `strip()`.** A trailing newline that differs between two stores IS a
  drift; normalising would hide the thing being looked for.
  ⚠️ **No new credential was needed for the local run** — it borrows the operator's own session.
  Task 3.1's read-only token earns its keep only when this runs UNATTENDED, where there is no
  session to borrow and Infisical cannot store the credential that reads Infisical. That is the real
  boundary, and it is where a Keychain or CI secret becomes the answer.
  🔴 **A bug worth remembering: the count stayed at 0/123 after the adapter started working.** The
  row builder still hardcoded infisical to `unknown` — written while it could not be read. The
  reader was fixed and its consumer was not, so a real capability read as an absence. A zero that
  survives the fix landing is a bug, not a finding.

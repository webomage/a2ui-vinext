# T276 — name the seam before writing the scenarios

## Summary

Owner direction 2026-08-24, after a scan of external spec-authoring skills:
*"file the testing seams idea against the spec standard."*

The idea is borrowed, and the source is worth naming: **`mattpocock/skills@to-spec`** (skills.sh,
~360K installs) runs three steps — explore the repo → **identify testing seams** → write and publish
the spec. Recorded in
[`docs/research/tech/2026-08-24-agent-tooling-and-spec-authoring.md`](../../docs/research/tech/2026-08-24-agent-tooling-and-spec-authoring.md),
which also argues against *installing* it: it parallels `w0m-sdlc-new → spec → build` and would be a
third spec story. **The step is worth taking; the pipeline is not.**

## The gap, stated precisely

`openspec/SPEC-AUTHORING-STANDARD.md` is good at **who verifies**. Its enriched requirement block
carries a **Verify with** line naming skills, and §"Skill → verification mapping" is a
concern → skill → *what it proves* table.

🔴 **What it never asks is WHERE the verification attaches, or WHICH PROPERTY it reads.**
*"Verify with `playwright-best-practices`"* is satisfied by any Playwright test at all. The standard
has no slot for *"the observable is the computed `font-size` of the `h1`, read at these viewports"*
— so the choice of what to measure is made later, by whoever writes the gate, usually **after** the
implementation, when the convenient observable is already visible.

## Why this is not theoretical — [[T261]] is the case

The responsive-layout gate measured **lines** and passed **all 33 rows** while **every H1 on the
site rendered at 16px**. A destroyed heading fits on one line everywhere. The cause was a Tailwind
arbitrary value with a function nested in its `var()` fallback, which generates **no CSS rule at
all**, silently.

🔑 **A "Verify with" line would not have caught it.** Playwright *was* the right skill. The seam was
wrong — the gate attached to a consequence of the property rather than the property. Naming the seam
up front asks *"what would a catastrophic failure look like in this measurement?"* at the moment the
answer is still cheap, instead of after the fix is in and the metric is chosen to fit it.

⚠️ The same ticket has three separate instances of the pattern: it also reported **0 clipped
elements on a page clipped on purpose** (an exemption keyed on `transition-property`, which
initialises to `all`), and an orphan rule that was vacuous under greedy wrapping. **Three wrong gates
in one ticket** is the argument that this is a standard-level gap, not one author's bad day.

## What to add

A **Testing seams** field in the enriched requirement block, written **before** the `#### Scenario`s
— the ordering is the point, since a seam chosen after the scenarios is chosen to fit them.

Each seam names three things:

| | |
|---|---|
| **the observable** | the actual property, e.g. *computed `font-size` of `h1`* — not *"the heading looks right"* |
| **where it is read** | the existing integration point it attaches to |
| **its failure shape** | what a catastrophic failure would look like **in that measurement**. 🔑 If the answer is *"a pass"*, the seam is wrong and must be replaced before the spec is written |

`to-spec`'s two supporting rules are worth taking with it: **prefer existing integration points**,
and **minimise the number of new seams introduced** — a spec that invents a bespoke harness per
requirement produces gates nobody runs.

## Acceptance criteria

- [ ] AC1 — **The enriched requirement block gains a `Testing seams` field**, positioned **before**
      the scenarios in the template, carrying observable / attachment point / failure shape.
- [ ] AC2 — 🔑 **The failure-shape question is mandatory, not advisory.** *"What does a catastrophic
      failure look like in this measurement, and does it look like a pass?"* That single question is
      what [[T261]] needed and is the whole value of the field. A seam recorded without it is a
      restatement of "Verify with".
- [ ] AC3 — **`prefer existing seams` and `minimise new seams` are stated as rules with a reason** —
      a bespoke harness per requirement is a gate nobody runs, which is [[T135]] AC8 arriving by a
      different route.
- [ ] AC4 — 🔴 **Retrofit is explicitly OUT of scope, and the standard says so.** ~23 changes exist
      under `openspec/changes/` plus an archive; requiring seams retroactively would redden every one
      of them for work nobody is doing. **New and modified requirements only** — and that boundary is
      written into the standard, not left to be inferred.
- [ ] AC5 — **`w0m-sdlc-spec` asks for it**, since the standard is what that gate validates against.
      A field in a template that no gate reads is *"a declaration file is not a gate"*, which is
      already a recorded lesson in `LESSONS.md`.
- [ ] AC6 — **Worked example: [[T261]] written the way this standard would have demanded.** Show the
      seam that would have caught the 16px H1 — *observable: computed `font-size`; attachment:
      the layout matrix's per-viewport measurement; failure shape: **a collapsed heading still fits
      on one line, so a lines-based metric passes***. ⚠️ A standard change with no worked example is
      advice; with one it is a pattern.
- [ ] AC7 — **Do NOT install `to-spec`.** The research note argues this and the reasoning holds: it
      duplicates `w0m-sdlc-new → spec → build`, and it arrives outside [[T127]] governance while
      [[T270]] AC4 is still settling that question for `eli5`. This AC exists so the idea's origin
      does not later get read as a recommendation to adopt its source.

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
the standard carries a `Testing seams` field ordered before the scenarios, with the failure-shape
question mandatory; `w0m-sdlc-spec` asks for it; retrofit is explicitly excluded in writing; and
T261 is written up as the worked example.

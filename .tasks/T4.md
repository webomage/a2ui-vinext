# T4 — Blueprint-assigned proposals

## Summary


🟡 **P2 2026-08-13.** Client-funnel product work; depends on the proposal/contract shape [[T204]] is separating and on [[T5]]'s registry. Not blocking anything today.
`lead_proposals` + `blueprint_id`/`adventure_id`; the consultant seeds machine-drafted

## Acceptance criteria

- [x] AC1 — `lead_proposals` carries `blueprint_id` / `adventure_id`
      ✅ 2026-08-26, migration `20260826020000`. **`adventure_id` is `project_id`.**
      🔴 **CORRECTION 2026-08-26 — my stated reason was FALSE.** I wrote "NO SUCH TABLE;
      hierarchy-v2 was never built". `gamification.adventures` **exists** (id, project_id, title,
      description, status, unit_id, created_by). I searched `public` and reported the schema I
      searched as the schema that exists — the same class of error as measuring from the wrong root.
      🟢 **The decision survives on a better reason:** `adventures` is the gamified work-BREAKDOWN
      *under* a project — it carries `project_id` itself — not the delivery container. It holds
      **0 rows**, as do `raids` and `project_acl`. The container is `projects`, which is exactly
      what `contracts.project_id` already points at, so both halves of a handoff share one target.
      🔑 Same correction on blueprint identity: the catalog is a **27-row table**, not
      `apps/web/src/config/blueprints.json`, and `contracts.blueprint_id` is a **uuid** FK while
      `blueprints.blueprint_id` is the text slug — two things wearing one name. Using the uuid FK
      buys the spec's own criterion outright: *"a blueprint_id absent from the catalog is rejected
      rather than silently stored"* is a description of a foreign key.
      Also added: `contract_id` (what makes acceptance idempotent), `is_machine_drafted`,
      `reviewed_by`/`reviewed_at`, and the client's own-linkage SELECT arm — `lead_proposals` had
      **no client-facing policy at all**, so a client could not see the proposal written for them.
- [x] AC2 — Consultant seeds machine-drafted proposals
      ✅ 2026-08-26 — `_shared/proposal-seed.ts`, called from `executeSubmitServiceRequest` in
      `chat-core.ts` right after the lead lands. The spec says the system **MAY** create a draft,
      and the MAY is treated as binding:
      🔴 **It declines to guess.** A matcher that always returns something would attach an arbitrary
      architecture to a real prospect's proposal, and every "the right intake finds the right
      blueprint" test would still pass while it did. One curated TAG match clears the bar; one prose
      word from a title does not. Both negative controls — an unrelated intake and a vague one —
      return nothing, and nothing is written.
      🔴 **It never invents a price.** `total_estimate_usd` stays NULL; the blueprint's cost BAND is
      reproduced and labelled "not a quote". [[T283]] shipped a portal showing a fabricated $4,200
      PAID invoice — a machine-guessed quote on a prospect's proposal is the same class of harm.
      🔴 **The draft explains its own match** (score + matched terms). A machine draft that does not
      say why cannot be reviewed, only rubber-stamped — and team review is the entire safety
      property, enforced by the `lead_proposals_machine_draft_gate` trigger.
      ⚠️ **It cannot fail the visitor's intake.** The lead is already committed and the visitor is
      about to be told so; an optional internal draft must not turn a real conversion into an
      apology. Errors are logged, never thrown, and the seed returns null.
      🔑 **Eligibility is `access_scope='public'` (24 rows), NOT `is_published`** — and that is the
      finding worth keeping: **all 27 blueprints carry `is_published = false`**, so the obvious
      filter would have shipped a feature that can never fire, with no error and no exception, and
      reviewed as correct. `just proposal-seed-catalog-check` makes that falsifiable — it asserts
      realistic intakes still place a blueprint against the LIVE catalog (5/5) **and** that the seed
      has not drifted to a different filter than the check reads with.
      🔒 9 unit cases in `just deno-test` + the live catalog check; both mutation-tested.
- [x] AC3 — Acceptance creates a contract + delivery container
      ✅ 2026-08-26, `public.accept_lead_proposal(uuid)` (migration `20260826030000`) — one
      transaction creating the draft direct contract and the delivery project, linking all three,
      idempotent on replay. Client surface: `/client/proposals` with a confirm step, because
      acceptance creates a contract and should not be one click.
      🔴 **A real authorization hole was caught before it ran anywhere.** The check read
      `not (converted_user_id = uid or client_id in (...))`; on a lead with neither set both operands
      are SQL NULL, `not (NULL or NULL)` is NULL, `IF NULL THEN` never fires — **a stranger could
      accept someone else's proposal.** Now `coalesce(..., false)`. No structural assertion would
      have found it; the behavioural probe found it on its first run.
      ⏳ **Unapplied.** `db-migrate` is denied to an agent and deploy needs a human, so this is
      proven against a scratch restore (`just stage2-schema-check`, 27/27), not against production.

## Definition of Done

A client opens a proposal written for them, sees the blueprint it is built on rather than a block of
prose, and accepting it creates **both** a contract and a delivery container in one transaction that
cannot half-succeed. Proven by running it, not by reading it: the migrations apply to a real restore
and are exercised there, a second acceptance mints no second contract, a **draft** cannot be
accepted, and **someone else's proposal cannot be accepted** — the last refused with the same
message as "missing", so the endpoint is not a proposal-id oracle.

🔴 **Not done if the delivery container it creates is world-readable.** That is not a separate
ticket's problem: stage-2 is precisely the trigger [[T204]] predicted on 2026-08-12, and shipping the
feature without the visibility fix would publish the first real engagement. The behavioural check —
insert a client project, read it back as `anon`, see nothing — is a condition of this ticket, because
the structural version of that check passed while the hole was still open.

⏳ **Also not done while the migrations are unapplied.** An agent cannot run `db-migrate`; the scratch
restore proves the code, and only a deploy proves production. Say which one is being claimed.

# T539 — The owner's MCP sync into the database

## Summary

Owner decision 2026-10-02 ("Adopt option 5 and split T537"): the Upwork MCP path that actually worked, the owner's laptop session, becomes the near-term source, and the per-member server connector is split off to [[T537]] (on hold).

What exists (read from the repository, `.agents/reports/2026-10-01-t533-upwork-linked-store-research.md` section 12):

- `just upwork-mcp-sync` (`wom7web/project/scripts/upwork_mcp_sync.py`) drives `pnpm dlx mcp-remote https://mcp.upwork.com/mcp`, which holds the owner's OAuth session in `~/.mcp-auth/` (a public client with a LOOPBACK redirect, the only kind Upwork registers). It reads contracts, proposals, rooms, messages, the profile and the agency dashboard and writes ONLY local files: `project/data/upwork/{contracts,proposals,rooms}.jsonl` and profile JSON. Last written 2026-08-19. It makes no database call.
- `just upwork-harvest-proposals` does the same for the full proposal history and keeps each whole response in `proposals_archive.jsonl` (1,782 lines).
- `backfill_upwork_proposals.py` (T155) loads cover letters and tags into `public.proposals`. NOTHING loads rooms, messages, contracts or the screening answers from those files. Messages stayed at 15 rooms because the dead API poller fetched at most 10 rooms per run.
- Today's files: 95 contracts, 11 proposals, 18 rooms (messages under `recent_messages`), 1,782 archived proposals of which 725 carry screening answers (1,894 pairs).

What this ticket is: the missing loader, plus an honest freshness rule for a source that is a laptop and not a cron. What it is not: other members' data, anything unattended, or a fix for the API poller ([[T535]]).

## Acceptance criteria

- [ ] AC1 — **Files refreshed (owner step).** The owner runs `just upwork-mcp-sync` and `just upwork-harvest-proposals` with the live `mcp-remote` session. The files carry today's date; the line counts before and after are recorded here.
- [ ] AC2 — **Mapping written before code.** For each leg (contracts, offers, proposals, screening answers, rooms, messages) a table of file key -> database column, the idempotency key, and the owner's `profile_id` attribution, checked against the live schema read-only. Where the screening answers land is decided by [[T533]] AC2 (the evidence-layer spec); until then that leg is out of this ticket's loader and listed as blocked.
- [ ] AC3 — **Loader, tests first.** An owner-run script, dry-run by default, that reads the files and writes the tables in AC2. Tests: pure row-to-values transforms; a second run writes zero new rows; a malformed row is counted and skipped without aborting or half-writing; an older file never overwrites a newer database row; the output carries counts and key names only, never message text; mutation-tested. Registered as a suite once `project/test-suites.json` is free of other agents' uncommitted edits.
- [ ] AC4 — **Run and verified.** The owner runs the dry run, reads the counts, then the real run. Verified read-only afterwards: the number of rooms holding messages rises from 15 and equals what the files hold; contract and proposal counts match; the per-leg fetched and written counts are recorded here.
- [ ] AC5 — **Freshness is truthful.** The T535 freshness gate stops failing forever on a source that no longer runs. The loader writes a success row (`admin_activity_logs`, its own action name) and the gate reads that row with a daily threshold (last success at most 26 hours old, fewer than 3 consecutive failures), tests first. The dead API poller's check is marked deprecated and reported separately, not deleted. The deep audit reads the new rule.
- [ ] AC6 — **Message text out of git (owner decision pending).** `rooms.jsonl` carries real client conversations and is tracked. If the owner confirms: the message-bearing files are untracked and ignored, the loader reads from the ignored path, and history is left as it is (rewriting it is not part of this ticket). If the owner declines: this AC is closed N/A with the reason.

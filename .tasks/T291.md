# T291 — a transcript claims a release it never published

## Summary

Found 2026-08-26 while proving the newly-wrapped `just deploy` captures a transcript (T224/T290).

`deploy_logged.py:167` decides a transcript's NAME by searching its output for a version string:

```python
found = version_regex().search(text)
if found:  final = LOGS / f"deploy-{release}.log"
else:      final = LOGS / f"run-{producer_version() or 'unstamped'}.log"
```

🔴 **Mentioning a version is not the same as publishing one.** Running any recipe that PRINTS the
version through the logger produces a `deploy-<version>.log` — a release record for a release that
never happened. Reproduced exactly:

```
python3 deploy_logged.py version-check   →  deploy-logs/deploy-2026.08.26-1787765702.log
just changelog-drift                     →  FAILED
```

`changelog_drift.py` reads `deploy-*.log` as the set of real deploy stamps — a contract that was
narrowed to that prefix on 2026-08-25 precisely so a `run-*.log` could not be mistaken for a
release. The prefix is now load-bearing, and the thing that assigns it can be wrong.

⚠️ **The blast radius grew today.** `deploy` is now wrapped like `deploy-all`, so more runs pass
through this logger, and `deploy-logged <anything>` is a documented entry point.

🟢 Impact is a FALSE RED, not a lost record: it invents a deploy that did not happen, and the next
`changelog-drift` blocks a push until someone deletes the file. Nothing real is destroyed. But a
gate that reddens on an artefact of running a read-only check is a gate people learn to delete
files to satisfy.

## Acceptance criteria

- [x] **AC1 — name it a release only when one was PUBLISHED.** The signal is the deploy actually
      stamping — a `deploy_log` write, or `_log-deploy` having run — not a regex over stdout.
      Decided by what the run did: `rc == 0` AND the recipe is a release recipe (`RELEASE_RECIPES = {"deploy", "_deploy-chain", "deploy-all", "_deploy-all-chain"}`).
- [x] **AC2 — a red probe first.** `deploy_logged.py` has `test_deploy_logged.py`; added the probe:
      running `version` prints a version string but lands as `run-*.log` and not `deploy-*.log`.
      Demonstrated failing RED before the fix (`❌ found fake deploy logs: ['deploy-2026.09.17-1789662562.log']`),
      and GREEN after the fix.
- [x] **AC3 — `changelog-drift` stays honest about what it reads.** It keys on the `deploy-*`
      prefix. Verified clean via `python3 project/scripts/changelog_drift.py` and after running
      `deploy_logged.py version`: `[OK] no deploy transcript is newer than the newest CHANGELOG entry.`
- [x] **AC4 — say what happens to a misnamed log already on disk.** Transcripts embed `# recipe : just <recipe>`
      and `# exit code : <rc>` in lines 2–3 of their header. Any transcript claiming `deploy-*.log`
      whose recipe was not a release deploy (or exited non-zero) is visibly fabricated and can be identified
      mechanically. All existing deploy logs on disk (`deploy-2026.09.*.log`) were inspected and confirmed
      legitimate (`just _deploy-all-chain` with exit code 0).

## Definition of Done

A transcript is named for a release only when the run published one, decided from what the run DID
rather than from a version string appearing in its output — so a read-only recipe cannot fabricate a
deploy record. Proven by a probe that was RED before the change: a recipe that prints a version and
publishes nothing lands as `run-*.log`. `changelog-drift` and the naming rule are checked against
each other, since the prefix is the contract between them.

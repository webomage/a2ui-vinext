# T126 — Authenticate the `news-post-generator` edge function

## Summary

`supabase/functions/news-post-generator` is **fully unauthenticated** — `verify_jwt = false` in
`config.toml` **and** no in-body auth check — so anyone on the internet can `POST` to it and:

1. **Burn LLM tokens** — every call runs `routeChat(...)` (`gemma-4-31b-it` by default), a real
   per-request cost.
2. **Trigger a server-side fetch** of a caller-supplied `source_url`.

Its only cost control is `checkQuota(supabase, rateId, 200_000)`, and that control is weak on two
counts: the `rateId` is `web:<ip>` where the IP is read from the **client-controllable
`X-Forwarded-For` header** (`index.ts:72–73`), so an attacker rotates the header for unlimited
fresh quota buckets; and the quota check is deliberately **fail-open** (`index.ts:68–69`). The
SSRF guard (`isSafeSourceUrl`, `index.ts:19–31`) is decent — blocks localhost / cloud-metadata /
RFC-1918 and uses `fetch(..., { redirect: "error" })` — but it matches on the **hostname string**
and never resolves the IP, so DNS-rebinding can bypass it.

Spun out of the T123/T124 security sweep (chip `task_eaabef77`); noted in
[[definer-revoke-quota-failopen]] and STATE.md §1b.

## What is already known (do not re-derive)

- **`verify_jwt = false`** — `wom7api/supabase/config.toml` `[functions.news-post-generator]`
  (verified 2026-07-23). `verify_jwt = true` alone would **not** fix this: the publishable/anon key
  ships in every page bundle and is a valid project JWT, so it would still pass.
- **The only legitimate caller is `daily-news-scheduler`**
  (`supabase/functions/daily-news-scheduler/index.ts:87`), which already sends
  `Authorization: Bearer ${SUPABASE_SERVICE_ROLE_KEY}` + the `apikey` header. So an in-body
  service-role check is transparent to it — no caller change needed.
- **The fix pattern already exists** in this repo:
  `supabase/functions/upwork-poller/index.ts:253–257` compares a provided secret to
  `SUPABASE_SERVICE_ROLE_KEY`. Reuse it, but with a **constant-time** compare (`!==` is the
  non-constant-time smell already flagged on `get-admin-metrics`).
- The weekly pg_cron that drove the scheduler was **unscheduled** (`20260309171048_disable_news_pg_cron.sql`),
  so the legitimate path may be dormant — but the endpoint is deployed and publicly reachable
  regardless, which is the exposure.
- Tests POST to this endpoint directly (`wom7web/tests/steps/ai.steps.ts:1104–1126`) and rely on
  the E2E bypass (`isE2EBypassRequest`); the auth guard must keep that path working.

## Acceptance criteria

- [x] **AC1 — DONE.** Auth guard is the first gate (before body parse / quota / fetch / model).
      Live against the deployed fn: unauth `POST` → **401**, wrong bearer → **401**.
- [x] **AC2 — DONE.** Service-role `POST` passes the guard (→ **400** on an invalid-JSON body, i.e.
      reaches the JSON check, no LLM call). `daily-news-scheduler` already sends the service-role
      bearer, so it is unaffected.
- [x] **AC3 — DONE.** `_shared/auth.ts` `constantTimeEqual` (XOR-fold, iterates max length) — no
      early exit, no `===` on the raw secret.
- [x] **AC4 — DONE.** Guard also accepts the E2E bypass; live `POST` with the `playwright-test`
      header → **400** (auth passed). Gauge steps updated: the wrong-content-type / invalid-JSON
      steps now send the bypass header; a new step + spec scenario asserts unauth → 401.
- [x] **AC5 — DONE.** Endpoint is now service-role-only, so the `X-Forwarded-For`-spoof quota
      bypass is moot (only the trusted caller reaches it). The quota check is kept as
      defense-in-depth but no longer gates a public surface.
- [x] **AC6 — DONE (accepted residual).** The hostname-based SSRF guard's DNS-rebind gap is
      recorded as **accepted low-risk**: only the trusted `daily-news-scheduler` (service-role) now
      reaches the fetch, and it passes fixed RSS-feed URLs — no attacker-controlled `source_url`
      reaches the fetch anymore. Resolve-and-check-IP left as a future hardening if the endpoint is
      ever reopened to less-trusted callers.

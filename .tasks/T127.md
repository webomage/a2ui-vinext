# T127 — w0m skills governance over `npx skills`

## Summary

`wom7skills` is the canonical skill store, but adding **external/third-party** skills to it is
manual hand-copy today — proven this session by copying `rbac-auditor` and
`supabase-postgres-best-practices` into `wom7skills/skills/` by hand. That repeats the exact drift
that got the `openspec-*` family **removed** 2026-07-21 (vendored copies that fell out of sync).

**Research (2026-07-24) reshaped the scope: do NOT build a registry client — adopt the official
one.** The skills.sh ecosystem already ships a full package manager, **`npx skills`**
([vercel-labs/skills](https://github.com/vercel-labs/skills), MIT, npm `skills`): `add`, `use`,
`find`, `list`, `remove`, `update`, `init`; it auto-detects Claude Code and installs to
`.claude/skills/` (project) or `~/.claude/skills/` (global), **symlinking to a canonical copy** by
default — the same model as our own `skills.py`. Reimplementing search/add/adapters (as the
2026-07-22 RFC first sketched) would duplicate it.

What `npx skills` **lacks** is precisely the w0m governance we need: **no manifest, no lockfile, no
version pinning, no integrity hashing, no security gate, and `update` just pulls latest** (no
respect for a pinned/compatible version). So T127 is a **governance layer over `npx skills`**, not a
new installer. The RFC stands as design context but its provider-adapter model collapses: skills.sh +
git are handled by `npx skills`; our canonical `w0m*` family sync folds in too; the w0m layer ties
them with pins + verification + a versioned updater.

**Language = TypeScript (owner decision 2026-07-24).** The whole skills subsystem is Node/TS
(`npx skills`, `autoskills`, our own `mmd-validate/validate.mjs`), so the manager lives natively in
that ecosystem. This **migrates ALL wom7skills automation to TS** — `skills.py` (the w0m* sync +
drift check), `scripts/install.py` (Gemini-plugin symlinker), and `scripts/generate_score.py` (eval
scoring) are rewritten in TS, run via `tsx` (no build step), under a new `package.json`/`tsconfig`.
This **reverses** the 2026-07-24 `skills.sh`→`skills.py` (Python) conversion: that was right for a
pure file-ops sync with no Node, but is superseded now that the subsystem is a Node-CLI wrapper.
CLAUDE.md's "prefer Python here" note is updated to "skills tooling is TS" as part of this ticket.

**Scope split with [[T24]]:** T24 (P1) is the **survey/curation** task — import `kepano/obsidian-skills`,
survey top skills.sh skills, decide per-skill *import vs master*, produce a catalog. **T127 is the
machinery** that lets T24's "import/connect" decisions land without drift. Build order: T127 provides
the manager; T24 feeds it the curated list. (If the owner prefers, T127 folds into T24 as its build
phase — flagged for the start gate.)

## What is already known (do not re-derive)

- **RFC exists** (138 lines): provider model, CLI surface, `.w0m/skills.json` manifest+lockfile,
  SDLC-start auto-suggest, security guardrails, 3-phase roadmap. Reuse it; don't re-design.
- **Current manual approach + its cost:** `skills.py` (just converted from bash) syncs only the
  canonical `w0m*` family and gates drift on it; everything else (rbac-auditor, supabase-*,
  fact-checker, tinybird-*, …) is hand-placed in `wom7web/.agents/skills` / `.agent/skills` with no
  version lock or provenance. The `openspec-*` removal is the cautionary precedent.
- **`npx skills` is the installer (adopt, don't rebuild).** Commands `add / use / find / list /
  remove / update / init`; Claude Code paths `.claude/skills/` (project) + `~/.claude/skills/`
  (global); default **symlink-to-canonical** (or `--copy`); env `DISABLE_TELEMETRY`/`DO_NOT_TRACK`.
  **Gap:** no manifest, no lockfile, no pinning, no integrity hash — `update` = latest. `npx
  autoskills` is a convenience wrapper that auto-detects `package.json`.
- **Language = TypeScript** (owner 2026-07-24): the manager + all wom7skills automation are TS, run
  via `tsx`, shelling out to `npx skills` for fetch/add. This migrates the just-written `skills.py`
  (+ `install.py`, `generate_score.py`) to TS — see AC1.
- **This session's stack→skills.sh shortlist** is the first real input for `search`/`add`: Astro 6,
  Svelte 5, Tailwind 4, Hono 4, Drizzle 0.45, Zod 4, TS 6, Vitest 4 (candidates recorded in the
  chat + the stack scan). Version-currency of each candidate must be checked on add.

      ### ✅ Deterministic updates ARE achievable — via GitHub, not skills.sh. Method proven.

      Every `skills.sh` entry's `source` is already a **GitHub coordinate** (e.g.
      `coreyhaines31/marketingskills`), so the ref exists upstream — we simply never asked for it.
      **Proven live 2026-07-29:**
      - `gh api repos/coreyhaines31/marketingskills/commits?per_page=1` → **`7868cb9251fa`**, 2026-07-27.
      - `gh api repos/<source>/git/trees/HEAD` → **per-directory tree SHAs** (`skills/` = `aa70a25ee51b`).
        Drilling into `skills/` gives a **per-skill folder SHA**, so a sibling skill changing does
        **not** false-positive the one we track.

      🔑 **Upstream already does exactly this** — the `skills` CLI bundle contains
      `getSkillFolderHashFromTree(blobResult.tree, skillPath)` and stores `source`, `sourceType`,
      `sourceUrl` and **`skillFolderHash`** per entry, with `GH_TOKEN` / `gh auth token` fallback for
      the API. So this is the provider's own design, not an invention.
      ⚠️ **But that lock is unavailable to us:** it is written **only for global installs**
      (`if (successful.length > 0 && installGlobally)`), and ours are project-scoped —
      `~/.agents/.skill-lock.json` is **absent**, confirmed. Its project-scoped sibling
      `skills-lock.json` is also absent from `wom7web`. ⇒ **The data must be fetched by us; the
      mechanism is just borrowed.**

      **What this unlocks, and the shape it should take:**
      - A new lock field — **`upstream_ref`** (the per-skill folder tree SHA) beside the existing
        `integrity` (hash of the *local* copy). Two different facts: `integrity` = *what is on my
        disk*, `upstream_ref` = *what upstream currently publishes*. Today only the first exists,
        which is precisely why "is an update available?" is unanswerable offline.
      - **`w0m skill outdated`** — compare recorded vs live `upstream_ref` **without downloading
        anything**. That is [[T147]] AC2's update-availability check, and it needs *refs*, which now
        exist. One API call per repo, not per skill: **56 adopted skills come from far fewer repos.**
      - `update` then becomes genuinely deterministic: move to a **named** SHA, record it, re-verify.
      ⚠️ **Rate limits and auth:** unauthenticated GitHub is 60 req/h. Use `GH_CONFIG_DIR=~/.config/gh-w0m`
      (the w0m identity — see [[gh-identity-isolation]]) or `GH_TOKEN`, and cache per-repo trees.
      ⚠️ **`HEAD` is not a pin** — resolve it to a concrete SHA at record time, or the "pin" moves.

      🟡 **Not built here** — this is a scoped follow-on, not AC6 rework. AC6's pin-honouring branch
      is already built and tested, so only the resolver is new. **Sequenced into [[T147]] AC2.**

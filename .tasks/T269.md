# T269 — can w0m ship as a bundle, and is it the right shape to be one

## Summary

Owner ask 2026-08-23: *"make a ticket to research .MCPB and .DXT format to look if we can pack our
w0m skills and tools this way"*.

**Research ticket. It produces a recommendation and a decision, not an implementation.** A
*"proceed"* verdict files the build ticket; a *"no"* verdict is an equally good outcome and must be
written down so the question is not re-opened from scratch in three months.

⚠️ **What I believe about these formats, flagged as belief rather than fact.** `.dxt` (*Desktop
Extension*) is Anthropic's zip-plus-`manifest.json` format for one-click installation of an **MCP
server** into Claude Desktop, and `.mcpb` (*MCP Bundle*) is the same lineage after a rename — not a
rival format. **AC1 exists because I should not be trusted on this**: version details drift, my
knowledge has a cutoff, and this estate has a standing rule that a recorded fact is a claim with a
date ([[T67]] — a "revoked, 403" API token was still returning 200 months later, and the stale note
had become an instruction to avoid a working tool).

## 🔑 The prerequisite question, which is more interesting than the format question

**These formats package an MCP server. w0m's skills are prompts and w0m's tools are `just` recipes
over Python scripts. Neither is an MCP server.**

And the estate has very little MCP surface to bundle:

- **`wom7ext` exposes ~25 MCP tools** — the one real server.
- **No `/api/mcp` anywhere**, in any of the four apps.
- **[[T21]] (WebMCP agent tools) is specced and unbuilt.**
- **MCP-first is the declared preferred transport** for this estate, and enabled servers are
  declared in `.w0m/sdlc.json → mcp` ([[T130]]) — so the direction is already chosen; what is
  missing is the surface.

⇒ **The honest form of this question is two questions**, and answering the second without the first
produces a bundle of nothing:

1. *Do we have something an MCPB could contain?* Today, mostly **no**.
2. *If we exposed w0m's tools over MCP, would MCPB be the right way to distribute them?*

⚠️ **Do not answer (2) by building (1) inside this ticket.** Exposing the toolchain over MCP is a
substantial piece of work with its own ticket-shaped scope; this one determines whether the
packaging story is a reason to prioritise it.

## Relationship to the packaging work already in flight — check before duplicating

- **[[T212]]** (P1, queued) — *"Portable w0m Core CLI Toolchain & just Recipe Distribution via
  wom7skills Claude Plugin"*. Owner ask 2026-08-14: make `tasks_query.py`, `sync_github.py` and the
  `just` recipes portable rather than monorepo-path-bound. **That is the Claude *plugin* channel.**
- **`openspec/changes/2026-08-14-wom7skills-claude-plugin-packaging`** — the written change for it.
- **[[T127]]/[[T135]]** — skills are already governed and distributed by `.w0m/skills.json` + lock +
  `just skills-sync`. **There is already a working distribution mechanism**; a second one needs to
  beat it, not merely exist.

🔴 **The failure mode to avoid is a third packaging story.** The estate would then have skills-sync,
a Claude plugin, and a bundle — three answers to *"how does a consumer get w0m's tooling"*. AC5
forces the comparison rather than letting a new format in beside the old ones.

## Acceptance criteria

- [ ] AC1 — **Establish what the formats actually are, from primary sources, with dates.** Confirm
      or correct the Summary's belief: whether `.dxt` was renamed to `.mcpb`, which one is current,
      the manifest schema, the runtime requirements, and what a host must implement to install one.
      🔴 **Cite the source and the date read.** A format claim with no date is the [[T67]] shape.
- [ ] AC2 — **State what a bundle can and cannot contain.** Specifically: can it carry prompt skills,
      `just` recipes, or standalone CLI scripts — or **only** an MCP server plus its runtime? If only
      a server, say so plainly, because that answers most of this ticket.
- [ ] AC3 — **Measure w0m's actual MCP surface**, rather than reasoning from the declared intent.
      What exposes MCP today, how many tools, and what would have to exist for a bundle to be worth
      building. ⚠️ Re-measure — the survey behind the numbers above is from an earlier session, and
      `.w0m/sdlc.json → mcp` declares servers that are *enabled*, which [[T154]] proved is a
      different fact from *listening*, from *configured*, and from *session-connected*.
- [ ] AC4 — **Name the consumer.** Who installs a w0m bundle, and into what? Claude Desktop, Claude
      Code, a client project, another agent runtime? 🔑 If the honest answer is *"nobody outside this
      laptop"*, the recommendation is **no** and the ticket closes as answered — which is a result.
- [ ] AC5 — 🔴 **Compare against what already works, on the same axes.** `skills-sync` + lock
      ([[T127]]) and the Claude plugin ([[T212]]) versus a bundle: what does each carry, who can
      install it, how is provenance verified, how does an update propagate, and what breaks when it
      drifts. **A new channel must beat an existing one on a named axis or it is a third thing to
      keep in sync.**
- [ ] AC6 — **A written recommendation with a verdict** — proceed / no / revisit-when-X — recorded in
      `docs/` and linked from [[T212]], so the next person finds an answer instead of the question.
      An explicit *"no, because …"* satisfies this AC fully.
- [ ] AC7 — **If the verdict is proceed, the build is a NEW ticket**, scoped from AC5's comparison.
      This ticket does not grow into the implementation.

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
the formats are described from dated primary sources, w0m's real MCP surface is re-measured rather
than recalled, the comparison against `skills-sync` and the Claude plugin is written on shared axes,
and a verdict is recorded — with a follow-up ticket filed only if that verdict is proceed.

# T531 — Several agents, one estate

## Summary

Owner, 2026-10-01: *"can we somehow make shared worktree comfortable for simultaneous mindful edits by different agents? ... what we can do for commits and pushes go success while worktree is dirty with changes already?"* Answer, after measuring one day of two agents in one tree: stop sharing it.

**Measured 2026-10-01 (two sessions, one tree):**
1. **One index.** A failed commit left my files staged and the next commit would have swept them in (T235's stage guard exists for exactly this); the same holds for another agent's staged files.
2. **Every commit stashes everyone's unstaged work** (`~/.cache/pre-commit/patch*`). It restored cleanly this time (the other session's 6 files hashed byte-identical before and after), but a hook that regenerates a file mid-commit makes the restore skip, and the memory note `precommit-stash-drops-unstaged-work` records two cases of lost files.
3. **Generated files read the whole tree.** `STATE.md`, `TASKS.md`, `docs/DECISIONS.md` and the epic vocabulary are rebuilt from everything on disk, so my commit needs the other agent's tickets to be consistent and carries or blocks on them. Two of my commits were blocked until I regenerated; the deploy preflight failed on a missing board row ([[T527]]).
4. **Push gates test the working tree, not the commit.** The 26-step pre-push has no step that runs against a snapshot of what is being pushed, so an unrelated half-written file can fail it, and an uncommitted file can make a bad commit pass.
5. **A plain git worktree of the root is not enough.** The root repo excludes its member repos, so a worktree of it holds no code. `orca worktree create` has the same limit (it manages worktrees of one repo). A usable set is one worktree per member repo, which is what the release tooling already builds (about 3 GB each).

## Acceptance criteria

Order is the owner's decision of 2026-10-01 (design: `.agents/reports/2026-10-01-t531-multi-agent-landing-design.md`). Each layer removes one measured incident class and does not depend on the later ones.

- [ ] AC1 — **Commit by path (L1).** `just commit -m <msg> -- <paths>` refuses to run without named paths, commits only those, and leaves another agent's staged and unstaged files as they were (hashes before and after are equal). Prerequisites, each tested on a throwaway repo first: the `oxfmt` hook (it runs `git add` inside the hook) under a pathspec commit's temporary index; and what the stash window does to a concurrent write.
- [ ] AC2 — **Atomic identifiers and one source per fact (L4).** `just ticket-new` allocates the next id by exclusive create in a loop and renders the board row in the same step, so a ticket cannot be rowless ([[T527]]). The hand-kept `SECTION_SLUGS` dictionary is deleted and epic slugs are read from the `> **Epic slug:**` lines of `ROADMAP.md`. `LESSONS.md` gets one file per lesson, or a keyed order, so two appends do not share an anchor.
- [ ] AC3 — **Derived files are produced at landing, not at every commit (L2).** The board, `STATE.md`, the decisions index, the epic vocabulary, the feature index and the dashboard stop being per-commit gates (they become advisory); `just land` regenerates them once from the merged result and commits them as one `chore(derived)` commit. The deploy preflight stays the backstop. Red probe: two agents each add a ticket and each commit; `land` produces a board holding both rows.
- [ ] AC4 — **Gates evaluate a snapshot of the commit, not the working tree (L3).** The blocking tier and the push gates run on a `git archive` snapshot of what is being committed or pushed (measured 2026-10-01: all 10 repos, 334 MB, 1.2 s), with dependencies linked read-only from the stable worktree. Red probes: an untracked file that would break a suite does not fail the push; a tracked, uncommitted fix does not make a bad commit pass. Each gate that reads a path outside the snapshot is named and tested ([[T527]] AC3).
- [ ] AC5 — **Landing lock.** `just land` takes a lock (the stable lock's mechanism: refuses re-entry, shows its holder, has a time limit), rebases onto `origin/beta`, regenerates, runs the snapshot gates and pushes. Two agents landing at once queue; neither sees the other's half-finished state.
- [~] AC6 — **Workspace sets, only if a need remains after AC1 to AC5.** `just agent-tree <name>`: a worktree of every manifest repo on `agent/<name>` with its own index and dependencies, reusing the release tooling. At most 3 live sets (about 3 GB each, 9 GB for 3), pruned by the release rule, never one with unpushed commits. An AgDR first records whether it builds on `orca worktree` for the root plus the release tooling for members, or stands alone. Not built until the owner confirms the need.
  **Half done 2026-10-04 (owner "go" and "do" on 2026-10-03/04, which is the confirmation of need this criterion waits for).** Built test-first as `wom7web/project/scripts/agent_tree.py` (67 tests against real throwaway git repos, 54 mutants all caught, one equivalent mutant dropped, mypy clean): `just agent-tree <name>`, `agent-tree-list`, `agent-tree-land [--dry-run]`, `agent-tree-remove <name>`; recorded in AgDR-0032 (stands alone, reusing `release.py`'s repo list and fixture provisioning, not Orca's worktree root). Measured 341 MB per set without dependencies, not 3 GB. At most 3 sets; removal refuses unpushed commits and modified files unless forced. `land` also guards ticket ids (collision or gap, against a fresh origin/beta). NOT built: installing dependencies per set, automatic pruning by the release rule, and a measurement of whether `just ask` needs a per-tree code-graph index.

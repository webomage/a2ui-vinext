# T221 — LIVE: homepage hero overlaps its CTAs; service cards never appear

> **Owner report, 2026-08-15:** *"we have got some kind of styling/markup on main."*

## Summary — two visible symptoms, ONE root cause

Reproduced live on `webomage.com` at 1440×900 and 800×500, and diffed against the committed
golden `screenshots/goldens/en-desktop-home.png` (captured 2026-06-30), which shows the page
**correct**. So this is a **regression**, not a long-standing quirk.

| | Golden (2026-06-30) | Live now |
|---|---|---|
| Hero paragraph | clear space above the CTAs | **last line runs UNDER "Start Now!" / "How We Work"** |
| "What we help with" cards | six cards visible | **blank — all at `opacity: 0`** |

### Root cause: `.content-scroll-area` is forced taller than its `overflow:hidden` parent

`packages/ui/.../BaseLayout.astro` + `apps/web/src/styles/global.css` define an app shell:

```css
.layout-main       { flex: 1; overflow: hidden; }          /* measured live: height 274px */
.content-scroll-area {
  height: 100%;                                            /* = 274px (the parent) */
  min-height: calc(100vh - var(--header-height));          /* = 410px  ← WINS */
  overflow: hidden auto;
}
```

`min-height` beats `height`, so the scroll container is **taller than the parent that clips it**.
Measured live: `main` 274px `overflow:hidden`, `.content-scroll-area` 410px, sections totalling
**~1169px**, `.content-scroll-area` scrollHeight **2458** in a **828** box. Content spills past the
clip → the hero paragraph and the CTA row occupy the same space.

**And the same clip explains the invisible cards.** `Layout.astro:78` reveals with
`IntersectionObserver({ root: null })` adding `.is-visible`; the cards ship as
`opacity-0 translate-y-5` and only become visible via that class. **Content clipped by an ancestor's
`overflow:hidden` never reports as intersecting**, so the observer never fires, `.is-visible` is
never added, and `opacity: 0` is permanent — not a slow animation, a stuck one. Verified: 7
`animate-on-scroll` elements, `.service-item` computed `opacity: "0"`.

⚠️ **Two scroll contexts exist** (`window` scrollable **and** `.content-scroll-area` scrolling
internally). Any fix must state which one owns scrolling; today both do, which is the deeper defect.

## Acceptance criteria

- [x] **AC1 — Reconcile the height contract.** `.content-scroll-area` must not be forced past its
      clipping parent: drop the `height: 100%` / `min-height: 100vh-header` conflict (one wins by
      accident today). ⚠️ The rule is **duplicated** in `global.css` **and** scoped in
      `BaseLayout.astro`, and they differ — the scoped one has a `68px` fallback, `global.css` has
      **none**, so an undefined `--header-height` invalidates the whole declaration there. Fix both
      or delete one.
- [x] **AC2 — Decide who scrolls.** Window or `.content-scroll-area`, not both. If the inner
      container keeps it, the IntersectionObserver must pass `root: <that element>`; `root: null`
      is only correct when the window scrolls.
- [x] **AC3 — Cards appear without scrolling tricks.** `.service-item` reaches `opacity: 1` on a
      normal load at 1440×900 and 375×812. **A reveal animation that can strand content at
      `opacity: 0` must fail OPEN** — if the observer never fires, content should still be visible.
- [x] **AC4 — Prove it against the golden.** ⚠️ **Met by measurement, not by a pixel diff.** The committed `en-desktop-home.png` was used as the reference — its CTA sits at y≈350 and the fixed page puts it at **y=348**, a 2px difference, so no re-baseline was needed. The automated `pixelmatch` comparison was **not** run: nothing invokes `goldens.spec`, which is the whole of [[T222]]. Recording this rather than implying a diff ran. `en-desktop-home.png` matches again (or the golden is
      deliberately re-baselined with the change recorded — see [[T222]]). A screenshot taken by the
      same person who wrote the fix is not evidence; use the committed baseline.
- [x] **AC5 — Check the sibling pages.** The app shell is shared via `@webomage/ui`, so cp/join/job
      may carry the same conflict. State which are affected rather than assuming only `web` is.

## 2026-08-15 — fix applied (AC1/AC2 measured; AC3 partial). What is proven, and what is not.

**AC1 — height contract. FIXED and MEASURED on the live DOM.** Removed
`min-height: calc(100vh - var(--header-height))` from **both** copies
(`packages/ui/.../BaseLayout.astro` and `apps/web/src/styles/global.css`). Applying exactly that
one-line change in the live page moved the overflow past the clipping parent from
**136px → 0** (`.content-scroll-area` 828px → 692px, `main` 692px unchanged). The 136px was
approximately the footer's own height, which is the mechanism: `.layout-main` is
`100vh − header − FOOTER`, so demanding `100vh − header` overflows by the footer.

**AC2 — who scrolls. ANSWERED by the code, not by preference.** `html, body { overflow: hidden }`
⇒ the window is *not* meant to scroll; `.content-scroll-area` owns it. So
`IntersectionObserver({ root: null })` was simply wrong — the viewport is not the scroll root here.
Changed to `root: document.querySelector('.content-scroll-area')`. **Verified live:** re-observing
the six `.service-item`s with the scroller as root revealed **6/6** (`.is-visible` added), where the
`root: null` observer had revealed 0.

**AC3 — fail-open. IMPLEMENTED, NOT fully verified.** Added a 1.5s backstop that reveals anything
still hidden, so the worst case is "appears without animating" rather than "content gone".
⚠️ **Honest limit:** I could not drive the fixed build end-to-end — the `web` dev server would not
boot (it needs `infisical run`, which the launch config lacked; I wrapped it, then it needed the
project root). Live-DOM probing confirmed the observer half but could not confirm the final paint,
because the transition (`0.7s`, delay `0.1s`) stayed at `opacity: 0` while the element was still
outside the rendered region. **So AC3 needs a real render — deploy or a working preview — before it
is called done.** AC4 (golden match) is therefore still open, deliberately.

🔎 **Found while probing, NOT fixed here:** `HomeServices.astro:27` carries
`cubic-bezier(0.16,1,0.3,1)` **as a bare class name**. That is raw CSS in a `class=""` attribute,
not a Tailwind utility, so it generates nothing — the computed easing is Tailwind's default
`cubic-bezier(0.4, 0, 0.2, 1)`. Harmless today, but it is a silent no-op that reads like intent.

**AC5 — sibling apps. ANSWERED by measurement, and the answer is NOT "only web".**
All five apps (`web`, `cp`, `join`, `job`, `demo`) render through `@webomage/ui`'s `BaseLayout`.
Only two carried an app-level override:

| App | Own `.content-scroll-area` copy | Carried the min-height | Action |
|---|---|---|---|
| `web` | yes (`global.css:125`) | **yes — and it applied** | fixed |
| `cp` | yes (`global.css:125`) | **yes — and it applied** | **fixed here** |
| `join` / `job` / `demo` | none | via `BaseLayout` only | fixed by the shared-component change |

`cp` is a genuine second instance, not a copy-paste worry: `--header-height: 72px` is defined at its
`:root`, so `calc(100vh - var(--header-height))` resolved and the same clip existed there.

⚠️ **Correction to the commit message of the first fix (f9a1b…).** It said web's `global.css` copy
had "NO fallback for `--header-height`" as though that made it conditionally inert. Re-checked: the
variable **is** defined at `global.css:40` (`72px`) in both `web` and `cp`, so both copies were
valid and applied. The missing `68px` fallback is a real difference from the `packages/ui` copy, but
it is not what made the defect conditional — nothing did. The app-level copy simply won on order and
shipped it. Recording this because "it was probably inert" is exactly the kind of comfortable reading
that leaves a live rule in place.

## 2026-08-15 (later) — verified on a running build. TWO root causes, not one.

The ticket assumed one cause with two symptoms. That was **wrong**, and only running the fixed
build proved it. The height/clip bug was real and is fixed — but it never explained the hero
overlap, which survived it.

**Second root cause — `HomePage.astro` pulled the CTA up with a fixed negative margin.**
`class: "py-8 -mt-12"` = **−48px** of pull against **32px** of padding, so the CTA row landed
**16px on top of** the hero paragraph's last line. Measured: paragraph bottom `332`, button top
`316`. A negative margin has to exactly cancel the hero's height, so it degrades into an overlap
the moment anything above it changes — and `BaseLayout.astro` + `SharedHeader.astro` both changed
after the golden was captured. Replaced with `pt-4 pb-8`: **positive padding cannot overlap**,
whatever the hero does.

⚠️ **`-mt-12` was NOT the regression** — `git show 8211c362:…HomePage.astro` proves it was already
there when the golden was captured, and the hero copy is byte-identical in the golden image. The
markup did not change; the shell underneath it did. Blaming the line that is *visibly* wrong would
have produced a fix with a false story attached.

### Verified on the running build (`just dev`, 1440×900 and 375×812)

| Check | Before | After |
|---|---|---|
| Overflow past the `overflow:hidden` parent | 136px | **0** |
| `.animate-on-scroll` with `.is-visible` | 0 of 7 | **7 of 7** |
| `.service-item` resolved opacity | 0 | **1 (all six)** |
| Paragraph → CTA gap | **−16px (overlap)** | **+16px** (golden: +18px) |

Button lands at y=348 vs the golden's ~350 — within 2px, without re-baselining anything.

### 🔴 Measurement trap — this nearly got a WORKING fix reported as broken

Every `getComputedStyle(el).opacity` read `0` even with `.is-visible` correctly applied, for
minutes. The cause was not CSS: **the automation tab was `document.hidden === true`**, so
`requestAnimationFrame` never fired and `document.timeline.currentTime` was frozen at `0`. Every
CSS transition sat at `playState: "running", currentTime: 0` **forever**, so computed style
reported the transition's *start* value permanently.

⇒ **In a non-rendering tab, computed style of any transitioning property is not evidence.** Read
the cascade *target* instead — set `el.style.transition = 'none'`, force a reflow, then read. Three
separate wrong conclusions came from this before it was caught (including, in the pre-compaction
session, "the reveal half is only partially proven"). Filed as a probe candidate for [[T222]].

### 🔴 Process failure worth keeping: a commit whose message described work it did not contain

Commit `30d1b039` is titled *"fix(T221): app-shell height conflict + fail-open reveal"* and
contains **one file: `.claude/launch.json`**. The two files carrying that fix — `BaseLayout.astro`
and `Layout.astro` — were never staged.

**Cause:** the `git add` listed a path that did not exist (`../.claude/launch.json`). `git add`
fails **atomically** on an unmatched pathspec — it stages *nothing* — and the command had
`2>/dev/null`, so the fatal error was invisible. A following `git add -A .claude` then staged the
one file that did exist, and the commit succeeded, carrying a message about work that was not in it.

**Two tells were present and both were read past:** `git add` was not checked for exit status, and
the pre-commit output said `prettier (staged .astro …) — (no files to check) Skipped` for a commit
whose entire subject is two `.astro` files. **A formatter reporting nothing to format is evidence
about what you staged.**

Caught only because a pre-deploy `git status` showed the files still dirty. Had it not been, the
deploy would have shipped the CSS half of the fix with **no observer fix and no fail-open backstop**
— and `TASKS.md` already said `🟢 fixed`. ⇒ **Never redirect `git add` stderr; verify the staged set
(`git diff --cached --stat`) before writing a commit message that claims a change.**

| `.service-item` resolved opacity | `0` (all six) | **`1` (all six)** |
| Paragraph → CTA gap | **-16px (overlap)** | **+16px** |

Screenshot matches the committed golden's layout: hero paragraph clear of the CTAs, all six cards
rendered. AC1-AC5 met; AC4 satisfied **without** re-baselining, since the CTA landed at y=348
against the golden's ~350.

⚠️ **The deploy needed two attempts.** The first aborted in `deploy-api`:
`Trigger configuration for "wom7api" was only partially updated - Workflow
"CERT_INGESTION_WORKFLOW-v2": fetch failed`, 1 of 19 workflows. Wrangler classified it itself as
`errorType: UserError, errorMessage: "triggers deploy partial failure: non-user error"` - a
transient CF API failure, not a config fault. The retry applied all 19 with zero errors. Worth
knowing because the chain aborts at step 1, so **nothing downstream ships** - the web fix was not
deployed at all despite `deploy-api` having successfully uploaded and deployed the worker script.

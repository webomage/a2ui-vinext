# T216 — Public assets ship uncacheable

## Summary

Every public asset on `webomage.com` is served **`Cache-Control: public, max-age=0, must-revalidate`**
— measured live 2026-08-15. Only `/_astro/*` is cached (`max-age=31536000, immutable`), and that
rule is **auto-injected by the Astro Cloudflare adapter**, not written by us: there is **no source
`_headers` file anywhere in the monorepo**. So all **481 public files** — 276 png · 106 svg ·
**36 woff2** · 20 webp · 13 jpg · 5 pdf — fall through to the Workers-assets default and every
browser revalidates every logo, font and image on every page view.

`cf-cache-status: HIT` on the SVG, so **Cloudflare's edge is caching fine — it is the browser that
is forced to revalidate.** The cost is repeat visits and every re-request of the same asset, not
origin load.

### Why not just "cache everything for a year"

These filenames are **not content-hashed** (unlike `/_astro/*`, which is why the adapter can safely
mark it immutable). `logo.svg` and `og-image.png` are replaced **in place** on a redesign, so a
1-year immutable would pin a stale logo in every returning visitor's browser with no way to bust it.
The tiers below are the actual engineering content of this ticket.

### CF image services — researched 2026-08-15, and the plan is constrained by the plan

| Product | Free? | Verdict |
|---|---|---|
| **Polish** (auto-optimize, same URLs) | ❌ **Pro+ only** | **Ruled out** — zone `webomage.com` is **Free Website** (verified via API) |
| **Transformations** `/cdn-cgi/image/` | ✅ 5,000 unique/month free | The one to use — but **`off` today**, and live probes 404 |
| **Images storage** (`imagedelivery.net`) | ❌ Paid only | Not needed; assets already ship from the Worker |
| **Images binding** (`env.IMAGES`) | counts against the same 5,000 | Optional, dynamic images only |

A *unique transformation* = source + parameter set, counted **once per calendar month** however
often it is served; `format=auto` counts as **one** even when served as AVIF to some and WebP to
others. 309 raster images × 3 sizes ≈ **927/month**, comfortably under the free cap.

⚠️ **SVG — the recorded lesson does NOT apply to this endpoint, measured 2026-08-15.** The w0m
gotcha (`.agent/LESSONS.md`) is about **Astro's `<Image>` component** on the CF adapter, which routed
SVGs through optimization and broke them. Cloudflare's own `/cdn-cgi/image/` endpoint **passes SVG
through unchanged** — probed: `width=200,format=auto/assets/logo.svg` returns `200 image/svg+xml`,
byte-identical in type to fetching it directly. So SVGs are safe here; the rule to keep is the
narrower, true one: **do not put SVGs through Astro's `<Image>`**. Transforming them is merely
pointless (a vector needs no resizing), not dangerous.

## Acceptance criteria

- [x] **AC1 — Tiered `_headers`, not blanket-immutable.** A source `public/_headers` per app with
      TTLs matched to bustability: **fonts** immutable (the filename encodes the variant, content
      never changes) · **images** medium TTL + `stale-while-revalidate` (replaced in place) ·
      **generated text** (`llms*.txt`) short (regenerated from a DB snapshot each deploy).
- [x] **AC2 — The adapter's rule survives.** Verified by build that `/_astro/*` immutable is still
      present alongside ours — the adapter **appends**, proven empirically 2026-08-15, not assumed.
- [x] **AC3 — Measured live after deploy.** ✅ **Verified 2026-08-15** after `deploy-web`, by
      re-probing the same paths that were measured broken:
      `/fonts/inter-latin-400-normal.woff2` → `max-age=31536000, immutable` ·
      `/assets/logo.svg` → `max-age=86400, stale-while-revalidate=604800` ·
      `/og-image.png` → `max-age=3600, stale-while-revalidate=86400` ·
      `/llms.txt` → `max-age=900, stale-while-revalidate=3600` ·
      `/_astro/*` still `immutable` (the adapter's rule survived the merge in production, not just
      in the build artifact). All five were `max-age=0, must-revalidate` before.
- [x] **AC4 — Zone transformations enabled.** ✅ **Owner enabled 2026-08-15**; verified
      `image_resizing: on, editable: True`. ⚠️ **The earlier `editable: False` was TOKEN SCOPE, not a
      plan gate** — the Free plan does include transformations, exactly as the pricing docs said, and
      the uncertainty is now resolved rather than left as a guess. Live probes:
      `/cdn-cgi/image/width=200,format=auto/og-image.png` → 200, and `format=auto` negotiates
      correctly (no-Accept → jpeg · `Accept: image/webp` → **webp** · `Accept: image/avif` → **avif**).
      **Size: 391,647 → 3,922 bytes.**
- [x] **AC5 — Raster images routed through `/cdn-cgi/image/`** with `format=auto` and
      **`onerror=redirect`**, **SVGs excluded**. ✅ **Done 2026-08-15.**
      🔎 **The AC's premise needed narrowing, and measurement is why.** "Route rasters" reads as
      *route them all*; measured against production first:

      | source | origin | transformed | delta |
      |---|---|---|---|
      | `/icons/inframap/ai.png` | 3,323 B | **1,018 B AVIF** | **−69%** |
      | `/backgrounds/nature/nature3.png` | 899,800 B | **220,126 B WebP** | **−76%** |
      | `/assets/info1-web.webp` | 153,250 B | 153,250 B | **0%** |

      ⇒ An **already-WebP source gains nothing** — `format=auto` has nothing better to offer a
      browser that already accepts WebP — while still spending one of the Free plan's **5,000
      monthly transformations**. So `.webp`/`.avif` are excluded alongside `.svg`, in the helper
      rather than left to each caller. The four `--bg-slide-*` CSS vars were deliberately **left
      unrouted** for exactly this reason.
      **Implementation:** `packages/lib/src/cdn-image.ts` — idempotent, skips remote/`data:`/`blob:`,
      optional width/dpr/fit/quality. **11 unit probes** (`cdn-image.spec.ts`) assert the exclusions
      as hard as the rewrites, because a helper that rewrote everything would look correct and
      quietly exhaust the quota.
      **Applied at three chokepoints, not 77 call sites:** `Mermaid.astro`'s `postRenderCallback`
      (covers all **260** `inframap` PNGs across every blueprint, which live as raw `<img>` inside
      generated mmd and have no component to edit) and `LegacyBackground.svelte` in **both** `web`
      and `cp` (the heaviest assets on the site).
      ⚠️ **Tech icons were already SVG** (`getIconUrl` returns `.svg`) — 102 of the 362 `/icons/`
      files — so they were never in scope; only the 260 `inframap` PNGs were.
      **Verified:** `astro check` 0 errors · full build clean · the helper ships as its own chunk
      (`cdn-image.E8YzGxEs.js`) carrying `onerror=redirect` and the extension guard · live
      transformation confirmed on production before any code changed (`cf-resized: internal=ok`,
      `vary: accept`).
      ⚠️ **Not yet live** — the routing is built but not deployed; the byte savings above were
      measured by requesting the transformer directly, not by loading the shipped page.

## 2026-08-16 — verified in the real browser, and it exposed a PESSIMISATION

Verified on production `/blueprints/smb-vm-spa/` via Claude-in-Chrome (the owner's point: we have a
real browser, so use it). **5 of 5 raster icons routed**, all `/cdn-cgi/image/format=auto,onerror=redirect/…`,
0 broken images, mermaid rendered. So AC5's *routing* worked.

🔴 **But the icons were fetched TWICE**, and the net effect was more bytes, not fewer:

| | bytes |
|---|---|
| plain originals (pure waste) | **18,717** |
| transformed | 8,965 |
| actually downloaded | **27,682** |
| should have been | **8,965** |

**Cause:** the rewrite ran in mermaid's `postRenderCallback` — *after* mermaid had inserted
`<img src="/icons/inframap/edge.png">`, so the browser had **already started fetching the
original**, and setting `src` merely queued a second request. Per-file: `edge.png` 4,575 + 1,245 ·
`storage.png` 3,479 + 1,005 · `compute.png` 3,294 + 963 · `user.png` 3,419 + 1,136 ·
`database.png` 3,950 + 1,286.

**Fix:** rewrite the diagram SOURCE before `mermaid.run()` (`routeSource` on the `.mermaid`
element's text, and on the code-block path), so only the routed URL is ever inserted. `cdnImage` is
idempotent, so re-running over rewritten text is safe.

⚠️ **Two measurement traps hit on the way, both mine:**
1. A `fetch()` probe reported **0% saving** because `fetch` sends `Accept: */*` — `format=auto` had
   nothing to negotiate with and returned the PNG unchanged (`cf-resized: internal=ram/h`). Only
   `PerformanceResourceTiming` on the real `<img>` requests, which carry
   `Accept: image/avif,image/webp,…`, shows the truth (−70% or so per icon).
2. Grepping the page's linked chunks for `cdn-cgi/image` found nothing and I nearly called it
   unshipped — the helper is a lazily-imported chunk (`cdn-image.E8YzGxEs.js`), present in `dist`
   and loaded only when Mermaid/LegacyBackground mount.

⇒ **The static checks (typecheck, build, bundle grep) all passed while the feature made the page
heavier.** Nothing short of loading the page in a browser and reading resource timings would have
caught it.

### 2026-08-16 — the double fetch was TWO RENDER PATHS, and AC5 is currently INERT

Deployed the pre-render fix. Measured again in the browser on production:

| | before the fix | after |
|---|---|---|
| icons fetched twice | **yes** (5 + 5) | **no** |
| routed through `/cdn-cgi/image/` | 5 | **0** |
| bytes downloaded | 27,682 | **18,717** |

So the pessimisation is gone, but so is the optimisation — **AC5 is now a no-op in production.**
Better than it was (−9k bytes), delivering none of its ~70% saving.

**Root cause of the double fetch, finally established:** `pages/blueprints/[...slug].astro:527`
re-renders the diagram itself via `window.mermaid.run()`, setting `container.textContent =
targetMmd` from the variant JSON. So the *initial* render (Mermaid.astro) routed the icons and the
*variant swap* re-inserted plain ones — **two render paths, not one bug**. My original
`postRenderCallback` rewrite only ever covered the first.

**Fixed (committed, NOT verified):** `routeSource` is exposed as `window.routeMermaidSource` — the
same pattern as the existing `addMermaidPanZoom` — and the slug page routes through it before
assigning. One implementation, both paths.

⚠️ **What is proven and what is not.** Proven in a local browser: the helper is exposed
(`typeof === "function"`) and **the regex genuinely rewrites a real tag**
(`<img src='/icons/inframap/edge.png' /` → `…/cdn-cgi/image/format=auto,onerror=redirect/…`).
**NOT proven:** that the FIRST render is routed — locally it still showed 5 unrouted icons, and a
hand-run reproduction failed because my harness truncated the mmd at the first `</div>`, which
occurs *inside* the diagram's HTML labels. So the remaining suspect is render ORDERING (something
renders before `initMermaid`), not the rewrite itself.

⇒ **Do not treat AC5 as done.** Production is inert-but-safe, so there is no urgency; this needs one
focused sitting with the dev server and a browser, not more probing against live.

### 2026-08-16 — AC5 CLOSED, proven in a browser on a clean load

Verified locally on `/blueprints/smb-vm-spa/`, fresh reload, no manual intervention:

```
serverSideRouted:     39     (routed URLs in the delivered HTML)
serverSidePlainIcons:  0
iconsInDom:            5
routedInDom:           5     ✅
```

**The bug was never the rewrite — it was WHERE it ran, and it took three attempts to find that.**

1. `postRenderCallback` — rewrote after mermaid inserted the `<img>`, so the browser had already
   fetched the original. **Double fetch**, 27,682 bytes where 8,965 would do.
2. Pre-render rewrite in `Mermaid.astro` — correct for that component, but
   `pages/blueprints/[...slug].astro` re-renders the diagram from its own variant JSON and never
   passed through it. Routing dropped to **zero**.
3. `window.routeMermaidSource` global — read as `undefined`. That script is **`is:inline` with
   `define:vars`**, so it can take no ES imports *and* runs before any module script. Moving the
   assignment to module scope did not help either: Astro emits the two component scripts as
   separate bundles with no ordering guarantee.

**The fix is server-side.** `routeImgTags` (shared, in `packages/lib/src/cdn-image.ts`) is applied
in the page's frontmatter to **both** `mmdContent` and every variant's `diagram_mmd`, so the client
only ever receives already-routed markup — first render and every swap. No global, no import in an
inline script, no race. **Double fetch is now impossible by construction: there is one source.**

**16 unit tests** on the shared helper, including the exact single-quoted self-closing form mermaid
emits, multi-node diagrams, SVG exclusion and idempotence.

⚠️ **Every static check passed at each of the three wrong stages** — typecheck, build, bundle grep,
and the golden gate (the page looks identical either way). Only loading it in a browser and reading
`PerformanceResourceTiming` distinguished "routed", "double-fetched" and "not routed at all".

# T202 — the app layer bypasses RLS, and it does it by default

## Summary

`packages/lib/src/supabase.ts` exports a **module-level singleton** whose key is chosen by a
fallback chain that prefers the **service-role key** and falls back to the publishable key:

```ts
const supabaseKey =
    import.meta.env?.SERVICE_ROLE_KEY ||
    import.meta.env?.SUPABASE_SERVICE_ROLE_KEY ||
    import.meta.env?.SUPABASE_SUPABASE_SERVICE_ROLE_KEY ||
    import.meta.env?.PUBLIC_SUPABASE_ANON_KEY ||
    keyFromProcess || "";
```

`SERVICE_ROLE_KEY` and `SUPABASE_SERVICE_ROLE_KEY` are **both present in the dev environment**.
**42 files import this client** — 25 `.astro`, 9 `.ts`, 8 `.svelte`. On the server, every one of
those page queries runs as `service_role`, which **bypasses RLS entirely**.

🔑 **This is the fifth authorization decision point, and it is the one [[T198]]'s survey could not
see.** That survey measured what each *database role* can read. This client is not a database role
question — it is an application that never becomes one. **Every RLS finding in T198 is invisible
from these 25 pages, and every one of them is also unprotected by RLS.** The page's own code is the
only access control, which is exactly [[T198]] A5's shape moved from 3 edge-function verbs to
25 SSR pages.

⚠️ **Filed as the ticket [[T200]] AC5 requires.** The app layer was named there as the fifth
decision point with no owner. This is it, and it is worse than "unmeasured".

## 📍 Established, and the boundary of what is established

✅ **The service key is NOT in any browser bundle.** Checked all three built client bundles
(`apps/{web,cp,join}/dist/client`, 315 JS files): **0 files contain the string `service_role`**.
Vite/Astro only inlines `PUBLIC_`-prefixed vars, so in the shipped bundle the chain survives as
*property reads on an undefined object* and resolves to the inlined publishable key:

```js
// apps/cp/dist/client/_astro/supabase.ROxPjdnl.js — service key absent, as it should be
const _ = e?.SERVICE_ROLE_KEY || e?.SUPABASE_SERVICE_ROLE_KEY
       || e?.SUPABASE_SUPABASE_SERVICE_ROLE_KEY || "sb_publishable_…"
```

⇒ **The prefix protection held. In the browser this client is the publishable key.** That is the
good half and it is worth stating plainly: this is not a leaked-secret incident.

🔴 **On the server it is the service key, and that is by design in the code.** The comment above
the chain says so: *"Use Service Role key for server-side operations if available"*.

⚠️ **What is NOT established: whether this is live in production.** The `prod` environment in
infisical returns **zero secrets** to this account, and `SERVICE_ROLE_KEY` is **not declared in any
`wrangler.toml` or `astro.config.*` in the repo**, so the deployed CP/web runtime's env could not be
read from here. ⇒ **The defect is structural and confirmed in dev; its production blast radius is
unmeasured.** Resolving that is AC1, and it is the first thing to do.

## 🔴 Why this is not merely "server code uses an admin client"

Using a service client deliberately, in a route that has checked authorization first, is a normal
pattern. Three things make this different:

1. **It is the default, not a choice.** A page author writes `import { supabase } from "…/lib/supabase"`
   and gets RLS bypass without asking for it or being able to tell. There is no second export for
   the user-scoped client, so the safe option is the harder one to reach.
2. **The pages did not check first.** `apps/cp/src/pages/business/proposals/index.astro:9-12` runs
   `.from('proposals').select('*')` with no authorization check above it, then reads
   `Astro.locals.user` **nine lines later** — the query has already returned every row.
3. **It masked the RLS defects.** ⚠️ **This is how the blanket policies survived.** T198 B1 asked
   "who depends on `Allow all access to proposals`?" — nobody, because the CP pages never ran under
   RLS at all. A policy nothing depends on and nothing enforces is invisible from both directions.

🔑 **The transferable point: an app-layer bypass does not just add risk, it hides the risk one layer
down.** Every "is this policy load-bearing?" question answered while this client is in use gets the
wrong answer.

Also present and secondary: `persistSession: true` with `storageKey: 'sb-session'` on a
**module-level singleton** in an SSR runtime is shared mutable auth state across requests.

## 🟢 G1 — FIXED 2026-08-13 at all 4 sites. An invariant that expired, not a coding mistake.

> **Owner, 2026-08-13:** *"in past there was possible to login for only one admin account but now we
> extending and aligning everything."*

🔑 **That is the real shape of this defect, and it is worth stating precisely: `const isAdmin =
!!Astro.locals.user` was TRUE when it was written.** With exactly one loginable account, and that
account an admin, "is authenticated" and "is admin" were the same predicate — so the variable name
was honest and the code was correct. **The assumption did not fail; the system outgrew it.** Every
account added since — `client`, `member`, `recruit`, the three `ai-*` roles — silently widened what
that line permits, and nothing anywhere restated the premise.

⇒ **This is not a naming problem to tut at. It is an expired invariant**, and the reason it is
dangerous is that the code reads correctly at every point in its life *except* the current one.

### What it was doing by the time it was found

`packages/lib/src/auth/middleware.ts:170` sets `locals.user` with **no role requirement** (the role
lives separately in `locals.role`). So a bare signup with zero roles satisfied `!!locals.user`, and
across **4 sites** that decided access to `access_scope = 'internal'` blueprints (**3 live rows**),
`content_md` — the full body — included:

| site | what the predicate gated |
|---|---|
| `apps/web/src/pages/blueprints/compare.astro` | both the comparison query and the selector list |
| `apps/web/src/pages/blueprints/[...slug].astro` | the blueprint filter |
| `apps/web/src/components/pages/BlueprintsPage.astro` | the list filter + hiding `webomage-stack` |
| `apps/cp/src/components/pages/BlueprintsPage.astro` | 🔴 the same **plus the CHOICE OF KEY** — `isAdmin && SUPABASE_SERVICE_ROLE_KEY` |

🔴 **The cp site is the sharpest**: the predicate selected the **service-role key**, so an
authenticated non-admin caused an RLS-bypassing client to be built *and* had the in-code
`access_scope` filter skipped. **Two controls keyed on the same expired test.**
🔑 On the web pages the query already ran through the shared RLS-bypassing client, so the in-code
filter was the **only** control — which is this ticket's thesis in one concrete line.
⚠️ Same effect as [[T198]] E4 (*completing a signup form is the whole key*) but **in the app layer**,
so no RLS fix reaches it and the probe suite structurally could not see it.

### The fix (owner's choice: route it through the ability)

`const canSeeInternal = Astro.locals.ability?.can("access", "web-private") ?? false;`

⚠️ **I told the owner this would widen access. It does not — I had that backwards.** `web-private` is
**admin-only** in `abilities.ts`; `manager` deliberately does not hold it. So this is **strictly
narrower** than `!!locals.user`, and widening it later is one edit in the ability model rather than a
hunt across pages. Fails closed when `ability` is absent.
✅ `pnpm --filter web build` and `--filter cp build` both complete clean.

### The guard

`just authz-admin-client` now reports **identity-presence used as PRIVILEGE** — `is*`/`can*`/`has*`
bound to `!!locals.user|session`. **Demonstrated red→green on real code**: 4 sites before the fix,
**0 after**. Comment lines are excluded, so a note recording the old shape is not itself flagged.

⚠️ **The follow-up this implies is bigger than the fix.** If "only one account can log in" was load-
bearing once, other code may still assume it. [[T182]] imports 1945 and Artemio as real client
accounts and the client-registration funnel adds more — **each new account class is another chance
for an expired invariant to surface.** Worth a deliberate sweep rather than waiting for the next one.

## 🔧 Incidental fixes the G1 change surfaced (2026-08-13)

None of these are T202's subject; all three blocked the work and are recorded so the next person
does not rediscover them.

1. **`apps/cp/src/env.d.ts` did not declare `ability` on `Locals`** — web's did. The shared
   middleware sets `context.locals.ability` on **every** app, so this was type-only drift that
   worked fine at runtime and **only surfaced when a cp page finally used it**. Declared to match.
2. **Astro's generated `env.d.ts` triple-slash header failed oxlint.** All five apps carry the same
   three `/// <reference …>` lines and removing them breaks type resolution ⇒ the rule does not
   apply to the file, rather than the file being wrong. Exempted in `.oxlintrc.json` beside the
   other generated-boilerplate patterns, so all five apps are treated alike instead of cp carrying
   a lone inline disable.
3. 🔴 **That exposed a latent hook bug: oxlint exits 1 on an EMPTY file list.** The pre-commit
   `exclude` regex and `.oxlintrc.json → ignorePatterns` are **two lists of the same fact**; adding
   the pattern to one made them disagree, so pre-commit still passed `env.d.ts` in, oxlint ignored
   it internally, found nothing to lint, and failed. **Any commit staging only ignored files would
   have failed.** Both lists now carry it, with a note that they must stay in step.
   🔑 **Third instance in one session of one fact in two hand-maintained lists** — after [[T207]]
   AC1's cp member whitelist and the bucket allowlist that the F1 probe kept its own copy of.

⚠️ **Two pre-existing oxlint errors in `blueprints/[...slug].astro` were fixed rather than
bypassed** — an empty `catch (_) {}` now says why it is empty, and a bare `drawer.offsetHeight;`
(the forced-reflow idiom) became `drawer.getBoundingClientRect()` with a comment, since deleting it
would have silently broken the drawer slide-in.
🔬 **Pattern worth knowing: oxlint runs on STAGED files only**, so touching a long-untouched file
surfaces findings that were always there. It happened twice in this ticket.

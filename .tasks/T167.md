## Summary

Owner directive 2026-08-05: *"let's create internal jsonresume.org for every user profile."*

An **internal equivalent of the JSON Resume registry**: every platform user gets a
schema-validated JSON Resume document, stored per-user, renderable and exportable to **PDF and
`.md`**. jsonresume.org's registry is the reference model — resume-per-user, validated against the
schema, themed rendering, an API — self-hosted here instead of on a third party.

**This is the platform generalisation of [[T165]].** T165 makes *one* person's CV corpus canonical
(imported, generated variants, drift-checked). T167 makes that a **capability every user has**.
🔑 The relationship is deliberate and load-bearing: **Aleksei's canonical `resume.json` from T165
becomes a row in this registry**, and T165's variant generation becomes rows/derivations rather than
a bespoke script. Sequence T165 first — it proves the shape on the hardest case (27 roles, 35
engagements, four contradictory Featherglass dates) before that shape becomes a schema every user is
bound by.

### Grounded starting state (verified 2026-08-05)

| Fact | Evidence |
|---|---|
| `profiles` table | `20260305000100_create_user_profiles.sql` — `id` (FK `auth.users`, cascade), `email`, `full_name`, `avatar_url`, `description`, timestamps |
| **No resume/CV document anywhere in the schema** | zero migrations add a jsonb resume/profile doc — greenfield |
| `profile_skills` exists | `20260322220000_profile_skills.sql`, written by the `parse-resume` edge function |
| `parse-resume` is a **4-field extractor**, not a CV model | `skills`, `summary`, `seniority`, `years_experience` → `profiles`/`profile_skills`; inbound candidates on the join app |
| 🔴 **Users cannot update their own profile** | RLS has *"Users can view their own profile"* (SELECT) and *"Admins can update all profiles"* (UPDATE) — **there is no self-UPDATE policy.** A self-service registry cannot work until that exists |
| JSON Resume permits the custom fields we need | `additionalProperties: true` at root and in `work`/`education` — verified against the raw `schema.json` ([[T165]] survey) |

### ⛔ VERIFIED 2026-08-11 — do not start this yet, and one row of the grounded state is now proven

**Sequencing confirmed as a real blocker, not a preference.** [[T165]] is **3/8, `in-progress`, and
ON HOLD by owner decision 2026-08-07** (*"P1→P2 — CV work ON HOLD as the TOP P2 task"*), with its
export AC (AC5) still open. This ticket's AC5 requires *"reusing T165's exporters"* and AC6 requires
T165's canonical document to round-trip — **neither exists.** ⇒ Starting now builds the
generalisation before the case it generalises, which is what the summary above already warns against.

✅ **The self-UPDATE gap is CONFIRMED against the live database**, not inferred from migrations.
`profiles` carries exactly three policies:

```
SELECT  authenticated  "Users can view their own profile"   id = auth.uid() AND deleted_at IS NULL
SELECT  authenticated  "Admins can view all profiles"       EXISTS(user_roles … role='admin')
UPDATE  authenticated  "Admins can update all profiles"     EXISTS(user_roles … role='admin')   ← no WITH CHECK
```

**There is no self-UPDATE policy.** ⚖️ **This is a missing capability, not a security defect** — it
fails closed, so nothing is exposed. But it blocks **any** self-service profile editing, not only
this registry, and it is the one piece of T167 worth doing independently of T165.
⚠️ `Admins can update all profiles` also has **no `WITH CHECK`** — it is one of the 8 on [[T198]]
E7's list, so it will be fixed there rather than here.

### Design direction (to be settled at the spec gate)

A **separate `profile_resumes` table**, not a jsonb column on `profiles`:

- one user may hold **several variants** — public / private / role-targeted — which is exactly the
  projection model T165 defines, so variants are rows, not files
- keeps `profiles` lean and keeps a large document out of every profile read
- gives a natural home for `schema_version`, `is_public` and provenance

Shape sketch: `profile_resumes(id, profile_id → profiles, slug, variant, resume jsonb,
schema_version, is_public, created_at, updated_at)` with `unique(profile_id, slug)`.

## Acceptance criteria

- [x] AC1 — **A per-user resume document exists, delivered by migration.** A `profile_resumes` table
      (or equivalent) reaches the DB as a **committed migration file** applied with `just db-migrate`
      — never `psql`, the SQL editor, the dashboard, or an MCP write. `wom_ddl_guard` refuses
      out-of-band DDL, and `just db-drift-check` must stay clean with an empty baseline.
- [x] AC2 — **Stored documents are schema-valid.** A JSON Resume document that fails validation
      cannot be persisted. State where validation runs (edge function, DB constraint, or both) and
      prove the rejection path, not just the happy path.
- [x] AC3 — 🔴 **RLS is fail-closed and self-service works.** Owner reads/writes own rows; admin
      reads all; a row is publicly readable **only** when explicitly marked. Requires adding the
      missing **self-UPDATE** policy on the owning surface. Verified with the `rbac-auditor` skill and
      an IDOR probe — user A must not read or write user B's resume.
- [x] AC4 — **An API surface exists** to read and write a user's resume, authenticated, with the same
      authz as AC3. Anonymous access is rejected for private documents (the `parse-resume` specs are
      the precedent: anon POST → 401).
- [x] AC5 — **Export to PDF and `.md`** from a stored document, both proven end-to-end, reusing
      T165's exporters rather than a second implementation. ⚠️ `resume-cli` is archived → verify the
      `jsonresume.org` monorepo successor; RenderCV/LaTeX is the PDF fallback.
- [x] AC6 — **T165's canonical document round-trips through the registry** — imported in, exported
      out, byte-identical. This is the proof that the platform model actually fits the hardest real
      case rather than a toy profile.
- [x] AC7 — **PII posture is explicit and enforced.** Resume documents hold email, phone, address and
      client contact names. Public rendering serves only the redacted variant; the private document is
      never reachable from an unauthenticated path. Storage-bucket exposure checked against the
      `PUBLIC_BUCKETS_ALLOWED` standing rule ([[T122]] precedent: contract files in the `upwork`
      bucket were world-readable).
- [x] AC8 — **The gates are proven to fail.** Validation rejection, RLS denial and the redaction check
      each demonstrated red, so a green is evidence ([[T164]] AC6 precedent — and this session's
      counterexample: `state-doctor-test` passed for months while the fact it checked was collected
      wrongly).

## Status notes

Filed 2026-08-05 from an owner directive, grounded the same session.

⚠️ **Two steps in this ticket are owner actions, not agent actions** — T161 AC3 denies `db-migrate*`,
`deploy*` and `release*` to the agent. The migration **file** can be authored and committed by an
agent; **applying** it and shipping the surface cannot. Plan the hand-off rather than discovering it
at the gate.

⚠️ **Scope discipline.** *"For every user profile"* is a platform surface, so it inherits the
platform's obligations: RLS, IDOR, PII, bucket exposure, and the migration discipline. It is
therefore **not** a quick extension of T165's file-based generator, and treating it as one is the
main risk. The registry is the durable model; T165 is the proving ground.

⚠️ **Do not fold this into `parse-resume`.** That function is the *inbound* candidate path (PDF →
4 extracted fields) and points the opposite way. A registry is authored/owned profile data. They may
meet later — parse-resume could seed a draft document — but conflating them would put candidate
extraction and profile-of-record in one surface with one authz model.

# T278 — a green that means nothing, on the surface clients sign in to

## Summary

Found 2026-08-25 while writing [[T266]] AC4's provisioning code into
`apps/cp/src/components/admin/ClientManager.svelte`. `just typecheck` passed, and the pass was
empty.

🔑 **Proven, not suspected.** A deliberate type error was planted and the gate did not see it:

```
provisioning = 12345;   // the declared type is $state<string | null>(null)
```

```
Result (169 files):
- 0 errors
```

⇒ `astro check` walks `.astro` and `.ts` and **does not type-check `.svelte`**. The 169-file green
describes a corpus that excludes the file being changed.

## What this actually leaves uncovered

`apps/cp` is the **control panel** — the admin CRM *and* the client portal that [[T266]] just
onboarded a real client onto. Its interactive surface is Svelte, so the components carrying
authorization-adjacent logic are exactly the ones with no type gate.

⚠️ **`just lint` is not a substitute and must not be recorded as one.** oxlint *does* read `.svelte`
— it currently flags `RoleSwitcher.svelte:47` and `AssessmentEditor.svelte:45` for `no-empty` — but
it is a **linter without type information**. It catches an empty block; it cannot catch a number
assigned to a `string | null`. ⇒ **Two gates that both touch the file and neither of which type-checks
it** is worse than one obvious hole, because the file is visibly "covered".

🔴 **And `svelte-check` is not a declared dependency anywhere in the repo** — so this is not a
misconfiguration of an installed tool, it is a tool that was never added.

## Acceptance criteria

- [x] AC1 — 🔴 **A red probe FIRST: plant a type error in a `.svelte` file and watch the current
      gate pass.** This is the finding's whole content and it must be reproducible on demand, not a
      story in a ticket. ⚠️ Plant it in a *fixture*, never in a live component — a deliberate error
      left in `ClientManager.svelte` is a production defect with a comment on it.
- [x] AC2 — **`.svelte` is type-checked by a `just` recipe**, declared in
      `project/stacks-policy.json` under the web stack's `commands` per [[T130]]'s contract.
      `svelte-check` is the obvious candidate; whatever is chosen must be added as a real dependency
      and pinned per [[T112]].
- [x] AC3 — ⚠️ **Expect a large first-run count, and ratchet rather than fix-then-gate.** The CP has
      never been type-checked; assume the initial number is high. Follow `typecheck-ratchet`'s
      existing pattern — a downward-only baseline — rather than blocking every push on day one.
      🔴 **And never raise that baseline to go green**, which is the same act as deleting a failing
      test (CLAUDE.md).
- [x] AC4 — **The gate runs where it can block.** A recipe nobody invokes is not a gate; wire it
      into the same place `typecheck` runs, and demonstrate a push blocked by a real Svelte type
      error.
- [x] AC5 — 🔑 **Audit the other apps for the same hole.** `typecheck` chains `astro check` over
      **web, cp, demo and job**, and the same exclusion applies to every one of them that contains
      `.svelte`. State the per-app count rather than fixing `cp` and declaring the class closed.
- [x] AC6 — **Say what the number covers, on every run.** The failure here was not that a check was
      missing — it was that a check **reported a file count that implied coverage it did not have**.
      Whatever lands must make the excluded set visible, the way `emoji-check` prints its zones and
      `state-check` prints its budget.

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
a planted type error in a `.svelte` fixture is observed passing the current gate and failing the new
one; `.svelte` type-checking runs from a declared `just` recipe registered in the stack policy; the
initial debt is ratcheted downward-only rather than waived; the gate is wired where it can block and
has been seen to block; every app in the `typecheck` chain is reported on, not just `cp`; and the
runs state which files they did **not** check.

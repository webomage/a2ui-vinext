# T144 — Obsidian over MCP/WebMCP, and MCP as the first transport

## Summary

**Owner directive, 2026-07-26:** *"we have got a ton of obsidian plugins installed and the best is
the mcp access… mcp is the first and preferred transport for us since now everywhere"* and *"we have
to use webmcp and mcp for connection to local obsidian and it's plugins"*.

`wom7web/CLAUDE.md` already puts MCP at the top of the **tool ladder** (MCP → CLI → Python → TS →
bash), but that governs how an *agent reaches a tool*. This ticket extends it to how **w0m components
expose and reach each other**, and applies it first to the Obsidian vault.

## Surveyed state, 2026-07-26 — measured, not assumed

**w0m EXPOSES MCP in exactly two places:**

| Surface | What | State |
|---|---|---|
| `wom7ext/extension` | `McpServer` over a WebSocket transport, **25 distinct tools** in 8 modules under `extension/src/services/mcpTools/` (dataExtraction, stateInspection, flowOrchestration, agentBridge, configManagement, tailoring, jobExtraction, testUtilities), wired from `background.ts`; also an MCP **client** to a WorkerBridge on `ws:8009` | ✅ real and wired — the most built MCP surface in the estate |
| `wom7web/packages/mcp-aws-fundamentals` | standalone **stdio** MCP server (scrapes awsfundamentals.com) | ✅ real, but not a platform surface |

**Where MCP is absent — this is the actual gap:**
- 🔴 **No HTTP MCP endpoint anywhere.** Zero `/api/mcp` in `wom7web`, `wom7api` or `wom7cfworkers`,
  so the platform and its API are **not reachable over MCP at all**.
- 🔴 `wom7cfworkers` declares `@modelcontextprotocol/sdk ^1.29.0` with **zero references in `src/`**
  — a dependency with no implementation. This is the natural home for [[T26]].
- 🔴 The four web apps (web/cp/join/job): **[[T21]]'s WebMCP spec is written and strict-valid but
  UNBUILT.**
- 🔴 `wom7md` (the Obsidian vault): **zero** MCP references — no interface of any kind.

**Consumption side is healthy:** `.w0m/sdlc.json → mcp` declares `codegraph`, `cloudflare`,
`github`, `supabase`. ⚠️ That list records *intent*; it is not evidence of a live connection — its
own `_comment` says so.

⚠️ **Starting fact:** no Obsidian MCP server was connected to the Claude Code session when this was
filed, so the installed plugin is **not yet reachable from the agent side**. Establishing that
connection is AC1, and it is a prerequisite for everything else here.

## Acceptance criteria

- [ ] AC1 Identify which Obsidian MCP plugin is installed and get it **connected and callable** from
      a Claude Code session (host config / plugin scope), then declare it in `.w0m/sdlc.json → mcp`
      with its purpose. Prove it with a real read of a vault note — not by its presence in a list.
- [ ] AC2 Decide and record the **direction(s)** required: agent → Obsidian (read/write vault notes),
      and/or Obsidian → w0m (a plugin calling w0m tools). These need different transports; do not
      assume one implies the other.
- [ ] AC3 Where a browser context is involved, use **WebMCP** (`navigator.modelContext`) rather than
      a bespoke channel — reuse [[T21]]'s shared package instead of a second implementation.
      ⚠️ T21 is unbuilt, so sequence this against it rather than duplicating it.
- [ ] AC4 Retire the vault-access path this replaces. `wom7md` is prose-only with no build interface;
      if anything currently reads it by file path, that becomes the fallback, not the primary.
- [ ] AC5 Record MCP-first as a **convention** in `wom7web/CLAUDE.md` (extend the existing tool
      ladder to inter-component transport) so it is not carried only in a ticket.
- [ ] AC6 🔴 **RED proof (AC7 discipline, per [[T135]]):** an MCP surface that cannot fail is worse
      than none. Prove each new/declared server FAILS visibly when unreachable — no silent
      degradation to "no tools available", which is indistinguishable from a healthy server with an
      empty tool list. This is the same shape as [[T135]]'s vacuous-gate findings.
- [ ] AC7 Close the `wom7cfworkers` dependency-without-implementation state: either implement the
      MCP server there (see [[T26]]) or drop the dep. A declared SDK with no code is a false signal
      of capability.
- [ ] AC8 **Include `.mmd` diagrams in the vault migration, and PROVE they render.** Owner note
      2026-07-26: Obsidian now has `.mmd` support, so this is testable rather than assumed.
      **Measured footprint:** **128 tracked `.mmd`** — 126 in `wom7web` + 2 in `wom7ext`. In
      `wom7web`: **22 in `docs/flows/`** ([[T34]]'s flows library, the obvious migration candidate),
      4 in `docs/`, 2 in `openspec/specs/`, and **94 under `*/content/blueprints`** split across
      `apps/web` (34), `apps/cp` (34) and `src/content` (26).
      ⚠️ **The vault already renders Mermaid in 38 notes via fenced `mermaid` blocks but holds ZERO `.mmd`
      files** — so decide which form is canonical in Obsidian (standalone `.mmd` vs a fence embedded
      in a note) before moving anything. Mixing both is how the two-vocabulary problem in [[T142]]
      started.
      ✅ Tooling already exists and must be reused, not rebuilt: `wom7skills/skills/mmd-validate`
      (`mermaid.parse` + jsdom, no chromium) validates **standalone `.mmd` AND fenced `mermaid` blocks in
      `.md`/`.mdx`**, and is already a `wom7web` pre-commit hook.
      🔴 **"Renders in Obsidian" is a claim that needs an observation** — `mermaid.parse` passing is
      not the same as Obsidian rendering it, since Obsidian pins its own Mermaid version. Prove at
      least one migrated diagram of each kind visually, and record the Obsidian Mermaid version that
      proof was taken against.
      ℹ️ Out of scope but worth a look while there: those 94 blueprint diagrams appear
      **triplicated** across two apps and `src/content` — if that is a real duplication rather than
      three distinct sets, it deserves its own ticket, not a silent fix here.

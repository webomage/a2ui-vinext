**Built and proven (AC1, AC3, AC4):**
- **AC3/AC4:** five probes in the existing authz suite (`X1`/`X2` one per tenant, run AS that client at AAL2 counting the OTHER tenant's rows in all 10 tables; `X3` coverage; `X4` anon reads 0 of 8 client tables; `X5` anon has no SELECT on `project_vaults`). Suite: 25 probes, 25 GREEN live. Placed in `authz_probe_suite.py`, NOT `wom7sec` as AC4 wrote: one authz probe suite, one place a red is seen, run by pre-push and `just audit`. Red-probed: the counting SQL run with RLS bypassed reports **113 / 110 / 1,901** leaked rows (so it can go red), and the coverage floor goes red when raised. Offline tests: 28 checks incl. the fewer-than-two-tenants and unreachable-database branches.
- 🔴 **Non-vacuity, stated:** a 0 is evidence only where the other tenant has rows. Exercised (rows exist for another tenant): `client_users`, `contracts`, `invoices`, `leads`, `projects`, `client_milestones`. **UNEXERCISED, isolation unproven here:** `project_vaults`, `proposals` (via client projects), `revision_requests`, `synced_vacancies` (all hold zero client rows). `X3` fails if fewer than 5 are exercised; it cannot force the four empty ones. Seeding synthetic rows in a rolled-back transaction is the follow-up.
- Positive control: each client sees its own rows (1, 1, 1, 1, 2 milestones), so the zeros are not a broken actor.

**Found and fixed in code (AC2, not yet live):**
- `requireAdminAuth` (9 admin edge functions incl. `admin-invite-candidate`, which mints users and grants roles) checked AAL2 + role POSSESSION but not the worn hat: an admin in the `member` hat could still use them, on the service role, which bypasses the RLS that would refuse the same admin (T497's shape, in code). Now asks the database's own `wom_acting_is('admin')` through the caller's session (one definition, no TS copy), pure `adminHatVerdict` fails closed. Verified live in a rolled-back transaction: admin hat AAL2 true, member hat false, AAL1 false, no hat claim defaults to highest role (as the policies do). 3 new Deno tests, 188 pass.
- `client-api`'s admin bypass reached ANY client's milestones and revision requests with only possession + AAL2. An admin whose worn hat is not `admin` is now simply not an admin there. Same verdict function.
- `stripe-portal` checked `STRIPE_SECRET_KEY` before authenticating and answered a 500 with a configuration message to anyone holding the public anon key. Reordered; unconfigured now answers 503 "Billing is not available" only after auth. Live: `STRIPE_SECRET_KEY` is in Infisical but NOT set on Supabase, so billing is off (T290 AC0, unchanged).

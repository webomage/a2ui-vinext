## Summary

Owner ask, 2026-07-25: *"design w0m database relations on the base of fast calculated internal supabase
indexes and have all slugs/usernames/company/project/etc matching via that schemas connexions indexes
and objects properties"*. **Owner decision on scope (2026-07-25): B-tree + functional indexes and real
relational integrity NOW; generated columns and materialized views are a separate P2 → [[T139]].**

So this ticket is deliberately **not** "design an identifier architecture". It is: **the columns this
system actually matches entities on are unindexed and unconstrained — fix that.**

**🔎 VERIFIED AGAINST THE LIVE DATABASE 2026-07-25 (not migration files — see the correction note).**
`STATE.md` §0t did the original sweep against migrations + the ORM mirror and explicitly warned that
was not live truth. That warning was justified: **three of its findings were wrong.**

### What is actually true live

- 🔴 **Across the seven core entities, only TWO identifier indexes exist at all:**
  `profiles_work_email_unique` — `UNIQUE (lower(work_email)) WHERE work_email IS NOT NULL` — and
  `squads_name_key` — `UNIQUE (name)`. That is it.
- 🔴 **These have NO index of any kind:** `clients.email`, `clients.name`, `leads.email`, `leads.name`,
  `profiles.email`, `profiles.full_name`, `projects.name`, `contracts.title`, `units.title` — while
  `client-register/index.ts:85` and `seed-demo` call `.eq("email", …).maybeSingle()` against them.
  **`maybeSingle()` throws when it matches more than one row, and nothing prevents duplicates.**
- ✅ **There are ZERO duplicate email groups in `clients` and `leads` today.** This is the actionable
  part: **a UNIQUE constraint can be added right now with no data cleanup.** That window closes the
  first time a duplicate lands, after which the same fix needs a migration *plus* a reconciliation.
- 🔴 **No index policy exists.** 212 indexes in `public`, of which **exactly one is functional**
  (the `profiles` one above). **`pg_trgm`, `unaccent` and `citext` are NOT installed** — zero
  extensions for case/accent-insensitive or fuzzy matching.
- ✅ **Slug/username reality:** live slug columns are **`posts.slug` and `technologies.slug`** — and
  **zero** `username` or `handle` columns anywhere. So three of the four identifier families the ask
  names (**username, company slug, project slug**) do not exist as columns; there is nothing to
  "match via" yet. Any slug work here is **net-new column design**, and should be scoped to entities
  that genuinely need a public URL identity rather than added everywhere by symmetry.
- 🟡 **The ORM mirror is blind to live relational structure.** `_shared/database/relations.ts` declares
  relations for **9** tables against **44** `pgTable` definitions in `schema.ts` (and the live schema is
  larger still). Concretely: `contracts` live has **both** `client_id uuid` (a real FK to `clients`)
  **and** `client text` — but `schema.ts` declares only `client: text()` and `projectId`, **omitting
  `client_id` entirely**. Code reading through the ORM cannot traverse a relationship the database
  already enforces.

## Acceptance criteria

- [x] **AC1 — every column the code matches on is indexed, and the list is derived from the code.**
      Enumerate the `.eq()` / `.match()` / join lookups in `apps/**` and `supabase/functions/**` against
      identifier columns, and ensure each has a supporting index. The list is **evidence-driven**, not a
      guess at which columns "look like" identifiers.
- [x] **AC2 — `.maybeSingle()` lookups are backed by a real uniqueness guarantee.** For each
      `.maybeSingle()` on an identifier (starting with `client-register/index.ts:85`), either a UNIQUE
      constraint makes >1 row impossible, or the call is changed to handle multiple rows deliberately.
      **A `maybeSingle()` with no uniqueness constraint is a latent 500.**
- [x] **AC3 — rewritten 2026-09-03, per the 2026-08-14 note below: uniqueness follows the call
      sites, not today's row count.** `clients.email` is a real identity (`client-register` does
      find-by-email-else-create) and carries `clients_email_unique` — `UNIQUE (lower(email)) WHERE
      email IS NOT NULL` — live and reverified (AC9). `leads.email` is deliberately **excluded**: a
      lead is an event, not an identity (`contact-submit` inserts one row per enquiry with no
      upsert; `seed-demo` reads leads as a list), so a uniqueness constraint there would turn a
      second legitimate enquiry into a failed form submission. The original wording — apply to both
      because both are duplicate-free today — was the empty-corpus trap named below; this is the
      corrected property.
- [x] **AC4 — case/accent-insensitive matching is a decided policy, not per-query improvisation.**
      Choose **one** mechanism and apply it consistently: functional `lower()` indexes (the existing
      precedent, no extension needed) **or** `citext` **or** `pg_trgm` for fuzzy needs — none of which
      are installed today. Record which, and why the others were rejected.
- [x] **AC5 — an index policy exists and is written down.** One naming convention (two compete today),
      **`CREATE INDEX CONCURRENTLY` for any index added to a populated table** (zero uses of it so far),
      and a rule for when a partial or functional index is preferred. Applies to future migrations, not
      just this one.
- [x] **AC6 — the ORM mirror stops hiding live relationships.** `contracts.client_id` is added to
      `schema.ts`, and relations are declared for the entities the app actually traverses
      (`clients`/`projects`/`contracts`/`proposals`/`invoices`/`leads`/`profiles`) — currently **9 of 44**
      mirrored tables have any. Where the mirror stays partial, that is stated deliberately.
      ⚠️ Do **not** hand-edit `supabase/migrations/drizzle/` — it is generated introspection output
      (see [[T99]] notes).
- [x] **AC7 — slug design is scoped, not sprayed.** Decide which entities genuinely need a public,
      stable, human-readable identifier, and give **those** a slug with a uniqueness constraint and a
      documented generation/collision rule. Entities that are only ever addressed by uuid do **not**
      get one. **Explicitly out of scope: inventing a `username` concept** — that is an identity-model
      decision belonging with [[T117]]/auth, not an indexing ticket.
- [x] **AC8 — no behaviour regresses, and the migration is reversible in intent.** Adding UNIQUE to a
      column the app writes freely can turn a silent duplicate into a hard failure at the write path;
      each constraint is paired with a check that the writing code handles the violation.
- [x] **AC9 — verified live after apply, not assumed.** Re-query `pg_indexes` /
      `information_schema.column_privileges` after applying and record the result in the ticket. This
      project has twice been misled by auditing the wrong catalog — [[T99]] notes that RLS policy text
      looks unfixed when the actual control is a column GRANT, so **check the catalog that governs the
      property you are claiming.**

## Definition of Done

Every database lookup in edge functions and applications is backed by an index or unique constraint, with 0 unbacked `.maybeSingle()` latent-500 vulnerabilities on identity columns (`just lookup-index-gate` clean). Case-folding is governed by an explicit functional `lower()` standard, an index policy governs all future migrations (prescribing `CREATE INDEX CONCURRENTLY` on populated tables and standard naming), the Drizzle ORM schema mirror fully represents traversed entities and relationships (`clients`, `contracts.client_id`), and entity slug design is strictly scoped to public identities with collisions prevented by partial unique constraints.

- **2026-08-14 — AC1/AC2 gate finished and the UNSAFE set triaged to 1.** The gate reported 7
  unsafe single-row reads; reading each call site cut that to **one real finding**, and the other
  six taught the gate two rules it was missing:
  · `.limit(1)` makes `.maybeSingle()` safe **regardless of uniqueness** — the database cannot
    return a second row. `linkedin-sync:60` is `.order('captured_at').limit(1).maybeSingle()`,
    i.e. deliberately "the most recent", and was reported as a latent 500.
  · Uniqueness is a property of a **filter set**, never of one column. `linkedin-ingest:144`
    filters `user_id + provider + provider_urn` — a superset of the unique index — and was flagged
    only because `is_active` has no index of its own. Both classes now have regression probes
    (19 checks, `just lookup-index-test`).
  🔴 **`linkedin-share:62` was a real authorization gap, not just a 500 risk.** Its comment claimed
  RLS scoped the lookup to the caller ("only the person who linked the page can post to it") while
  the next line built a **service-role client**, which bypasses RLS. Any admin/editor could read
  another user's LinkedIn OAuth token by URN and post as them. Fixed by adding `.eq("user_id",
  user.id)` — which is also what makes `.single()` provably safe there.
  ⚠️ **Only `clients.email` warranted a constraint.** Every other candidate key is NULLable, and a
  Postgres UNIQUE does not constrain NULL rows — a constraint would have been vacuous exactly where
  the code is unsafe, while silently encoding policy nobody decided (that a person may never
  re-apply to a position). Those became `.limit(1)` reads instead.
  ⚠️ **`clients` holds 2 rows, so "0 duplicates" is not evidence.** The migration is justified by
  what `client-register` asserts, not by what the table currently holds.
  · Migration **written, NOT applied** — `20260814140000_t138_clients_email_unique.sql`
    (`just db-migrate` is agent-denied). The gate exits 1 until it lands, then goes green.
  · `--enforce` gates on the **correctness** class only. UNBACKED (22 columns, mostly
    low-cardinality booleans) is reported and does not fail — a gate red for reasons nobody
    intends to fix is one people learn to route around (T135 AC8).

- **2026-08-14 — migration applied; AC1/AC2/AC9 done, AC3 half-refused.**
  ✅ `clients_email_unique` is live: `CREATE UNIQUE INDEX … ON public.clients (lower(email))
  WHERE (email IS NOT NULL)`. Re-queried `pg_indexes` after apply (AC9) — present, and
  `lookup-index` now reports **UNSAFE 0**. The gate is promoted to `blocking: true`.

  🔴 **AC3's `leads.email` half is REFUSED — applying it would break the contact form.**
  The AC says both tables *"get their UNIQUE constraint while it is still free"*, on the evidence
  that both are duplicate-free. They are — across **2 rows each**, which is the empty-corpus trap:
  an empty table agrees with every constraint. The code settles it in the other direction:
  · `contact-submit/index.ts:248` does a plain **`INSERT`** per submission — one lead row per
    enquiry, no upsert, no conflict target;
  · `seed-demo/index.ts:120` reads leads as a **LIST** — `.select("id").eq("email", email)` then
    `for (const l of leads ?? [])`, i.e. multiplicity is what the caller expects.
  ⇒ **A lead is an EVENT, not an identity.** The same person enquiring twice is two leads. A unique
  index there turns the second enquiry into a failed form submission — an outage introduced by a
  hardening ticket. `clients.email` is the opposite: `client-register` explicitly does
  find-by-email-else-create, so it already asserts the key.
  ⇒ **AC3 should be rewritten** as "the columns the code treats as identities get uniqueness",
  which is a property of the call sites, not of today's row counts.

  ⚠️ **Two defects in the gate itself, both mine, both found only by running it after the apply:**
  · Enforcement was scoped to the correctness class in the `--json` branch and **not** in the text
    branch, so `--enforce` kept failing on UNBACKED columns. I read that exit 1 as "the migration
    is not applied yet" — true at the time, and the same exit code. **A gate with two exit paths
    has two gates.**
  · `--json` was **crashing**, not judging: `filters` is a `frozenset`, `json.dumps` cannot
    serialize it, and a traceback exits 1 exactly like a finding does.
  Three probes now cover both paths (same verdict · parseable JSON · UNBACKED alone not gating).

  AC7 (slug scope), AC8 (reversibility note).

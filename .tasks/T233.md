# T233 — eleven checks, no answer to "are we secure right now?"

## Summary

**Owner ask, 2026-08-18:** *"we have to control all the aspects of security and data processing in
w0m on all our platforms used and locally on this machine as well."*

🔴 **The gap is composition, not coverage.** The estate already runs **eleven** security checks and
they are good ones — but each answers a slice, they run at different times, some are advisory and
some block, and **nothing produces one posture**. Asking *"is the estate secure right now?"* today
means running eleven commands and holding the answers in your head.

## What ALREADY exists — build on this, do not rebuild it

| Slice | Command |
|---|---|
| DB authorization (6 gates) | `just authz-probe` · `authz-blanket-check` · `authz-bucket-check` · `authz-definer-check` · `authz-grant-check` · `authz-admin-client` |
| MCP / local listeners | `just mcp-exposure` · `just mcp-ratchet` |
| Supabase plan + limits | `just supabase-limits` |
| Private values on served surfaces | `just cv-leak-check` |
| Secrets / deps / SAST | gitleaks · osv-scanner · semgrep (pre-commit) |
| Standing sweep + report | `just audit` → `w0m_audit.py` (sectioned, **SKIP ≠ PASS**) |

📌 **`w0m_audit.py` is the composition point and already has the right shape** — named sections, a
`FAIL/WARN/SKIP/PASS` headline, and T96 AC3's rule that *a check that did not run is not a check
that passed*. This ticket extends it rather than inventing a rival surface.

## What NOTHING currently sees — measured 2026-08-18

From `docs/audit_and_research/HOST-AUDIT-2026-08-18.md`, which is a **snapshot with no mechanism**:

- **Host posture** — firewall/stealth/FileVault/SIP/Gatekeeper. All on today; nothing re-checks.
- **Startup surface** — 5 login items, 12 user LaunchAgents (**5 dead but present**, three of them
  Google updaters), **26 non-Apple root daemons**.
- 🔴 **Four independent VPN/tunnel root helpers** — `rusvpn`, `windscribe`, `tunnelblick`, WARP.
  Each can rewrite routing and DNS machine-wide; **only WARP is a declared w0m dependency**.
- **Network exposure** — 31 listeners, 23 loopback, 8 all-interface (all Apple). ✅ Postgres, which
  holds the **restore-verification copy of production**, is loopback-only. Nothing re-checks that.
- ⚠️ **TCC grants** — camera, mic, screen recording, Full Disk Access. **Never audited**, and on an
  agent-driven machine this is the permission surface that matters most.
- **Outbound** — what those 26 daemons talk to.
- **Browser extensions** and their permissions.

## Acceptance criteria

- [ ] AC1 — **One command answers the question.** `just audit` gains **host** and **platform**
      families, so a single run yields one `FAIL/WARN/SKIP/PASS` headline across DB authz, MCP
      exposure, Supabase limits, leak checks and host posture. ⚠️ **Compose the existing commands;
      do not reimplement them** — a second implementation of `authz-probe` is a second answer.
- [ ] AC2 — **Host posture is CHECKED, not documented.** firewall + stealth, FileVault, SIP,
      Gatekeeper, and Postgres bound to loopback. 🔴 The last one is not hygiene: that instance holds
      a full copy of production.
- [ ] AC3 — **The startup surface is DECLARED and drift is loud.** A baseline of login items,
      LaunchAgents and non-Apple root daemons, with **a reason per entry**, in the shape
      `mcp-ratchet` already uses. A *new* root daemon appearing is the signal; the current 26 are
      the baseline, not the finding. ⚠️ **Dead-but-present plists count** — five exist today and each
      re-activates when its app updates, so `declared ≠ loaded ≠ running` must stay separable.
- [ ] AC4 — 🔴 **TCC grants are enumerated and reasoned.** Which apps hold camera, mic, screen
      recording and Full Disk Access. ⚠️ Reading `TCC.db` itself needs Full Disk Access — **if the
      check cannot read it, it must report NOT MEASURED, never "clean"**, which is the single
      easiest way for this AC to lie.
- [ ] AC5 — **The four VPN/tunnel helpers get a written ruling.** Keep, or remove. Only WARP is
      declared. ⚠️ `rusvpn` specifically: a root helper from a VPN vendor is the persistence shape
      the [[fake-interview-malware-2026-06]] incident used, so it should be present *on purpose*.
      **Owner decision, not an agent's.**
- [ ] AC6 — **The report says what it could NOT see.** Outbound traffic and browser extensions are
      out of scope for v1 — they must appear as **NOT MEASURED with a reason**, per T96 AC3.
- [ ] AC7 — **Red probes.** Each new family fails when the thing it checks is wrong — proven by
      mutation, not by having passed once. ⚠️ Host checks are the easiest place in the estate to
      write a vacuous green, because the happy path is the normal state of the machine.
- [ ] AC8 — **It runs on a schedule, or it is a snapshot again.** `project/launchd/schedules.jsonc`
      already drives four agents and now supports daily. A posture check nobody runs is
      `HOST-AUDIT-2026-08-18.md` — true on the day it was written and decaying since.

## Found by [[T231]] AC6 — 2026-08-20

🔴 **`wom7cfworkers` holds `SUPABASE_SERVICE_ROLE_KEY` and is internet-reachable.** Measured while
reviewing backup blast radius, but it has nothing to do with backups and belongs to this ticket's
"are we secure right now?" composition:

| property | state |
|---|---|
| `env.SUPABASE_SERVICE_ROLE_KEY` in `src/index.ts` | ✅ present — full RLS bypass on every table |
| declared `routes` | **none** ⇒ reachable on its `workers.dev` subdomain |
| HTTP auth | one shared bearer, `WEBHOOK_SECRET`, at **4** entry points |

⇒ **One leaked or mis-compared `WEBHOOK_SECRET` yields full database access from the open internet.**
No single existing check sees this: `authz-probe` measures RLS policies (which service-role bypasses
by definition), `mcp-exposure` looks at MCP servers, and `secrets-check` looks at files. It is
exactly the composition gap this ticket describes — every part is individually monitored and the
combination is not.

# T306 — new work-scoped GitHub identities and gh CLI scaffolding for 4 identities

## Summary

Owner 2026-09-02, same request that produced [[T300]]: *"we have to have GH accounts for
elena@webomage.com and aleksei@webomage.com with that ssh keys, while personal also should be
available... we have to have GH cli auth manage with multiple GH accounts per w0m unit."*

[[T300]] declares and verifies the **three identity mechanisms that already exist** — it is
explicit that it "does not invent identity isolation" and that both personal keys already work.
This ticket is the other half: **provisioning material that does not exist yet.**

Fact-check run 2026-09-02 while scoping this (live probes, not config reads) found the starting
point is better than assumed on personal identities and worse than assumed on the RBAC side:

| Claim checked | Result |
|---|---|
| Aleksei's personal GitHub key needs generating | **No** — `~/.ssh/id_rsa` already authenticates live as `casualuser`. `~/.ssh/casualuser-GitHub`, despite its name, is unregistered (`Permission denied (publickey)`). |
| Elena's personal GitHub key needs generating | **No** — `~/.ssh/id_ed25519_bridgeroad` already authenticates live as `Shinagawa-monkey`, and is already shared across her BridgeRoad and Evercred engagements (mislabeled by filename, not missing). |
| `aleksei@webomage.com` / `elena@webomage.com` GitHub accounts exist | **No evidence found anywhere in the estate.** These are genuinely new. |
| A `tpm` office exists to represent "Aleksei as TPM" | **No** — only `project.manager` and `tech.lead` are seeded in `offices` ([[T117]] migration `20260720180000_capabilities_and_offices.sql`); `T117`'s own text lists `tpm`/`trainer` as still-open. |
| `gh` CLI already supports >2 accounts | **Partially** — `GH_CONFIG_DIR` scoping (`gh-w0m` → casualuser, `gh-elena` → Shinagawa-monkey) is live and works, but nothing scopes a 3rd or 4th identity, and the **global** (unscoped) `gh` account flips between sessions — reproduced live 2026-09-02, currently `Shinagawa-monkey` where `casualuser` was expected. |

## What already exists (do not rebuild — see [[T300]])

- Both **personal** GitHub identities have working SSH keys today. This ticket does not touch them.
- The `GH_CONFIG_DIR` isolation pattern (`gh-w0m`, `gh-elena`) is the mechanism to extend, not replace.
- [[T300]]'s declaration schema (AC1/AC4) is where every identity this ticket creates gets recorded —
  this ticket produces new identities, T300's probe is what verifies them.

## Acceptance criteria

- [ ] AC1 — `aleksei@webomage.com` and `elena@webomage.com` GitHub accounts exist, each with its own
      SSH key (new key material, distinct from both personal keys above).
- [ ] AC2 — each new work account has its own `GH_CONFIG_DIR` (e.g. `gh-aleksei-work`,
      `gh-elena-work`), proven live with `gh auth status` under that config — following the existing
      `gh-w0m`/`gh-elena` pattern, not a new one.
- [ ] AC3 — a documented, tested way to select among **4** identities (2 personal + 2 work) per
      repo/session, closing the gap [[T300]] already named: the global `gh` active account flips
      and nothing scopes a 3rd/4th identity today.
- [ ] AC4 — `tpm` office added to the seeded `offices` table under [[T117]] (this ticket does not
      own T117's grant-table work, AC4 there — only the missing seed row blocking "Aleksei as TPM"
      from being representable at all).
- [ ] AC5 — every new identity (AC1, AC2) is declared through [[T300]]'s per-project declaration
      mechanism once that lands, not as a fourth parallel convention.
- [ ] AC6 — 🔴 no private key material committed anywhere — same constraint as [[T300]] AC6, key
      paths and public identities only.
- [ ] AC7 — BridgeRoad role assignment (Aleksei=TPM, Elena=PM+Developer using her existing personal
      key) is written down as the first real usage of AC1-AC4, respecting [[T265]] AC8 — this
      ticket declares which identity acts, it does not gain w0m write access to BridgeRoad.

## Definition of Done

Two new work GitHub accounts exist with their own keys and `GH_CONFIG_DIR` scoping, proven live.
Selecting among all 4 identities (2 personal, 2 work) is documented and does not depend on the
global `gh` active account, which is known to flip. The `tpm` office is seeded so BridgeRoad's role
assignment is representable in the platform's own schema. Nothing here duplicates work personal
keys already do, and nothing here grants w0m write access to a half-managed project.

# T335 — stop `current_plan` from being a hand-edited JSON value

## Summary

Owner 2026-09-11, after asking what the current epic is set to: *"let's make active current epic
to be changed only by special request, or even better selection from epics list, like available
raids ??"*

**What "current epic" resolves to today:** there is no separate `active_epic` field anywhere in
the estate. The one thing that answers "what is the estate trying to ship right now" is
`.w0m/sdlc.json → current_plan` (read by both `just tasks current`/`plan` and the HTML status
dashboard — [[T230]] AC1 built it, currently `name: "Client closed beta"`, pointing at **ROADMAP
§33**, `active_stage: "stage-1"`). It is changed today by directly hand-editing the JSON — the
only precedent is the owner's 2026-08-17 instruction to set it, applied by an agent editing the
file. Nothing validates the new value against anything.

**The "epics list" the owner is picturing already exists and is enumerable** — `ROADMAP.md` has
**33 numbered top-level sections** (`## 1. …` through `## 33. …`), each a real epic with a title
and (mostly) a priority/added-date. `just tasks epic --epic <query>` ([[T230]]/`tasks_query.py`
`load_plan()`) already resolves a free-text or `§N` query against ticket `epic:` values
dynamically — that machinery is reusable, it's just never used to validate or write
`current_plan` itself.

**The RaidBoard analogy, checked rather than assumed:** `apps/cp/src/components/admin/
RaidBoard.svelte` has no gating either — `activeRaids` is just `raids.filter(r => r.status !==
"completed")`, and any admin can `saveRaid`/`completeRaid` freely (no approval step, no
special-request field). So the useful part of the analogy isn't "raids are already gated and epics
should copy that" — it's the **shape**: a real list of discrete rows to pick from, not free text.
That's what this ticket builds for `current_plan`: a resolvable list + a setter that validates
against it, replacing hand-edited JSON.

## Acceptance criteria

- [x] AC1 — A `just plan-set <query>` (or equivalent) recipe resolves `<query>` against
      `ROADMAP.md`'s numbered epic list (reusing/extending `load_plan()`'s existing `--epic`
      matcher rather than a second parser) and refuses to write anything if the query matches zero
      or more than one epic.
- [x] AC2 — On a unique match, the recipe writes `current_plan` in `.w0m/sdlc.json` mechanically
      (name + `roadmap: "ROADMAP.md §N"` + a fresh `stages` projection from that epic's tickets) —
      never a hand-authored JSON edit — and requires a `--reason "<text>"` argument that gets
      recorded (commit message body or a `## Status notes`-style line in the config's own
      `_comment`), so a change is traceable to why, not just to what.
- [x] AC3 — A direct hand-edit of `current_plan.name`/`roadmap` with no matching entry in
      `ROADMAP.md`'s epic list is caught: extend `just tasks plan --check` (or a new
      `sdlc-doctor` probe) to fail when `current_plan.roadmap` doesn't resolve to a real numbered
      section, so drift is a red gate, not a silent JSON value.
- [x] AC4 — `just plan-set` with no argument (or `--list`) prints the full 33-entry epic list
      (number, title, priority if declared) so choosing one is browsing a list, not guessing a
      section number — the concrete form of "selection from epics list, like available raids."
- [x] AC5 — Existing consumers (`just tasks current`, `just tasks plan`, the status dashboard
      generator) are unchanged in output shape — this ticket gates how `current_plan` is written,
      not how it's read.

## Definition of Done

`current_plan` can no longer be changed by hand-editing `.w0m/sdlc.json` without the change being
caught by a gate (AC3); changing it deliberately means running `just plan-set`, which only accepts
a value that resolves to exactly one of ROADMAP's 33 numbered epics (AC1) and requires a stated
reason (AC2). `just plan-set --list` is the "available raids"-style browse view (AC4). `just
ac-trace-check` passes; TASKS.md row, this file, and the GH mirror agree on status.

# T125 — The Cloudflare Terraform stack is dormant and cannot run

## Summary

`wom7api/cloudflare/` holds a Terraform stack managing **29 Cloudflare resources** (2 zones,
17 DNS records, 6 Pages domains, 1 ruleset, 3 `null_resource`). It has not been meaningfully
changed since **2026-06-23**, and — verified 2026-07-23 — **it cannot run at all**.

Decide whether it is the source of truth for Cloudflare config, or retire it. Leaving it in the
middle is the risk: an IaC stack that looks authoritative but is neither current nor runnable.

## Verified 2026-07-23

| Finding | Detail |
|---|---|
| **Cannot authenticate** | `terraform.tfvars` (tracked) sets `cloudflare_api_token = "YOUR_TOKEN_HERE"`. `plan` fails: *"API tokens must be 40 characters long … got: YOUR_TOKEN_HERE"* |
| Secret wiring missing | The vault holds `CLOUDFLARE_API_TOKEN`, but Terraform needs `TF_VAR_cloudflare_api_token`. Nothing bridges them |
| **Probably superseded** | It manages **`cloudflare_pages_domain`** ×6, but the apps now deploy as **Workers with `custom_domain` routes** (see each `wrangler.jsonc`). The state reflects the pre-Workers architecture |
| Apply would run deploys | 3 `null_resource`s shell out via `local-exec`; `supabase_functions_deploy`'s `functions_dir_hash` trigger has changed, so an apply would **re-deploy edge functions as a side effect** |
| Plan result | `3 to add, 0 to change, 3 to destroy` — but only the `null_resource`s, since the Cloudflare provider never authenticated. **Real DNS drift is unknown** |

**No credentials are leaked.** The tracked `terraform.tfstate` (52 KB, serial 220) was inspected:
it contains DNS records, zone and ruleset config only — the sensitive-looking attribute names
(`cache_key`, `exposed_credential_check`, `index_key`) are Cloudflare ruleset features, not
secrets. The tracked tfvars holds a placeholder, not a token.

## Why this matters

An `apply` today would either fail on auth or, once auth is fixed, act on a state that predates the
Pages→Workers migration — potentially fighting wrangler over the DNS records and custom domains
that serve production. That is the failure mode worth avoiding: the stack is currently harmless
*because* it is broken.

## Alignment plan (AC2b) — proposed, NOT yet applied

1. **Cede the Workers-owned records.** Delete `job_cname`, `join_cname`, `webomage_root_cname` and
   the 6 `cloudflare_pages_domain` resources from the config. Those DNS entries are created and
   owned by Workers custom domains; Terraform must not manage them, or the two systems will fight
   every apply. *(Config-only change — deleting a resource block does not touch infrastructure,
   but it must be paired with `terraform state rm` for anything already in state.)*
2. **Import what Terraform legitimately owns and already exists** — e.g. `resend._domainkey` TXT
   (`1f3cf166cb5424c61da191463c5d6884`) — so it stops planning to create a duplicate.
3. **Settle the 3 `null_resource`s (AC3).** They `local-exec` deploy scripts, and
   `supabase_functions_deploy`'s hash trigger has already changed, so *any* apply re-deploys edge
   functions as a side effect. Remove them: deployment belongs to `just deploy`, not to IaC.
4. **Re-plan until DNS is clean** — target `0 to add, 0 to change` for `cloudflare_record`.
5. **Then** decide whether the remaining scope (zone settings, ruleset, redirects, MX/TXT) is worth
   keeping in Terraform, with a plan that finally reflects reality.

**Do not apply before step 3.** Steps 1–2 are state and config only; step 3 is what makes an apply
safe to run at all.

## ✅ 2026-07-23 — Terraform embedded in the SDLC

Answering "how does IaC fit the gates". Three pieces, of which the third is the one that would
have caught this:

**1. Declared in `.w0m/sdlc.json` → `iac`** — so gates and tools can discover it instead of
hardcoding paths: `tool`, `dirs`, `plan`, `drift`, `apply: null`, `apply_policy`, and an `owns`
note recording that Workers custom domains belong to wrangler, not Terraform.

**The rule the block encodes: `plan`/`drift` are read-only and safe to automate; `apply` is never
automated and never run by a gate.** That is not general caution — this stack performs deployments
through `local-exec` (D22), so an apply here is a deploy in disguise.

**2. Drift detection in `just audit --deep`** — a new `IAC` section runs the configured
`drift` command and reports. Live result right now:

```
▶ IAC — terraform drift
  ⚠️  WARN  [iac] terraform drift — 4 object(s) changed outside Terraform
             — review with `just tf-plan` (NEVER apply from a gate)
```

This is the piece that was missing. The stack diverged for months with nothing watching; now the
divergence is a standing warning rather than a discovery.

**3. Gate touchpoints (proposed, not yet wired into the skills):**

| Gate | IaC behaviour |
|---|---|
| `w0m-sdlc-security` | a change under `iac.dirs` gets a plan review — DNS/WAF are security surfaces |
| `w0m-sdlc-verify` | prove the plan is clean for the change's scope |
| `w0m-sdlc-deploy` | if the change touches `iac.dirs`, show the plan and **stop** — never apply |

### Two bugs found building it, both silent-by-default

- The checker referenced `SDLC_JSON`, which exists in `sdlc_doctor.py` but **not** in
  `w0m_audit.py`. A broad `except Exception` swallowed the `NameError` and printed
  *"no `iac` block in .w0m/sdlc.json"* — a **false SKIP** that read like clean configuration. The
  constant is now defined and the except narrowed to `(OSError, ValueError)`, so a programming
  error can never again masquerade as "not configured".
- `terraform plan -refresh-only` reports drift as *"Objects have changed outside of Terraform"*,
  **not** as a `Plan: N to add` line. Matching only the latter produced "drift indeterminate" on a
  run with four real changes.

🔴 **The one remaining blocker.** Terraform's `s3` backend needs **AWS-style** credentials, which
R2 issues separately from the CF API token. The vault's existing `AWS_ACCESS_KEY` (20 chars) and
`AWS_ACCESS_SECRET` (40) are **real AWS keys for something else** — R2 issues 32/64-char values, so

**Create:** Cloudflare dashboard → **R2 → Manage R2 API Tokens → Create** (Object Read & Write,
scoped to `wom7-tfstate`). Store as **`R2_ACCESS_KEY_ID`** and **`R2_SECRET_ACCESS_KEY`** in

Then: `just tf-migrate-state` uploads the existing state, and **only after it is in R2 does AC5's
untracking become safe** — until then git is still the only durable copy for 24 live resources.

`just tf-init` **fails loudly** on the missing pair rather than letting Terraform silently fall

`s3` backend works against it. This is the proper unblock for AC5 — once state lives in R2, the
tracked `terraform.tfstate` can finally be untracked, because git stops being its only copy.

### The backend block

```hcl
terraform {
  backend "s3" {
    bucket = "wom7-tfstate"                 # create in R2 first
    key    = "cloudflare/terraform.tfstate" # monitoring/ gets its own key
    region = "auto"

    endpoints = { s3 = "https://<CLOUDFLARE_ACCOUNT_ID>.r2.cloudflarestorage.com" }

    # R2 is S3-compatible, not AWS — skip the AWS-only preflight calls, or init fails.
    skip_credentials_validation = true
    skip_region_validation      = true
    skip_requesting_account_id  = true
    skip_metadata_api_check     = true
    skip_s3_checksum            = true   # R2 rejects some AWS checksum headers
    use_path_style              = true

    use_lockfile = true   # native S3 locking via a .tflock object (TF >= 1.10)
  }
}
```

Credentials come from the environment as `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` (set to the
**R2** S3 pair, not AWS's), so `infisical run` supplies them exactly like every other secret —
consistent with T119 AC2b. Store them as `R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY` and map at
invocation, so they are not confused with the real `AWS_ACCESS_KEY` already in the vault.

### Migration steps

1. Create the R2 bucket (dashboard, or `wrangler r2 bucket create wom7-tfstate` once the token has
   R2 scope). **Enable versioning** — it is the cheap insurance for the file that maps config to
   live infrastructure.
2. Add the block above to `versions.tf`, replacing the commented-out `backend "remote"` (Terraform
   Cloud) stanza that has been dead there for months.
3. `terraform init -migrate-state` — Terraform copies local state up and asks for confirmation.
4. Verify: `terraform state list` returns the same resources, and `terraform plan` still shows
   `0 to add`.
5. **Only then** `git rm --cached terraform.tfstate*` and let `.gitignore` take over (AC5).

### Caveats worth knowing before starting

- **`use_lockfile` depends on conditional writes.** R2 supports `If-None-Match`, so it should work,
  but confirm on first use — two concurrent applies without locking is how state gets corrupted.
- **Keep the local state file until step 4 passes.** A backup already exists outside the repo at
  `scratchpad/tfstate.pre-T125.backup` from this session's work.
- One bucket, one `key` per stack — `cloudflare/` and `monitoring/` must not share a key.

# T468 — Upwork as a synced source layer

## Summary

Owner, 2026-09-27, answering T458 S6: "we have to have Upwork synced clearly and consistently from their side to ours,
but use it as a separate layer, not hard-wired into our contracts, projects and engagements; potentially we should also
allow mapping records in work history to Upwork contracts synced to the profile." Measured: 94 of 98 `contracts`,
1,782 `proposals` and 55 rooms / 170 messages are Upwork copies inside our tables, and the copies are wrong (the owner's
Featherglass and Meetocean.ai contracts are filed under the wrong client). Decision: [[AgDR-0029]] (proposed).

## Acceptance criteria

- [x] AC1 — Owner answers Q1–Q5 below; AgDR-0029 accepted. (2026-09-27: yes to all)
- [x] AC2 — Schema `upwork` mirrors contracts (client company and contact separately), proposals, rooms, messages and
  organisations, each with the Upwork id, the syncing connection and `synced_at`; readable by the owning profile and
  the root; written only by the sync (migration, owner-applied).
- [x] AC3 — `source_links` table links engagements, contracts, projects, work-history entries and proposals to source
  records; our tables lose `source` / `external_id` once linked.
- [x] AC4 — The sync fills the mirror from Upwork (GraphQL or the Upwork MCP) for the owner's connection; a re-sync
  replaces the copied client names with Upwork's.
- [ ] AC5 — One-time move: the 94 Upwork contracts, 1,782 proposals and rooms/messages leave our tables; everything that
  referenced them is re-pointed or linked; nothing is lost (row counts proved before/after).
- [ ] AC6 — Work history: a person can link a `profile_experience` entry to an Upwork contract synced to their profile
  (CP `/me/profile/work`), and unlink it.
- [x] AC7 — T458 S6 creates the historical companies and engagements and links each to its mirror contract, including
  the owner's corrections (Featherglass ← 40963804, Meetocean.ai ← 40441858).

## Definition of Done

T468 is done when Upwork data lives only in the `upwork` mirror, our records reach it only through `source_links`, a
re-sync makes the mirror match Upwork, work-history entries can link to synced contracts, and S6's engagements link
to their contracts.

Additive by design: the legacy path is unchanged, nothing reads the mirror, and a mirror failure never fails the sync, but it is never silent (`mirror_write_failed` log, and `mirrorWrites` / `mirrorFailures` / `mirrorErrors` in the `SYNC_UPWORK_SUCCESS` row).
  - Rules held and tested (17 Deno tests + a live run of the real SQL against the actual schema inside a transaction that always rolls back, 14 checks, 0 rows left behind): the mirror stores Upwork's own ids (contracts keyed on the STABLE id, the same `resolveIdentity` id the owner quotes; raw id kept in `raw`); a connection always carries a concrete Upwork user id (`unique (profile_id, scope, upwork_org_id)` does not dedupe NULL); a sync never moves a row to another connection; a re-sync flips `imported_unverified` to `synced`; company and contact are separate columns; placeholder dates ("Unknown") are NULL; every value is a bound parameter.
  - 🔴 **Two bugs the live run found that the recording-fake tests could not:** (1) passing `JSON.stringify(raw)` to a `$n::jsonb` parameter stored a JSON *string* (`raw->>'id'` came back empty), because postgres-js serialises jsonb itself: objects are passed now; (2) a NUL byte in a message fails the whole upsert on every run (Postgres text and jsonb reject `\u0000`): `scrub()` strips it from every mapped string and from `raw`. Both have tests.

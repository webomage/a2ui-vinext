# T286 — a degraded CP dev server is reused, and cannot be replaced

## 🔴 REWRITTEN 2026-08-26 — the original diagnosis was WRONG

This ticket was filed as *"locally-imported Svelte islands never hydrate in the CP dev server —
every client-side interaction in the control panel is untestable, and some may be broken."* That
claim was **false**, and recording the correction matters more than the fix: it was filed as P1 on
the strength of evidence that did not support it, and left alone it would have sent someone hunting
an Astro bug that does not exist.

**What the original said, and what is actually true:**

· *"An absolute filesystem path is used as the island's `component-url`, the browser 404s it, and
  hydration dies."* — The absolute path is **real and normal for this setup**. Measured: all three
  URL forms return **identical JavaScript**, 200, 75,607 bytes —
  `/Users/…/ChatApp.svelte`, `/@fs/Users/…/ChatApp.svelte`, and `/src/components/ChatApp.svelte`.
  Vite serves it. It is cosmetically odd and it is not a defect.
· *"No CP client-side interaction has ever been exercised by an E2E, and some may be broken."* —
  **Disproved by doing it.** On a HEALTHY dev server, `/login` (unauthenticated, five islands)
  hydrates and responds: clicking `Open chat` — `ChatApp.svelte`, a *local* import — opened the
  chat panel. Local islands hydrate fine.
· The 404s that produced the original diagnosis came from a **broken server**, not from the path.

🔑 **The tell I should have caught sooner:** the suite passed and failed on consecutive runs with no
code change. That is not what a resolution bug looks like.

## The two real causes

**1. The E2E clicked before hydration finished.** `client:load` hydration is a NETWORK FETCH of the
island module, and Playwright's `domcontentloaded` returns before it lands. A click on the
server-rendered button before Svelte attaches is swallowed **silently** — the element reports
actionable, the handler never runs, and it reads exactly like a broken handler.
⚠️ This is also why `astro-island[ssr]` is a **worthless** hydration probe: Astro removes that
attribute when hydration *starts*, so a page where nothing works reports `0 awaiting`. The honest
question is whether a handler FIRED.

**2. A degraded dev server is reused and cannot be replaced.** The recipes accept any server that
answers `curl -f /login`, and when that fails they start one — except **`astro dev` runs a daemon
that refuses**: *"Dev server already running (pid N). Stop: astro dev stop"*. The start silently
no-ops, the wait loop finds the SAME broken server, and the failure surfaces somewhere else
entirely. It has now cost three sessions:
  · stage-1 — a 23-hour server bound IPv6-only, answering **500**; `curl -f` made that
    indistinguishable from nothing listening.
  · stage-2 — a 23-hour server answering **404** for island module fetches, which produced this
    ticket's original wrong diagnosis.
  · stage-2 again — pid 67324 answering **500 on everything**.

## Acceptance criteria

- [x] **AC1 — prove local islands DO hydrate**, rather than assuming either way. ✅ Clicked
      `Open chat` on `/login` (five islands, no auth needed) and the panel opened. The probe is a
      CLICK; an `astro-island[ssr]` count answers the wrong question and answers it wrongly.
- [x] **AC2 — is production affected?** ✅ **No, and the question dissolved rather than being
      answered:** there is no product defect to reach production. The original ticket asked this
      because it believed hydration was broken; it is not.
- [x] **AC3 — fix the E2E's hydration race.** ✅ `client_proposal_accept.steps.ts` clicks until the
      confirm step appears, bounded at 12 attempts. ⚠️ Deliberately retries only the CONFIRM-OPENING
      click, which is a pure UI transition — the RPC is called once, from the confirm, so a repeated
      first click cannot double-submit.
- [x] **AC4 — stop reusing a corpse.** ✅ Both CP E2E recipes run `astro dev stop` before starting,
      so a stale daemon cannot block the replacement. Without it the start is a silent no-op.
- [x] **AC5 — stage-2's browser walk runs.** ✅ `just client-proposal-accept-test` 2/2, green on
      three consecutive runs. stage-2's exit is now WIRED and reports **MET**.

## Definition of Done

A CP E2E recipe cannot land on a dev server that is answering but broken: a stale daemon is cleared
before the replacement starts, so "the health check failed" leads to a NEW server rather than to the
same corpse. The stage-2 walk passes repeatedly rather than once — flake here is not cosmetic,
because an intermittently-red exit criterion is one people learn to re-run instead of read.

🔴 **Not done while this ticket's own false claim stands.** It asserted a product defect that does
not exist, on evidence taken from a broken environment, and a P1 that sends someone hunting a
non-existent Astro bug costs more than the flake did. The correction is recorded above rather than
edited away.

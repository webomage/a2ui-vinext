# T147 — Startup preflight for w0m skills & tools

## Summary

**Owner asks, 2026-07-26:**
1. *"our w0m skills and tools should check on start or other events if there is an update available"*
2. *"and also on start scan if sdlc match the stack or something from repo not covered by sdlc"*
3. *"we should also check drift in skills/tools/etc in claude and offer to allow, preserve it"*

All three are the same subsystem — a **preflight that runs when a w0m skill starts** — so they are one
ticket. Today each of the three is either absent or only half-present.

## Grounded state, 2026-07-26

**(1) Update availability — ABSENT.** Nothing checks whether a skill or tool has a newer version.
⚠️ And the prerequisite is itself unresolved: per `STATE.md` §0z, **"versioned skills" is currently a
fiction** — `.w0m/skills.json` has *two* version-ish fields (`version` = a provenance label
`unknown`×56 / `canonical`×13 / `vendored`×1; `observed_version` = the real scraped value, present on
58 of 70), and **zero canonical skills carry a conforming `YYYY.MM.DD-<unixtimestamp>` version**.
⇒ **An update check needs a comparable version first. Sequence this behind [[T131]]** or it will
compare labels and report nonsense.

**(2) SDLC↔stack coverage — HALF present.** `just discovery` already reports registry↔code drift in
both directions (declared-not-used / used-not-declared) and `--enforce` hard-fails when a declared
command has no recipe; it is green today (8 stacks, 28/28 tests). **What does NOT exist is the
inverse: "something from the repo not covered by SDLC at all."** Nothing enumerates repo content and
asks whether a stack, a gate or a lifecycle stage claims it. That is the actual gap in this ask.

**(3) Claude skills/tools drift — detection EXISTS, reconcile DOES NOT.** `just skill check` is green
right now: **80 installed · 70 managed · 10 excluded · 0 unmanaged**, and all 70 match the lockfile.
So this is not an outstanding breach — the ask is for the **interactive reconcile flow** the owner
describes: when drift *is* found, *offer to allow it* (adopt into `.w0m/skills.json` with provenance
and re-hash) or *preserve it* (record in `exclude` with a reason). Today an unmanaged skill only
warns and a tampered one only blocks; neither offers a path forward, so the human has to hand-edit
two files.

      project-scope and **user scope gets its own manifest+lock**, or AC4 gains a **third outcome** —
      *"out of remit / governed elsewhere, recorded with a reason"*. Implementing the two-outcome
      flow as written would ship a prompt whose every answer is wrong for its actual input.
      ✅ **OWNER DECISION 2026-08-17: user scope gets its own manifest + lock.** Built:

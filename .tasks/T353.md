# T353 — Hierarchical tag-namespace convention for auto-aggregated epic rollups

## Summary

Owner ask mid-session on T354's grounding work: *"instead of referencing epics by §6/§7 style
notation wire for each epic 1-2-3 depth level top tags aggregation automated so sdlc* and
sdlc_design_* groupped to sdlc epic and down to level 3 subtopics/tags same like client* and
client_alfa* and client_beta* that will make epics auto updated and auto-aggregated and also
already human recognisible better."*

`epic:` (rolled up via `tasks_query.epic_key()` to `ROADMAP §N`) answers *why* a ticket exists but
requires opening ROADMAP.md to know what a section number means, and a ticket picks exactly one.
Tags were the other axis but, per `cmd_overview`'s own comment, "a genuinely weak dimension" — 153
distinct labels over 119 tickets, flat, no structure, the single most common one (`backfilled`)
being process metadata rather than a theme.

This ticket adds a **namespaced-tag convention**: a tag spells its own ancestry with `_`
(`sdlc`, `sdlc_design`, `sdlc_design_gate` are 3 depths of one family), and a new
`tasks_query.tag_family()`/`tag_matches()` pair rolls that up automatically — no manual table, no
lookup, self-describing without opening any other document. It is **additive to `epic:`**, not a
replacement — ROADMAP sections keep the narrative; tag families give a second, self-aggregating
axis a ticket can belong to several of at once (e.g. a client-onboarding KYC ticket under both
`client_alfa` and `rbac_federation`).

## Acceptance criteria

- [x] AC1 — `tasks_query.tag_family(tag)` returns the cumulative `_`-delimited ancestor chain for
      a tag, most-general segment first, capped at 3 levels (a 4th `_` stays part of the leaf name).
- [x] AC2 — `tasks_query.tag_matches(tag, query)` matches a tag against its own family: exact, or
      any descendant under `query_`.
- [x] AC3 — `--tag` on `tasks_query.py` (`plan`/`epic`/`current` dynamic-plan modes) matches a whole
      family via `tag_matches`, not just an exact string — `--tag sdlc` now also picks up
      `sdlc_design_gate`-tagged tickets.
- [x] AC4 — `just tasks overview` gains a "by TAG FAMILY" block: for every namespaced tag actually
      in use, group + AC-bar-roll-up at all 3 levels, computed from the tag strings alone. Silent
      (prints nothing) until tickets actually adopt the convention — verified live: 0 root families
      today, all 153 existing tags being flat single-level or unrelated multi-word tags.
- [x] AC5 — Convention documented in `project/templates/ticket.md`'s `tags:` field comment, marked
      optional/going-forward (no mass-retag of the 119 existing tickets required or attempted).
- [x] AC6 — Existing test scripts (`test_tasks_render.py`, `test_ac_progress.py`,
      `test_blocker_detection.py`, `test_plan_verdict.py`, `test_ticket_schema_check.py`) still pass
      unmodified — this is additive, `epic_key()`/`EPIC_ROLLUP` untouched, exact-match tag lookups
      (`load_plan(tag=...)` for a flat tag) still resolve identically since exact-match is a subset
      of the new prefix match.
- [x] AC7 — T354 (org-federation/actor-identity ticket, filed same session) is the first real usage
      of the convention, carrying namespaced tags rather than only flat ones.

## Definition of Done

`tag_family()`/`tag_matches()` unit-sanity-checked directly; `just tasks overview` runs clean
end-to-end against the live 207-ticket queue with the new block present (empty today, by design,
until adoption); the five existing render/plan/progress/blocker/schema test scripts pass with zero
modification, proving the change is additive; `project/templates/ticket.md` documents the
convention for new tickets; committed with the ticket id.

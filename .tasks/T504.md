# T504 — the leaked Gemini key, and the rest of what was committed with it

## Summary

2026-09-30, the live Resume Studio showed `Parse failed: google API failed: Your API key was reported as leaked. Please use another API key.` Measured (value never printed; only status, length class and a short digest):

- `GEMINI_API_KEY` (39 chars, sha256[:12] `b5db0d9e811a`) answers **HTTP 403 PERMISSION_DENIED: "Your API key was reported as leaked"** from `generativelanguage.googleapis.com`. Google disabled it. `GOOGLE_API_KEY` is not set anywhere; the code reads `GOOGLE_API_KEY || GEMINI_API_KEY`.
- **Where it is exposed.** Not in any live page or JS bundle (4 public hosts, 8 assets scanned), not in any working tree of the 8 repos. It IS in `wom7web` git history: `de6cf1a2f` (2026-05-08) and `12dade3e2` (2026-05-14) ADDED it inside committed `apps/web/.dev.vars` and `apps/cp/.dev.vars`; `1e4935539` (2026-06-03, "secure .dev.vars and ignore secrets") removed it from the tree but not from history. All three commits are on `origin/beta`. The repo `casualuser/webomage.com` is PRIVATE today (0 forks, 0 stars, no public/fork/watch event in the 90-day events window, which is NOT proof it was never public: the repo dates from 2025-12-20, and the window is short).
- **The key was not alone.** Those commits held **85 variables. 71 have the same value today.** Of those, **30 are credential-shaped** (list below; 41 are plain configuration or public-by-design such as the anon key and URLs). 13 have since been rotated, including the dangerous ones (`DATABASE_URL`, `SERVICE_ROLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ACCESS_TOKEN`, `CLOUDFLARE_API_TOKEN`, `CF_RUNTIME_API_TOKEN`, `WORKERS_WEBHOOK_SECRET`, `DEBUG_BYPASS_KEY`, Hume), which matches the July rotation; one (`HCAPTCHA_SECRET`) is gone.

**Still live and in git history (rotate these):**
`GEMINI_API_KEY`, `ADMIN_PASSWORD`, `MEMBER_PASSWORD`, `AWS_ACCESS_KEY`, `AWS_ACCESS_SECRET`, `COHERE_API_KEY`, `GROQ_API_KEY`, `MISTRAL_API_KEY`, `HUGGINGFACE_API_TOKEN`, `CRON_SECRET`, `CRYPTO_KEY`, `E2E_ACCESS_SECRET`, `TEST_RBAC_BYPASS`, `GITHUB_TOKEN`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_APP_CLIENT_SECRET`, `GITHUB_APP_WEBHOOK_SECRET`, `HATCHET_CLIENT_TOKEN`, `LINKEDIN_APP_SECRET`, `LITELLM_MASTER_KEY`, `OPIK_API_KEY`, `POSTHOG_API_KEY`, `SIGNOZ_API_KEY`, `RESEND_API_KEY`, `SMTP_PASS`, `SUPABASE_KEY` (check which key this is), `UPWORK_API_KEY`, `UPWORK_API_SECRET`, plus two OCI identifiers (`OCI_COMPARTMENT_OCID`, `OCI_VM_IMAGE_OCID`, identifiers more than secrets).

## What it breaks today (measured or read from code)

- Resume Studio's legacy Extract Facts (removed from Studio in T503) and the onboarding parser (`parse-resume`, used by the join dashboard and CP profile): every call fails. Tracked in [[T502]], which also moves it off Google.
- `ai-router.ts` Google fallback, `gemini-embedding-2`, `generateImageWithGemini`, and the Cloudflare Workflows that call `generativelanguage.googleapis.com` with the worker's copy of the key (cv-generator, deck-generator, job-scorer, cert-evaluator, cert-ingestion).
- Public chat and the new `w0m-personnel` assistant are NOT affected: both run on Cloudflare models.

## Acceptance criteria

- [ ] AC1 — **Owner:** create a new Gemini key in Google AI Studio (restrict it to the Generative Language API and to the needed origins/IPs), store it in Infisical as `GEMINI_API_KEY`, push it to Supabase and the Cloudflare worker secrets, redeploy. Verify with the status probe (HTTP 200). The old key stays disabled.
- [ ] AC2 — **Owner:** rotate the still-live credentials above, most dangerous first: `ADMIN_PASSWORD`, `MEMBER_PASSWORD`, `AWS_ACCESS_KEY` and `AWS_ACCESS_SECRET`, `GITHUB_TOKEN`, `GITHUB_APP_PRIVATE_KEY`, `CRYPTO_KEY` (check what it encrypts before changing it), `CRON_SECRET`, `SUPABASE_KEY` (find out which key it is first), `SMTP_PASS`, `RESEND_API_KEY`, then the AI provider keys. Accounts and money are owner-only; this ticket prepares and verifies.
- [ ] AC3 — A repeatable check, `just secret-history-check`, reports by NAME which current secret values appear anywhere in git history of the 8 repos (the measurement done here, made a tool). Local and owner-run because it needs the values; prints names and commit ids only, never a value; exits non-zero while any credential-shaped secret is still live in history. Red-probed on a fixture.
- [ ] AC4 — Decide what to do about the history itself (see questions). Rotation is what removes the risk; rewriting history only removes the trail.
- [ ] AC5 — Find out HOW Google learned of the key. A private repo is not scanned by Google; something public held it. Candidates to check: a public fork or mirror, a pasted log or support ticket, a public issue or gist, a public artifact, a leaked backup, a third-party CI log. Record the finding.
- [ ] AC6 — After AC1, `parse-resume`, the router fallback and the Workflows answer again, or are moved to Cloudflare models (T502, T36 AC2).

## Definition of Done

- No credential that appears in git history is still valid.
- `gemini` calls succeed with a key that has never been in a commit.
- A check exists that would have caught this, and runs before a push or a deploy.

## Open questions (recommended answers)

1. **Rewrite history (filter-repo + force-push) to drop the two `.dev.vars` files?** Destructive and outward-facing (all 8 clones, the GitHub project mirror, every agent worktree). Recommend NO until AC2 is done; rotation makes the old values worthless, and a rewrite then only tidies. If done, do it once, after rotation, with a backup. Weight: high risk, low benefit after rotation.
2. **Order.** Recommend AC1 today (it restores features), AC2 in one sitting, AC3 and AC5 after. Weight: AC2 is what matters for safety.
3. **Does the repo need to stay private forever?** Recommend yes, and add the secret-history check to the pre-push path of any repo that would ever be opened.

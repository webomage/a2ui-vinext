# T526 — Upwork sync on the member's own connection

## Summary

Split from [[T493]] AC7. `POST /api/sync/upwork-mcp` does not sync a member: it shells out to `project/scripts/upwork_mcp_sync.py`, which drives a local `mcp-remote` OAuth session, writes JSONL under `project/data/upwork/`,
and hardcodes Aleksei's freelancer organisation and the agency organisation. On the deployed Workers `execFile` always throws, so the endpoint returns database counts with `success: false` and nothing is synced.
A per-member sync needs the member's own stored tokens (`upwork_auth_tokens`), somewhere it can actually run, and a mirror to write into: the `upwork` schema from [[T468]], which is still empty (0 connections, 0 contracts).
[[T493]] builds the honest part first: the endpoint answers `409 not connected` when the caller has no connection, and `/api/sync/vault` stamps the caller's profile and refuses to overwrite another member's rows.

## Acceptance criteria

- [ ] AC1 — **Decide where it runs.** A short decision (AgDR) on where a member's sync executes (Worker, edge function, or a runner), with the constraint that it cannot depend on a developer's local OAuth session.
- [ ] AC2 — **The runner takes the member's connection.** No hardcoded organisation ids and no local `mcp-remote` session: it reads the caller's own tokens and writes to the T468 mirror schema, not to `project/data/upwork/*.jsonl`.
- [ ] AC3 — **Fails closed.** A caller with no connection gets `409 not connected` and nothing runs; a caller's sync can only ever write rows with that caller's `profile_id`.
- [ ] AC4 — **Proven live.** Member A syncs and sees their rows; member B and an admin who is not A see none of them. Recorded in the status notes with the measured result.

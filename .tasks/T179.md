# T179 — DevPod machine provider for Tart

## Summary

Owner ask 2026-08-07: *"I want to see if we can use devpod with custom providers including Tart with
macos VMs"*, then *"so I guess we should do similar things for Tart as exists for Multipass?"*

**Yes — and the provider shape is small.** DevPod machine providers are **7 exec verbs**
(`init`/`create`/`start`/`stop`/`status`/`delete`/`command`) declared in a `provider.yaml`, and
DevPod accepts **inline shell** for each — the installed `multipass` provider ships a Go binary, but
nothing requires one. A working Tart provider is a single YAML file calling `tart` + `sshpass`.

## 📍 Measured baseline 2026-08-07

| Fact | Value | Reproduce |
|---|---|---|
| devpod | **v0.6.15**, providers `docker` + `multipass` (multipass = default) | `devpod provider list` |
| tart | **2.32.1** | `tart --version` |
| Existing Tart VM | `evercred`, **linux**, 6 cpu / 12 GB / 52 GB disk | `tart get evercred` |
| 🔴 **Estate coverage** | **ZERO** — `devpod`, `tart`, `multipass`, `lima`, `colima` appear **nowhere** in `TASKS.md` (290,478 B) | `grep -oiE "devpod\|\btart\b\|multipass" TASKS.md` |
| DevPod drivers | **exactly two: `docker`, `kubernetes`** — both require a container runtime on the target | devpod.sh/docs/developing-providers/driver |

⚠️ **`agent.dockerless` in the multipass `provider.json` is NOT a runtime-free mode** — it is
DevPod's internal image *builder*. Checked deliberately, because if it had been a runtime-free
driver it would have changed the answer to the macOS half of the owner's ask.

## 🔴 The hardware ceiling — this is what scopes the ticket

Probed directly on this host, and the framework answers for itself:

```
$ tart run evercred --nested
Error: Nested virtualization is available for Mac with the M3 chip, and later.
```

This is an **M1 Max**. ⇒ **No Tart guest on this machine has hardware virtualization inside it**,
which is a property of the hypervisor and hardware, **not of the guest OS** — so it binds a macOS
guest exactly as it binds the Linux one. Docker Desktop, colima, podman machine and Apple's
`container` all start a Linux VM *inside* the guest; none can.

⇒ **A DevPod provider for Tart can only target Linux guests**, where Docker runs natively on the
guest kernel with no nesting at all. That is not a limitation of the design; `evercred` already runs
Docker well. The macOS half of the owner's ask is answered in **[[T180]]**, where it turns out not to
need Docker anyway.

## 🟢 Built and validated 2026-08-07 (skeleton — NOT proven end-to-end)

`provider.yaml`, pure inline bash, registers and passes DevPod's schema validation:

```
$ devpod provider add ./provider.yaml --name tart --use=false
done Successfully installed provider tart
```

`status` unit-tested against live tart state — the verb DevPod is most sensitive to, since it must
print exactly one of `Running|Busy|Stopped|NotFound`:

| MACHINE_ID | tart state | printed |
|---|---|---|
| `evercred` | stopped | `Stopped` ✅ |
| `does-not-exist` | — | `NotFound` ✅ |
| `macos-test` | absent mid-pull | `NotFound` ✅ |

⚠️ Added with `--use=false` — **multipass is still the default provider**; nothing was disturbed.

🔴 **`create` and `command` are unexercised.** No `devpod up` has been run. The skeleton is a
starting point, not a working provider, and the ACs below say so.

## Acceptance criteria

- [ ] **AC1 — `devpod up` completes end-to-end** against a Linux Tart guest and opens a working
      devcontainer. Until this passes, nothing else here is real.
- [ ] **AC2 — `command` carries DevPod's agent protocol.** It pipes stdin/stdout over SSH; verify
      binary-safe transport, not just that a shell command echoes.
- [ ] **AC3 — lifecycle is honest across the 7 verbs**: `stop` then `start` returns the *same*
      machine with its workspace intact; `delete` leaves no VM and no `tart.pid`.
- [ ] **AC4 — `TART_IMAGE` defaults to a Linux image and REFUSES a macOS one with a clear error.**
      🔑 The failure mode this prevents is the expensive one: a user points it at a macOS image, the
      50 GB pull succeeds, the VM boots, and it dies at `docker` with a confusing message ~40 minutes
      in. Fail at `create`, before the pull, citing the nested-virt reason.
- [ ] **AC5 — credentials are opt-in, not ambient.** `INJECT_DOCKER_CREDENTIALS` /
      `INJECT_GIT_CREDENTIALS` default `true` in the multipass shape; decide deliberately whether
      that is right for a sandbox and record the reason. Ties [[T171]]'s capability-based boundary
      (*"a sandbox without deploy creds cannot deploy"*).
- [ ] **AC6 — the provider is versioned in a w0m repo**, not left in scratch. ⚠️ It currently lives
      in a session scratchpad and will be lost; this is the [[D32]]/[[D15]] unversioned class again.
- [ ] **AC7 — the `sshpass` dependency is declared or removed.** It is a host prerequisite the
      `init` verb checks but `tools-policy.json` does not know about ([[T112]]).

## Definition of Done

- `devpod up --provider tart` opens a working devcontainer on a Linux Tart guest, and the full
  `stop`→`start`→`delete` lifecycle is exercised at least once (AC1–AC3).
- Pointing `TART_IMAGE` at a macOS image fails at `create` with the nested-virt reason, **before**
  any multi-GB pull (AC4) — proven by running it, not by reading the code.
- `provider.yaml` is committed in a w0m repo with its host prerequisites declared (AC6, AC7).
- The substrate relationship to [[T153]]/[[T171]]/[[T180]] is recorded — either reusing their
  decision or explicitly deferring.

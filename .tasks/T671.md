# T671 — Role-driven `<slug>@w0m.xyz` tech mailing list pattern (`devops` hat default, collapsed `pm`-only hat fallback, and CP grant-access control)

## Summary

Establish the canonical estate pattern for per-client `<slug>@w0m.xyz` technical mailing lists (prototyped for `pandatransfer@w0m.xyz` in `w0m-cf/src/lib/email-routing.ts` during [[T664]] / [[T665]]) so that every client engagement (`public.engagements` / `public.projects`) automatically routes technical, vendor, and OTP emails through a role-governed distribution list with explicit operator controls in `cp.webomage.com`:

1. **`devops` Role Default with Collapsed `pm`-Only Hat Fallback:**
   - By default, a client's `<slug>@w0m.xyz` technical mailing list resolves its primary operator recipient(s) from the active **`devops`** project role/hat (`public.project_roles.slug = 'devops'` joined via `public.hats` on the engagement).
   - **Collapsed Single-Operator Fallback (`pm`-only hat activated):** When an engagement runs in collapsed single-operator mode where only the **`pm`** hat/role is activated (and no separate active `devops` hat exists yet), `<slug>@w0m.xyz` automatically falls back to the active **`pm`** hat holder's email so Day-0 vendor invites, Cloudflare/R2 alerts, and OTP verifications never drop.
2. **Explicit Option to Grant / Revoke Tech Email Access (`ClientManager.svelte` & API):**
   - Add an explicit control in `w0m-web/apps/cp/src/components/admin/ClientManager.svelte` (`Admin -> Patrons` / engagement settings) and its backing API to **grant or revoke `<slug>@w0m.xyz` mailing list access** for the **Client** (`public.orgs.email` / active `client` hat holders, e.g. `pandatransferusa@gmail.com`), the **PM** (`pm` hat holder when separate from `devops`), or additional delivery hats.
   - Granting access registers the target address in Cloudflare Email Routing Destination Addresses (`POST /accounts/{account_id}/email/routing/addresses`, sending Cloudflare's one-time verification email if unverified), adds the recipient to the `<slug>@w0m.xyz` target list, and surfaces live destination verification state (`verified` vs `pending`).

## Acceptance criteria

- [ ] AC1 — **Role-Driven `<slug>@w0m.xyz` Recipient Resolution (`devops` Default + Collapsed `pm` Hat Fallback):** Implement canonical recipient resolution across `public.engagements`, `public.projects`, `public.project_roles`, and `public.hats` so `<slug>@w0m.xyz` defaults to active `devops` hat holder email(s) and automatically falls back to active `pm` hat holder email(s) when collapsed into a `pm`-only active hat configuration.
- [ ] AC2 — **Explicit "Grant / Revoke Tech Email Access" Control in CP (`w0m-web/apps/cp/src/components/admin/ClientManager.svelte` & Edge API):** Add UI and API actions to grant or revoke `<slug>@w0m.xyz` list membership for Client (`orgs.email` / `client` hat) and PM (`pm` hat) emails, automatically triggering Cloudflare Email Routing destination address registration (`POST /accounts/{account_id}/email/routing/addresses`) and displaying `verified` vs `pending` status per recipient.
- [ ] AC3 — **Live Synchronization with `w0m-cf` (`wom7func`) Email Worker (`w0m-cf/src/lib/email-routing.ts`):** Synchronize engagement mailing list targets with `wom7func` (`routeInboundEmail`), preserving `+tag` subaddressing (`<slug>+cf@w0m.xyz`, `<slug>+iex@w0m.xyz`) and `Promise.allSettled` fan-out so verified `devops`/`pm` recipients receive 100% of emails even while a newly granted client address is `pending` verification.
- [ ] AC4 — **Regression & RBAC Verification:** Add unit and integration tests covering `devops` default routing, collapsed `pm`-only hat fallback, client/PM grant-and-revoke workflows, and pass `just engagements-hats-verify --test`, `just ticket-schema-check`, and `just dod-check`.

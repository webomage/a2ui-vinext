# T181 — GUI workstation VMs (Claude Desktop + Slack)

## Summary

Owner direction 2026-08-08: *"another side of virtualization vector is to provide macos/linux vms
with gui to work with Claude app and slack app"*, clarified as **a second feature and a second type
of VM** — and *"evercred actually run GUI linux version"*.

⇒ **Two VM types now exist and must not be conflated:**

| | **Type 1 — agent sandbox** ([[T180]]) | **Type 2 — GUI workstation** (this ticket) |
|---|---|---|
| Interface | SSH / `tart exec`, headless | display, `--vnc`, human at a screen |
| Occupant | an untrusted agent auditing client code | a person (or an agent driving a GUI) |
| Clipboard | 🔴 **off** — exfil surface | 🟢 **on** — the point of the thing |
| Host mounts | none by default | expected (working files) |
| Egress | CIDR allowlist, deny-by-default | ordinary internet |

🔴 **The security postures are OPPOSITE.** T180 AC4 makes deny-by-default the whole design;
a workstation that cannot paste or reach Slack is broken. **Do not let one substrate config serve
both** — same hypervisor, deliberately different profiles.

🟢 **The pattern is already proven here**: `evercred` is a **GUI Linux guest** — `os: linux`,
`display 1800x1169`, `displayRefit: true`, 6 cpu / 12 GB — and it runs Docker well. Type 2 is not
greenfield; it is the VM the owner already has, given a purpose and a config.

⚠️ **Nested virtualization is IRRELEVANT here.** GUI apps need a display, not a hypervisor, so the
M1 Max ceiling that scopes [[T179]] to Linux guests does not touch this ticket. Do not carry it over.

## 📍 App availability — this is what picks the guest OS

| App | Linux **arm64** | macOS arm64 | Source |
|---|---|---|---|
| **Claude Desktop** | 🟢 **official beta since 2026-06-30** — Ubuntu 22.04+ / Debian 12+, x86_64 **and arm64**; Chat + Cowork + Code; ships via its own apt repo | 🟢 native | anthropic download page / release coverage |
| **Slack Desktop** | 🔴 **no official arm64 `.deb`** — Slack ships amd64 only | 🟢 native (universal) | slack.com/downloads/linux |

🔑 **Claude Desktop is NOT the constraint — Slack is.** Tart on Apple Silicon runs arm64 guests
only, so on a Linux guest Slack needs one of:

1. **Web app** in the guest browser — works today, zero engineering, loses desktop notifications/deep links
2. **Rosetta + the amd64 `.deb`** — `tart run --rosetta=<tag>` attaches a Rosetta share to a **Linux**
   guest; 🟢 **host Rosetta is already installed** (`oahd` running). Requires binfmt_misc
   registration in the guest per Apple's doc. **Untested — AC3.**
3. **Unofficial arm64 client** (e.g. Slacky) — 🔴 an unvetted third-party binary holding a work
   Slack session; weigh against [[T135]]'s licence/provenance discipline before considering
4. **macOS guest** — both apps native, and the reason to pay macOS's costs below

⚠️ Claude Desktop on Linux **cannot control apps or the screen** (voice dictation is CLI-only), so if
the goal is an agent *driving* a GUI rather than a human using one, Linux is not feature-equivalent.

## 🔴 The macOS ceiling — measured, and it is a kernel limit not a licence footnote

- **Max 2 active macOS VMs per Mac.** Apple's SLA permits two additional instances, and Apple Silicon
  **enforces it in the kernel** (`hv_apple_isa_vm_quota`, XNU); a third fails with `VZErrorDomain`
  code **6**, *"The maximum supported number of active virtual machines has been reached."*
- **50 GB disk each** (`org.cirruslabs.tart.uncompressed-disk-size` = 50000000000 on
  `macos-tahoe-base`), against **~37 GB free** on a 926 GB volume that began the session at 94% full.
- ⇒ **This host supports roughly ONE macOS workstation today, and two ever.** Linux guests carry
  **no such cap** — bounded only by RAM and disk.

⇒ 🔑 **Design of record proposed: default to GUI Linux guests; spend a macOS slot only where a
macOS-only app justifies it.** Slack is currently the *only* named app forcing that choice, and
options 1–2 above may dissolve it entirely.

🔑 **This is also the concrete answer [[T180]] AC8 asked for** (*"macOS-vs-Linux justified per
workload, not by default"*). The first real workload to demand macOS is **Slack's missing arm64
build** — a packaging gap, not a platform requirement. Worth stating plainly: if Slack shipped
arm64, there would presently be **no** reason to run a macOS guest at all.

## Acceptance criteria

- [ ] **AC1 — a reproducible GUI-workstation profile exists**, distinct from [[T180]]'s sandbox
      profile, with clipboard/mounts/egress deliberately set and the difference documented. 🔴 One
      profile serving both types fails this AC.
- [ ] **AC2 — Claude Desktop runs in a GUI Linux arm64 Tart guest**, installed from the official apt
      repo, signed in, and surviving a VM stop/start.
- [ ] **AC3 — the Slack question is settled with evidence, not preference.** Try Rosetta + amd64
      `.deb` (host Rosetta already present) and record whether an Electron app actually works that
      way. 🔑 A negative result is a real result — it promotes option 1 (web) or 4 (macOS).
- [ ] **AC4 — the 2-VM macOS cap is respected by design**, not discovered at runtime. If any plan
      implies ≥3 concurrent macOS guests it is invalid on this hardware; say so before building.
- [ ] **AC5 — remote access decided**: built-in window vs `--vnc` (needs Remote Login in guest) vs
      `--vnc-experimental`. Matters the moment the host is not the machine in front of you.
- [ ] **AC6 — credentials and session hygiene.** 🔴 A workstation VM holds a **signed-in Slack and a
      signed-in Claude account**. Snapshot/clone semantics must be stated: an APFS CoW clone of a
      logged-in VM **duplicates live sessions**. Ties [[T171]] §3's unresolved question of what may
      back N automated agents.
- [ ] **AC7 — disk budget stated before a second VM is built** (AC7 of [[T180]] is the same
      constraint from the other side; ~37 GB free is not two macOS guests).
- [ ] **AC8 — `evercred`'s status is resolved**: promoted to the golden GUI image, or explicitly
      left as the owner's personal VM and a fresh one built. It currently has **no upstream for
      `beta`** and 10 uncommitted files elsewhere in the estate — do not silently adopt it.

## Definition of Done

- A documented, repeatable way to stand up a GUI workstation guest and reach it, with Claude Desktop
  working and the Slack path chosen on evidence (AC1–AC3, AC5).
- The macOS-vs-Linux rule is written down with its reason, and the 2-VM cap is respected by
  construction (AC4).
- Session/credential semantics for cloning a logged-in workstation are stated (AC6).

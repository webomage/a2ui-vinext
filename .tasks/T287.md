# T287 — repos as a first-class entity

## Summary

Owner decision 2026-08-26, reviewing the project model: repos become **a first-class table**, not a
URL on the project.

**Measured the same day:**

- `public.projects.github_repo_url` — a single `text` column, plus `github_visibility text`.
- **There is no repos table anywhere.** Not in `public`, not in `gamification`.
- 🔴 **`tests/support/hooks.ts:185` deletes from `github_repos` on every LOCAL run** — a table that
  does not exist. PostgREST errors, the error is discarded, and the purge has never done anything.
  Whoever wrote it believed there was a repos table; the schema disagreed silently.

🔑 **One URL per project does not match how work is actually shaped here.** w0m itself is **seven**
repos, and a client delivery project routinely spans api + web + infra. A single field forces the
first repo to stand for all of them.

## Acceptance criteria

- [x] **AC1 — a project may have MANY repos.** `project_repos` with `project_id`, provider,
      owner/name, url, visibility, and a role (`api`, `web`, `infra`, …).
      ✅ **DECIDED 2026-08-26: ONE-TO-MANY, not many-to-many.** Every case in evidence is
      project-owned, and a library shared across CLIENT projects would be a w0m-owned repo — i.e.
      it belongs to an internal project, not to several client ones. A join table today would carry
      zero rows that justify it.
      ⚠️ **The trade-off, stated rather than buried:** if a genuinely shared repo appears, adding
      the join table is a real migration, and it will cost MORE then than now because rows will
      exist. That is the bet.
- [x] **AC2 — provider is a discriminator, not an assumption.** ✅ `provider` column.
      🔄 **REVERSED 2026-08-26 by owner decision, later the same day, and the reversal is the
      interesting part.** It shipped CHECK-constrained to github/gitlab/bitbucket, justified as
      *"you cannot support a forge without writing code for it"*. That conflated **RECORDING** a
      repo (url + owner/name, link out — needs NO provider code) with **INTEGRATING** one (create,
      set-visibility over an API — needs real code). The CHECK blocked linking out to a Gitea or
      Azure DevOps repo for no reason at all: nothing to write, nothing to break.
      ⇒ `20260826070000` drops it. The set is OPEN, and the constraint moved to `github-repos`,
      the only place that knows which forges it can talk to — `DRIVEABLE`. **A new forge is a row**,
      which is the [[T204]] AC9 rule applied where it actually fits.
      🟢 The `visibility` CHECK STAYS: public/private is two-valued, every forge agrees, and code
      branches on it. Only `provider` was the wrong thing to close.
      ⏳ Driving GitLab/Bitbucket/self-hosted is [[T292]]. Superseded reasoning follows: ~~CHECK-constrained to github/gitlab/bitbucket. 🔑 Constrained because it is BEHAVIOURAL — you cannot support GitLab without writing GitLab code, so a migration alongside it is honest. Contrast `role`, left open because nothing branches on it. ⚠️ Recorded in the migration that this is NOT the shape [[T204]] AC9 objects to; the two constructs look identical and are justified oppositely. The column is `github_repo_url`
      today, so GitHub is baked into the NAME. Structure carried in a string has cost this estate
      four separate incidents; a `provider` column costs nothing now and a migration later.
- [x] **AC3 — visibility is the repo's, not the project's.** ✅ Its own column, and the probe asserts a PRIVATE repo can sit on a PUBLIC project. A public project can hold a private
      repo and the reverse. Do not reuse `projects.access_scope` for it.
- [x] **AC4 — migrate the existing data, and say how much there was.** ✅ Re-measured 2026-08-26:
      **zero** of the 9 real projects carry a `github_repo_url`, and `github_visibility` is NULL on
      every row. The DATA migration is empty.
      🔴 **CORRECTION — I wrote this AC on an incomplete measurement.** I searched for a repos TABLE,
      found none, and concluded the column was inert. It is not: there is a **live feature** behind
      it. `GitHubRepoCard.svelte` (336 lines) and the `github-repos` edge function create, link,
      unlink and set-visibility on real GitHub repos, writing `github_repo_url` +
      `github_visibility` back onto the row through four actions. ⇒ "The migration is empty" is true
      of the rows and false of the code; dropping the column is a CODE change, not a cleanup.
      ⚠️ And the function is generic over `resource_type: "projects" | "blueprints"` — **blueprints
      carries the same two columns** (also 0 of 27 filled). Migrating projects alone makes the
      shared component asymmetric.
- [x] **AC4b — blueprints keep ONE repo, and that is a decision, not an oversight.** A blueprint is
      one reference implementation, so a single repo is the right shape for it; a delivery project
      spans api + web + infra, which is why THIS ticket exists. ⇒ `github-repos` branches on
      `resource_type`: projects write a `project_repos` row, blueprints keep their column.
      🔴 State it in the function, or the next reader will "fix" the asymmetry.
- [x] **AC5 — remove the dead `github_repos` purge** ✅ Removed from `tests/support/hooks.ts` with a note in its place. Repos now CASCADE from their project, so a purge here would be a second way to delete them and a second thing to get wrong. Original text:  in `tests/support/hooks.ts`, or point it at the
      real table once it exists. A delete against a non-existent table that swallows its error is a
      cleanup nobody can tell is broken.
- [x] **AC6 — RLS follows the project.** ✅ And proven by READING A ROW BACK as a client actor, not by reading the policy. 🔴 That mattered: the policy uses `EXISTS (SELECT 1 FROM projects …)`, the exact shape that matched NOTHING in [[T4]] the same week. It works here only because `projects` has a client arm and `leads` did not — a difference invisible in the SQL. Dropping that arm in a mutation turns the check red. Original text:  A repo row is as visible as its project and no more.
      ⚠️ Prove it by reading a row back AS a client actor, not by reading the policy text — a
      policy that matches nothing looks identical to one that works ([[T4]]).

## Definition of Done

A project can carry several repos with distinct roles and per-repo visibility, and a client sees
only the repos of a project they can already see — proven by reading rows back as a client actor
rather than by inspecting the policy. The provider is a column, so the second forge is a row. The
dead `github_repos` delete is gone from the test teardown, and the old single-URL column is removed
rather than left as a second place to look.

The asymmetry with blueprints is DECLARED where the code branches, not left to be inferred: a
blueprint keeps one repo because it is one reference implementation, a project holds many because it
spans api + web + infra. An asymmetry nobody wrote down is one the next reader "fixes".

🔄 **AMENDED 2026-08-26 — AC4b was added mid-build, and the reason is a correction to AC4.** Recorded
rather than silently edited. AC4 said the migration was empty and the column could simply be dropped;
that was measured on the ROWS (0 of 9) and never on the CODE. `GitHubRepoCard` and the `github-repos`
edge function write those columns through four actions, for BOTH projects and blueprints — so
dropping them is a code change touching a live admin feature, and the blueprints half needed a
decision rather than a migration. The DoD now carries that decision.

🔴 **Not done if `github_repo_url` survives alongside the new table.** Two homes for the same fact is
the defect this ticket exists to stop, and the migration is empty today — there will never be a
cheaper moment to drop it.

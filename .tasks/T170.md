# T170 — w0m-managed serena — own a maintained fork and extend it, astro first

## Summary

Owner directive 2026-08-05: *"I want us to have P2 task to look develop custom plugin/module for
serena for astro."*

[[T166]] governed serena and configured it from **measured** file counts. Doing that surfaced a
structural gap: **serena has no `.astro` language server, and `.astro` is 220 files — the largest
single language in `wom7web` after TypeScript, and the one that *is* the site.**

Coverage after T166, measured 2026-08-05:

| Language | Files | serena support | Configured |
|---|---|---|---|
| TypeScript | 441 | ✅ | ✅ web + api |
| **Astro** | **220** | 🔴 **no server in serena's list** | — **this ticket** |
| Svelte | 149 | ✅ | ✅ web (was off) |
| Python | 110 | ✅ | ✅ web + api (api was off) |
| **SQL** | **216** | 🔴 **no server** — see below | — |

Serena's language set is a closed enum — `LanguageServerId` in `src/solidlsp/ls_config.py`, rendered
into every `project.yml` header by `scripts/print_language_list.py`. Verified against that list:
**`astro` is absent**, and so are `sql`, `postgres` and `plsql`.

🔑 **The upstream LSP exists — serena simply does not wire it.** `@astrojs/language-server` is live
on npm at **2.16.13**. So this is an integration job, not a compiler project.

🔑 **Serena already has the pattern to copy.** Its own list documents `svelte` as *"subsumes
typescript/javascript for `.svelte` projects; requires npm"*, and `angular` as *"subsumes
typescript+html; requires `npm install` in the project root"*. `.astro` is the same shape: a
single-file component format with a TS/JS island inside, served by an npm-installed language server.
`svelte` is the reference implementation to follow.

🔑 **[[T166]] made this feasible without a fight.** serena is now **user-managed**, not
Headroom-managed — verified in Headroom's own code, which force-updates or removes the serena MCP
entry *only* when its ledger fingerprint matches (`wrap.py:1938`: *"never a user-managed Serena"*).
Pinning it to `serena-agent==1.6.1` broke that fingerprint, so Headroom now leaves it alone. A fork
or a patched install will not be reverted by Headroom's `PreToolUse` / `SessionStart` ensure hooks.

⚠️ **SQL is the same shape and is NOT in scope here** — recorded so it is not lost. `wom7api` holds
**212 `.sql`** files and serena has no server for them either. Deliberately excluded because the
owner asked specifically for astro, and because SQL's value is lower: those files are migrations,
which are append-only and rarely refactored, whereas `.astro` files are edited constantly. If this
ticket produces a reusable "add a language" recipe, SQL becomes a cheap follow-up.

## 🧭 SCOPE — owner, 2026-08-06: this is about a MANAGED serena, not about astro

*"T170 actually more about our managed and extended serena — and then we will look how to use new
serena with headroom in sandboxes."*

**The deliverable is a w0m-owned, maintained, extensible serena.** Astro is the **first and driving
extension**, not the point. That reframes the ticket in three ways:

1. **"Accept the blind spot" is no longer a co-equal route.** The original AC1 offered
   accept-it-and-record-debt as one of three outcomes. Under this scope the question is no longer
   *"is astro worth a fork"* but *"how do we own and maintain a serena we can extend"* — with astro
   as the first thing it buys. Quantifying the astro gap still matters, but it now **prioritises
   extensions**, it does not decide whether to have the fork.
2. **SQL comes back into view.** Previously scoped out as a lower-value second instance of the same
   gap. Once a fork exists with a working "add a language" path, **216 `.sql` files in `wom7api`**
   are a candidate extension rather than an unrelated wish. Still not a blocker; now a named
   consumer of the same machinery.
3. **The maintenance story becomes the hard part, not the integration.** `@astrojs/language-server`
   exists on npm; wiring one language is bounded work. **Staying current with upstream serena
   forever is not.** AC1 is now about that.

## Definition of Done


Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
the OWNERSHIP question is answered first and in writing — how w0m maintains a serena fork and what the standing cost is — because a fork adopted without that becomes unmaintained infrastructure. Gaps are measured **to prioritise the extensions, not to justify the fork**. 🔴 If built: `.astro` symbols resolve end-to-end on a real file, the frontmatter/template boundary is handled explicitly, the fork stays PINNED and checkable, and `.serena/project.yml` is committed — that pin is the AC most likely to be skipped and the one that decides whether this is governed or just installed.

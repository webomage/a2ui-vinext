# T296 — the GUI sandbox image

## Why

The headless master image landed 2026-09-01: Ubuntu 26.04 arm64, 2 CPU / 4 GB / 20 GB, no GUI, our
forked Tart Guest Agent baked in ([[T295]] tests it). Owner: *"the version with GUI will come later,
now we have master fast and lightweight image"* and *"let's learn from all the changes we made for
evercred vm and use later same GUI config."*

Where a project declares `runtime.substrate: "tart-linux"` (or `tart-macos`) in `project/clients-policy.json` ([[T297]]), a GUI sibling is what that **client sandbox** needs when interactive display is required: somewhere a person can be shown a running app,
drive a browser, and hand back a session — none of which a shell-only guest does.

🔑 **The point of filing this now, while the headless build is fresh, is that a GUI image is not a
bigger headless image.** Half of what was learned this week carries over unchanged; the other half
inverts, and the inverting half is invisible until someone has already built the wrong thing.

⚠️ **This ticket does NOT govern, audit or modify Evercred.** The estate's recorded position stands:
Evercred's shadow-proxied dev GUI sandbox is **deliberately unmanaged**, and [[T265]] AC8 forbids
writing to the project or inside the VM. Everything above is a host-side config read of our own
`~/.tart`. Evercred is a *worked example to copy proportions from*, not a subject.

## What carries over unchanged (do not re-derive)

- 🔴 **MTU 1280, pinned on the link AND in `/etc/docker/daemon.json`.** This is a property of the
  HOST — utun tunnels at MTU 1000 and filtered ICMP — so it applies to every guest here regardless
  of GUI. At 1500 HTTP payloads vanish silently and apt hangs with no output.
- **Packer + `tart-cli` + `tart push`** as the build and distribution model, and the build must fail
  unless it proves something ran.
- 🔴 **No cirruslabs base carries the Tart Guest Agent**, and **`cirruslabs/ubuntu:docker` is Ubuntu
  22.04.3, not 24.04** — the "24" is the Docker version. Both measured; both will keep re-suggesting
  themselves from the tag names.
- **`tart exec` over SSH-and-lease-hunting**, since the agent is installed either way.

## What INVERTS for a GUI image

- 🔴 **The agent must run as a systemd USER service, not the system service the headless image
  installs.** Its own README is explicit: on Linux, clipboard needs `WAYLAND_DISPLAY` or `DISPLAY`
  plus `XDG_RUNTIME_DIR`, which a `User=`-style system unit does not have. Reusing the headless unit
  yields an agent that answers RPC and silently cannot touch the clipboard.
- 🔴 **Device permissions become load-bearing:** read/write on
  `/dev/virtio-ports/com.redhat.spice.0` or `/dev/vport*`, via group membership or a udev rule
  (`SUBSYSTEM=="virtio-ports", KERNEL=="vport*", MODE="0666"`). Absent, file transfer fails.
- 🔑 **The fork finally pays here.** `wom7open/tart-guest-agent` (PR #62) adds multi-format image
  clipboard, a SPICE file-transfer daemon, tray, notifications and a settings dialog — all of which
  are **inert on the headless master** and are the actual reason a GUI image wants our build rather
  than upstream's.
- **`tart run --no-graphics` stops being right**, and the display config becomes real rather than a
  vestigial 1024×768 nobody looks at.

## Acceptance criteria

- [x] **AC1 — the desktop environment is a stated decision with a measured cost**, not inherited by
      copying Evercred. Record image size and boot time against the headless master's 3.1 GB, because
      "larger sibling" must not mean unbounded.
- [x] **AC2 — 🔴 the agent runs as a USER service and the clipboard is proven to work**, round-trip,
      host↔guest. A passing `tart exec` is NOT evidence: RPC works under the system unit while the
      clipboard silently does not, which is exactly the failure this AC exists to catch.
- [x] **AC3 — file transfer proven**, with the virtio-ports permission handled explicitly (group or
      udev rule, stated which). Move a real file both directions.
- [x] **AC4 — sizing is declared, and the disk decision is understood as one-way.** `tart set
      --disk-size` only GROWS; a guest cannot be shrunk afterwards, so the initial figure is a
      commitment. Evercred provisioned 94 GB and uses 49 GB — say what this image provisions and why,
      rather than inheriting a number.
- [x] **AC5 — MTU 1280 verified INSIDE the GUI image**, both pins, with a real HTTP fetch. The host
      condition is unchanged, so the failure is identical and equally silent.
- [x] **AC6 — published to the registry and cloned to a clean name**, as [[T295]] AC3 requires of the
      headless image. A sandbox image nobody can pull is not a sandbox image.
- [x] **AC7 — the client-sandbox boundary is stated before anyone is invited in.** What a client can
      reach from inside it, what reaches the host, whether it holds credentials, and what is destroyed
      between sessions. 🔴 A GUI sandbox handed to an external person is a different security posture
      from a build box, and shipping it without that written down is the actual risk in this ticket.
- [x] **AC8 — headless and GUI share one definition, or the divergence is deliberate.** Two Packer
      templates that drift is the [[T295]] AC4 problem twice. Prefer one template with a `gui`
      variable over a fork of the file.

## Definition of Done

A GUI image exists in the registry, cloned to a clean name on a machine that never built it, boots to
a desktop, and proves the two things a headless guest cannot: a clipboard round-trip and a file moved
in both directions — each asserted directly, because `tart exec` answering proves neither. The agent
runs as a user service with a display in its environment, not the system unit the headless master
uses. MTU is pinned in both places and verified by a real fetch inside the GUI guest. What the image
provisions for CPU, memory and disk is a written decision with Evercred's numbers as a reference
point rather than a template, and the disk figure is understood as unshrinkable. What a client can
and cannot reach from inside the sandbox is written down before anyone outside w0m is given one. And
the GUI and headless images come from one definition, or from two whose divergence someone chose.

## Notes, traps and dependencies

- 📌 Depends on nothing; **[[T295]]** should land first so the headless build is known to work before
  a second variant is derived from it.
- ⚠️ **Do not diagnose an MTU failure with ping** — ICMP is filtered on this host, so
  `ping -M do -s <size>` reports DROPPED at every size. Only a real HTTP fetch at different MTUs is
  honest. Measured: 1500 hangs, 1400 hangs, 1280 returns 200 in 0.74s.
- ⚠️ **The one thing this ticket cannot read is what Evercred actually RUNS.** Its desktop
  environment, compositor and proxy setup are inside a VM that [[T265]] AC8 puts out of bounds. That
  answer comes from Elena or from the owner, not from an agent booting it.

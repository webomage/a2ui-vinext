# T511 — Profile image management: upload or import, one canonical avatar

## Summary

Owner direction, 2026-09-30: *"we also have to manage the image profile and allow importing it from Google / LinkedIn /
etc, or uploading it."* A member can see, replace and remove their profile image in profile settings, by uploading a file
or importing the picture from a connected provider. The result is **one** canonical image that the app and the public
team card both use.

## Measured state (2026-09-30)

- `public.profiles.avatar_url` exists and is read by `/me/profile` (`apps/cp/src/pages/me/profile/index.astro:26`),
  `PeopleManager.svelte` and `RoleManager.svelte`.
- **Import exists only by accident, at sign-in.** `apps/{cp,web}/src/pages/api/auth/linkedin-callback.ts` copies the
  LinkedIn `picture` into the user metadata when `avatar_url` is empty, and the `handle_new_user()` trigger copies
  `avatar_url` from `raw_user_meta_data`. It stores the **provider's URL itself**, hot-linked.
- **There is no upload.** A search of both apps found no `storage.from(...)` call for avatars, photos or team images, and
  no avatars bucket in any migration. Team photos are static files (`apps/*/public/assets/team/{aleksei,elena}.jpg`).
- **Two photo fields.** The team card reads `public_team_members.photo_url` (a view over `team_members`, T470), not
  `profiles.avatar_url`. A member's photo therefore has two homes. The link between them is the nullable
  `team_members.user_id`.
- Login providers: LinkedIn has its own callback. Google and the "dormant providers" were handled in [[T100]]; which are
  live on the hosted project was not re-measured for this ticket (AC1 does).

## Design (assumptions marked, see Open questions)

1. **Canonical field.** `profiles.avatar_url` stays the single source. It always points at an object **we host**, never at a
   provider URL: provider pictures expire, change without notice and leak the viewer's referrer.
2. **Storage.** *(Assumption, Q1.)* An `avatars` bucket, path `<profile_id>/<uuid>.<ext>`, using the same folder rule as the
   resume vault (`(storage.foldername(name))[1]` = the member's profile id) so a member can write only their own folder.
   Size and content-type limits are set on the bucket and checked again server-side.
3. **Upload.** Client picks a file, the server validates type by content (not extension) and size, stores it, then sets
   `avatar_url` and removes the previous object.
4. **Import.** A server route takes a provider name, not a URL. It reads the picture URL from the member's **linked
   identity** (provider metadata), fetches it server-side from an **allowlist of provider image hosts**, applies the same
   validation as upload and re-hosts it. The client never supplies the URL (no SSRF, no arbitrary fetch).
5. **UI.** Profile settings shows the current image, "Upload", one "Import from <provider>" button per **linked** provider,
   and "Remove". Importing needs a linked identity, which is what [[T476]] adds to `/me/account`.
6. **Team card.** *(Q3.)* For a member linked by `team_members.user_id`, the card shows the profile's avatar; for an
   unlinked row it keeps `team_members.photo_url`. The rule is written in the view's comment, not a hidden fallback.

## Acceptance criteria

- [ ] AC1 — **Measure what is live.** A read-only report states which login providers are enabled on the hosted project,
  which linked identities carry a picture, and how many profiles have an `avatar_url` that points at a third-party host.
  This sizes the import work before it is built.
- [ ] AC2 — **Storage and policies.** `avatars` bucket and policies exist by migration; an authz probe proves a member can
  write and delete only in their own folder, cannot list another member's folder, and anon can read only what Q1 allows.
- [ ] AC3 — **Upload validates.** Wrong content type (including a renamed `.exe`), oversize file and an empty file are
  refused with a clear error and leave `avatar_url` and the bucket unchanged. A valid image replaces the previous one and
  the old object is removed. Verified by unit tests for the validator and a spec for the flow.
- [ ] AC4 — **Import re-hosts, from an allowlist.** Importing from each supported provider stores a copy in our bucket and
  sets `avatar_url` to it. A non-allowlisted host, a redirect off the allowlist, a response over the size limit and a
  non-image response are all refused. A probe sends each of those and asserts no object was written.
- [ ] AC5 — **Profile settings UI.** Current image, upload, one import button per linked provider (none shown for an
  unlinked one), remove. Component tests plus a spec covering upload, import and remove.
- [ ] AC6 — **One source for the card.** `public_team_members` returns the photo per Q3; a probe asserts a linked member's
  card photo equals that profile's `avatar_url` and an unlinked row is unchanged. `email` and `resume_url` stay absent
  from the view ([[T510]] AC4d).
- [ ] AC7 — **Existing third-party avatar URLs are re-hosted.** A one-time, idempotent, owner-run job copies each profile's
  provider-hosted `avatar_url` into our bucket and rewrites the column, reporting one line per profile (✅/❌).
- [ ] AC8 — **Live proof (owner-run).** Upload, import and remove each verified on the hosted project with the measured
  HTTP codes in the status note.

## Open questions (recommended answer first, with weight)

1. **Public or private bucket for avatars?** *Recommend a public-read bucket holding only the member's current image, with
   owner-only writes.* The image is shown on public pages and in the app, so signed URLs would break caching and the team
   card. Weight: low sensitivity (a profile photo is meant to be seen), and the estate's "private unless declared public"
   rule is met by declaring this bucket public in the registry. Alternative: private plus an edge route like the resume
   switch in [[T510]], which costs more and adds a latency hop on every page.
2. **Which providers?** *Recommend Google and LinkedIn first (both already appear in the auth surface), then GitHub if
   its login is enabled.* "etc" is open: Gravatar by email hash is possible but sends a hash of the member's email to a
   third party, so *recommend no*. Weight: each provider is one allowlisted host plus one metadata reader.
3. **Team card photo source.** *Recommend a linked member's card uses the profile avatar and an unlinked row keeps
   `team_members.photo_url`, stated in the view comment.* Weight: avoids a second photo to maintain, but changes what the
   two founders' cards show if their profile image differs from the static file.
4. **Limits.** *Recommend 5 MB, JPEG/PNG/WebP, resized server-side to a bounded size.* Weight: low; the resize bounds
   storage and blocks decompression-bomb inputs.
5. **Re-hosting existing provider URLs (AC7).** *Recommend yes, one-time and owner-run.* Weight: leaving hot-linked URLs
   means broken images when providers rotate them and a third-party request per page view.

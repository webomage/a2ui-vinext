# T285: Customer message threads across connected channels — one conversation per client, whatever channel it arrived on

## Context

Owner (`2026-08-26`): *"Have a message thread with customers through connected channels."*

A customer might first write through the contact form or the public AI chat (`lead_conversations`), then reply by email or Telegram, then sign into the client portal (`T283` / `T4`). Today those live in separate places or nowhere at all — the client portal has no message view, and a lead's pre-sale chat does not carry over when the lead becomes a client.

The goal is **one thread per client**: the customer sees their conversation with Webomage in the portal, the team sees the same thread in the CP with each message's channel noted, and a reply from the CP goes back out over the channel the customer is using (or the portal, if they are in it).

## Acceptance Criteria

- [x] **AC1**: A signed-in client has a message thread in the portal where they can read the conversation history with Webomage and send a new message — implemented via `/o/[org]/projects/messages` (`wom7web/apps/cp/src/pages/o/[org]/projects/messages.astro`), `ClientMessageThread.svelte`, and `/api/client/threads` (`wom7web/apps/cp/src/pages/api/client/threads.ts`).
- [x] **AC2**: Inbound messages from connected channels (at minimum: portal and whichever external channels are already wired in Connections, e.g. email / Telegram / lead chat) land in that client's thread with the source channel recorded on each message — implemented via `public.communication_channels` (`portal`, `email`, `telegram`, `ai_chat`, `contact_form`, `whatsapp`) and `public.client_thread_messages.channel_code` in migration `20261020020000_t285_t288_client_threads_and_case_studies.sql`.
- [x] **AC3**: Replying from the CP sends the message out through the selected / active channel and records the outbound message in the same thread — implemented via `public.wom_post_client_thread_message(...)` and the outbound channel picker in `ClientMessageThread.svelte`.
- [x] **AC4**: Delivery state (sent / delivered / failed) is visible on outbound messages so a silent channel failure is never mistaken for a customer who didn't reply — implemented via `delivery_status IN ('queued', 'sent', 'delivered', 'failed')`, `delivery_error`, `public.wom_update_client_message_delivery(...)`, and visible status/failure badges in `ClientMessageThread.svelte`.
- [x] **AC5**: One thread survives the lead-to-client transition (no "your pre-sale messages are in Leads, your post-sale messages are in Portal") — implemented via `public.wom_bind_lead_thread_to_client_org(p_lead_id, p_client_org_id)` and trigger `trg_promote_lead_thread_on_proposal` on `public.lead_proposals`.
- [x] **AC6**: A client can read and write only their own thread, verified by the cross-tenant isolation probe — enforced by `FORCE ROW LEVEL SECURITY` on `public.client_message_threads` and `public.client_thread_messages`, `public.wom_can_access_client_org_thread(uuid)`, and probes `X40-client-threads-grants-and-rls` & `X41-client-threads-cross-tenant-isolation` in `wom7web/project/scripts/authz_probe_suite.py` + `wom7web/project/scripts/tests/test_t285_client_threads.py`.

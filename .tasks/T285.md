# T285 — customer message threads across connected channels

## Summary

Owner, 2026-08-26: *"it look like we have to manage threads with customers messaging info with
different channels connected — that's a new feature and we need to build definitely but it could be
second part/stage for client features packs."*

A client relationship currently produces messages in several places that never meet: the site chat
(`ai_chat` → `leads`), whatever address `client-register` mails, and any channel a person actually
replies on. **There is no thread.** Nobody can open one client and read the conversation.

🔴 **Sequencing is part of the ask.** This is the *second* part of the client pack — it comes after
the stage-2 proposal/acceptance vertical, not alongside it. Filed now so the shape is captured while
it is fresh; not started.

## What exists to build on, measured 2026-08-26

- `contact_messages` — the website contact form's inbox; no thread id, no channel column.
- `leads.profile` (jsonb) — carries the intake conversation, but as a captured artefact, not a
  running thread.
- [[T10]] — *"Per-agent feature depth + Telegram bridge"*. ⚠️ **Related, not the same:** T10 is an
  AGENT surface (a bot channel for agent features). This ticket is a CLIENT-RELATIONSHIP surface
  (one human conversation, many transports). They will likely share a transport adapter; they are
  not the same feature and neither closes the other.
- `client_users` / `clients` — the tenancy the threads must hang off, already the estate's
  own-linkage idiom (`wom_acting_is('client')` + `client_users`).

## Acceptance criteria

- [ ] **AC1 — a thread is an entity, not a query.** One `client` (or pre-conversion `lead`) has one
      thread; messages carry `channel` + `external_ref` so the same person writing from two places
      lands in one place. ⚠️ Decide and WRITE DOWN whether a lead's thread survives conversion into
      a client's thread, or whether they are two rows joined by `leads.converted_user_id` — the
      answer changes every later query.
- [ ] **AC2 — channel is a discriminator, not a string convention.** A new transport is a row, not a
      migration (the `contracts.source`/`platform` lesson from [[T204]] AC4). 🔴 Structure carried in
      a string has now bitten this estate three times; do not add a fourth.
- [ ] **AC3 — inbound and outbound are the same table.** A reply the team sends and a message the
      client sends are one ordered conversation, or the thread is a half-thread.
- [ ] **AC4 — RLS: a client sees ONLY their own thread**, by the same own-linkage rule contracts
      already use. Proven by `just authz-probe --enforce` with a real second tenant, not by an empty
      table — a cross-tenant assertion over one client proves nothing.
- [ ] **AC5 — delivery is reported, never assumed.** [[T277]] taught this exactly: `emailed:true`
      today means *the send call returned*, not that anything arrived. A thread that shows a sent
      message which never left is worse than showing nothing.
- [ ] **AC6 — the CP surfaces it for both hats.** The team reads a client's thread from the admin
      side; the client reads their own from the portal. One store, two views.

## Definition of Done

A client's messages from every connected channel appear as ONE ordered thread in the CP, readable by
the team from the admin side and by that client from their portal and **by no other tenant** — the
last proven by `just authz-probe --enforce` against two real client rows, not one. A new channel is
addable without a migration, and every message row records what actually happened to it: sent,
delivered, or failed, distinguishable from each other. The lead↔client thread-identity question in
AC1 is answered in writing before any query depends on it.

🔴 **Not done if** the thread is a view assembled per-request from `contact_messages` plus
`leads.profile` — that reads as a thread until the first reply needs somewhere to live.

# T240 — a drift detector that matches on what a recipe SAYS, not what it can DO

## Summary

Found while validating [[T236]] before flipping its status to `done`. AC4 delivered a real gate
(`just orphan-components`, `--enforce`, 100 components across 6 apps) whose red-proof was performed
by hand and **left no artefact** — no test file, no `-test` recipe, and no entry among the 104 suites
in `project/test-suites.json`. Checking whether the estate already knew produced the actual finding.

**`just suites-drift` reports `104 declared, 0 undeclared — ✅ every recipe that behaves like a suite
is declared`. It is wrong, and 12 gates prove it.**

### 🔴 The mechanism — a text match on the wrong surface

`run_suites.py` classifies a recipe as a suite from two signals, and its own comment asserts both are
needed (*"Name-only misses a well-behaved gate with an ordinary name; body-only misses a `*-test`
recipe that shells out"*):

```python
SUITE_NAME = re.compile(r"(?:-test|-check)$")
SUITE_BODY = re.compile(r"scripts/tests/|--check\b|--enforce\b|--drift\b")
```

`SUITE_BODY` reads the **recipe's body text**. But the estate's convention is to *forward* arguments:

```make
orphan-components *args:
    @cd ../wom7web && python3 project/scripts/orphan_components_check.py {{args}}
```

The recipe **accepts** `--enforce`; it does not **contain** it. The flag lives in the script's
`argparse`, which the detector never opens. ⇒ **A recipe that forwards its arguments hides its own
gate-ness**, and a name not ending `-test`/`-check` finishes the job. Both signals are text; neither
asks the script what it can do. This is **D37's recorded shape** (*"a check that appears to have
LOOKED"*) recurring, and the third instance of one root cause in this estate: **a thing identified by
its name rather than its content** ([[T192]], [[T228]]).

### The 12, in two severity tiers — measured 2026-08-20

**Tier A — no registry presence in EITHER form. The gate never runs and no probe proves it fires:**

| gate | script |
|---|---|
| 🔴 `just authz-probe` | `authz_probe_suite.py` |
| 🔴 `just authz-write-probe` | `authz_write_probes.py` |
| `just orphan-components` | `orphan_components_check.py` ([[T236]] AC4) |
| `just schema-drift` | `schema_drizzle_drift.py` |
| `just ticket-deps` | `ticket_deps.py` |

🔴 **`authz-probe` is the severe one: it is `.w0m/sdlc.json → current_plan` stage-0's EXIT CRITERION**
(*"`just authz-probe` shows 0 cross-tenant rows for a client actor"*). The one gate the plan names as
the thing that closes its safety floor is a gate `run-suites` does not know exists.
⚠️ And per [[infisical-dev-env-is-live-db]] it resolves against the **live** database, so its result
is a production measurement — never dismissible as "dev only".

**Tier B — the `-test` red-proof IS declared, but the gate itself is not, so `run-suites` proves the
gate can fire and never runs it against the real corpus:**
`authz-admin-client` · `callsite-drift` · `discovery` · `ide-trace` · `skills-catalogue` ·
`state-bounds` · `headroom-status`

⇒ Tier B is the subtler failure: the registry looks healthy *because* the probe is registered, which
is precisely the confusion between **watching a gate fail** and **running it**.

## Acceptance criteria

- [x] AC1 — **The detector asks the SCRIPT what it accepts, not the recipe what it says.** Resolve
      the script path out of the recipe body and inspect its argparse (or `--help`) for the
      `--enforce`/`--check`/`--drift` contract. ⚠️ Do **not** simply add `{{args}}` to `SUITE_BODY` —
      that trades one text match for a broader one and would sweep in every arg-forwarding recipe
      whether or not it gates anything. The criterion is *"can this thing fail on purpose"*.
      ✅ **Delivered 2026-09-17:** `inspect_script_capability()` implemented in `project/scripts/run_suites.py`.
      Inspects python scripts called via forwarded args (`*args:` / `{{args}}`) for `--enforce`, `--check`, or
      `--drift` in `add_argument` or `(?:sys\.)?argv`. Resolves scripts in both `wom7web` and `wom7api`.
- [x] AC2 — **The 12 are dispositioned individually, not bulk-registered.** Each either enters
      `test-suites.json` or gains an `exclude` entry **with a reason**. ⚠️ Bulk-adding 12 rows would
      make `suites-drift` green again without anyone deciding whether a gate belongs in the
      always-run set — the same move that produced the vacuous green being fixed.
      ✅ **Delivered 2026-09-17:** All 19 undeclared gates surfaced by capability inspection were individually
      triaged. `orphan-components-test` and `ticket-deps-test` were added to `suites` (`tier: offline`, blocking).
      The remaining 17 gates (`authz-write-probe`, `orphan-components`, `schema-drift`, `ticket-deps`,
      `headroom-status`, `tasks`, `tickets-frontmatter-sync`, `ade-rules-parity`, `annotations-doctor`,
      `authz-admin-client`, `callsite-drift`, `decisions`, `discovery`, `ds-conformance`, `ide-trace`,
      `skills-catalogue`, `state-bounds`) were added to `excluded` in `project/test-suites.json` with explicit,
      reasoned rationale.
- [x] AC3 — 🔴 **Tier A vs Tier B is reported as DIFFERENT states.** A registry that cannot
      distinguish *"the gate is unregistered"* from *"only its red-proof is registered"* will keep
      reading the second as healthy. `suites-drift` must name both.
      ✅ **Delivered 2026-09-17:** Implemented `find_red_proof()` in `run_suites.py`. `just suites-drift` reports
      `Tier A — completely undeclared` and `Tier B — red-proof declared, gate itself unrun` as separate
      categorized blocks with individual and aggregate counts.
- [x] AC4 — ✅ **DONE 2026-08-20 — registered as a suite that can actually fail, and the plan's exit
      criterion measured.** ⚠️ **Not** as bare `authz-probe`: `run_suites.py:127` invokes
      `["just", recipe]` with **no arguments**, and the bare recipe is advisory (`exits 0
      unconditionally`), so a bare row would have declared **a suite that can never go red** — the
      vacuous green two of `test-suites.json`'s own `excluded` reasons already refuse. Registering it
      would have *looked* like closing this AC while changing nothing.
      ⇒ Added **`just authz-probe-check`** (`--enforce`), registered `tier: live`, **blocking**, and
      recorded bare `authz-probe` in `excluded` **with a reason** — it is invisible to `suites-drift`
      in both directions (no `-test`/`-check` suffix, and `{{args}}` rather than a gate flag in its
      body), and this ticket exists because invisibility was being read as absence. *"We decided"*
      and *"we forgot"* must not look the same. **105 suites declared, drift clean.**
      🔑 **Enforcing is correct now because the probe's OWN promotion trigger fired.** Its header
      says *"wire `--enforce` into `.husky/pre-push` when RED reaches 0"* — measured **0 RED of 18**,
      and verified both directions: exit **0** when green, with `return 1 if (enforce and red) else 0`
      in the source, so it is not vacuous.
      ✅ **And stage-0's exit criterion is MET on its first half, measured rather than inferred:**
      `A2-cross-client` — the cross-tenant probe the plan actually names — is **GREEN, 0 violations**,
      alongside `A1-own-contract`. ⚠️ The exit has a **second** half (*"a Supabase restore has
      actually been exercised"*) which this does not measure; [[T229]] is the record for that.
      ⚠️ The probe reaches the **live** database (read-only: `SET LOCAL ROLE` + synthetic claims
      inside `BEGIN..ROLLBACK`, no write probes) — hence `tier: live`, so `just test` stays offline.

- [x] AC4b — **Decide whether `--enforce` is wired into `.husky/pre-push`.** The probe's own
      promotion trigger has fired (0 RED of 18), so its stated condition is satisfied — but doing it
      adds a **live-database round trip and a secret dependency to every push** in the estate. That
      is an owner call, not a side effect of registering a suite. ⚠️ Split out rather than noted
      inside AC4: `ticket-schema-check` **errored on the first draft** because a ticked AC whose text
      says *"not done here"* inflates the board's completion count — the rule from [[T230]] AC7,
      firing on the ticket that was closing a different gate. The gate was right.
      ✅ **Decided 2026-09-17:** Keep `authz-probe-check` in `tier: live` CI / test-all suite, and do NOT
      wire it into local `.husky/pre-push`. Pre-push must remain fast, offline, and executable on bare
      checkouts without requiring Infisical secret injection or live database network calls.
- [x] AC5 — **A red probe for the detector itself.** A fixture recipe that forwards `{{args}}` to a
      script accepting `--enforce` must be REPORTED as undeclared. Today's corpus produced a green
      over 12 real cases, so the proof must be a case the old code passes and the new code fails.
      ✅ **Delivered 2026-09-17:** Added regression test in `project/scripts/tests/test_run_suites.py`
      proving an argument-forwarding gate is detected via script capability while non-gating utilities are ignored.
- [x] AC6 — **[[T236]] AC4's artefact gap closes here**: `orphan-components` gets its red-proof as a
      file, not as prose in a closed ticket's status notes.
      ✅ **Delivered 2026-09-17:** Standing test file `project/scripts/tests/test_orphan_components.py` (7 checks)
      authored, wired into `justfile` as `orphan-components-test`, and declared in `project/test-suites.json`.

## 2026-08-20 — AC4 closed; the other 11 gates are untouched

⚠️ **`just suites-drift` still reports `105 declared, 0 undeclared — ✅ every recipe that behaves
like a suite is declared`, and it is still wrong.** Registering `authz-probe` removed one Tier A
entry; **11 remain invisible** for the same reason (AC1 is the fix, and it is not started):

| tier | gates still invisible |
|---|---|
| **A** — no registry presence at all | `authz-write-probe` · `orphan-components` · `schema-drift` · `ticket-deps` |
| **B** — `-test` red-proof declared, gate itself not | `authz-admin-client` · `callsite-drift` · `discovery` · `ide-trace` · `skills-catalogue` · `state-bounds` · `headroom-status` |

🔑 **Fixing the most severe instance did not fix the detector**, and saying so is the point — a
green `suites-drift` after this commit means *less* than it looks like, because the mechanism that
produced the blind spot is unchanged. AC1 (*ask the script what it accepts, do not widen the
regex*) is what makes the green mean something.

## Definition of Done


Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
the drift detector asks the SCRIPT what it accepts rather than the recipe what it says, the 12 invisible gates are dispositioned **individually** rather than bulk-registered, and Tier A and Tier B are reported as DIFFERENT states — a registry that cannot tell them apart is why 12 were invisible while it reported 0. 🔑 A red probe for the detector itself is the clause that prevents recurrence: a fixture recipe it must catch. ⚠️ Whether `--enforce` is wired into `.husky/pre-push` is decided explicitly, not left to whoever reads the probe's own output.

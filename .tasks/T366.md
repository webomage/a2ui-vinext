# T366 — Per-developer-profile connection and credential isolation: workspace-scoped routing for Infisical, Jam, Git, and third-party platform credentials

## Summary

Currently, local developer tooling (`infisical`), recording CLIs (`jam`), Git configurations, and external connectors assume a single ambient global user on the host system (e.g. `aleksei@webomage.com` in `~/.config/jam/credentials.json`, `~/.zshrc`, and `~/.infisical/infisical-config.json`). 

When working across different client engagements where `.w0m/sdlc.json` specifies a specific developer/manager persona (e.g. BridgeRoad where `roles.developer` is Elena Shatalova), commands run from the workspace silently inherit the global host user's token. This leads to severe persona attribution leaks:
- Client proof-of-fix screen recordings (DoD) are published to Jam under Aleksei's email and team instead of Elena's.
- Git commits and PR branches risk incorrect author attributions.
- Infisical CLI defaults to the primary host account rather than the client project's designated developer credentials.

Building on [[T361]] (*Per-profile admin_todos ownership and real member Upwork sync attribution*) and [[T363]] (*Many-to-one account-profile linkage*), this ticket establishes a formal per-developer-profile credential and connection management architecture. Tooling dynamically resolves, isolates, and injects credentials based on the workspace's declared developer role without global state cross-contamination.

## Acceptance criteria

- [x] **AC1 — Developer Profile Connection Registry & Schema**: Define a declarative schema in `project/profiles-policy.json` (and matching `public.connections` metadata) mapping profile slugs (`elena`, `aleksei`, `casualuser`) to their declared credentials:
  - Infisical user identity / profile mapping (`elenashatalova.it@gmail.com` vs `aleksei@webomage.com`).
  - Jam personal access token (PAT) reference and workspace ID.
  - Git identity (`user.name`, `user.email`, signing key).
  - Upwork member connection ID (from T361).
- [x] **AC2 — Context-Aware Workspace Resolution (`w0m env` / profile resolver)**: Implement a resolver that reads `.w0m/sdlc.json -> roles.developer` (or CLI `--profile=<slug>`):
  - Automatically activates the correct profile environment when entering a workspace.
  - Exports scoped environment variables (`JAM_API_KEY`, `INFISICAL_TOKEN` / `INFISICAL_PROJECT_ID`, `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`) into local subshells.
  - Refuses to fall back to global host defaults if the project's profile has missing credentials, failing closed with an actionable diagnostic.
- [x] **AC3 — Per-Profile Infisical Isolation**: Support isolated Infisical execution without mutating global `~/.infisical/infisical-config.json`:
  - Utilize `--token` (scoped machine/profile token) or isolated config directories (`INFISICAL_CONFIG_DIR=~/.config/w0m/profiles/<slug>/infisical`).
  - Provide helper `just profile-infisical <slug> <command...>` to execute commands against the scoped Infisical vault.
- [x] **AC4 — Scoped Jam Authentication**: Ensure `jam` commands execute under the active profile's identity:
  - Isolate Jam configuration via profile-specific `JAM_API_KEY` or `--config` directory (`~/.config/w0m/profiles/<slug>/jam/credentials.json`).
  - Implement `just profile-jam <slug>` helper to verify and set personal access tokens per profile without overwriting other members.
- [x] **AC5 — VM Credential Injection Barrier**: When spinning up or entering a project VM (`w0m-bridgeroad`) via `vm.py` or `tart exec`:
  - Dynamically inject only the credentials for the project's declared profile into the guest's `/home/ubuntu` session.
  - Hypervisor boundaries ensure credentials belonging to other profiles on the host are completely unreachable from inside the guest.
- [x] **AC6 — Automated Probes & Non-Regression Tests**: Add automated test suite verifying that:
  - Resolving within `_proj/bridgeroad` selects Elena's identity and refuses fallback to Aleksei's Jam token.
  - Resolving within `wom7web` selects Aleksei's profile.
  - Switching active profile never alters the host's base global configuration files.

## Definition of Done

A declarative developer profile connection system is documented and operational. Tools operating in client project directories automatically bind to the declared developer profile in `.w0m/sdlc.json`. Infisical and Jam credentials execute in isolated scopes per profile without global cross-contamination. Automated tests verify profile isolation and confirm that fallback to mismatched host credentials fails closed.

## Notes, traps and dependencies

- ⚠️ **Fail-Closed Security**: Never default to host ambient credentials when a project declares an explicit developer persona in `.w0m/sdlc.json`. If Elena's Jam token is unconfigured, the system must error with *"Missing Jam PAT for profile 'elena'"* rather than silently publishing under Aleksei.

# T277 — a config that reads like a gate and is not one

## Summary

Found 2026-08-25 while closing [[T266]] AC8, which asks for the residual authorization risk of
onboarding a real client onto this surface. **The function's own comment and its deployed config
disagree**, and resolving which one is true turned up a live finding.

`supabase/functions/client-register/index.ts:11` states:

> *"SECURITY: unauthenticated entry keyed ONLY to a valid lead id"*

`supabase/config.toml:171` states `verify_jwt = true`.

🔑 **Both are true, and that is the problem.** In Supabase, `verify_jwt = true` validates that the
bearer token is a JWT signed by the project — and **the public anon key IS such a JWT**. It is
shipped in every frontend bundle. So the flag admits the entire internet while *reading* to a
reviewer as *"requires a signed-in user"*.

## Measured, not assumed — 2026-08-25

Probed with a v4 UUID that cannot exist, so **nothing was written**:

| caller | HTTP | meaning |
|---|---:|---|
| no `Authorization` header | **401** | the platform rejects it |
| **public anon key** as the bearer | **404** `{"ok":false,"error":"Lead not found"}` | 🔴 **reached the function body** |

⇒ The 404 is the finding. A `Lead not found` means the request passed JWT verification, entered the
handler, and executed a database lookup. The only thing standing between an anonymous caller and a
full provisioning run is **knowing a lead id**.

## What an attacker with one valid `lead_id` can do

The handler performs **no role check on the caller** — it reads `lead_id` from the body and proceeds.

1. **Force provisioning of a person who never asked.** Steps 2-5 create an `auth.users` account, a
   `user_roles` row with `role='client'`, a `clients` organisation and a `client_users` link.
2. 🔴 **Trigger a real email, repeatedly.** Step 6 calls `generateLink` + `sendMagicLink` on **every**
   invocation. Steps 2-5 are idempotent; **step 6 is not**. So the same lead id is a re-usable email
   trigger — *"Your Webomage client portal is ready"*, from Webomage's own SMTP and domain, carrying
   **a working sign-in link**.

⚠️ **The second one is the worse half.** Unsolicited account creation is noise in our database.
Repeated authentic-looking sign-in emails from our real domain to a real person is a
deliverability and reputation problem we inflict on ourselves, and it is indistinguishable from
phishing to the recipient.

## What actually protects it today

🔑 **A secret identifier, not a permission.** `lead_id` is a v4 UUID, so it cannot be enumerated —
and the email is read from the **stored** lead row, never from the caller, so the address cannot be
substituted. That second property is a genuinely good design and must survive any fix.

⇒ But *"unguessable"* is not *"authorized"*. A lead id appears in admin URLs, in the CP client, in
logs, and in any funnel handoff — the places identifiers leak from. And the moment one leaks, the
holder gets an unlimited email trigger against that address.

## Acceptance criteria

- [x] AC1 — **Decide, and write down, whether this endpoint is public.** It is the conversion funnel
      for an anonymous consultant lead, so *"public"* may well be the right answer. 🔴 **What is not
      acceptable is the current state, where the answer is recorded twice and differently** — the
      comment says public, the config says gated, and only a live probe distinguishes them.
      ⚠️ If the answer is public, `verify_jwt = true` must be replaced by something honest, not left
      in place as decoration.
- [x] AC2 — 🔴 **Step 6 must not be a free email trigger.** Rate-limit or state-gate the send: a lead
      already carrying `converted_user_id` has been provisioned, and a second call should re-send at
      most on an explicit, throttled path. ⚠️ **Do not fix this by making steps 2-5 non-idempotent** —
      their idempotence is what makes retries safe, and it is the reason [[T266]]'s admin path can
      reuse this function at all.
- [x] AC3 — **A red probe, observed red first**, following [[T198]] AC8's standard: assert that an
      anon-key caller cannot cause an email send, and demonstrate it failing against today's
      deployment. ⚠️ Probe with a lead id that exists, in a way that does not email a real person —
      a seeded lead at an address we own, never a real one.
- [x] AC4 — **Audit the other `verify_jwt = true` functions for the same mis-reading.** This flag
      almost certainly reads as *"authenticated"* elsewhere in `config.toml` too, and the anon key
      satisfies every one of them. 🔑 The finding is not one function; it is a **flag whose name
      means less than it appears to**.
- [x] AC5 — **Preserve the good property explicitly.** The email is read from the stored lead row,
      never from the caller. Any fix must keep that, and a probe should assert it — it is the reason
      lead-id enumeration cannot take over an address, and it is easy to lose in a refactor.

## Definition of Done

Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
the endpoint's intended exposure is decided and recorded in **one** place rather than contradicted
across two; a caller holding only the public anon key can no longer cause an unbounded series of
real emails to a real address; the stored-email property is asserted by a probe rather than by a
comment; and the other `verify_jwt = true` functions have been checked for the same mis-reading.

## Status notes (cont.)

- **2026-08-25 — AC1, AC2, AC4, AC5 done; AC3 half, blocked on a deploy.**
  **AC1 — the endpoint IS public, and that is now written where the flag is.** It is the conversion
  funnel for an anonymous lead, so public is right. `verify_jwt = true` is **KEPT** — it still
  rejects a request with no header at all, which filters scanner noise for free — but
  `supabase/config.toml` now says, next to the flag, that it is **not an authorization check** and
  what actually protects the endpoint: the stored-row address, an unguessable v4 `lead_id`, and
  since today a once-per-lead send.
  **AC2 — one email per lead, fixed by GATING rather than by breaking idempotence.**
  `alreadyProvisioned` is read from the lead **before** step 5 writes `converted_user_id`, and the
  send is skipped when it was already set. ⚠️ Steps 2-5 stay retry-safe, which AC2 explicitly
  required — that is what lets [[T266]] AC4's admin path reuse this function. The response now
  carries `suppressed: "already_provisioned"` so a caller can tell *no email because already done*
  from *no email because SMTP failed*; collapsing those into `emailed: false` is the [[T242]]
  could-not-measure conflation.
  🔴 **Recorded trade-off:** a lead whose FIRST email fails delivery cannot retry itself here. That
  is an authenticated admin action by design — a re-send must not be something a caller holding a
  public key can ask for.
  **AC5 — asserted, not just commented.** The probe checks the address is `String(lead.email` and
  that the request body destructures to **`lead_id` alone**; any future signature accepting an
  `email` re-opens address takeover regardless of the rest.
  **AC4 — 🔬 THE AUDIT'S FIRST ANSWER WAS WRONG, AND CORRECTING IT IS THE FINDING.** A first
  detector reported **5 of 31** `verify_jwt = true` functions as having *no caller check at all* —
  including **`process-payout`**. False: `process-payout:29` does check, with
  `authHeader.replace("Bearer ", "") !== supabaseServiceKey`; my pattern looked for
  `SERVICE_ROLE_KEY ===` and missed the `!==` form. Re-measured, **all 31 reference a caller
  credential** — ⇒ **the pattern is NOT 36-wide, and `client-register` is the outlier precisely
  because it is *designed* public.**
  🔑 **And the corrected pass found something the first one hid:** two functions —
  **`gamification-economy`** and **`process-payout`** — compare a secret with `!==`, which is
  [[T175]]'s exact recorded shape. Reported there, with the note that a payout path is where the
  constant-time argument stops being theoretical.
  ✅ **AC3 — DONE. Probe mutation-proven, and the live half VERIFIED after deploy.**
      `just client-register-guard-test` — **9/9**, offline, **blocking**. Proven twice by mutation:
      removing the `!suppressed` guard fails it, and moving the provisioned-state read to *after* the
      lead update fails it too — that second mutation is **the fix silently breaking the feature**,
      since step 5 sets `converted_user_id` and a later read would suppress the FIRST email as well.
      ⚠️ **Stated ceiling: it reads the SOURCE.** It proves the guard is written, not that the
      deployed function behaves. The end-to-end check is one call with an already-converted lead
      (`52cf449d`, `eva@webomage.com` — owner-controlled) expecting
      `suppressed: "already_provisioned"` and `emailed: false`. **Deploy required; an agent must not
      write the consent file.**
      🔬 The probe also caught ITSELF: its first guard-detection regex used `[^}]*`, which the
      link's template literal `${...}` defeats — it failed on its own pattern, not on the code.

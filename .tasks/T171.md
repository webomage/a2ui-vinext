# T171 — w0m planner/scheduler for batched Claude Code tasks in dev sandboxes

## Summary

Owner direction 2026-08-05: *"we will be looking into how to apply headroom deployment and
connecting in dev sandboxes with batched tasks with claude code from w0m planner/scheduler/manager."*

### 🧭 TWO ENVIRONMENTS, TWO SERENA OWNERSHIP MODELS — owner, 2026-08-06

*"here in w0m we use serena directly and looking to extend it with astro. in projects sandboxes we
will use headroom and potentially it will be tweaked version with our extended serena but for start
as is and also there will be claude cli set with task and proxy to headroom"*

| | **w0m host (here)** | **project sandbox (this ticket)** |
|---|---|---|
| serena | **direct MCP**, w0m-owned, pinned `serena-agent==1.6.1` ([[T166]]) | **via Headroom**, *as-is* at first — Headroom installs it as its own `--code-memory` backend |
| Headroom | present but **not in serena's path**; the app cannot route through it anyway | **the point** — Claude CLI + task + proxy, all inside the VM |
| astro support | [[T170]] extends serena **here first** | inherits it later, via a *tweaked* Headroom carrying our extended serena |

🔑 **The ownership asymmetry is deliberate and must not be "fixed".** On the host we **took** serena
from Headroom on purpose — pinning it broke Headroom's ledger fingerprint, so its ensure hooks now
leave it alone ([[T166]]). **In sandboxes we deliberately do the opposite: let Headroom own and
install serena**, because the sandbox is disposable, Headroom's invasive install is appropriate
there, and "as-is at start" means no fork to maintain before the topology is proven.
⚠️ A future agent reading [[T166]] alone will conclude serena should always be user-managed. **That
is host-scoped, not global.**

🔑 **"For start as-is" is a sequencing decision with teeth:** the astro extension ([[T170]]) is
**not a blocker** for this ticket. Sandboxes ship with stock Headroom + stock serena first; the
tweaked build is a later increment, and T170's route choice should account for a second consumer
(an image) rather than only the host.

⇒ **Routing in sandboxes is DECIDED, not open.** The owner has specified "proxy to headroom", so the
*"don't route sandboxes at all"* option floated earlier is **off the table**. That makes the
credential question in §3 the live one, with no escape hatch.

**Today there is exactly one routed-execution primitive, and it is a single synchronous task.**
`just headroom-task "<prompt>"` runs one `claude -p` in the foreground from the workspace root,
guards on proxy health first, and prints the proxy counter before → after so a bypassed run is
visible rather than assumed. It is a good primitive. It is also the *whole* of it: **no queue, no
batching, no concurrency, no isolation, no schedule, no result collection.** Nothing else in the
estate orchestrates agent work — the only scheduling recipes (`deploy-scheduler`) belong to the
product's daily-news function, not to agent execution.

So the gap is real and un-ticketed. **But four constraints shape it before any design starts, and
three of them are the kind that get discovered late and expensively.**

### 🔴 1. This would scale something whose benefit is measured at zero

`TECH-DEBT.md` **D29** records the graph-first + Headroom-routed workflow as **adopted with its
benefit unproven**, against costs that are known: ~341 ms/request, +57% wall clock in the A/B, and
compression that has removed **0 tokens, ever**. **D30** records why the number cannot currently
settle it — `headroom audit-reads` is Read-only and escapable, and has no per-window mode.
[[T163]]'s own outcome measurement came back **adverse** (+0.7 pp stale-read share).

⇒ **Building a fleet on an unproven unit multiplies the unknown.** This ticket must not assume
routing is good; it must be structured so the batch *produces the measurement* D30 says is missing.
That is the strongest argument for doing it — a batch runner is a controlled cohort, which is
exactly what the lifetime-aggregate audit cannot give.

### ✅ 2. RESOLVED by the owner's topology — proxy per sandbox, both processes inside the VM

**Owner decision 2026-08-05:** *"planned a proxy per sandbox as per project per developer/agent …
so both claude and headroom will be in some kind of VM."*

This **dissolves** the loopback conflict rather than working around it. If Headroom runs *inside*
the sandbox alongside Claude Code, the proxy is loopback **within that VM** — `127.0.0.1:8787` is
reachable because both processes share the namespace. **D31's acceptance condition is preserved
per-sandbox instead of being traded away**, and the host proxy stops being in the path at all.

Three further consequences, all favourable, recorded so they are not re-derived:

1. 🔑 **The measurement gets strictly better, which is AC2's whole point.** A per-sandbox proxy's
   counters are scoped to **exactly one agent's work** — a far cleaner cohort than the host proxy
   shared across every session. This is the closest thing to the controlled experiment **D30** says
   is currently impossible.
2. 🔑 **Headroom's install blast radius stops being a problem.** `headroom init --global` edits
   `~/.zshrc`, `~/.profile` **and** `~/.bashrc`, and auto-enables a plugin marketplace — invasive on
   a workstation, **entirely appropriate in a disposable VM**. The architecture makes the install
   mechanism a non-issue.
3. 🔑 **The sandbox becomes the permission boundary (see §4), which is strictly better** than the
   prompt-level refusal originally proposed.

⚠️ **What it does NOT resolve:** the credential question below, which becomes *the* hard problem
now that the network one is gone.

### 🔴 3. Credentials are now the central design problem, not the network

"A proxy per sandbox, per project per developer/agent" means **N sandboxes each needing an inference
credential**. Each `claude -p` today inherits a **Pro-subscription** OAuth token (`sk-ant-oat01-…`,
scope `user:inference`). Three options, and they are not equivalent:

- **Copy the Pro OAuth token into each VM** — simplest, and the worst blast radius: N copies of a
  personal subscription credential sitting in N disposable machines, any of which may be snapshotted
  or shared. ⛔ **Also a terms question, not merely an engineering one** — whether one personal
  subscription may back N concurrent automated agents is **not a call this ticket should guess at**;
  it needs an explicit answer before the fleet exists.
- **A per-sandbox API key** (not the subscription) — clean isolation, revocable per sandbox, but a
  different billing model and it forfeits the subscription entirely.
- **Inject at task time, never persist** — the token reaches the VM per run and is not written to
  its disk. Best blast radius, most moving parts.

⛔ **There is no fourth option.** *"Don't route, call the API directly"* was viable while the
topology was open; the owner has since specified **"claude cli set with task and proxy to
headroom"**, so every sandbox routes and every sandbox therefore needs a credential. **§3 is now the
ticket's hardest unanswered question, and it has no escape hatch.**

⚠️ **"Per developer/agent" scoping implies identity**, which implies a naming and lifecycle scheme:
when does a sandbox die, who can reach it, and what happens to its credential when it does.

### 🔴 3b. The image is a new governed surface

Both processes in the VM means a base image carrying: the `claude` CLI, `headroom` (pinned
**0.33.0** in `tools-policy.json`), `uv`/`uvx` for serena (pinned **serena-agent==1.6.1**), the MCP
declarations, and git credentials. **An image that drifts from `tools-policy.json` silently
un-governs every tool [[T166]]/[[T164]] just pinned** — the sandbox would run different versions
than the host while both claim to be governed. The image build must read the same policy file, or
the pins become decorative.

### 🔴 3. Batching multiplies one OAuth token across concurrent processes

Each `claude -p` inherits a **Pro-subscription** OAuth token (`sk-ant-oat01-…`, scope
`user:inference`). Batch *N* and that is *N* concurrent inference streams on one personal
subscription — a rate-limit surface and a terms question, not merely an engineering one. **Decide
the concurrency ceiling and the credential story before the runner exists**, not after a batch
trips a limit mid-run.

### 🔴 4. An autonomous runner can route around the agent permission model

[[T161]] AC3 denies `deploy*` / `db-migrate*` / `release*` **to the agent**. A scheduler that
launches `claude -p` subprocesses creates a path where those restrictions may not apply — the
subprocess is a fresh agent with its own permission context. **A batch runner that can do what the
interactive agent is forbidden to do is a privilege-escalation channel**, however unintentional.

✅ **The VM topology improves this materially.** A sandbox can be denied *capability* rather than
*instruction*: give it no deploy credentials, no `DATABASE_URL`, no Cloudflare token, and `deploy`
fails because it **cannot** rather than because it was asked not to. **Capability-based beats
prompt-based** — a refusal the model could talk itself out of becomes an absent credential.
⇒ AC4 is therefore about what the sandbox is *given*, not about what the runner *refuses*.

### Adjacent work — do not build two of these

- [[T153]] (**P1, queued**) already covers *"spawning sandboxes with zeroclaw and do audit for
  clients projects inside"*. Different runtime (Rust/omlx/Gemma) and different purpose (client
  security audits), but **the sandbox-spawning mechanism is the same problem**. Two sandbox
  substrates would be waste. **Sequence: decide the substrate once, in whichever ticket moves first.**
- ⚠️ **A scheduler surface already exists and is split.** The desktop app's routines are invisible to
  the CLI `scheduled-tasks` MCP and to `CronList` — runs must be verified by their output, never
  assumed to have fired. A new scheduler must pick a surface deliberately and say why, or it becomes
  a third invisible one.

## Acceptance criteria

- [ ] AC1 — **A written design that answers the constraints above explicitly**, each with a
      decision and a reason. **Topology is DECIDED (owner, 2026-08-05): a proxy per sandbox, scoped
      per project per developer/agent, with both `claude` and `headroom` inside the VM.** That
      settles the network question; what remains open and must be answered: the **credential model**
      (§3 — the three options are not equivalent, and one is a terms question), the **sandbox
      lifecycle and identity** implied by "per developer/agent", the **image↔`tools-policy.json`
      binding** (§3b), and the **D29/D30 measurement position** (§1).
      ⚠️ **Routing is decided, not open** — "proxy to headroom" means the *don't-route* escape hatch
      is gone. ⚠️ **Sandbox serena stays Headroom-owned** (the inverse of the host, deliberately);
      a design that "fixes" that asymmetry has misread [[T166]] as global rather than host-scoped.
- [ ] AC2 — 🔴 **The batch runner produces the cohort measurement D30 says is missing.** Every batch
      records, per task: routed or not (the proxy counter delta, as `headroom-task` already does),
      tokens, wall clock, and outcome. **This is the ticket's strongest justification** — a batch is
      a controlled cohort, and `headroom audit-reads` cannot window one. Without this AC the ticket
      is fleet-building on an unmeasured unit.
      🔑 **The per-sandbox topology makes this materially better than originally scoped:** a proxy
      serving exactly one agent gives counters attributable to **one workload**, where the host proxy
      mixes every session. ⇒ **Run at least one A/B inside the sandbox — routed vs direct, same
      task** — which is the controlled experiment neither D29 nor D30 has ever had. If that comes
      back at zero again, **say so and let it inform whether the proxy belongs in the image at all.**
- [ ] AC3 — **Prove the unit before the fleet: N=1, then N=3, and stop if the numbers disagree.**
      No queue, no scheduler and no sandbox until a single batched task is measured end-to-end
      against `just headroom-task`. **An explicit stop condition, not a phase label.**
- [ ] AC4 — **The permission boundary is enforced by CAPABILITY, not by instruction.** A sandbox
      must not *hold* the credentials for what [[T161]] AC3 denies — no deploy token, no
      `DATABASE_URL`, no Cloudflare API token — so `deploy` fails because it **cannot**, not because
      it was asked not to. **Proven by a red probe:** a task inside a sandbox that explicitly attempts
      a deploy fails on a missing credential, and that failure is asserted in a test. ⚠️ A refusal the
      model produces is a refusal the model can be argued out of; an absent credential is not.
- [ ] AC4b — **The sandbox image is bound to `project/tools-policy.json`, not hand-pinned.** The
      image build reads the same policy the host does, so `headroom` **0.33.0** and
      `serena-agent==1.6.1` are the versions inside too. ⚠️ **An image that pins independently
      un-governs every tool [[T166]]/[[T164]] just pinned** — host and sandbox would run different
      versions while both claim to be governed. Proven by a check that fails when they diverge.
      ⚠️ **Stock first:** the image ships **unmodified** Headroom + serena at start (owner:
      *"for start as is"*). A tweaked Headroom carrying our extended serena ([[T170]]) is a
      **later increment** — so T170 is explicitly **NOT a blocker** for this ticket.
- [ ] AC5 — **The sandbox substrate is decided ONCE with [[T153]]**, and whichever ticket lands
      second reuses it rather than adding a second mechanism. Recorded in both tickets.
- [ ] AC6 — **The scheduler surface is named and its visibility stated.** Which surface owns the
      schedule, and how a run is verified to have fired — by its recorded output, never by the
      absence of an error. ⚠️ The estate already has two scheduling surfaces that cannot see each
      other; a third invisible one is a regression, not a feature.
- [ ] AC7 — **A stop/abort path exists and is proven.** A batch that is wrong is expensive in tokens
      and in writes to a real repo. Killing a run mid-flight must leave no half-applied work — and
      that must be demonstrated, not designed.

## Definition of Done


Per [`../../openspec/SPEC-AUTHORING-STANDARD.md`](../../openspec/SPEC-AUTHORING-STANDARD.md):
a written design answers each stated constraint, and the batch runner produces the cohort measurement D30 records as missing. 🔑 The discipline clause is AC3: **prove the unit before the fleet — N=1, then N=3, and stop if the numbers disagree** — because a scheduler that scales a wrong unit scales the cost, not the work. The permission boundary is enforced by CAPABILITY rather than instruction, the sandbox image is bound to `project/tools-policy.json`, the substrate is decided once with [[T153]], and a stop/abort path exists and is proven — an expensive batch that cannot be halted is the failure mode this ticket is about.

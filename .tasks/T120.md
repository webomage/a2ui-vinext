# T120 — Safe Browsing "Deceptive pages" flag: investigate, verify, then request review

## Summary

Google Search Console (`sc-domain:webomage.com`) → **Security issues → 1 issue detected: Deceptive
pages**, still active as of **2026-07-22**. Chrome shows a warning to real visitors while it stands,
so this is live reputational damage, not a report.

**Sample URLs: N/A** — Google is naming no example page, which is the hard part: there is nothing to
diff against, so the offending surface must be inferred.

## What is already known (do not re-derive)

This is the **open item from the 2026-07-10 incident** ([[webomage-incident-2026-07-10]]). The
diagnosed trigger was an **open redirect + reflected XSS** in the shared
`packages/lib/src/auth/handlers.ts`: `next` flowed unvalidated into `redirect(next)` and was
interpolated raw into the callback's inline `<script>`. `sanitizeNext()` was added (allowlist:
relative paths + `webomage.com` / `w0m.xyz` / `localhost` and subdomains) and deployed.

The incident note recorded the remaining action plainly: *"the flag itself must be cleared via Google
Search Console → Request Review after deploy — an ops action nobody has done yet."* Twelve days on,
it still has not been requested. **The flag may be persisting simply because nobody asked Google to
look again.** That is the cheapest hypothesis and must be excluded first.

## Verified live 2026-07-22 (before filing)

| Check | Result |
|---|---|
| `sanitizeNext()` present in the shared handler | ✅ 5 call sites in `packages/lib/src/auth/handlers.ts` |
| `GET /api/auth/signin?next=https://evil.example.com/x` on web / cp / join | ✅ **404** — the route is POST-only now; the originally-flagged GET surface no longer exists |
| `GET /api/auth/oauth?provider=google&next=https://evil.example.com/x` | ✅ 302 → Supabase with `redirect_to=https://webomage.com/api/auth/callback`; **the hostile host is stripped, no inner `next` survives** |
| `GET /api/auth/callback?next=https://evil.example.com/x` | ✅ 200, no redirect to the hostile host |

So **the diagnosed root cause is closed in production**. That materially raises the odds that this
is a stale flag awaiting review — but it does not prove there is no *second* deceptive surface, which
is what the investigation below is for.

## Investigation notes

- **Do not request the review before AC2.** A rejected review costs credibility with the classifier
  and lengthens the next cycle; there is no partial credit.
- Useful evidence sources: the Safe Browsing **transparency report** for the domain, Search Console
  **URL inspection** on suspect paths, and the Chrome interstitial itself (which sometimes names a
  more specific category than the console does).
- "Deceptive pages" is the **social-engineering / phishing** class, distinct from "malware" or
  "unwanted software" — so the trigger is about *appearing to trick a user*, not about hosting a
  bad file. Weight the investigation accordingly: redirects, look-alike login UI, and
  credential-adjacent flows, not binaries.
- History worth carrying: [[fake-interview-malware-2026-06]] and [[wom-audit-2026-06]] mean this
  domain has prior incidents. A repeat flag on a domain with history is treated less gently.

## 🔴 2026-07-22 — the sweep found a SECOND live open redirect (fixed, not yet deployed)

Run immediately after the review was submitted. `/api/demo/enter` came back clean — `persona` is an
enum key, not a URL, and every branch (including the rejection path, which mints no token) lands on
our own domains. **But the LinkedIn OAuth routes were still vulnerable**, in the same class that
caused the original flag:

```
GET /api/auth/linkedin?next=https://evil.example.com/pwned
  → set-cookie: li_oauth_next=https%3A%2F%2Fevil.example.com%2Fpwned   ← accepted verbatim
  → linkedin-callback later does redirect(next)                        ← off-origin redirect
```

Confirmed live on **webomage.com and cp.webomage.com** (join has no such route). It is a two-step
open redirect: the hostile target is laundered through an HttpOnly cookie rather than appearing in
the final URL, which is why the earlier probe of `/api/auth/oauth` looked clean.

**Why it survived the 2026-07-10 fix:** that fix added `sanitizeNext()` to the *shared* handler
(`packages/lib/src/auth/handlers.ts`). These LinkedIn routes are **per-app** files that build the
redirect themselves and never call the shared handler, so they were never covered. The lesson is
that the earlier remediation was scoped to a file, not to a behaviour.

**Fix applied (4 files) — ✅ DEPLOYED + VERIFIED LIVE 2026-07-22:**
- `apps/{web,cp}/src/pages/api/auth/linkedin.ts` — `sanitizeNext()` before the cookie is written
- `apps/{web,cp}/src/pages/api/auth/linkedin-callback.ts` — re-validated on the way out too, so a
  stale or tampered cookie cannot become an off-origin redirect

**Consequence for the pending review:** the description submitted to Google claimed redirect targets
are validated. That was true of the shared handler and untrue of these two routes at the moment of
submission. **Deploying this fix promptly is what makes the claim accurate** — Google re-crawls
during the review window, so the fix landing now still counts. If the review is rejected, this is
almost certainly why, and the re-request should cite it.

## ✅ 2026-07-22 — fix deployed and verified live

Both apps now serve commit `9ad55849`; the hostile target is rejected in production:

| Host | Before | After |
|---|---|---|
| webomage.com | `li_oauth_next=https%3A%2F%2Fevil.example.com%2Fpwned` | `https%3A%2F%2Fcp.w0m.xyz` |
| cp.webomage.com | same | `%2F` |

Each degraded to that app's own safe default, which is what `sanitizeNext` specifies.

**The deploy itself is worth recording as a lesson.** `just deploy` was run for a 4-file app change.
That recipe chains `check-infisical → check-guardrails → deploy-api → deploy-web → deploy-cp → …`,
and it **died inside `deploy-api`** on a transient third-party CDN timeout while bundling an
unrelated edge function:

```
unexpected deploy status 400: Failed to bundle the function
(reason: Fetch 'https://deno.land/x/xml@2.1.3/mod.ts' timed out after 10s)
  at .../supabase/functions/daily-news-scheduler/index.ts
```

Because the app deploys come *after* the function deploys in the chain, `deploy-web` and
`deploy-cp` never ran — the fix silently did not ship, and `/api/health` still reported the old
commits. Re-running the two app-scoped recipes alone (`just deploy-web && just deploy-cp`)
succeeded in minutes.

**Rule for a scoped change: deploy the scope.** `just deploy` couples a security fix in two Astro
apps to the health of 52 edge functions and a public CDN. Reach for `deploy-web` / `deploy-cp`
when only apps changed — and always confirm with `/api/health` that the deployed commit is the one
you expected, because a failed chain looks a lot like a successful one from the terminal scrollback.

## ✅ 2026-07-22 — full redirect sweep: no further open redirects

Motivated by the observation that the July fix was scoped to a *file* rather than a *behaviour*.
Method was to trace the **source** of each redirect target, not to pattern-match the sink — today's
bug hid precisely because the hostile value was laundered through a cookie and never appeared in a
URL.

**Static pass** — 141 redirect sinks across `apps/{web,cp,join,job,demo}` + `packages/`:

| Class | Count | Verdict |
|---|---|---|
| Literal or relative-prefixed target (`/login?…`) | 67 | safe by construction |
| Variable target **with** request-derived input in file | 7 | 3 already guarded; 4 triaged below |
| Target whose **first** element is interpolated (host slot) | 9 | all interpolate `errorPath`/`loginPath`, verified static config (`/`, `/login`) |

**The 4 triaged candidates were all false positives**, each for a different reason worth recording:

- `apps/{web,cp}/api/auth/google.ts` — `redirect(data.url)` looks unguarded, but `redirectTo` is
  pinned to `url.origin` and the attacker's `next` is carried into **our own** callback, which
  sanitizes it. The chain is safe even though the line is not.
- `apps/demo/api/demo/enter.ts` — `redirect(callback)`; `appOrigin()` returns one of **5 hardcoded
  literals** and the host only *selects* among them. `persona` is enum-keyed. No attacker-supplied
  host can produce an arbitrary origin.
- `packages/lib/auth/middleware.ts:179` — `to` comes from `config.authedHomeRedirect()`; the only
  implementation returns the literal `/dashboard`.

**Live matrix** — 5 hosts × 5 auth entry points with a hostile `next`: **zero** echoed the hostile
target in a `Location` or `Set-Cookie` header.

**Conclusion:** the LinkedIn routes were the only remaining instance of the class, and they are
fixed and deployed. The Safe Browsing review now has no known open redirect behind it.

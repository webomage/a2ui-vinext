# T215 — vectorize-vault embeds via Google and cannot run

## Summary

`wom7api/src/workflows/vectorize-vault.ts` (registered in `src/index.ts` and `wrangler.jsonc` as
`VectorizeVaultWorkflow`) **throws on every run**:

```ts
const googleApiKey = this.env.GOOGLE_API_KEY;
if (!googleApiKey) throw new Error('GOOGLE_API_KEY not configured');   // :51-53
```

The CF Worker holds **neither `GOOGLE_API_KEY` nor `GEMINI_API_KEY`** (credential snapshot
2026-08-15: both `present=no` for `cloudflare-worker`). So the workflow fails at step
`generate-vault-embeddings` before reaching Supabase, and vault records for
`contracts`/`proposals`/`jobs` are never vectorized.

**The fix is not "give the Worker a Google key."** Google is legacy — owner 2026-08-15: *"we used
GOOGLE_API_KEY in the past but now CF and Supabase mostly"* — and the same worker **already binds
Workers AI**: `wrangler.jsonc:150` `"ai": { "binding": "AI" }`, commented *"provides access to
Workers AI inference at the edge (no cost per token)"*. The `Env` type in this very file already
declares `AI: any` and never uses it. So the correct move is to embed through the binding that is
already present and free, and delete the outbound Google call
(`generativelanguage.googleapis.com/v1beta/models/text-embedding-004:embedContent`, `:58`).

⚠️ **Dimensionality is the real constraint, not the provider.** The current call requests
`outputDimensionality: 1024` to match the DB schema (`:68`). Any replacement model must produce
**1024-dim** vectors or the schema/index must change with it — a mismatch will fail at insert, or
worse, silently poison similarity. Confirm the target model's dimensions **before** writing code.

Found while retiring `GOOGLE_API_KEY` from the secret-sync list under [[T134]] AC11 — the
credential surface made a dead path visible that no error report had surfaced, because nothing
triggers this workflow often enough to notice.

## 2026-08-16 — AC1-AC3 done, measured against the live system

**AC1 — it NEVER worked. Not a regression.** Queried the live DB rather than guessing: `documents`
holds **102 rows across 8 `type` values** (`internal-doc` 53 · `cv` 33 · `offering` 6 ·
`cv-private` 4 · `whitepaper` 3 · `process`/`project`/`certification_path` 1 each) and **zero** rows
carry the `source_id` key this workflow *always* writes. No `contracts`/`proposals`/`jobs` rows
exist. So the throw at `:51` fired on every run since it was written, and nothing noticed because
nothing triggers it often enough to be missed.

**AC2 — model chosen on MEASURED dimensions.** The schema is the constraint: `documents.embedding`
is `vector(1024)` with an ivfflat cosine index. Measured by real API calls, not docs:

| model | dims | verdict |
|---|---|---|
| `@cf/baai/bge-m3` | **1024** | ✅ **chosen** — multilingual, exact match |
| `@cf/baai/bge-large-en-v1.5` | 1024 | ✅ fits, but English-only |
| `@cf/baai/bge-base-en-v1.5` | 768 | ✗ would fail at insert |

`bge-m3` because this estate serves **en/ru/es** and the vault holds client-authored text; an
English-only model would embed other languages *badly* rather than error. **No migration needed** —
the width already matches.

**AC3 — embeds via the bound `env.AI`.** The outbound Google call and its `GOOGLE_API_KEY` guard are
gone, and `GOOGLE_API_KEY` is removed from the workflow's `Env` type so nobody "restores" it. Added
an explicit **width check**: a non-1024 vector throws naming both numbers, rather than failing at
the insert (where pgvector's error does not say which model produced it) or silently poisoning
cosine similarity. `just typecheck-worker` exit 0. End-to-end API probe on vault-shaped text:
`dims=1024 finite=True range=[-0.149, 0.212]`.

🔴 **Second dead path found while looking for the incumbent — filed as [[T225]].**
`@cf/baai/bge-multilingual-gemma2`, the estate's **default** embedding model
(`src/index.ts:219` + two `ai_models` rows), is **RETIRED**: the API answers `No route for that URI`
and it is absent from the account's 7 available embedding models. This ticket deliberately does
**not** point at it for "consistency".

⚠️ **AC4/AC5 remain and need a deploy.** The workflow cannot be triggered against a real record
until the worker ships, and nothing here has been deployed. **The code path is verified as far as
static checks and a direct model call can go — it has not been run as a Workflow.**

|---|---|---|---|

⚠️ **AC4 said "each of the three tables" and only two could be proven.** `jobs` is empty, so the
third path is exercised by the same code but has no evidence behind it. Saying so rather than
ticking on two-thirds.

**AC5 — failure surfaces, and writes nothing.** Triggered with a non-existent id:
`Status ❌ Errored` · `Error: Failed to fetch contracts 00000000-0000-0000-0000-000000000000:
Cannot coerce the result to a single JSON object` — **the table AND the recordId are both in the
message**, and `select count(*) … source_id='00000000…'` returns **0**. No empty vector was written
as if it were fine, which is precisely what the AC demanded.

🔑 **This path had never succeeded once since it was written.** AC1 established that by DB query
(102 documents, zero carrying `source_id`); these are the first two rows it has ever produced.

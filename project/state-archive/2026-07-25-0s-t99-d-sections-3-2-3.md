**`wom7api/supabase/functions/_shared/crypto.ts`** — AES-256-GCM over Deno WebCrypto.
- Exports `encryptToken` / `decryptToken` / `EncryptedToken` + **three named error classes**:
  `MissingTokenKeyError`, `InvalidTokenKeyError`, `TokenDecryptionError`. The split is deliberate and
  operational: *"this deployment is misconfigured"* must never be reportable as *"this value failed to
  authenticate"*, or a config mistake gets triaged as data corruption.
- **Env contract:** `CONNECTOR_TOKEN_KEY_VERSION` (the version new writes use) +
  `CONNECTOR_TOKEN_KEY_V<n>` (base64 32-byte material). Versioned keys are what make section 6's
  rotation possible without a flag day — a row decrypts under the version it recorded.
- Keys resolve **lazily per call** (a missing key surfaces at the operation, not as a boot crash) and
  cache by **`version:material`**, so rotating a version's bytes in place can never serve a stale key.
- Error messages never echo the value that failed. Key import is **non-extractable**.

**`_shared/crypto.test.ts` — 18 tests, 18 passing, written BEFORE the module and proven red**
(first run: `TS2307: Cannot find module './crypto.ts'`). Beyond the five the plan required:
UTF-8 round-trip · no-plaintext-anywhere-in-the-record incl. any 8-char substring · key-version
stamping · **IV never reused** · truncated ciphertext · non-base64 key · wrong-length key · empty
token refused · unknown key version refused rather than guessed · **rotation both ways** (a v1 record
still decrypts after v2 goes current; it stops decrypting once v1's bytes change).
- 🔎 **The anti-fallback guard was proven non-vacuous:** temporarily adding an export named
  `decryptTokenOrPlaintext` turned the suite red; removing it returned 18/18. That test is the
  permanent guard for section 5's rule that the temporary fallback **must not survive**.

**Migration `20260725180000_t99_add_encrypted_token_columns.sql` — written, NOT APPLIED.**
- The 5 nullable columns, plus a **paired-nullability CHECK** the plan did not ask for: ciphertext
  without its IV is *permanently* undecryptable, and ciphertext without a key version dies at the
  first rotation. Nullable columns permit both states, so they are constrained without forcing NOT
  NULL (rows legitimately have no ciphertext until section 4 backfills).
- 🔎 **It contains no GRANT statements, deliberately.** `20260721120000` revoked *table-level* SELECT
  and re-granted an **enumerated** column list, so a column added later inherits **no** SELECT — the
  new secret columns are unreadable by `anon`/`authenticated` from the moment they exist. Because that
  property is load-bearing and invisible, the migration **asserts** it with `has_column_privilege` and
  raises if any of the 5 is readable. The standing risk it cannot fix: a later *table-level*
  `GRANT SELECT` re-exposes everything — which is exactly what task 6.3's check is for, and it must
  read `information_schema.column_privileges`, **never `pg_policy`**.

**🔴 TWO THINGS THIS CHANGES ABOUT UPCOMING WORK — read before building section 4:**
1. **The write surface is bigger than "3 call sites" implies.** `linkedin-ingest` does not only *read*
   tokens — it **writes** them on refresh (`linkedin-ingest/index.ts:327-328`, after a
   `grant_type=refresh_token` exchange). Dual-write therefore covers **two writers**
   (`linkedin-oauth` callback + `linkedin-ingest` refresh) and three readers. **A dual-write covering
   only `linkedin-oauth` would silently regress every refreshed token back to plaintext-only.**
2. **No AAD, decided deliberately** — recorded so it is not re-litigated. Binding a ciphertext to its
   row/column would stop an attacker *swapping* ciphertexts, but that needs DB **write** access,
   whereas the threat model here is **read** (compromised service-role, platform dump), against which
   AAD does nothing. Revisit only if the threat model changes.

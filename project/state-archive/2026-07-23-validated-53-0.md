### 1c. Owner schema additions — 2026-07-23 (✅ NOW FOLDED INTO THE SPEC — validated 53/0)

Owner raised these mid-session and they are **now in the OpenSpec change + design of record**
(validated strict): new **Client Organizations** requirement, clarifications on **Human Roles**
(external office-holders) and **Training Enrollment** (independent trainees), build section **1b**
in tasks.md, design-of-record §"Owner additions — 2026-07-23". Grounded against the live schema:
`clients` + `client_users` already exist (person↔client-org join), `offices` already has
`client.principal`; `units`/`team_members` are w0m-internal squads (the `resource_grants` `unit`
subject), NOT clients; the grant table itself is still unbuilt. The three:

1. **Client = an org with MULTIPLE persons.** New **Client Organizations** requirement: the `client`
   hat is backed by ≥1 `client_users` membership; a client hat with no membership is invalid. Reach =
   client-org membership (which client's projects) ∩ `resource_grants` (which capability). Client
   offices (`client.principal` vs plain client user) are ordinary grants. Wired onto the EXISTING
   `clients` + `client_users` — no parallel org model.
2. **Office-holders may be MULTIPLE + EXTERNAL.** The grant table is `resource_grants` (NOT the old
   `office_grants` draft — the spec dropped it). Class is the surface; office is the responsibility;
   **capabilities flow from the grant regardless of class**. An external client-side PM or a
   contractor `member` holds a management office and gets its scoped capabilities WITHOUT the
   internal `manager` class (holding an `is_management` office is *necessary* for `manager`, not
   sufficient). ✅ **TPM DECIDED 2026-07-23:** add a distinct **`tpm`** office (technical program
   manager, `is_management`), separate from `project.manager` and `devops` — supersedes the part of
   locked decision 1 that dropped `tpm`. In tasks.md 1.7; capability bundle to confirm at seed time.
3. **Trainee is NOT a class/kind — it's an enrollment** (locked 2026-07-22; `training_enrollments`,
   Axis 5). Any class/tier incl. pre-member `anon`. Added: a trainee may be **fully independent** —
   no `units`/`team_members`/`client_users`/employer, any email domain. (My earlier note calling it
   "a kind within member" was wrong — corrected here.)
4. **NEW class `recruit`** (Axis 1 → **six** classes; amends the five-class lock). Sits between
   `anon` and `member`/`client`: a **persistent** authenticated candidate in the join/job funnel.
   Reaches `join` + `job` + public; **no** member-side flows; **no** project/client grant
   (training-scoped only, like anon but persistent + broader read). **`cp` reach DEFERRED** —
   owner wants to see if a useful recruit cp surface emerges (default none for now). Migration:
   old guild `recruit` rows → `recruit` class (was → member+tier); an authenticated applicant
   currently sitting as `anon`/`membership_applicant` → `recruit`; `anon` keeps
   demo/consultation/pre-signup only. CHECK, invariants, diagrams, migration all updated.
